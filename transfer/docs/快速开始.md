# Transfer 模块快速开始

更新时间：2026-10-31

本文以 bounded/snapshot table Transfer 演示创建、启动和观察一次任务。任务与执行语义见[模块入口](../CLAUDE.md)，配置以[基本概念及配置说明](transfer-基本概念及配置说明.md)为准；能力与验收范围分别认定，本文不作为某一版本的运行通过记录。

## 一、启动

以下命令从仓库根目录由用户在自己的终端执行；启停、生命周期锁、进程归属和停止失败边界统一见[启动脚本指南](../../scripts/docs/启动脚本使用指南.md#启动与重启边界)。

启动基础设施：

```bash
bash scripts/infra/up.sh
```

启动 Transfer：

```bash
bash scripts/dev/start.sh -transfer
```

后端修改后重启：

```bash
./scripts/dev/restart.sh -transfer
```

核对实际 Infra 映射，并从标准启动结果读取 Transfer 的开发端口；`8083` 只是首选值，实际值见启动输出和 `.dev-state/ports.env`，规则见[端口规范](../../docs/spec/addp端口分配.md)。

```bash
bash scripts/infra/status.sh
TRANSFER_BACKEND_PORT=$(sed -n 's/^TRANSFER_BACKEND_PORT=//p' .dev-state/ports.env)
: "${TRANSFER_BACKEND_PORT:?请先核对标准启动结果和实际开发端口}"
TRANSFER_BASE_URL="http://127.0.0.1:${TRANSFER_BACKEND_PORT}"
curl --fail-with-body "${TRANSFER_BASE_URL}/health/ready"
```

就绪响应只证明该 Backend 当前满足接纳工作的条件，不证明源读、目标写、Worker 执行或业务结果正确。下文使用本地 Backend 直连；Gateway、统一 Nginx 与公开 HTTPS 入口仍需分别验证，不能以直连通过认定证书、转发和公开访问已验收，见[部署与公开入口](../../docs/spec/addp端口分配.md#前端-docker-端口规则)。

下文任务操作使用[任务表的用户任务定义入口](tables/tasks表.md#用户任务定义与控制)；`/task-provider/` 是固定 Orchestrator 服务身份的机器接口，不接受本节用户令牌与任务权限，见[机器入口](tables/tasks表.md#taskprovider-机器发现与执行)。API 前缀：

```text
/api/v1/transfer
```

## 二、创建 table Transfer 任务

下面示例展示 PostgreSQL native table 导出到 NFS CSV。源 Locator 和目标父 Locator 必须从当前有权访问的 Meta 目录／数据项结果取得，保留真实 `item_id` 或 `node_id`，不要仅替换示例 Engine ID 后猜测路径；规则见[资源定位规范](../../docs/spec/addp存储引擎路径体系规范.md#四resourcelocator-路径规则)。示例字段、类型和空间字段名也须按真实源结构调整，不能默认存在 `geom`。`replace` 会替换所选目标，执行前须核对目标路径和写入效果。

业务请求使用正式用户授权流程取得、绑定当前 Tenant 的短期 opaque User Access Token，放在当前终端的 `TOKEN` 变量中；不在文档、文件或命令字面值中保存令牌，不从 CLI Keychain 导出凭据，认证规则见[用户认证](../../docs/spec/api/认证授权.md#认证方式)。此 encoded target 示例不属于 Agent 委托创建的 native-table 范围，也不使用模块 Service Token 冒充用户。

创建要求 `transfer.task.create`，读取任务／执行要求 `transfer.task.read`，启动与重试要求 `transfer.task.execute`；运行还须当前用户的 `system.execution_authorization.create` 及本次源读、目标写等效果资格，不能用任务创建权替代。各动作与精确权限统一见[任务表 API](tables/tasks表.md#用户任务定义与控制)，独立动作、角色保护与 Owner 校验见[模块契约](../CLAUDE.md#核心-api)。

```bash
: "${TOKEN:?请先通过正式用户授权取得当前 Tenant 的短期 User Access Token}"
```

注意：Transfer 当前接口层只保留 `task_type=sync`。导入、导出是 Manager 等调用方的用户动作语义，不作为 Transfer 任务类型并行暴露。

```bash
curl --fail-with-body -X POST "${TRANSFER_BASE_URL}/api/v1/transfer/task-definitions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "道路表导出 CSV",
    "description": "从 PostgreSQL native table 导出到 NFS CSV",
    "task_type": "sync",
    "batch_size": 10000,
    "schedule": "",
    "enabled": false,
    "auto_scan_metadata": true,
    "config": {
      "runtime": {"boundary": "bounded"},
      "load": {"mode": "snapshot"},
      "source": {
        "locator": "addp://engine/1/path/public/roads?type=table&item_id=101",
        "data_type": "table",
        "representation": "native"
      },
      "target": {
        "parent_locator": "addp://engine/2/path/exports?type=directory&node_id=201",
        "name": "roads.csv",
        "data_type": "table",
        "representation": "encoded",
        "format": "csv",
        "options": {"header": true},
        "policy": {"apply_mode": "replace"}
      },
      "transforms": [
        {
          "type": "field_mapping",
          "version": "v1",
          "mode": "project",
          "fields": [
            {"source": "id", "target": "id", "target_type": "bigint"},
            {"source": "name", "target": "road_name", "target_type": "string"},
            {"source": "geom", "target": "geometry", "target_type": "geometry"}
          ]
        }
      ],
      "batch_size": 10000
    }
  }'
```

### 启动与观察执行

创建成功只保存任务定义，不表示已执行。将创建响应的整数 `id` 填入 `TASK_ID`；确认本次运行效果后，通过任务表中的 `POST /task-definitions/:id/start` 启动：

```bash
: "${TASK_ID:?请填写创建响应中的任务 id}"
```

```bash
curl --fail-with-body -X POST "${TRANSFER_BASE_URL}/api/v1/transfer/task-definitions/${TASK_ID}/start" \
  -H "Authorization: Bearer $TOKEN"
```

将启动响应的 UUID 字段 `execution_id` 填入 `EXECUTION_ID`，不要使用响应中的内部整数 `id`。返回 execution 不等于执行成功，可先查询任务的执行列表：

```bash
curl --fail-with-body "${TRANSFER_BASE_URL}/api/v1/transfer/task-definitions/${TASK_ID}/executions" \
  -H "Authorization: Bearer $TOKEN"
```

查看本次执行进度：

```bash
: "${EXECUTION_ID:?请填写启动响应中的 execution_id UUID}"
```

```bash
curl --fail-with-body "${TRANSFER_BASE_URL}/api/v1/transfer/executions/${EXECUTION_ID}/progress" \
  -H "Authorization: Bearer $TOKEN"
```

查看运行过程事件（`EXECUTION_ID` 为执行记录的 UUID）：

```bash
curl --fail-with-body "${TRANSFER_BASE_URL}/api/v1/transfer/executions/${EXECUTION_ID}/events?after=0&limit=100" \
  -H "Authorization: Bearer $TOKEN"
```

### 暂停与恢复定时调度

本例 `schedule=""` 是手动 bounded 任务，不能调用 pause/resume；Owner 会拒绝无调度的暂停或恢复。以下示例仅适用于另一个已配置合法 Cron 的 bounded 定时任务：先按[任务表入口](tables/tasks表.md#用户任务定义与控制)读取并核对当前 Tenant、任务配置与调度状态，将其整数 ID 放入 `SCHEDULED_TASK_ID`，并确认后续运行的源读与目标写效果。

暂停要求 `transfer.task.update`，只关闭后续调度，不中断已有 pending/running execution：

```bash
: "${SCHEDULED_TASK_ID:?请填写已核对的 bounded 定时任务 id，勿使用本例无调度的 TASK_ID}"
curl --fail-with-body -X POST "${TRANSFER_BASE_URL}/api/v1/transfer/task-definitions/${SCHEDULED_TASK_ID}/pause" \
  -H "Authorization: Bearer $TOKEN"
```

确需恢复这个已暂停任务的后续调度时，仍使用当前 Tenant 的用户令牌和 `transfer.task.update`，并重新校验 `transfer.task.execute`、`system.execution_authorization.create` 等调度授权条件；不能借用暂停前的主体。授权与原子更新规则统一见[Transfer 定时任务授权](../../docs/spec/tasks/任务定义与授权.md#transfer-定时任务授权)。

```bash
curl --fail-with-body -X POST "${TRANSFER_BASE_URL}/api/v1/transfer/task-definitions/${SCHEDULED_TASK_ID}/resume" \
  -H "Authorization: Bearer $TOKEN"
```

bounded resume 成功只表示恢复未来调度与授权主体，不立即创建新 execution，也不从当前执行的 checkpoint 续写；已有执行的配置、状态与发起主体保持不变。通过任务详情核对调度状态，再按任务执行列表核对后续实际触发结果，不能从成功响应认定运行或断点恢复通过。

continuous 的 pause/resume 属于运行控制，恢复使用新 execution 并遵守已提交位置与 CDC 阻塞等约束；本节不提供 continuous 操作示例，统一见[任务表执行与恢复边界](tables/tasks表.md#执行恢复与验收边界)。

## 三、常见任务形态

下列形态复用第二章的[完整任务请求](#二创建-table-transfer-任务)，只调整 `config`。三种形态均使用 bounded/snapshot、`data_type=table`，`target.policy.apply_mode=replace` 及覆盖效果仍按[写入策略](transfer-基本概念及配置说明.md#六写入策略)核对；公共字段、批大小、真实源与目标父 Locator 见[顶层字段](transfer-基本概念及配置说明.md#21-顶层字段)和[Endpoint 字段](transfer-基本概念及配置说明.md#22-endpoint-字段)。单资源 encoded source 的字段核对及失败边界见[单资源结构核对](transfer-基本概念及配置说明.md#单资源结构核对)。

### 3.1 encoded file/object 导入 native table

Parquet 单文件使用 `source.representation=encoded`、`source.format=parquet`，目标使用 `representation=native`，以真实 schema 的 `parent_locator` 和目标 `name` 定位写入。单文件与 whole scope 数据集必须按 Meta 已确定的 layout 选择读取入口，不能因格式支持目录读取就把单文件当作目录；读取形态及原生目标约束见[读取布局与入口](transfer-基本概念及配置说明.md#读取布局与入口)和[Native table target](transfer-基本概念及配置说明.md#34-native-table-target)。

### 3.2 encoded object 到 encoded object

CSV 读取后写出 Parquet 时，两端均为 `representation=encoded`，源 `format=csv`、目标 `format=parquet`；这是 table 格式转换，不是 raw copy。CSV 源的 `source.options.header=true` 表示有表头，表头选项优先级以[CSV 与 TSV 表头](transfer-基本概念及配置说明.md#csv-与-tsv-表头)为准；Parquet 的 `target.options.compression`、默认值及允许 codec 统一见[Parquet 列式压缩](transfer-基本概念及配置说明.md#parquet-列式压缩)。

### 3.3 Shapefile multi refs

Shapefile 作为 `data_type=table + format=shapefile + layout=multi` 进入 table Transfer。source 已入库时，使用 source locator 的 `item_id`，由 Transfer 从 Meta attributes 读取已确认 refs。完整 refs 不能以单个 `.shp` 文件替代，来源与布局规则见[读取布局与入口](transfer-基本概念及配置说明.md#读取布局与入口)。

写入 native table 时须保留空间字段与 CRS 事实；Transfer 不隐式转换 CRS，细节见[空间字段与 CRS 边界](transfer-基本概念及配置说明.md#35-空间字段与-crs-边界)。

这些 encoded 源／目标形态不属于仅允许 native table 到 native table 的 Agent 委托创建范围。操作仍逐项核对[用户身份与权限](#二创建-table-transfer-任务)；支持矩阵、配置示例或格式回归不等于真实源读、目标写和保护链路已通过，结果认定沿用[开发验证](#五开发验证)。

## 四、Checkpoint 和重试

本节只演示上述 bounded/snapshot 任务的失败重试：restartable retry 创建新的 execution 并从头执行，append 拒绝重试；snapshot checkpoint 仅供观测，不代表断点续写。字段口径与 provider marker 统一见[Checkpoint、进度和重试](transfer-基本概念及配置说明.md#十checkpoint进度和重试)。

watermark incremental 的跨 execution resume 另有源能力、稳定键与目标幂等条件，统一见[增量同步契约](transfer-基本概念及配置说明.md#七watermark-bounded-incremental)；这与[bounded 定时任务的调度恢复](#暂停与恢复定时调度)是不同动作，不据此扩大本节 snapshot 的恢复范围。执行与恢复入口分工统一见[任务表](tables/tasks表.md#执行恢复与验收边界)。

仅对 Owner 允许重试的失败 execution 操作；`EXECUTION_ID` 必须是该失败执行的 UUID，成功返回新的 `execution_id`，后续观察切换到新 UUID：

```bash
curl --fail-with-body -X POST "${TRANSFER_BASE_URL}/api/v1/transfer/executions/${EXECUTION_ID}/retry" \
  -H "Authorization: Bearer $TOKEN"
```

## 五、开发验证

测试和构建不要求重启个人开发服务。从仓库根目录使用标准 Owner 门禁：

```bash
make test-module MODULE=transfer
```

门禁分层、隔离数据库和共享依赖扩散见[测试与验收规范](../../docs/spec/addp测试与验收规范.md#三标准入口)，固定版本证据、失败与修复结论、未覆盖项见[模块验证](../CLAUDE.md#开发与验证)。未运行、失败或跳过项分别记录，不计为通过；确定性回归不替代真实 System → Gateway → Owner／Worker 链路和目标数据核对。启动、调度暂停／恢复、snapshot 重跑和增量续读须分别验收，本文示例与静态路由核对不代表这些链路已通过。

确需加载新代码时，由用户按[启动脚本指南](../../scripts/docs/启动脚本使用指南.md#选择操作)重启受影响模块；`common/` 改动需要运行验收时重启全套，停止失败不得继续启动。健康检查、任务创建成功和执行结束分别认定，仍须核对终态、记录数、目标内容及相应权限和保护断言。
