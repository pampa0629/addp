# Transfer 模块配置中心集成说明

## 修改内容

### 1. 移除本地配置文件

已删除以下文件：
- `transfer/backend/.env`
- `transfer/backend/.env.example`

**原因**: Transfer 模块已实现配置中心模式，从 System 模块获取共享配置，无需本地 `.env` 文件。

### 2. 更新启动脚本

修改 `scripts/dev-start.sh`，移除了创建 `.env` 文件的逻辑：

**修改前**:
```bash
# 检查 .env 配置
if [ ! -f "transfer/backend/.env" ]; then
  echo -e "${YELLOW}⚠ transfer/backend/.env 不存在，正在创建...${NC}"
  cp transfer/backend/.env.example transfer/backend/.env
  echo -e "${GREEN}✓ .env 文件已创建${NC}"
  echo -e "${YELLOW}  请检查并修改 transfer/backend/.env 中的配置（特别是 INTERNAL_API_KEY）${NC}"
fi
```

**修改后**:
```bash
# 直接启动，无需检查本地 .env
(cd transfer/backend && go run cmd/server/main.go) 2> logs/transfer-backend-stderr.log &
```

### 3. 新增配置文档

创建 `transfer/backend/CONFIG.md`，详细说明：
- 配置中心模式工作原理
- 配置来源（System vs 环境变量）
- 配置加载流程
- 开发和生产环境配置方式
- 故障排除指南

### 4. 更新 README

在 `transfer/README.md` 中新增「配置说明」章节，说明：
- Transfer 采用配置中心模式
- 共享配置从 System 获取
- 模块特有配置通过根目录 `.env` 设置
- 不使用本地 `.env` 文件

### 5. 更新根目录配置模板

更新 `.env.example`，完善 Transfer 模块配置项：
- `WORKER_COUNT` - Worker 进程数量
- `CONCURRENT_TASKS` - 并发任务数量
- `TASK_QUEUE_NAME` - Redis 任务队列名称
- `MAX_RETRIES` - 最大重试次数
- `RETRY_DELAY` - 重试延迟
- `DEFAULT_BATCH_SIZE` - 默认批处理大小
- `TASK_TIMEOUT` - 任务执行超时时间

## 配置方式对比

### 修改前（错误）

```
项目根目录/.env         ← 部分配置
transfer/backend/.env   ← Transfer 特有配置（冗余）
   ↓
容易造成配置分散、难以维护
```

### 修改后（正确）

```
项目根目录/.env         ← 所有模块配置统一管理
   ↓
Transfer 从 System 获取共享配置
Transfer 从环境变量获取特有配置
   ↓
配置集中、易于维护、符合微服务最佳实践
```

## 配置加载流程

```
1. Transfer 启动
   ↓
2. 加载项目根目录 .env (通过 commonConfig.LoadEnv(3))
   ↓
3. 读取 Transfer 特有配置（PORT, DB_SCHEMA, Redis 等）
   ↓
4. 调用 System /internal/config 接口获取共享配置
   ↓
   ├─ 成功 ✅
   │  └─ 使用 System 返回的 JWT_SECRET, DB 连接, INTERNAL_API_KEY
   │
   └─ 失败 ⚠️
      └─ 回退到环境变量中的 fallback 配置
```

## 与其他模块的一致性

| 模块 | 本地 .env | 配置中心 | 状态 |
|------|----------|---------|------|
| System | ❌ | N/A (配置提供者) | ✅ |
| Manager | ❌ | ✅ | ✅ |
| Meta | ❌ | ✅ | ✅ |
| Transfer | ❌ | ✅ | ✅ (本次修复) |

所有模块现在都遵循统一的配置管理模式。
