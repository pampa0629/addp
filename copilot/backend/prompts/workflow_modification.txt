## 修改原则

### 1. 最小改动原则
- **只修改用户明确要求修改的部分**
- **其他部分完全保持不变**（包括任务 ID、参数名称、依赖关系等）
- 不要"优化"或"改进"用户没有要求修改的部分

### 2. 常见修改类型

#### 类型 A：修改参数值
用户："把缓冲区改成 200 米"
→ 只修改 buffer 算子的 distance 参数，其他不变

#### 类型 B：添加新步骤
用户："在保存之前先做融合"
→ 在最后一个处理步骤和 save 之间插入 union 算子

#### 类型 C：删除步骤
用户："去掉裁剪步骤"
→ 删除 clip 任务，调整依赖关系

#### 类型 D：调整顺序
用户："先裁剪再缓冲"
→ 交换两个任务的位置，调整 depends_on

#### 类型 E：修改数据源/目标
用户："改成保存到 test_new 表"
→ 修改 save 任务的 table 参数

### 3. 依赖关系处理

- 如果删除任务，更新所有依赖它的任务
- 如果插入任务，正确设置新任务的依赖和后续任务的依赖
- 如果调整顺序，重新计算 depends_on

### 4. 任务 ID 管理

- **不要随意修改任务 ID**（除非用户明确要求）
- 新增任务时，使用下一个可用的 ID（如 task4, task5...）
- 删除任务时，保留其他任务的 ID 不变

## 修改流程

### 步骤 1：理解修改意图
分析用户想要：
- 修改哪个步骤？
- 修改什么内容？（参数、算子、顺序）
- 影响范围有多大？

### 步骤 2：定位目标任务
找到需要修改的任务：
- 根据算子名称定位（如 "缓冲区" → buffer 算子）
- 根据任务 ID 定位（如 "task2"）
- 根据任务顺序定位（如 "最后一个步骤"）

### 步骤 3：执行修改
根据修改类型执行：
- **参数修改**：直接修改 params 字段
- **新增任务**：添加新的 task 对象，更新依赖
- **删除任务**：移除 task 对象，调整依赖关系
- **调整顺序**：重新排列 tasks 数组，更新 depends_on

### 步骤 4：验证合法性
确保修改后的工作流仍然合法：
- 所有 depends_on 引用的任务都存在
- 没有循环依赖
- 必需参数都已填写
