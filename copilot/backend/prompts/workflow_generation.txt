## 任务要求

请生成一个完整的工作流 JSON，遵循以下原则：

### 0. 简化原则（最重要）
- **不是所有筛选出的算子都必须使用**：只使用真正需要的算子
- **优先简单直接**：能用更少的步骤完成就不要增加不必要的算子
- **数据复制场景**：如果只是简单的表复制（如"把 A 表复制为 B 表"），只需要 load → save 两步即可，不需要 sql 算子
- **sql 算子使用场景**：只在需要复杂查询、数据过滤、字段筛选时才使用 sql 算子
- **举例**：
  - ❌ 错误：load → sql(SELECT * FROM table) → save（多余的 sql）
  - ✅ 正确：load → save（简单直接）

### 1. 工作流结构
- 每个任务必须有唯一的 ID（task1, task2, task3...）
- 每个任务指定一个算子（operator）
- 每个任务提供完整的参数（params）
- 正确设置任务依赖关系（depends_on）

### 2. 参数填写规则
- **仔细参考每个算子的 `workflow_example`**：这是最重要的参考！
- **必需参数**：确保所有 required=true 的参数都填写
- **参数类型**：严格按照算子定义的类型填写（字符串、数字、布尔值、数组、对象）
- **参数引用（重要）**：
  - 引用前驱任务输出：使用 `{{"$ref": "task_id"}}` 格式（对象格式，不是字符串！）
  - ✅ 正确：`"input_df": {{"$ref": "task1"}}`
  - ❌ 错误：`"input_df": "{{task1}}"` 或 `"input_df": "{{{{task1}}}}"`
  - 第一个 load 任务的参数直接从数据源信息获取（engine_id、schema、table 等）
  - 最后一个 save 任务的参数指定保存位置

### 3. 依赖关系
- load 任务通常没有依赖（depends_on 为空数组）
- 处理任务依赖 load 任务或其他处理任务
- save 任务依赖最后一个处理任务
- 确保依赖的 task_id 存在于工作流中

### 4. 常见模式

**模式 1：简单 ETL（提取-转换-加载）**
```
load（读取数据）→ process（处理）→ save（保存）
```

**模式 2：多步骤处理**
```
load → process1 → process2 → process3 → save
```

**模式 3：并行处理后合并**
```
load → process1 ┐
              → merge → save
load2 → process2 ┘
```

### 5. 算子 workflow_example 的重要性

每个算子的 `workflow_example` 字段提供了该算子在工作流中的标准用法，包括：
- 参数的正确格式
- 如何引用前驱任务的输出
- 常见的参数组合

**务必仔细参考这些示例！**

## 重要提示

1. **只返回 JSON 格式**，不要有任何其他内容或解释
2. **所有参数名称必须与算子定义完全一致**（区分大小写）
3. **任务 ID 必须唯一**，格式为 task1, task2, task3...

选定的算子是 load、buffer、save。

正确的工作流 JSON：
```json
{{
  "tasks": [
    {{
      "id": "task1",
      "operator": "load",

        "table": "test"

        "schema": "public",
        "table": "test_buffer",
        "mode": "replace"
      }},
      "depends_on": ["task2"]
    }}
  ],

    "description": "读取 test 表，计算 100 米缓冲区，保存为 test_buffer"
  }}
```
