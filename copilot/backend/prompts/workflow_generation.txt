## 任务要求

请生成一个完整的工作流 JSON，遵循以下原则：

### 0. 简化原则（最重要）
- **不是所有筛选出的算子都必须使用**：只使用真正需要的算子
- **优先简单直接**：能用更少的步骤完成就不要增加不必要的算子
- **数据复制场景**：如果只是简单的表复制（如"把 A 表复制为 B 表"），只需要 load → save 两步即可，不需要 sql 算子
- **sql 算子使用场景**：只在需要复杂查询、数据过滤、字段筛选时才使用 sql 算子
- **举例**：
  - ❌ 错误：load → sql(SELECT * FROM table) → save（多余的 sql）
  - ✅ 正确：load → save（简单直接）

### 1. 工作流结构
- 每个任务必须有唯一的 ID（task1, task2, task3...）
- 每个任务指定一个算子（operator）
- 每个任务提供完整的参数（params）
- 正确设置任务依赖关系（depends_on）；每个任务都必须显式包含 `depends_on`，没有依赖时写空数组 `[]`

### 2. 参数填写规则
- **仔细参考每个算子的 `workflow_example`**：这是最重要的参考！
- **必需参数**：确保所有 required=true 的参数都填写
- **参数类型**：严格按照算子定义的类型填写（字符串、数字、布尔值、数组、对象）
- **参数引用（重要）**：
  - 引用前驱任务输出：使用 `{{"$ref": "task_id"}}` 格式（对象格式，不是字符串！）
  - ✅ 正确：`"input_df": {{"$ref": "task1"}}`
  - ❌ 错误：`"input_df": "{{task1}}"` 或 `"input_df": "{{{{task1}}}}"`
- **⭐ 数据源参数（非常重要）**：
  - 读取已有表、文件或对象时，load 任务必须使用 `locator`
  - 创建新目标时，save 任务必须使用 `target_parent_locator + target_name`
  - `source_type` / `target_type` 表达访问形态，只能使用 `table`、`file`、`geojson` 等算子定义中的枚举值，不能使用 `nfs`、`minio`、`s3` 等存储引擎类型
  - **禁止在算子 params 中填写 `engine_id`、`connection_info`、`schema`、`table`、`path`**，这些是 Develop Backend 执行前派生的运行时参数
  - 如果"数据源信息"提供了"源资源 locator"，第一个 load 任务直接使用该 locator，不要自己编造
  - 如果"数据源信息"提供了"目标父 locator"，save 任务使用该 locator；目标名称从用户需求中提取，无法确定时使用清晰的候选名称
  - 如果没有提供 locator，不要自行拼接 `addp://...`，应只生成不依赖数据源的处理步骤或在 metadata 中标注需要用户补充资源选择

### 3. 依赖关系
- load 任务通常没有依赖（depends_on 为空数组）
- 处理任务依赖 load 任务或其他处理任务
- save 任务依赖最后一个处理任务
- 确保依赖的 task_id 存在于工作流中

### 4. 常见模式

**模式 1：简单 ETL（提取-转换-加载）**
```
load（读取数据）→ process（处理）→ save（保存）
```

**模式 2：多步骤处理**
```
load → process1 → process2 → process3 → save
```

**模式 3：并行处理后合并**
```
load → process1 ┐
              → merge → save
load2 → process2 ┘
```

### 5. 算子 workflow_example 的重要性

每个算子的 `workflow_example` 字段提供了该算子在工作流中的标准用法，包括：
- 参数的正确格式
- 如何引用前驱任务的输出
- 常见的参数组合

## 重要提示

1. **只返回 JSON 格式**，不要有任何其他内容或解释
2. **所有参数名称必须与算子定义完全一致**（区分大小写）
3. **任务 ID 必须唯一**，格式为 task1, task2, task3...
4. **依赖关系必须正确**，不能有循环依赖
5. **参数引用格式**：使用对象格式 `{{"$ref": "task_id"}}`，不要使用字符串模板
6. **第一个任务通常是 load**，最后一个任务通常是 save
7. **参考 workflow_example**：这是最可靠的参数填写参考！

## 示例

假设用户需求是"读取 test 表，计算 100 米缓冲区，保存为 test_buffer"，
数据源是 PostgreSQL，源资源 locator 为 `addp://engine/1/path/public/test?type=table`，目标父 locator 为 `addp://engine/1/path/public?type=schema`，
选定的算子是 load、buffer、save。

正确的工作流 JSON：
```json
{{
  "tasks": [
    {{
      "id": "task1",
      "operator": "load",
      "params": {{
        "source_type": "table",
        "locator": "addp://engine/1/path/public/test?type=table"
      }},
      "depends_on": []
    }},
    {{
      "id": "task2",
      "operator": "buffer",
      "params": {{
        "input_gdf": {{"$ref": "task1"}},
        "distance": 100,
        "unit": "meters"
      }},
      "depends_on": ["task1"]
    }},
    {{
      "id": "task3",
      "operator": "save",
      "params": {{
        "input_df": {{"$ref": "task2"}},
        "target_type": "table",
        "target_parent_locator": "addp://engine/1/path/public?type=schema",
        "target_name": "test_buffer",
        "mode": "replace"
      }},
      "depends_on": ["task2"]
    }}
  ],
  "metadata": {{
    "description": "读取 test 表，计算 100 米缓冲区，保存为 test_buffer"
  }}
}}
```
