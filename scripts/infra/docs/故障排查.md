# ADDP Infra：故障排查

[返回 Infra 指南](../README.md)

## 常见问题

### Q: 为什么 down.sh 删除了 business 容器？

标准 `down.sh` 按 `docker-compose.infra.yml` 的 `addp-infra` 项目取得待停止容器，并核对 Compose 工作目录；Business 由独立 `business` 项目管理。若 Business 容器进入待停止范围，先取消操作，核对项目配置、容器标签和执行所在工作区，不通过 `--force` 继续。

Business Compose 应声明 `name: business`。容器名称只用于识别，不能代替项目、服务和工作区归属核验。

### Q: 如何确认只操作 addp 容器？

```bash
bash scripts/infra/status.sh
```

容器状态表按 `com.docker.compose.project=addp-infra` 筛选，当前核心服务见[容器清单](部署与项目隔离.md#管理的容器addp-)；启用日志或指标后还会有对应可选设施。完整输出可能包含单独的 Business PostgreSQL replication slot 只读诊断，不表示 Infra 接管该业务容器。

需要核对具体容器时，检查项目、服务及工作目录标签，例如 PostgreSQL：

```bash
docker inspect --format '{{index .Config.Labels "com.docker.compose.project"}} | {{index .Config.Labels "com.docker.compose.service"}} | {{index .Config.Labels "com.docker.compose.project.working_dir"}}' addp-postgres
```

预期项目为 `addp-infra`、服务为 `postgres`、工作目录为当前仓库绝对路径；不同工作区的同名容器不能接管。

### Q: 如何完全清理并重建？

先核验可恢复备份和当前项目的数据范围。普通 `down.sh` 保留数据卷；下列删除操作需按[本地交互确认规则](部署与项目隔离.md#执行顺序)执行，`--force` 不跳过数据卷删除确认。

```bash
# 1. 停止并删除所有数据（警告：数据丢失）
bash scripts/infra/down.sh -v

# 2. 重新启动
bash scripts/infra/up.sh
```

删除数据卷会丢失当前 Infra 项目拥有的持久数据，包括 PostgreSQL 数据库、Redis 状态、FalkorDB 投影、MinIO 文件、当前 Meilisearch 索引、Kafka 日志，以及已部署的日志/指标设施持久状态。恢复范围见[备份与隔离恢复](备份恢复与搜索迁移.md#本地-infra-备份与隔离恢复演练)，不能把普通备份成功视为所有数据均可恢复。

### Q: 如何单独重启某个服务？

```bash
# 重启 PostgreSQL
docker compose -f docker-compose.infra.yml restart postgres

# 重启 Redis
docker compose -f docker-compose.infra.yml restart redis

# 重启 MinIO
docker compose -f docker-compose.infra.yml restart minio

# 重启 Meilisearch
docker compose -f docker-compose.infra.yml restart meilisearch
```

## 故障排查

### PostgreSQL 连接失败

```bash
# 先核实 Infra 归属、实际端口和健康状态
bash scripts/infra/status.sh

# 查看当前 Compose 服务日志
docker compose -f docker-compose.infra.yml logs --tail=100 postgres

# 使用容器中的实际数据库用户名与库名连接
docker compose -f docker-compose.infra.yml exec postgres sh -c 'exec psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

### Redis 连接失败

```bash
bash scripts/infra/status.sh
docker compose -f docker-compose.infra.yml logs --tail=100 redis

# 交互输入实际部署密码
docker compose -f docker-compose.infra.yml exec redis redis-cli --askpass ping
```

### MinIO 连接失败

先用状态输出中的实际 Console 映射端口打开控制台；`19001` 只是首选值。

```bash
bash scripts/infra/status.sh
docker compose -f docker-compose.infra.yml logs --tail=100 minio
```

### Meilisearch 连接失败

当前源码固定 Meilisearch `1.54.3`、Go SDK `0.36.3`。Manager 新文档投递必须使用 `customMetadata` 并关闭自动重试；旧服务仍可运行其他模块，但 Manager 搜索保持隔离，不退回无标记写入。

已有 `1.7.6` 持久卷**不得只改镜像后重启**。[官方迁移指南](https://www.meilisearch.com/docs/resources/migration/updating) 明确 `--upgrade-db` 不支持低于 `1.12` 的数据库，因此需先确认 dump 迁移及恢复步骤：停止各 Owner 写入，保留旧版本可启动的卷备份与任务历史，核查 Manager 持久投递；备份验证成功后才在独立新卷导入并验证三个 Owner。任务身份／历史必须逐项验证，不能假定 dump 保留原回执或把编号复用当作成功。尚无编号的旧提交若无法证明收敛，保持隔离；受控重建另行确认。普通启动入口不得代替显式授权的迁移操作。

当前 Compose 固定 `1.54.3` 的多架构 registry digest，唯一挂载命名卷 `meilisearch_data_v1543`（默认物理名称 `addp-infra_meilisearch_data_v1543`）。旧物理卷 `addp-infra_meilisearch_data` 不再被当前 Compose 引用；它和原镜像保留作回滚，不删除、不改名，也不由新版本打开。正式迁移只操作 Meilisearch 服务，不启动或重启 ADDP 应用。尚待完成的 Owner 与故障验收见[企业资源目录能力专题](../../../docs/next/ADDP企业资源目录能力专题.md)。

普通 `infra/up.sh` 在构建／拉取／启动容器之前，必须核对当前工作区已有 Meilisearch 容器与 Compose 所选镜像的实际 Image ID；不同、归属不明或身份无法核实均拒绝自动替换，不能把 `docker compose up -d` 的幂等性当作数据库可升级证明。该检查保护仍保留原容器的环境，不证明脱离容器的历史卷可以直接使用；删除旧容器不能代替迁移。应用 `restart.sh` 可能间接调用该入口，因此目标隔离导入成功后仍须先完成正式新卷导入、验收与切换，不能直接全量重启完成升级。

应用恢复与搜索迁移分开：当前核心 Infra 健康时，开发启动入口直接复用现有容器，不调用 Infra 构建或 Compose 更新，也不应用搜索镜像变化；核心 Infra 未就绪时才调用 `up.sh`，若上述替换被拒绝但核心已健康，仍可继续启动应用。旧搜索容器／卷不动；Manager 搜索继续隔离，不退回无标记投递。此行为只允许恢复其他功能，不表示新版本搜索已可用，也不替代正式迁移、当前保护核验或完整应用启动验收。

新建无历史数据的部署直接使用固定版本；Owner 初始化和恢复单测通过，不等于现有开发卷已迁移，也不等于真实故障 T4 通过。

具体执行阶段、冻结条件、任务身份对账与回滚边界见[旧 Meilisearch 卷迁移与回滚](备份恢复与搜索迁移.md#旧-meilisearch-卷迁移与回滚)。`make infra-backup` **默认不包含 Meilisearch**；仅显式传入既有成功 dump 和任务 UID 时收录，不能以 PostgreSQL／MinIO 备份成功代替搜索恢复验证。实际 dump、停服、迁移导入及卷切换须另行确认操作窗口；普通 `up.sh` 不是旧索引卷迁移入口。

```bash
bash scripts/infra/status.sh
docker compose -f docker-compose.infra.yml logs --tail=100 meilisearch

# 在容器内部使用固定服务端口检查；宿主机连接使用状态输出的实际映射
docker compose -f docker-compose.infra.yml exec -T meilisearch curl -fsS http://localhost:7700/health
```

### 端口被占用

本地首次映射遇到端口占用时，标准入口会选择空闲端口；已经运行且归属当前工作区的容器复用实际映射。Online 专用 Runner 使用显式端口，冲突时失败，不自动改选；本地可选范围耗尽、归属不符或实际绑定遇到并发抢占也会失败。

先对照启动报错和以下只读输出确认监听者，不能仅按端口号认定服务归属：

```bash
bash scripts/infra/status.sh
lsof -nP -iTCP -sTCP:LISTEN
```

确认占用进程由谁管理后，使用其所属服务的标准入口处理。需要调整 Infra 首选端口时修改对应根 `.env` 部署字段，再由部署方沿标准生命周期生效；已有运行映射不会因此自动迁移。完整规则见[端口分配规范](../../../docs/spec/addp端口分配.md#system-addp-基础设施)，运行连接与测试 DSN 始终使用已核实的实际端口。
