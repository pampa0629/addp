## 脚本说明

### 核心管理

- **up.sh** - 启动 ADDP 基础设施
  ```bash
  bash scripts/infra/up.sh
  ```

- **down.sh** - 停止并删除本工作区 Infra 容器，默认保留持久数据卷
  ```bash
  bash scripts/infra/down.sh           # 保留数据卷
  bash scripts/infra/down.sh -v        # 交互输入确认短语后删除数据卷
  bash scripts/infra/down.sh --force   # 仅跳过非 ADDP 容器确认
  ```

- **status.sh** - 查看基础设施状态
  ```bash
  bash scripts/infra/status.sh
  ```

<a id="初始化由-upsh-自动调用"></a>

### 初始化与独立检查

- **init-postgresql.sh** - 初始化 PostgreSQL（保留测试库、扩展、开发库 Schema）
- **init-minio.sh** - 初始化 MinIO buckets
- **init-meilisearch.sh** - 校验 Meilisearch API 健康
- **init-redpanda.sh** - 由 `redpanda-init` 一次性服务执行，初始化 SCRAM 用户、Kafka Connect internal topics 和 infra principal ACL；`VERIFY_ACL=1` 时执行临时 topic 权限验收

前三项由 `up.sh` 按跳过开关调用；Redpanda 初始化随核心 Compose 服务执行。`init-redis.sh` 是独立的缓存、事件和分布式锁状态检查入口，不由当前 `up.sh` 自动调用，使用见[手动初始化脚本](#手动初始化脚本)。

## 脚本设计原则

1. **单一职责**: 同样功能只在一处实现,其他地方调用
2. **适应性**: 适应不同环境(OS、CPU架构),脚本自动适配
3. **清晰明了**: 一看就懂的结构和命名
4. **可重复执行**: 按各脚本约定复用或应用资源；配置变更、初始化、停用和删除分别遵循对应契约
5. **易用性**: 用户无需了解技术细节,按顺序执行即可
6. **分散和集中**: 模块相关配置分散,整体管理脚本集中
7. **敢于删除**: 删除重复或无用的内容,避免违反单一职责原则

## 目录结构

下列仅列主要入口与关键支撑文件，具体配置和分层实现按对应专题查阅。

```
scripts/infra/
├── README.md                        # Infra 指南总入口
├── docs/                            # 本文及部署、初始化、观测专题
├── up.sh                            # 核心设施与可选观测的标准启动
├── down.sh                          # 来源停用、发现撤销与 Infra 下线
├── status.sh                        # 状态读取、健康探测及条件式日志投递探针
├── ports.sh                         # 标准生命周期的端口解析与容器归属核验
├── init-postgresql.sh               # 准备 HBA、测试库、扩展与开发 Schema
├── init-minio.sh                    # 模块桶创建及 manager 策略应用
├── init-redis.sh                    # 独立连接与统计检查；可显式选择清理
├── init-meilisearch.sh              # 校验 API 健康，不创建业务索引
├── init-redpanda.sh                 # 一次性服务的用户、internal topics 与 ACL 准备
├── metrics-sources.py               # 按作用域与类型统一管理采集来源
├── host-metrics.sh                  # 委托统一入口管理主机 node 来源
├── generate-metrics-config.py       # 指标中心配置生成与预检
├── generate-trace-config.py         # Trace 配置生成及显式本机部署材料准备
├── init-runtime-log-store.sh        # 一次性服务的日志桶、账号与 Loki 卷权限准备
└── init-trace-store.sh              # 一次性服务的 Trace 桶、账号与 WAL 卷权限准备
```

采集来源的作用域、恢复与实际采样核验见[统一采集管理](指标中心与来源.md#统一采集管理)。日志设施与一次性存储准备见[运行日志专题](运行日志.md#模块实例运行日志)，Trace 接线和本机材料准备见[日志链路与 Trace 部署](运行日志.md#日志链路与-trace-部署)。配置生成或存储准备成功不代表能力已启用，也不替代投递、采样和业务链路验收。

## 使用方法

### 快速启动（推荐）

```bash
# 1. 启动基础设施（按配置和跳过开关执行初始化／检查）
./scripts/infra/up.sh

# 2. 查看状态
./scripts/infra/status.sh

# 3. 停止基础设施
./scripts/infra/down.sh
```

镜像准备、核心设施检查、初始化与可选观测的处理范围见下文 [up.sh 说明](#upsh)。基础设施启动不替代应用模块启动与业务验收。

### 通过 Makefile（推荐）

```bash
# 按配置启动 Infra 并执行检查
make infra-up

# 查看状态，并按条件运行日志投递探针
make infra-status

# 下线 Infra 容器，默认保留持久数据卷
make infra-down

# 创建模块桶，并尝试应用 manager 桶策略
make init-minio

# 检查 Redis 连接与统计，默认不清理数据
make init-redis
```

这些目标只委托对应脚本，不增加初始化或验收逻辑。启动、下线与状态检查的边界分别见 [up.sh](#upsh)、[down.sh](#downsh) 和 [status.sh](#statussh)；MinIO 结果判定见[建桶与策略验收](存储与缓存初始化.md#init-miniosh)，Redis 默认读取范围见[默认检查与结果判定](存储与缓存初始化.md#默认检查与结果判定)。

### 手动初始化脚本

如果需要单独运行某个初始化脚本:

```bash
# 初始化 MinIO buckets（模块化 buckets）
./scripts/infra/init-minio.sh

# 初始化 PostgreSQL 扩展（PostGIS + pgvector）
./scripts/infra/init-postgresql.sh

# 校验 Meilisearch API 健康
./scripts/infra/init-meilisearch.sh

# 检查 Redis 缓存、事件和分布式锁
./scripts/infra/init-redis.sh

# 查看所有服务状态
./scripts/infra/status.sh

# 停止所有基础设施服务
./scripts/infra/down.sh
```

## 脚本详细说明

### up.sh

**功能**: 启动 Infra 核心容器，按配置执行初始化／检查，并独立处理可选观测设施。

**特性**:
- ✅ 自动检测 CPU 架构（x86_64/ARM64）并选择合适的 PostgreSQL 镜像
- ✅ x86_64 自动构建仓库 PostgreSQL 镜像，其他缺失镜像自动拉取
- ✅ 解析宿主机端口占用并核对容器工作区归属，首选值与实际映射规则见[端口表](部署与项目隔离.md#端口映射)
- ✅ 检查服务运行状态并复用已有映射，配置和镜像变化仍按各服务生命周期规则处理
- ✅ 按各服务固定探针等待核心设施健康，检查范围与失败边界见下文
- ✅ 按跳过开关执行 PostgreSQL、MinIO、Meilisearch 初始化／检查，并等待 Redpanda 一次性初始化服务成功

**检查范围与失败边界**:

- **核心设施**。PostgreSQL 检查 `pg_isready`，Redis 检查认证后的 `PING/PONG`；FalkorDB、Redpanda 核对容器健康状态，MinIO、Meilisearch 和 Kafka Connect 检查各自的固定 HTTP 入口；另等待 `redpanda-init` 成功退出。核心探针等待超时或必需初始化失败会中止脚本；检查通过不代表应用权限、业务查询、Connector 任务或数据链路已验收。
- **可选观测**。核心检查后独立处理本地日志清理、所选日志／Trace／指标中心和 Infra 采集来源；这些步骤失败时保留核心服务运行，最终返回非零。日志、Trace 和 Prometheus 的 Ready 不证明完整投递或实际采样；分别见[日志诊断与验证](运行日志.md#诊断与验证边界)、[Trace 部署与验证](运行日志.md#日志链路与-trace-部署)和[指标中心隔离验证](指标中心与来源.md#中心隔离验证)。
- **失败排查**。核心容器健康但采集恢复或启动观测失败时，按[现行排查导航](故障排查.md#业务容器健康但采集恢复或启动观测失败)先核对本次失败步骤，再判断是否需要部署者显式重新应用；各环节以实际执行和证据范围认定。

**环境变量**:
- `SKIP_POSTGRESQL_INIT=1` - 跳过 PostgreSQL 的 HBA、扩展、保留测试库和开发库 Schema 初始化
- `SKIP_MINIO_INIT=1` - 跳过 MinIO Bucket 初始化
- `SKIP_MEILISEARCH_INIT=1` - 跳过 Infra 的 Meilisearch API 健康检查，不跳过模块索引初始化

**使用示例**:
```bash
# 正常启动（完整初始化）
./scripts/infra/up.sh

# 仅跳过 PostgreSQL 初始化，其他服务启动、健康检查和初始化继续执行
SKIP_POSTGRESQL_INIT=1 ./scripts/infra/up.sh
```

镜像自动选择及根 `.env` 中的显式镜像配置见[环境与跨平台配置](环境与跨平台配置.md#cpu-架构自动检测)。跳过开关不关闭服务，也不改变应用模块自己的初始化契约。

### down.sh

**功能**: 停用本工作区 Infra 采集来源并撤销部署发现，再通过 `docker-compose.infra.yml` 下线 Infra 容器及网络。

**操作范围与确认**:

- **项目与归属**。Compose 下线范围为 `addp-infra`，包含日志、Trace、指标等可选 Profile；执行前核对待处理容器的 Compose 工作目录。`--force` 仅跳过非 `addp-*` 名称的确认，不跳过工作区归属检查或删卷确认。项目职责见[部署与项目隔离](部署与项目隔离.md#docker-compose-项目)。
- **采集来源**。先通过统一入口执行 `down --scope infra`，仅按 Infra 各来源契约停用来源及其采集账号、清理专属配置；主机和 Business 来源不在本次选择内。不对共享采集项目整批执行 Compose 下线，归属与清理限制见[采集项目与来源隔离](../../../docs/spec/addp平台运行观测规范.md#采集项目与来源隔离)。
- **数据卷与确认**。普通下线保留 Infra 持久数据卷；采集来源的专属配置卷仍可能随停用移除。`-v`／`--volumes` 会删除当前 Compose 声明的卷，必须按[执行顺序与删卷确认](部署与项目隔离.md#执行顺序)办理；非交互例外仅适用于已完成独立准入的 Online 一次性环境。卷保留不等于备份或恢复已验证，范围见[备份与隔离恢复](备份恢复与搜索迁移.md#本地-infra-备份与隔离恢复演练)。

**失败边界**:

来源停用或部署发现撤销未能确认完成时，脚本继续执行核心 Compose 下线，最终返回非零；即使输出“完成”，仍须核对前序失败。Compose 下线本身失败则中止，不提供整批回滚。按实际结果分别核对容器、网络、来源、账号及卷的状态，不能将部分完成认定为全部停止或零残留。

**使用示例**:
```bash
./scripts/infra/down.sh
```

### status.sh

**功能**: 读取当前部署状态、执行固定健康探测，并在满足条件时运行日志投递探针；不是纯状态读取或完整业务验收入口。

**输出信息与验证范围**:

| 输出项 | 当前检查及边界 |
| --- | --- |
| 容器、地址与端口 | 容器表按 `addp-infra` 项目筛选，地址取实际 Docker 映射；不表示公开入口可达，也不包含共享采集项目的完整来源状态。来源核对另见[只读排查](指标中心与来源.md#只读排查)。 |
| 核心设施健康 | PostgreSQL 执行 `pg_isready`，Redis 执行认证后的 `PING/PONG`；FalkorDB、Redpanda 读取容器健康状态，MinIO、Meilisearch、Kafka Connect 请求各自固定 HTTP 入口。通过只证明相应探针，不替代业务权限、查询或数据链路验收。 |
| Kafka 附加诊断 | Redpanda 健康时读取数据目录的文件系统占用并按部署阈值提示；Kafka Connect 可达且安装 `jq` 时展开已有 Connector／Task 状态。未展开不证明没有 Connector，状态展示也不证明事件已完整处理。 |
| Business PostgreSQL logical replication | 仅发现运行中的 `business-postgres` 时，按 `business/.env` 配置只读查询 slot 名称、活跃状态和 retained WAL；读取失败单独提示，不表示 Infra 接管 Business，也不证明 CDC 消费进度。 |
| 指标中心与 Gateway 控制入口 | Prometheus 检查部署输入并执行 mTLS Ready 探测；Gateway 的 `Selected` 只表示已配置监听输入，监听、mTLS 和 OAuth 仍需实测。中心就绪与来源实际采样分别核验，见[指标中心与查询身份](指标中心与来源.md#可选指标中心)。 |
| Trace 中心 | 核对实际端口、容器归属、Tempo 运行、查询入口健康及 Alloy 的 Trace 配置声明；Ready 不证明实际采样或投递，见[Trace 部署与验证](运行日志.md#日志链路与-trace-部署)。 |
| 集中日志与本地计数 | 日志关闭或配置无效时分别报告并跳过日志探针；启用后检查查询代理与 Alloy Ready，读取发送计数、仍保留的接收器计数及最近清理结果。这些计数不是完整历史或零丢失证明，口径见[运行日志正文](运行日志.md#模块实例运行日志)。 |

**日志投递探针与退出结果**:

日志启用且查询代理、Alloy 均有映射端口时，脚本调用 `runtime-log probe`，通过写入技术消息并查询验证投递。成功只证明当前节点当次测试消息送达；未执行、失败或缺少结果均不能计为通过。独占环境的验证入口及其清理范围见[日志诊断与验证边界](运行日志.md#诊断与验证边界)。

脚本不汇总各项健康结果为统一退出码，日志探针失败后也继续输出诊断；退出码为 0 不代表全部健康或链路通过。需结合逐项结果判断，采集或启动观测失败时沿[现行排查导航](故障排查.md#业务容器健康但采集恢复或启动观测失败)核对，不由状态命令自动恢复或重新应用来源。

**使用示例**:
```bash
./scripts/infra/status.sh
```
