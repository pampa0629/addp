# ADDP Infra：部署与项目隔离

[返回 Infra 指南](../README.md)

## 职责范围

本目录脚本**仅管理 ADDP 系统基础设施容器**，不涉及 business 容器。

### 管理的容器（addp-*）

| 容器名称 | 服务 | 用途 |
|---------|------|------|
| addp-postgres | PostgreSQL 15 + PostGIS | ADDP 系统元数据 |
| addp-redis | Redis 7 | 缓存、事件和分布式锁 |
| addp-falkordb | FalkorDB 4.20.6（固定 digest） | Ontology 可重建语义关系投影 |
| addp-minio | MinIO | 系统文件存储 |
| addp-meilisearch | Meilisearch | 全文搜索 |
| addp-redpanda | Redpanda v24.3.18 | 唯一内部 Kafka API CDC 总线 |
| addp-redpanda-init | Redpanda `rpk` 一次性任务 | SCRAM 用户、Connect internal topics 和 ACL 幂等初始化 |
| addp-kafka-connect | Debezium Connect 3.6.0.Final | 数据库日志捕获运行时 |

Infra MinIO 镜像由 `scripts/infra/Dockerfile.minio` 从固定的 MinIO Server 和 `mc` 官方源码修订构建；首次执行 `scripts/infra/up.sh` 时会构建，后续复用本地镜像。此构建不依赖已撤下的公开 MinIO 容器镜像或预编译二进制。

Infra Kafka 固定使用 Redpanda，不提供 Apache Kafka/Redpanda 运行时选择。broker service/container/DNS 分别固定为 `redpanda`、`addp-redpanda` 和 `redpanda:29092`；`addp-redpanda-init` 使用同一 Redpanda 镜像内置的 `rpk`，不是第二个 broker 或数据面。

### 不管理的容器（business-*）

business 容器由 `business/` 目录独立管理，可脱离 ADDP 部署。

用户部署 business 数据库后，通过 ADDP System 模块注册引擎，即可在 ADDP 中使用。

### Docker Compose 项目

- `addp-infra` - 本目录管理（`docker-compose.infra.yml`）
- `addp-platform` - 平台服务（`docker-compose.yml`）
- `addp-runtimes` - 内置计算与 Notebook Runtime（`docker-compose.runtimes.yml`）
- `business` - 业务数据库（`business/docker-compose.yml`）

### 网络隔离

- `addp-network` - ADDP 系统和应用共享
- `business-network` - business 数据库独立网络

business 容器不连接 `addp-network`，确保隔离性。

## 开发提示

- **查看日志**：`docker compose -f docker-compose.infra.yml logs -f <service>`
- **进入容器**：`docker exec -it <container-name> bash`
- **修改配置**：编辑根 `.env` 的部署参数后按对应标准生命周期生效；已有映射与可选设施各按自身规则应用。

## 注意事项

### 执行顺序

1. ✅ **先启动基础设施**: `./scripts/infra/up.sh`
2. ✅ **再启动应用服务**: `make dev-start` 或 `bash scripts/dev/start.sh`

自动初始化、跳过开关与独立检查入口的分工见[生命周期脚本](生命周期脚本.md#初始化与独立检查)；基础设施启动不代替应用模块初始化或专项验收。

`down.sh -v` 在本地必须由交互终端输入 `DELETE addp-infra VOLUMES`，`--force` 不会跳过这项确认；非交互删除仅供已完成独立准入的 GitHub Online 一次性环境使用。脚本还会核对容器的 Compose 工作目录，拒绝从另一个 worktree 停止本工作区的容器。

### 数据持久化

当前根 Infra Compose 声明以下持久卷；可选观测卷随对应能力部署使用，不因卷已声明就表示能力已启用或数据已接入。

| 卷逻辑名 | 保存内容 |
| --- | --- |
| `postgres_data` | PostgreSQL 数据 |
| `redis_data` | Redis 持久化文件及受管认证记录 |
| `falkordb_data` | FalkorDB 语义关系投影数据 |
| `minio_data` | MinIO 对象，包括已启用日志／Trace 的存储 Bucket 内容 |
| `meilisearch_data_v1543` | 当前 Meilisearch 索引 |
| `redpanda_data` | Infra Kafka 日志、Connect internal topics 和 CDC topic |
| `prometheus_data` | 指标中心时序块、WAL 等本地存储 |
| `loki_data` | 日志 WAL、索引缓存及 Compactor 状态 |
| `alloy_data` | Alloy 采集器状态与日志读取位置 |
| `tempo_data` | Trace WAL；Trace 对象存储位于 Infra MinIO |

以上为 Compose 卷逻辑名；默认物理名称带 `addp-infra_` 前缀。旧 `meilisearch_data` 卷不再挂载，仅按[迁移与回滚流程](备份恢复与搜索迁移.md#旧-meilisearch-卷迁移与回滚)保留，不属于当前索引卷。

持久卷不是全部部署文件：节点日志源目录由 `ADDP_RUNTIME_LOG_ROOT` 以宿主目录绑定，配置、证书和私有状态也有各自的部署归属。日志文件、读取位置与远端完整性的区别见[运行日志正文](运行日志.md#模块实例运行日志)，指标历史窗口见[配置应用与数据保留](指标中心与来源.md#配置应用与数据保留)。

普通 `down.sh` 默认保留 Infra 持久数据卷，但采集来源停用可能移除其专属配置卷；显式删卷及失败处理统一见[下线范围与确认](生命周期脚本.md#downsh)。卷仍存在不证明数据完整、历史窗口或恢复能力已验证。

本地备份与隔离恢复只覆盖各自明确的导出范围，不是全部 Infra 卷的备份；默认覆盖、显式 Meilisearch dump、未覆盖项及恢复证据要求统一见[备份与隔离恢复](备份恢复与搜索迁移.md#本地-infra-备份与隔离恢复演练)。删除当前 Compose 卷前，须按[删卷确认规则](#执行顺序)核对操作范围和恢复准备：

```bash
# 危险操作：删除当前 Infra Compose 卷中的数据，须完成删卷确认
bash scripts/infra/down.sh --volumes
```

### 端口冲突检查

`up.sh` 启动前会自动检查以下端口:
- 15432 (PostgreSQL)
- 16379 (Redis)
- 19000 (MinIO API)
- 19001 (MinIO Console)
- 17700 (Meilisearch)

这些是首选宿主机端口示例，不是运行中的固定地址；当前完整服务与映射见[端口表](#端口映射)。本地首次映射冲突会自动选择空闲端口，已运行的本工作区容器复用现有映射。Online 专用 Runner 冲突时直接失败；本地找不到空闲端口、归属核验失败或实际绑定发生并发抢占也会报错。以 `status.sh` 输出的实际映射建立连接，不连接占用首选端口的其他服务。

### 健康检查

核心设施探针、初始化顺序与可选观测失败的处理统一见[up.sh 检查范围](生命周期脚本.md#upsh)。各初始化脚本只验证自身负责的步骤，不统一承诺全部服务或业务链路就绪。

状态读取、固定健康探测、日志投递探针及退出结果的区别见[status.sh 验证范围](生命周期脚本.md#statussh)。容器运行、HTTP 可达、技术探针送达和正式业务验收分别认定；未执行、失败或未覆盖项不能计为通过。

### 幂等性保证

重复执行以各入口的资源复用与变更规则为准，不表示无写入、无重建或无删除。启动、停用与删卷边界统一见[生命周期正文](生命周期脚本.md#脚本详细说明)，不能将 `--drop` 视为通用删除开关。

- **PostgreSQL**。初始化涉及认证规则、保留测试库、扩展和开发 Schema；默认 SQL 还会不带 `CASCADE` 地移除无依赖的 `postgis_topology` 扩展及空 `topology` Schema。SQL 错误会停止后续执行，已完成步骤不按整批回滚认定。入口范围见[PostgreSQL 初始化](PostgreSQL与测试库.md#init-postgresqlsh)，显式 Schema 删除按该脚本自己的参数及确认执行。
- **MinIO**。建桶、私有访问与过期规则分别核验，具体复用行为、失败提示和验收边界统一见[存储初始化专题](存储与缓存初始化.md#init-miniosh)。
- **Redis 与 Meilisearch**。Redis 独立检查的 `--clean` 会清理数据；Meilisearch 初始化只检查 API，业务索引由 Owner 安装。职责和各自入口见[初始化与独立检查](生命周期脚本.md#初始化与独立检查)及[存储与缓存初始化](存储与缓存初始化.md)。
- **Redpanda**。一次性服务按存在性创建用户和 internal topics，同时应用集群配置与 ACL；已有用户不会因再次执行而自动轮换密码。`VERIFY_ACL=1` 的临时 topic 验证与完整 Kafka 认证分别认定，入口分工见[初始化说明](生命周期脚本.md#初始化与独立检查)和[Kafka 认证专题](Kafka认证.md#infra-kafka-认证)。

## 容器命名规范

**Docker Compose 项目名**: `addp-infra`

核心基础设施容器使用 `addp-` 前缀，以下仅为命名示例；完整核心服务见[容器清单](#管理的容器addp-)。名称前缀不能代替 Compose 项目、服务和工作区标签的归属核验：
- `addp-postgres` - PostgreSQL 容器
- `addp-redis` - Redis 容器
- `addp-minio` - MinIO 容器
- `addp-meilisearch` - Meilisearch 容器

**命名优势**:
- ✅ 清晰标识: 一眼看出容器属于 ADDP 系统基础设施
- ✅ 避免冲突: 与其他项目(如 business-postgres)明确区分
- ✅ 项目筛选: `docker ps -a --filter label=com.docker.compose.project=addp-infra` 查看 Infra 项目容器
- ✅ 便于管理: `docker compose -f docker-compose.infra.yml ps -a` 查看项目服务；操作前仍核对当前工作区归属
