## 统一采集管理

恢复失败时，统一入口显示已确认的具体原因：安装证明缺失／停用、证明读取校验失败、来源组件不完整、资源归属不符、部署输入变化、容器或卷身份／安全配置变化、原镜像不可用。缺失、停用或发生变化的安装须由部署者核对后显式 `up` 重新应用；归属或私有文件校验失败须先核对所属工作区和文件保护，不能绕过校验。未知失败不猜测原因，清理未确认另行提示；不回显原始日志、私有路径或凭据。

引擎来源的固定阶段也显示为中文，例如“更新 PostgreSQL 认证规则阶段失败”或“构建采集来源镜像阶段失败”，并给出相应核对方向。阶段仅定位步骤，不能据此认定密码错误、容器未启动或变更已回滚；有清理缺口时先核对状态。未知阶段仍显示操作失败，不通过原始日志推断原因，也不自动重试。

在仓库根目录执行 `python3 scripts/infra/metrics-sources.py status`，汇总主机、Infra／Business PostgreSQL、Redis、MinIO 的配置与来源运行状态。`check` 只复用已启用来源的部署输入校验器，不连接业务数据库、不修改账号或启动容器；各来源的证书校验范围仍按下文原有契约，检查通过不能替代真实 mTLS；`up` 明确安装／应用已有来源配置，可能重建来源；`down` 只停用来源及其专属账号，不启动或停止被监控引擎。支持重复 `--scope host|infra|business`、`--kind node|postgresql|redis|minio` 限定对象，未指定则处理全部。各项独立执行并汇总，任何失败返回非零，不中断其他选中来源，也不把可选来源失败变成核心服务不可用。

配置仍归根 `.env` 和 `business/.env`，直接执行统一入口时Business不继承根环境中的采集选择、端口、证书或数据库凭据；不新增中央配置副本。标准部署调用者通过 `--resolved-env` 显式交接已解析的本域环境，保留注入值及实际部署参数；此模式强制限定一个明确scope，不能混入其他域或自动回退到配置文件。Hosted文件模式只接受其既有显式隔离环境文件，禁止回读个人配置。状态检查只读取本地 Docker、工作区／作用域归属与当前数据库容器身份，不读取容器环境、账号凭据或业务数据；“来源运行中”不等于 Prometheus 已采到或 Monitor 可读，实际采集仍由原观测链验证。

Infra 和 Business 的标准入口通过统一采集管理调用本域的来源生命周期。主机来源须显式选择，Prometheus、System 和 Monitor 由各自的部署入口管理。同一 Docker Engine 上的一套 ADDP 部署中，主机、Infra 和 Business 采集来源共用 `addp-metrics-sources` Compose 项目，各来源的网络、凭据和操作范围分别管理。[统一采集分组](#统一采集分组)

`recover` 复用已安装的 PostgreSQL／Redis／MinIO 来源，沿用原账号及权限，通过校验的健康来源保持原状。来源已停用、安装未完成、凭据或权限漂移、被监控引擎容器被替换时，拒绝自动恢复，由部署者核对后显式执行 `up` 重新应用。恢复入口按次执行，实际应用与启停由部署者操作。全量启动的来源选择见[部署指南的采集恢复与监控摘要](../../../docs/guide/addp部署和开发步骤.md#startup-source-recovery)。

主机来源可由部署者显式执行 `python3 scripts/infra/metrics-sources.py recover --scope host --kind node` 恢复。未选主机作用域的批量 `recover` 跳过主机。全量、局部及 Hosted 精确进程入口的触发范围统一见[部署指南的采集恢复与监控摘要](../../../docs/guide/addp部署和开发步骤.md#startup-source-recovery)。

- **安装证明**。标准 `up` 成功后在仓库外的 `~/.local/state/addp/<工作区路径摘要>/node-metrics/installation.json` 保存私有安装证明，只含模板／证书摘要、文件身份及 Docker 安装事实。

  比较 Docker 容器配置时，仅对已有的 `Dns`、`DnsOptions`、`DnsSearch` 字段将 `null` 与 `[]` 视为等价，两者都表示无容器 DNS 覆盖。真实 DNS 配置、字段缺失、其他类型及其他安全字段仍按原值比较，与证明不符时拒绝恢复。空值归一化只在内存中进行，健康来源的安装证明保持原样。仅有这类表示差异时，无需重新执行 `up` 或重建采集器。

- **恢复与拒绝条件**。`recover` 仅启动与证明完全匹配的既有停止容器，健康来源保持原状。只有容量采样器停止时，只恢复该采样器。容器缺失、证明缺失或停用、证书／模板／Engine／内核或容器安全配置变化时拒绝恢复。镜像拉取和重建由部署者显式应用时处理。
- **失效与核验**。`down` 或失败的 `up` 都会使旧证明失效。旧安装须由部署者先显式执行 `up --scope host --kind node`。容器恢复运行后，仍须在 Monitor 核对实际采集。

启动监控摘要仅读取指标中心和可选控制入口的归属及运行健康状态，以及七类来源的配置与运行状态。七类来源包括主机，以及 Infra 和 Business 各自的 PostgreSQL、Redis、MinIO。来源恢复或摘要检查失败时，启动命令保留非零退出结果，业务服务仍继续启动。实际采样、主机关联和有效指标须在 Monitor 核对。摘要的触发范围见[部署指南的采集恢复与监控摘要](../../../docs/guide/addp部署和开发步骤.md#startup-source-recovery)。

<a id="startup-observation-stage-failures"></a>

末尾来源“失败0项”只代表当前来源状态正常，不能清除本次启动前面已失败的配置预检、设施健康、端口读取或恢复步骤。启动末尾会逐项列出本次失败阶段，明确与当前采集状态分开；具体原因沿该阶段原输出核对，不因随后正常推断原失败已修复，也不自动重试或要求重建全部设施。

```bash
python3 scripts/infra/metrics-sources.py status
python3 scripts/infra/metrics-sources.py check
python3 scripts/infra/metrics-sources.py up --scope infra --scope business
python3 scripts/infra/metrics-sources.py down --scope business --kind postgresql
```

## 可选指标中心

根模板 `ADDP_OBSERVABILITY_METRICS_ENABLED=false` 默认关闭 Prometheus。设置 `true` 时，标准 `bash scripts/infra/up.sh` 在核心 Infra Ready 后独立预检、校验配置并启动 `observability-metrics` Profile。中心失败返回非零，开发/生产入口依据核心实际健康继续启动业务；日志与指标独立选择。关闭后再运行标准入口会停止当前工作区的中心并保留时序卷，不停止其他工作区容器。不要用全量 Compose 启动替代生命周期入口。

启用前将 `ADDP_METRICS_TLS_DIR` 设置为部署方管理的绝对证书目录，内含 `ca.crt`、`server.crt`、`server.key`、`health.crt`、`health.key`。此目录仅存放这五项输入，CA 私钥和其他客户端私钥由各自部署 Owner 在目录外保管。CA 只信任本中心部署客户端；`server.crt` 包含 `localhost` 和 `prometheus` DNS SAN，`health.crt` 具有客户端认证用途。目录和文件须可被容器 UID/GID `65534:65534` 读取，私钥不得通过仓库或 Artifact 分发；标准脚本不生成部署 CA 或证书。错误、过期、不匹配或容器不可读证书由真实 mTLS 启动/探针拒绝。

中心的节点作业通过原生 OAuth2 和 HTTP SD 连接已有 System/Monitor API。部署另外设置 `PROMETHEUS_SYSTEM_URL` 和 `PROMETHEUS_MONITOR_URL`，值为容器可达的规范 HTTPS origin，必须有显式端口，不含路径或尾部斜杠；由受控 TLS 入口分别转发固定 `/api/v1/system/oauth/token` 和 `/api/v1/monitor/platform/metrics_discovery`。不按本机 Backend 首选端口或模块注册 URL 拼接地址，不将发现凭据用于节点指标抓取。

`ADDP_METRICS_DEPLOYMENT_DIR` 指向仓库外的绝对目录，只存放 `control-ca.crt`、`source-ca.crt`、`collector.crt`、`collector.key`、`prometheus-client-secret` 和生成的 `prometheus.yml`。控制面 CA 用于验证 Token/发现服务，来源 CA 用于验证节点 IP SAN；独立 collector 证书只访问来源，不能复用中心健康证书。Secret 文件内容不带尾部换行，须精确匹配 System 部署中的 `PROMETHEUS_SERVICE_CLIENT_SECRET`，不得与日志或业务服务 Secret 相同。部署负责把目录设为容器可遍历、私钥和 Secret 仅向需要的 UID/GID 开放（如目录 `0750`、Secret `0640`，由部署正确设置所有者/组）；生命周期脚本不修改现有私钥权限。

预检从唯一版本化模板和部署输入原子生成 `prometheus.yml`，该文件不含 Secret 值，不得手工编辑。更换控制面地址、信任根或证书后由部署方重新创建中心容器应用，不承诺热更新；目标启停通过成功的 30 秒发现刷新生效，不要求重启业务。发现失败时中心保留上次成功目标列表，紧急阻断依赖凭据撤销和网络边界，不能承诺控制面故障期间即时停采。未填写完整接线输入时只报告可选指标未配置，核心启动仍继续。

中心 API/UI 强制 mTLS，宿主只发布 `127.0.0.1:${PROMETHEUS_PORT:-19090}`。本地冲突沿用端口解析和现有映射，实际值用 `bash scripts/infra/status.sh` 查看；容器间使用 `https://prometheus:9090`。管理员写入、远端写入和 HTTP 重载不开启。独立卷 `prometheus_data` 保留时序块 7 天或 10 GiB，体积淘汰可能缩短历史窗口；WAL 与压缩空间需要额外磁盘容量。镜像版本及 digest、资源预算和固定采集限制统一定义在 `metrics.yml` 及 `prometheus*.yml`。

中心自身作业与节点 HTTP SD 作业已分别接线，Ready 不代表节点或业务引擎已接入。正式目标只由 Monitor HTTP SD 与 System 当前对象绑定提供，不支持手工生产静态目标文件。`make test-monitor-metrics` 使用独占临时项目、临时证书及固定镜像，验证原生 OAuth/HTTP SD、真实受控采样和故障恢复，退出清理容器、网络、卷及文件；控制面为协议夹具，不证明真实部署全链路、生产规模或完整 7 天保留窗口。

生产平台通过根 Compose 向 System 传递可选指标开关及独立发现 Secret，向 Monitor 传递指标开关与明确 CIDR/端口集合。`scripts/prod/start.sh` 只在选中指标且三个 `MONITOR_METRICS_*_FILE` 是可读绝对文件时合并 `scripts/prod/metrics-platform.yml`，仅向 Monitor 挂载来源准入 CA/客户端证书/私钥，不重复定义服务。未选中或证书缺失不挂载不存在的文件、不创建空证书目录；缺失时报告可选能力未配置并继续业务启动。Monitor 准入证书可独立于 Prometheus collector 管理，两者均不使用中心健康证书。


### 独立 Linux 主机指标来源

中心和业务启动不自动启用节点采集。部署方在明确纳管的 Linux 节点按根 `.env.example` 配置根 `.env` 的三个输入后，通过统一入口显式执行：

```bash
python3 scripts/infra/metrics-sources.py up --scope host
python3 scripts/infra/metrics-sources.py status --scope host
python3 scripts/infra/metrics-sources.py down --scope host
```

底层唯一实现 `node-metrics.py` 只消费统一入口传入的环境，不自动读取或改写 `.env`。`ADDP_NODE_METRICS_ENABLED=false` 时 `up` 不调用 Docker；选择 `true` 后要求 `ADDP_NODE_METRICS_LISTEN` 为明确本机 IP:端口（IPv6 使用 `[IP]:端口`），不能通配监听、使用 DNS 或自动避让。`ADDP_NODE_METRICS_TLS_DIR` 为仓库外绝对目录，只含 `ca.crt/server.crt/server.key`，不能混入签发私钥或客户端私钥；文件须可由 UID/GID 65534 读取。来源 CA 仅信任独立 Monitor 准入与 Prometheus 采集客户端，不信任中心健康身份；服务器证书包含 Monitor 发现使用的 IP SAN。文件存在不代表证书已通过验证。

同一入口根据本地 Engine 事实选择部署层，不新增 `.env` 开关。原生 Linux 要求内核 5.12+、Docker Engine 与当前宿主内核一致；采用 host 网络/PID 和宿主根目录只读 rslave 挂载，显式从 `/host/proc`、`/host/sys` 读取，启用十个资源采集器。macOS 的 Docker Desktop Linux VM 采用 `node-metrics-desktop.yml`：独立 bridge 网络，按显式 IP:端口发布来源；只启用 cpu、meminfo、loadavg、diskstats、stat、uname、time 七个内核全局采集器，使用 `/proc`、`/sys`，不挂载宿主根、Docker Socket，不用 host 网络/PID。不发布 filesystem、netdev、netstat；文件系统容量/inode API 对该来源明确无数据。diskstats 读取 Linux VM 内核块设备统计，提供五项磁盘 IO 观测，不代表 Mac 物理磁盘或单个容器的消耗，也不跨设备层求总和。仍拒绝远程 Docker Endpoint、非 Linux Engine、旧内核和未知环境。两层共用同一固定官方镜像 tag/digest、原生 mTLS、0.25 CPU/256 MiB、非 root、只读容器文件系统与全部 capability 移除。节点源能读取宿主资源属于明确部署权限，不由中心开关授予。证书替换和配置变更通过再次执行节点 `up` 重建生效；密钥文件 inode 替换不会自动更新既有文件 bind mount，不能承诺热轮换。生产宿主子挂载的实际只读状态与传播仍需 Linux 验收；配置声明和内核门槛不能替代运行检查。

Docker Desktop 主机登记必须使用 `virtual` 类型并明确命名为 Linux VM；指标反映 VM 中所有工作负载的合计，不能当作 Mac 本机或某个引擎消耗。在 Mac 直接运行的模块不归该节点。`ADDP_NODE_METRICS_LISTEN` 在 Desktop 模式表示宿主发布 IP:端口，来源内部固定监听 9100；正式监测目标必须同时对 Monitor 和 Prometheus 可达，不能把 Mac 回环地址直接当作中心容器的回环地址。服务器 IP SAN 对应正式目标准入解析出的地址，端口不自动避让。

macOS 本地验证需要避免 DHCP 地址变化时，可显式将 `ADDP_NODE_METRICS_LISTEN=127.0.0.1:19091`、`MONITOR_METRICS_ALLOWED_CIDRS=127.0.0.1/32` 与 `ADDP_METRICS_DESKTOP_LOOPBACK_PORTS=19091` 配为同一端口。正式目标使用 `https://127.0.0.1:19091/metrics`；端口列表最多 64 个规范非零端口，逗号分隔，不允许重复、空项或空格。中心唯一 Job 将列表内每个显式回环地址转换为同端口 `host.docker.internal`（此例为 `host.docker.internal:19091`），同时保留原地址作为 `instance`，确保宿主准入与中心查询沿同一作用域。Go 进程来源可以追加自己的显式端口；不转换列表外的端口或非回环地址。仅 macOS、本地 unix Docker Desktop Engine 接受该输入，缺省不启用转换；来源证书必须同时含 `127.0.0.1` IP SAN 与 `host.docker.internal` DNS SAN，仍使用独立 mTLS，不设置证书名称覆盖。此地址表示采集访问入口，不能作为 VM 物理网卡地址或身份依据。端口冲突必须处理原占用，不自动避让。配置与证书准备完成后，由部署方分别执行节点 `up`、Monitor 标准重启及中心 `up.sh --metrics`，再更新已有目标；保留原节点和目标身份，不建立重复记录。

主机来源位于当前工作区的统一采集分组，保留仓库绝对路径 Owner 标签；命中同名服务但归属不符时拒绝操作。`down/status` 不校验已失效的来源证书或当前开关，不依赖中心，不删除业务容器、网络或卷。启动成功只说明来源容器运行；部署方仍需通过独立 mTLS 验证来源，再用 Monitor 正式目标接口完成准入，来源部署不会自动创建 System 节点、目标或发现标签。端口与来源错误只影响这个独立入口。

已启用并运行的本工作区节点来源可以沿同一入口导出接入清单；仍需先提供与 `up` 相同的三个显式环境输入，入口不自动读取 `.env`：

```bash
python3 scripts/infra/node-metrics.py export-admission > /tmp/addp-host-admission.json
```

Desktop 自动声明 `virtual` 与 Linux VM 名称。原生 Linux 必须额外传 `--node-kind physical` 或 `--node-kind virtual`；显示名可通过 `--display-name` 提供，主机地址可通过重复的 `--address` 明确提供，缺省地址为空，不将监听地址推作节点地址。`--module` 最多 64 项且不能重复；导出的整个 UTF-8 文件最多 16 KiB。上述属性参数只用于导出，不用于 `up/down/status`。导出核验本地 Engine、内核、当前运行的唯一来源与工作区 Owner，仅读取状态，不执行 Compose 变更；禁用、远端、异工作区或来源未运行时拒绝，不导出其他环境键或证书路径。

仅在 Console“平台主机管理 → 从部署清单接入”导入 v2 JSON，预览后明确选择已有主机或按清单新建；只在确认时写入。System 创建新 node_id，Monitor 执行原 mTLS 和端点准入并保存配置，不自动修改根 `.env` 或当前进程声明。已有主机信息保留；新建主机和采集保存分步完成，失败时页面标明已完成步骤，未知结果先核验，不能从头自动重试。文件不含身份凭据，不是独立物理位置证明；无主机采集的原生 macOS/Linux 服务宿主可显式使用 `--host-only --node-kind physical`（或明确的 virtual），不访问 Docker、来源证书或中心；重复 `--module monitor --module meta` 声明允许的 ADDP 服务，不自动探测服务位置。省略采集的宿主清单只用于 System 登记及生成部署参数，仍由新进程首次声明绑定。含来源的清单在主机确认后通过 Console 内存草稿到 Monitor 独立保存；不根据 Docker 容器名、数据库地址或资源量建立引擎关联。协议及门禁见平台运行监控设计 4.2 节。

`make test-monitor-metrics` 还以相同基础/Web 模板运行真实 node_exporter，验证客户端认证、资源样本进入唯一原生 HTTP SD 作业、来源中断与恢复。独占 T2 使用 bridge、随机回环端口和临时证书，不挂载宿主根、不使用 host 网络/PID。同一临时来源再部署为 Desktop 受限层，实际对照 Engine 核数、内存和内核，检查仅七采集器、不同命名空间容器的原始磁盘计数对照、被禁用指标族缺失、mTLS、唯一 HTTP SD 磁盘即时/趋势查询及恢复。macOS Docker Desktop 上的执行证明 VM 内核全局基础资源，Linux CI 只证明受限部署层；完整文件系统、cAdvisor、真实 System/Monitor 控制面和生产权限仍按各自验收范围验证，不以 T2 协议夹具替代。


### Monitor 资源查询身份

指标中心的 query/query_range 由 Monitor 使用独立 mTLS 客户端访问。显式部署 `MONITOR_PROMETHEUS_URL`（HTTPS origin、端口，无路径）以及 `MONITOR_PROMETHEUS_CA_FILE/CLIENT_CERT_FILE/CLIENT_KEY_FILE`（绝对文件路径）。CA 信任中心服务器证书；中心的客户端 CA 需信任该独立查询证书。不要复用 health、collector 或节点准入私钥。Prometheus 原生 mTLS 验证客户端身份，不提供按证书区分 HTTP 路径的 RBAC；查询客户端只调用固定读取端点，部署网络只允许 Monitor 访问中心，中心不得开启 admin/lifecycle API。

原生开发由标准环境加载传给 Monitor；生产通过唯一 `scripts/prod/start.sh` 在输入完整时添加 `metrics-query.yml` 的三项只读挂载，不增加中心启动依赖。未填写查询 origin 时不挂载，资源 API 报能力未配置；填写 origin 但证书缺失时生产脚本报告可选观测失败，业务仍继续启动。仅恢复同一中心的连接不重启业务；修改端点或证书须按服务生命周期由运维生效。

当前固定主机目录包含九项标量、文件系统容量与 inode、磁盘吞吐与 IO 时间、网络收发共 25 项，提供即时及趋势读取；实际可用项由来源环境决定。预算位于模块级 `/settings/resource-query-policy`；查询参数、权限和验收边界见平台运行监控设计第 5.2、6、9 节。


### 指标控制面的可选私有 TLS 转发

本地独立 TLS 入口由同一标准 `bash scripts/infra/up.sh --metrics` 管理，仅调和指标服务，使用既有 `addp-network`；不会启动、构建、初始化或重建核心和日志设施，也不生成日志凭据。默认不带参数仍为全量标准入口。再次执行指标入口会重新创建所选指标容器以应用生成配置和证书；保留中心时序卷，不能视为热更新。设置 `ADDP_OBSERVABILITY_METRICS_ENABLED=true`、`ADDP_METRICS_CONTROL_ENABLED=true`、外部 `ADDP_METRICS_CONTROL_DIR` 和明确 `ADDP_METRICS_CONTROL_GATEWAY_URL=http://host.docker.internal:实际Gateway端口`；两个发现 origin 均使用 `https://metrics-control:9444`。入口只在 `addp-network` 提供 TLS，不发布宿主端口；其 CA 放入中心 deployment/control-ca.crt。目录仅含 `server.crt/server.key/nginx.conf`，标准脚本不签发证书。版本化模板仅转发 Token POST 和发现 GET，拒绝其他路径、方法及查询参数；Authorization 保留，访问日志关闭，资源为 0.25 CPU/128 MiB，UID/GID 65534、只读文件系统、移除全部 capability。上游 HTTP 属于明确的受控本地网络边界，不能替代生产 TLS 验收。

关闭入口时不校验入口输入，停止当前 Owner 的入口容器；关闭中心也停止入口并保留中心数据卷。状态 Running 只证明容器运行，Token/发现接通须经真实请求验证；业务仍不依赖该入口。现有外部 HTTPS 控制面部署不需要选择此转发容器。

个人 macOS Docker Desktop 的新建凭据可以采用完整路径隔离：Owner 私有 0700 外层目录，容器仅只读挂载各自 0755 子目录，所需新建叶子文件设为容器 UID 65534 可读，其他本机用户无法穿过外层目录。CA 私钥与原生 Monitor 查询/准入私钥另存 0700 目录及 0600 文件，不挂载到中心或入口；不得递归放宽已有目录与私钥权限。此布局仅用于个人开发验证，生产密钥 Owner/组与权限按独立 T5 验收。来源使用明确且同时可达的 Mac IP，IP 改变后需重新签发 SAN 并通过正式目标准入更新，不能自动沿用旧绑定。

### PostgreSQL 固定汇总边界

数据库侧唯一活动安装版本为 `scripts/infra/postgres-observation/000002_lifecycle.sql`，只支持 PostgreSQL 15；旧版本保留为不可变历史。由 `postgres-observation/lifecycle.py` 通过私有 stdin 提交作用域、SCRAM 校验值及明确的 Login 启停意图，不手工运行 SQL，不把原始密码或校验值放入命令参数、环境模板或发现快照。

固定角色、函数、PUBLIC 授权限制与维护连接库准入见[平台运行观测规范 4.6](../../../docs/spec/addp平台运行观测规范.md#46-postgresql-数据库侧汇总读取边界)。`make test-monitor-metrics MONITOR_METRICS_TEST_ARGS=--case=postgres-observation` 只启动本轮专属 PostgreSQL，真实验证密码和读取边界；默认 `make test-monitor-metrics` 同时执行它和现有完整指标链路。该专项不要求个人 Infra 端口或密码，不接入个人／业务数据库，不等于专业指标已进入 Prometheus 或 Monitor 页面。

### PostgreSQL 采集账号与指标来源启停

`scripts/infra/postgres-metrics.yml` 提供固定 SQL Exporter 与 Nginx 配对模板，单连接、固定查询、只读文件系统和受控 mTLS；SQL 连接凭据与 TLS 文件分别只读挂载，不在容器环境或参数中传密码。配置唯一生成器为 `postgres-observation/source.py`，来源统一由 `postgres-observation/lifecycle.py` 管理，已接入标准 Infra／Business 启停；不直接用 Compose 拼接另一条安装路线。

<a id="postgresql-source-pair-troubleshooting"></a>

配对发现异常时，先在仓库根目录运行 `python3 scripts/infra/metrics-sources.py status --scope infra --kind postgresql`。排查 Business 来源时将 `infra` 换成 `business`。状态命令用于核对配置和容器运行情况，发现结果按配对契约判断。[PostgreSQL 配对来源发现契约](../../../docs/spec/addp平台运行观测规范.md#postgresql-source-pair-discovery)

- **只启动一侧**。在 `addp-metrics-sources` 项目内按同一作用域核对 `<scope>-postgres-metrics` 和 `<scope>-postgres-metrics-web` 两个服务。各自应有且仅有一个运行中的容器，并绑定同一当前数据库容器及启动时刻。两侧都未发现时为 `not_deployed`，单侧缺失、停机或重复时为 `unavailable`。
- **端口映射错配**。只读核对 mTLS 入口的 `HostConfig.NetworkMode` 是否为 `container:<Exporter 完整容器 ID>`。再核对 Exporter 的 `NetworkSettings.Ports`，其中 `9443/tcp` 应只有一条映射，宿主机 IP 和端口应与本作用域的 `ADDP_POSTGRES_METRICS_LISTEN` 一致。mTLS 入口容器自身应无发布端口。

`make test-monitor-metrics MONITOR_METRICS_TEST_ARGS=--case=postgres-source` 在同一门禁私有环境内验证固定 16 项指标、真实数据库账号、mTLS、HTTP 路径隔离、SQL 失败无旧样本、恢复新时间及统计关闭缺值；也包含前述数据库权限专项。HTTP 200 或 Prometheus up 不等于 SQL 采集成功，具体口径见[平台运行观测规范 4.7](../../../docs/spec/addp平台运行观测规范.md#47-postgresql-受保护的固定指标来源)。

同一 `source.py` 的 `authentication_configuration` 生成采集账号专属的 HBA 首部块；只允许维护连接库与显式私网／回环 CIDR 的 SCRAM，拒绝其他数据库、Unix socket 及物理复制，保留其他用户记录。它不写文件、不重载、不更改权限；部署 owner 须先验证角色归属，再核对文件版本、原子安装、重载并验证真实认证，全部成功后才启动来源。归属／规则漂移、外部保留账号记录、无界网络或预算超量均拒绝。标准 `postgres-source` T2 覆盖真实认证、文件恢复和指标传输；产品生命周期在旧来源停止及无遗留会话后，先完整安装为 NOLOGIN，原子更新并重载 HBA 后才复核并启用 Login。遇到未知会话拒绝安装，不主动终止连接。

Business 标准启动已接入同目录 `authentication.py prepare-business`，准备仓库外、当前工作区拥有的 HBA 运行目录；数据库只读目录挂载，移除原单文件绑定。运行目录与模板的版本、归属和漂移分别核查，认证文件更新复用同一锁及原子替换；不在 Web 或普通发现进程中执行。`postgres-source` T2 另在专属 PostgreSQL 重建后验证只读目录、宿主替换可见、真实重载、认证及 mTLS 采集和原文件恢复；不接触个人 Business 数据卷。角色与来源随各自标准入口的显式开关生效；来源启动仍不等于采集成功；正式发现、Monitor 查询及页面必须分别确认。


Infra 在根 `.env`、Business 在 `business/.env` 分别配置下列四项，开关默认 `false`，不因中心已启用而自动开启：

```dotenv
ADDP_POSTGRES_METRICS_ENABLED=false
ADDP_POSTGRES_METRICS_TLS_DIR=
ADDP_POSTGRES_METRICS_LISTEN=
ADDP_POSTGRES_METRICS_STATE_DIR=
```

启用时将开关改为 `true`，提供仓库外只含 `ca.crt/server.crt/server.key` 的证书目录，以及规范的本机私网或回环 `IP:端口`（IPv6 为 `[IP]:端口`）。服务器证书必须覆盖该 IP；Docker Desktop 由中心经宿主访问时还需相应 DNS SAN。来源端口不提供默认值、不自动避让；两个作用域的端口须各自明确。CA 只信任独立采集客户端，入口不生成 CA 或扩大信任。来源由部署发现 v2 自动记录；System 只为管理员已确认纳管且主机关联有效的部署投影私有来源，Monitor 准入后加入唯一 HTTP SD，无需手工重复登记目标。Desktop 优先选用 Monitor 与容器中心均可到达的宿主私网 IP；使用回环地址时仍须配置既有 Desktop 精确端口转发，不扩大或自动改写网络准入。

可选状态根必须为仓库外绝对目录；默认按工作区摘要放在当前部署用户的 `~/.local/state/addp/` 下，再分隔 `infra/business`。外层目录 `0700`，凭据与归属记录 `0600`；首次生成独立随机密码，重复启动沿用。容器分别只读挂载外层私有目录内的必要子目录，不共享 SQL 凭据和 TLS 私钥。已有角色但私有密码丢失时拒绝自动重置，应先核对部署状态与备份。

配置随 `bash scripts/infra/up.sh`、`bash business/scripts/start.sh -postgres` 应用；Infra 仅重试可选指标可用 `bash scripts/infra/up.sh --metrics`。首次 Business 认证目录切换会由标准启动重建 PostgreSQL 容器，保留数据卷，应由部署方安排执行。停止入口在数据库停服前先关闭本方来源与 Login；把开关改回 `false` 后再运行相应启动入口也会关闭来源。停用保留函数、密码、历史和数据卷，不自动终止未知数据库会话。

来源失败返回非零的可选结果，核心服务继续运行；证书、端口、账号、HBA 或归属检查失败都不能保留旧来源为成功。Business 认证内容未变时，仍先核验归属、权限、基线及输入版本，再保留原文件和 inode，不重复替换；内容变化仍沿唯一原子替换路径。文件读取有明确字节上限，容器内必须读到精确的新内容后才校验和重载。挂载不可见、内容漂移、权限错误、符号链接和读取超限均拒绝，不通过重试或放宽认证继续安装。失败诊断只输出封闭的阶段与原因，不输出认证文件、SQL、凭据或原始命令错误。真实采集是否成功仍以 mTLS 返回的新鲜固定快照为准。Monitor 已提供引擎监控的十二项即时指标、当前页四项摘要与当前数据库容器段的最长七天趋势；本入口不创建平台引擎部署或租户 Engine，不授予租户数据权限。实际正式身份链路和容量须分别验收。


完整开发启动（`bash scripts/dev/start.sh` 或 `-all`）在发布发现前分别自检已安装来源；单模块启动及 `ADDP_ONLINE_HOST=1` 隔离验收入口不处理。自动恢复只处理同一数据库容器的来源停止／启动声明失配，健康来源保持不动；不安装或启用账号、不修改认证、不启动数据库。采集账号／私有安装状态失效、新数据库容器或权限漂移时，使用本页原 Infra／Business 标准入口重新应用，不直接启动旧采集容器。此能力不提供宿主无人值守恢复或定时任务。


### MinIO 采集身份与固定指标来源

唯一生命周期实现为 `scripts/infra/minio-observation.py`，由 Infra 标准 `up.sh`（含 `--metrics`）／`down.sh` 及 Business 标准 `start.sh -minio`／`stop.sh -minio` 调用。它管理独立的原生受限 Access Key 和 `cmd/minio-metrics-source`；不由 Monitor Web 直连 S3。17 项产品指标边界见[正式规范](../../../docs/spec/addp平台运行观测规范.md#minio-专业观测首期边界2026-11-02-已确认)。实现范围与分层证据见本节后文；来源部署成功、专业查询与页面验证分别记录。

根环境与 Business 环境分别配置，默认关闭，不相互继承开关、监听、TLS 或私有状态。启用需要：

```dotenv
ADDP_MINIO_METRICS_ENABLED=true
ADDP_MINIO_METRICS_LISTEN=<明确的本机私网或回环IP:端口>
ADDP_MINIO_METRICS_TLS_DIR=<仓库外仅含ca.crt/server.crt/server.key的绝对目录>
# ADDP_MINIO_METRICS_STATE_DIR=<可选仓库外绝对私有状态目录>
```

证书由部署方提供，服务器证书覆盖监听 IP，私钥归当前部署用户且仅本人可读；入口不生成 CA、不开放公网或自动分配端口。两作用域端口独立指定，状态默认按工作区及作用域隔离。账号私钥保存在 `0700` 目录、`0600` 状态文件；来源配置和证书复制到独立受管私有卷，以非 root 只读挂载，不放入容器环境或 argv，不挂载 Docker Socket、MinIO 数据卷或宿主目录。来源只加入该数据库的标准 Compose 私网，目标为核验后的当前容器 IP:9000。Infra 多网络时只选择 `addp-network`，Business 只选择 `business-network`，不按 IP 或名字猜测宿主。

启用先核验并移除本方旧来源，校验证书／监听，构建固定来源并安装或启用独立账号，再启动 mTLS 来源。关闭开关或停止入口先移除本方来源和私有配置卷，再停用账号、核验旧 JWT 被拒绝；保留原生账号、数据卷和仓库外凭据供下次显式启用。显式安装／应用中途失败也执行来源移除和账号停用；无法证明清理时单独报告 `cleanup=failed`。陌生来源／账号、归属或策略漂移、丢失私有凭据均拒绝收养或重置。未安装且关闭时不访问 Docker，采集失败独立报非零，核心服务仍继续运行或停止。

MinIO 镜像须经标准固定源码构建并包含 `minio-observation-status`。该工具复用同一 mc 源码已锁定的管理 SDK，固定回环地址、输入预算和唯一内联策略；原生普通 enable／disable 会清除内联策略，产品不使用。专用工具在一次更新中提交状态和 `admin:Prometheus`，部署侧重读核验。正常重复启动不重置账号或改写凭据，同卷容器重建后重新绑定当前容器，计数代际随之变化。

来源只读四个固定 v3 端点并重读进程边界；mTLS TLS1.3 只开放无 query／请求体的 `GET /metrics`。固定数值之外的原生标签全部删除，失败返回 503，不缓存旧数据。固定上游版本省略零值系列，尚未扫描也没有对象统计，不能补零或承诺健康时 17 项均有值；最近扫描时间与本次采集时间分别表达。来源只输出原始数值，速率与占比留给唯一查询层。

只读发现从共享 `addp-metrics-sources` 项目按 `infra-minio-metrics` 或 `business-minio-metrics` 服务名定位唯一来源。发布受管 v2 快照的私有 `minio_metrics` 前，核对工作区 Owner、作用域和服务标签、当前数据库容器的完整 ID 与启动时刻、标准私网的网络 ID 与 Compose 归属，以及唯一显式的 `9443/tcp` HTTPS 映射。[运行观测规范的统一部署分组](../../../docs/spec/addp平台运行观测规范.md#采集来源统一部署分组2026-11-04)

System管理员从现有自动发现候选确认Infra／Business MinIO及有效主机，只保留9000 API端口；不会自动纳管或按地址推断主机。私有来源仅向Monitor后台投影，经原准入进入HTTP SD，不进入浏览器DTO或持久声明。Monitor已接通17项固定专业查询，详情按容量／状态10项、请求／流量7项分组，列表取四项摘要，管理页面提供现有监控跳转。缺失原生指标单项留空；实时采集与最近扫描分别解释，相关tip放在指标旁。个人部署的真实页面与正式身份全链路尚须分别验收。

本地入口为 `make test-monitor-minio-observation-unit` 与 `make test-monitor-minio-observation`。T2 独占两个临时 MinIO，原生数据库不发布宿主端口，仅临时来源发布随机回环端口；验证 S3／管理越权拒绝、短 JWT、两作用域独立账号及 CA、真实 mTLS 固定输出、非 root／只读及资源预算、停用失败关闭／恢复／错误清理、保卷重建及计数代际；同一独占门禁还运行固定Prometheus评估器，验证17项与缺样／重置／代际／扫描边界，最终核对容器、网络、卷和私有材料清零。Redis 与 MinIO 复用同一 HTTP/TLS 和受管来源部署内核，协议适配各自独立。个人服务不自动应用；CI 和 Hosted 由专门会话安排回传。

### Redis 采集账号与指标来源启停

唯一生命周期实现为 `scripts/infra/redis-metrics.py`，标准 Infra／Business 脚本通过统一采集管理入口调用；固定来源为 Monitor 内 `cmd/redis-metrics-source`，不由 Web 进程直连 Redis。账号及指标边界以[Redis 正式契约](../../../docs/spec/addp平台运行观测规范.md#redis-专业观测首期边界2026-11-01-确认分阶段实施)为准。

根 `.env` 与 `business/.env` 各自配置以下四项，默认关闭、端口无默认值且不自动避让：

```dotenv
ADDP_REDIS_METRICS_ENABLED=false
ADDP_REDIS_METRICS_TLS_DIR=
ADDP_REDIS_METRICS_LISTEN=
ADDP_REDIS_METRICS_STATE_DIR=
```

启用时提供仓库外的 `ca.crt/server.crt/server.key` 和规范的私网／回环 `IP:端口`，IPv6 使用 `[IP]:端口`。服务器证书覆盖该 IP，CA 仅信任专属采集客户端；私钥归当前部署用户所有且不向其他用户开放。不签发证书、不改变个人网络或 Docker 配置。状态根可省略，默认以工作区摘要分隔至当前用户 `~/.local/state/addp/`，再按作用域隔离；自定义目录必须在仓库外。密码只在该私有状态中首次生成并沿用，不填写在环境模板中。

由用户在对应配置就绪后执行标准入口：Infra 使用 `bash scripts/infra/up.sh`；已经切换原生 ACL 启动的运行实例可通过 `bash scripts/infra/up.sh --metrics` 重新应用可选来源。Business 使用 `bash business/scripts/start.sh -redis`。首次 ACL 启动切换须重建 Redis 容器，标准入口保留原数据卷；此前运行的旧 `requirepass` 容器不能仅靠 `--metrics` 切换。未启用来源也保留 Infra 原默认账号、Business 原 admin／reader 的认证及权限配方。

`redis-authentication.sh` 在启动时生成唯一原生 ACL 文件；只将 Redis 数据卷中经过严格校验的本方采集记录追加其中。记录损坏时输出固定诊断并跳过可选账号，原业务认证照常启动；来源生命周期仍拒绝该记录。更新仅在 VM 内原子替换本方记录，不使用宿主共享目录替换或全局 `ACL SAVE`。账号状态与私有归属记录按前后版本核验，写入中断只允许精确的旧版本／待发布版本恢复，未知状态拒绝接管。

各自停止入口或关闭开关后再运行相应启动入口，会先删除经归属验证的本方采集容器及配置卷，再完整 reset/off 清权并持久化；Redis 重启后仍停用。停用不依赖 TLS 证书或重新构建镜像，保留私有密码、归属记录和数据卷。已有账号而缺失私有状态、权限／归属漂移或数据库不可核验时明确失败，不重置陌生账号。来源故障不阻止业务 Ready，清理失败仍以非零结果报告。

来源容器为独立 uid、只读根文件系统、无特权和固定资源上限，只连接已确认数据库私网 IP，仅提供客户端证书认证的 `GET /metrics`。管理员凭据只进入安装期的 stdin，不进入长期来源；TLS 与采集配置经有归属的专用卷传递，源容器不读取宿主目录、Docker socket 或 Redis 数据卷。源码构建只发送固定 Go 输入，不发送仓库 `.env` 或私有材料。

Redis已复用同一v2部署发现、System管理员批量确认／有效主机关联与私有来源精确投影；HTTP SD仍沿原mTLS、CIDR／端口及预算准入。Monitor专业查询与Console专业页面已沿原链路在工作区接通：列表按引擎类型筛选，Redis详情分组查看资源／连接、吞吐／命中和持久化状态；容量、时长和布尔状态按指标解释。迁移及功能须按前置提交顺序发布，本地测试不代表个人环境已应用或正式用户全链路通过。来源已启动不能计作正式监控完成，也不承诺 Docker 自行重启后的无人值守恢复。`make test-monitor-redis-source-unit` 覆盖确定性转换；`make test-monitor-redis-source` 复用独占 Redis 标准夹具，验证两作用域的真实账号、mTLS、重启持久化、清权及零残留。Business 原认证与样例回归使用 `make test-business-redis`。


### Redis／MinIO 既有来源恢复

需要单独恢复引擎来源时，由部署者显式选择作用域和引擎类型。例如，同时恢复 Infra 和 Business 的三类引擎来源时，执行 `python3 scripts/infra/metrics-sources.py recover --scope infra --scope business --kind postgresql --kind redis --kind minio`。恢复不重新安装、启用或轮换账号，不重新构建来源镜像；健康来源保持原容器。若同一数据库容器仅重新启动或地址变化，或本方来源已停止／删除，则在原安装、账号及私有卷仍可证明的前提下，只恢复来源。

- **Redis 专属校验**。核对私有状态、已提交且启用的持久记录和精确 ACL。
- **MinIO 专属校验**。核对原父身份、归属、原生策略、启用状态及固定指标认证。
- **共享来源与私有卷校验**。核对原 Compose、镜像归属、来源标签、只读挂载和原私有卷中的四个固定文件。卷检查使用短时、无网络、非 root、固定资源限额的临时容器，挂载范围限于本来源的只读私有卷，退出时按本次随机标记回收。
- **拒绝与失败清理**。证书内容、端口或私有身份字段漂移，缺少安装证明，出现陌生资源、停用身份或新数据库容器 ID 时，拒绝自动接管，由部署者显式执行标准 `up` 重新应用。恢复前后重读数据库和账号状态，重建失败时清理范围仅限本方来源。

具体事实边界及门禁见[统一恢复规范](../../../docs/spec/addp平台运行观测规范.md#已安装引擎采集来源的统一恢复)。

**原镜像不可用**。`recover` 只使用已核验的本地原镜像。即使来源容器仍在运行，原镜像缺失或读取失败时，仍报告“原采集镜像不可用”并保留当前来源。具体原因以只读检查核对，诊断只显示固定信息。部署者通过统一入口显式重新构建和应用本方来源，例如 `up --scope infra --kind minio`，其他作用域或协议须明确选择对应项。重建范围仅限采集来源，数据库进程保持原状。

### 统一采集分组

指标中心和数据库沿各自的部署归属管理。主机采集服务使用唯一名称，引擎采集服务以作用域区分。每个引擎来源使用自己的私网、账号、私有卷和证书，主机来源使用独立的宿主／Desktop 网络视图。PostgreSQL 的 Exporter 与 mTLS 入口分别运行，数据库凭据只交给 Exporter。查询、恢复和清理须限定项目与服务，并核对工作区、作用域和对应的数据库身份。使用统一入口按 `--scope`、`--kind` 选择操作对象，禁止项目级 `down`、`--remove-orphans` 和跨来源清理。[运行观测规范的统一部署分组](../../../docs/spec/addp平台运行观测规范.md#采集来源统一部署分组2026-11-04)

原带工作区摘要的分组需要逐来源显式应用以切换名称，例如 `python3 scripts/infra/metrics-sources.py up --scope infra --kind minio`。该命令核验并退役旧分组中的对应来源，随后在固定分组重建本来源；其他来源不变。逐项确认后，可用同一入口选择多个 scope／kind 应用。主机单独显式选择 `--scope host --kind node`。普通启动的 `recover` 不负责迁移；旧安装声明或镜像不可用时，按输出提示显式应用。应用涉及短暂采集中断，不删除引擎或指标历史。
