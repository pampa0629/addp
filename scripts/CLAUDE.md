# scripts/ 目录使用规范

本文件为 Claude Code 在 scripts/ 目录中工作时的指导说明。

## 目录结构说明

```
scripts/
├── build/          # 构建相关脚本（Docker 镜像构建、Go 编译等）
├── dev/            # 开发环境脚本（启动、停止、重启、模块管理）
├── infra/          # 基础设施脚本（PostgreSQL、Redis、MinIO、Meilisearch 初始化）
├── local/          # 本地开发辅助脚本
├── migrations/     # 数据库迁移脚本
├── prod/           # 生产环境脚本（健康检查、等待基础设施就绪）
├── registry/       # 服务注册相关脚本
├── test/           # 测试相关脚本
└── utils/          # 通用工具脚本（依赖检查、端口验证、颜色输出等）
```

## 重要规则

### 1. 禁止自行创建目录

**未经用户明确允许，不得在 scripts/ 下创建新目录。**

- ✅ 可以在现有目录中创建新脚本
- ✅ 可以修改现有脚本
- ❌ 禁止创建新的一级子目录
- ❌ 禁止创建新的二级子目录

**原因**：scripts/ 目录结构已经规划好，新增目录会破坏现有的组织结构。

**正确做法**：
1. 如果需要创建新脚本，先判断应该放在哪个现有目录
2. 如果现有目录都不合适，**必须先询问用户**，说明原因并征求同意
3. 用户同意后再创建新目录

### 2. 脚本分类规则

**创建新脚本时，按功能归类到对应目录**：

- **dev/** - 开发环境相关（启动、停止、重启、日志、模块管理）
- **prod/** - 生产环境相关（部署、健康检查、监控）
- **infra/** - 基础设施初始化（数据库、缓存、存储、搜索引擎）
- **build/** - 构建相关（编译、打包、镜像构建）
- **utils/** - 通用工具（不依赖特定环境，可被其他脚本复用）
- **test/** - 测试相关（集成测试、API 测试、性能测试）
- **migrations/** - 数据库迁移脚本
- **registry/** - 服务注册和发现相关

**判断标准**：
- 如果脚本是工具性质（被其他脚本 source 引用），放在 `utils/`
- 如果脚本只在开发环境使用，放在 `dev/`
- 如果脚本只在生产环境使用，放在 `prod/`
- 如果脚本用于初始化基础设施，放在 `infra/`

### 3. 共享工具脚本规范

**utils/ 目录专门存放可复用的工具脚本**：

- `colors.sh` - 终端颜色输出变量（被 dev 脚本引用）
- `check-deps.sh` - Go 依赖版本一致性检查
- `check-deps-version.sh` - 依赖版本验证
- `ports-validate.sh` - 端口占用检查
- `detect-common.sh` - Common 模块依赖检测
- 其他通用工具...

**工具脚本特点**：
- 可以被其他脚本通过 `source` 引用
- 或作为独立命令行工具使用
- 不依赖特定的运行环境（dev/prod）
- 功能单一、职责明确

### 4. 脚本命名规范

- 使用小写字母和连字符：`start.sh`、`check-deps.sh`
- 名称应清晰表达功能：`ports-validate.sh` 而非 `validate.sh`
- 避免过于简短的名称：`modtidy.sh` 虽然简短但语义明确

### 5. 脚本文档规范

**每个脚本应包含头部注释**：

```bash
#!/bin/bash
# script-name.sh - 简短描述
#
# 功能:
#   1. 主要功能点1
#   2. 主要功能点2
#
# 用法: bash scripts/category/script-name.sh [options]
#
# 选项:
#   -h, --help    显示帮助信息
#   -v, --verbose 详细输出

set -e
```

## 工作流程

### 创建新脚本时

1. **明确脚本功能**：这个脚本是做什么的？
2. **判断归属目录**：参考上述分类规则
3. **检查是否需要新目录**：99% 的情况下应该能归类到现有目录
4. **如果现有目录都不合适**：
   - 停止操作
   - 向用户说明情况："这个脚本的功能是 XXX，现有的 dev/prod/infra/utils 等目录都不太合适，建议创建新目录 `scripts/新目录名/`，是否同意？"
   - 等待用户明确同意后再创建

### 修改现有脚本时

1. **先阅读脚本**：理解现有逻辑和代码风格
2. **保持一致性**：遵循脚本现有的风格和命名约定
3. **避免破坏性修改**：除非用户明确要求重构
4. **测试修改**：修改后建议运行脚本验证

## 示例

### ✅ 正确示例

**场景**：需要创建一个检查前端依赖版本的脚本

```bash
# 分析：这是一个工具脚本，类似于 check-deps.sh
# 决策：放在 utils/ 目录
# 文件：scripts/utils/check-frontend-deps.sh
```

**场景**：需要创建一个自动重启某个模块的脚本

```bash
# 分析：这是开发环境使用的脚本
# 决策：放在 dev/ 目录
# 文件：scripts/dev/restart-module.sh
```

### ❌ 错误示例

**场景**：需要创建一个监控脚本

```bash
# ❌ 错误：直接创建新目录
mkdir scripts/monitoring/
touch scripts/monitoring/monitor.sh

# ✅ 正确：先询问用户
# "我需要创建一个监控脚本，可能需要多个监控相关的脚本。
#  现有的 prod/ 目录主要是部署相关，utils/ 是工具脚本。
#  建议创建 scripts/monitoring/ 目录专门存放监控脚本，是否同意？"
```

## 总结

**核心原则**：
1. 🚫 **不创建目录** - 除非用户明确同意
2. 📂 **归类清晰** - 新脚本必须归类到现有目录
3. 🤔 **存疑就问** - 不确定时询问用户
4. 📝 **文档完善** - 脚本包含清晰的注释和使用说明

这些规则确保 scripts/ 目录保持整洁、结构清晰、易于维护。
