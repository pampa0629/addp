# ADDP 模块选择启动指南

[返回脚本导航](../README.md) · [启动、重启与停止速查](启动脚本使用指南.md)

本指南说明本机源码开发如何选择启动范围。模块参数决定需要启动的服务及依赖，不等于强制编译或全量重启；生命周期操作与排障统一见[启动脚本使用指南](启动脚本使用指南.md)。

## 选择一个或多个模块

从项目根目录选择当前需要联调的模块：

```bash
# 启动 Manager 及其依赖
bash scripts/dev/start.sh -manager

# 同时选择多个模块，启动其依赖并集
bash scripts/dev/start.sh -asset -meta

# 无参数或显式 -all：全量启动
bash scripts/dev/start.sh -all
```

多个模块参数支持任意顺序，重复项去重；`-all` 不能与模块参数混用。已运行的本工作区服务复用，缺失项才启动；代码变化需要通过重启入口应用。

`-gateway` 和 `-console` 分别选择脚本定义的一组后端或平台前后端，不等于无参数全量启动。需要完整开发清单时使用无参数或 `-all`，具体模块选项以[启动脚本参数定义](../dev/start.sh)为准。

## 如何合并依赖

普通模块选择都保留 System Backend、Gateway 和 Console。Meta Backend/Worker 按选择结果决定；不统一拉起全部模块前端，也不统一拉起 Engine Runtime。

| 选择范围 | 启动清单中的关键内容 |
| --- | --- |
| 单独选择 `-asset`、`-catalog` 或 `-ontology` | 启动所选模块的 Backend/Frontend 及上述公共入口；不包含 Meta Backend/Worker |
| 仅组合上述三个模块 | 按并集合并各模块 Backend/Frontend，仍不包含 Meta Backend/Worker |
| 同时选择 `-meta` 或其他需要 Meta 的模块 | 包含 Meta Backend/Worker；显式选择 `-meta` 时同时启动 Meta Frontend |
| `-manager` | Manager Backend/Frontend、Meta Backend/Worker、Transfer Backend/bounded Worker/continuous Worker；不因 Manager 自动启动 Transfer Frontend |
| `-transfer` | Transfer Backend/Frontend、bounded Worker 与 continuous Worker，以及公共依赖 |
| `-model` | Model Backend/Frontend、Standard Backend/Frontend，以及公共依赖 |
| `-quality` | Quality Backend/Frontend/Worker、Standard Backend，以及公共依赖；不因 Quality 自动启动 Standard Frontend |
| `-workbench` | Workbench Backend/Frontend、Service Backend，以及公共依赖 |
| `-portal` | Portal Backend/Frontend、Asset Backend，以及公共依赖；不因 Portal 自动启动 Asset Frontend |
| `-copilot` | Copilot Backend、Develop Backend，以及公共依赖 |

例如 `-asset -meta` 会增加 Meta Backend/Worker/Frontend；`-asset -catalog` 仍不启动 Meta。需要额外模块页面时显式追加对应模块，避免把后端依赖误认为同时启动其前端。

Catalog、Workbench 是 Asset 相关业务操作的运行时软依赖，不随 Asset 隐式启动。单独选择 `-asset` 时，运行中的 Console 复用，前端就绪检查只覆盖本次清单中的 Asset 和 Console。

Backend 先完成所属迁移并达到 `/health/ready`，再启动自己的 Worker；不同模块仍可并行。已初始化数据库中的 Worker 独立重启规则与启动编排分开，详见[生命周期规范](../../docs/spec/addp开发服务生命周期与构建身份规范.md#模块迁移与-worker-启动顺序)。

## 显式选择 Runtime 联调

业务模块不会隐式启动 DuckDB、Workflow 或 Jupyter 等引擎。需要空间计算联调时，将 Develop 与所需 Runtime 一起选择，例如：

```bash
bash scripts/dev/start.sh -develop -geopython-workflow
```

Manager 需要三维或点云快显转换时，同样显式选择对应 Runtime：

```bash
bash scripts/dev/start.sh -manager -model3d-workflow -pointcloud-workflow
```

Math Workflow 随无参数或 `-all` 全量启动，也可显式选择 `-math-workflow`；单独选择 `-develop` 不包含 Math。服务启动后仍需在 System 中手动注册，操作见 [Math README](../../engines/math-workflow/README.md#开发启动)。

PointCloud、Document 等 Runtime 的原生开发准备，以及 SuperMap 完整 SDK、基础镜像与许可要求，统一见[Runtime 准备说明](启动脚本使用指南.md#显式启动-runtime)和对应引擎文档。SuperMap 不随 `-develop` 单独拉起；其登记要求遵循[引擎与端口规范](../../docs/spec/addp端口分配.md)，不由启动命令推断已登记可用。

无参数全量启动包含默认 Runtime。Manager 自己的 Raster Mosaic Runtime 随 Manager 标准入口管理，其归属与准备要求见[生命周期规范](../../docs/spec/addp开发服务生命周期与构建身份规范.md#三运行时依赖构建输入)。

## 重启与停止的范围

所选模块及显式 Runtime 的重启、停止命令、内容指纹构建与局部范围，统一见[启停操作速查](启动脚本使用指南.md#选择操作)；Swagger 预检、停止失败不得继续准备或启动等规则见[启动与重启边界](启动脚本使用指南.md#启动与重启边界)。

启动选择器和停止范围分别解释：`start.sh -gateway` 可补齐其后端清单，`restart.sh -gateway` 的停止范围仅为 Gateway，随后补齐缺失依赖。当前 `restart.sh` 不接受 `-console`；全量重启使用 `-all`。完整支持参数分别以[启动脚本](../dev/start.sh)、[重启脚本](../dev/restart.sh)和[停止脚本](../dev/stop.sh)为准。

局部停止保留运行中的公共依赖。工作区锁、进程归属、停止顺序、失败记录与保活退出范围统一见[停止与进程归属](启动脚本使用指南.md#停止与进程归属)。

## 运行状态与验证

- 访问地址以本次启动输出和 `.dev-state/ports.env` 为准，Infra 映射用 `bash scripts/infra/status.sh` 查询；冲突、归属与 Online 显式端口规则见[端口规范](../../docs/spec/addp端口分配.md)。
- PID、实例日志与启动失败的只读检查见[排查失败](启动脚本使用指南.md#排查失败)，不通过固定模块日志文件或无认证业务请求判断启动是否成功。
- 模块选择用于开发环境联调，不替代测试。改动验证走 `make test-changed` 或对应 owner 的 `make test-module`，分层与真实运行验收见[测试规范](../../docs/spec/addp测试与验收规范.md)。
