测试分层、身份和清理规则以[测试与验收规范](../../docs/spec/addp测试与验收规范.md)为准；历史结果仅适用于所列源码和运行尝试，不代表当前 HEAD 已重跑。

## 模块与消费方恢复

`module-registry-recovery` 要求专用部署中的 `GATEWAY_URL`、`SYSTEM_URL`、`MANAGER_URL` 和现有 `MANAGER_SERVICE_CLIENT_SECRET`。Host Gate 先通过受保护的正式进程入口依次启动 Manager、System、Gateway，验证 Manager 在 System 前为 Alive/Not Ready 且业务路由返回 `module_not_ready`，System 到达后以同一 `instance_id` Ready，Gateway 首个快照建立路由；随后停止 System，等待 Manager 转为 Not Ready、租约路由消失，再恢复 System 并验证 Manager 和 Gateway 无需重启即恢复。五个阶段分别写入 `module-lifecycle-*.json`。正式 Manager 优雅停止后，owner 套件再使用 `addp-manager` Platform Service Principal 获取短期 Token，经 System 正式注册、心跳和注销 API验证两个回环探针的幂等注册、租约失效、同 ID 恢复、双实例路由、发布元数据更新、优雅注销和零活跃实例残留。`ADDP_ONLINE_PROCESS_TIMEOUT_SECONDS`、`ADDP_ONLINE_ROUTE_TIMEOUT_SECONDS` 和 `ADDP_ONLINE_LEASE_TIMEOUT_SECONDS` 分别控制正式进程、路由和租约收敛上限。

`consumer-engine-recovery` 要求全量 ADDP 服务、Console、Manager、Service 和一个专用 PostgreSQL Engine Fixture。Host Gate 通过 `business/scripts/online-engine-fixture.sh` 管理物理端点，该入口只允许 `ADDP_ONLINE_HOST=1` 的 macOS 专用 Runner，使用独立 `ADDP_ONLINE_TEST_ENGINE_*` 变量并拒绝接管非 `business/postgres` Compose 容器；它不读取或创建 `business/.env`。suite 使用真实测试 User 用户名和密码登录 Console，并以同一 User 的 Access Token 校验 Tenant AuthContext 与最小权限。Configuration、Manager Data Explorer、Service Query Services 在同一 Browser Context 中各首次导航一次并等待自身首个请求成功；随后保持同一 Manager iframe，停止/恢复物理 Fixture，并通过 `POST /api/v1/system/engines/{id}/test` 记录 `offline → online`，页面必须通过既有轮询自动收敛。Manager、Service Backend 与 Console、Manager、Service Frontend 的 PID 前后必须一致。Engine Instance 由专用环境长期预置，suite 不创建、删除或修改其身份；退出路径恢复 `online` 后再停止 Fixture 与应用。

## 关系型 SQL 与指标服务

`transfer-relational-sql-etl` 唯一使用 GitHub Hosted `ubuntu-24.04` x86_64 临时部署，在 `Online T4 gates` 手工选择该 suite 即可，不需要自托管 Runner、永久账号或外部环境文件。`online-hosted-transfer-gate.sh` 复用 Hosted 公共生命周期，建立独立 Infra、非默认 Tenant、具备精确 10 项 Permission 的真实测试 User，并通过独立 Provisioner 和 System API 注册当次 PostgreSQL Engine Instance。Business Fixture 使用本轮独占的 tmpfs 容器；数据库用户只读取源表并在指定 schema 创建自己的目标表。正式启动脚本启动 Transfer、Meta、Manager、System、Gateway 和 Console，业务断言仍只有 `make test-online ONLINE_SUITE=transfer-relational-sql-etl` 一条入口。

同一 suite 验证原生表字段改名、decimal 精度转换、常量生成、replace 旧入边关闭和两跳自动采集，并从 Console Manager iframe 验证字段图与结构快照；SQL 查询源由真实浏览器构造投影和参数化过滤，验证 2 行结果及字段血缘 unavailable。四个临时任务通过正式 API 删除，Business owner 校验三个目标表的数据与精度。成功、失败和中断路径均销毁业务容器、Infra 数据卷及 owner-only 凭据目录，残留使门禁失败；强制终止不能声称清理完成。Actions Artifact 仅归档报告、截图、脱敏日志和清理证据。确定性验证使用 `make test-online-runner` 与 `make test-platform`；首次真实 T4 成功前只登记手工触发。

`metric-service-revision-lifecycle` 唯一运行于 GitHub Hosted `ubuntu-24.04`，从 `Online T4 gates` 手工选择同名 suite，并用 `metric_engine` 选择 `postgresql` 或 `tidb`；手工运行只验收所选引擎，每日夜间调度分别验收两个引擎，无需专用 Mac、预置 Tenant 或仓库 Secret。`online-hosted-metric-gate.sh` 复用 Hosted 生命周期及 System 临时身份入口，启动独立 Infra 与所选只读业务引擎。TiDB 使用固定 digest 的 PD/TiKV/TiDB 临时 Compose 集群；两种引擎均通过真实 API 扫描并建立 Standard 定义、逻辑表、关系和指标修订，复用同一指标契约和确定性结果。仅当次身份凭据与引擎描述写入 `runner.temp` 的 owner-only 文件，不接受永久业务环境提供的 ID 或数据。

业务断言仍只走 `make test-online ONLINE_SUITE=metric-service-revision-lifecycle`：首次查询得到非空确定结果；发布新修订不自动重绑；旧修订撤回后 Model 返回 `409 metric_implementation_state_conflict`、Service 返回 `500 query_execution_failed` 且服务仍 active、绑定不变；显式重绑后恢复相同数据。临时服务按 ID 删除并确认 404；指标历史在运行期间保留，随后与整套临时部署共同销毁，无历史记录强删旁路。

报告 `metric-service-revision-lifecycle.json` 记录引擎类型、Run ID、实现/修订/服务 ID、校验结果与临时服务清理状态；Hosted `summary.txt` 另记录部署销毁结果。两者及脱敏日志由 Actions Artifact 保留 14 天，不归档凭据、连接密码、原始计划或查询结果正文。强制终止时不得声称清理通过，Runner 的临时 VM 回收承担最终隔离。确定性回归统一由 `make test-online-runner` 与 Platform CI 覆盖；PostgreSQL 与 TiDB 已在同一提交分别完成首次真实通过，夜间两个 Job 保留独立引擎标识和清理证据。

## Workbench 与关系引擎

`workbench-service-consumption` 要求全量 System、Gateway、Service、Workbench 和 Console，并使用 `business/scripts/online-workbench-mysql-fixture.sh` 管理独立 Business MySQL。Fixture 只接受仓库外 `ADDP_ONLINE_WORKBENCH_MYSQL_*` 变量，不读取或创建 `business/.env`；它重建仓库已有确定性样例并把 Engine 使用的账号收敛为仅有 `SELECT` 的读取账号。suite 分离非管理员专用 User Token 与同 Tenant 的专用 Tenant Administrator Token：前者使用永久 MySQL Engine Instance，经 Gateway 检测 Service 输出契约，临时发布主 SQL 服务 `commerce-order-analysis` 和同契约未授权服务 `commerce-order-analysis-denied`，再经 Consumer Descriptor 直接创建含 Table、Chart 两个 Component 的未发布 Data Application；后者只经 System 正式 API 创建仅授权主服务的 API 消费方和一枚进程内凭据。API 层真实验证 cursor、动态筛选、标量类型、有限 CSV、无空间输出、契约指纹变化，以及 API Key 对已授权服务的 200、对未授权服务的 403、对控制面的 401 和删除后 45 秒内收敛失效；浏览器层以非管理员 User 登录 Console，在正式 Component 编辑器中验证两种 renderer 及契约变化后的预览阻断。Host Gate 安装专用 Chromium；完整 API Key 不得进入报告或日志，API 消费方及级联凭据、未发布 Data Application 与两个 Query Service 只按本轮创建 ID 在 `finally` 删除，不使用名称前缀或数据库清理，也不为自动化测试增加已发布应用强删旁路。

`oceanbase-consumer-flow` 要求全量 System、Gateway、Meta、Manager、Transfer、Develop 和 Service，并使用 `business/scripts/online-oceanbase-consumer-fixture.sh` 管理独立 OceanBase CE。专用环境预置永久 `engine_type=oceanbase` Engine Instance；Fixture 固定维护 5 行 InnoDB watermark 源表和同构空目标表。suite 经 Gateway 和 Meta 获取正式 ResourceLocator，只创建一条 bounded watermark + upsert Transfer 任务，连续执行并精确断言 5 行首批、2 行增量和 0 行空增量；Manager 表预览、Develop SQL 与临时 Query Service 通过各自正式数据出口读取同一目标表，最终必须得到相同的 6 行 checksum，Manager 还校验扫描列顺序。任务和服务按捕获 ID 删除并确认 404，Fixture 在退出路径恢复源表基线和空目标表。该 suite 仅可从手工 workflow 运行，首次真实通过前不得增加 schedule。

`opengauss-consumer-flow` 使用同一个 `relational-consumer-flow-online.py` 断言 Manager、Transfer、Develop 和 Service，上层流程只通过通用 Engine Plugin/Provider 和 SQLDialect 工作。由于 openGauss 6.0.6 官方容器的 NUMA 限制，该 suite 使用 GitHub Hosted `ubuntu-24.04` x86_64 profile：`online-hosted-opengauss-gate.sh` 通过正式 Infra 生命周期在镜像缺失时从 `scripts/infra/Dockerfile.postgres` 构建 x86_64 PostgreSQL 镜像，再从固定 SHA-256 官方介质创建独占 openGauss，启动 disposable `addp_online` Infra 及 Manager/Transfer/Develop/Service 参与链路；Business Fixture 只输出 owner-only Engine 描述，System IAM owner helper 创建非默认 Tenant、仅含租户可定制业务 Permission 的最小消费 User，并把一次性 Engine Provisioner 绑定到正式内置 `tenant.infrastructure_administrator` Role。通用 `online-engine-registration.py` 使用 Provisioner Token 通过正式 System API 注册并验证当次 Engine Instance，随后立即从业务断言环境清除该 Token 与数据库凭据；consumer 不访问 System Engine 控制面，只验证 Manager、Transfer、Develop 和 Service 的消费路径，证据另写入 artifact 目录。成功、失败和中断均停止应用、删除 openGauss 容器并销毁 Infra 数据卷。它不读取根 `.env`、Business `.env`、GitHub Environment 或外部实例。2026-09-10 的 [Online T4 run 34469670386](https://github.com/pampa0629/addp/actions/runs/34469670386) 已确认构建身份、5/2/0 watermark、三出口同 checksum、清理和零残留全部通过，因此当前同时保留手工 `workflow_dispatch`，并在每日 `20:30 UTC` 只调度该 Hosted profile。

`tidb-consumer-flow` 与 OceanBase/openGauss 复用同一个 `relational-consumer-flow-online.py`，只新增 `engine_type=tidb` 的 database catalog profile，不在 Manager、Transfer、Develop 或 Service 增加数据库分支。macOS 专用 Runner 预置永久 TiDB Engine Instance，并在仓库外环境文件提供 `ADDP_ONLINE_TIDB_ENGINE_ID`、`ADDP_ONLINE_TIDB_PORT`、`ADDP_ONLINE_TIDB_DATABASE`、`ADDP_ONLINE_TIDB_USER` 和可为空的 `ADDP_ONLINE_TIDB_PASSWORD`；`online-tidb-consumer-fixture.sh` 复用 T2 的固定 digest、无卷 PD/TiKV/TiDB Compose，重建 5 行源和空目标，推进 2 行 watermark 后由同一 Transfer 任务得到 5/2/0 读取计数，并由 Manager、Develop、Service 比较 6 行同 checksum。任务、服务和三组件在退出路径清理并验证零残留。首次真实通过前仅允许手工 `workflow_dispatch`，不得加入 schedule。

`transfer-insert-only-mysql` 要求全量 System、Gateway、Meta、Transfer 和 Console，并使用 `business/scripts/online-transfer-insert-only-fixture.sh` 同时管理专用 PostgreSQL 源表和可写 MySQL 目标库。suite 以真实 User 登录 Console，经 Transfer 向导选择两端资源；字段映射阶段必须调用正式推荐接口，把无声明精度的 `numeric` 当前值分析为 `DECIMAL(6,2)`，配置阶段再选择仅新增并自动派生 `id` 水位和目标键。页面创建后首轮必须写入 6 行；Fixture 修改旧 `id=1` 并新增 `id=7` 后，从任务详情再次执行只能写入 1 行，最终目标共 7 行、旧值不变、新值存在且无重复键。任务按捕获 ID 删除并确认 404，复合 Fixture 在所有退出路径删除固定表并停止两个容器。该 suite 仅可从手工 workflow 运行，首次真实通过前不得增加 schedule。

## Redis 消费

Redis Online 验收使用 `make test-online ONLINE_SUITE=redis-consumer-flow`，在 `online-t4-gates.yml` 选择该 suite 后由人工 `redis-hosted-t4` Job 执行 `bash scripts/test/online-hosted-redis-gate.sh`。该入口复用 `scripts/utils/hosted-online.sh` 的准入、一次性 Infra、秘密分区及清理；Business owner 脚本 `business/scripts/online-redis-consumer-fixture.sh` 提供固定镜像、只读 ACL 与九个原生样例，System owner helper 创建普通验收用户及独立 Engine provisioner，登记后移除 provisioner 凭据。验收覆盖 System 实时目录、Meta 扫描、Manager 原生预览以及真实 Console Meta 重扫和 Manager 页面，截图、API 与同一 User/Tenant 的浏览器报告归档到仓库外 artifact 目录。脚本/断言确定性门禁是 `make test-online-runner`；登记检查从 Hosted metadata 自动发现 suite 并核对 workflow choice，不需要额外 owner 清单。该 gate 拒绝 macOS、脏 checkout、个人环境与已有资源；首次真实运行前不计为 T4 通过，不纳入夜间执行。
