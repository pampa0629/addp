# ADDP 启动脚本使用指南

[返回脚本导航](../README.md) · [模块选择与依赖](模块选择启动指南.md#选择一个或多个模块) · [开发脚本详细说明](../dev/README.md) · [部署和开发总览](../../docs/guide/addp部署和开发步骤.md#快速开始)

本文用于选择本机源码开发的启动、重启和停止操作。参数、依赖与实现细节统一查阅开发脚本指南和对应规范；容器部署见[开发与容器部署](开发与容器部署.md)。

## 选择操作

以下命令从项目根目录执行：

| 需要完成的操作 | 标准入口 |
| --- | --- |
| 启动完整开发环境 | `bash scripts/dev/start.sh` |
| 启动 Manager 及其依赖 | `bash scripts/dev/start.sh -manager` |
| 修改 Manager 后重启所属服务 | `bash scripts/dev/restart.sh -manager` |
| 重启多个模块 | `bash scripts/dev/restart.sh -meta -transfer` |
| 全量重启 | `bash scripts/dev/restart.sh -all` |
| 仅停止 Manager 所属进程 | `bash scripts/dev/stop.sh -manager` |
| 停止完整开发环境 | `bash scripts/dev/stop.sh` |

`start.sh` 复用已运行的受管服务、补齐缺失依赖，不更新已经运行的代码。需要应用服务代码变化时使用 `restart.sh`。

`restart.sh` 无参数等同 `-all`；所有重启均按构建输入指纹决定是否编译，不能把“无参数”理解为“只重启、不编译”。`-all` 不能与模块参数混用。完整选项见[开发脚本指南](../dev/README.md#restartsh)和脚本参数定义。

`start.sh`、`restart.sh` 均支持多个模块参数。局部重启只更新所选模块的 Backend、Worker、前端及显式 Runtime，保留其他模块和运行中的依赖；停机期间，调用所选模块的功能可能短暂不可用，System、Gateway 的重启尤其影响公共能力。

仅修改支持热更新的前端代码时，通过开发服务器查看变化；确需重启对应模块时选择该模块参数。修改 `common/` 后如需运行验收，按仓库规则在用户终端执行全量重启。

## 启动与重启边界

- 先检查核心 Infra；健康时复用，未就绪时由启动入口调用 `scripts/infra/up.sh`。实际端口从 Compose 映射和 `.dev-state/ports.env` 读取，首选端口不等于运行地址。
- System 先完成公共 schema 初始化与就绪；各模块 Backend 就绪后启动自己的 Worker，模块之间仍可并行。Backend 独占迁移，Worker 只校验 schema；任务持久化和领取规则见[模块任务契约](../../docs/spec/tasks/模块任务契约.md)，Transfer bounded 与 continuous 的 Worker、runtime session 和租约边界见[同步执行契约](../../docs/spec/tasks/Transfer同步执行.md)。
- 指定模块时按依赖并集合并启动清单，复用运行中的依赖。Engine Runtime 使用显式参数启动；无参数全量启动包含默认 Runtime。
- 重启前同步相关 Swagger 并执行覆盖检查；全量先停止再同步，局部在预检通过后停止所选进程，再准备依赖、按需构建和启动。停止失败时不得继续准备或启动；准备失败不得启动该服务，入口返回非零，不自动恢复旧进程；此前已启动的其他服务可能仍在运行。

完整顺序、工作区锁、原子构建及构建身份见[生命周期规范](../../docs/spec/addp开发服务生命周期与构建身份规范.md)。构建采用内容指纹与缓存，不通过 touch 源码时间戳触发。

启动输出反映本次选择、准备与健康检查结果。耗时取决于工具链、依赖缓存、首次原生构建及所选模块，不以旧终端输出或历史耗时表作为当前承诺。

## 显式启动 Runtime

例如需要单独启动或重启 PointCloud：

```bash
bash scripts/dev/start.sh -pointcloud-workflow
# 修改后由用户在终端执行
bash scripts/dev/restart.sh -pointcloud-workflow
```

Runtime 的准备方式各不相同，使用所属文档中的同一条开发路径：

| Runtime | 开发准备与说明 |
| --- | --- |
| PointCloud | 开发使用独立 Conda 前缀隔离 Python/PDAL 及原生库；启动前验证驱动、真实 COPC 转换与点数，失败不启动；产品部署使用正式容器镜像。详见[开发启动](../../engines/pointcloud-workflow/README.md#开发启动)与[产品部署](../../engines/pointcloud-workflow/README.md#产品部署) |
| Document | 开发使用独立 Python venv、私有 LibreOffice 与字体，仅处理可信文件；启动准备只检查依赖完整性、LibreOffice 版本及服务导入，不执行转换。真实中文三页 PPTX 转 PDF 由 `make test-document-native` 独立验证；产品部署保留非 root、只读文件系统等容器隔离。详见[启动说明](../../engines/document-workflow/README.md#启动)与[转换验收](../../engines/document-workflow/README.md#测试) |
| Model3D | macOS Apple Silicon 原生开发使用按指纹绑定的私有工具包，准备时校验完整性并执行真实转换预检；其他开发平台明确拒绝，不回退开发容器。Linux amd64/arm64 产品镜像通过根构建入口每次构建单一平台；原生预检不替代产品镜像或 Hosted Manager T4 验收。详见[原生启动](../../engines/model3d-workflow/README.md#启动)与[产品镜像](../../engines/model3d-workflow/README.md#linux-amd64--arm64-容器) |
| SuperMap | 当前接入 Linux ARM64 iObjects C++ SDK，开发与产品部署均用 Docker；完整 SDK 母版通过 `SUPERMAP_CPP_SDK_PATH` 准备基础镜像，许可更新须重建基础镜像。启动检查 Core 许可可用，不承诺无试用水印；动态 NFS 挂载需 `nfs-common`、Linux mount 权限与 `SYS_ADMIN`。构建及容器权限见[本地依赖与两层镜像](../../engines/supermap-workflow/README.md#本地依赖与两层镜像)，许可限制见[许可边界](../../engines/supermap-workflow/README.md#许可边界) |
| Spark | 原生开发使用 Python 3.11/3.12 venv 和 OpenJDK 11，与 Business Spark Worker 的 JVM 主版本一致；macOS 在宿主机将 `host.docker.internal` 映射到 `127.0.0.1`，Docker Worker 保留内置解析。Driver/Executor 须双向可达，并共用可达的存储端点；产品部署与 Hosted 产品验收使用独立容器入口。详见[配置与启动](../../engines/spark-workflow/README.md#配置与启动)与[连接要求](../../engines/spark-workflow/README.md#driver-与-executor-连接) |

局部 Runtime 重启复用正在运行的依赖；缺失依赖仍由 `start.sh` 补齐，不能据此承诺完全没有 Go 构建。准备阶段在所选服务停止后执行，失败不启动。

## 停止与进程归属

`stop.sh` 根据模块范围收集 PID、子进程和残留监听者，核验当前工作区归属后处理。全量停止先让依赖 System 的模块和 Runtime 退出、完成注销，再停止 System；两阶段各有 5 秒优雅退出窗口，超时才强制终止所属进程。

标准停止保留开发二进制和构建缓存，清理所选前端缓存及成功停止进程的 PID 记录，不停止 Infra 或删除其数据卷。失败时保留错误与身份记录，按[PID 残留说明](../dev/README.md#pid-文件残留)排查；不要按通用进程名强杀，也不要先删 PID 目录再判断归属。

`start.sh`、`restart.sh`、`stop.sh` 和 `keepalive.sh` 使用工作区级生命周期锁。锁被占用时立即失败并显示当前操作信息，不得并行修改 `.dev-pids`、`.dev-bins` 或运行进程；锁继承和释放规则见[生命周期互斥规范](../../docs/spec/addp开发服务生命周期与构建身份规范.md#一生命周期互斥)。

`keepalive.sh` 仅用于命令结束后会回收后台进程的托管环境，整个托管周期持锁、退出清理后释放；即使只托管单模块，退出仍停止当前工作区整套开发服务。开发服务重启由用户在自己的终端执行；本次明确许可及不得接管外部环境等边界见[保活说明](../../docs/guide/troubleshooting/开发服务与构建.md#codex-等托管命令环境中-restartsh-退出后服务立刻不可用)。

## 排查失败

### 端口与启动状态

先保留启动终端的原始报错，核对核心 Infra 与当前工作区实际端口，例如 Manager：

```bash
bash scripts/infra/status.sh
sed -n '/^MANAGER_BACKEND_PORT=/p' .dev-state/ports.env
```

本地首选端口冲突由标准入口避让；已运行的本工作区服务复用映射。对归属不明的监听者不接管；Online 显式端口冲突时失败。检查后的端口抢占仍可能使启动失败，按[端口规范](../../docs/spec/addp端口分配.md)定位，不按固定端口直接终止进程。

### 日志与 PID

有日志读取权限时，从“System → 模块管理 → 服务实例 → 查看日志”定位对应实例。尚未登记就启动失败时，检查受控节点源 `logs/runtime/<module>/<instance_id>/*.jsonl` 和启动终端输出；Runtime 与前端保留各自的启动日志，详见[日志规范](../../docs/spec/addp模块服务运行日志规范.md)。

只读核对受管 PID，例如：

```bash
ps -p "$(cat .dev-pids/manager.pid)" -o pid=,command=
```

PID 文件存在不等于进程仍存活或已就绪，需结合命令行、工作区及监听归属。Backend 使用 `/health/ready`，Runtime 使用各自健康协议；按[开发指南](../dev/README.md#健康检查超时)从当前状态读取实际端口。

### 编译或注册失败

- 编译失败：核对启动输出、[技术栈规约](../../docs/spec/addp技术栈规约.md)与模块依赖，再通过标准入口重试；不直接覆盖 `.dev-bins/` 的正式产物。
- 注册失败：核对 System readiness、模块服务身份、对应 OAuth Client 配置及注册响应，见[登录认证要求](../../docs/spec/addp登录认证的统一要求.md)。不要输出整份 `.env` 或模块 Client Secret。
- 注册、迁移和 Worker 领取条件遵循生命周期及任务规范，不能将注册失败一概视为“不影响服务运行”。

## 测试与运行验收

确定性测试不依赖当前开发服务，也不通过“停止开发环境 → 启动整套服务 → 测试”接管个人环境。选择改动范围对应的标准门禁：

```bash
make test-changed
# 明确单个 owner 时
make test-module MODULE=manager
```

T0–T3、隔离的 T4 Online 与 T5 发布认证分别遵循[测试与验收规范](../../docs/spec/addp测试与验收规范.md)。生命周期实现变更的专项入口为 `make test-dev-lifecycle`；它在临时工作区验证，不操作正在运行的开发服务。
