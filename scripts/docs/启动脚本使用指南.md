# ADDP 启动脚本使用指南

## 📖 概述

ADDP 开发环境提供了三个核心脚本来管理服务的生命周期：

- **[scripts/dev/start.sh](../dev/start.sh)** - 启动完整开发环境
- **[scripts/dev/restart.sh](../dev/restart.sh)** - 智能重启服务（支持选择性编译）
- **[scripts/dev/stop.sh](../dev/stop.sh)** - 停止所有服务

经过深度优化，启动时间从 **47-78 秒** 降至 **25-39 秒**，提速 **50%**。

---

## 🚀 start.sh - 完整启动

### 基本用法

```bash
cd /path/to/addp
bash scripts/dev/start.sh
```

### 启动流程

```
Step 1/6: 启动基础设施 (Docker)
  └─ PostgreSQL, Redis, MinIO, Meilisearch

Step 2/6: 启动 System Backend
  └─ 等待 health check 就绪（5-8 秒）

Step 3/5: 并行启动所有后端服务 + Workers
  ├─ 并行编译 (Manager, Meta, Transfer, Orchestrator, Develop + 3 Workers)
  ├─ 并行启动所有服务
  └─ 并行健康检查（5 个 Backend 同时检查）
  时间: 7-11 秒

Step 4/5: 启动 Python Workflow Engine (Python)
  └─ 依赖检查 + 虚拟环境 + health check (3-5 秒)

Step 5/5: 启动 Gateway
  └─ 必须最后启动（反向代理所有后端，2-3 秒）

Step 6/6: 启动前端服务（并行）
  └─ Console, System, Manager, Meta, Transfer, Orchestrator, Develop (8-12 秒)
```

### 特性

- ✅ **并行编译** - 8 个 Go 服务同时编译
- ✅ **并行健康检查** - 5 个后端同时检查就绪状态
- ✅ **智能服务检测** - 自动跳过已运行的服务
- ✅ **健康检查超时保护** - 60 秒超时，防止无限等待

## 🔄 restart.sh - 智能重启

### 基本用法

```bash
# 场景 1: 只重启服务，不重新编译（最快）
bash scripts/dev/restart.sh

# 场景 2: 重新编译单个模块
bash scripts/dev/restart.sh -manager

# 场景 3: 重新编译多个模块
bash scripts/dev/restart.sh -meta -transfer

# 场景 4: 重新编译所有模块
bash scripts/dev/restart.sh -all
```

### 支持的模块选项

| 选项 | 说明 |
|------|------|
| `-system` | 重新编译 System 模块 |
| `-manager` | 重新编译 Manager 模块 |
| `-meta` | 重新编译 Meta 模块 |
| `-transfer` | 重新编译 Transfer 模块 |
| `-orchestrator` | 重新编译 Orchestrator 模块 |
| `-develop` | 重新编译 Develop 模块 |
| `-gateway` | 重新编译 Gateway 模块 |
| `-all` | 重新编译所有 Go 模块 |

### 使用场景

#### 场景 1: 修改了 Manager 模块的 API

```bash
# 只重新编译 Manager，其他模块使用缓存
bash scripts/dev/restart.sh -manager
```

**效果**:
- Manager 重新编译：~2 秒
- 其他 7 个模块使用缓存二进制
- 总时间：**10-15 秒**（节省 70% 时间）

#### 场景 2: 修改了 common 模块

```bash
# common 模块被所有模块依赖，需要重新编译所有模块
bash scripts/dev/restart.sh -all
```

**效果**:
- 所有模块并行重新编译
- 总时间：**25-35 秒**

#### 场景 3: 只修改了前端代码

```bash
# 不重新编译任何 Go 代码
bash scripts/dev/restart.sh
```

**效果**:
- 直接重启所有服务
- 总时间：**15-20 秒**

#### 场景 4: 修改了 Meta 和 Transfer 模块

```bash
# 只重新编译 Meta 和 Transfer
bash scripts/dev/restart.sh -meta -transfer
```

**效果**:
- Meta 和 Transfer 重新编译
- 其他模块使用缓存
- 总时间：**12-18 秒**

### 实现原理

```bash
# 通过 touch 修改文件时间戳，触发 Go 重新编译
if [[ " ${FORCE_BUILD_MODULES[@]} " =~ " manager " ]]; then
  find manager/backend -type f -name "*.go" -exec touch {} \;
fi

# Go build 检测到文件修改时间变化，会重新编译
# 未修改的模块直接使用缓存的 .dev-bins/addp-* 二进制
```

### 性能对比

| 操作 | 时间 | 说明 |
|------|------|------|
| `restart.sh` | 15-20s | 无编译，最快 |
| `restart.sh -manager` | 10-15s | 单模块编译 |
| `restart.sh -meta -transfer` | 12-18s | 双模块编译 |
| `restart.sh -all` | 25-35s | 全量编译 |

## 🛑 stop.sh - 停止服务

### 基本用法

```bash
bash scripts/dev/stop.sh
```

### 停止流程

```
Phase 1: 收集所有 PID（从 .dev-pids/*.pid）
Phase 2: 并发发送 TERM 信号（优雅停止）
Phase 3: 等待进程退出（最多 5 秒）
Phase 4: 强制杀死残留进程（SIGKILL）
Phase 5: 兜底清理（pkill 清理可能的残留）
Phase 6: 清理临时文件和 PID 文件
```

### 特性

- ✅ **优雅停止** - 先发送 SIGTERM，给进程清理资源的机会
- ✅ **强制清理** - 5 秒后仍未退出的进程强制杀死
- ✅ **兜底机制** - pkill 清理所有可能的残留进程
- ✅ **清理缓存** - 清理 go-build 临时文件和 PID 文件

### 预期输出

```
🛑 停止 ADDP 开发环境

发现 18 个进程，发送 TERM 信号...
等待进程优雅退出（最多 5 秒）...

✓ 所有服务已停止（优雅退出）

清理临时文件和缓存...
✓ go run 临时文件已清理
✓ PID 文件已清理

========================================
✓ 所有服务已停止并清理完成
========================================
```

## 🎯 使用最佳实践

```bash
# 1. 首次启动（完整启动）
bash scripts/dev/start.sh

# 2. 修改了 Manager 模块代码
bash scripts/dev/restart.sh -manager

# 3. 修改了 common 模块代码（影响所有模块）
bash scripts/dev/restart.sh -all

# 4. 只修改了前端代码
bash scripts/dev/restart.sh

# 5. 结束开发，停止所有服务
bash scripts/dev/stop.sh
```

### 故障排查工作流

```bash
# 1. 某个服务出现问题，重启该服务
bash scripts/dev/restart.sh -meta

# 2. 问题未解决，查看日志
tail -f logs/meta-backend.log
tail -f logs/meta-backend-stderr.log

# 3. 修复代码后，重新编译并重启
bash scripts/dev/restart.sh -meta

# 4. 验证问题是否解决
curl http://localhost:8082/health
```

## ❓ 常见问题

### Q1: 为什么 restart.sh 比 start.sh 快？

**A**: `restart.sh` 默认不重新编译，直接使用缓存的二进制文件（`.dev-bins/addp-*`），节省了编译时间。

### Q2: 什么时候使用 `-all` 选项？

**A**: 以下情况需要使用 `-all`:
- 修改了 `common` 模块（被所有模块依赖）
- 修改了多个模块，不确定影响范围
- 更新了 Go 依赖（`go.mod`）
- 长时间未编译，想确保所有模块最新

### Q3: 服务启动失败怎么办？

**A**: 按以下步骤排查:
```bash
# 1. 查看日志
tail -f logs/<service>-backend.log

# 2. 检查端口是否被占用
lsof -ti :8081  # 检查 Manager 端口

# 3. 检查基础设施是否正常
docker ps  # 确认 PostgreSQL, Redis, MinIO 运行正常

# 4. 重新启动
bash scripts/dev/stop.sh
bash scripts/dev/start.sh
```

### Q4: 为什么 Workers 可以与 Backends 并行启动？

**A**: Workers 只依赖 Redis (Asynq 队列)，不依赖对应的 Backend API。它们直接访问数据库执行任务，不通过 HTTP 调用。

### Q5: System Backend 为什么要先启动？

**A**: Manager/Meta/Transfer 模块启动后会异步注册能力到 System。虽然注册失败不影响服务运行，但 System 先启动可以确保注册成功。

### Q6: 如何查看所有服务的 PID？

**A**:
```bash
# 方法 1: 查看 .dev-pids 目录
ls -l .dev-pids/

# 方法 2: 查看进程
ps aux | grep "addp-"

# 方法 3: 启动脚本会打印所有 PID
bash scripts/dev/start.sh
# 输出包含:
# 后端服务 PID:
#   System Backend:       12345
#   Manager Backend:      12346
#   ...
```

## 🔧 故障排查

### 问题 1: 编译失败

**症状**: 某个服务编译失败
```
✗ 编译 manager 失败，查看日志
```

**排查**:
```bash
# 手动编译查看详细错误
cd manager/backend
go build -o ../../.dev-bins/addp-manager ./cmd/server
```

**常见原因**:
- Go 版本不匹配（需要 Go 1.23+）
- 依赖未下载（`go mod download`）
- 代码语法错误

### 问题 2: 健康检查超时

**症状**: 服务启动超时
```
✗ Manager Backend 启动超时
查看日志: tail -f logs/manager-backend.log
```

**排查**:
```bash
# 1. 查看日志
tail -f logs/manager-backend.log
tail -f logs/manager-backend-stderr.log

# 2. 检查进程是否真的启动失败
ps aux | grep addp-manager

# 3. 手动启动查看错误
.dev-bins/addp-manager
```

**常见原因**:
- PostgreSQL 未启动
- Redis 未启动
- 配置文件错误（`.env`）
- 端口已被占用

### 问题 3: 端口被占用

**症状**:
```
✗ 端口 8081 已被占用 (PID: 12345)
```

**解决**:
```bash
# 方法 1: 停止所有服务
bash scripts/dev/stop.sh

# 方法 2: 手动杀掉占用端口的进程
kill -9 12345

# 方法 3: 查找并杀掉所有 ADDP 进程
pkill -9 -f "addp-"
```

### 问题 4: 能力注册失败

**症状**: 日志显示
```
⚠️ 能力注册失败（不影响服务运行）
```

**排查**:
```bash
# 1. 确认 System Backend 已启动
curl http://localhost:8180/health

# 2. 检查 INTERNAL_API_KEY 配置
cat .env | grep INTERNAL_API_KEY

# 3. 重启服务，能力会重新注册
bash scripts/dev/restart.sh -manager
```
