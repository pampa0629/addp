## 三、编译和构建 (build/)

仓库只维护根 `Makefile`，不允许模块级 Makefile。正式构建只提供两个标准入口：`make build` 调用 `scripts/build/compile.sh`，`make build-images` 调用 `scripts/build/build-images.sh`。构建事实只维护在这两个脚本中，不得在 Makefile、Workflow 或其他脚本中复制服务清单和构建命令。需要传递参数时分别使用 `BUILD_ARGS="..."` 和 `IMAGE_BUILD_ARGS="..."`。

生命周期入口同样只做脚本薄封装：开发环境使用 `make dev-start/dev-restart/dev-stop`，基础设施使用 `make infra-up/infra-restart/infra-down/infra-status`，生产环境使用 `make prod-start/prod-restart/prod-stop/prod-health`。模块级 `go run`、直接 Compose 生命周期目标和兼容别名均不保留；模块参数通过 `make dev-restart ARGS="-<模块名>"` 传递。

### 核心脚本

| 阶段 | 标准入口 | 输入与产物 |
| --- | --- | --- |
| Go 编译 | `make build` | Go 构建输入 → `dist/{BUILD_TYPE}-{GOOS}-{arch}/` |
| 产品镜像构建 | `make build-images` | 对应架构的 Go 产物或 Runtime/前端源码 → 产品镜像；普通模式同时推送 |
| 跨 Registry 推送 | `bash scripts/build/push-images.sh` | 本机源镜像 → 目标 Registry；构建目标就是发布目标时无需重复执行 |
| 部署包生成 | `bash scripts/build/package.sh` | 已有镜像或 Registry 配置 → images 包或 registry 配置目录 |

参数、环境变量、平台限制及失败边界唯一维护在 [Build 指南](../build/README.md)。SuperMap 私有基础镜像的首次准备与升级见该指南的[专节](../build/README.md#build-supermap-workflow-basesh)。

### 完整构建流程

1. 确定目标 Linux 架构、Registry、版本及所需服务。源码开发进程使用 Dev 生命周期；发布镜像使用对应 Linux 产物，不能混用本机 OS 二进制。
2. 所选镜像需要预编译 Go 产物时先运行 `make build`；再通过 `make build-images` 构建产品镜像。默认推送到所选 Registry；仅做单平台镜像验证时使用 `--verify`，它仍会预热并推送基础镜像。
3. 构建 Registry 与发布 Registry 不同时，先登录目标 Registry，再调用推送脚本。核对实际成功、缓存复用和缺失跳过项，不把退出码为零视为完整交付。
4. 按目标环境选择 `images` 或 `registry` 打包。`images` 导出本机现有镜像并生成 tarball；`registry` 只生成配置目录，目标镜像须已推送。两种模式均不在服务器重新编译应用，脚本不接受 `offline` 参数。
5. 核对镜像与部署配置的架构、版本和凭据，再按 [Local 指南](../local/README.md)或 [Prod 指南](../prod/README.md)部署。已有 `.env` 会随包复制；镜像缺失或导出失败可能仅记录到摘要，包生成成功不能代替完整部署验收。

构建、推送和打包不证明真实业务或发布认证通过。实际 CI 编排与登记边界见[测试与发布入口](测试与发布入口.md#ci-登记与隔离检查)，各层验证使用[统一测试规范](../../docs/spec/addp测试与验收规范.md)中的标准入口。
