# Frontend Docker 构建规范

[返回脚本导航](../README.md) · [镜像构建入口](../build/README.md#build-imagessh)

本文定义前端镜像的构建输入、依赖解析与静态资源要求。正式构建使用根 `make build-images`，服务清单和参数由 `scripts/build/build-images.sh` 唯一维护。

## 核心要求

| 核对项 | 现行规则 |
| --- | --- |
| 构建上下文 | 从仓库根目录构建，`COPY` 源路径包含实际模块前缀，以便同时访问模块与 common-frontend |
| Node 版本 | 根 `.node-version` 是唯一事实源；Dockerfile 声明无默认值的 `ARG NODE_VERSION`，构建入口传入参数 |
| 基础镜像 | 当前前端引用 `localhost:5001/node:${NODE_VERSION}-alpine` 和 `localhost:5001/nginx:alpine`，预热与 Registry 配置沿标准构建入口处理 |
| 锁文件 | 安装前复制模块的 `package.json`、`package-lock.json`，仅通过 `npm ci` 安装；依赖清单与锁文件保持一致 |
| 平台依赖 | 锁文件包含 Rollup 的 Linux arm64-musl 与 x64-musl 可选包；构建阶段不追加架构专用安装命令 |
| 共享依赖 | common-frontend 复用消费模块的依赖，保持 Vue 单一实例；不在共享库中独立安装第二份依赖 |
| 源码输入 | 显式复制构建配置、源码及模块需要的静态资源和许可证材料；不整目录覆盖宿主机 `node_modules`、`dist` 等运行产物 |
| 运行阶段 | 将本次构建的 `dist` 与模块自己的 Nginx 配置复制到静态服务镜像，容器内监听 80 |

锁文件是不可变构建输入。需要更新依赖时，在所属模块的依赖维护流程中修改并提交清单与锁文件，再构建；冻结安装的行为见[npm ci 官方说明](https://docs.npmjs.com/cli/v11/commands/npm-ci/)。

## 构建阶段与参考

| 阶段 | 需要保留的输入或关系 |
| --- | --- |
| 依赖安装 | 先复制依赖清单和锁文件，再执行 `npm ci`；使用本地 `file:../../common-frontend` 的模块还需保留相对目录关系并先提供共享库清单 |
| 共享源码 | 安装后复制 common-frontend 源码；镜像构建阶段的链接指向当前消费模块的同一份 `node_modules`，路径必须与实际 `WORKDIR` 对应 |
| 模块源码 | 按模块实际需要复制 Vite 配置、`src`、存在的 `public` 及其他构建输入，再执行 `npm run build` |
| 静态镜像 | 从对应 builder 工作目录取本次 `dist`，同时复制该模块的 `nginx.conf` |

工作区中的 common-frontend 不保留自己的 `node_modules`；镜像私有构建目录中的依赖链接用于解析消费模块已有依赖，不执行第二次安装。模块通过 `overrides` 和 Vite 的别名、去重规则维持共享依赖一致，见[共享前端说明](../../common-frontend/README.md)。

构建布局以现有模块 Dockerfile 为准，新增或调整模块时核对相应依赖关系：

- [Manager Dockerfile](../../manager/frontend/Dockerfile)：保留 `file:` 本地依赖的仓库目录关系，以及预览静态资源与许可证输入。
- [Console Dockerfile](../../console/frontend/Dockerfile)：按消费模块工作目录连接共享源码与依赖。
- [Quality Dockerfile](../../quality/frontend/Dockerfile)：按模块的实际源码与静态资源集合复制输入。

## Nginx 与资源路径

Vue Router history 模式需要 SPA 回退；模块的 Nginx 配置还必须匹配 Vite `base`、实际静态资源路径和既有代理规则，不能只复制一个通用 fallback 片段。

例如 [Manager Nginx 配置](../../manager/frontend/nginx.conf)还处理模块前缀下的 assets、预览插件和 WASM 路径；构建输入同步参考其 [Vite 配置](../../manager/frontend/vite.config.js)。平台公开入口与容器内部端口的边界遵循[端口规范](../../docs/spec/addp端口分配.md)。

当前 Agent、Graph、Model、Monitor、Security、Standard 的 Dockerfile 尚未复制模块 Nginx 配置，而这些模块使用 history 路由。其 SPA 回退要求仍需落实并在真实镜像下验证深层链接刷新；构建登记通过不能作为这部分已实现或已验收的证据。

## 常见错误

| 问题 | 核对与处理 |
| --- | --- |
| `nginx.conf` 或源码找不到 | 核对根构建上下文、`COPY` 的模块前缀和真实文件路径 |
| `npm ci` 报清单不一致 | 在模块依赖维护阶段修正并提交清单与锁文件，不在镜像中删除锁文件或改用安装命令重算依赖 |
| Rollup 原生包缺失 | 核对目标架构、锁文件中的两类 musl 可选包及安装环境是否省略所需依赖，不追加写死 arm64 或 x64 的安装步骤 |
| common-frontend 依赖无法解析 | 同时核对 `WORKDIR`、本地 `file:` 依赖、共享源码位置、镜像内链接目标与 Vite 解析配置 |
| 页面可访问但预览资源 404 | 核对 `public` 等静态输入、构建 `base` 与模块 Nginx 路由；状态页成功不代表预览资源齐全 |

## 新增模块与验证

新增模块同时登记唯一镜像构建入口、Compose 与 owner 测试，具体步骤见[新模块开发指南](../../docs/spec/addp新模块开发指南.md)。不要在文档、Makefile 或 Workflow 再维护一套构建命令和服务清单。

```bash
# T0：构建登记、前端依赖规则和镜像影响选择
make test-build-registration

# 真实镜像构建示例：仅选择所需前端，强制验证，不推送产品镜像
make build-images IMAGE_BUILD_ARGS="--verify --services console,manager-frontend --jobs 1"
```

`--verify` 仍需要 Docker、基础镜像与依赖获取条件，并包含基础镜像预热；它不是静态检查。镜像构建、前端组件测试与浏览器验收分别记录结果，不能互相替代，见[CI 与交付规范](../../docs/spec/testing/CI与交付规范.md)。
