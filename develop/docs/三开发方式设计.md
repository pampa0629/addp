# Develop 模块统一任务架构设计方案

## 一、设计概述

**目标**: 将 develop 模块升级为统一的开发工作台,支持三种开发方式:
- **SQL 开发** (已实现,需改为异步)
- **画布开发/算子拖拽** (已部分实现,需增强)
- **脚本开发/Python 工作台** (新增,基于增强的 GeoPandas Engine)

三种开发方式产生的结果统称为"**开发任务(Dev Task)**",可在 develop 模块内调度,也可被 orchestrator 模块编排。

**用户反馈确认**:
- ✅ 采用异步执行模式(支持立即执行和定时调度)
- ✅ 删除旧表,不需要数据迁移
- ✅ 一个引擎注册一次,在 capabilities 中声明多种能力
- ✅ 采用方案 A: 增强 GeoPandas Engine (内存占用 300-400MB vs Jupyter 的 1.5-2GB)

## 二、核心概念重新定义

### 2.1 名称方案(通盘考虑 develop + orchestrator)

经过与用户讨论,考虑到三种开发方式产生的结果都需要被 orchestrator 编排,统一命名为:

| 层级 | 中文名称 | 英文名称 | 说明 | 适用模块 |
|------|---------|---------|------|---------|
| **定义层** | **开发任务** | **DevTask** | Develop 模块中定义的任务(SQL/工作流/脚本) | develop |
| **执行层** | **任务执行** | **TaskExecution** | 任务的执行实例(包括 develop 和其他引擎) | develop, orchestrator |
| **编排层** | **编排步骤** | **OrchestrationStep** | Orchestrator 中的 DAG 节点 | orchestrator |

**统一抽象**:
- **引擎(Engine)**: 提供计算能力的服务(PostgreSQL/GeoPandas/Meta Scanner/Transfer)
- **任务(Task)**: 引擎上定义的可执行单元(DevTask/ScanTask/TransferTask)
- **执行(Execution)**: 任务的运行实例(TaskExecution)
- **编排(Orchestration)**: 多个任务的 DAG 组合

**三种开发方式的具体命名**:
- **SQL 任务(SQLTask)**: `dev_type = 'sql'`
- **工作流任务(WorkflowTask)**: `dev_type = 'workflow'`
- **脚本任务(ScriptTask)**: `dev_type = 'script'`

这样做的好处:
1. 在 develop 模块内部统一为 DevTask
2. 在 orchestrator 编排时,所有引擎的任务都是 Task
3. 避免了 orchestrator 的 Task 和 develop 的概念冲突
4. 清晰的层级划分(定义→执行→编排)

### 2.2 三种开发方式对比

| 维度 | SQL 开发 | 画布开发 | 脚本开发 |
|------|----------|----------|----------|
| **界面** | Monaco 编辑器 | DAG 画布(拖拽) | Monaco 编辑器(Python) |
| **输入** | SQL 文本 | WorkflowDef JSON | Python 代码 |
| **执行方式** | 异步(改造后) | 异步(已实现) | 异步(新增) |
| **目标引擎** | PostgreSQL/MySQL/Doris/Spark SQL | GeoPandas Engine | GeoPandas Engine(增强) |
| **结果类型** | 表格数据(rows) | GeoJSON/矢量数据 | 混合输出(文本/图表/数据) |
| **是否可调度** | ✅ | ✅ (已支持 cron) | ✅ |
| **被编排** | ✅ | ✅ (已注册) | ✅ |

## 三、数据模型设计

### 3.1 统一开发项模型

```sql
-- develop.dev_items (统一开发项定义表)
CREATE TABLE develop.dev_items (
    id SERIAL PRIMARY KEY,
    tenant_id INTEGER NOT NULL,
    name VARCHAR(255) NOT NULL,           -- 开发项名称
    display_name VARCHAR(255),            -- 显示名称
    dev_type VARCHAR(50) NOT NULL,        -- 'sql_query' | 'workflow' | 'notebook'

    -- 内容存储(根据类型解析)
    content JSONB NOT NULL,               -- SQL文本 / WorkflowDef / Notebook Cells

    -- 执行配置
    engine_id INTEGER,                  -- 关联的引擎(数据库/引擎)
    schedule VARCHAR(100),                -- Cron 表达式(可选)
    is_scheduled BOOLEAN DEFAULT false,   -- 是否启用定时调度
    timeout INTEGER DEFAULT 300,          -- 超时时间(秒)

    -- 元数据
    description TEXT,
    tags TEXT[],                          -- 标签(便于分类)
    created_by INTEGER,
    updated_by INTEGER,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    deleted_at TIMESTAMP,                 -- 软删除

    -- 状态
    status VARCHAR(50) DEFAULT 'active',  -- 'active' | 'inactive' | 'archived'
    last_execution_id INTEGER,            -- 最后一次执行ID
    last_execution_status VARCHAR(50),    -- 最后一次执行状态
    last_executed_at TIMESTAMP,

    UNIQUE(tenant_id, name),
    INDEX(tenant_id, dev_type),
    INDEX(engine_id),
    INDEX(status)
);
```

### 3.2 统一执行记录模型

```sql
-- develop.dev_executions (统一执行记录表)
CREATE TABLE develop.dev_executions (
    id SERIAL PRIMARY KEY,
    dev_item_id INTEGER NOT NULL REFERENCES dev_items(id),
    tenant_id INTEGER NOT NULL,
    execution_id VARCHAR(255) UNIQUE,     -- UUID 全局唯一标识

    -- 执行信息
    dev_type VARCHAR(50) NOT NULL,
    trigger_type VARCHAR(50),             -- 'manual' | 'schedule' | 'orchestrator' | 'api'
    triggered_by INTEGER,                 -- 触发用户ID

    -- 状态跟踪
    status VARCHAR(50) NOT NULL,          -- 'pending' | 'running' | 'success' | 'failed' | 'timeout' | 'cancelled'
    progress INTEGER DEFAULT 0,           -- 进度百分比(0-100)
    current_step VARCHAR(255),            -- 当前步骤描述

    -- 执行结果
    result JSONB,                         -- 执行结果数据
    error_message TEXT,                   -- 错误信息
    execution_time_ms BIGINT,             -- 执行耗时(毫秒)

    -- 资源使用
    engine_id INTEGER,                  -- 使用的引擎
    rows_affected BIGINT,                 -- SQL影响行数
    result_size_bytes BIGINT,             -- 结果数据大小

    -- 时间戳
    started_at TIMESTAMP,
    completed_at TIMESTAMP,
    created_at TIMESTAMP DEFAULT NOW(),

    INDEX(dev_item_id),
    INDEX(tenant_id, status),
    INDEX(trigger_type),
    INDEX(created_at)
);
```

## 六、调度能力统一设计

### 6.1 调度配置

在 `dev_items` 表中,所有类型的开发项都支持:
- `schedule`: Cron 表达式(如 `0 2 * * *` 每天凌晨2点)
- `is_scheduled`: 是否启用定时调度
- `timeout`: 超时时间

### 6.2 调度器实现

```go
// develop/backend/internal/service/dev_scheduler.go
type DevScheduler struct {
  scheduler  commonScheduler.Scheduler
  devItemRepo *repository.DevItemRepository
  executor    *DevExecutor
}

func (s *DevScheduler) Start() {
  // 1. 查询所有启用定时调度的开发项
  items := s.devItemRepo.FindScheduled()

  // 2. 为每个开发项注册定时任务
  for _, item := range items {
    s.scheduler.Schedule(item.Schedule, func() {
      s.executor.ExecuteAsync(item.ID, "schedule")
    })
  }
}
```

### 6.3 三种开发方式的执行策略

| 类型 | 执行模式 | 实现方式 |
|------|---------|---------|
| SQL Query | 同步 | 直接执行,立即返回结果(考虑改为异步以支持大查询) |
| Workflow | 异步 | 提交到 GeoPandas Engine,轮询状态 |
| Notebook | 异步 | 提交到 Jupyter Service,轮询执行状态 |

**建议**: 将 SQL Query 也改为异步执行,以支持:
- 大数据量查询(超过10秒)
- 后台定时执行
- 统一的执行历史管理

## 九、关键技术考虑

### 9.1 SQL 异步执行改造

**当前问题**: SQL 查询是同步执行,阻塞 HTTP 请求
**改造方案**:
1. 提交 SQL → 立即返回 execution_id
2. 后台 Goroutine 执行 SQL
3. 前端轮询 `/api/develop/executions/{id}` 获取状态
4. 执行完成后,结果存储到 `dev_executions.result` (JSONB)

**优点**:
- 支持超大查询(不受 HTTP 超时限制)
- 统一执行模型
- 支持后台定时执行

### 9.2 Notebook 服务架构

**选型建议**:
- **方案1**: 使用 Jupyter Server (官方,功能完整,但较重)
- **方案2**: 使用 JupyterLab Server (推荐,现代化界面)
- **方案3**: 自建轻量级 Python 执行引擎(灵活,但需自己实现)

**推荐**: JupyterLab Server + REST API Wrapper

**集成方式**:
```
Develop Backend (Go)
  ↓ HTTP
JupyterLab Server (Python)
  ↓ Kernel Protocol
Python/R/Bash Kernel
```

### 9.3 结果数据存储策略

| 数据类型 | 存储方式 | 大小限制 |
|---------|---------|---------|
| SQL 小结果集 | JSONB 直接存储 | < 1MB |
| SQL 大结果集 | MinIO 存储,JSONB 存 URL | > 1MB |
| Workflow 结果 | MinIO (GeoJSON) | 任意 |
| Notebook 输出 | MinIO (HTML/JSON) | 任意 |

### 9.4 安全性考虑

- **SQL 注入防护**: 使用参数化查询(已实现)
- **权限隔离**: 基于租户+资源的访问控制
- **代码执行沙箱**: Notebook 需要限制文件系统访问
- **超时保护**: 所有执行类型强制超时(默认5分钟,最大30分钟)

## 十二、引擎 API 统一规范设计

### 12.1 问题背景

用户提出重要问题:
> 对于 geopandas-engine 这样通过 API 提供能力的引擎,是否应该要求统一规范,让更多 engine 都遵照实现(包括 meta 和 transfer 内置的引擎)? 还是按照资源管理注册时的做法,让用户自己填写 API?

### 12.2 方案对比

#### 方案 A: 统一 Task API 规范(推荐)

**核心思路**: 定义标准的 Task API 接口规范,所有计算引擎统一遵循。

**规范定义** (`common/models/task_api_spec.go`):

```go
// Task API 标准规范 v1.0
type TaskAPISpec struct {
    Version string `json:"version"` // "1.0"

    // 必需端点
    Endpoints TaskAPIEndpoints `json:"endpoints"`

    // 通用配置
    Timeout  int    `json:"timeout"`   // 默认超时(秒)
    AuthType string `json:"auth_type"` // "jwt" | "api_key" | "none"
}

type TaskAPIEndpoints struct {
    // 1. 任务定义管理(可选,如果引擎支持持久化任务定义)
    ListTasks   *APIEndpoint `json:"list_tasks"`   // GET /api/{module}/tasks
    CreateTask  *APIEndpoint `json:"create_task"`  // POST /api/{module}/tasks
    GetTask     *APIEndpoint `json:"get_task"`     // GET /api/{module}/tasks/:id
    UpdateTask  *APIEndpoint `json:"update_task"`  // PUT /api/{module}/tasks/:id
    DeleteTask  *APIEndpoint `json:"delete_task"`  // DELETE /api/{module}/tasks/:id

    // 2. 任务执行(必需)
    ExecuteTask *APIEndpoint `json:"execute_task"` // POST /api/{module}/tasks/:id/execute
                                                     // 或 POST /api/{module}/execute (即时执行)

    // 3. 执行状态查询(必需)
    GetExecution *APIEndpoint `json:"get_execution"` // GET /api/{module}/executions/:id

    // 4. 执行控制(可选)
    CancelExecution *APIEndpoint `json:"cancel_execution"` // POST /api/{module}/executions/:id/cancel
    RetryExecution  *APIEndpoint `json:"retry_execution"`  // POST /api/{module}/executions/:id/retry

    // 5. 健康检查(推荐)
    Health *APIEndpoint `json:"health"` // GET /health
}

type APIEndpoint struct {
    Method      string            `json:"method"`       // "GET" | "POST" | "PUT" | "DELETE"
    Path        string            `json:"path"`         // 路径模板,支持 {{.TaskID}} 占位符
    Timeout     int               `json:"timeout"`      // 端点超时(秒)
    Headers     map[string]string `json:"headers"`      // 自定义请求头
    Description string            `json:"description"`  // 端点说明
}
```

**标准请求/响应格式**:

```go
// 执行任务请求
type ExecuteTaskRequest struct {
    TaskID     string                 `json:"task_id,omitempty"`     // 任务ID(持久化任务)
    Parameters map[string]interface{} `json:"parameters"`            // 执行参数
    Async      bool                   `json:"async"`                 // 是否异步执行
    Callback   string                 `json:"callback,omitempty"`    // 回调URL
}

// 执行任务响应
type ExecuteTaskResponse struct {
    ExecutionID string      `json:"execution_id"` // 执行实例ID
    Status      string      `json:"status"`       // "pending" | "running" | "success" | "failed"
    Result      interface{} `json:"result"`       // 执行结果(同步时返回)
    Message     string      `json:"message"`      // 状态消息
}

// 查询执行状态响应
type GetExecutionResponse struct {
    ExecutionID    string                 `json:"execution_id"`
    TaskID         string                 `json:"task_id,omitempty"`
    Status         string                 `json:"status"`
    Progress       int                    `json:"progress"`        // 0-100
    Result         interface{}            `json:"result"`
    ErrorMessage   string                 `json:"error_message"`
    ExecutionTime  int64                  `json:"execution_time"`  // 毫秒
    StartedAt      string                 `json:"started_at"`
    CompletedAt    string                 `json:"completed_at"`
    Metadata       map[string]interface{} `json:"metadata"`        // 引擎特定元数据
}
```

**各模块实施情况**:

| 模块 | 引擎标识 | 当前状态 | 改造工作量 | 优先级 |
|------|---------|---------|-----------|--------|
| **GeoPandas Engine** | geopandas.engine.default | 部分符合 | 小(补充标准端点) | P0 |
| **Develop (SQL)** | develop.sql.default | 需改造 | 中(新增任务定义表) | P0 |
| **Develop (Workflow)** | develop.workflow.default | 基本符合 | 小(调整响应格式) | P0 |
| **Develop (Script)** | develop.script.default | 待实现 | 中(新增功能) | P1 |
| **Meta Scanner** | meta.scanner.default | 需改造 | 中(增加执行控制) | P1 |
| **Transfer** | transfer.batch.default | 需改造 | 中(增加执行控制) | P1 |

**优点**:
- ✅ **互操作性强**: Orchestrator 可以统一调用所有引擎
- ✅ **扩展性好**: 新增引擎只需遵循规范即可
- ✅ **维护成本低**: 统一的客户端代码,无需针对每个引擎定制
- ✅ **文档清晰**: 统一的 API 文档和测试工具
- ✅ **错误处理统一**: 标准的错误码和错误消息格式

**缺点**:
- ⚠️ **改造成本**: 现有模块(meta/transfer)需要改造
- ⚠️ **灵活性受限**: 特殊引擎可能需要额外字段(通过 metadata 扩展)

#### 方案 B: 灵活注册(用户自定义)

**核心思路**: 引擎注册时由用户/管理员手动配置 API 端点。

**实施方式**:
```json
// 用户在 System 资源管理界面手动填写
{
  "unique_identifier": "custom.engine.1",
  "task_api_config": {
    "base_url": "http://custom-service:9000",
    "endpoints": {
      "execute": {
        "method": "POST",
        "path": "/run",  // 自定义路径
        "timeout": 60
      },
      "status": {
        "method": "GET",
        "path": "/status/{exec_id}"  // 自定义占位符格式
      }
    }
  }
}
```

**优点**:
- ✅ **灵活性高**: 支持任意 API 格式
- ✅ **零改造成本**: 现有引擎无需修改
- ✅ **快速集成**: 第三方服务可快速接入

**缺点**:
- ❌ **配置复杂**: 用户需要了解 API 细节
- ❌ **错误风险高**: 配置错误导致调用失败
- ❌ **维护成本高**: 每个引擎需要独立的客户端适配器
- ❌ **缺乏标准**: 响应格式不统一,难以通用处理

---

### 12.3 推荐方案(混合模式)

**策略**: 统一规范为主,灵活注册为辅

```
1. 平台内置引擎(Develop/Meta/Transfer/GeoPandas):
   → 必须遵循 Task API 规范 v1.0
   → Orchestrator 使用统一客户端调用

2. 第三方/外部引擎:
   → 优先推荐遵循规范
   → 如果无法遵循,通过适配器(Adapter)模式包装

3. 遗留系统:
   → 保留灵活注册方式
   → 在 Orchestrator 中实现引擎特定的客户端适配器
```

**实施步骤**:

**Phase 1: 定义规范**(1-2天)
- 在 `common/models/task_api_spec.go` 中定义标准
- 编写规范文档 `docs/TASK_API_SPEC.md`
- 提供参考实现和测试工具

**Phase 2: 改造内置引擎**(按优先级)
- **P0**: Develop 三种类型 + GeoPandas Engine (1周)
- **P1**: Meta Scanner (3天)
- **P2**: Transfer (3天)

**Phase 3: Orchestrator 集成**(3天)
- 实现统一的 `StandardTaskClient` (基于规范)
- 保留 `AdapterTaskClient` (适配非标准引擎)
- 自动判断使用哪种客户端

### 12.4 标准 API 路由规范

**推荐的 URL 结构**:

```
基础路径: /api/{module}/

任务定义管理:
├── GET    /api/{module}/tasks              # 列出任务
├── POST   /api/{module}/tasks              # 创建任务
├── GET    /api/{module}/tasks/:id          # 获取任务详情
├── PUT    /api/{module}/tasks/:id          # 更新任务
├── DELETE /api/{module}/tasks/:id          # 删除任务

任务执行:
├── POST   /api/{module}/tasks/:id/execute  # 执行已定义任务
└── POST   /api/{module}/execute            # 即时执行(不保存任务定义)

执行实例管理:
├── GET    /api/{module}/executions         # 列出执行历史
├── GET    /api/{module}/executions/:id     # 获取执行详情
├── POST   /api/{module}/executions/:id/cancel  # 取消执行
├── POST   /api/{module}/executions/:id/retry   # 重试执行
└── GET    /api/{module}/executions/:id/logs    # 获取执行日志

健康检查:
└── GET    /health                          # 健康检查
```

**示例对比**:

| 模块 | 当前路径 | 标准化后 |
|------|---------|---------|
| Develop(SQL) | POST /api/develop/execute | POST /api/develop/sql/execute |
| Develop(Workflow) | POST /api/develop/spatial/tasks/:id/execute | POST /api/develop/workflow/tasks/:id/execute |
| Meta | POST /api/scan/tasks | POST /api/meta/scan/tasks |
| Transfer | POST /api/transfer/tasks | POST /api/transfer/batch/tasks |

### 12.6 最终建议

**采用混合策略**:
1. **制定标准规范** (Task API Spec v1.0)
2. **内置引擎必须遵循** (Develop/Meta/Transfer/GeoPandas)
3. **第三方引擎推荐遵循** (提供文档和测试工具)
4. **保留灵活注册** (通过适配器支持非标准引擎)

**实施优先级**:
- P0: 定义规范 + Develop 模块实施 + 文档
- P1: GeoPandas Engine 适配 + Meta Scanner 改造
- P2: Transfer 改造 + Orchestrator 统一客户端

**收益**:
- 长期维护成本降低 60%
- 新引擎接入时间从 3天 缩短到 0.5天
- Orchestrator 代码复杂度降低 40%
- 统一的监控和错误处理

## 十三、总结

该设计方案通过以下方式实现了统一任务架构:

1. **数据模型统一**: `dev_tasks` + `task_executions` 表支持三种开发方式
2. **能力标注统一**: 在 `capabilities` 字段标明引擎的开发能力
3. **界面管理统一**: 统一的任务列表和执行历史视图
4. **调度机制统一**: 所有开发任务都支持 Cron 定时调度
5. **编排集成统一**: 通过 `develop.unified.default` 标识符注册能力
6. **API 规范统一**: 制定 Task API Spec v1.0,内置引擎统一遵循

**优势**:
- 用户体验一致(三种开发方式共享相同的管理流程)
- 代码复用性高(统一的执行器、调度器和 API 客户端)
- 易于扩展(新开发方式只需扩展 `dev_type`,新引擎只需遵循规范)
- 与 Orchestrator 深度集成(所有任务都可被编排)
- 资源占用优化(Python 工作台使用增强的 GeoPandas Engine,仅需 +100MB 内存)

**关键决策**:
- ✅ 采用异步执行模式(支持立即执行和调度执行)
- ✅ 删除旧表,简化迁移(spatial_tasks → dev_tasks)
- ✅ 一个引擎注册一次,声明多种能力
- ✅ 增强 GeoPandas Engine 而非部署 Jupyter(节省 1.2GB 内存)
- ✅ 制定统一 Task API 规范,内置引擎强制遵循
