## 执行摘要

### 核心结论

经过对现有架构的深入分析，**推荐采用混合方案**:

1. **开发环境**: 基于 Monaco Editor 的轻量级 Python 编辑器（与 SQL Editor 一致）
2. **执行引擎**: 扩展现有 Python Workflow Engine，增加通用 Python 脚本执行能力
3. **结果存储**: 混合策略（小结果存 PostgreSQL，大文件存 MinIO）
4. **编排集成**: 与 SQL/Workflow 相同，统一通过 dev_tasks 表管理

**核心理由**:
- 保持与现有 SQL/Workflow 开发模式的一致性
- 最小化新增服务和复杂度
- 充分复用 Python Workflow Engine 的 Python 运行环境
- 避免 Jupyter 的资源开销（1.5-2GB vs 300-400MB）
- 遵循 ADDP 的 DRY 原则和架构一致性原则

## 关键决策分析

### 决策 1: Jupyter 环境选择

#### 详细对比

| 维度 | 选项 A: JupyterLab | 选项 B: Jupyter Notebook | 选项 C: Monaco Editor | 选项 D: 混合方案 |
|------|-------------------|------------------------|---------------------|-----------------|
| **内存占用** | 1.5-2GB | 800MB-1GB | 300-400MB | 300-400MB (生产) |
| **用户体验** | 现代化，多标签，文件浏览 | 经典界面，单文档 | 代码编辑器，无单元格 | Monaco 开发 + 脚本执行 |
| **交互性** | 单元格级执行，内联结果 | 单元格级执行 | 整体执行 | 整体执行 |
| **集成复杂度** | 高（iframe + 认证 + 存储） | 中（iframe + 认证） | 低（前端组件） | 中（Monaco + Engine） |
| **技术栈一致性** | 低（新增 Python 服务） | 低（新增 Python 服务） | 高（与 SQL 一致） | 高（与现有一致） |
| **运维成本** | 高（新服务监控） | 中 | 低（无新服务） | 低 |
| **数据分析场景** | 优秀（探索式分析） | 良好 | 中等（无即时反馈） | 良好（脚本化分析） |
| **生产稳定性** | 中（Jupyter 稳定性问题） | 中 | 高 | 高 |

#### 深度分析

**选项 A/B (Jupyter) 的优势**:
1. **交互式探索**: 单元格级执行非常适合数据探索和调试
2. **内联可视化**: 图表、表格直接显示在 Notebook 中
3. **Markdown 支持**: 可以编写文档和代码混合的分析报告
4. **生态系统**: 丰富的扩展插件（变量检查器、调试器）

**选项 A/B 的劣势**:
1. **资源消耗**: 800MB-2GB 内存，对于多租户场景压力大
2. **集成复杂度**:
   - 需要管理 Jupyter Server 生命周期
   - 认证集成困难（JWT vs Jupyter Token）
   - Notebook 文件存储位置（本地 vs MinIO）
   - 内核管理复杂（租户隔离、超时清理）
3. **生产化困难**:
   - Notebook 转 Python 脚本需要额外处理
   - 依赖管理（用户自定义 pip install 风险）
   - 版本控制不友好（ipynb 格式的 JSON 难以 diff）
4. **架构不一致**: 引入全新的技术栈，与 SQL/Workflow 割裂

**选项 C (Monaco Editor) 的优势**:
1. **轻量级**: 无需额外服务，300-400MB 内存足够
2. **技术栈一致**: 与 SQL Editor 使用相同组件
3. **维护简单**: 无需管理 Jupyter Server
4. **生产稳定**: Python 脚本直接执行，无 Notebook 依赖
5. **版本控制友好**: 纯文本脚本，Git 友好

**选项 C 的劣势**:
1. **无交互式执行**: 不能单元格级别执行
2. **无内联结果**: 执行结果需要单独面板展示
3. **调试困难**: 无法在执行过程中检查变量状态

**选项 D (推荐的混合方案)**:
- **开发阶段**: 用户可以在本地使用 Jupyter 进行探索式分析
- **任务保存**: 将成熟的代码保存为 Python 脚本到 dev_tasks
- **生产执行**: Develop/Orchestrator 执行纯 Python 脚本
- **优势平衡**:
  - 用户可选择自己喜欢的开发工具（Jupyter、VS Code、PyCharm）
  - 平台只负责稳定的脚本执行
  - 避免在平台内维护复杂的 Jupyter 环境

#### 推荐决策

**选择选项 C（基于 Monaco Editor）**，理由：

1. **架构一致性**: 与 SQL Editor 保持一致，降低用户学习成本
2. **资源效率**: 复用 Python Workflow Engine，无需额外服务
3. **运维简单**: 无需管理 Jupyter Server 的生命周期和隔离问题
4. **符合场景**: 
   - 数据分析脚本通常在本地 Jupyter 开发完成
   - 保存到平台时是成熟的、可重复执行的脚本
   - 平台重点是**调度执行**而非**交互式开发**
5. **遵循 ADDP 原则**: 
   - 彻底解决根本原因（脚本化数据处理）
   - 保持简洁（无需新服务）
   - DRY（复用 Python Workflow Engine）

**未来扩展路径**: 
- 如果用户强烈需要在线 Jupyter，可以作为独立服务提供
- 通过导入/导出功能桥接 Jupyter 和 Script Editor

### 决策 2: 编排集成方式

#### 详细对比

| 维度 | 选项 A: 统一管理 (推荐) | 选项 B: 独立引擎 |
|------|----------------------|----------------|
| **架构一致性** | 高（与 SQL/Workflow 相同） | 低（新增独立服务） |
| **维护复杂度** | 低（单一入口） | 高（多服务协调） |
| **API 一致性** | 高（统一 /api/v1/develop/task-definitions） | 低（独立 API） |
| **Orchestrator 集成** | 简单（统一任务列表 API） | 复杂（需查询多个服务） |
| **服务数量** | 不变 | +1 (Script Engine) |
| **资源隔离** | Schema 级别（develop schema） | 服务级别 |
| **扩展性** | 中（Develop Backend 承载更多类型） | 高（独立扩展） |

#### 深度分析

**选项 A (统一管理) 的优势**:
1. **用户体验统一**: 
   - SQL、Workflow、Script 都在 Develop 模块管理
   - 统一的任务列表、执行历史、调度配置
2. **架构简洁**:
   ```
   Orchestrator
     ↓
  GET /api/v1/develop/tasks
     ↓
   Develop Backend (统一入口)
     ↓ 根据 dev_type 分发
   ├─ SQLEngineService
   ├─ WorkflowEngineService
   └─ ScriptEngineService (新增)
   ```
3. **开发效率**: 复用现有的 dev_tasks 表、执行流程、认证中间件
4. **符合领域模型**: Develop 模块本身就是"开发工具集"，Script 是其中一种开发方式

**选项 A 的劣势**:
1. Develop Backend 职责增加（但仍在合理范围）
2. 需要增强 Python Workflow Engine 以支持通用 Python 脚本

**选项 B (独立引擎) 的优势**:
1. **职责单一**: Script Engine 只负责 Python 脚本执行
2. **独立扩展**: 可以独立升级 Python 环境、依赖库
3. **故障隔离**: Script Engine 崩溃不影响 SQL/Workflow

**选项 B 的劣势**:
1. **服务激增**: 
   - 需要新增 Script Engine Service (Go + Python)
   - 需要独立的 schema 或数据表
   - 需要独立的 Docker 容器、端口分配
2. **Orchestrator 集成复杂**: 需要查询多个 API 获取完整任务列表
3. **违反 DRY**: Python Workflow Engine 已有 Python 环境，重复构建

#### 推荐决策

**选择选项 A（统一管理）**，理由：

1. **架构一致性**: 与现有 SQL/Workflow 模式完全一致
2. **实现简单**: 
   - 复用 dev_tasks 表（已支持 dev_type='script'）
   - 复用 common.task_executions 表
   - 新增 ScriptEngineService（类似 SQLEngineService）
3. **用户体验佳**: 
   - 统一的任务管理界面
   - 统一的执行监控
   - 统一的调度配置
4. **TaskProvider 集成简单**:
   - 单一 API: `/api/v1/develop/tasks`
   - 由 TaskProvider capabilities 声明 `query` / `workflow` / `script`
5. **遵循 ADDP 原则**: 全面考虑，保持模块间一致性

**实现路径**:
```
Develop Backend
├── internal/service/
│   ├── sql_engine_service.go (已有)
│   ├── workflow_engine_service.go (已有)
│   └── script_engine_service.go (新增)
├── internal/api/
│   └── script_handler.go (新增，可选，复用 dev_task_handler)
```

### 决策 3: 结果存储策略

#### 详细对比

| 维度 | 仅 MinIO | 仅 PostgreSQL | 混合策略 (推荐) |
|------|---------|--------------|--------------|
| **小结果性能** | 低（网络 IO） | 高（直接查询） | 高 |
| **大文件支持** | 高（TB 级） | 低（JSONB 限制） | 高 |
| **查询便利性** | 低（需下载） | 高（SQL 查询） | 高 |
| **存储成本** | 中 | 高（数据库存储贵） | 低（优化分配） |
| **实现复杂度** | 低 | 低 | 中 |

#### 典型结果类型分析

| 结果类型 | 典型大小 | 存储策略 | 理由 |
|---------|---------|---------|------|
| **文本输出** | <10KB | PostgreSQL | 快速查询，无需下载 |
| **JSON 数据** | <100KB | PostgreSQL | JSONB 支持，可索引 |
| **CSV 表格** | <1MB | PostgreSQL | 适合预览，可转 JSONB |
| **Matplotlib 图表** | 100KB-1MB | MinIO | PNG/SVG 文件 |
| **大数据集** | >1MB | MinIO | CSV/Parquet 文件 |
| **机器学习模型** | >10MB | MinIO | .pkl/.h5 文件 |
| **GeoJSON** | 100KB-10MB | 混合 | 小文件存 PG，大文件存 MinIO |

#### 推荐决策

**选择混合策略**，具体规则：

1. **阈值判断**: 
   ```python
   RESULT_SIZE_THRESHOLD = 1 * 1024 * 1024  # 1MB
   
   if result_size < RESULT_SIZE_THRESHOLD:
       store_in_postgresql(result)
   else:
       store_in_minio(result)
   ```

2. **存储实现**:
   ```go
   type ExecutionResult struct {
       Type     string      // 'inline' | 'file'
       Data     interface{} // 小结果直接存储
       FilePath string      // 大文件的 MinIO 路径
       FileSize int64       // 文件大小
       MimeType string      // 文件类型
   }
   ```

3. **MinIO 路径规范**:
   ```
   develop/{tenant_id}/executions/{execution_id}/result.{ext}
   develop/{tenant_id}/executions/{execution_id}/figure_1.png
   develop/{tenant_id}/executions/{execution_id}/output.csv
   ```

4. **复用 Transfer S3Writer**:
   ```go
   // 复用 Transfer 模块的 S3Writer（遵循 DRY 原则）
   import transferStorage "github.com/addp/transfer/backend/internal/storage"
   
   writer := transferStorage.NewS3Writer(minioConfig)
   err := writer.WriteFile(ctx, bucketName, objectKey, dataReader)
   ```

**优势**:
1. **性能优化**: 小结果零延迟，大文件不占数据库
2. **成本优化**: 数据库只存元数据和小结果
3. **灵活性**: 支持各种结果类型（文本、图表、数据集）
4. **查询便利**: 小结果可直接 SQL 查询和聚合

### 决策 4: 执行环境设计

#### 详细对比

| 维度 | 共享 Kernel | 每任务独立进程 (推荐) | 租户级 Kernel |
|------|------------|---------------------|-------------|
| **资源利用率** | 高 | 中 | 中 |
| **启动开销** | 低（热启动） | 高（每次冷启动） | 中（首次冷启动） |
| **隔离性** | 差（内存共享） | 优（完全隔离） | 中（租户隔离） |
| **安全性** | 差（跨任务污染） | 优（进程级隔离） | 中（租户级隔离） |
| **内存占用** | 低（单实例） | 高（N 个进程） | 中（M 个租户） |
| **故障影响** | 大（Kernel 崩溃影响所有） | 小（单任务失败） | 中（租户级影响） |
| **实现复杂度** | 高（Kernel 管理） | 低（subprocess） | 高（租户 Kernel 池） |
| **适用场景** | 轻量级任务，高 QPS | 中低频任务 | 中频任务，租户多 |

#### 深度分析

**选项 A (共享 Kernel) 的问题**:
1. **全局变量污染**: 
   ```python
   # Task A
   import pandas as pd
   df = pd.read_csv('data.csv')  # 全局变量
   
   # Task B（在同一 Kernel）
   print(df)  # 能访问 Task A 的数据！
   ```
2. **内存泄漏累积**: 长期运行的 Kernel 会累积未释放的内存
3. **库版本冲突**: 不同任务可能需要不同版本的库
4. **安全风险**: 恶意脚本可以访问其他任务的数据

**选项 B (独立进程) 的优势**:
1. **完全隔离**: 
   ```go
   // 每次执行启动新进程
   cmd := exec.Command("python3", "-c", scriptContent)
   cmd.Env = []string{
       "PYTHONPATH=/opt/venv/lib/python3.12/site-packages",
       "EXECUTION_ID=" + executionID,
   }
   ```
2. **自动清理**: 进程结束后所有资源自动释放
3. **超时控制**: 可以强制 Kill 超时进程
4. **错误隔离**: 一个脚本崩溃不影响其他任务

**选项 B 的优化**:
- **预热 Python 解释器**: 使用 PyInstaller 打包常用库
- **缓存依赖**: 共享 virtualenv 目录
- **并发控制**: 限制同时执行的脚本数（如 10 个）

**选项 C (租户级 Kernel) 的权衡**:
- 适合租户数量有限、任务频繁的场景
- 实现复杂度高（需要维护 Kernel 池）
- 在 ADDP 的多租户场景下，租户数量可能很多

#### 推荐决策

**选择选项 B（每任务独立进程）**，理由：

1. **安全性优先**: 多租户场景必须保证隔离
2. **实现简单**: 
   ```go
   type ScriptExecutor struct {
       pythonPath string  // /opt/venv/bin/python3
       timeout    time.Duration
       maxProcs   int  // 并发限制
   }
   
   func (e *ScriptExecutor) Execute(ctx context.Context, script string) (*Result, error) {
       cmd := exec.CommandContext(ctx, e.pythonPath, "-c", script)
       output, err := cmd.CombinedOutput()
       return parseResult(output), err
   }
   ```
3. **资源可控**: 通过并发限制控制总资源消耗
4. **符合现状**: Python Workflow Engine 已采用类似模式（Workflow 执行）

**启动优化方案**:
1. **共享 virtualenv**: 所有脚本共享预装库的 venv
2. **并发池**: 限制同时运行的脚本数量（默认 10）
3. **超时设置**: 默认 5 分钟，可配置
4. **资源限制**: 通过 cgroups 限制内存/CPU（Docker 级别）

#### 2. ScriptEngineService (后端)

**文件位置**: `/Users/pampa/code/addp/develop/backend/internal/service/script_engine_service.go`

**职责**:
1. 接收脚本执行请求

3. 处理执行结果（解析输出、提取图表、保存数据）

**核心方法**:

package service

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"io"
	"net/http"
	"time"

	"github.com/addp/develop/backend/internal/models"
	"github.com/google/uuid"
)

type ScriptEngineService struct {
	geopandasEngineURL string
	httpClient         *http.Client
}

// ExecuteScript 执行 Python 脚本
func (s *ScriptEngineService) ExecuteScript(
	ctx context.Context,
	scriptContent string,
	timeout int,
) (*ScriptExecutionResult, error) {
	// 构建请求
	req := ScriptExecuteRequest{
		Script:  scriptContent,
		Timeout: timeout,
	}

	reqBody, err := json.Marshal(req)
	if err != nil {
		return nil, fmt.Errorf("failed to marshal request: %w", err)
	}

	// 调用 Python Workflow Engine
	url := fmt.Sprintf("%s/api/scripts/execute", s.geopandasEngineURL)
	httpReq, err := http.NewRequestWithContext(ctx, "POST", url, bytes.NewBuffer(reqBody))
	if err != nil {
		return nil, fmt.Errorf("failed to create request: %w", err)
	}
	httpReq.Header.Set("Content-Type", "application/json")

	// 执行请求
	resp, err := s.httpClient.Do(httpReq)
	if err != nil {
		return nil, fmt.Errorf("failed to execute script: %w", err)
	}
	defer resp.Body.Close()

	// 解析响应
	body, err := io.ReadAll(resp.Body)
	if err != nil {
		return nil, fmt.Errorf("failed to read response: %w", err)
	}

	var result ScriptExecutionResult
	if err := json.Unmarshal(body, &result); err != nil {
		return nil, fmt.Errorf("failed to unmarshal response: %w", err)
	}

	if resp.StatusCode != http.StatusOK {
		return &result, fmt.Errorf("script execution failed: %s", result.Error)
	}

	return &result, nil
}

// ScriptExecuteRequest 脚本执行请求
type ScriptExecuteRequest struct {
	Script  string `json:"script"`
	Timeout int    `json:"timeout"` // 秒
}

// ScriptExecutionResult 脚本执行结果
type ScriptExecutionResult struct {
	Status          string                   `json:"status"` // 'success' | 'failed'
	ExecutionID     string                   `json:"execution_id"`
	Stdout          string                   `json:"stdout"`
	Stderr          string                   `json:"stderr"`
	ReturnValue     interface{}              `json:"return_value,omitempty"`
	Figures         []FigureOutput           `json:"figures,omitempty"`         // Matplotlib 图表
	DataFrames      []DataFrameOutput        `json:"dataframes,omitempty"`      // pandas DataFrame
	ExecutionTimeMs int64                    `json:"execution_time_ms"`
	Error           string                   `json:"error,omitempty"`
}

// FigureOutput Matplotlib 图表输出
type FigureOutput struct {
	Index      int    `json:"index"`       // 图表编号
	Format     string `json:"format"`      // 'png' | 'svg'
	Data       string `json:"data"`        // Base64 编码的图片数据
	MinIOPath  string `json:"minio_path"`  // MinIO 存储路径（如果大于1MB）
	Width      int    `json:"width"`
	Height     int    `json:"height"`
}

// DataFrameOutput pandas DataFrame 输出

	Name      string              `json:"name"`        // 变量名

"""
新增脚本执行端点
"""

import io
import sys
import base64
import traceback
from contextlib redirect_stdout, redirect_stderr
import matplotlib
matplotlib.use('Agg')  # 非交互式后端
import matplotlib.pyplot as plt

@app.route('/api/scripts/execute', methods=['POST'])
def execute_script():
    """
    执行通用 Python 脚本
    
    Request Body:
        {
            "script": "import pandas as pd\\ndf = pd.read_csv('data.csv')\\nprint(df.head())",
            "timeout": 300
        }
    
    Response:
        {
            "status": "success",
            "execution_id": "...",
            "stdout": "...",
            "stderr": "...",
            "figures": [...],
            "dataframes": [...]
        }
    """
    try:
        data = request.get_json()
        script = data.get('script')
        timeout = data.get('timeout', 300)
        
        if not script:
            return jsonify({
                "status": "failed",
                "error": "script is required"
            }), 400
        
        execution_id = str(uuid.uuid4())
        logger.info(f"Executing script {execution_id}")
        
        # 执行脚本
        result = execute_python_script(script, timeout)
        
        # 构建响应
        response = {
            "status": result['status'],
            "execution_id": execution_id,
            "stdout": result.get('stdout', ''),
            "stderr": result.get('stderr', ''),
            "figures": result.get('figures', []),
            "dataframes": result.get('dataframes', []),
            "execution_time_ms": result.get('execution_time_ms', 0)
        }
        
        if result['status'] == 'failed':
            response['error'] = result.get('error', '')
            status_code = 500
        else:
            status_code = 200
        
        return jsonify(response), status_code
        
    except Exception as e:
        logger.error(f"Script execution failed: {e}", exc_info=True)
        return jsonify({
            "status": "failed",
            "error": str(e)
        }), 500


def execute_python_script(script: str, timeout: int) -> dict:
    """
    执行 Python 脚本并捕获结果
    
    Args:
        script: Python 脚本内容
        timeout: 超时时间（秒）
    
    Returns:
        {
            "status": "success" | "failed",
            "stdout": "...",
            "stderr": "...",
            "figures": [...],
            "dataframes": [...],
            "error": "..." (如果失败)
        }
    """
    start_time = time.time()
    
    # 准备执行环境
    stdout_capture = io.StringIO()
    stderr_capture = io.StringIO()
    execution_globals = {
        '__name__': '__main__',
        '__builtins__': __builtins__,
    }
    
    try:
        # 重定向标准输出
        with redirect_stdout(stdout_capture), redirect_stderr(stderr_capture):
            # 执行脚本
            exec(script, execution_globals)
        
        # 提取结果
        figures = extract_matplotlib_figures()
        dataframes = extract_dataframes(execution_globals)
        
        execution_time_ms = int((time.time() - start_time) * 1000)
        
        return {
            "status": "success",
            "stdout": stdout_capture.getvalue(),
            "stderr": stderr_capture.getvalue(),
            "figures": figures,
            "dataframes": dataframes,
            "execution_time_ms": execution_time_ms
        }
        
    except Exception as e:
        execution_time_ms = int((time.time() - start_time) * 1000)
        error_msg = traceback.format_exc()
        
        return {
            "status": "failed",
            "stdout": stdout_capture.getvalue(),
            "stderr": stderr_capture.getvalue() + "\n" + error_msg,
            "error": str(e),
            "execution_time_ms": execution_time_ms
        }
    
    finally:
        # 清理 Matplotlib 图表
        plt.close('all')


def extract_matplotlib_figures() -> list:
    """提取 Matplotlib 生成的所有图表"""
    figures = []
    for i, fig_num in enumerate(plt.get_fignums()):
        fig = plt.figure(fig_num)
        
        # 保存为 PNG（Base64 编码）
        buf = io.BytesIO()
        fig.savefig(buf, format='png', dpi=100, bbox_inches='tight')
        buf.seek(0)
        img_base64 = base64.b64encode(buf.read()).decode('utf-8')
        
        figures.append({
            "index": i,
            "format": "png",
            "data": img_base64,
            "width": int(fig.get_figwidth() * fig.dpi),
            "height": int(fig.get_figheight() * fig.dpi)
        })
    
    return figures


def extract_dataframes(execution_globals: dict) -> list:
    """提取执行环境中的 pandas DataFrame"""
    import pandas as pd
    
    dataframes = []
    for var_name, var_value in execution_globals.items():
        if isinstance(var_value, pd.DataFrame):
            # 提取前100行作为预览
            preview_rows = var_value.head(100).to_dict(orient='records')
            
            dataframes.append({
                "name": var_name,
                "columns": var_value.columns.tolist(),
                "rows": preview_rows,
                "total_rows": len(var_value)
            })
    
    return dataframes

# 限制危险操作
RESTRICTED_IMPORTS = ['os', 'subprocess', 'sys', 'socket']

def validate_script(script: str) -> bool:
    """验证脚本是否包含危险操作"""
    import ast
    
    try:
        tree = ast.parse(script)
        for node in ast.walk(tree):
            # 检查导入语句
            if isinstance(node, ast.Import):
                for alias in node.names:
                    if alias.name in RESTRICTED_IMPORTS:
                        raise ValueError(f"导入 {alias.name} 模块被禁止")
            
            if isinstance(node, ast.ImportFrom):
                if node.module in RESTRICTED_IMPORTS:
                    raise ValueError(f"导入 {node.module} 模块被禁止")
        
        return True
    
    except SyntaxError as e:
        raise ValueError(f"脚本语法错误: {e}")

### 安全设计

#### 1. 脚本沙箱

**限制策略**:
- 禁止导入危险模块（os、subprocess、socket、sys）
- 限制文件系统访问（只能读取 /tmp/ 目录）
- 限制网络访问（只能访问白名单 URL）
- 内存限制（单个脚本最大 2GB）
- 超时限制（默认 5 分钟，最大 30 分钟）

**实现方式**:
```python
# 使用 RestrictedPython 库
from RestrictedPython import compile_restricted

def execute_restricted_script(script: str):
    # 编译受限代码
    byte_code = compile_restricted(
        script,
        filename='<script>',
        mode='exec'
    )
    
    # 提供受限的全局环境
    restricted_globals = {
        '__builtins__': {
            'print': print,
            'len': len,
            'range': range,
            # 只暴露安全的内置函数
        },
        'pandas': __import__('pandas'),
        'numpy': __import__('numpy'),
        # 只暴露白名单库
    }
    
    exec(byte_code, restricted_globals)
```

#### 2. 租户隔离

**数据隔离**:
- 脚本只能访问当前租户的数据
- MinIO 路径前缀包含 tenant_id
- PostgreSQL 查询自动过滤 tenant_id

**资源隔离**:
- Docker 容器级别的 CPU/内存限制
- 租户级别的并发限制（每个租户最多 5 个并发脚本）

## 风险评估与缓解措施

### 风险 1: 脚本安全风险
**描述**: 恶意脚本可能执行危险操作（文件系统访问、网络攻击）

**影响**: 高（数据泄露、服务中断）

**缓解措施**:
1. **技术防护**:
   - 使用 RestrictedPython 限制危险模块导入
   - AST 解析检测危险代码模式
   - 沙箱环境（Docker 容器 + cgroups 资源限制）
2. **流程防护**:
   - 脚本执行前进行代码审查（可选）
   - 租户级别的白名单管理（允许的模块列表）
   - 审计日志记录所有脚本执行
3. **监控告警**:
   - 异常行为检测（CPU/内存突然飙升）
   - 敏感操作告警（文件读写、网络请求）

---

### 风险 2: 资源耗尽
**描述**: 脚本执行占用过多 CPU/内存，导致服务不可用

**影响**: 中（影响其他租户）

**缓解措施**:
1. **资源限制**:
   - 单个脚本内存限制（2GB）
   - 单个脚本 CPU 限制（1 核）
   - 超时限制（5-30 分钟）
2. **并发控制**:
   - 全局并发限制（10 个脚本）
   - 租户级别并发限制（每租户 5 个）
3. **优先级队列**:
   - 交互式执行优先于调度任务
   - 付费租户优先于免费租户

---

### 风险 3: 复杂度增加
**描述**: Develop Backend 职责增加，维护难度提升

**影响**: 中（开发效率降低）

**缓解措施**:
1. **架构分层**:
   - 保持清晰的 Service 层边界
   - ScriptEngineService 独立实现
2. **代码复用**:
   - 复用 SQLEngineService 的模式
   - 复用 WorkflowEngineService 的 HTTP 调用逻辑
3. **单元测试**:
   - 高测试覆盖率（>80%）
   - 模拟 Python Workflow Engine 响应

---

### 风险 4: 依赖版本冲突
**描述**: 不同脚本需要不同版本的库（如 pandas 1.x vs 2.x）

**影响**: 低（部分脚本执行失败）

**缓解措施**:
1. **统一环境**（推荐）:
   - 所有脚本使用相同的库版本
   - 定期升级依赖，提前通知用户
2. **虚拟环境**（未来扩展）:
   - 为每个脚本创建独立 virtualenv
   - 按需安装依赖（会增加执行时间）
3. **依赖声明**:
   - 脚本声明依赖版本
   - 后端验证是否可用

---

### 风险 5: 调试困难
**描述**: 脚本执行失败时，用户难以定位问题

**影响**: 中（用户体验差）

**缓解措施**:
1. **详细日志**:
   - 捕获完整的 stdout/stderr
   - 记录 Python 异常堆栈
2. **变量检查器**:
   - 执行后展示所有变量
   - 支持中间结果查看
3. **测试模式**:
   - 提供"调试模式"（verbose 输出）
   - 支持分段执行（手动拆分为多个脚本）

---

### 风险 6: 数据泄露
**描述**: 脚本打印敏感数据到 stdout，被保存到数据库

**影响**: 高（合规风险）

**缓解措施**:
1. **敏感数据脱敏**:
   - 检测 stdout 中的敏感信息（密码、密钥）
   - 自动脱敏或告警
2. **访问控制**:
   - 执行结果只对创建者可见
   - 权限管理（查看、下载）
3. **审计日志**:
   - 记录所有执行记录的访问
   - 支持合规审计

---

### 风险 7: MinIO 存储成本
**描述**: 大量图表和数据集上传到 MinIO，存储成本高

**影响**: 低（可控）

**缓解措施**:
1. **结果保留策略**:
   - 执行结果保留 30 天（可配置）
   - 自动清理过期结果
2. **压缩优化**:
   - 图片使用压缩格式（PNG → JPEG）
   - DataFrame 使用 Parquet 而非 CSV
3. **配额管理**:
   - 租户级别的存储配额
   - 超额告警和限制
