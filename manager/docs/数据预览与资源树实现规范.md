# Manager 数据预览与资源树实现规范

> 状态：Manager 模块稳定实现规范。本文定义 Manager 数据探查、资源树、数据预览、容器子项选择和预览插件编排的当前契约。预览响应材料语义见 [数据预览语义协议](数据预览语义协议.md)，存储流和原始下载语义见 [存储流与原始下载语义](存储流与原始下载语义.md)。

## 一、定位

Manager 负责面向用户的数据探查和只读预览：

1. 从 System 读取用户可访问的引擎信息。
2. 从 Meta 读取已扫描入库的节点、item 和 attributes 事实。
3. 消费 Meta resource-tree API 定位资源树节点或数据项。
4. 通过 PreviewResolver 和 PreviewProvider 生成前端可展示的预览材料。
5. 对存储叶子提供 `storage-stream` 预览流，对存储型 item 提供 `downloads/file` 原始下载入口。

Manager 不管理存储引擎配置，不绕过 Meta 自行定义 data type / format，不提供通用资源树事实代理，不在预览链路中写入派生产物事实。资源树刷新归 Meta resource-tree；Manager 保留已知 item refresh 作为预览建议触发入口。空间快显、瓦片缓存和矢量物化视图属于独立快显体系，见 [快显概念说明](快显概念说明.md) 和 [快显实现规范](快显实现规范.md)。

## 二、ResourceLocator

Manager 预览、资源树刷新、资源定位和跨页面跳转统一使用标准 ResourceLocator URI 作为定位入口。

格式示例：

```text
addp://engine/1/path/?type=database&node_id=10
addp://engine/1/path/public?type=schema&node_id=11
addp://engine/1/path/public/users?type=table&item_id=100
addp://engine/1/path/bucket/folder/file.txt?type=object&item_id=101
```

约束：

1. `locator` 是公共 API 的主身份；`engine_id/schema/table` 等拆散参数只允许作为 provider 内部解析结果。
2. 路径由 ResourceLocator 负责编码和解码，调用方不得手工拼接未转义路径。
3. 预览必须基于已由 Meta 扫描入库的 node 或 item。缺少 Meta 事实时，应提示刷新或扫描，而不是由 Manager 直接猜测结构。
4. 前端保存选中节点、展开节点和跳转上下文时，应使用 locator，而不是旧式拼接 node id。
5. 资源树定位以 locator path 为主事实源。检索索引、任务记录或前端缓存中的 `node_id` / `item_id` 可能因重新扫描发生漂移，只能作为定位身份锚点，不能压过 locator path。
6. locator 是内部定位契约，不作为用户理解对象暴露。界面应展示引擎名、资源路径、资源名和操作按钮，不展示 locator URI。

## 三、API 契约

路由前缀为 `/api/v1/manager`。

### 1. 引擎与资源树

```http
GET  /engines
POST /engines/{engine_id}/items/refresh
```

Manager 不再提供 `/tree/{engine_id}` 通用资源树 API。资源树 root、node children、ancestors、search 和 refresh 统一调用 Meta：

```http
GET  /api/v1/meta/resource-tree/{engine_id}?expand_depth=2
GET  /api/v1/meta/resource-tree/{engine_id}/node?locator={resource_locator}
GET  /api/v1/meta/resource-tree/{engine_id}/ancestors?locator={resource_locator}
GET  /api/v1/meta/resource-tree/{engine_id}/search?q={keyword}&node_types=table,object&limit=50
POST /api/v1/meta/resource-tree/{engine_id}/refresh?locator={resource_locator}
```

资源树 API 返回面向前端的公共资源树节点，节点必须携带 locator。资源树节点展示字段来自 Meta node、Meta item 和 System engine 事实，不得改变 Meta 中的事实定义。

#### 资源树祖先链定位

`GET /api/v1/meta/resource-tree/{engine_id}/ancestors?locator={resource_locator}` 用于根据 ResourceLocator 返回从 catalog root 到目标资源自身的祖先链，服务资源树懒加载场景下的深层定位和高亮。

该接口语义是“为资源树展开返回祖先链”，不是读取内容、刷新扫描或创建 Meta 事实。

请求约束：

| 参数 | 说明 |
| --- | --- |
| `engine_id` | 路径参数，用于租户权限和 engine 边界校验。 |
| `locator` | 标准 ResourceLocator URI，必须与 `engine_id` 匹配，并携带 `node_id` 或 `item_id` 作为身份锚点。 |

响应结构：

```json
{
  "engine_id": 1,
  "target_locator": "addp://engine/1/path/bucket/a/b/report.pdf?type=object&item_id=123",
  "target_kind": "item",
  "ancestors": [
    {
      "locator": "addp://engine/1/path/?type=service&node_id=10",
      "type": "service",
      "label": "对象存储",
      "node_id": 10,
      "item_id": null,
      "has_children": true
    },
    {
      "locator": "addp://engine/1/path/bucket?type=bucket&node_id=11",
      "type": "bucket",
      "label": "bucket",
      "node_id": 11,
      "item_id": null,
      "has_children": true
    },
    {
      "locator": "addp://engine/1/path/bucket/a/b/report.pdf?type=object&item_id=123",
      "type": "object",
      "label": "report.pdf",
      "node_id": null,
      "item_id": 123,
      "has_children": false
    }
  ]
}
```

约束：

1. `ancestors` 必须按 root 到目标自身排序。
2. 最后一项必须对应 `target_locator`。
3. node 目标最后一项带 `node_id`，item 目标最后一项带 `item_id`。
4. 每项 locator 必须是标准 ResourceLocator，供前端作为 tree node key。
5. 展示字段可包含 `label/type/has_children`，但不得返回 engine 凭据或 provider 私有连接信息。
6. 部分祖先缺失时返回 404，不引入 `resolved=false` 成功态双轨响应。

Meta resource-tree 处理原则：

1. 先解析 locator，校验 engine、type、`node_id` / `item_id`。
2. 如果 locator 携带 `item_id`，先按 locator path 查询当前 Meta item，再基于当前 item ID 查询祖先链，并用当前 `full_name` 和 item_type 生成目标 locator。
3. 如果 locator 携带 `node_id`，先按 locator path 查询当前 Meta node，再基于当前 node ID 查询祖先链，并用当前 node path 生成目标 locator。
4. 祖先链事实来自 Meta 已落库 node 关系，不触发扫描，不写 Meta attributes，不隐式创建 node / item。
5. engine catalog 模型差异由 Meta resource-tree 统一处理，前端只消费返回链。

### 2. 数据预览

```http
GET /preview?locator={resource_locator}&page=1&page_size=20
```

容器和多组件格式的选择参数必须保持语义独立：

| 参数 | 语义 | 示例 |
| --- | --- | --- |
| `child_name` | 当前容器第一层 child。 | `Sheet1`、`cities`、`inner.zip` |
| `ref_path` | multi 格式 child 的 ref 路径。 | `roads.shp`、`roads.dbf` |
| `nested_child_path` | 当前 child 是容器时，其内部 child 相对路径。 | `data/cities.csv`、`middle.zip/data/cities.csv` |

示例：

```http
GET /preview?locator={zip_locator}&child_name=inner.zip&nested_child_path=data/cities.csv
GET /preview?locator={zip_locator}&child_name=roads.shp&ref_path=roads.dbf
```

这些参数不能互相替代：

1. `child_name` 只表示当前容器的第一层 child。
2. `ref_path` 只表示 multi item 的组成 ref。
3. `nested_child_path` 只表示已经进入 child 容器后的内部路径。
4. 前端切换 child、ref 或 nested child 时，应重新请求预览，并重置与上一层选择不兼容的参数。

### 3. 存储流与原始下载

```http
GET /storage-stream?engine_id={engine_id}&storage_ref={storage_ref}
GET /downloads/file?locator={resource_locator}
```

`storage-stream` 永远只读取一个存储叶子内容，支持 HTTP Range，主要服务 PDF、图片、视频、音频等在线预览。

`downloads/file` 表示下载一个存储型 item 逻辑对象，由后端基于 ResourceLocator 和 DownloadPlan 自动选择单文件流或 multi refs zip 打包。前端不得根据 `format`、`preview_material`、`frontend_renderer` 或 `content.metadata.refs` 自行拼接下载。

### 4. 资源动作能力

Manager 面向用户提供四个数据进出动作：

| 动作 | 适用对象 | 用户含义 | Transfer 参与 |
|---|---|---|---|
| `upload` | 存储型 engine 的 node | 把本地文件上传到 bucket / prefix / directory。 | 不参与 |
| `download` | 存储型 engine 的 item | 把已有文件 / 对象原样下载到本地，multi refs 可由后端打包。 | 不参与 |
| `import` | 数据库 engine 的 node | 把本地 table 型文件导入为数据库表。 | Manager 创建并触发 Transfer `sync` |
| `export` | 数据库 engine 的 item | 把数据库表导出为本地文件。 | Manager 创建并触发 Transfer `sync` |

资源树当前选中的 node 或 item 不支持某个动作时，前端不得显示对应按钮。前端不应按 engine type、item type、format 或 data type 自行散落判断，而应调用 Manager 的资源动作能力 API：

```http
GET /resource-actions?locator={resource_locator}
```

`resource-actions` 只回答当前资源可显示哪些 Manager 用户动作，以及对应格式、限制和不支持原因；它不负责执行业务动作，不创建 Transfer 任务，不触发 Meta scan，也不保存资源树事实。

动作矩阵：

| 当前资源 | 显示动作 | 不显示动作 |
|---|---|---|
| MinIO bucket / prefix node、NFS directory node | `upload` | `download` / `import` / `export` |
| MinIO / NFS file item、multi refs item | `download` | `upload` / `import` / `export` |
| PostgreSQL schema node、MySQL/Doris/ClickHouse database node | `import` | `upload` / `download` / `export` |
| 数据库 table item | `export` | `upload` / `download` / `import` |

第一阶段不支持数据库 table item 的当前页预览下载，不支持 database / schema node 级下载，也不支持 bucket / prefix / directory node 级导出。

## 四、后端实现路线

### 1. ExplorerService

ExplorerService 是 Manager 数据探查页的轻量业务服务，负责：

1. 调用 System 获取当前租户可访问引擎。
2. 过滤出可用于 Manager 数据探查的存储引擎。

ExplorerService 不再构造资源树节点，不触发资源树刷新，不直接实现具体格式预览逻辑。资源树事实统一由 Meta resource-tree API 提供。

### 2. PreviewResolver

PreviewResolver 是预览编排层，负责：

1. 解析 ResourceLocator。
2. 根据 locator 查回 System engine 和 Meta node / item。
3. 组装 PreviewResolverRequest，包括分页、容器选择、Graph sample filter、Meta attributes、item fingerprint、scanned depth 等上下文。
4. 将请求转换为 PreviewProvider 所需的 PreviewRequest。
5. 通过 PreviewRegistry 选择 provider 并执行预览。
6. 组装 PreviewResult。

PreviewResolver 必须保证预览来源可追溯到 locator 和 Meta facts；不得为了兼容旧调用重新接受 `schema/table` 作为公共入口。

### 3. PreviewRegistry 与 PreviewProvider

PreviewRegistry 维护已注册的 PreviewProvider。Provider 应按能力处理明确的预览模式：

| 模式 | 典型来源 | 说明 |
| --- | --- | --- |
| `node` | catalog node、目录、bucket、prefix | 返回节点概览或容器索引。 |
| `table` | 数据库表、文件表、图样本表格化概览 | 返回 rows / columns 等表格材料。 |
| `object` | 文件、对象、multi item、容器 child | 返回对象预览材料或不支持状态。 |

Provider 只生成 Manager 预览材料，不反向定义平台 data type / format。新增 provider 时，应同时补充语义矩阵测试，确认 `content.kind`、`preview_material`、`frontend_renderer` 一致。

## 五、前端实现路线

前端 DataExplorer 以 Pinia store 维护资源树和预览状态：

1. `engines`：当前可访问引擎列表。
2. `engineTrees`：按 engine id 缓存资源树。
3. `selectedLocator`：当前选中资源 locator。
4. `expandedLocators`：已展开节点集合。
5. `selectedChildName` / `selectedRefPath` / `selectedNestedChildPath`：容器和 multi item 当前选择。
6. `previewData` / `activeChildPreviewData`：当前预览结果。
7. `pagination`：预览分页状态。

前端发起预览时必须传 locator。普通预览组件按 `frontend_renderer -> preview_material -> content.kind` 选择 renderer；不得直接用 `format` 选择组件。

资源树定位流程：

1. 从数据检索结果、向量化结果、任务详情、快显或跨页面跳转中拿到 locator。
2. 调用 `GET /api/v1/meta/resource-tree/{engine_id}/ancestors?locator=...`。
3. 按 `ancestors[].locator` 逐级合并到当前资源树状态。
4. 保留已加载 sibling children，不因为定位链覆盖已有子节点。
5. 展开祖先节点，并把 current node key 设置为目标 locator。

前端不得为了定位深层资源自行拆分 `/`、`.`、bucket、schema 或 table，也不得绕过 ancestors API 递归查找尚未加载的树节点。

## 六、与其他 Manager 能力的关系

### 1. 与快显

普通空间预览返回源坐标下的小样本 geometry，并通过 CRS 字段告诉前端是否可直接渲染。普通预览不做后端 CRS transform，不返回双 geometry 字段，不隐式创建 3857 物化视图或瓦片缓存。

空间数据需要地图式连续浏览时，走 Quick View capability、动态 MVT 或瓦片缓存体系。

快显、瓦片缓存、矢量物化视图等创建页的路由入口也应只以 locator 作为资源身份。`schema/table/source_engine_id` 可以继续作为空间渲染、建表和任务执行配置字段，但必须由 locator capability 解析或任务记录反填，不能作为创建入口锁定来源的并行定位路线。

### 2. 与向量化

预览可以展示向量化入口和状态，但向量化任务定义、execution 和结果状态归向量化能力管理。预览不得把 embedding 结果写入自身响应事实源。

### 3. 与导入和导出

资源树数据库 node 可以提供“导入”入口；数据库 table item 可以提供“导出”入口。完整数据库表导出、跨格式转换和批量数据产出进入 Manager export，内部调用 Transfer sync。文件/对象原始下载走 `downloads/file`。

第一阶段导入、导出、上传、下载的后续专题不进入当前主路径：

1. 上传 zip 默认按单个原始对象写入存储型 engine；“解压后上传”需要先补用户交互和 Meta scan 边界设计。
2. 下载第一阶段不引入 download session；如后续需要下载审计、大文件准备、一次性 token 或断点续取，再设计独立 session。
3. 导入第一阶段不引入 import session；如后续需要导入历史、失败重试、上传包保留或可追溯审计，再设计独立 session。
4. 多 item 批量 download / export、外部 URL import 等能力需先确认用户场景和 Transfer 支持边界，再进入实现。
5. export 创建请求应进入审计；导出文件下载是否单独审计，后续按统一审计规范确认，不在当前 Manager resource-actions 中隐式扩展。

## 七、禁止事项

1. 不得恢复旧的 `engine_id/schema/table` 公共预览入口。
2. 不得让 Handler 按单一数据源写特殊预览分支；格式和数据源差异应进入 PreviewProvider。
3. 不得把 `preview_material` 当成 `common/format` reader capability。
4. 不得把 unsupported 预览伪装成 text 或 empty table。
5. 不得在前端解析 multi refs 或拼接 zip 下载。
6. 不得在普通预览链路隐式创建矢量物化视图目标、瓦片缓存、embedding 或其他派生产物。
