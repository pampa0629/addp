# Manager 数据剖析规范

> 状态：当前实现规范。本文定义 Manager 表格型数据剖析的产品边界、模块归属、执行语义、结果语义和演进约束，不得另建平行路线。

## 一、定位

数据剖析（data profiling）是在数据开发和数据分析之前，通过受控采样理解表格型 data item 或其条件数据范围的规模、完整性、基数、值域和分布特征的 Manager 数据探查能力。

数据探查中的三个视图统一为：

```text
预览 | 剖析 | 属性
```

- 预览回答“具体记录是什么”。
- 剖析回答“这份数据整体呈现什么特征”。
- 属性回答“Meta 已保存了哪些身份、结构、格式和能力事实”。

剖析不是：

- Meta scan 的默认阶段。
- BI 聚合分析或业务报表。
- Quality 质量规则检查、质量评分或问题工单。
- Develop 查询工作台的替代品。
- 接受 SQL 文本、SQL 片段、函数、子查询或关联查询的自由查询入口。
- 根据当前预览页记录临时拼出的前端统计。

## 二、对象边界

首期剖析对象固定为内容语义为 `data_type=table` 的 data item 或当前选中的表格型容器 child。

是否展示剖析能力必须根据 Meta attributes 和当前内容选择上下文判断，不得只根据 `item_type=table`、引擎类型、文件扩展名或预览 renderer 判断。因此：

- PostgreSQL / MySQL / Doris / ClickHouse 等数据库 table 或 view 可以进入剖析。
- `item_type=collection + data_type=table` 的动态 schema 记录集合可以进入剖析。
- CSV、Parquet 等表格文件可以进入剖析。
- Excel、SQLite 等容器内选中的表格 child 可以进入剖析，但 child 选择参数必须与预览协议保持一致。
- point cloud、gaussian splat、CAD entity 等即使内部可列化，也不能因此归入表格剖析。

首期不包含字段相关性、联合分布、重复行分析、异常检测模型、历史趋势、报告导出和自动质量评分。

## 三、模块归属

数据剖析的执行、结果和生命周期统一归 Manager 所有。

| 对象 | Owner | 职责 |
| --- | --- | --- |
| data item 身份与结构事实 | Meta | 提供 ResourceLocator、item fingerprint、source version、字段结构、行数和扫描事实 |
| 剖析执行 | Manager | 校验权限和能力，冻结执行配置，采样、计算、限流并提交结果 |
| 剖析结果 | Manager | 保存当前成功结果、字段分布、观察结论和源依赖快照 |
| 执行历史 | Common | 统一写入 `common.task_executions` |
| 通用结果结构与 Provider 契约 | Common | 只承载稳定结构和接口，不拥有存储、任务或生命周期 |
| 质量规则与质量问题 | Quality | 独立执行正式质量检查；不能把采样剖析直接视为质量结论 |

Manager 不得把字段级剖析结果写入 `meta_item`、`meta_item.attributes` 或 Meta 私有结果表。其他模块不得直接读取 Manager 私有表，应通过 Manager API 或后续明确的完成事件消费结果。

## 四、Meta Scan 边界

Meta basic / deep scan 可以保存其职责范围内的低成本事实：

- 字段名、字段类型、主键和可空声明。
- catalog、system table、格式头或有限分析可提供的精确 / 估算行数。
- 数据大小、索引、空间字段和格式结构。
- 动态 schema 推断所使用的采样规模、是否采样和平均记录大小等扫描过程事实。

Meta scan 不得为了数据剖析自动计算：

- 字段实际空值率、不同值数和唯一率。
- 均值、中位数、分位数和标准差。
- 字段直方图、高频值和长度分布。
- 常量列、高缺失、高基数和分布偏斜等观察结论。

Meta scan 成功不表示剖析结果存在；剖析失败也不得影响 data item 发现、资源树、预览、下载或 Meta 扫描状态。

## 五、触发与执行

### 当前授权切换边界

后台采样必须使用 `manager.data_profile.execute` 对应的独立 execution 源授权，不能借用普通预览凭据、服务账号或仅凭已选叶子读取。2026-10-06 按用户决定收敛首版：开放已扫描 PostgreSQL 单表的有界采样，视图、物化视图和多来源计划明确不支持；只消费已绑定的分页计划，逐页及提交前复核现行授权与本地保护。旧 Preview／ReadBatch 采样路径不恢复。首版暂不处理准备后源端并发 DDL 改变读取对象的特殊情况，不宣称原生事务内依赖冻结已经完成。

剖析结果也是源数据的派生内容，不能仅凭功能权限或历史执行成功读取。结果的 `dependency_snapshot.read_set` 必须来自实际采样计划的完整、规范 `QueryReadSet`，包含视图及其底表；不能从当前选中叶子、当前 Meta 结构或历史血缘补造。缺失、空集合、非法或非规范来源的历史结果保留但拒绝返回，不能回填后继续展示。

读取结果使用当前同步请求的普通 User Bearer 调用 System 固定 `manager-profile-result` 检查，复核当前 `manager.data_item.read`、Client API Scope 和全部历史来源的现行源规则。不存储或后台转发 Bearer，不借机器身份重试，不把旧 Execution Authorization 当作结果 TTL 或当下 Allow。部门／项目组 Grant 和 Deny 仍由 System 唯一判断；结果不因此变成发起人的私有副本。本地 Security 保护继续独立执行。此只读检查不签发执行授权，不恢复后台采样。

### 1. 标签页按需触发

选择 data item 时只加载预览和已有 Meta 事实，不执行剖析。用户首次打开“剖析”标签时：

1. Manager 查询当前成功剖析结果和活跃 execution。
2. 当前结果存在且源版本、模式和配置一致时直接展示，不创建 execution。
3. 当前结果不存在时自动创建一次采样剖析 execution。
4. 已有相同语义的 `pending` / `running` execution 时复用其状态，不重复创建并发执行。
5. 当前结果已过期时继续展示旧结果和过期原因，由用户显式刷新；不得因每次切换标签自动重跑。

### 2. 首期是 ad-hoc execution

首期剖析统一为一次性执行：

```text
module=manager
task_type=data_profiling
source_task_id=null
trigger_type=manual
```

`execution_config` 必须冻结本次执行所需的完整配置，包括资源定位、稳定源身份、源版本、模式、采样策略、预算、字段范围和配置版本。

后台消费只接受当前配置版本及完整冻结预算，逐项核对模式、采样策略、配置摘要、引擎和源身份；预算缺失或非法时拒绝，不使用进程默认值补齐。采样和超时均使用入队预算，进程配置后续变化不得扩大这次执行。配置摘要覆盖超时，旧版本执行不迁就或回填；重新解析的引擎或源身份不一致时，在采样前拒绝。上述核验只固定执行边界，不代表 System 已授予源读取权。

剖析入队只接受认证中间件提供的当前租户 User AuthContext。发起人、租户成员关系及授权版本分别冻结到共享 execution 的 `actor_principal_id`、`actor_tenant_membership_id`、`issued_authorization_version`；`triggered_by` 只是展示事实，不能替代授权来源。请求体不得指定这些身份，不保存或后台转发 User Token，也不以这些来源事实代替 System 的当前授权判定。

活跃执行的复用及当前账号的活跃／最近执行查询，必须同时绑定租户、发起人、租户成员关系、授权版本、资源、内容选择和配置。不同账号、成员关系或授权版本不能复用同一执行。已成功的当前剖析结果仍遵循原有资源／配置结果与保护契约；执行复用隔离不表示结果已经获得独立源授权，也不改变结果的共享范围。缺少可信来源的请求不得入队；不支持的来源在准备时拒绝，缺失或失效的独立源授权在读取前拒绝。

首期不创建 `manager.data_profile_tasks`，不提供剖析任务管理页，也不把 `data_profiling` 声明为可供 Orchestrator 选择的 TaskProvider 任务类型。

### 3. sample / full 与任务定义正交

`sample` 和 `full` 是同一执行能力的范围模式，不是两个 task type：

- 首期只开放 `mode=sample`。
- 契约预留 `mode=full`，但未完成成本控制、执行能力和验证前不得在 capability 或 UI 中宣称可用。
- 未来一次手动全量剖析仍可以是 ad-hoc execution。
- 只有用户明确保存可重复、可调度、可编排配置时，才新增持久任务定义并接入 TaskProvider。

未来持久任务必须复用同一个 DataProfileExecutor、结果结构和结果表，不得形成“页面剖析”和“任务剖析”两条实现路线。

### 4. 剖析数据范围

剖析数据范围（profile data scope）固定为：

- `kind=all`：分析当前 data item 或容器 child 的全部逻辑行范围。
- `kind=condition`：先按结构化字段条件限定逻辑行范围，再对命中行执行采样剖析。

条件剖析首期采用单层条件组：一组条件统一使用 `logic=and|or`，不支持嵌套组。每个条件只能包含 Meta schema 中存在的字段、允许的操作符和按 ADDP 统一类型校验后的值。首期操作符为：

- 通用：`eq`、`ne`、`is_null`、`is_not_null`。
- 数值和时间：`gt`、`gte`、`lt`、`lte`、`between`。
- 字符串：`contains`、`starts_with`。
- 离散值：`in`、`not_in`。

前端和 API 不得提交 SQL 文本、SQL 片段、函数名、排序、分组、关联或子查询。条件规范化后必须进入 `profile_config_hash` 和 execution 的 `target_key`；同一源上的全范围结果与不同条件结果分别保存，互不覆盖。

首期条件只是 ad-hoc execution 的冻结配置，不提供命名保存、常用条件管理、定时执行或 TaskProvider 能力。

## 六、采样与计算

### 1. 统一执行入口

恢复后台采样前，Manager 必须先准备本次预算内的全部分页查询，再从这些不可变 `PreparedQuery` 取得完整 `QueryReadSet`。分页查询生成复用表格预览的唯一数据库查询生成器，但不调用预览读取、不统计预览响应。准备阶段只读取结构／依赖目录事实，不执行内容查询、行数查询或采样；任一分页依赖无法证明时整次准备失败，不能缩小为选中叶子。

首版采样只覆盖 PostgreSQL 单表，完整 ReadSet 必须只有一个 `kind=table` 的叶子；不能从视图的完整依赖集合中只取底表继续执行。累计读取预算不超过 10000 行，单页不超过 2000 行。全部范围的页位置按已扫描行数作系统化分布；未知行数、条件范围或缺少分页稳定键时保留有界／部分采样语义。分页 offset、limit 和完整读取集合由 Manager 冻结，不由浏览器提供；预算非法时拒绝，不补默认值、不保留未核验 ReadBatch 路线。每页只能消费其原计划，规范来源集合必须与绑定集合一致。

2026-10-06 的真实 PostgreSQL 回归发现：普通 SQL PreparedQuery 的执行没有在内容读取事务内复核视图依赖，准备后替换视图定义可能读取新的底表。用户决定暂时搁置此类特殊并发情形，优先交付首版。因而当前门禁验证单表正常读取、授权拒绝及视图不支持，不再要求并发改源增强作为首版先决条件。此缺口仍记入专题后续清单；普通表并发删除重建为视图也不属于本轮保证，不能将范围收缩说成根因修复。后续增强应在共享 Provider 唯一执行边界实现，Manager 不自行解析 SQL、不回退旧读取路径。

准备计划不是 Allow，不能据此恢复生产采样。实际接线还须完成 v6 入队、当前 User 签发、授权引用绑定、有效 lease 下的 Service 消费，以及逐次内容读取和结果提交前复核。完整配置摘要使用 Common 的 `NewManagerProfileReadScope`；输入必须是持久执行记录的原始 JSON，不得经过 GORM `JSONMap` 的浮点数反序列化后再计算。Common 只规范化完整 JSON、克隆和校验来源集合，不解释 Manager 私有配置、不作授权决定。

v6 创建先冻结全部页位置和完整 ReadSet，保存发起人来源，然后仅在当前同步 User 请求内签发。绑定必须在同一行锁事务内重读原始配置，核对完整范围、租户、执行、发起人、成员关系和授权版本；只有尚未领取且没有授权引用的 pending 执行可绑定。未绑定的剖析不得被混合任务队列领取，也不能阻塞其他任务类型；授权引用只表示可以领取，不是源读取 Allow。签发或绑定失败时关闭该未领取执行，不保存 User Bearer、不自动重试。相同主体的已绑定活动执行可以复用；正在签发的未绑定执行不报告受理成功。持久化后的签发和绑定共用最长 60 秒的系统处理预算；中断遗留且创建超过 2 分钟的未绑定 pending 由现有队列恢复流程显式失败收敛，给请求清理留出余量，不能长期占用活跃复用键。这两项时间只限制系统准备过程，不是用户的数据访问有效期。后台消费必须从持久原始 JSON 解码，不能通过 `JSONMap` 重编码恢复条件或摘要。

Worker 消费入口只接受已领取的本租户 Manager 手工 bounded 剖析执行。上下文 lease 必须与执行的 execution、tenant、attempt、token、owner 完全相同，且执行已绑定正数授权引用和到期时间。租约与授权的当前有效期由 System 依据数据库现状核验，不以领取时的时间快照作长期放行依据。Worker 从持久原始 JSON 生成完整范围，并重新准备全部分页；分页位置和规范完整 ReadSet 必须与冻结配置完全一致，不能以来源子集替代。仅在这些条件成立后，通过当前 Tenant Service 调用固定消费入口；缺少客户端、撤权、到期、租约变化、无完整观察响应或 System 不可用均阻断采样。成功观察不缓存、不重试，也不等于逐页及提交前持续授权或原生执行来源已经被证明。

实际采样只消费重新核验的同一不可变分页计划，不重新准备查询。Worker 每页读取前重新核验完整源授权，并在本地保护 checkpoint 边界复核原保护版本、当前规则与自然到期；授权观察不缓存，取消或任何核验失败均停止后续读取。累计读取与返回样本分别受冻结预算约束，返回列必须与 Meta 字段一致，不发额外 COUNT。未知行数、条件范围或没有稳定分页键时明确标记部分采样，不把有界读取宣称为全范围代表性。

结果提交前在本地事务外再次消费相同源授权，然后在原保护版本的事务内重新核验当前保护并写入结果与字段。不得持执行行更新锁跨 HTTP 调用 System；System 当前观察与 Manager 本地写入不是跨数据库原子事务，也不是一段缓存有效期。执行租约仍由 Repository 在同一结果写入事务内核验。

当前受控执行切片检查完整 ReadSet 的全部本地保护状态。选中条目的已实现 `profile=suppress` 继续在结果写入前删除字段剖析及观察；读取集合中其他受管来源在底表字段到剖析输出的保护映射完成前明确拒绝，不能因为选中视图未受管就忽略底表保护。此限制不改变完整源 Grant／Deny 的核验，也不表示全部视图的保护执行已经完成。

Manager 必须通过统一的数据剖析编排服务调用稳定 Provider 契约。引擎和格式差异留在 Provider 内，不得在 Handler、Frontend 或按 engine type 分叉的 service 代码中拼接私有 SQL。

字段剖析的语义结构使用 Meta 已保存的 `type_info.table.fields`。其中 `type` 是指标选择、类型筛选和观察计算的唯一依据；采样 Provider 只负责读取字段值，不得用预览展示类型或 `native_type` 重新定义字段语义。`native_type` 只作为来源结构辅助信息随剖析结果保存和展示。采样列与 Meta 字段结构不一致时应报告源结构变化，不得退回到原生类型猜测。

Provider 能力必须显式声明和检测。不支持剖析时返回稳定的不可用原因，不得退回到预览首屏、随机前 N 行或前端本地统计。

条件必须在采样之前由 Provider 对源数据执行：

```text
源数据 -> 条件过滤 -> 命中行采样 -> 剖析指标
```

数据库 Provider 必须使用字段白名单、方言标识符引用和参数绑定；文件或对象 Reader 必须具备等价的 predicate pushdown 或有界条件读取能力。Provider 不支持条件过滤时应声明 `condition_supported=false`，不得先采样或读取预览页再在 Manager / 前端过滤。

### 2. 采样要求

采样结果必须记录：

- `sample_method`
- `sample_size`
- `profile_mode`
- `profile_config_hash`
- `profiled_at`
- source version / dependency snapshot
- 是否截断、近似和部分完成
- `data_scope` 及条件范围的命中行数精确 / 未知语义

采样不得以 `ORDER BY random()` 全表排序作为通用实现，也不得默认前 N 行具有代表性。数据库来源应由对应 Provider 使用引擎可承受、可解释的采样或聚合能力；文件和对象来源应通过受控 reader / access index 读取，并遵守最大读取行数、字节数、字段数、耗时和并发预算。

预算由 Manager 服务端统一控制。前端和普通调用方不能提交无限制采样规模、任意 SQL 或绕过超时的参数。

### 3. 指标矩阵

所有支持字段应提供可用值数、空值数、空值率、不同值数及其精确 / 近似语义。类型专用指标首期至少包括：

| 字段类型 | 指标 | 分布 |
| --- | --- | --- |
| 数值 | min、max、mean、median、quantiles、stddev、zero_count、negative_count | 直方图 |
| 时间 | min、max、有效值数、时间覆盖范围 | 自适应时间桶 |
| 字符串 | empty_count、blank_count、min_length、max_length、avg_length、distinct_count | 长度直方图、受限 Top N |
| 布尔 / 低基数枚举 | 各值数量和占比 | 受限横条分布 |
| 空间字段 | 空值、有效几何数量、实际几何类型分布 | 几何类型分布；地图仍归预览 / 快显 |

指标未计算、Provider 不支持和真实值为 0 必须是三种不同状态。近似 distinct、估算行数和采样比例不得伪装为精确值。

## 七、结果模型与生命周期

### 1. 结果与 execution 分离

概念对象保持分离：

| 对象 | 建议存储 | 含义 |
| --- | --- | --- |
| 当前剖析结果 | `manager.data_profiles` | 最近一次成功结果的表级摘要、源依赖和结果版本 |
| 字段剖析结果 | `manager.data_profile_fields` | 每个字段的指标、分布和观察标签 |
| 执行历史 | `common.task_executions` | pending / running / success / failed / timeout / cancelled 过程 |

数据库字段、索引和 JSON schema 在实现阶段同步写入 Manager 数据库架构文档。结果表不得充当任务定义表或 execution 历史表。

### 2. 稳定身份与新鲜度

结果关联必须至少保存：

```text
tenant_id
item_fingerprint
item_id
locator
source_version / dependency snapshot
profile_mode
profile_config_hash
last_execution_id
```

稳定源身份使用 `tenant_id + item_fingerprint`；`item_id` 和 locator 只用于当前回查。源版本和配置 hash 用于判断当前结果是否仍适用，不得用 item fingerprint 代替内容版本。`profile_config_hash` 必须包含规范化的剖析数据范围，因此全范围和各条件范围可以同时拥有当前成功结果。

Manager 不对 Meta 私有表建立跨模块数据库外键。Meta item 重新扫描导致 ID 漂移时，应按稳定身份回查并更新当前引用。

### 3. 成功切换与失败保留

- 新 execution 运行期间继续提供上一份成功结果，并显示正在刷新。
- 新 execution 成功后，原子提交表级和字段级结果并切换 `last_execution_id`。
- 新 execution 失败或超时时保留上一份成功结果，错误只进入 execution 和面向用户的执行摘要。
- 首次执行失败时表现为“暂无剖析结果 + 最近执行失败”，不得创建伪成功结果。
- 源版本变化后旧结果标记为 stale，但不自动删除或自动重跑。

剖析刷新不需要快显物理产物式的 `existing_result_action=overwrite` 确认；它通过成功后原子替换当前逻辑结果实现无损刷新。

## 八、前端呈现

“剖析”标签只在当前内容语义支持时显示，并采用按需加载。首期布局包括：

1. 数据范围：默认全部数据；Provider 支持时允许使用单层 `AND` / `OR` 条件构造器发起条件剖析，并支持清除条件返回全范围结果。
2. 紧凑摘要带：数据范围、行数、字段数、模式、样本量、执行时间、源版本和新鲜度。
3. 字段剖析表：以 ADDP 统一类型为主，支持按统一类型、空值率、基数和观察标签筛选、排序。
4. 字段详情：根据统一类型展示指标和分布图，同时展示只读的原生类型；统一类型为 `unknown` 时仍必须显示原生类型以便诊断 Provider 映射。
5. 数据观察：展示高缺失、常量、疑似标识、高基数和明显偏斜等描述性观察。

观察只能描述数据特征，不得称为质量问题、违规或质量评分。图表必须使用成熟图表库，不手写统计绘图引擎；颜色使用 ADDP 主题变量，图表在空数据、单值、长标签、宽表和窄屏下不得溢出或重排失控。

## 九、权限与敏感信息

- 读取剖析结果至少要求对源 data item 的内容读取权限，因为 Top N、min / max 等聚合仍可能泄露业务值。
- 发起剖析属于有源端读取成本的操作，实现时应定义独立的 Manager execute permission，不得仅凭资源树可见权限执行。
- 每次读取当前结果都重新校验租户和源 data item 权限，不能因为结果已缓存而绕过授权。
- Top N、min / max 和分布标签不得写入搜索索引、日志、错误详情或 Meta attributes。
- 其他模块使用内部服务认证读取时仍必须携带明确租户和资源上下文，不能用内部 API key 绕过 owner 授权决策。
- 数据剖析在解析到 Meta DataItem fingerprint 后必须查 Manager 本地保护投影；未纳管时继续原路径，用户请求期间不调用 Security。
- 当 DataItem 已纳管时，Manager 只接受有效 `profile` 动作规则。`profile=suppress` 删除敏感字段、全部祖先 object/array 容器的字段剖析对象和对应全局观察，避免父级 Top N 通过完整对象或数组再次携带敏感叶子值；Top N、min/max、分布、基数、空值统计及类型专属指标均不得持久化或返回。保护后 `field_count` 表示可见字段数。`profile=deny`、未知效果、规则冲突或结构不匹配统一返回禁止访问。
- `preview` 的行值遮盖算法不得直接复用于 `profile`。Security 唯一编译器把有效 `preview=mask|suppress` 派生为 `profile=suppress`，把 `preview=deny` 派生为 `profile=deny`；`profile` 首期不建立可编辑 Policy，也不产生 `allow|mask`。
- 已纳管 DataItem 首期只允许 `kind=all`。在条件值保护契约落地前，`kind=condition` 创建和读取统一拒绝，避免条件原值进入 execution 配置或返回结构。
- 后台 execution 在采样前通过 Common 在 checkpoint 锁内读取持久保护事实并绑定版本，采样不占用该锁。提交时在同一 checkpoint 锁内比较版本、重新校验规则有效期、保护结果，并使用同一事务提交表级和字段级结果；版本变化以 `protection_version_changed` 失败，提示用户重新执行，不自动重跑。投影 upsert、revision 变化或 release 时，Manager 必须在保存投影 cursor 的同一事务删除目标的历史剖析结果并清除历史条件原值；任一步失败都不得确认新 cursor。Manager 重启对已安装投影重放清理，release 后不恢复旧缓存结果。保护变化清除的结果不能因“失败保留”被恢复；未被清除的上一份成功结果继续保留。

## 十、跨模块消费

其他模块消费剖析结果时使用 Manager 正式 API：

- 单个 data item 的当前完整结果。
- 多个 data item 的紧凑摘要批量查询。
- 后续确有异步投影需求时，由 Manager 发布剖析完成事件。

Quality 可以使用剖析结果推荐规则，但正式检查必须重新按 Quality 规则执行。Asset、Model、Copilot 等模块可以消费所需投影，但不得复制 Manager 完整结果作为第二事实源，也不得直接查询 Manager 私有表。

Manager 不可用或结果不存在时，消费者应表现为“暂无剖析结果”，不能阻塞自身核心流程。

## 十一、当前实现基线

当前首期实现统一为：

1. `manager/backend/internal/dataprofile` 定义 Manager 拥有的 `data.profile/v2` 结果结构并计算描述性指标；`v2` 显式携带规范化的 `data_scope`。其他模块通过 Manager API 消费结果，不依赖其内部 Go 类型。
2. `manager.data_profiles` 和 `manager.data_profile_fields` 保存当前成功结果，不保存失败状态或任务定义。
3. `GET /api/v1/manager/data-profiles/current` 查询结果、新鲜度和关联 execution，不隐式执行。
4. `POST /api/v1/manager/data-profile-executions` 创建或复用 `data_profiling` ad-hoc execution。
5. 服务端默认采样预算为 2000 个样本、最多扫描 10000 行、每批 500 行、超时 2 分钟、最多并行执行 4 个剖析；采样页在源数据范围内系统化分布，并使用 reservoir 收敛最终样本。
6. 前端只在当前有效内容为表格语义时展示“剖析”，首次进入且无结果时自动执行；pending / running 状态轮询，stale 结果继续展示并由用户显式刷新。
7. ECharts 只作为 Manager 前端局部依赖，用于字段分布图；`common-frontend` 不承担图表库依赖。
8. 条件剖析使用结构化 `data_scope`；当前只对能够源端过滤并安全绑定参数的 Provider 开放。创建 execution 返回服务端计算的 `profile_config_hash`，后续按该 hash 查询条件结果，条件值不进入 GET URL。

`full`、持久任务定义、TaskProvider、Orchestrator 和历史趋势仍属于后续独立设计范围。

## 十二、禁止事项

1. 不得把字段级剖析结果写入 Meta attributes。
2. 不得从预览页记录、当前分页或前端本地数组计算并冒充数据剖析。
3. 不得为 `sample` / `full` 建立两个 task type 或两套执行器。
4. 首期不得隐式创建 `data_profile_tasks`，也不得在 TaskProvider capabilities 中声明不存在的任务定义。
5. 不得把 execution 状态写成结果状态，或用结果表替代 execution 历史。
6. 不得因刷新失败删除上一份成功结果。
7. 不得把描述性观察升级为 Quality 结论。
8. 不得让其他模块直接读取 Manager 私有表。
9. 不得在 Manager 数据剖析 API 或前端接受任意 SQL。
10. 不得在 Provider 不支持源端条件过滤时退回到采样后过滤。
