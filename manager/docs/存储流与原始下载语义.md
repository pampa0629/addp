# Manager 存储流与原始下载语义

## 背景

浏览器不能假设可以直接访问真实数据存储引擎。MinIO、S3、NFS、NAS、HDFS 等存储可能位于内网、容器网络或只允许后端服务访问。因此 Manager 暴露给前端的预览流和原始下载入口必须以 ADDP 后端代理为稳定契约，而不是以真实存储 URL 为默认契约。

Manager 将存储内容访问拆成两个不同 HTTP 语义：

- `storage-stream`：读取一个存储叶子内容，支持 HTTP Range，主要服务图片、PDF、视频、音频等在线预览。
- `storage-download`：下载一个逻辑存储对象，内部通过 `DownloadPlan` 自动决定单叶子下载或 multi refs 打包下载。

两者不得混用。`storage-stream` 不能因为遇到 multi item 就改为返回 zip；`storage-download` 也不应由前端按格式或 refs 自行拼装。

## 核心概念

### storage_ref

`storage_ref` 是 Manager 后端可打开的存储叶子内容引用：

| 引擎路径模型 | `storage_ref` 示例 | 说明 |
|---|---|---|
| 对象存储 catalog | `bucket/path/to/file.pdf` | 以 bucket 开头，后接 object key |
| 文件 catalog / NFS | `path/to/file.pdf` | 挂载根内相对路径，不包含 NFS `export_path` |

ZIP entry、Excel sheet、SQLite table 等容器内部 child 不是存储叶子内容，不应伪造 `storage_ref`。数据库 table、SQL 查询结果和计算结果也不是存储叶子，它们的完整下载属于导出语义。

### 逻辑存储对象

逻辑存储对象是用户看到并希望下载的一个完整数据对象。它可能是一个存储叶子，也可能由多个相关存储叶子组成，例如 Shapefile 的 `.shp`、`.shx`、`.dbf` 等 refs。

### DownloadPlan

`DownloadPlan` 是 Manager 后端把 `engine_id + storage_ref` 解析成的统一下载计划：

```text
DownloadPlan
  kind: stream | bundle | export
  filename
  content_type
  refs:
    - storage_ref
      role
      required
      primary
      filename
```

当前 Manager 已实现：

- `stream`：单存储叶子下载。
- `bundle`：多个相关存储叶子打包为 zip 下载。

`export` 是为数据库表、SQL 查询结果等非存储叶子完整导出预留的计划类型，后续应接 Transfer/export 任务，不与存储叶子原始下载混用。

## DownloadPlan 解析规则

所有用户触发的文件/对象原始下载都应先解析为 `DownloadPlan`，而不是在前端或 Handler 中按格式写分支。

解析流程：

1. 校验用户认证、租户隔离和引擎访问权限。
2. 将入口 `storage_ref` 解析为当前引擎的 catalog path。
3. 尝试通过 Meta 根据 `engine_id + storage_ref` 找回 item 元数据。
4. 读取 item attributes 中的通用事实，例如 `item.layout`、`item.refs`、`item.format`、`storage.physical_path`。
5. 生成 refs：
   - single item：refs 只有入口 `storage_ref`。
   - multi item：必须使用 Meta 已裁决的 `item.refs`。
   - multi item 缺失 refs、缺少唯一 primary 或 required refs 不完整时，应返回明确错误并提示重新扫描，不在 Manager 下载链路中重新猜测 sibling content。
6. 校验 refs 都属于当前引擎下的合法存储叶子；required ref 不可打开时失败，optional ref 可跳过。
7. 决定执行形态：
   - refs 数量为 1：`stream`。
   - refs 数量大于 1：`bundle`。
   - 没有 storage leaf：`export`。

前端不应从 `content.metadata.refs` 拼下载 URL，也不应理解 Shapefile 等格式的组成规则。

## storage-stream

`storage-stream` 使用同一个 HTTP API 支持两种读取模式，且永远只读取一个存储叶子：

- 不带 `Range` header：返回完整内容，HTTP 状态码为 `200 OK`。
- 带 `Range: bytes=start-end`：返回指定字节范围，HTTP 状态码为 `206 Partial Content`。

Manager 后端负责：

- 用户认证、租户隔离、引擎权限校验。
- 将 `storage_ref` 转换为插件层 `CatalogPath`。
- 调用插件 `OpenContent` 或 `OpenRange`。
- 设置 `Content-Type`、`Content-Length`、`Content-Disposition`、`Accept-Ranges`、`Content-Range` 等响应头。
- 以流式方式把真实存储内容写回浏览器。

`storage-stream` 的稳定职责是单叶子流式读取，不负责 multi item 自动打包。

## storage-download

`storage-download` 是用户点击“原始下载”时的默认入口，语义是下载一个逻辑存储对象。

```text
GET /storage-download?engine_id=...&storage_ref=...
  -> Resolve DownloadPlan
  -> stream: 返回原文件流
  -> bundle: zip.NewWriter 流式写入 refs
  -> export: 返回明确的导出任务语义，后续交由 Transfer/export
```

`storage-download` 可以根据 `DownloadPlan` 返回原文件流或 zip 包。这个行为是透明且符合语义的，因为它下载的是逻辑对象，而不是固定的单个存储叶子。

multi item 默认下载 zip 包，而不是一次点击触发多个浏览器下载。原因：

- 浏览器对多文件下载限制多，体验不稳定。
- multi item 是一个逻辑对象，zip 更符合完整交付语义。
- 后端可以统一控制 entry 文件名、required/optional ref 校验、缺失错误和流式写出。

用户查看 multi item 中的某个单独 ref 时，仍可通过该 ref 的 `storage_ref` 走单叶子下载。

## 前端下载原则

右上角“原始下载”不应使用 axios `responseType: blob` 拉完整文件。这样会把大文件完整放入浏览器 JS 内存，并受 axios timeout 影响。

前端应：

- 对 Manager 返回的 `storage-download` URL 创建原生 `<a>` 下载链接。
- 将认证 token 追加到 query 参数中，由后端认证中间件转换为 `Authorization`。
- 让浏览器直接从 ADDP 后端流式下载，JS 不持有完整文件内容。
- 不根据 `format`、`preview_material`、`frontend_renderer` 判断原始下载能力。
- 不解释 multi refs，也不拼 zip。

表格预览导出、文本导出、base64 小内容导出仍可以使用 Blob，因为这些内容本身来自前端已持有的预览材料。

数据库表当前页 CSV 导出可以作为预览材料导出保留，但它不是“原始下载”。完整数据库表下载应归入 `export`，后续交由 Transfer/export 任务生成文件，再返回新的 `storage_ref` 下载。

## 存储引擎差异

MinIO / S3：

- 插件通过对象存储 SDK 的 `GetObject` 读取内容。
- Range 请求可通过 SDK 的 range options 下推到对象存储。
- 即使底层支持 presigned URL，默认仍应走 ADDP 后端代理流。

NFS：

- 插件通过 NFS client 打开文件。
- Range 请求通过 `Seek` 到偏移位置，再限制读取长度实现。
- NFS 没有天然浏览器可访问的 HTTP 下载 URL，因此必须走 ADDP 后端代理流。

## external_url

`external_url` 是未来可选的插件优化能力，例如 MinIO/S3 presigned URL。它不是默认契约，也不能替代 `storage-stream` / `storage-download`。

`external_url` 只能作为性能优化使用，前提是网络、权限、审计和租户隔离策略都明确满足要求。NFS、数据库表、multi item 等场景通常无法用一个外部 URL 表达完整下载语义。

## 责任边界

- `common/format`：声明格式能力和 related refs 规范，例如 `RelatedRefSpecs()`；不组装 Manager 下载 DTO，不访问具体引擎。
- `meta`：保存 item 的 layout、format、refs、storage physical path 等事实。
- `manager/service`：把 `engine_id + storage_ref` 解析成 `DownloadPlan`，并执行 stream / bundle。
- `manager/api`：暴露 `storage-stream` 和 `storage-download`，维护 HTTP 语义和响应头。
- `manager/frontend`：打开后端下载 URL；只在没有 storage leaf 的预览材料上做显式“导出当前页/导出预览内容”。

## 禁止事项

- 不得把 multi item 的完整下载逻辑放到前端。
- 不得让前端从 `content.metadata.refs` 拼接下载 URL。
- 不得把 `storage-stream` 改造成有时返回单文件、有时返回 zip 的混合语义。
- 不得仅因 table preview 就把原始下载降级成当前页 CSV。
- 不得用 unknown binary reader 代替原始下载链路。
- 不得为某个格式在下载 Handler 中写特殊分支；格式差异应收敛到 Meta 已入库的 item refs 和 `DownloadPlan` 的统一消费。
