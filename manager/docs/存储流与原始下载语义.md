## 背景

浏览器不能假设可以直接访问真实数据存储引擎。MinIO、S3、NFS、NAS、HDFS 等存储可能位于内网、容器网络或只允许后端服务访问。因此 Manager 暴露给前端的预览流和原始下载入口必须以 ADDP 后端代理为稳定契约，而不是以真实存储 URL 为默认契约。

Manager 将存储内容访问拆成两个不同 HTTP 语义：

- `storage-stream`：在一个已校验 DataItem 范围内读取一个存储叶子内容，支持 HTTP Range，主要服务图片、PDF、视频、音频等在线预览。
- `downloads/file`：按 ResourceLocator 下载一个逻辑存储对象，内部通过 `DownloadPlan` 决定单叶子、multi refs 或已支持的 whole 目录打包下载。

两者不得混用。`storage-stream` 不能因为遇到 multi item 就改为返回 zip；`downloads/file` 也不应由前端按格式或 refs 自行拼装。

## 核心概念

### storage_ref

`storage_ref` 是 Manager 后端可打开的存储叶子内容引用：

| 引擎路径模型 | `storage_ref` 示例 | 说明 |
|---|---|---|
| 对象存储 catalog | `bucket/path/to/file.pdf` | 以 bucket 开头，后接 object key |
| 文件 catalog / NFS | `path/to/file.pdf` | 挂载根内相对路径，不包含 NFS `export_path` |

ZIP entry、Excel sheet、SQLite table 等容器内部 child 不是存储叶子内容，不应伪造 `storage_ref`。数据库 table、SQL 查询结果和计算结果也不是存储叶子，它们的完整下载属于导出语义。

### 逻辑存储对象

逻辑存储对象是用户看到并希望下载的一个完整数据对象。它可能是一个存储叶子，也可能由多个相关存储叶子组成，例如 Shapefile 的 `.shp`、`.shx`、`.dbf` 等 refs。

### DownloadPlan

`DownloadPlan` 是 Manager 后端把存储型 item 的 ResourceLocator 解析成的统一下载计划：

```text
DownloadPlan
  kind: stream | bundle
  filename
  content_type
  refs:
    - storage_ref
      role
      required
      primary
      filename
  directory_root: EngineCatalogPath (仅目录型 bundle)
```

当前 Manager 已实现：

- `stream`：单存储叶子下载。
- `bundle`：多个相关存储叶子打包为 zip 下载。

目录型 `bundle` 的 NFS FileGDB 准入、整项授权、完整 ZIP、源变化检测与临时包清理统一见[FileGDB 下载契约](#filegdb-原始内容的源授权)。

数据库表和动态 schema collection 等非存储叶子的完整导出走 Manager `exports`，内部调用 Transfer sync，不进入存储 item 原始下载链路。表使用 table Transfer；collection 原始记录导出使用引擎声明的 encoded record read session，不能先经过预览值归一化或 table pipeline。

## DownloadPlan 解析规则

所有用户触发的文件/对象原始下载都应先解析为 `DownloadPlan`，而不是在前端或 Handler 中按格式写分支。

### 下载能力声明

动作分类、`resource-actions` API 与按钮显示规则统一见[资源动作能力](数据预览与资源树实现规范.md#4-资源动作能力)；预览材料与下载能力的区别见[预览语义协议](数据预览语义协议.md#与存储下载的关系)。本节维护 `download` 专有的计划准入与身份声明。

Manager 的 `resource-actions.download` 必须复用实际下载计划的准入规则。缺失或矛盾的 Meta 身份、缺失 multi refs、尚未支持的 whole 类型不能仅因引擎具有 ContentRead 就宣布可下载；上游故障不能转换为允许。需要当前 User 的原始下载通过 `requires_current_user` 明确声明，前端不再按格式自行推断认证方式。

能力查询只解析 Meta 身份与下载计划，不枚举或读取源内容；动作支持或要求当前 User 均不授予数据读取许可。页面与内容 Permission 的区别见[预览规范的权限边界](数据预览与资源树实现规范.md#一定位)，实际原始读取仍执行[内容入口身份与保护](#内容入口身份与保护)及各类源授权。

NFS 原始内容动作还要求该 DataItem 的格式已接入正式源读取授权。下载能力与内容入口共用这一准入规则；格式尚未接入时，`resource-actions.download.supported` 为 `false`，页面不显示下载按钮。

声明后的交付选择、完整接收与失败取消见[前端下载原则](#前端下载原则)；完整交付、临时资源清理及固定版本证据分别沿[验收边界](#验证入口与验收边界)核对，不以能力查询成功替代。

### 计划解析流程

解析流程：

1. 校验用户认证、租户隔离和引擎访问权限。
2. 解析入口 ResourceLocator，确认它指向存储型 engine 的 item。
3. 尝试通过 Meta 根据 ResourceLocator 找回 item 元数据。
4. 读取 item attributes 中的通用事实，例如 `item.layout`、`item.refs`、`item.format`、`storage.physical_path`。
5. 生成源范围：
   - single item：refs 只有入口 `storage_ref`。
   - multi item：必须使用 Meta 已裁决的 `item.refs`。
   - multi item 缺失 refs、缺少唯一 primary 或 required refs 不完整时，应返回明确错误并提示重新扫描，不在 Manager 下载链路中重新猜测 sibling content。
   - 已支持的 whole item：以已确认根生成 `directory_root`，不伪造静态 refs。
6. 校验 refs 都属于当前引擎下的合法存储叶子；required ref 不可打开时失败，optional ref 可跳过。
7. 决定执行形态：
   - refs 数量为 1：`stream`。
   - refs 数量大于 1：`bundle`。
   - `directory_root` 非空：目录型 `bundle`。

前端不应从 `content.metadata.refs` 拼下载 URL，也不应理解 Shapefile 等格式的组成规则。

## 内容入口身份与保护

`storage-stream` 与 `downloads/file` 读取原始内容前，共用以下身份与保护要求：

- 用户认证、租户隔离、引擎权限校验。
- 强制要求带 `item_id` 的 DataItem `locator`，按 ID 从 Meta 重新读取 item，不信任调用方提供的 fingerprint。
- 以 Meta `engine_id + full_name` 重算 DataItem fingerprint，查询 Manager 本地 Security 投影。当前原始字节流无字段级执行器，命中纳管目标时失效关闭；未纳管目标继续原路径。
- NFS 的原始下载、单叶子流和路径型资源流只开放已接入源读取授权的模型、ENVI 和 FileGDB，沿各自的边界执行当前源权限裁决。普通 CSV 等未接入格式在任何源存储探测或读取前返回 HTTP 403。元数据查看与原始内容读取分别执行各自的准入。

`downloads/file` 的 Meta 身份校验与 fingerprint 重算在解析 `DownloadPlan` 前完成；返回原始字节或 refs 原始字节包时，不能套用结构化 `preview` 的保护规则。FileGDB 与模型的当前 User、精确组成和逐次读取核验，分别见[FileGDB 源授权](#filegdb-原始内容的源授权)、[模型身份与权限](#模型身份与权限)。

## storage-stream

`storage-stream` 使用同一个 HTTP API 支持两种读取模式，且永远只读取一个存储叶子：

- 不带 `Range` header：返回完整内容，HTTP 状态码为 `200 OK`。
- 带 `Range: bytes=start-end`：返回指定字节范围，HTTP 状态码为 `206 Partial Content`。

身份与保护统一见[共用要求](#内容入口身份与保护)；该入口另负责：

- 校验 `storage_ref` 归属于该 item：`single` 精确匹配主内容，`multi` 精确匹配已扫描 refs，`whole` 必须位于该 scope 的路径边界内。
- 将 `storage_ref` 转换为插件层 `EngineCatalogPath`。
- 调用插件 `OpenContent` 或 `OpenRange`。
- 设置 `Content-Type`、`Content-Length`、`Content-Disposition`、`Accept-Ranges`、`Content-Range` 等响应头。
- 以流式方式把真实存储内容写回浏览器。

`storage-stream` 的稳定职责是单叶子流式读取，不负责 multi item 自动打包。

S3M 等 manifest 会以相对 URL 继续请求子资源，使用独立的路径型入口 `/storage-assets/{engine_id}/items/{item_id}/{storage_ref}`。`item_id` 必须位于路径中，使每个相对子资源请求都保留同一 DataItem 身份。该入口与 `storage-stream` 使用同一 Meta 归属校验和 Security 本地门禁，无主身份的旧路径不保留。

## downloads/file

`downloads/file` 是用户点击存储型 item“下载”时的默认入口，语义是下载一个逻辑存储对象。

当前下载不引入 download session；如后续需要下载审计、大文件准备、一次性 token 或断点续取，再设计独立 session。导入来源、导出会话与跨动作后续事项统一见[预览规范的导入和导出职责](数据预览与资源树实现规范.md#4-与导入和导出)，不与原始下载共用会话语义。

```text
GET /downloads/file?locator=...
  -> Resolve DownloadPlan
  -> stream: 返回原文件流
  -> bundle: zip.NewWriter 流式写入 refs
```

该入口的身份、fingerprint 与原始内容保护统一见[内容入口身份与保护](#内容入口身份与保护)；不因返回 ZIP 就改变同一 DataItem 的授权边界。

本节导航：[名称与相对目录](#multi-refs-zip-名称与相对目录) · [组成预检](#multi-refs-zip-组成校验与拒绝) · [交付与失败](#multi-refs-zip-交付与失败边界)。

### multi refs ZIP 名称与相对目录

多文件 ZIP 以已确认 refs 的共同父目录为根，逐段保留原始相对目录和文件名；不裁剪空白、不改变大小写、不解码百分号，也不将同名文件摊平或自动添加后缀。例如 `models/obj/red/color.png` 与 `models/obj/blue/color.png` 分别写为 `red/color.png` 与 `blue/color.png`，保持模型的相对引用可用。同目录 Shapefile 的组成仍位于 ZIP 根。

归档名称只由当前下载计划中的 refs 计算，不发现或补读其他文件。缺失 optional ref 可按既有规则跳过，但 ZIP 根仍由完整已确认清单计算，不因缺失改变其他成员位置。

### multi refs ZIP 组成校验与拒绝

打开任何 ref 前，拒绝非 UTF-8、绝对路径、驱动器路径、反斜杠、NUL、空路径段、`.`／`..` 段、重复成员及文件／目录前缀冲突；校验原始 Meta refs 时不得先去重或清理非法路径。非法组成返回 HTTP 400、稳定 `error_code=download_bundle_invalid` 和中英文消息，不返回部分 ZIP。此规则统一适用于文件和对象引擎，不按具体数据格式分支。

### multi refs ZIP 交付与失败边界

multi item 默认下载 zip 包，按逻辑对象完整交付；不以一次点击触发多个浏览器下载，避免浏览器的多文件下载限制。后端统一控制 entry 文件名、required/optional ref 校验、缺失错误和流式写出。

用户查看 multi item 中的某个单独 ref 时，仍可通过该 ref 的 `storage_ref` 走单叶子下载。对应内容入口仍沿 [storage-stream](#storage-stream)，不把单叶子读取改为自动打包。

上述 HTTP 400 与不返回部分 ZIP 的约束针对组成预检；成员打开、读取或传输失败另按实际 I/O 结果认定，不能仅凭 HTTP 成功就认定完整包已交付。multi refs 流式写出、成员关闭和错误传播见[下载实现](../backend/internal/service/metadata_service.go)，前端认证、完整接收和失败／取消行为见[前端下载原则](#前端下载原则)。目录型 FileGDB 的临时包机制单独沿[目录清理](#filegdb-临时包与清理)，不作为 multi refs 流式交付的清理证明。

原名、完整成员与字节、失败和清理分别按[验证入口与验收边界](#验证入口与验收边界)核对；工具断言、受控页面与隔离真实链路各自认定，不以 ZIP 已开始生成或成功响应替代完整交付验收。

## 前端下载原则

本节导航：[交付选择与完整接收](#前端交付选择与完整接收) · [失败与取消](#前端下载失败与取消) · [清理与验收](#前端下载清理与验收) · [与导出的边界](#与导出的边界)。源读取权限统一见[内容入口身份与保护](#内容入口身份与保护)，FileGDB 与模型的独有要求分别见[整项授权](#filegdb-整项授权与读取)、[模型身份与权限](#模型身份与权限)。

### 前端交付选择与完整接收

前端按服务端 `resource-actions.download` 声明选择交付方式，不根据 `format`、`preview_material`、`frontend_renderer` 判断原始下载能力，不解释 multi refs，也不拼 zip：

- `requires_current_user=true` 的模型源和 NFS FileGDB 使用当前账号认证 fetch；[源下载工具](../frontend/src/utils/storageSource.js)只接受同源 `downloads/file` 且仅含一个 `locator` 的地址，不携带 Cookie、不跟随重定向、不使用缓存。响应必须为 HTTP 200、具有合法服务端附件原名，并完整读成非空 Blob 后才调用保存。首期接受完整文件占用浏览器资源的代价，不宣称原生流式保存。
- 其余已支持的原始下载沿现有后端交付 URL 创建原生 `<a>` 下载链接；认证由现有资源访问契约处理，不向 URL 追加账号凭据。这条路径交给浏览器接收，页面触发链接不能证明文件已完整交付。

附件名的编码、保真分层与浏览器建议名差异统一见[原名与字节保真](#模型原名与字节保真)。前端完整读入响应不等于独立验证源字节或 ZIP 结构；源下载工具未另做 ZIP 解析或源摘要比对。服务端完整包要求分别见[multi refs ZIP](#multi-refs-zip-交付与失败边界)、[FileGDB ZIP](#filegdb-完整-zip-交付)，页面“下载已开始”只表示已触发浏览器保存，不能证明落盘完成。

### 前端下载失败与取消

[下载按钮](../frontend/src/components/explorer/PreviewPanel.vue)在请求忙碌时不重复发起；认证 fetch 最终遇到认证／授权拒绝、非 200、附件名无效、读取中断或空响应均不调用保存，也不显示成功。失败显示错误提示，401／403 不重复记录下载失败控制台错误，其余失败保留错误日志；认证层的 401 刷新与再请求归[共享认证实现](../../common-frontend/basic/src/composables/useAuth.js)，不以单次点击推断仅有一次 HTTP 请求。失败不改走裸链接或资源票据。

资源 locator 切换或组件卸载时取消在途认证下载、复位忙碌状态；完整读取后、保存前再次检查取消信号，取消不保存文件，也不显示失败或成功提示。此范围不包含撤销已经交给浏览器的原生下载，也不承诺回收用户已保存的文件。

### 前端下载清理与验收

浏览器对象 URL 的创建、触发后临时链接移除与延迟释放统一由[共享下载工具](../../common-frontend/basic/src/utils/exportSession.js)负责；延迟释放不是浏览器落盘完成回执。请求取消与浏览器对象 URL 释放不替代服务端读取器、临时 ZIP 的清理证明，分别见[multi refs 交付](#multi-refs-zip-交付与失败边界)、[FileGDB 临时包与清理](#filegdb-临时包与清理)。

工具断言、受控页面与真实链路沿[验证入口与验收边界](#验证入口与验收边界)分别记录；现有页面夹具不能证明真实上游中断、源授权或服务器临时资源已回收，未运行或未覆盖项不计通过。

### 与导出的边界

预览材料不提供下载旁路。第一阶段不支持数据库表当前页预览下载；完整数据库表导出归入 `exports`，由 Manager 调用 Transfer sync 生成 infra 临时文件，再通过 Resource Ticket 保护的 export session 文件接口直接流式交付，前端不得把完整导出文件读入 Blob。

MongoDB collection 第一阶段只提供“原始记录格式导出”：格式固定为 `mongodb_extended_jsonl`，内容为 Canonical Extended JSON v2、UTF-8、每行一个紧凑文档，扩展名为 `.ejsonl`。它保持 BSON 类型交换语义，但不是 `mongodump` BSON archive 或物理备份；“原始记录格式”不表示绕过 Security，已纳管 collection 必须先执行 Transfer `export` 投影，再编码 EJSON，不能导出未经保护的原值。表格化导出必须显式选择记录粒度；基础单表模式最多展开一个数组，多数组不得自动生成笛卡尔积。

## 存储引擎差异

MinIO / S3：

- 插件通过对象存储 SDK 的 `GetObject` 读取内容。
- Range 请求可通过 SDK 的 range options 下推到对象存储。
- 即使底层支持 presigned URL，默认仍应走 ADDP 后端代理流。

NFS：

- 插件通过 NFS client 打开文件。
- Range 请求通过 `Seek` 到偏移位置，再限制读取长度实现。
- NFS 没有天然浏览器可访问的 HTTP 下载 URL，因此必须走 ADDP 后端代理流。

## external_url

`external_url` 是未来可选的插件优化能力，例如 MinIO/S3 presigned URL。它不是默认契约，也不能替代 `storage-stream` / `downloads/file`。

`external_url` 只能作为性能优化使用，前提是网络、权限、审计和租户隔离策略都明确满足要求。NFS、数据库表、multi item 等场景通常无法用一个外部 URL 表达完整下载语义。

## 责任边界

- `common/format`：声明格式能力和 related refs 规范，例如 `RelatedRefSpecs()`；不组装 Manager 下载 DTO，不访问具体引擎。
- `meta`：保存 item 的 layout、format、refs、storage physical path 等事实。
- `manager/service`：把存储型 item ResourceLocator 解析成 `DownloadPlan`，并执行 stream / bundle。
- `manager/api`：暴露 `storage-stream` 和 `downloads/file`，维护 HTTP 语义和响应头。
- `common/exportartifact`：统一导出会话、Transfer 状态回查、infra artifact manifest、用户隔离和到期清理。
- `common-frontend`：统一导出弹窗、状态轮询和浏览器直接下载交互。
- `manager/frontend`：组合共享导出能力；存储型 item 显示下载动作，数据库 table / collection item 显示各自能力声明允许的导出动作。

## 禁止事项

- 不得把 multi item 的完整下载逻辑放到前端。
- 不得让前端从 `content.metadata.refs` 拼接下载 URL。
- 不得把 `storage-stream` 改造成有时返回单文件、有时返回 zip 的混合语义。
- 不得仅因 table preview 就把原始下载降级成当前页 CSV。
- 不得用 unknown binary reader 代替原始下载链路。
- 不得为某个格式在下载 Handler 中写特殊分支；格式差异应收敛到 Meta 已入库的 item refs 和 `DownloadPlan` 的统一消费。

## FileGDB 原始内容的源授权

本节导航：[目录准入](#filegdb-目录下载准入) · [整项授权](#filegdb-整项授权与读取) · [ZIP 交付](#filegdb-完整-zip-交付) · [源变化](#filegdb-源变化检测) · [临时包清理](#filegdb-临时包与清理)。支持范围与真实结果分别认定，入口与适配缺口见[验证与验收边界](#验证入口与验收边界)。

### FileGDB 目录下载准入

目录型 `bundle` 只准入已由 Meta 基础识别的 NFS FileGDB `whole` DataItem。下载计划使用精确的 `directory_root`，与静态 `refs` 互斥；不把目录伪装成单文件，不开放普通目录或其他 whole 格式。

目录能力查询只判定准入；解析范围及与实际读取授权的区别统一见[下载能力声明](#下载能力声明)。

### FileGDB 整项授权与读取

NFS FileGDB 的原始成员内容要求当前普通 User Bearer：在源 Facts 和每次 Open 前，使用既有 System `manager-preview` 入口核验 `.gdb` 根 DataItem 的现行 Grant／Deny／期限。根身份取自服务端已验证的 Meta 与 locator，成员必须位于该精确根内；不按内部文件签发独立许可，也不接受相邻目录、资源票据或 Service 身份。每个 Range 请求重新判权，已放行的流不因后续撤权被追溯中断。原有 `manager.content.read`、System 读取功能权限与本地 Security 保护分别保留。

目录枚举与每个成员读取均以当前 User 重核同一根 DataItem 的整项授权，不按内部文件新增 Grant。

### FileGDB 完整 ZIP 交付

ZIP 保留 `<原名>.gdb/` 顶层及内部原名和相对目录，附件名为 `<原名>.gdb.zip`。FileGDB 完整 ZIP 沿[前端完整接收](#前端交付选择与完整接收)保存；不退回浏览器票据或匿名链接。

ZIP 的顶层目录和空子目录均保留，输出前完成 ZIP 校验所需的关闭步骤，不向浏览器交付半成品。

### FileGDB 源变化检测

服务器逐目录枚举、逐文件读取，形成请求私有临时 ZIP；完成后重新枚举，比对成员、文件大小与修改时间，检测到变化返回 `409 download_source_changed` 并提示源稳定后重试。此检查不承诺在线数据库的事务一致性备份。

### FileGDB 临时包与清理

打包完成及交付前再次核验整项授权；失败、取消或交付结束均关闭临时包，不重跑、不改变源文件或 Grant。

临时文件创建后立即解除文件名绑定，由请求持有打开的文件描述符，正常关闭或进程退出均回收存储。

## 模型原始内容的源授权

本节导航：[身份与权限](#模型身份与权限) · [组成与快照](#模型精确组成与读取快照) · [完整交付与取消](#模型完整交付与取消) · [原名与字节](#模型原名与字节保真) · [格式边界](#模型格式读取边界)。验证入口与清理范围统一见[验收边界](#验证入口与验收边界)。

### 模型身份与权限

模型的 `storage-stream`、`storage-assets` 与 `downloads/file` 使用同一请求级源读取检查；现有内容／下载功能 Permission 与 Security 保护仍分别保留，不因源 Grant 自动获得下载资格。当前普通 User Bearer 必须在源 Facts 和每个实际 Open 前，经既有 System `manager-preview` 入口同次核验当前 Engine 聚合版本、完整 Meta 文件组成及现行 Grant／Deny／期限。Resource Ticket、Service 身份、终态 EA 和仅主文件许可均不能替代。

已确认完整组成的 FTP／NFS／MinIO IFC、3DS、DAE、OBJ，以及 STL 共用该路线；其他模型的原始内容缺少完整组成投影时明确拒绝，不退回未核验流。非模型数据继续沿用既有消费策略。

### 模型精确组成与读取快照

Manager 只用当前请求已取得并经同次版本裁决的 Engine 快照取流，不在裁决后换取其他版本的连接。源包先验证全部成员恰为完整组成，再逐项重核；不能借下载计划、纹理 URL、相邻 DataItem 或目录前缀扩张读取。

历史 STL 元数据或产物若没有独立基础组成事实、正式冻结来源与执行授权，须先重新基础扫描、批准并生成，不将旧配置或源主文件许可升级为新契约。原始字节和相对名称的保真要求见[模型原名与字节保真](#模型原名与字节保真)。

### 模型完整交付与取消

模型原始下载按钮沿同一当前 User 认证 fetch 读取 `downloads/file`；完整接收、拒绝与读取失败、资源切换或离页取消及浏览器临时资源释放统一见[前端下载原则](#前端下载原则)。非模型下载仍按服务端动作声明选择交付方式，不从模型格式外推认证路线。

### 模型原名与字节保真

附件名称按 RFC 6266／5987 编码和解析，中文名称使用 UTF-8 扩展参数；保留合法首尾空格及 ZIP 后缀，不依据页面标签改名。

原名保真分层验收：源路径、`Content-Disposition` 解码后的附件名称、前端传给 HTML `download` 属性的名称，以及 ZIP 内的相对目录和成员名必须逐字保持原样；返回的单文件字节或 ZIP 内成员字节必须与对应源文件完全一致。浏览器建议保存名是接收端的独立观察，不能反过来修改源名称、响应头、页面下载属性或 ZIP 成员。浏览器可以基于本地文件系统规则调整建议名，见 [RFC 6266 §4.3](https://www.rfc-editor.org/rfc/rfc6266#section-4.3)；固定 Chromium 首空格样例的原名为 ` 原名 %.GLB`，页面仍传原名，浏览器建议为 `_原名 %.GLB`，须分别记录并严格核对。单文件仍直接下载裸源，不为通过命名断言更换样例、改写文件或另加 ZIP 路线。

### 模型格式读取边界

按格式阅读：[STL](#stl-预览与快显输入) · [GLB](#glb-自包含读取) · [FBX](#fbx-固定-profile-读取)。

#### STL 预览与快显输入

STL 基础预览通过当前身份请求取得字节后交给既有解析器，不再用无当前身份的直接 URL 加载。

STL 快显首期输入准备上限为 64 MiB，完整缓冲并调用与 basic 相同的结构验证后，只暂存这次验证的同一份字节；超限或验证失败在上传／调用 Runtime 前拒绝。基础组成识别与原始流读取不据此伪造几何或材质，deep 的采样完成状态不影响已提交的结构完整性。

#### GLB 自包含读取

自包含 GLB 在 FTP／NFS／MinIO 使用同一精确组成源授权，只直接预览与原文件下载，不创建转换任务。Meta 必须已有完整单主项组成；每次实际请求仍完整缓冲最多 64 MiB，并使用格式层 Provider 对这份字节重新验证自包含边界，防止同名源内容在扫描后改变。源 Facts 超限、读取超限、结构或组成无效时不交付任何字节。验证通过后再次核验现行源权限，再从该缓冲返回 full／Range／原始下载；不重新打开另一份源流。文件名和字节保持原样，JSON 预算为 16 MiB。无外部 URI、data URI 或扩展的 GLB 2.0 才准入，格式完整性与浏览器实际渲染分别验收。

#### FBX 固定 profile 读取

FBX 在 FTP／NFS／MinIO 的精确组成路线仅接入 Binary 7400 静态无贴图 profile。Meta 必须同时具有 `composition_complete=true`、固定 `profile=binary7400_static_untextured` 与唯一主 `model` ref。源 Facts、原始 full／Range／下载及转换准备均不取得父目录许可；原始出口完整缓冲不超过 64 MiB 的同一次主文件字节，以同一格式 Provider 复核后再次核权，再交付缓冲或暂存。相同路径和相同大小不能豁免实际结构校验。转换使用 `file/fbx` 访问计划，替代原父目录源；旧产物缺少冻结组成则须重新生成。SKP 尚未通过严格组成读取准入，不因 FBX 开放而获得精确组成授权。格式校验、前端解析及三来源运行证据分别认定。
