# ADDP 湖仓一体化设计方案

> 状态：讨论确认  
> 日期：2026-04-17（更新：补充双模式识别策略）  
> 范围：Meta、Develop、Manager、Transfer、common 模块

---

## 一、背景与目标

### 1.1 背景

ADDP 作为全域数据平台，需要支持用户根据不同需求自由组合数据流。当前平台对对象存储（MinIO/S3）的理解停留在"文件/对象"层面，无法将 MinIO 上的 Parquet 文件作为结构化表来查询和管理。

湖仓一体化的目标是：**让 ADDP 能够理解、管理和查询存储在对象存储上的结构化数据（湖表）**，与现有关系型数据库、NoSQL 等引擎统一纳入平台管理体系。

### 1.2 第一阶段目标

- 将 MinIO/S3 上的 Parquet 文件目录识别为逻辑表（lake_table）
- 在 Meta 模块中统一管理湖表元数据（Schema、统计信息）
- 在 Develop 模块的 SQL 工作台中支持湖表查询（内置 DuckDB）
- 在 Manager 模块中支持湖表数据预览

### 1.3 暂不引入

- Apache Iceberg / Delta Lake / Apache Hudi 等开放表格式（按需引入）
- Trino 联邦查询引擎（作为标准引擎注册，后续引入）
- Iceberg REST Catalog（后续按需引入）

## 二、核心架构决策

### 2.1 双模式识别策略（Convention over Configuration）

ADDP 兼容业界两种主流的 Parquet 使用范式，扫描时按优先级依次判断：

**模式 A：目录即表（Directory-as-Table）**

这是 Apache Hive、Spark、Iceberg、Delta Lake 的标准范式，适合大数据分布式写入场景：

```
s3://bucket/warehouse/orders/
  ├── part-0001.parquet
  ├── part-0002.parquet   →  逻辑表：warehouse.orders
  └── part-0003.parquet
```

识别条件：一个目录下的**直接子文件全部为 Parquet/ORC/Avro**（无子目录）→ 整个目录识别为一个 lake_table，内部文件是实现细节，不对外暴露。

**模式 B：文件即表（File-as-Table）**

这是 DuckDB、Pandas、数据分析师的日常用法，适合数据导出、临时分析、文件交换场景：

```
s3://bucket/exports/
  ├── orders_2024.parquet    →  逻辑表：orders_2024
  ├── customers.parquet      →  逻辑表：customers
  └── products.parquet       →  逻辑表：products
```

识别条件：目录下存在 `.parquet/.orc/.avro` 文件，但**不满足模式 A**（如目录下有混合文件类型，或文件直接在 bucket 根目录）→ 每个结构化文件单独识别为一个 lake_table。

**完整识别规则（按优先级）**：

| 场景 | 识别方式 | item_type | 说明 |
|------|---------|-----------|------|
| 目录下全是 .parquet/.orc/.avro（无子目录） | 目录 → 1 个 lake_table | lake_table | 模式 A，优先 |
| 目录下有 .shp 文件 | 目录 → 1 个 shapefile | shapefile | ShapefileDetector |
| 目录下混合文件（parquet + 其他） | 每个 .parquet 文件 → lake_table | lake_table | 模式 B |
| bucket 根目录下的 .parquet 文件 | 每个文件 → lake_table | lake_table | 模式 B，Transfer 导出场景 |
| 其他文件 | 文件 → object | object | 不变 |

**Transfer 模块无需强制 prefix**：Transfer 将 Parquet 写到 bucket 根目录是合法的，Meta 扫描会将其识别为模式 B 的 lake_table。用户也可以指定 prefix 组织目录结构，Meta 会自动识别为模式 A。

- 不处理嵌套分区目录（第一阶段简化，Iceberg/Hudi 分区留待第三阶段）

### 2.2 lake_table 是 MetaItem

lake_table 在 Meta 模型中表示为 **MetaItem**（而非 MetaNode），两种模式的存储结构如下：

**模式 A（目录即表）**：

```
MetaNode(type=bucket, name="manager")
  └── MetaNode(type=prefix, name="warehouse")
        └── MetaItem(item_type="lake_table", name="orders")
              path            = "warehouse/orders/"
              Attributes = {
                "format":        "parquet",
                "mode":          "directory",   ← 标记为目录模式
                "fields":        [...],
                "file_count":    3,
                "physical_path": "warehouse/orders/"
              }
```

**模式 B（文件即表）**：

```
MetaNode(type=bucket, name="manager")
  └── MetaItem(item_type="lake_table", name="test")
        path            = "test.parquet"
        Attributes = {
          "format":        "parquet",
          "mode":          "file",              ← 标记为文件模式
          "fields":        [...],
          "file_count":    1,
          "physical_path": "test.parquet"
        }
```

**与关系型表保持一致**：

| | 关系型表 | 湖表 |
|---|---|---|
| 结构节点 | MetaNode(type=schema) | MetaNode(type=prefix) |
| 数据项 | MetaItem(item_type="table") | MetaItem(item_type="lake_table") |
| Schema 存储 | Attributes.fields | Attributes.fields（相同） |

上层代码（Manager 展示列信息、Develop 自动补全）取 Schema 路径完全一致，无需区分。

### 2.3 DuckDB 内置于 Develop 模块

- DuckDB 是嵌入式引擎（CGO），**只在 Develop 模块中嵌入**，其他模块不引入 CGO 依赖
- Meta 模块使用 `parquet-go`（纯 Go）推断 Schema，不依赖 DuckDB
- Manager 模块使用 `parquet-go` 做简单行预览，不依赖 Develop 模块
- DuckDB 在 System 中**自动注册为内置引擎**（类似 Python Workflow），用户可见但无需手动注册

### 2.4 DuckDB 动态获取存储引擎凭证

DuckDB 查询时**动态获取**当前租户下所有可用的对象存储引擎，无需在注册时静态关联：

```
查询请求到达 Develop
  → SystemClient.GetEnginesByType(tenantID, ["minio", "s3"])
  → 为每个引擎配置 DuckDB httpfs 凭证
  → 按引擎名挂载命名空间：engine_name.bucket.table
  → 执行 SQL
```

### 2.5 SQL 改写方案（方案 Q）

不预注册虚拟视图，而是在执行前做 SQL 改写：

```
用户写：SELECT * FROM my_minio.warehouse.orders WHERE ...

Develop 改写：
  1. 解析 SQL，识别表引用 my_minio.warehouse.orders
  2. 查 Meta 获取 orders 的 physical_path
  3. 替换为：SELECT * FROM read_parquet('s3://my-bucket/warehouse/orders/*.parquet') WHERE ...
  4. 执行改写后的 SQL
```

优点：无连接池失效问题，新增湖表后立即可查，实时感知。

## 三、新增抽象层设计

### 3.1 FileSystemPlugin 接口

在现有插件体系中，抽出 `FileSystemPlugin` 作为所有文件系统语义存储的统一接口：

```
StoragePlugin（现有）
  ├── RelationalDBPlugin（现有，不变）
  ├── NoSQLPlugin（现有，不变）
  └── FileSystemPlugin（新增）← 所有基于文件系统语义的存储
        ├── ObjectStoragePlugin（改为继承 FileSystemPlugin）
        │     ├── MinIO 插件
        │     └── S3 插件
        ├── NASPlugin（未来）
        └── HDFSPlugin（未来）
```

**接口定义**（`common/engine/plugin/filesystem.go`）：

```go
type FileSystemPlugin interface {
    StoragePlugin

    // 列出路径下的直接子内容（非递归）
    ListDirectory(ctx context.Context, connInfo map[string]string,
                  path string) (files []FileEntry, subdirs []DirEntry, error)

    // 流式读取文件内容（调用方负责关闭）
    ReadFile(ctx context.Context, connInfo map[string]string,
             path string) (io.ReadCloser, error)

    // 获取文件元数据
    GetFileMetadata(ctx context.Context, connInfo map[string]string,
                    path string) (*FileMetadata, error)

    // 列出根节点（对象存储=Bucket，NAS=挂载点，HDFS=根目录）
    ListRoots(ctx context.Context, connInfo map[string]string) ([]RootEntry, error)
}

type FileEntry struct {
    Name        string
    Path        string    // 完整路径，供 ReadFile 使用
    Size        int64
    ModifiedAt  time.Time
    ContentType string
}

type DirEntry struct {
    Name string
    Path string
}
```

`ObjectStoragePlugin` 改为继承 `FileSystemPlugin`，原有方法保留：

```go
type ObjectStoragePlugin interface {
    FileSystemPlugin          // 继承统一文件系统接口

    ListBuckets(ctx, connInfo) ([]BucketInfo, error)  // 对象存储特有
    DefaultBucket() string
    SupportsSSL() bool
}
```

MinIO 插件的 `ListDirectory` 实现：调用 S3 `ListObjectsV2` with `Delimiter="/"` 实现非递归列举，性能远优于递归（对 OSGB 千万文件场景尤为重要）。

### 3.2 CompositeItemDetector 接口

**核心思想**：当一个目录被识别为某种复合数据类型时，整个目录作为一个 MetaItem，内部文件不再单独扫描。

**接口定义**（`common/engine/detector/detector.go`）：

```go
type CompositeItemDetector interface {
    // 根据目录内容判断是否匹配（不需要读文件内容）
    Detect(ctx context.Context, files []FileEntry, subdirs []DirEntry) bool

    // 匹配后提取元信息（需要读内容时通过 plugin 读取）
    ExtractItemInfo(ctx context.Context, plugin FileSystemPlugin,
                    connInfo map[string]string, dirPath string,
                    files []FileEntry) (*CompositeItemInfo, error)

    Priority() int    // 优先级，越大越先检测
    ItemType() string // 对应 MetaItem.item_type
}

type CompositeItemInfo struct {
    Fields     []format.FieldInfo     // 列定义，复用现有 FieldInfo
    Attributes map[string]interface{} // 其他扩展属性
}
```

**注册机制：全局注册 + `init()` 自动注册**

检测器与存储后端无关（只关心文件名模式），采用全局注册：

```go
// common/engine/detector/registry.go
func Register(d CompositeItemDetector) { ... }  // 注册
func GetAll() []CompositeItemDetector  { ... }  // 按优先级排序返回
```

各检测器在自己包的 `init()` 中注册（与 Go 数据库驱动注册模式一致）：

```go
// common/format/parquet/detector.go
func init() { detector.Register(&LakeTableDetector{}) }
```

调用方通过 `import _ "common/format/parquet"` 激活检测器。

**内置检测器**：

| 检测器 | 优先级 | 检测条件 | item_type | 模式 |
|---|---|---|---|---|
| ShapefileDetector | 90 | 存在 .shp 文件 | shapefile | 目录 |
| LakeTableDetector | 80 | 直接子文件全是 .parquet/.orc/.avro（无子目录） | lake_table | 模式 A |
| OSGBDetector | 70 | 存在 .osgb 文件 | osgb_model | 目录（未来） |

**模式 B 的识别不走 CompositeItemDetector**，而是在 `FileSystemScanService` 的第 3 步（逐文件处理）中直接判断扩展名：`.parquet/.orc/.avro` → `item_type="lake_table"`，其余 → `item_type="object"`。

### 3.3 FileSystemScanService

Meta 模块新增 `FileSystemScanService`，统一处理所有 `FileSystemPlugin` 类型的存储扫描：

```
FileSystemScanService.ScanPath(plugin, connInfo, path)
  │
  ├── 1. plugin.ListDirectory(path) → files + subdirs
  │
  ├── 2. 运行 CompositeItemDetector 链（目录级检测，模式 A）
  │     for _, d := range detector.GetAll():
  │       if d.Detect(files, subdirs):
  │         info = d.ExtractItemInfo(plugin, connInfo, path, files)
  │         → 建 MetaItem(item_type=d.ItemType(), attributes=info)
  │         → return（停止递归，目录内文件不再单独建 item）
  │
  ├── 3. 无检测器匹配：逐文件处理（模式 B + 普通文件）
  │     for file in files:
  │       ext = 文件扩展名（.parquet/.orc/.avro）
  │       if isLakeTableFile(ext):
  │         → 建 MetaItem(item_type="lake_table", attributes={mode:"file", ...})
  │         → 读取 Parquet Schema 填充 fields（通过 parquet-go）
  │       else:
  │         → 建 MetaItem(item_type="object")
  │     for subdir in subdirs:
  │       → 建 MetaNode(type="prefix")
  │       → 递归 ScanPath(subdir.Path)
  │
  └── 4. 索引到 Meilisearch（现有逻辑不变）
```

**`isLakeTableFile` 判断的扩展名**：`.parquet`、`.orc`、`.avro`

### 4.5 Transfer 模块

**已完成**：`ParquetWriter`（写 Parquet 到 MinIO/S3）、`ParquetReader`（从 MinIO/S3 读 Parquet）。

**无需强制 prefix**：Transfer 将 Parquet 写到 bucket 根目录是合法的（模式 B），Meta 扫描会自动识别。用户也可以指定 prefix 组织目录结构（模式 A）。

**两种典型用法**：

```
# 模式 B（文件即表，Transfer 当前默认行为）
bucket=manager, prefix="", file_name=orders.parquet
→ manager/orders.parquet  →  lake_table: orders

# 模式 A（目录即表，适合大数据场景）
bucket=manager, prefix="warehouse/orders", file_name=part-0001.parquet
→ manager/warehouse/orders/part-0001.parquet  →  lake_table: orders
```

### 4.6 System 模块

DuckDB 在系统初始化时**自动注册为内置引擎**：

```
engine_type = "duckdb"
display_name = "湖查询"
category = "compute"
dev_modes = ["query"]
auto_registered = true   ← 系统内置，不可删除
```

## 七、关键设计原则

1. **双模式兼容**：同时支持"目录即表"（Hive/Spark 范式）和"文件即表"（DuckDB/分析师范式），Transfer 无需强制 prefix
2. **存储无关**：CompositeItemDetector 只关心文件名模式，与存储后端解耦
3. **模型一致**：lake_table 的 Schema 存储方式与关系型表完全一致
4. **DRY**：parquet-go 能力放在 common/，Meta 和 Manager 共用
5. **最小依赖**：DuckDB（CGO）只在 Develop 模块，其他模块保持纯 Go
6. **渐进扩展**：FileSystemPlugin 体系为 NAS、HDFS 等预留标准扩展点
7. **不破坏现有**：ObjectStoragePlugin 继承 FileSystemPlugin，现有扫描逻辑平滑迁移
