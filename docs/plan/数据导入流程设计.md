# ADDP 数据导入流程设计方案

## 一、背景与目标

### 问题描述

当前 ADDP 的工作流引擎（`io_operators.py`）存在 `source_type='file'` 和 `target_type='file'` 分支，直接读取/写入本地文件系统路径，这违背了数据中台的统一管理理念：
- 数据来源不可追溯
- 无法进行元数据管理和搜索
- AI 无法通过 Meta 模块发现数据
- 缺乏权限控制和安全性

### 设计目标

建立完整的"数据导入"机制，将外部数据纳入 ADDP 数据中台管理：
1. 用户通过 Manager 模块上传数据文件（支持 Shapefile ZIP 包）
2. Manager 调用 Transfer HTTP API 创建导入任务（`auto_scan_metadata=true`）
3. Transfer 异步执行导入到业务数据库（business-postgres）
4. Transfer 执行完成后自动触发 Meta 扫描（无需新增代码）
5. 工作流算子通过"数据资产引用"（engine_id + schema + table）访问数据
6. 删除 `io_operators.py` 中直接读取/写入本地文件的代码

---

## 二、架构设计

### 2.1 整体数据流

```
用户在 Manager 前端触发"导入数据"
（触发点：Manager 数据探查中，业务 PG 的 schema 节点上的操作入口）
  ↓
Manager Frontend: 上传文件（支持 Shapefile ZIP 包）
  ↓
Manager Backend: 接收上传文件
  - 校验文件格式（自动识别文件类型）
  - 如果是 ZIP 包，解压并校验完整性（必须包含 .shp/.dbf/.shx）
  - 上传所有相关文件到 infra-minio: manager 桶 temp/{upload_uuid}/ 前缀
    （railway.shp / railway.dbf / railway.shx / railway.prj）
  ↓
Manager Backend: 调用 Transfer HTTP API
  POST /api/transfer/tasks（创建导入任务，auto_scan_metadata=true）
    payload: {
      reader: { type: "s3_shapefile", config: { bucket: "manager", prefix: "temp/{uuid}/" } },
      writer: { type: "postgres_copy", config: { engine_id, schema, table } },
      auto_scan_metadata: true
    }
  POST /api/transfer/tasks/{id}/trigger（触发执行）
  ↓
Transfer Worker 异步执行:
  1. 从 MinIO 下载所有文件到 /tmp/{job_uuid}/
     （railway.shp / railway.dbf / railway.shx / railway.prj）
  2. ShapefileReader 读取 /tmp/{job_uuid}/railway.shp
  3. postgres_copy_writer 批量写入 business-postgres
  4. defer 清理 /tmp/{job_uuid}/ 本地目录
  5. 因 auto_scan_metadata=true，自动调用 triggerMetadataScan()
     → metaClient.CreateManualScanRun(engineID, schemaNames)
  ↓
Meta 创建后台扫描运行（利用现有能力，无需新增代码）:
  - 提取空间元数据（几何类型、SRID、边界、字段信息）
  - 存储到 metadata.meta_node 和 metadata.meta_item 表
  - 索引到 Meilisearch
  - 发布事件 meta:events:scan_completed（已有逻辑）
  ↓
Manager 订阅 meta:events:scan_completed，自动刷新缓存（已有逻辑）
  ↓
用户在 Manager 数据探查中看到新导入的数据
```

### 2.2 关键设计决策

#### 决策 1：临时文件存储位置 - MinIO 中转（而非服务端 /tmp）

**选择 MinIO 中转的理由**：
1. **任务重试可靠性**：Transfer 任务失败重试时，MinIO 中的文件仍然存在，而 /tmp 可能被 OS 清理
2. **部署解耦**：不要求 Manager 和 Transfer Worker 在同一服务器或共享文件系统
3. **自动清理**：利用 MinIO Lifecycle Policy 自动过期删除临时文件（7天），无需代码逻辑处理

**性能考虑**：
- 单机部署时，MinIO 在本机 Docker 容器，loopback 传输速度接近磁盘 I/O
- "多一次传输"的开销极小，换来架构灵活性

#### 决策 2：Shapefile 必须下载到本地再导入

**技术约束**：
- `go-shp` 库要求本地文件路径（`shp.Open(filePath)`），不支持流式读取
- Shapefile 是多文件格式（.shp/.dbf/.shx/.prj），必须同时存在于同一目录

**实现方式**：Transfer Worker 从 MinIO 下载全部文件到 `/tmp/{job_uuid}/`，然后调用 ShapefileReader。

#### 决策 3：Manager → Transfer 通过 HTTP API（而非 Asynq 消息队列）

**选择 HTTP API 的理由**：
- Transfer 已有完整的 HTTP API（`POST /api/transfer/tasks` + trigger）
- 通过 API 可以立即获得任务 ID，便于后续状态查询
- Transfer Worker 自己管理 Asynq 队列，Manager 无需了解队列实现细节
- 避免 Manager 直接依赖 Redis Asynq 协议，降低模块间耦合

**实现方式**：
```
Manager Backend → POST /api/transfer/tasks（创建任务）
                → POST /api/transfer/tasks/{id}/trigger（触发执行）
```

#### 决策 4：Meta 扫描由 Transfer 自动触发（无需新增代码）

**现有能力**：Transfer 的 `ExecutionEngineService` 已有 `auto_scan_metadata` 机制：
```go
// transfer/backend/internal/service/execution_engine_service.go
if task.AutoScanMetadata {
    s.triggerMetadataScan(task)
}
// triggerMetadataScan 调用 metaClient.CreateManualScanRun(engineID, schemaNames)
```

**结论**：Manager 创建任务时设置 `auto_scan_metadata=true`，Meta 扫描自动触发，**无需在 Meta 模块新增任何代码**。

#### 决策 5：通用导入 API（而非格式特定 API）

**API 设计**：`POST /api/manager/import`（通用），而非 `/api/manager/import/shapefile`

**理由**：
- 防止随格式增多导致 API 数量爆炸
- 通过上传文件的扩展名或 Content-Type 自动识别格式
- 统一的响应格式，前端无需针对不同格式分别处理

#### 决策 6：前端触发点 - 业务 PG schema 节点

导入功能的入口设置在 Manager 数据探查的**业务 PG 数据库的 schema 节点**上：
- 用户已选定目标数据库（业务 PG 引擎）和目标 schema
- 在该节点操作菜单中增加"导入数据"入口
- 用户在当前上下文中自然了解导入目标

## 三、模块职责划分

### 3.1 Manager 模块（数据上传入口）

#### 新增功能

**前端**：
- 在数据探查页面的**业务 PG schema 节点**操作菜单中，增加"导入数据"入口
- 支持上传 Shapefile（单文件或 ZIP 包）
- 显示导入进度（通过轮询 Transfer 任务状态：`GET /api/transfer/tasks/{id}`）
- 导入完成后自动刷新当前 schema 下的表列表（利用已有的 `meta:events:scan_completed` 订阅）

**后端**：
- 接收上传文件（`multipart/form-data`）
- 自动识别文件类型（根据扩展名）
- 如果是 ZIP 包，解压并校验文件完整性（必须包含 .shp/.dbf/.shx）
- 将文件上传到 infra-minio 的 `manager` 桶 `temp/{upload_uuid}/` 前缀
- 调用 Transfer HTTP API 创建并触发导入任务（设置 `auto_scan_metadata=true`）
- 返回任务 ID 供前端轮询状态

#### API 设计

```
POST /api/manager/import
Content-Type: multipart/form-data

参数：
- file: Shapefile ZIP 包或单个 .shp 文件（如果是单文件，需要同时上传 .dbf/.shx/.prj）
- target_engine_id: 目标数据库引擎 ID（业务 PG）
- target_schema: 目标 schema（默认 public）
- target_table: 目标表名（可选，默认使用文件名）
- encoding: DBF 编码（可选，默认 UTF-8，支持 GBK）

响应：
{
  "upload_uuid": "xxx",
  "transfer_task_id": 123,   // Transfer 任务 ID，用于前端轮询状态
  "status": "pending"
}
```

#### 数据库变更

**无需新增表**。Manager 不持久化导入记录（导入历史通过 Transfer 任务记录查询）。

### 3.2 Transfer 模块（数据导入执行）

#### 新增功能

**S3 Shapefile 下载支持**：
- 扩展现有 S3Reader 或新增专用下载工具，支持将 MinIO prefix 下的多个文件（.shp/.dbf/.shx/.prj）全部下载到同一本地临时目录
- 下载完成后由 ShapefileReader 打开本地目录中的 .shp 文件

**实现要点**：

```go
// Transfer Worker 处理流程（复用现有 ExecutionEngine）
// 读取器配置
reader := pipeline.ConnectorConfig{
    Type: "shapefile",
    Config: map[string]interface{}{
        "file_path": downloadedLocalPath, // 从 MinIO 下载后的本地路径
    },
}

// 写入器配置（复用现有 postgres_copy_writer）
writer := pipeline.ConnectorConfig{
    Type: "postgres_copy",
    Config: map[string]interface{}{
        "engine_id": targetEngineID,
        "schema":    targetSchema,
        "table":     targetTable,
    },
}
```

**任务执行流程**（Transfer 任务 handler 层面新增逻辑）：
```go
// 1. 创建本地临时目录
tmpDir := filepath.Join("/tmp", jobUUID)
os.MkdirAll(tmpDir, 0755)
defer os.RemoveAll(tmpDir) // 确保清理

// 2. 从 MinIO 下载所有 Shapefile ref 文件
downloadShapefileFromMinIO(bucket, prefix, tmpDir)
// 下载 .shp / .dbf / .shx / .prj

// 3. 找到 .shp 主文件路径
shpFilePath := filepath.Join(tmpDir, findShpFile(tmpDir))

// 4. 通过现有 ExecutionEngine 执行导入
// ExecutionEngine 在 auto_scan_metadata=true 时，完成后自动触发 Meta 扫描
```

#### 无需修改的现有能力

以下能力**已完整存在**，无需修改：
- `ShapefileReader`：读取本地 .shp 文件
- `postgres_copy_writer`：批量写入 PostgreSQL
- `auto_scan_metadata` 机制：任务完成后自动调用 `metaClient.CreateManualScanRun()`
- Transfer HTTP API：`POST /api/transfer/tasks` + `POST /api/transfer/tasks/{id}/trigger`

## 六、关键技术细节

### 6.1 Shapefile ZIP 包解压

Manager Backend 需要处理 ZIP 包解压：

```go
func extractShapefileZip(zipPath string, targetDir string) error {
    r, err := zip.OpenReader(zipPath)
    if err != nil {
        return err
    }
    defer r.Close()

    requiredExts := map[string]bool{".shp": false, ".dbf": false, ".shx": false}

    for _, f := range r.File {
        ext := strings.ToLower(filepath.Ext(f.Name))
        if _, ok := requiredExts[ext]; ok {
            requiredExts[ext] = true
            extractFile(f, targetDir) // 解压到 targetDir
        } else if ext == ".prj" {
            extractFile(f, targetDir) // .prj 可选，但有则解压
        }
    }

    // 验证必需文件是否都存在
    for ext, found := range requiredExts {
        if !found {
            return fmt.Errorf("missing required file: %s", ext)
        }
    }

    return nil
}
```

### 6.3 Transfer 中的多文件下载逻辑

```go
// 从 MinIO prefix 下载 Shapefile 的所有ref 文件到本地目录
func downloadShapefileFromMinIO(s3Client *s3.S3, bucket, prefix, localDir string) (string, error) {
    // 列出 prefix 下的所有对象
    output, err := s3Client.ListObjectsV2(&s3.ListObjectsV2Input{
        Bucket: aws.String(bucket),
        Prefix: aws.String(prefix),
    })
    // 下载每个文件到 localDir
    var shpFile string
    for _, obj := range output.Contents {
        key := aws.StringValue(obj.Key)
        localPath := filepath.Join(localDir, filepath.Base(key))
        downloadObject(s3Client, bucket, key, localPath)
        if strings.HasSuffix(strings.ToLower(key), ".shp") {
            shpFile = localPath
        }
    }
    if shpFile == "" {
        return "", fmt.Errorf("no .shp file found in prefix: %s", prefix)
    }
    return shpFile, nil
}
```

### 6.4 文件类型自动识别

Manager `POST /api/manager/import` 接口通过文件扩展名自动识别类型：

```go
func detectFileType(filename string) string {
    ext := strings.ToLower(filepath.Ext(filename))
    switch ext {
    case ".zip":
        return "shapefile_zip" // 需要解压，自动探测内部格式
    case ".shp":
        return "shapefile"
    case ".geojson", ".json":
        return "geojson"
    case ".gpkg":
        return "geopackage"
    default:
        return "unknown"
    }
}
```

## 七、风险与缓解措施

### 风险 1：大文件上传超时

**缓解措施**：
- Manager API 设置合理的超时时间（建议 5 分钟）
- 前端显示上传进度条
- 超大文件考虑使用分片上传（MinIO 支持 multipart upload）

### 风险 2：导入任务失败后 MinIO 临时文件堆积

**缓解措施**：
- MinIO Lifecycle Policy 自动清理（7天过期）
- Transfer Worker 的 `defer os.RemoveAll(tmpDir)` 清理本地 /tmp
- Transfer 任务失败时前端提示用户，支持重试

### 风险 3：并发导入同名表冲突

**缓解措施**：
- 导入前检查目标表是否存在，若存在则提示用户（覆盖/追加/重命名）
- 可选：表名自动加时间戳后缀（如 `railway_20260312_143022`）

### 风险 4：Shapefile 编码问题（中文字段名乱码）

**缓解措施**：
- ShapefileReader 支持指定 DBF 编码（默认 UTF-8，可配置 GBK）
- Manager 上传 API 提供 `encoding` 参数（默认 UTF-8，支持 GBK）

### 风险 5：Shapefile ZIP 内文件路径嵌套问题

**缓解措施**：
- ZIP 解压时递归处理子目录，将 .shp/.dbf/.shx 扁平化到同一目录
- 支持常见的 ZIP 打包方式（文件直接在根目录、或在一层子目录中）

| Manager 前端 | 新增 | 业务 PG schema 节点"导入数据"入口；上传/进度展示组件 |
| Transfer 后端 | 新增 | MinIO 多文件下载工具；`s3_shapefile` reader 类型支持 |

| infra 脚本 | 修改 | `init-minio.sh` 添加 `manager:temp/` Lifecycle Policy（7天过期） |

## 十、总结

本方案通过 **Manager（上传）→ Transfer（导入+自动扫描）→ Meta（元数据就绪）** 的协作链路，建立了完整的数据导入流程。

**核心设计要点**：
1. **通用 API 设计**：`POST /api/manager/import` 自动识别文件类型，避免 API 数量随格式增多而爆炸
2. **直接调用 HTTP API**：Manager → Transfer HTTP API，而非 Asynq 消息队列，利用现有接口能力
3. **零新增代码触发 Meta**：`auto_scan_metadata=true` 复用现有 Transfer→Meta 机制，无需在 Meta 模块新增任何代码
4. **MinIO 中转**：解耦 Manager 和 Transfer 的物理位置，支持任务重试，利用 Lifecycle Policy 自动清理
5. **Shapefile 本地化**：Transfer 先下载到 /tmp，再由 ShapefileReader 读取，满足 go-shp 的本地文件要求

完成本方案后，ADDP 工作流引擎将不再依赖本地文件路径，所有数据都纳入统一管理。
