# ADDP 字段名大小写问题全面排查与修正计划

## 📋 计划概述

根据 `docs/addp常见故障排查.md` 中的 **MVT 物化视图创建失败 - 主键大小写问题** 说明，在 ADDP 平台中存在系统级的 PostgreSQL 字段名大小写敏感性问题。

通过全面代码排查，已发现 **5 个高风险问题点** 和 **多个潜在风险区域**，需要系统性修复。

---

## 🎯 核心问题分析

### 问题本质

PostgreSQL 中不带引号的标识符会自动转换为小写。当表的字段使用混合大小写（如 `SmID`、`SmGeometry`、`OBJECTID`、`SHAPE` 等）时，SQL 语句必须用双引号包裹这些列名以保留原始大小写。

### 问题范围

- **影响深度**：跨越后端多个模块的动态 SQL 生成
- **影响类型**：数据查询失败、数据转换失败、索引创建失败、MVT 生成失败
- **常见场景**：
  - SuperMap 数据：`SmID` + `SmGeometry`
  - ArcGIS 数据：`OBJECTID` + `SHAPE`
  - PostGIS 标准：`id` + `geom`
  - QGIS 导入：`fid` + `geometry`

## 🚨 高风险问题详情

### 问题 1：common/spatial/query.go - 几何列未加引号

**文件**: `common/spatial/query.go:189-199`

**问题代码**:
```go
query := fmt.Sprintf(`
    SELECT
        ST_XMin(extent) as min_lon,
        ST_YMin(extent) as min_lat,
        ST_XMax(extent) as max_lon,
        ST_YMax(extent) as max_lat
    FROM (
        SELECT ST_Extent(ST_Transform(%s, 4326)) as extent
        FROM "%s"."%s" TABLESAMPLE BERNOULLI (1) LIMIT 10000
    ) t
`, geomColumn, schema, table)
```

**问题**:
- 第 196 行：`ST_Transform(%s, 4326)` 中的 `geomColumn` 未用双引号包裹
- Schema 和 table 正确使用了双引号，但几何列没有

**影响**:
- **影响范围极广**：Common 模块被 Manager、Meta、Service 等多个模块调用
- 混合大小写几何列（如 `SmGeometry`、`GeomData`）会导致查询失败

**修复方案**:
```go
query := fmt.Sprintf(`
    SELECT ST_Extent(ST_Transform("%s", 4326)) as extent
    FROM "%s"."%s" TABLESAMPLE BERNOULLI (1) LIMIT 10000
`, geomColumn, schema, table)
```

**风险等级**: 🔴 **极高**（Common 模块，影响多个上层模块）

### 问题 2：manager/backend/internal/mvt/preparation_service.go - Schema/Table 未加引号

**文件**: `manager/backend/internal/mvt/preparation_service.go:531-538`

**问题代码**:
```go
createMVSQL := fmt.Sprintf(`
    CREATE MATERIALIZED VIEW %s AS
    SELECT
        %s,
        ST_Transform("%s", 3857) AS geom_3857
    FROM %s.%s
    WHERE "%s" IS NOT NULL
`, mvFullName, selectClause, geomColumn, schema, table, geomColumn)
```

**问题**:
- 第 536 行：`FROM %s.%s` 中的 schema 和 table 未加引号
- 虽然几何列正确加了引号，但 schema.table 未保护

**影响**:
- 混合大小写的 schema 名或 table 名会导致物化视图创建失败
- 这是文档中记录的核心问题

**修复方案**:
```go
createMVSQL := fmt.Sprintf(`
    CREATE MATERIALIZED VIEW %s AS
    SELECT
        %s,
        ST_Transform("%s", 3857) AS geom_3857
    FROM "%s"."%s"
    WHERE "%s" IS NOT NULL
`, mvFullName, selectClause, geomColumn, schema, table, geomColumn)
```

**风险等级**: 🔴 **高**（核心功能 MVT 生成）

### 策略 2：创建统一的 SQL 构建工具（长期方案）

在 `common/` 模块中创建 SQL 安全构建工具：

```go
// common/sql/builder.go
package sql

import "github.com/lib/pq"

// SafeQualifiedIdentifier 生成安全的 "schema"."table" 格式
func SafeQualifiedIdentifier(schema, table string) string {
    return pq.QuoteIdentifier(schema) + "." + pq.QuoteIdentifier(table)
}

// SafeColumnName 生成安全的列引用
func SafeColumnName(col string) string {
    return pq.QuoteIdentifier(col)
}

// SafeGeometryTransform 生成安全的几何转换 SQL
func SafeGeometryTransform(col string, targetSRID int) string {
    return fmt.Sprintf(`ST_Transform("%s", %d)`, col, targetSRID)
}

// BuildMVTQuery 统一构建 MVT 查询
func BuildMVTQuery(schema, table, geomCol string, ...) string {
    // 所有列名自动加引号
}
```

**优点**:
- 集中管理 SQL 安全构建逻辑
- 强制开发者使用安全方法
- 便于单元测试覆盖

### 策略 3：元数据优先策略（推荐）

**Manager MVT 修复**:
```go
// 1. 从 Meta 获取表结构（包含正确大小写的列名）

// 3. 构建 SQL 时使用双引号

        "%s" AS id,
        ST_Transform("%s", 3857) AS geom_3857

```

**优点**:
- 减少数据库查询（Meta 已缓存）

- 性能更好
