## 二、后续开发顺序

| 优先级 | 下一步 | 进入条件 |
| --- | --- | --- |
| 1 | 补齐原生宿主与多进程部署覆盖 | Linux VM 单新 Monitor 绑定已验；原生宿主与 Desktop VM 分别声明，多进程按各自实例身份验证，不在线改挂既有实例 |
| 2 | 补齐原功能表的服务质量、引擎专业指标及容器资源 | PostgreSQL 专业发现、Monitor 读取与页面已落地且正式身份专业 T4 已通过；来源准入新增回归的 Linux T2 结果由专门 CI 会话回传。其他引擎和容器资源先明确对象归属、配额和 OS 支持，复用固定目录与唯一采集链 |
| 3 | Trace 长时保留验证与后续覆盖 | 两档短测已满足 20 GiB/72 小时容量外推；下一步另定本地长时资源窗口，验证真实过期删除、长期合并增长及查询余量，不能沿用本次四十分钟授权。Python、异步关联和 SQL 另批明确传播与授权边界 |
| 4 | 生产发布及受控运维 | 真实平台 T5；SSH/初始化/防火墙/启停另有权限、计划、执行与审计确认 |

Trace 中 request_id、trace_id、execution 身份分别表达请求、调用链和业务执行；异步任务明确关联并创建新运行跨度，不能把长任务硬挂在创建请求下。慢请求保留须证明实际采样策略，随机头部采样不能保证保留全部慢请求。

受控运维中 ADDP 管理目标、计划、权限与审计，成熟执行设施实施变更。主机登记不默认保存 SSH 密码，采集身份不具备 Shell 权限；Monitor 不提供任意命令执行器，租户 Orchestrator 任务不隐含获得平台主机操作权。

## 五、服务承载清单接入边界

部署清单接入统一由 System 平台主机管理负责，v2 主机清单可省略采集并明确 ADDP 服务允许名单；需要采集时经 Console 一次性内存草稿将同一主机及来源交给 Monitor。协议和失败处理见正式规范 4.2，旧 Monitor 导入编排已删除。

macOS 原生宿主与 Docker Desktop Linux VM 分别登记，不能跨宿主绑定。接入结果只生成实际宿主上的 `ADDP_HOST_NODE_ID` 部署参数；新进程首次声明后仍由既有当前允许集合裁决，不自动修改全局 `.env`、重启服务或在线改挂旧实例。

## 六、Business 引擎接入设计

### 已确认的自带部署自动接入方向

2026-10-19 用户确认：Infra 与平台维护的 Business 部署统一作为 Platform 运维对象，租户连接、凭据、数据和任务继续按 Tenant 授权。日常入口改为部署侧自动发现、页面批量确认、随后自动更新来源与采集；不要求用户运行导出命令或传递 JSON。首次主机关联及扩大纳管范围须管理员确认；容器重建只更新运行来源，不自动迁移主机或授予租户权限。

实现顺序为：复用部署生命周期，统一只读发现本工作区 Infra/Business 实际 Compose 服务并自动发布有界无凭据快照；System 消费候选服务并维护确认的部署身份与承载声明；Monitor 按已实现的专业适配器配置采集。部署来源、管理员声明、实际可用性、采集结果分别表达，配置文件中的服务不等于已运行服务。发现失败清除当前有效候选，停服不等于删除已确认部署，观测故障不阻断业务启动。

发现只读取固定 Docker 字段，不读取 `.env`、容器环境变量、凭据或业务内容，不授予 System Web 服务 Docker 管理能力。快照由部署侧按作用域原子替换，Infra 与 Business 互不覆盖；未知服务与集群组件可以展示来源，但未适配能力明确标为不支持，不猜测集群、租户或物理消耗归属。首批专业指标依次覆盖 Infra PostgreSQL 与 Business PostgreSQL 的连接、事务、等待、回滚／死锁及容量；容器资源和其他引擎分别适配，主机总指标不冒充引擎指标。

自动来源刷新与已确认声明的存储、最小权限及并发契约需在实现相应阶段明确；既有手工导入不是长期并行路线，替代页面与正式前向迁移就绪时删除旧入口。旧手工登记 T4 不作为新自动链路验收；新链路须独立记录真实运行及全退出清理证据。当前本节为已确认方向，尚未实现的环节不能计为完成。

控制面先提供只读 `GET /platform/engine_deployments/discovery`：沿用非委托 Platform User 与 `platform.engine_deployment.read`，不接受 query/body。System 仅读取部署配置指定目录的 `infra.json/business.json`，不执行 Docker、不接受请求指定文件路径，不改变声明或权限。响应固定包含两个作用域，分别表达未配置、缺失、不可用、过期或有效快照；有效期限 120 秒，允许最多 30 秒时钟偏差，失败不得带旧候选或主机推断。批量确认写入未接入前，该只读能力不表示已完成自动纳管。管理员确认的版本与历史不随运行来源刷新改写，后续当前运行来源通过匹配已确认的来源键独立投影。

持续来源由部署侧独立观测进程每轮完成后间隔 30 秒刷新，不放入 System 请求或业务 Ready。复用同一发现入口和私有目录，Infra 启动／停止管理其生命周期，Business 与开发启动只确保同一工作区进程存在；启动结果与来源采样结果分别表达。进程只继承 Docker 所需环境，以私有运行记录和当次随机标识核对 PID 归属，拒绝操作不明进程；停止时立即将来源标为不可用，Hosted 退出同样须停止并确认无当次进程。观测进程只执行固定的只读 Docker 命令，不提供 Docker 变更入口，也不获得主机／部署登记、数据库访问或租户权限。

批量确认首批覆盖 Infra 与 Business 的两个单容器 PostgreSQL；其他服务显示发现事实及未适配原因，不将集群组件冒充完整引擎。唯一集合 POST 改为至多 16 个显式成员，各项只传作用域、服务名、来源事实摘要、名称、纳管意图及主机 UUID。服务端重新读取有效来源并校验摘要，按来源键排序后在同一数据库事务创建全部部署、声明及审计；重复成员、来源变化／过期、主机失效或任一写入失败均整批回滚。摘要不含每次刷新时间，也不充当持久资源 version；新建版本仍为 1，更新使用各自 version。PUT 只修改名称、纳管意图与主机，不接受客户端改写来源快照；来源运行变化独立投影，不覆盖声明历史。

确认快照统一为 `addp.engine-deployment-inventory/v1`，来源项目允许 `addp-infra/business`。已有根记录通过正式前向迁移规范化协议标识，稳定部署 ID、版本及声明时间不变；不可变声明历史和审计保留当时原始载荷，不增加旧协议读取分支。替代页面与批量 API 同批删除文件导入、单项原始来源创建、旧文件解析器及用户导出命令；失败和未知写入保留草稿、禁止自动重试，重新读取前不重复创建。

平台运维范围按实际运维责任确定，租户读取按对象权限确定。平台自管 Business 服务的部署、整体资源及可用性属于平台运维；租户自行部署的外部服务默认不纳管，委托监控须显式授权。平台角色不由运维关联获得租户连接凭据、表内容、SQL 或执行结果；共享主机和引擎的整体消耗不归算为某个租户用量。

区分纳管主机、实际引擎部署及 System Engine Instance。现有引擎地址去重按租户范围进行，同一部署可以对应多个登记；不按 engine_id 累加同一物理消耗。System 拥有部署身份和显式承载关联及其有效时间，Monitor 只消费授权投影。集群可以承载于多主机，云服务允许主机未知；不得按 IP、容器名或共享 VM 资源猜测关联。

租户登记与部署的关联须经服务端核验；租户外部引擎委托监控、租户用量归属和租户专业监控权限不在首批开放范围。平台维护同一底层故障事件，租户只读取获授权的影响提示。

部署侧持续发现和 System 候选读取已落地；管理员批量确认接入已实现并通过确定性回归，契约见[平台运行观测规范 4.4](../spec/addp平台运行观测规范.md#44-平台引擎部署登记)。普通操作不再要求导出或导入文件。两个单容器 PostgreSQL 的真实自动接入 T4 已通过，精确源码、身份、回滚与退出清理见[专项证据](../spec/testing/evidence/Monitor历史证据.md#infra与business-postgresql-自动接入)。该结果不包含专业指标采集。

2026-10-20 用户已确认 Infra／Business 各自独立的只读采集账号，由部署侧管理凭据；通过固定函数仅返回连接、事务、回滚、死锁、等待及数据库容量汇总，不读业务表、SQL 正文或租户凭据，不归算租户用量。先实现和验证数据库侧最小读取边界，再接入既有指标拉取及 Monitor 查询页面。多服务／集群、租户 Engine 关联和租户用量归属仍未开放。新自动流程如需扩展一次性 Hosted 临时管理员测试用途，须在具体调用范围明确后按测试规范确认，不沿用已被替代的手工导入验收。

### PostgreSQL 专业发现、查询与展示方案

沿用部署发现 → System 当前引擎身份 → Monitor 唯一 HTTP SD → Prometheus → Monitor 授权查询 → Console 页面这一条链，不新增手工登记采集目标、数据库凭据或租户 Engine 关联。权限沿用 `monitor.resource_observation.read` 与逐请求核验的 `platform.engine_deployment.read`，不新增权限／角色分配或调整 IAM 内核。

可信来源由部署侧仅读取固定 Docker 身份、Owner／作用域标签及指标容器的显式发布端口，核对采集器所绑定的数据库容器与当前 PostgreSQL 完全一致；不读取容器环境、SQL 端口、密码、文件 Secret 或数据库。来源端口和数据库端口分开，不按名称或 IP 猜测对应关系。无采集器、部分启动、归属不明、来源变化或过期分别表达，不因专业来源不可用清空合法主机和进程身份。

**已确认的后台读取扩展**：同一个 System 私有观测投影，仅为已纳管且有效关联主机的 Infra／Business PostgreSQL 增加指标 HTTPS 端点与当前数据库容器运行身份／启动时刻。既有后台身份及权限不变，字段不进入普通浏览器 DTO；不增加 SQL 地址、连接凭据、租户引擎或业务内容。System 继续唯一裁决管理有效性，Monitor 只核验固定 mTLS／CIDR／端口准入并派生采集标签。部署发现协议采用单一更新版本，旧读写路径同批移除；引擎确认摘要与不可变声明不包含采集配置，不让来源启停改写管理历史。

固定查询目录首期 12 项：总连接、活跃连接、空闲连接、事务内空闲连接、活跃等待、锁等待、IO 等待、最大连接数（均为数量）；每秒提交、每秒回滚、每秒死锁（各自为独立累计量的速率）；非模板数据库总容量（字节、页面自动换算）。这是整体 PostgreSQL 观测，不将采集事务当业务吞吐、不归算租户用量，也不凭连接数直接判断健康。

速率使用固定一分钟完整窗口，至少四次有效采样，并验证过去和当前属于同一服务启动／统计代际、无计数回退且窗口两端新鲜；重启、统计重置或统计关闭时留空，不补零、不跨代际计算。SQL Exporter 的 HTTP 200／up=1 仍不足以证明 SQL 成功，必须验证固定快照、采样时间与字段完整性；来源不可用或 SQL 失败清空当前值，缺样形成趋势断点。

接口为 `/platform/engine_resource_observations`（单部署、最多十二指标）、`/platform/engine_resource_summaries`（当前页部署的四项摘要）及 `/platform/engine_resource_trends`（单部署固定目录）。预算复用当前查询策略；用户 Token 每请求交 System 裁决，查询后再核对当前身份／权限／来源，不用后台权限或旧时序兜底。页面在运行监控下提供“引擎监控”，从现有 System 引擎部署列表进入；不让用户重复填写节点或端点，复用共享格式化、图表、自动刷新与 URL 恢复。

**已确认的首期历史范围**：即时值与最多七天趋势只读取当前 PostgreSQL 容器运行段；采集器重启但数据库运行身份不变时可延续，数据库容器重建后不混入旧容器数据。数据库进程重启或统计重置位置的速率仍按前述代际检查留空。退出容器历史及跨运行段拼接另定保留／授权规则。

验证沿既有 Monitor／System／Common T1、System 投影／Monitor PostgreSQL T2、固定指标 mTLS T2、Monitor／Console 前端门禁及 Swagger 覆盖；部署发现协议、标签和 Prometheus 配置变更同步既有 CI 登记。正式身份专业查询／页面 T4 沿下述已确认的限定 Hosted 用途执行，未执行、失败或清理不完整均不计通过。

2026-10-21 已确认的正式身份 T4 限定用途：沿同一一次性 Hosted 的 `engine-admission` 前置，只给当次临时平台管理员增加三个 `engine_resource_*` GET 的专业观测测试用途，并操作当次两个已接入 PostgreSQL 的真实 Console 引擎监控页面。验证固定目录、单位与零值、当前容器趋势、停用／来源缺失清空和恢复，以及无权限身份拒绝；沿正式密码／MFA、既有平台读取权限和独立 Prometheus 身份，不读取租户 Engine、SQL 正文、业务表或凭据，不改生产 IAM、不加压、不触及个人环境。仍使用原 1800 秒场景及 Job 60 分钟上限，退出销毁当次部署／身份／凭据并核验零残留；必须实际执行且清理通过后才计为 T4 通过。
