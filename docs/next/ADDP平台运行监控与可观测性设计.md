已实现的对象、部署、采集、查询和告警契约迁入[平台运行观测规范](../spec/addp平台运行观测规范.md)。本专题仅保留当前能力摘要、未实施设计和验收缺口；摘要区分当前实现与实际验收，不将文档整理计为产品验证。

## 二、后续开发顺序

| 优先级 | 下一步 | 进入条件 |
| --- | --- | --- |
| 1 | 完善 Business 引擎的明确承载清单和接入 | 运维与租户边界已确认，来源导出已实现；继续 System 部署登记、聚合版本与显式承载有效区间，沿管理员确认路径，不按地址猜测 |
| 2 | 补齐原生宿主与多进程部署覆盖 | Linux VM 单新 Monitor 绑定已验；原生宿主与 Desktop VM 分别声明，多进程按各自实例身份验证，不在线改挂既有实例 |
| 3 | 补齐原功能表的服务质量、引擎专业指标及容器资源 | 确认专业凭据、对象归属、配额和 OS 支持，复用固定目录与唯一采集链 |
| 4 | Trace、慢接口与调用拓扑 | OpenTelemetry → Alloy OTLP → Tempo，先明确采样、传播、敏感内容与容量 |
| 5 | 生产发布及受控运维 | 真实平台 T5；SSH/初始化/防火墙/启停另有权限、计划、执行与审计确认 |

Trace 中 request_id、trace_id、execution 身份分别表达请求、调用链和业务执行；异步任务明确关联并创建新运行跨度，不能把长任务硬挂在创建请求下。慢请求保留须证明实际采样策略，随机头部采样不能保证保留全部慢请求。

受控运维中 ADDP 管理目标、计划、权限与审计，成熟执行设施实施变更。主机登记不默认保存 SSH 密码，采集身份不具备 Shell 权限；Monitor 不提供任意命令执行器，租户 Orchestrator 任务不隐含获得平台主机操作权。

## 三、验收状态与剩余缺口

完整样本比较已通过 [Hosted 专项](https://github.com/pampa0629/addp/actions/runs/39082438625)（源码 `74adc2d45`）：自然采样形成 CPU/内存各 41 个有效评估点，三次 5 分钟比较均进入完整分支，原始报告独立重算、页面刷新恢复及退出零残留通过。原 1800 秒场景预算和浏览器期限保持不变；该专项与 CPU、内存压力分别验收，不推定长时段或进程比较已经验证。

资源告警已分别通过[真实内存 T4](https://github.com/pampa0629/addp/actions/runs/39016166744)（源码 `8111363d2`）和[受限 CPU T4](https://github.com/pampa0629/addp/actions/runs/39082008910)（源码 `53be389c5`）。内存覆盖打开、缺样保持、恢复及签名重试；CPU 在 4 核 VM 以 1 核硬配额加压约 96.51 秒，固定测试阈值下触发并恢复同一事件，两条通知 delivered，首次 503 后自动重试共三次请求。两轮均验证正式身份隔离与退出零残留。该证据不代表生产满载、容量评估、自动扩容或生产 T5 已验收。

主机组合筛选、详情返回及重置已有个人 Safari 验证。System 清单接入 → Monitor 采集保存已通过 [Hosted 专项](https://github.com/pampa0629/addp/actions/runs/39127927703)（受验源码 `fb13955d8f3cc48b254f2c840e55b8f8f638d2cc`，包含 `70c62a09a`、`9263ab6ee`）：单台 Linux VM 创建一次主机，正式 400 拒绝后只重试同一主机采集，刷新、两 Owner 独立读取及准确数量均通过。场景约 63.535 秒，浏览器约 39.370 秒；配置退役通过 API 删除采集并核验 404、停用主机且核验版本递增，随后独占部署销毁与外层零残留通过，不表示产品已提供主机 DELETE。

新进程真实绑定已通过 [Hosted 专项](https://github.com/pampa0629/addp/actions/runs/39169909912)（精确源码 `fee7cb91d8ef674d2beb41036a288519bc1d6be7`）：新 Monitor 首次绑定当前主机，旧实例退出且资源为 `not_active`，System 对等实例保持未绑定；停用主机后同一进程拒绝绑定但资源有效，重新启用后恢复。真实 Console 从当前主机名进入同一 iframe 的资源页，收据包含精确九项有效标量与主机版本 3，后退及刷新恢复筛选。场景约 162.642 秒，绑定浏览器约 12.533 秒；配置退役与外层部署销毁、Infra 零残留分别核验通过。浏览器收据按端点、主机及完整指标集合选择，不能由并发网卡响应替代；原角色、预算和单一路径保持不变。

上述为一次性 Linux VM 的单个新 Monitor 进程验证，不代表原生 macOS、多进程、Business 引擎承载、总览多真实主机或生产 T5 已验收。精确源码的 Console 与 Platform consistency CI 已实际执行通过；本地 Console 聚合的 4 项其他场景失败单独保留，不用远端结果覆盖本地失败事实。

聚合门禁须核对对应源码与实际执行项；连接预检未通过、排队、路径跳过和旧批次结果均不计为通过，分项结果只证明各自范围。正式测试产物由现有 CI/验收报告保存，本文不追加临时失败日志。

## 五、服务承载清单接入边界

部署清单接入统一由 System 平台主机管理负责，v2 主机清单可省略采集并明确 ADDP 服务允许名单；需要采集时经 Console 一次性内存草稿将同一主机及来源交给 Monitor。协议和失败处理见正式规范 4.2，旧 Monitor 导入编排已删除。

macOS 原生宿主与 Docker Desktop Linux VM 分别登记，不能跨宿主绑定。接入结果只生成实际宿主上的 `ADDP_HOST_NODE_ID` 部署参数；新进程首次声明后仍由既有当前允许集合裁决，不自动修改全局 `.env`、重启服务或在线改挂旧实例。

## 六、Business 引擎接入设计

平台运维范围按实际运维责任确定，租户读取按对象权限确定。平台自管 Business 服务的部署、整体资源及可用性属于平台运维；租户自行部署的外部服务默认不纳管，委托监控须显式授权。平台角色不由运维关联获得租户连接凭据、表内容、SQL 或执行结果；共享主机和引擎的整体消耗不归算为某个租户用量。

区分纳管主机、实际引擎部署及 System Engine Instance。现有引擎地址去重按租户范围进行，同一部署可以对应多个登记；不按 engine_id 累加同一物理消耗。System 拥有部署身份和显式承载关联及其有效时间，Monitor 只消费授权投影。集群可以承载于多主机，云服务允许主机未知；不得按 IP、容器名或共享 VM 资源猜测关联。

实施顺序：先提供当前工作区 PostgreSQL 的只读部署来源清单，再实现管理员确认的 System 部署登记与主机关联，最后接入引擎专用指标。租户登记与部署的关联须经服务端核验；租户外部引擎委托监控、租户用量归属和租户专业监控权限不在首批开放范围。平台维护同一底层故障事件，租户只读取获授权的影响提示。

来源导出与 System 部署登记、显式单主机关联已落地，契约见[平台运行观测规范 4.4](../spec/addp平台运行观测规范.md#44-平台引擎部署登记)。首批只接 Business PostgreSQL；文件、登记和关联均不证明实时在线或采集成功。代码与确定性验证不替代产品 T4，真实导入/登记验收仍待执行。

下一步先验收真实 PostgreSQL 部署来源到 System 身份与承载声明的链路，再接 Monitor 的引擎专用指标；多服务/集群、租户 Engine 关联、专业采集和租户用量归属仍未开放。新权限仅向既有平台系统管理员发布，运行验收需 System 正式迁移后重新完成密码/MFA 登录；一次性 Hosted 临时管理员如需新增部署接口用途，须按测试规范先明确限定范围。
