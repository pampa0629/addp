## 一、边界说明

当前已经落地的 TIFF / COG 快显解决的是“Manager 中快速查看”的问题，不等于完整栅格计算体系。

本文只讨论第一阶段之外的能力，例如：

1. 栅格坐标重投影。
2. 栅格裁剪、镶嵌和重采样。
3. 多 band 计算、统计和直方图。
4. COG 合规校验和通用栅格格式优化。
5. 图片瓦片或发布服务所需的渲染产物生成。

这些能力应作为 GeoPython Workflow 或未来独立栅格引擎的任务型算子设计，不应成为 Manager 打开 TIFF item 的硬前置。

## 二、对象模型建议

后续栅格算子可以采用三类运行时对象。

### 2.1 `RasterRef`

轻量输入引用，表示一个可被栅格算子消费的源对象。

可包含：

- 原始 `ResourceLocator`
- `storage_ref`
- 主文件与 related refs
- format / profile
- extent / CRS / transform
- width / height / band 摘要

`RasterRef` 是跨 API 传递的轻量描述，不携带大数组。

### 2.2 `RasterDataset`

计算引擎内部打开后的运行时对象，例如 rasterio dataset 或 xarray DataArray / Dataset。

`RasterDataset` 只在引擎内部流转，不作为外部 API 结果返回。

### 2.3 `RasterArtifact`

栅格算子的输出产物引用。

典型形态：

- COG 对象
- 裁剪后的 GeoTIFF
- 重投影后的 GeoTIFF / COG
- 镶嵌后的 COG
- tiles 目录
- PNG 预览图
- 统计结果 JSON

输出给平台时应返回：

- `artifact_type`
- `storage_ref`
- `format`
- `profile`
- `extent`
- `crs`
- `bands`
- `metadata`

不能返回整幅 raster 数据。

## 三、候选算子

### 3.1 基础信息与校验

| 算子 | 作用 | 边界 |
| --- | --- | --- |
| `raster_info` | 读取 width、height、bands、dtype、CRS、transform、extent、nodata、overview。 | 可作为 Meta 受控 probe helper 的实现参考，但正式 facts 归 Meta scan。 |
| `validate_cog` | 判断对象是否是合格 COG，并输出不合格原因。 | 不替代 Manager `raster_cog` 结果状态。 |

### 3.2 格式优化与转换

| 算子 | 作用 | 边界 |
| --- | --- | --- |
| `raster_to_cog` | 通用栅格转 COG。 | 若后续进入完整栅格算子体系，再讨论是否把 `tiff_to_cog` 收敛为其 TIFF 专用配置。 |
| `raster_build_overviews` | 为 GeoTIFF / COG 生成 overview。 | 不在普通预览中隐式执行。 |
| `raster_reproject` | 将 raster 重投影到目标 CRS。 | 可服务非 4326 / 3857 数据的可视化或发布，但不是第一阶段快显前置。 |
| `raster_resample` | 按目标分辨率或目标尺寸重采样。 | 应明确重采样算法和 nodata 传播规则。 |

### 3.3 空间裁剪与组合

| 算子 | 作用 | 边界 |
| --- | --- | --- |
| `raster_clip` | 按 bbox、geometry 或图层边界裁剪。 | 输入边界 CRS 必须明确。 |
| `raster_mosaic` | 多个栅格镶嵌。 | 需要明确重叠策略、目标分辨率和目标 CRS。 |

### 3.4 分析与统计

| 算子 | 作用 | 边界 |
| --- | --- | --- |
| `raster_band_math` | 波段计算和指数计算。 | 表达式语言、类型转换和 nodata 规则需要单独规范。 |
| `raster_statistics` | 最小值、最大值、均值、标准差、nodata 比例。 | 大栅格应支持采样或分块执行。 |
| `raster_histogram` | 波段直方图。 | bucket 策略和采样策略必须进入执行配置。 |

### 3.5 发布与瓦片

| 算子 | 作用 | 边界 |
| --- | --- | --- |
| `raster_to_tiles` | 从 COG 或原始 raster 生成 PNG / JPEG / WebP 图片瓦片。 | 不属于第一阶段 Manager 快显；后续应和矢量样式化后的图片 tile 统一到发布服务设计中。 |

## 四、与 Manager 快显的关系

后续算子可以增强 Manager，但不应反向改变当前快显主路径。

| 场景 | 当前 Manager 快显 | 后续算子可能补充 |
| --- | --- | --- |
| 小 TIFF 查看 | 前端 `geotiff.js` 全量渲染。 | 不参与。 |
| 大 TIFF 查看 | 用户显式生成 Manager 受管 COG。 | 后续可统一到 `raster_to_cog`。 |
| CRS 不可渲染 | capability 返回不可用原因。 | 可由 `raster_reproject` 生成目标 CRS COG。 |
| 多 band 复杂样式 | 当前只做基础渲染策略。 | 可由 band/style 算子或发布服务处理。 |
| 高频地图服务 | 当前不提供图片 tile。 | 可由 `raster_to_tiles` 或发布服务生成图片瓦片。 |

## 五、待讨论问题

1. `tiff_to_cog` 是否长期保留为 Manager 专用 direct 算子，还是在完整栅格算子体系中收敛为 `raster_to_cog` 的一种配置。
2. 栅格算子结果应由哪个 owner 模块登记 artifact state：Manager、Develop、Service，还是未来独立栅格模块。
3. 大栅格统计、直方图和重采样是否必须进入异步任务体系，是否允许 direct 调用。
4. 栅格图片瓦片应归入 Service 发布体系，还是作为 Manager 快显缓存的后续能力。
5. 栅格算子是否继续放在 GeoPython Workflow，还是在任务规模、依赖和资源隔离要求上升后拆出独立栅格引擎。

## 六、近期建议

短期只保留现有 `tiff_to_cog` 主路径，不新增栅格算子族。下一阶段如果要扩展，优先评估 `raster_reproject` 或 `validate_cog`，因为它们能直接补齐 CRS 不可渲染和 COG 质量诊断两个明确问题。
