# 栅格算子体系后续专题

更新时间：2026-10-05

本轮完成 GeoPython Workflow 的通用栅格计算体系、Develop 访问计划与成果适配，以及 Manager COG 调用迁移。正式契约见 `docs/spec/addp工作流计算引擎接口规范.md` 的“栅格计算契约”，对象定义见 `docs/concepts/addp术语表.md`。本专题记录实施范围、验收入口和后续边界。

## 一、范围与归属

栅格计算使用现有 GeoPython Workflow 和 GDAL，不建立独立栅格模块、成果表或任务状态。图片瓦片生成和 Service 在线地图发布不在本轮范围。

- Develop 保存用户工作流、业务目标和执行契约，复用统一执行授权、`produced_targets`、ResourceLocator 稳定输出、血缘与 Meta scan。
- Manager 继续拥有私有 `raster_cog` 快显状态、目标 `storage_ref`、清理与内容读取；它通过通用 `raster_to_cog` direct 算子生成 COG。
- GeoPython 只负责计算、写入和结果摘要。Manager 的目录型 `build_raster_mosaic` 仍承担业务数据集生成，工作流 `raster_mosaic` 承担内部栅格计算组合。
- Meta scan 仍是平台数据事实归属；算子摘要不替代扫描和目录登记。

## 二、对象与执行主路径

### 2.1 公开资源与访问计划

公开源使用 ResourceLocator，公开目标使用父目录 ResourceLocator、目标名及 `create/replace` 写入模式。Develop 在执行期分别解析、授权源和目标，再派生唯一 `addp.workflow.access-plan/v1` 协议。`raster_load` 使用 source-only，`raster_save` 使用 target-only，`raster_to_cog` 同时使用两端。任务定义和公开执行契约不保存明文连接、GDAL URI 或访问计划。

加载支持自包含 TIFF、PNG、JPEG，Develop 通过标准格式识别器从源文件名派生格式，源格式必须与实际 GDAL driver 一致。外部 sidecar 和伪装成 TIFF 的 VRT 不可作为输入；缺少 CRS 可显式补充 `source_crs`，不能覆盖冲突的已有 CRS。空间变换还要求输入具备 geotransform。输出为 `.tif/.tiff`，GeoTIFF 和 COG 是其布局 profile。

### 2.2 内部对象与成果

`RasterDataset` 是当前 execution 工作目录内的私有文件支撑对象，端口类型为 `raster`。输入必须使用当前 DAG 的 `$ref`，不能用公开 JSON、路径或跨 execution 对象伪造。加载时创建源快照；计算节点生成新文件，不改写上游对象。

`RasterRef` 不成为另一种公开资源身份。运行时只对外投影尺寸、波段、CRS、transform、四角 extent、nodata 和 overview 摘要，不输出像元、临时路径或 GDAL 句柄。

`RasterArtifact` 表达已持久化栅格及摘要。Develop 根据自己解析的业务目标建立稳定输出 locator，凭据和临时文件不进入成果引用。Manager 的私有快显目标仍由 Manager 管理。

### 2.3 生命周期

GeoPython 复用 common-python `WorkflowRunner` 的 DAG、引用及多端口处理，复用 `ExecutionRegistry` 的异步状态。`POST /api/workflow` 接受合法授权后返回 202，通过标准 execution 接口回查。部署采用单 worker、多线程，以保证进程内 execution 状态可查询；目录型镶嵌的 GDAL 全局配置操作串行化。

成功和失败均释放执行工作目录。当前公共协议没有主动取消接口，不宣称支持取消。需要跨进程状态持久化时应改进公共执行核心，不建立栅格专用状态旁路。

## 三、已实现的 13 个通用算子

| 算子 | 输入及配置 | 结果与约束 |
| --- | --- | --- |
| `raster_load` | source-only 访问计划、可选 `source_crs` | 内部 raster 源快照。 |
| `raster_save` | raster、target-only 计划、GeoTIFF/COG profile | 持久化成果摘要；COG 发布前做结构校验，转换失败不覆盖目标。 |
| `raster_info` | raster | 尺寸、band dtype/nodata、CRS、transform、四角范围及 overview。 |
| `validate_cog` | raster | GDAL 完整布局校验的 valid、warnings、errors；不靠扩展名或 tiled 标记判断。 |
| `raster_to_cog` | source/target 计划、转换选项 | 唯一通用 COG 转换入口，支持 workflow/direct；旧 TIFF 专用入口删除。 |
| `raster_build_overviews` | raster、递增倍率、算法 | 新栅格金字塔，不改写源。 |
| `raster_reproject` | raster、目标 CRS、可选分辨率、算法 | 新栅格；源 CRS 与空间定位必须有效。 |
| `raster_resample` | raster、尺寸或分辨率、算法 | 两种目标网格配置互斥。 |
| `raster_clip` | raster、bbox 或 GeoJSON Polygon/MultiPolygon、边界 CRS | 转换边界、检查交集；面裁剪保留 alpha，Float64 数据波段以 NaN 传播边界外、孔洞及源无效像元；拒绝复数波段。 |
| `raster_mosaic` | 两个 raster、目标 CRS/分辨率、first/last、算法 | 可串联处理多个输入；共同网格，Float64 输出，空白区域为 NaN；拒绝复数波段。 |
| `raster_band_math` | raster、受限表达式 | Float64 单波段；每块最多 512×512，传播 mask、nodata 和无效计算。 |
| `raster_statistics` | raster、从 1 开始的 band | 按块全量累计 min/max/mean/总体标准差、有效/无效计数与比例；全无效时统计值为 null。 |
| `raster_histogram` | raster、band、bins、可选范围 | 按块全量计数，返回 edges/counts、有效/无效和范围外计数。 |

除 `raster_to_cog` 外，通用栅格算子只支持 workflow。波段表达式允许 `b1/b2/...`、常量、加减乘除、有限常数幂，以及 `abs/sqrt/log/minimum/maximum`；拒绝属性访问、索引、导入和任意 Python 执行。数值分析使用 Float64，不承诺大整数的逐位精度。COG 编码统一复用一个 GDAL 实现，压缩允许 DEFLATE/LZW/ZSTD/NONE，块大小为 128–4096 内的 16 倍数。

## 四、工作流使用

Develop 中选择 GeoPython Workflow，添加 `raster_load` 并从资源树选择源 TIFF/PNG/JPEG，连接重投影、裁剪或波段计算，再连接 `raster_save`。保存节点选择业务存储目录、目标文件名、写入模式和 profile。两个加载节点可分别连接到 `raster_mosaic` 的两个 raster 输入。表格、矢量、普通 object 与 raster 不可随意互连。

发布或调度工作流时，执行契约只开放已保存的公开配置和资源选择。内部栅格引用不成为调度输入；稳定资源输出来自保存节点。`raster_info`、统计等 JSON 结果可在执行结果中查看，不被伪装成持久化资源。

Manager 大 TIFF 快显继续通过显式任务生成私有 COG；普通查看不隐式触发重投影、分析或业务保存。相关规则见 `manager/docs/快显实现规范.md` 和 `manager/docs/tables/raster_cog表.md`。

## 栅格资源配置方案（2026-10-05，控制面归属已确认）

用户已确认 System 引擎实例管理拥有资源策略与租户额度，GeoPython 只应用策略并执行。并发与等待容量作为可配置默认值，允许平台或租户管理员在各自范围内修改；资源情况为配置提供参考。“同时运行 2 项、最多等待 2 项”作为初始默认策略，等待容量尚没有规模实验依据。256 MiB 块缓存是已测链路的初始预算，不是进程总内存上限。以下方案进入实施；完成状态仍以实现和门禁证据为准。

现有配置规范已有 `platform_only` 和 `platform_default_with_tenant_override`，可以沿用管理员授权、版本更新、有效值来源与生效方式。配置不进入任务算子参数，不增加数据库、System 下发值和环境变量互相回退的路径。GeoPython 所在的 `engines/` 不拥有 ADDP 业务配置、数据库和控制面；System 也不能以通用配置表代存其他 owner 的业务策略。因此必须先明确本次管理的是引擎实例资源策略，而不是把栅格业务配置直接放入 Runtime。

System 在已有 Engine Instance 管理边界内拥有强类型的栅格运行资源策略及本实例的 Tenant 使用额度，复用 Console 现有 System 模块入口，在“栅格资源配置”（`/system/engine-raster-policies`）呈现；不将容量塞进 `connection_info` 或静态 `capabilities`，不新建独立管理模块。内置引擎的通用更新接口仍禁止修改核心连接配置；资源策略使用独立的强类型读写契约，不改变连接地址和引擎身份。

| 配置 | 初始默认值 | 修改范围 | 含义 |
| --- | ---: | --- | --- |
| 单个 Runtime 进程栅格运行上限 | 2 | 平台管理员 | 所有 Tenant 的 workflow/direct 合计共享，不是每租户各获 2 个槽位。 |
| 单个 Runtime 进程工作流等待上限 | 2 | 平台管理员 | 只有有界等待中的工作流占用此额度；满额请求明确返回繁忙，不创建 Runtime execution。 |
| 进程 GDAL 块缓存预算 | 256 MiB | 平台管理员 | 整个进程共享，不提供 Tenant 覆盖，不等同于 RSS 或容器内存限制。 |
| Tenant 栅格运行额度 | 继承平台默认 2 | 有配置 Permission 的当前 Tenant 管理员 | 可在平台声明的上限内修改；运行仍受进程共享上限约束，不保证独享资源。 |
| Tenant 工作流等待额度 | 继承平台默认 2 | 有配置 Permission 的当前 Tenant 管理员 | 可在平台声明的上限内修改；各 Tenant 等待总数仍受进程共享上限约束。 |

执行级只占用一次运行额度：含栅格算子的混合工作流在执行前占用，direct 同步调用按同一额度立即准入或返回繁忙，不转成异步任务。目录镶嵌 `build_raster_mosaic` 同样消费栅格资源，但其当前算子分类是 `FORMAT_CONVERSION`；实现不能仅按 `RASTER` 分类或算子名前缀推断资源需求。其 Manager 业务职责、内部 leaf 并发和 `num_threads` 保持独立，执行数量上限不能替代内部线程预算。等待中的工作流不提前下载、建立私有工作目录或打开 GDAL 对象。复用公共 `WorkflowRunner/ExecutionRegistry`，不复制执行核心，不新增平台任务表或状态查询路线。

资源信息第一步只产生建议值，明确标注采样时间、适用 Runtime 实例、有效 CPU/内存约束和推导依据，由管理员选择是否采用。容器的 CPU 配额、允许 CPU 集合和内存限额需要纳入，不能只读取宿主机逻辑 CPU 与总内存；采样失败标注不可用，不伪造建议。瞬时空闲内存和已有 execution 的资源消耗不能直接生成安全并发保证，本机平均重采样链也不足以估算所有算子的单任务峰值。首版不做随负载自动扩大/缩小容量，不把监测事实变成第二配置源；后续自动调节需有覆盖实际算子组合的预算模型再讨论。

运行与等待上限建议采用版本化热更新：缩容不取消已受理或运行的工作，已有等待不丢弃，在新约束允许时继续领取；超过新等待上限时拒绝新入队。必须区分已保存版本与 Runtime 实际应用版本。缓存建议采用 `restart_required`，页面显示待重启生效，由用户按标准生命周期操作；不在每次 execution 中切换共享 GDAL 缓存，也不由 AI 自行重启服务。平台和 Tenant 修改均需要 owner API 再次校验 AuthContext、精确 Permission、版本与字段范围，并记录脱敏审计；Tenant 不能扩大进程总容量或修改其他 Tenant 的额度。
