# 快显当前问题与改造思路

> 状态：next 改造跟踪文档。本文记录当前已知问题、根因判断和下一步改造顺序。稳定概念见 [01-概念总览](01-概念总览.md)，规范和技术路线见 [02-规范与技术路线](02-规范与技术路线.md)。

## 一、整理结论

原 `docs/next` 根目录下快显相关文档已经混合了概念原则、表结构、API、调研记录、历史清理清单和具体问题排查，阅读成本过高。

本轮收敛为三层文档：

1. 概念层：说明价值、概念、分工、边界与协作。
2. 规范层：说明表结构、API 和内部技术路线。
3. 改造层：记录当前问题和下一步实施思路。

旧专题文档不继续保留为并行来源。后续所有快显相关 next 设计以本目录为入口。

## 二、当前已收敛的事实

1. `manager.quick_view` 只保存用户预览模式偏好。
2. `manager.tile_cache` 保存瓦片缓存结果状态。
3. `manager.tile_cache_tasks` 保存瓦片缓存生成任务定义。
4. `tile_cache_generation` 是任务类型。
5. MVT 是瓦片格式，不是任务类型。
6. 快显能力由 API 动态合成，不写回 `quick_view`。
7. 预览页发起生成时必须跳转瓦片缓存页面的“任务”tab，先创建任务定义，再执行。
8. 普通预览和普通瓦片请求不得隐式执行准备动作。
9. 源 spatial extent 是源事实，快显和瓦片缓存需要独立渲染事实。

## 三、当前已知问题

### 1. 大表快显定位不到真实范围

现象：

`public.dltb` 实际范围在广西，但切换快显后地图停留在默认视图。

根因：

1. Meta 中保存的是源 CRS extent，`dltb` 为 EPSG:2360。
2. Capability 当前没有返回可供 Web 地图消费的 WGS84 `quick_view.extent`。
3. 前端没有有效 extent 时只能使用默认视图。

判断：

这不是源数据范围错误，而是缺少低成本的派生渲染范围。

### 2. 动态 MVT 局部缺块且不再重新生成

现象：

手动移动到真实范围后可以看到动态 MVT，但局部缺块，部分瓦片后续不再重新生成。

根因：

1. 低层级大范围瓦片可能命中海量面要素，生成超过交互预算。
2. 后端超时后当前可能返回 `200 + 空 body`。
3. 前端会把空 body 视为成功加载的空瓦片，OpenLayers 后续不一定重新请求同一瓦片。

判断：

必须区分真实空瓦片和超时/降级瓦片。动态 MVT 可用于局部浏览，不应承担全部低层级全幅浏览压力。

### 3. 瓦片缓存任务默认层级不合理

现象：

从预览页跳转生成瓦片缓存时默认层级为 `0-18`。

根因：

1. 表单仍有硬编码默认值。
2. 跳转上下文带的是源 extent 和源 SRID。
3. 当前没有统一的层级推荐事实。

判断：

`min_zoom` 应面向全幅显示，`max_zoom` 应处在缓存和动态 MVT 的责任边界。固定 `0-18` 对大数据量面数据不可接受。

### 4. 动态预览和缓存生成路线不完全一致

状态：已改造。缓存生成执行阶段已复用动态 MVT 的可索引 3857 目标解析；非 3857 源表缺少可索引 3857 目标时，任务失败并记录原因，不再默认回退源表 `ST_Transform` 路径。

现象：

动态 MVT 已收紧到可索引 3857 目标，但瓦片缓存生成仍可能回到源表 SQL 内 `ST_Transform` 路径。

风险：

对非 3857 大表，源表 `ST_Transform` 会带来高成本生成压力，也与动态 MVT 的能力判断不一致。

判断：

缓存生成主路径也应复用可索引 3857 目标。准备动作应在任务执行中显式授权。

### 5. 命中瓦片缓存后浏览器放大或平移崩溃

状态：已改造。后端生成默认从 `extent=1024` 起步，超过大小阈值后降到 `512`、`256`；最小 extent 仍超限的瓦片不入缓存。前端降低矢量瓦片缓存和并发加载，并在 MVT 解码前设置解压后大小阈值。

现象：

瓦片缓存快显初始效果正常，但放大或移动后浏览器崩溃。

根因：

1. 大范围低层级瓦片可能命中数百万面要素。
2. 个别瓦片 gzip 后仍达到几十 MB，解压后可接近百 MB。
3. 浏览器在 `MVT.readFeatures` 阶段需要解码几何和属性，内存峰值远高于网络传输大小。
4. 重复生成任务刷新了对象存储后，Redis / 内存运行时缓存仍可能保留旧大瓦片。
5. 仅依赖前端缓存不能解决问题，必须限制单瓦片可消费体积，并在结果刷新时同步失效运行时缓存。

实测样本：

`z8/205/111` 使用不同 `extent/buffer` 的原始 MVT 体积约为：

| extent / buffer | 原始 MVT 体积 |
| --- | ---: |
| `2048 / 64` | `61MB` |
| `1024 / 32` | `24MB` |
| `512 / 16` | `7.9MB` |
| `256 / 8` | `2.0MB` |

判断：

降低 `extent` 能显著降低瓦片体积，但不能减少命中要素数。超大瓦片保护必须同时包含后端生成阈值和前端解码阈值。

### 6. 同一页面多次缩放平移后局部瓦片消失

状态：已改造并验证通过。前端不再在地图正常缩放/平移期间主动取消 OpenLayers 管理中的瓦片请求，只在组件卸载时清理未完成请求。

现象：

MinIO 中对应 MVT 瓦片对象存在，另开一个预览页面查看同一位置也能正常显示；但原页面多次缩放、平移后，局部区域不再显示。

根因：

1. 前端曾在 `movestart` 中按 zoom 主动 abort 不同层级的瓦片请求。
2. 被 abort 的 OpenLayers source tile 没有进入 `LOADED` / `ERROR` / `EMPTY` 终态，可能停留在 `LOADING`。
3. 该 tile 对象被当前页面的 VectorTileSource 缓存后，同一页面回到该位置不一定重新发起请求。
4. 新开页面会重建 source 和 tile 状态，因此能正常显示。

判断：

OpenLayers 的 tile 生命周期应由 OpenLayers 管理。前端可以在组件卸载时清理未完成请求，但不应在正常交互过程中绕过 source 生命周期主动 abort；否则会形成当前页面内的运行态假空白。

## 四、下一步改造顺序

### P1：统一渲染事实

目标：

建立单一内部事实链，供 capability、快显初始定位和瓦片缓存任务默认值共同消费。

工作项：

- [ ] 新增内部 `SpatialRenderFacts` / `QuickViewRenderFacts` 构建路径。
- [ ] 事实中区分源 extent 和渲染 extent。
- [ ] 从 ready `tile_cache` 或已有 3857 派生产物轻量获取 WGS84 渲染范围。
- [ ] 缺少可靠渲染范围时返回 `manual_required`，不扫源大表。
- [ ] 补测试覆盖 4326、3857、非 4326/3857 且有 3857 派生产物、缺少派生产物等场景。

验收重点：

`public.dltb` 的 capability 能给出广西 WGS84 渲染范围，快显初始视图不再落到默认位置。

### P2：层级推荐和任务表单默认值

目标：

瓦片缓存任务创建态不再固定 `0-18`。

工作项：

- [ ] 后端基于 render facts 输出 `zoom_recommendation`。
- [ ] `min_zoom` 按全幅显示语义推荐。
- [ ] `max_zoom` 按缓存与动态 MVT 边界推荐。
- [ ] 预览页跳转仍快速打开，任务页可异步轻量补齐推荐事实。
- [ ] 前端展示推荐状态和原因，`manual_required` 时要求用户确认。

验收重点：

千万级面数据不再默认 `0-18`；缺少可靠范围时不硬算。

### P3：动态 MVT 空瓦片语义

目标：

前后端区分真实空瓦片和超时/降级瓦片。

工作项：

- [x] 后端 MVT 响应增加 `X-ADDP-Tile-Status`。
- [x] 超时返回 `timeout`，保护性降级返回 `degraded`。
- [x] 查询成功但无数据返回 `empty`。
- [x] 前端对 `timeout/degraded` 不永久标记为真实空瓦片。
- [ ] 增加冷却、重试或提示策略，避免无限重试压垮后端。

验收重点：

低层级超时瓦片不再造成永久块状缺失。

### P4：缓存生成执行路径复用 3857 目标

目标：

动态 MVT 和瓦片缓存生成共享同一套可索引 3857 目标判断。

工作项：

- [x] 缓存生成任务执行阶段解析 `tile_target_3857`。
- [x] 非 3857 源表优先使用准备好的 3857 派生产物。
- [ ] 缺少派生产物时，根据任务配置和授权执行准备动作。
- [x] 不在大表主路径中默认回退源表 `ST_Transform`。
- [x] execution metadata 记录实际生成目标表、几何列、SRID 和是否为 prepared 3857 target。
- [ ] execution metadata 继续补齐准备动作、范围、层级和降级原因。

验收重点：

非 3857 大表的缓存生成不再走不可控源表转换路径。

### P5：MVT 单瓦片体积保护

目标：

瓦片缓存和动态 MVT 不再产出或解码浏览器不可安全消费的巨型瓦片。

工作项：

- [x] 默认 MVT extent 从 `1024` 起步。
- [x] buffer 随 extent 递减，使用 `extent/32`，限制在 `8-64`。
- [x] 缓存生成开启默认优化配置，单瓦片原始 MVT 阈值为 `4MB`。
- [x] 超阈值瓦片按 `1024 -> 512 -> 256` 动态降级。
- [x] 最小 extent 仍超限时跳过该瓦片，不写入缓存。
- [x] 前端 VectorTile `cacheSize` 降到 `64`。
- [x] 前端地图 `maxTilesLoading` 降到 `8`。
- [x] 前端解码前限制解压后 MVT 大小，默认 `8MB`。
- [x] 前端正常缩放/平移期间不再主动 abort OpenLayers 管理的瓦片请求。
- [x] 重复执行已有缓存任务时先清理旧对象前缀，避免旧瓦片全量命中导致假刷新。
- [x] 重复执行或删除已有缓存结果时，按 `tile_cache:{id}` 自动清理 Redis 和内存 LRU 运行时瓦片缓存。
- [ ] 后续可在 manifest 或 execution metadata 中统计 `oversized_skipped_tiles`。

验收重点：

已有异常缓存或新生成缓存中出现超大瓦片时，前端不会因 MVT 解码导致浏览器崩溃；新生成缓存不再写入超过保护阈值的巨型瓦片。

### P6：瓦片缓存任务统计

目标：

让瓦片缓存任务结束后能直接回答“预计处理多少瓦片、实际处理多少、生成多少、空多少、失败多少、瓦片大小如何”。

工作项：

- [x] execution metadata 记录 `tiles_total_estimate`、`tiles_processed`、`generated_tiles`、`empty_tiles`、`skipped_tiles`、`failed_tiles`。
- [x] execution metadata 记录 `total_size_bytes`、`max_tile_size_bytes`、`min_tile_size_bytes`。
- [x] execution metadata 记录 `zoom_levels` 分层统计。
- [ ] 继续细分被体积保护跳过的瓦片数，例如 `oversized_skipped_tiles`。
- [x] 前端任务详情页展示核心统计摘要。

验收重点：

瓦片缓存任务不只显示成功/失败和百分比，还能看到基于瓦片个数的执行结果摘要。

## 五、建议实施批次

第一批：

1. P1 统一渲染事实。
2. P2 层级推荐和任务表单默认值。

这批优先解决定位错误和默认层级错误，风险较小，收益直接。

第二批：

1. P3 动态 MVT 空瓦片语义。
2. 前端冷却和重试策略。

这批处理交互细节和缺块问题，需要前后端一起改。

第三批：

1. P4 缓存生成执行路径复用 3857 目标。
2. P5 MVT 单瓦片体积保护。
3. 准备动作和 execution metadata 收敛。

这批影响生成执行主路径，适合在前两批事实链稳定后推进。
