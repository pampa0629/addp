## 二、当前能力边界

目录主线保持：Meta 持久化 DataItem → Catalog 自动建立企业身份并维护业务关联与责任 → Asset 组合、发布 → Portal 消费。来源变化按 owner 日志与独立 checkpoint 恢复；Manager 提供技术资源浏览、预览、剖析与内容检索。旧 discoverable、Meta AssetRecord、Asset 自动发现及通用 source_reference 路线已删除，不恢复双轨来源。

| 能力 | 当前边界 |
| --- | --- |
| 企业目录基础 | 已具备自动建档、原子编目、显式来源重绑、不可变历史、四轴状态、目录可见性及独立搜索投影。 |
| 组织与治理 | 已具备责任维护、失效治理队列、我的目录、Project Group 集合、治理覆盖率及当前页显式成员批量分配；不新增统一 Workspace。 |
| 专业资源与关系 | 已接入专业 owner 的稳定资源；当前专业事实、质量摘要、血缘及模型关系动态联邦读取，不复制专业定义或关系边。具体接入类型以 Catalog 实现规范为准。 |
| 标准映射与字典 | 已具备人工候选、独立审核与版本控制；字典只组合 Meta 当前字段、已审核 StandardMapping 及冻结的 ElementRevision。人工接口可用不表示 Copilot 已接入。 |
| 源数据授权 | System 唯一维护精确逻辑目标的批准要求、不可变 Grant 与 Deny；独立批准与 Catalog 业务确认共享规则存储和读取裁决。责任、功能 Permission、管理资格和内容读取权分别核验；批准方式的初始化及显式切换不等于授予读取权。 |
| Manager 读取与剖析 | PostgreSQL 受控读取及后台独立执行授权已接线；剖析首版只支持已扫描普通单表，逐页与提交前检查当前源规则和本地保护。视图、多来源及源端并发 DDL 的增强不在首版通过范围。 |
| 搜索与结构命中 | 技术与正文分别幂等更新、相互保留；MongoDB 漏投递及真实命中字段展示已完成本轮功能验收。所有 Catalog 扫描与刷新策略接入技术投影，不等于历史全部补录或全部非表结构可搜索。 |
| 搜索基础设施 | 新版本独立导入和正式新卷切换已完成；旧卷、旧镜像与备份仍保留。迁移成功不替代 Owner 权限、保护或外部服务故障验收。 |

以上是能力范围，不是全平台验收通过声明。已有真实 PostgreSQL 预览允许／拒绝体验，以及 MongoDB 搜索和字段展示证据；剖析、完整授权办理、各引擎历史覆盖及隔离故障验收仍分别完成下列清单。

## 三、剩余工作

### 3.1 企业目录与标准映射

- [ ] 在专用环境完成 StandardMapping“人工候选 → 审核 → 已审核字典 → 认证时映射版本证据”的真实业务闭环，不在共享开发库为填满页面制造业务事实。
- [ ] Copilot 提交候选尚未接入；先确定真实 Service Principal、候选权限与证据契约，AI 只能提交候选，不能直接审核为权威映射。
- [ ] 使用普通读者、治理者及有 Project Group membership 的真实身份，核对默认入口、盘点权限、我的目录、项目集合名称与菜单优先级；不以管理员账号替代全部角色验收。
- [ ] 补验至少两个业务域、零资源域、切域后的迟到响应，以及 Standard/Quality 权限不足或不可达时的独立区域状态；核对 Model/Quality 专业导航，不把局部只读点击记为完整验收。
- [ ] 域级治理覆盖率、域级反向关系汇总和关联已发布资产暂不实施。需要这些能力时先确认 owner 查询、权限、适用对象、子域和跨域计数口径，不按同域共现推断关系或把全局数字改名。

### 3.2 源数据授权与正常使用闭环

- [ ] 在已确认账号和精确普通表范围内，完成独立批准路径的真实授予、接收方读取及收回后无其他有效授权来源时的拒绝；实际功能权限和引擎管理资格由有权主体显式安排，不从角色名推导。
- [ ] 使用同一接收账号完成已授权表的剖析创建、Worker 执行及结果查询，再核对未授权表、到期、撤销与 Deny 拒绝。已有预览允许／拒绝证据不代替后台剖析验收。
- [ ] 在既有 `enterprise-catalog-publishing` 中完成 Catalog 业务确认 → System 首次受理 → 自动签发 → 原参数恢复的真实 OAuth 验收，分别报告决定、受理、签发及实际读取，不将历史签发显示为当前 Allow。
- [ ] Develop 完整 QueryReadSet、扫描执行、Quality、Transfer、其他引擎及其他内容出口按实际消费者逐项贯通同一源授权契约；没有相应完整范围与运行凭据证明前，不借整库连接或 Service 身份放行。
- [ ] PostgreSQL 准备后源端并发改源问题保留为共享 Provider 的后续增强；不作为首版普通单表体验前置，也不宣称首版已证明原生事务内依赖冻结。

### 3.3 搜索覆盖与故障恢复

- [ ] 其他引擎历史 DataItem 的正式投递覆盖仍需盘点。缺少投递记录不直接证明当前索引无文档；补录须明确范围、成本和正式入口，不自动扩大扫描或重建索引。
- [ ] Neo4j 图标签、关系和属性结构尚未成为可检索投影；如有真实检索需求，先定义非表结构事实白名单及命中解释，再实现，不能套用关系表字段假设。
- [ ] NFS 手动扫描出现 `meta.execution.lease_expired_recovery_required`，根因与恢复尚未完成。先检查 execution、Worker 租约及部分元数据／投递，再确定精确重试范围，不把失败执行视为成功，也不直接全量重扫。
- [ ] 新版本真实“已接收但响应丢失 + 进程退出”故障验收仍未完成：恢复须认回同一原任务、提交次数不增加，历史不足或冲突继续隔离。HTTP 夹具与 PostgreSQL T2 不替代此 T4。
- [ ] Manager/Catalog/Asset 的当前租户、可见性、上架及保护负例按各 Owner 补证；Asset 搜索仍有索引估计总数及权威复核后不足一页的边界，可靠普通投递与精确分页留待该 Owner 的独立范围。
- [ ] 多 Backend／HA 回执与恢复认证独立安排，不从单实例运行成功外推。

### 3.4 相关消费链路

- [ ] Agent 搜索零召回已解除，但“先建任务、不要运行”的完整 Transfer 创建验收仍待推进：最近失败为 `platform_condition_unsatisfied:platform_context`。由 Agent/Ontology 主线完成 Runtime 上下文读取与条件校验，不再扩大本轮 Meta/Manager 修复；对应契约见 [Ontology 最小设计契约](ADDP%20Ontology最小设计契约.md)。
- [ ] 统一语义查询、计划编译和指标执行仍需端到端用例验证，Catalog 只承担企业身份、语义关联、治理及发现，不代替语义执行。具体业务闭环按 Outdoor 专题推进，不复制指标定义或提前新增 Semantic Runtime。

## 四、验收与维护方式

目录的真实运行验证继续复用已登记 `enterprise-catalog-publishing`：自动建档、编目、责任失效、标准映射、治理生命周期、资产发布与 Portal 消费沿各 owner 契约取得证据。停机追赶、来源 missing、显式重绑、System 恢复、owner 不可达及外部索引故障只在明确的隔离环境和操作窗口验证，不接管共享开发服务。

- 工作区总门禁使用 `make test-changed`；明确 owner 时使用 `make test-module MODULE=<模块>`，局部门禁通过不等于总门禁通过。
- PostgreSQL 测试先运行 `bash scripts/infra/status.sh` 核对实际端口，标准入口只使用 `addp_test` 或 `addp_iam_test`；专用 T4 使用已登记的 User、Tenant 和受控夹具，不擅自改变真实账号或业务资源。
- 按“通过、失败、未运行”分别交付结果。总门禁失败或测试条件不齐时不得宣称工程收口；以当前工作区复验，历史日志和某轮已通过结果不作为新改动的统一证据。
- 实际扫描、补索引、源授权配置、业务编目写入及故障操作先明确对象和影响范围。服务重启由用户操作；检索修复不包含 Transfer 执行或 Outdoor 业务数据写入。

后续只更新上面的能力边界与未完成项：稳定规则进入对应正式文档，完成的工作从待办移除，测试结果在当前交付与 CI 中报告，不再按日期追加实施长文。
