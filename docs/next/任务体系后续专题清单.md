# 任务体系后续专题清单

> 状态：专题入口。本文承接 `任务体系统一设计.md` 主干验收后尚未进入既有专题文档的剩余问题。已有专题的内容不在本文重复展开：Transfer 见 `transfer任务语义与同步模式设计.md`，MVT / QuickView 见 `../../manager/docs/快显问题与改造思路.md`，cleanup 见 `meta-cleanup边界与派生产物清理设计.md`。

## 一、Manager embedding 专题

正式文档：[Manager 向量化能力说明](../../manager/docs/向量化能力说明.md)

任务体系主干已经完成：

- Manager 作为单一 provider 声明 `tile_cache_generation`、`quick_view_optimization` 和 `embedding`。
- `manager.quick_view_optimization_tasks` 作为快显性能优化任务定义进入 TaskProvider，结果状态进入 `manager.quick_view_optimization`。
- `manager.embedding_tasks` 作为持久化向量化任务定义进入 TaskProvider。
- 持久化 embedding 任务执行复用任务服务创建的主 execution。
- ad-hoc embedding 只作为 ad-hoc execution，不产生 owner 任务定义。
- 内存 `TaskTracker` 已移除；状态入口统一为 `common.task_executions` 和 `manager.embeddings` artifact state。
- 持久化 `embedding`、`tile_cache_generation` 和 `quick_view_optimization` 执行已在 `common.task_executions.execution_config` 写入任务配置快照，用于 Monitor 追溯单次执行，不替代 owner 任务定义或 artifact state。

主线已沉淀到 Manager 正式文档。剩余问题不再放在 embedding 专题内悬置：

1. cleanup 和跨派生产物 lifecycle 见 [meta-cleanup 边界与派生产物清理设计](meta-cleanup边界与派生产物清理设计.md)。
2. 资源树按 locator 展开任意深度祖先链见 [资源树 locator 祖先链定位 API 专题设计](资源树locator祖先链定位API专题设计.md)。
3. 失败重试、取消、中断恢复是否进入标准 TaskProvider 能力，继续归入 TaskProvider capabilities 和具体 worker 可中断能力专题。

## 二、Develop 专题

任务体系主干已经完成：

- Develop 对外只声明 `query` / `workflow` / `script` 三类任务。
- Notebook 是 `script` 的当前 UI 和运行时形态，不是独立 `task_type`。
- `/develop/tasks` 是任务定义集散页和列表页，不作为 TaskProvider 创建或编辑目标。
- TaskProvider `create_url` / `edit_url` 已指向查询工作台、工作流编辑器和脚本开发页面。
- TaskProvider 执行入口已校验路径 `task_type` 与真实 `DevTask.dev_type` 一致。
- `query` / `workflow` / `script` 的 `definition_schema` 已细化为公开摘要 schema，仅用于跨模块展示和理解，不用于 Orchestrator 渲染完整 owner 表单。
- Develop 的 `execution_schema` 当前保持开放对象；运行时参数由具体 DevTask 的 `parameter_schema` / `default_parameters` 决定，执行时合并后的参数写入 `common.task_executions.execution_config.inputs`。

后续专题需要继续收敛：

1. query、workflow、script 三类专属页面的深层编辑体验。
2. script / Notebook runtime 如何访问 ADDP 管理的数据、凭证和执行上下文。
3. workflow 算子编排、算子运行时和 TaskProvider `workflow` 任务之间的边界。
4. 临时执行、保存为任务、发布为可编排任务之间的用户路径。

## 三、Monitor 专题

专题文档：[Monitor provider health 与 capabilities 漂移专题设计](Monitor%20provider%20health与capabilities漂移专题设计.md)

任务体系主干已经完成：

- Monitor 按 `execution_id / parent_execution_id` 构建执行树。
- 各模块拿到统一 `execution_id` 后可通过 `openMonitorExecution(execution_id)` 跳转 Monitor。
- Monitor 执行详情通过 TaskProvider capabilities 的 `edit_url` 回跳 owner 任务定义。
- provider health 第一阶段已实现：从 System 读取启用 TaskProvider，复用模块 `/health` 与标准 `GET /tasks?task_type=` 探测模块心跳、capabilities 基础结构和任务发现可调用性。
- Dashboard 的模块健康已接入 provider health，可展示 `up/degraded/down/unknown`、task discovery 数量和 capabilities 异常提示。

后续专题需要继续收敛：

1. 调度健康：owner scheduler 的 enabled、next_run_at、last_run_at、漏跑和多实例 claim 状态。
2. 队列健康：Asynq / Redis / DB claim 的 pending、active、retry、dead、延迟和积压。
3. 产物健康：QuickView、MVT tiles、embedding、Graph build material 等 artifact state 的可用性。
4. provider health 历史化、告警阈值、批量编排健康检查和 capabilities 漂移详情页。
5. Transfer 私有 progress / logs / queue 信息如何投影到 Monitor。
6. cleanup 如果进入统一 execution，应作为系统运维执行记录展示，不能成为可编排任务。

## 四、TaskProvider capabilities 专题

专题文档：[TaskProvider capabilities 专题设计](TaskProvider%20capabilities专题设计.md)

任务体系主干已经完成 `task.capabilities/v1` 基线：

- provider 按模块注册，通过 `task_types[]` 声明多个任务类型。
- `task_type` 必须是稳定小写下划线标识。
- `definition_schema` 和 `execution_schema` 当前必须是对象 JSON Schema。
- `supports_inline_execution` 当前必须为 `false`。
- `supports_cancel` 与 provider 顶层 `task_cancel_endpoint` 必须双向一致。
- `create_url` / `edit_url` 必须是 Console 相对 owner URL。

专题已经把以下问题拆入独立设计：

1. `definition_schema` / `execution_schema` 的字段、required、enum、默认值和版本演进规则。
2. 前端表单 schema 是否复用 JSON Schema，还是增加 UI schema。
3. 标准取消执行能力的真实契约：worker 可中断、资源可清理、状态可一致落库。
4. inline execution 是否需要进入 v2；如果进入，必须先定义 endpoint、执行配置 schema 和 Orchestrator Step 模型。
5. capabilities 版本演进和 deprecated task type 的 clean break 处理策略。
6. provider capabilities 缓存刷新、漂移检测和运行态告警。

专题当前已确认：

1. `definition_schema` 只作为跨模块公开摘要和轻量展示，不用于 Orchestrator 创建、编辑或渲染完整 owner 任务定义。
2. deprecated task type 不再作为可用任务类型处理；保存和执行编排时都直接拒绝引用，不做兼容迁移。
3. provider health 第一阶段复用模块 `/health` 与标准无副作用 `GET /tasks?task_type=` 探活，不新增 TaskProvider 专用 health endpoint。
4. provider 顶层私有扩展字段必须统一 `x_` 前缀，避免与未来标准字段冲突。
5. Monitor provider health、capabilities 漂移视图和批量编排健康检查并入 Monitor 专题，不继续放在 TaskProvider capabilities 专题内悬置。

## 五、Orchestrator 后续边界

任务体系主干已经完成：

- Step 固定引用 `provider + task_type + task_id`。
- 保存编排时校验 provider 和 task_type 已由 capabilities 声明，且不得引用 deprecated 类型。
- 执行时按 `depends_on` 先执行前置依赖，再执行当前步骤。
- Orchestrator 自身以 `task_type=orchestration` 暴露，可被其他编排引用。
- 编排引用编排时已做自引用和多层循环引用防护。
- 参数模板已收敛为完整字符串引用 `{{step_id.field.path}}` / `{{step_id}}`；引用的 step 必须在 `depends_on` 中显式声明，运行时路径缺失会导致当前 Step 失败。
- v1 Step 只支持 `provider + task_type + task_id` 任务引用，不支持内联执行。
- v1 明确不支持并行执行、分支或条件、Step 级重试策略、人工确认步骤，也不允许通过私有 Step 字段提前打开这些控制流能力。
- Orchestrator 节点配置抽屉已提供 owner 任务定义跳板；编辑入口来自 TaskProvider capabilities 和标准任务发现结果，仅作为前端运行态上下文使用，不写入 Step 持久化 JSON。

后续专题需要继续收敛：

1. 如后续需要并行执行、分支或条件、重试策略、人工确认步骤，应进入 Orchestrator 执行模型 v2 专题，先定义状态机、失败语义、资源隔离、审计、UI 表达和迁移边界。
2. owner 任务定义跳板后续可继续优化为 Console 内部导航，但不得改变 Orchestrator 不创建、不保存 owner 私有任务定义这一原则。

## 六、Graph / Quality 后续观察项

Graph 和 Quality 已按任务体系主干接入，但内部业务仍可能在专题中继续深化。

当前已确认：

- Graph `kg_build` 和 Quality `check` 的 TaskProvider capabilities 顶层私有扩展已统一使用 `x_` 前缀，避免被 System 注册校验拒绝。
- Graph / Quality 当前不声明 TaskProvider 标准取消、重试或调度能力；模块内部已有取消、重跑或手动执行入口，不等于跨模块标准能力。
- 标准取消、重试或调度后续如需开放，必须先确认执行体可跨进程中断、统一 execution 状态可一致落库、Orchestrator 失败语义和 Monitor 展示口径都已定义。

后续观察项：

1. Graph `kg_build` 的 build task 状态、material 状态和 review queue 状态之间的边界。
2. Graph `build_tasks.status` 作为最近执行摘要，应继续与统一 execution status 保持一致。
3. Quality `check` 任务与规则应用、issue 生成、问题治理之间的边界。
4. Graph / Quality 如果进入标准取消、重试或调度能力，应作为独立专题设计，不在当前 TaskProvider v1 接入中通过 capabilities 布尔值提前打开。
