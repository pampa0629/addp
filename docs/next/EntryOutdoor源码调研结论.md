# EntryOutdoor 源码调研结论

> 状态：源码调研结论。本文基于对 EntryOutdoor 微信小程序源码（GitHub `pampa0629/EntryOutdoor`，master 分支，2026-08-24 下载）的通读分析，以及仓库内 `doc/outdoors` 数据导出快照（127 条 2019 年活动记录）的数据验证，对《Outdoor领域理解.md》中的待定问题和业务口径进行闭合与勘误。
>
> 说明：源码版本与生产 MongoDB 数据库（2383 条活动）并非同一时点，2019 年快照主要用于辅助验证历史数据形态。凡代码逻辑明确的地方以代码为准；快照中出现但现行代码不再写入的状态（如"报名截止"）单独标注为遗留数据问题。

## 0. 调研方法与证据来源

| 证据类型 | 位置 | 说明 |
| --- | --- | --- |

## 1. 已闭合的业务问题（原 §8）

### 1.1 领队转让后 `myOutdoors[]` 不保留 —— 证实，且比假设更复杂

原假设：转让后原人员的 `myOutdoors[]` 不再保留该活动。**代码证实，且行为是双向搬移**。

`utils/outdoor.js` `OD.prototype.transferLeader()`（约 767-805 行）在转让领队时：

1. 把新领队成员对象换到 `members[0]` 位置（**不是只改角色标记，而是物理挪位**）；
2. 原领队：从其 `myOutdoors[]` 移除该活动，并向其 `entriedOutdoors[]` **加入**该活动（成员状态改为"领队组"）；
3. 新领队：向其 `myOutdoors[]` 加入该活动，并从其 `entriedOutdoors[]` 移除。

搬移由 `utils/person.js` 的 `dealOutdoors(myOutdoors/entriedOutdoors/caredOutdoors, ...)` 统一实现，所有调用点均通过该函数操作。

结论：`myOutdoors[]` 的准确语义是"**当前担任主领队的活动**"，不是"发起过的活动"。此外：

- 活动保存为草稿（拟定中）时即写入 `myOutdoors[]`（`CreateOutdoor.js` 保存路径）；
- 活动取消（已取消）不从 `myOutdoors[]` 移除；
- 只有彻底删除活动才移除操作者本人的 `myOutdoors[]`（见 §1.2）。

### 1.2 活动删除后 `caredOutdoors[]` 保留 —— 证实，且悬空引用面更广

原假设：活动删除后人员侧收藏摘要仍保留。**代码证实，且不止 `caredOutdoors[]`**。

`pages/CreateOutdoor/CreateOutdoor.js` `deleteOutdoor()`（约 225-260 行）删除活动时只做两件事：

1. 删除 `Outdoors` 集合中的活动文档本身；
2. 从**操作者本人**的 `myOutdoors[]` 中移除该活动。

**其他成员的 `entriedOutdoors[]`、任何人的 `caredOutdoors[]` 均不清理**。也就是说：

- `caredOutdoors[]` 会悬空（原假设证实）；
- **其他报名成员的 `entriedOutdoors[]` 同样会悬空**（原文档未覆盖）；
- 占坑到期"强制退坑"（`utils/odtools.js` 约 379 行的过期逻辑）同样只改活动侧成员状态，不清理人员侧 `entriedOutdoors[]`。

应用自身预期这种悬空引用：`pages/MyInfo/MyOutdoors.js`（约 145 行）在点开收藏列表时专门判断"活动是否已被删除"再做展示兜底。

结论：**人员侧三个数组（`myOutdoors`/`entriedOutdoors`/`caredOutdoors`）全部是可能悬空的缓存索引**，"以 `Outdoors` 活动主体为准"的既定原则正确且必要，但"悬空引用仅存在于 `caredOutdoors[]`"的隐含认知需要扩大到全部三个数组。

## 2. 原文档理解有误的地方

### 2.1 ❌ `members[0]` ≠ 初始发起人（最重要）

原 §3.1、§6 将 `Outdoors.members[0]` 等同于"初始发起人"，可信度标为"高"。**这是错的**。

代码事实：转让领队时 `transferLeader()` 会把新领队**换到 `members[0]` 位置**，原发起人挪到数组后部。因此 `members[0]` 的真实语义是**当前主领队**（代码主动维护的不变式），会随转让变化。

- 初始发起事实的稳定物理表达是 `Outdoors._openid`（创建账号，转让不改变）；
- "当前主领队"用 `Outdoors.leader`（创建时即写入，转让时更新为同一人，与 `members[0]` 保持一致）。

建议修订 §3.1 表格和 §6 表格："初始发起人"一行的物理表达改为 `Outdoors._openid`（语义：创建账号），`members[0]` 改标为"当前主领队（随转让变化）"。

### 2.2 `myOutdoors[]` 语义偏差

原 §2.2 描述为"人员发起的活动摘要"。实际语义是"**当前担任主领队的活动**"（见 §1.1），随转让双向搬移；草稿计入、已取消不计删除。

### 2.3 `entriedOutdoors[]` "只要报名过就计入"不完全成立

原 §2.2 口径为"只要报名过就计入，包括替补和占坑；退出活动后不计入"。两处修正：

1. **成为主领队时该活动会从 `entriedOutdoors[]` 移除**（无论此前是否报名过），卸任转出时加回；
2. 悬空引用问题比原文档认知更普遍（见 §1.2）：强制退坑和活动删除都不清理该数组。

### 2.4 活动状态清单缺"进行中"，"报名截止"是遗留状态

原 §3.4 观察到的状态全集为：拟定中、已发布、报名截止、已成行、已取消、已结束。源码补充两点：

1. **完整状态机还包含"进行中"**：`utils/odtools.js` `getSteps()` 的步骤为 拟定中→已发布→已成行→**进行中**→已结束。"进行中/已结束"是**客户端按当前时间推导**的状态（`outdoor.js` `checkStatus`：比较当前时间与 `title.date` + `meets[0].time` / `title.during`），并非全部由服务端写入。
2. **现行代码主动写入的状态只有**：拟定中、已发布、已成行、已取消。"报名截止"在现行代码中**从不写入**——数据快照中 3 条"报名截止"记录全部是 2019 年的，属遗留历史数据。

对 §3.4 统计分类的影响：`报名截止` 被归入"成行"有风险——报名截止 ≠ 成行，可能因未成行而不了了之。这 3 条遗留记录如何归类需要业务确认（见 §4 新增问题）。

### 2.5 文档未覆盖：`addMembers[]`（附加队员）与 `aaMembers[]`（A费名单）

活动对象上还存在两个与人员相关的数组，原文档未提及：

- `addMembers[]`：领队手工添加的**附加队员**（不经小程序报名流程的人员），**不进入 `members[]`**；
- `aaMembers[]`：AA 制费用分摊名单。

对 §7.3"实际参加活动数"的影响：只按 `members[]` 过滤状态会**漏掉附加队员**。至少应在口径中明确"附加队员是否计入实际参加"，避免隐性低估。

## 3. 验证无误的部分

以下口径与代码/数据一致，维持原文档结论：

| 原章节 | 结论 | 验证证据 |
| --- | --- | --- |
| §2.1 身份字段 | `Persons._id` / `_openid` / `userInfo.nickName` 的引用关系 | `utils/person.js`、`utils/group.js` 全部按此引用 |
| §3.2 title 结构 | `level`/`date`/`place`/`whole` 等字段 | 快照 127/127 条存在；缺 `title.date` 的仅 2 条且均为草稿，与"统计有效活动"规则吻合 |
| §3.3 报名状态口径 | 六种 `entryInfo.status` 的计入规则 | 代码与快照一致；快照另见 §5 数据形态备注 |
| §3.5 route 双形态 | object / array 并存 | 快照实测 64 条 object / 63 条 array |
| §4 Groups 结构 | `groupOpenid`、`owner`、OpenID 为动态键的 `members` 映射 | `utils/group.js` 完全吻合 |
| §5 Photos | 顶层字段 `_id`/`_openid`/`faces`，活动照片索引在 `Outdoors.photos` | `utils/facetools.js` 吻合 |
| §7 指标口径 | 各指标计算方式 | 无冲突 |

补充两个小事实：

- **领队不能直接退出活动**：退出流程限制主领队必须先转让领队或取消活动；
- **主领队转让后原领队变为"领队组"成员**留在活动中（见 §1.1 第 2 条）。

## 4. 新增的未闭合问题

1. **遗留状态 `报名截止`（3 条，均为 2019 年）如何归类**：按现分类规则落入"成行"，但报名截止 ≠ 成成行，需要业务确认是归入"未成行"还是单独处理。
2. **`addMembers[]` 附加队员是否计入"实际参加活动数"**：需要业务定义（建议口径显式声明包含或排除）。
3. **客户端推导状态与存储状态混用**：`进行中`/`已结束` 部分由客户端按时间推导，历史数据中存储的 `已结束` 与推导结果可能不一致；分析"是否结束"时应统一改用 `title.date` 等事实字段（原文档 §3.4 已有此原则，此处补充证据支持）。
4. **源码时点差异**：本调研基于开源仓库 master 分支，与生产库当前数据（2383 条活动，2026 年）存在时间差；2019 年快照中的历史形态（如老数据 `members[].entryInfo` 可能缺 `status` 字段，快照中 15/127 条）在生产库中可能仍然存在，建议治理 SQL 对缺字段情况做兼容。

## 5. 数据快照补充观察（2019 年，127 条）

- `status` 分布：已成行 84、已取消 22、已发布 13、拟定中 5、已结束 3、报名截止 3（无"进行中"，因为该状态不落库）；
- `leader` 字段在全部 127 条中均存在，且与 `members[0].personid` **100% 一致**（含 1 条转让过的活动也一致），印证 §2.1 的"`members[0]` 被维护为当前主领队"；
- 老数据 `members[].entryInfo` 可能缺 `status` 字段（15/127 条，多为旧结构成员，仅有 `personid` + `userInfo`）；
- 人员快照中出现过 `members[0]` 为"领队组"状态的记录（老版本数据形态），说明 `members[0]` 不变式在历史版本中曾不严格，进一步支持"以 `leader` 字段为准判断当前主领队"。
