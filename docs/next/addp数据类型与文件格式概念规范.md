# ADDP 数据类型与文件格式概念规范

更新时间：2026-05-04

本文定义 ADDP 平台中“数据是什么”“一套数据如何组成一个 meta item”“文件格式是什么”这三件事应如何建模。它是概念规范，不是实现说明。

## 总体结论

ADDP 的概念主轴应改为：

1. 存储引擎回答“数据存在哪里”。
2. 数据家族回答“数据长什么样”。
3. 组合形态回答“一套数据如何组成一个 item”。
4. 文件格式回答“单个文件如何编码”。
5. 扩展信息回答“这类数据还具备哪些附加语义”。

其中，`FieldInfo` 只属于结构化数据语义，应挂在 `TableInfo` 之下；`ObjectInfo` 不承担字段 schema 语义。

同时，`meta_item.attributes` 不应被理解为一个完全自由的 JSON 黑箱，也不应被设计成封闭的全字段强 schema。  
ADDP 的目标是全域数据平台，未来必须允许第三方扩展更多数据格式和格式私有属性，因此 attributes 应采用：

**受控核心 + 开放扩展。**

也就是说：

- 平台理解 item 所必需的核心语义必须受控。
- 具体格式和第三方插件的独有属性必须允许扩展。
- 开放扩展不能污染或覆盖平台核心语义。

## 一、概念边界

### 1. 存储引擎

存储引擎只回答资源的物理落点，例如：

- PostgreSQL
- MySQL
- ClickHouse
- MinIO
- S3
- 本地文件系统

这一层属于 `where`，不属于数据本体分类。

### 2. 数据家族

数据家族回答“数据长什么样”，是平台的主分类维度。

建议使用以下主术语：

- 表格型数据
- 图片型数据
- 视频型数据
- 文档型数据

不建议把 `table` / `object` 作为对外主术语，因为它们容易和“数据库表”“对象存储对象”混淆。

### 3. 组合形态

组合形态回答“一套数据如何构成一个 meta item”。

它是独立维度，不等于文件格式，也不等于数据家族。

典型形态包括：

- 单文件单 item
- 多文件单 item
- 容器文件单 item
- 目录树单 item
- 混合文件集合单 item

### 4. 文件格式

文件格式是具体编码形态，例如：

- `csv`
- `xls` / `xlsx`
- `parquet`
- `shp`
- `geojson`
- `gpkg`
- `pdf`
- `jpg` / `png`

同一数据家族可以对应多个文件格式。

### 5. 扩展信息

扩展信息描述某类数据的附加语义，例如：

- 空间信息
- 采样推断信息
- 媒体元信息
- 页面/页数信息
- 索引信息
- 编码信息

扩展信息不是任意顶层 key 的堆积。  
它应该有明确归属、来源和命名空间，尤其是第三方格式插件产生的属性，不应直接和平台标准属性平铺混写。

扩展信息可分为两类：

- 平台标准扩展：例如 `spatial`、`media`、`document`、`statistics` 等，平台可稳定理解并消费。
- 格式或插件私有扩展：例如某个遥感格式、仿真格式、行业专有格式的独有属性，应挂在格式名或插件命名空间下。

## 二、推荐术语

### 对外术语

对外建议优先使用：

- 表格型数据
- 图片型数据
- 视频型数据
- 文档型数据
- 空间矢量型数据
- 目录型数据

### 对内模型名

对内可以保留：

- `TableInfo`
- `ObjectInfo`
- `FieldInfo`
- `ExtensionInfo`

但这些只是实现模型名，不应反向污染概念层。

## 三、结构化属性

“结构化 / 非结构化 / 半结构化”应降级为属性，而不是一级分类。

例如：

- 表格型数据通常是结构化
- 图片型、视频型通常是非结构化
- 文档型可能是半结构化或弱结构化
- 空间矢量型通常是结构化 + 空间扩展

这意味着：

- 不能只靠“结构化/非结构化”决定数据家族
- 不能把所有边界都塞进这一维度

## 四、统一对象模型

### TableInfo

`TableInfo` 用于描述表格型数据，包括：

- 数据库表
- 文件表
- 文档数据库集合
- 空间矢量表

它应承载：

- `Fields`
- `PrimaryKey`
- `RowCount`
- `SizeBytes`
- `CreatedAt` / `UpdatedAt`
- `Extensions`

### FieldInfo

`FieldInfo` 是结构化数据的字段级元信息，只属于 `TableInfo`。

它应表达：

- 字段名
- 标准类型
- 原始类型
- 是否可空
- 是否主键
- 注释
- 长度 / 精度
- 采样出现率

### ObjectInfo

`ObjectInfo` 用于描述对象型数据，包括：

- 图片
- 视频
- PDF
- 其他按对象消费的内容

它应表达：

- 对象键
- 大小
- 修改时间
- MIME 类型
- 扩展信息

`ObjectInfo` 不应默认拥有 `FieldInfo` 语义。

### ExtensionInfo

`ExtensionInfo` 是数据家族的能力挂载点，不是任意黑箱。

建议每个扩展至少说明：

- 扩展类型
- 来源
- 是否采样得到
- 是否完整推断
- 版本或策略

对于第三方插件，`ExtensionInfo` 不要求平台预先知道所有字段，但插件应声明这些字段属于哪个命名空间、来自哪个 parser / extractor、是否可索引、是否可展示，以及是否影响预览或转换能力。

平台只能依赖已标准化的核心字段和标准扩展字段。  
第三方私有扩展可以被存储、展示和选择性索引，但不能直接决定平台级行为，除非它经过标准化并进入平台认可的扩展模型。

## 五、meta item attributes 的概念分层

`meta_item.attributes` 应表达一个 item 的补充属性，但其内容来源天然分层：

| 分层 | 回答的问题 | 主要来源 | 示例 |
|---|---|---|---|
| 存储属性 | 数据在哪里、源资源基础信息是什么 | 存储引擎、catalog provider、对象枚举接口 | bucket、path、name、size、content_type、last_modified_at |
| item 语义属性 | 这套资源如何构成 item，它属于什么家族和格式 | ADDP item 识别层、`common/dataitem` | composition_type、data_family、format、entry_path、component_files |
| 结构属性 | 结构化数据有哪些字段和表级信息 | 表解析器、数据库 metadata provider、文档集合采样器 | fields、primary_key、indexes、row_count |
| 标准扩展属性 | 平台已理解的通用扩展语义 | parser / extractor 标准模型 | spatial、media、document、statistics |
| 私有扩展属性 | 格式或插件独有语义 | 具体格式 parser / 第三方插件 | com.vendor.format_xxx 下的专有字段 |

因此，ADDP 应约束的是“平台如何理解一个 item”，而不是试图穷举“世界上所有格式可能携带的属性”。

推荐原则：

- `attributes` 顶层不应长期承载大量无归属字段。
- 平台保留字段应稳定、可校验、可文档化。
- 插件私有字段必须进入命名空间，避免和平台字段冲突。
- 当某类私有字段被多个格式复用，并被平台能力稳定消费时，可以晋升为平台标准扩展。

## 六、组合形态的定位

组合形态应单独建模，因为它直接影响 meta item 的归并方式。

典型示例：

- SQLite 文件：单文件容器型
- Shapefile：多文件单 item
- Parquet 数据集：目录型单 item
- OSGB 倾斜摄影：目录树单 item
- 影像镶嵌数据集：目录树或集合型单 item

这层应影响：

- `meta` 如何识别 item
- `manager` 如何预览
- `common/dataitem` 如何匹配目录、文件组和容器

### 组合形态示例

| 组合形态 | 例子 | 说明 |
|---|---|---|
| 单文件单 item | `data.csv`、`photo.jpg`、`report.pdf` | 一个文件就是一个 item |
| 多文件单 item | `roads.shp + roads.shx + roads.dbf + roads.prj` | 依赖多个配套文件，但整体是一个 item |
| 容器文件单 item | `demo.sqlite` | 一个文件内部包含多个表或对象 |
| 目录树单 item | `dataset/`、`scene/`、`mosaic/` | 一个目录整体构成一个 item |
| 混合集合单 item | 目录下若干主文件 + 辅助文件 | 例如主数据文件配元数据、索引、金字塔等 |
| 嵌套组合形态 | 目录里再有容器文件 | 以后复杂数据集可能会出现 |

## 七、空间扩展的定位

空间不属于数据家族本身，而属于扩展语义。

也就是说：

- Shapefile = 表格型数据 + 空间扩展 + 多文件组合形态
- PostGIS = 表格型数据 + 空间扩展
- GeoJSON = 表格型数据 + 空间扩展
- GeoTIFF / 带地理参考的影像 = 图片型数据 + 空间扩展

空间扩展会影响：

- 字段解释
- 预览渲染
- 过滤与查询
- 前端地图 / 空间视图

## 八、文件格式与数据家族的关系

建议采用下面关系：

- 数据家族是主分类
- 组合形态决定 item 归并方式
- 文件格式是该家族与组合形态的编码实现
- 扩展信息决定额外语义

例如：

- 表格型数据：CSV、Excel、Parquet、SQLite 表
- 图片型数据：JPG、PNG、GIF
- 视频型数据：MP4、AVI、MOV
- 文档型数据：PDF
- 空间矢量型数据：Shapefile、GeoJSON、PostGIS

## 九、结论

ADDP 的概念模型应从“格式驱动”转为“数据家族驱动”。

在属性治理上，ADDP 应从“attributes 自由堆叠”转为“受控核心 + 开放扩展”。  
核心语义必须稳定，扩展语义必须有归属，第三方格式必须能扩展但不能破坏平台对 item 的统一理解。

一句话概括就是：

**存储引擎管位置，数据家族管语义，组合形态管 item 组织，文件格式管编码，扩展信息管差异。**
