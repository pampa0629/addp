## 一、当前事实

1. Workflow Runtime 返回 `execution_id`、`final_result`、`all_results` 和执行摘要；这些结果必须可 JSON 序列化，不能承载完整大数据对象。
2. Runtime 本地 execution 用于状态轮询和短期诊断，不是 ADDP 长期事实源。
3. Develop 在执行前根据 Public Operator Spec 和资源 locator 派生 Runtime 参数；对于持久化转换，同时生成不含密钥的目标事实。
4. Develop 已把持久化目标保存为 `produced_targets`，并在执行成功后按目标 locator 提交 Meta scan。
5. SuperMap C++ Runtime 当前返回轻量 `lineage_events`，其中路径型 `asset_ref` 只能视为运行时诊断信息，不能作为 ADDP 长期资源身份。

尚未完成的是跨运行时统一的输入资源事实、节点级逻辑血缘、持久化产物事实和 Meta lineage 落库契约。

## 二、架构边界

### 2.1 Runtime 不构造 ADDP 资产身份

Workflow Runtime 不掌握完整的 Tenant、Engine Instance、权限、locator、Meta item 和资产生命周期，因此不得直接创建 ADDP locator、Meta item 或 Asset 记录。

Runtime 只返回执行事实：

- runtime execution id、状态、耗时和错误。
- 节点 ID、算子 ID、输入端口引用和输出端口引用。
- 可序列化的节点结果摘要。
- 是否产生运行时临时对象或执行了持久化写入的逻辑事件。

Runtime 不返回连接密钥，不把本地挂载路径、容器临时路径或 object store 临时访问参数当作长期资产引用。

### 2.2 调用方拥有资源事实

Develop / Orchestrator 等任务调用方掌握 Public Operator Spec、资源 locator、Develop Adapter Spec 和脱敏 audit plan，应由调用方构造并持久化：

- 输入资源引用。
- `produced_targets`。
- Runtime Engine Instance 和 Source Engine Instance 身份。
- 目标 Meta scan 状态。
- 任务定义、统一 execution 与 runtime execution 的关联。

因此，不在 `addp.workflow/v1` Runtime 响应中新增一套与 `produced_targets` 并行的 `produced_assets / consumed_assets` 资源身份协议。后续统一结果模型必须复用 locator、storage ref、meta item ref 和现有执行记录，不新增 workflow 私有资源身份。

### 2.3 内存对象不登记为资产

工作流节点之间可以继续传递 GeoDataFrame、DataFrame、SuperMap Datasource / Dataset 类型化句柄或其他运行时对象。血缘记录逻辑依赖，不要求每条边物理落盘。

| 类型 | 长期执行记录 | Meta / Asset | 血缘 |
| --- | --- | --- | --- |
| runtime memory object | 只记录节点和端口摘要 | 不登记 | 记录节点间逻辑依赖 |
| runtime temp artifact | 可记录诊断摘要 | 默认不登记 | 默认只作为内部依赖 |
| persisted target | 必须记录稳定资源引用 | 按 owner 策略扫描或登记 | 进入资源级血缘 |

是否进入 Meta 由资源归属和持久化意图决定，不能仅按“是否写到磁盘”判断。

### 2.4 Direct 调用保持 owner 边界

Manager 等模块通过 direct operator 生成私有 artifact 时，由 owner 模块保存领域结果、源 item fingerprint、目标 storage ref、Runtime Engine、算子和执行摘要。Direct 调用不因此创建 Develop 任务，也不自动进入通用工作流血缘。

如果未来要求 direct 结果参与统一血缘，必须先定义 owner 领域结果到统一 lineage event 的发布契约，不能让 Meta 反向抓取 Runtime 私有 API。

## 三、目标结果分层

### 3.1 Runtime 结果

`addp.workflow/v1` 继续保留：

```json
{
  "status": "success",
  "execution_id": "runtime-execution-id",
  "final_result": {},
  "all_results": {},
  "execution_time_ms": 12.3,
  "lineage_events": [
    {
      "event_type": "workflow.operator.executed",
      "task_id": "dissolve",
      "operator": "vector.dissolve",
      "input_ports": {
        "input_dataset": "filter.result_dataset"
      },
      "output_ports": {
        "result_dataset": "dissolve.result_dataset"
      }
    }
  ]
}
```

`lineage_events` 只表达 Runtime 能证明的节点执行事实。是否把它提升为 `addp.workflow/v1` 必填字段、字段名称和事件 schema，仍需在正式协议中统一。

### 3.2 统一执行记录

任务调用方应把长期事实写入 `common.task_executions` 的规范结果结构或后续统一结果表，至少覆盖：

- runtime execution id 与 Runtime Engine Instance。
- 输入资源引用和 `produced_targets`。
- 脱敏后的资源绑定摘要。
- 节点级逻辑血缘事件。
- Meta scan run 及其状态引用。
- 轻量结果摘要、错误和耗时。

完整大对象、连接信息、Access Token 和 Workflow Access Plan 原文不得进入长期执行记录。

### 3.3 Meta / Lineage

目标链路固定为：

```text
Workflow Runtime execution facts
  + Develop / Orchestrator resource facts
  -> common task execution result
  -> Meta lineage collector
  -> resource / operator execution nodes and edges
```

Meta 不直接调用 Workflow Runtime 私有状态接口。持久化目标先按 locator 完成 Meta scan，再把 execution 中的资源引用解析为稳定 lineage node。

## 四、空间数据注意点

### 4.1 UDBX Dataset

UDBX 文件可包含多个 Dataset。仅记录文件 locator 无法表达 Dataset 级输入输出；后续必须在数据项体系中确定 Dataset 是 file item 的可寻址子对象，还是独立 data item。该决定影响授权、预览、生命周期和血缘粒度，不能由 SuperMap Runtime 私自定义 `path#dataset` 身份。

### 4.2 PostGIS / SuperMap SDX+ for PostGIS / SuperMap SDX+ for PostgreSQL

普通 PostGIS 表、SuperMap SDX+ for PostGIS 业务表与 SuperMap SDX+ for PostgreSQL 业务表都应使用真实 Engine Instance、schema 和 table 身份。`sm*` 系统表不进入业务血缘；其识别和过滤规则归 PostgreSQL catalog 与 Meta scan，不归 Workflow Runtime。

### 4.3 临时输出

`/tmp`、运行时工作目录和容器挂载路径只用于执行，不是业务资源。需要长期治理的输出必须在 Public Operator Spec 中要求用户选择目标资源，并由调用方生成 `produced_targets`。

## 五、待确认问题

1. 长期结果继续放入 `common.task_executions.metadata.result`，还是建立结构化统一结果子表。
2. 输入资源事实的字段名称、结构和去重规则如何与现有 `produced_targets` 对称。
3. 节点级 `lineage_events` 的正式 schema、版本和必填范围。
4. UDBX Dataset 等容器内部对象的稳定资源身份。
5. Runtime 临时产物清理策略以及失败、取消时的清理责任。
6. Develop、Orchestrator 和 owner direct 结果是否需要同一 lineage event 发布接口。
7. 第一阶段只做 resource / dataset / table 级血缘，字段级和 Geometry 列级血缘何时进入。
8. Meta lineage collector 的任务触发、幂等键、失败重试和权限边界。

## 六、推进顺序

1. 先在任务体系和工作流协议中统一执行结果结构，复用现有 `produced_targets`，补齐输入资源事实和节点级逻辑事件。
2. 让 Develop 执行记录持久化这些结构，并验证 Runtime 重启后长期事实仍完整。
3. Meta 从统一执行记录采集 resource / dataset / table 级血缘，并关联 Meta scan 后的稳定 item。
4. 完成 UDBX Dataset、PostGIS、SuperMap SDX+ for PostGIS、SuperMap SDX+ for PostgreSQL 等空间资源粒度验证。
5. 最后评估字段级血缘和 direct owner 结果接入。

## 七、收口条件

以下事项全部完成后删除本文：

1. 工作流 Runtime 节点事件和调用方资源事实进入正式规范。
2. Develop / Orchestrator 按统一结果结构持久化，旧的运行时路径型资产引用被删除。
3. Meta lineage collector 完成 resource / dataset / table 级端到端验证。
4. UDBX Dataset 和厂商空间库业务表的资源身份进入数据项与血缘正式规范。
