# 工作流运行时结果产物与血缘专题

## 一、问题背景

SuperMap 工作流运行时已经验证可在同一个 JVM / SPS DAG 内传递 `DatasetVector` 等内存对象，并把最终或中间分析结果写入 UDBX / PostGIS 等持久化数据源。Develop 任务管理也已能保存并执行 SuperMap DAG。

当前暴露出的架构问题是：

1. Workflow Runtime 能返回 `final_result`、`all_results` 和轻量 `lineage_events`。
2. Develop 统一执行记录当前长期保存的是执行摘要，例如 `runtime_execution_id`、状态、耗时和结果大小。
3. Runtime 本地执行状态里仍可查询完整节点结果，但 runtime 本地状态不是 ADDP 长期事实源。
4. 如果后续要做资产登记、结果浏览、任务复现和数据血缘，不能只依赖 runtime 的 `/api/executions/{execution_id}`。

这不是 SuperMap 独有问题。GeoPython、Spark、Model3D、PointCloud 等工作流运行时只要产生外部数据产物，都需要回答同一组问题：

1. 哪些输入资产被消费。
2. 哪些输出产物被创建。
3. 哪些中间结果只是 runtime 内存对象或临时数据。
4. 哪些产物需要进入 Meta / Asset / Lineage。
5. 统一执行记录应保存哪些长期事实，哪些只是诊断摘要。

## 二、核心判断

### 2.1 Runtime 本地状态不能作为长期事实源

Workflow Runtime 的本地执行状态适合承载短期诊断信息，例如运行时本地 execution id、节点摘要、错误详情、临时日志。它不适合作为长期血缘或资产事实源，原因包括：

1. runtime 容器可能重启，内存执行记录会丢失。
2. runtime 可能扩缩容，多实例下本地状态不一定可路由。
3. runtime 只知道自身执行视角，不掌握 ADDP 租户、权限、资产生命周期和 Meta 扫描状态。
4. 长期血缘需要稳定引用 ADDP 资源，而不是 runtime 私有对象或临时路径。

因此，进入 ADDP 统一任务体系的执行结果，必须把需要长期保留的产物和血缘事实写入 ADDP 后端的持久化模型。

### 2.2 内存对象传递不妨碍血缘

SuperMap DAG 内部可以继续传递 `Datasource`、`DatasetVector`、`Recordset` 或自定义 handle，以减少落盘和重复读取。血缘记录的是逻辑依赖和可识别资产，不要求每条 DAG 边都物理落盘。

示例：

```text
example_data.udbx#Landuse_R
  -> vector.filter
  -> memory DatasetVector
  -> vector.dissolve
  -> addp_supermap_develop_task.udbx#LanduseLargeDissolve
```

这里中间 `DatasetVector` 可以不进入 Meta，但仍应记录：

1. `vector.filter` 消费了 `example_data.udbx#Landuse_R`。
2. `vector.dissolve` 逻辑上依赖 `vector.filter` 的输出。
3. `addp_supermap_develop_task.udbx#LanduseLargeDissolve` 来源于该工作流执行链路。

### 2.3 只登记持久化产物，不登记普通内存中间对象

第一阶段应明确区分三类输出：

| 类型 | 生命周期 | 是否进入统一执行记录 | 是否进入 Meta | 是否参与血缘 |
| --- | --- | --- | --- | --- |
| memory object | 单次 runtime execution 内 | 可记录逻辑端口摘要 | 否 | 作为 operator node 间逻辑依赖 |
| runtime temp dataset | runtime 临时工作区 | 可记录诊断摘要 | 默认否 | 默认只作为内部依赖 |
| persisted asset | 用户指定或算子显式写出的持久化数据 | 必须结构化记录 | 可进入 Meta / Asset | 必须参与资产级血缘 |

是否进入 Meta 不能只按“是否写到磁盘”判断。临时输出目录中的调试 UDBX 不一定是业务资产；写入业务 PostGIS / SDX+ 空间库或用户显式保存到项目目录的数据集，才应进入资产主链路。

## 三、建议的结果契约分层

### 3.1 Runtime 返回层

Workflow Runtime 可以继续返回 `final_result` 和 `all_results` 供调试和前端即时展示，但应新增结构化产物字段，避免上层从各 runtime 私有摘要中反推。

建议候选字段：

```json
{
  "produced_assets": [
    {
      "task_id": "dissolve",
      "operator": "vector.dissolve",
      "output_port": "result_dataset",
      "asset_kind": "dataset",
      "storage": {
        "kind": "udbx",
        "path": "/tmp/supermap-out/addp_supermap_develop_task.udbx"
      },
      "dataset": {
        "name": "LanduseLargeDissolve",
        "type": "Region",
        "record_count": 2
      },
      "persistence": "persisted",
      "meta_scan": {
        "recommended": true,
        "reason": "persistent_output"
      }
    }
  ],
  "consumed_assets": [
    {
      "task_id": "select_landuse",
      "operator": "dataset.select",
      "input_port": "datasource",
      "asset_kind": "dataset",
      "storage": {
        "kind": "udbx",
        "path": "/mnt/supermap/data/example_data.udbx"
      },
      "dataset": {
        "name": "Landuse_R"
      }
    }
  ],
  "lineage_events": [
    {
      "event_type": "workflow.operator.executed",
      "task_id": "dissolve",
      "operator": "vector.dissolve",
      "input_ports": {
        "input_dataset": "filter_large.result_dataset"
      },
      "output_ports": {
        "result_dataset": "dissolve.result_dataset"
      },
      "consumed_assets": [],
      "produced_assets": [
        "udbx:/tmp/supermap-out/addp_supermap_develop_task.udbx#LanduseLargeDissolve"
      ]
    }
  ]
}
```

说明：

1. `produced_assets` / `consumed_assets` 是资产事实候选，面向 ADDP 持久化。
2. `lineage_events` 是执行过程事实，面向血缘转换。
3. `all_results` 仍可保留为 runtime 即时结果摘要，但不作为长期契约事实源。
4. 资产引用需要后续统一为 ADDP locator / storage ref / meta item ref，不能长期使用裸路径。

### 3.2 Develop 执行记录层

Develop 执行完成后，应把 Runtime 返回的长期事实写入 `common.task_executions.metadata.result` 或后续统一结果表中。

第一阶段可保存：

```json
{
  "runtime_execution_id": "...",
  "status": "success",
  "execution_time_ms": 1078,
  "produced_assets": [],
  "consumed_assets": [],
  "lineage_events": [],
  "summary": {
    "has_result": true,
    "result_size_bytes": 1634
  }
}
```

注意：

1. 统一执行记录不应保存完整大数据。
2. 可保存轻量 schema、record_count、bounds、dataset type 等摘要。
3. 大对象预览、完整数据读取仍应通过 Manager / Meta / Storage Provider 完成。
4. 如果结果产物需要长期治理，应产生可稳定解析的资源引用。

### 3.3 Meta / Lineage 层

Meta / Lineage 不应直接调用 workflow runtime 私有 API 抓执行状态。更合理的路径是：

```text
Workflow Runtime
  -> Develop / Orchestrator 统一执行记录
  -> 结果产物事件 / 血缘事件
  -> Meta Lineage 采集
  -> meta item / lineage node / lineage edge
```

Meta 可消费：

1. `produced_assets`：决定是否触发 meta scan、创建或刷新 meta item。
2. `consumed_assets`：解析源资产节点。
3. `lineage_events`：转换为 operator execution node 和 lineage edge。
4. `execution_id` / `source_task_id`：关联任务定义、执行记录和血缘作业。

## 四、SuperMap 特有注意点

### 4.1 UDBX 内部 dataset 引用

SuperMap UDBX 是文件型数据源，内部可包含多个 dataset。血缘不能只记录 UDBX 文件路径，还必须记录内部 dataset name。

建议资源粒度：

```text
file item: /tmp/supermap-out/addp_supermap_develop_task.udbx
sub item:  /tmp/supermap-out/addp_supermap_develop_task.udbx#LanduseLargeDissolve
```

是否把 UDBX 内部 dataset 升格为独立 meta item，需要和数据项体系统一。若需要独立授权、检索、血缘、预览或生命周期管理，应支持 dataset 级 item / sub-item。

### 4.2 PostGIS / SDX+ 输出

SuperMap 写入 PostGIS 时可能有两种语义：

1. 普通 PostGIS 表：由 PostgreSQL / PostGIS Provider 识别和扫描。
2. SuperMap SDX+ 空间库：存在 `sm*` 系统表和 SuperMap 原生空间库语义。

血缘记录应表达输出表的真实存储位置和空间库语义：

```json
{
  "storage": {
    "kind": "postgis",
    "engine_id": 12,
    "schema": "public",
    "table": "landuse_dissolve",
    "spatial_workspace": {
      "ecosystem": "supermap",
      "kind": "sdx+"
    }
  }
}
```

后续 Meta scan 应结合引擎能力 `capabilities.extensions.spatial_workspaces` 过滤 SuperMap 系统表，并识别业务数据表。

### 4.3 Runtime 临时输出目录

`/tmp/supermap-out` 这类开发输出目录适合验证，不一定代表业务资产。后续应由 Develop Public Operator Spec 明确区分：

1. 临时输出：只用于本次执行，不进入 Meta。
2. 用户保存：写入用户选择的目标资源，进入结果产物和血缘候选。
3. 发布产物：进入 Manager / Asset 管理的 artifact 或 data item。

## 五、待解决问题

1. `produced_assets` / `consumed_assets` 是否写入现有 `common.task_executions.metadata.result`，还是新增统一任务结果表。
2. asset ref 的统一格式：沿用 locator、storage ref，还是新增 workflow result ref。
3. UDBX 内部 dataset 是否作为 meta item 子对象，还是独立 data item。
4. runtime 临时产物何时清理，清理后血缘如何保留。
5. 字段级血缘是否从第一阶段纳入，还是先只做 asset / dataset / table 级血缘。
6. Develop 任务结果、Orchestrator 编排结果和 Manager direct operator 结果是否共用同一产物模型。
7. `all_results` 中哪些内容需要保留到长期执行记录，哪些只作为短期 runtime 诊断。
8. SuperMap SDX+、ArcGIS SDE 等厂商空间库的系统表过滤、业务表识别和血缘节点类型如何统一。

## 六、建议推进路线

### 阶段 1：统一结果产物契约

1. 在 `addp.workflow/v1` 中定义 `produced_assets`、`consumed_assets` 和增强版 `lineage_events`。
2. 先要求 runtime 返回轻量结构，不要求直接创建 meta item。
3. Develop 执行记录保存这些结构化字段。
4. 保留 `final_result` / `all_results` 作为即时展示和诊断。

### 阶段 2：Meta 血缘采集

1. Meta 从统一执行记录中读取结果产物和血缘事件。
2. 建立 asset / dataset 级 lineage node 和 edge。
3. 对持久化产物按策略触发 meta scan。
4. Manager 数据详情页可查询直接上下游。

### 阶段 3：空间库与多格式深化

1. 支持 UDBX 内部 dataset 级血缘。
2. 支持 PostGIS / SDX+ 输出表血缘。
3. 扩展到 GeoPython / Spark 空间数据输出。
4. 再评估字段级血缘、几何列级血缘和空间分析参数血缘。

## 七、专题结论

工作流运行时可以继续追求高效的内存对象传递，但 ADDP 必须把持久化产物和血缘事实从 runtime 本地状态中抽离出来，写入平台统一执行与血缘模型。

后续专题的核心不是“每条边是否落盘”，而是：

```text
哪些输入资产被消费
哪些输出产物被持久化
哪些中间对象只是运行时内部状态
哪些事实需要进入长期任务结果、Meta 和 Lineage
```

只有完成这层契约，SuperMap、GeoPython、Spark、Model3D、PointCloud 等运行时的结果治理和血缘能力才能收敛为 ADDP 的统一能力。
