1. 单 OSGB：`data_type=model_3d + format=osgb + layout=single`，通过 `model3d_workflow` 的 `osgb_to_glb` 生成 Manager 受管 GLB 快显。

### 0.4 STL 结论与已修问题

STL 当前按单文件三维模型处理：

```text
data_type=model_3d
format=stl
layout=single
```

STL 没有标准 manifest，不表达装配关系、相对位置、材质或纹理。因此一批 STL 文件所在目录不能直接识别为 `format=stl + layout=multi`。

当前 NFS 样例：

```text
business/nfs/data/3d/stl/Print Light Gun
```

该目录是典型 3D 打印模型项目包：

- `files/`：10 个 binary STL 零件。
- `images/`：9 张预览或零件说明图。
- `README.txt` / `LICENSE.txt`：来源、构建说明、授权信息。
- 总大小约 26MB，STL 约 23MB。
- 最大零件 `LightGunLensAdapterThreaded.stl` 约 15MB / 31.8 万三角面。

建议：暂不实现 STL 多零件包能力。后续如要增强，只做目录级“3D 打印模型项目包概览”，不要把目录误识别为 STL 原生 multi item，也不要把 `images/` 当作 STL 纹理 refs。

最近修复了 STL 转 GLB 后前端预览的相机裁剪问题：

- 用户现象：贴近或斜看时模型被近裁剪面切掉；随后稍远位置出现明显闪烁。
- 根因：`Model3DPreview.vue` 固定 near / far 策略无法兼顾贴近观察和深度缓冲精度。
- 当前修复：基于模型包围球中心、半径和相机位置动态调整 near / far；贴近模型表面时降低 near，离模型较远时提高 near 以减少 z-fighting；恢复上次视角时也先计算 bounds。
- 用户已确认当前效果基本 OK。

## 一、后续原则

三维和点云后续扩展继续遵守以下边界：

1. 网格模型、倾斜摄影、大场景和 BIM 统一归入 `model_3d`，通过 `format`、`layout`、`type_info.model_3d.model_kind` 和 `format_info.<format>` 区分。
2. LAS / LAZ / COPC / E57 / EPT / 点云型 PLY 归入 `point_cloud`，不借用 `model_3d` 的 GLB 快显路线。
3. 3DGS PLY、`.splat`、`.ksplat` 和后续 `.spz` 归入 `gaussian_splat`，不归入普通点云，也不走 GLB。
4. 前端目标格式保持克制：单体三维优先 GLB，分块三维优先 3D Tiles，点云优先 COPC 或点云瓦片，高斯泼溅优先原生 renderer / KSplat / 后续 SPZ。
5. 新格式落地前先补正式规范，再补 detector、attributes、Manager 预览路线、workflow operator 和验证样例。

## 三、点云路线

### 3.1 LAZ

LAZ 是 LAS 的压缩形态，应作为独立 `format=laz`，不复用 `format=las`。

2026-07-02 已落地：

- `format=laz` descriptor 和内置加载。
- 复用 LAS-family header 读取点数、point format、bounds、scale / offset 和 spatial extent，但写入 `format_info.laz`。
- 不把 LAZ 伪装为 LAS，不接入 LAS 抽样预览。

后续路线：

1. 验证抽样预览是否可直接读取压缩内容。
2. 大数据量路线优先转 COPC 或点云瓦片。

### 3.2 COPC

COPC 是点云大数据量浏览的优先增强目标。

2026-07-02 已落地：

- `format=copc` descriptor 和内置加载，`.copc.laz` 优先识别为 COPC。
- 读取 LAS-family header 形成 spatial / bounds / point count 轻量摘要。
- 校验并解析 COPC Info VLR，写入 octree center、half size、root spacing、root hierarchy offset / size 和 GPSTime 范围等 `format_info.copc` 摘要。
- `PointCloudDescribeInput` 已支持 range-aware 输入；当调用方提供 range reader 时读取 root hierarchy page，并在预算内递归读取下级 hierarchy page，写入 root 与整体 hierarchy 的 entry 数、leaf/internal/page entry 数、level 范围、点数、字节数和读取完整性摘要。
- `type_info.point_cloud.point_cloud_kind=tiled_point_cloud`，COPC 私有事实写入 `format_info.copc`。

2026-07-03 PDAL / MinIO 写入结论：

- `pointcloud_workflow` 必须继续作为容器化运行时承载 PDAL，不能依赖宿主机 PDAL。
- 点云源访问计划由 Manager 派生：NFS / NAS / localfs 使用挂载路径，MinIO / S3 单文件源使用 presigned `/vsicurl/` URI，运行时不解析 ADDP locator。
- 当前 PDAL 2.10.2 实测 `writers.copc` 不能可靠直接写 `/vsis3/` 目标；同容器内 `writers.copc` 写 `/vsis3/...copc.laz` 会 abort，`writers.las` 也会出现 writable `/vsis3/` seek 不支持错误。因此当前不能把 COPC 目标做成类似 raster COG 的 `/vsis3` 直写路线。
- 当前单一路线收敛为：PDAL 写 `POINTCLOUD_WORK_DIR` 下的受控工作文件，运行时按 Manager infra MinIO 发布计划上传为 Manager 私有 COPC artifact。`POINTCLOUD_WORK_DIR` / `CPL_TMPDIR` 必须挂载到容量足够的目录或卷，尤其是 japan 这类数百百万点规模 LAS。
- 后续只有在目标 PDAL / GDAL 组合能通过真实 `writers.copc -> /vsis3/` 验证后，才重新讨论直写 MinIO 迁移；不在当前实现中保留直写和上传双轨。

2026-07-03 Manager 快显路线已落地：

- 已新增 `pointcloud_workflow` 点云处理专用工作流运行时，第一阶段依赖 PDAL。
- `las|laz|e57|pcd|xyz -> copc` 已作为 Manager 私有快显路线落地，任务类型为 `point_cloud_copc_generation`，结果表为 `manager.point_cloud_copc`；生成的 COPC artifact 存放在 Manager infra MinIO，不自动升格为业务 data item。XYZ 第一阶段只支持简单确定性文本 XYZ，不引入列映射 UI 或通用文本 schema 配置。
- 源文件本身已经是 `format=copc` 时，作为正式 `data_type=point_cloud + format=copc` data item 直接基础预览，不创建二次 COPC 快显任务。
- Manager 前端通过受控内容 URL、HTTP Range、COPC hierarchy 和点数据块实现动态 LOD 预览；首屏保留浅层 overview，交互靠近后按视角继续读取 hierarchy page 和 detail 节点。

后续路线：

1. 后续如用户明确需要“归一化为业务 COPC 数据集”，再单独设计业务数据准备 / 物化任务，不与快显任务混用。
2. 后续如需要更完整的统计画像，必须继续以预算内 hierarchy / tile 摘要为边界，不读取点样本写入 attributes。

### 4.2 KSplat 渐进加载优化

当前 KSplat 生成已按场景中心组织 section。后续更理想的体验是按“当前相机视野中心”优先加载。

2. 如可控，前端根据相机 target / frustum 动态调整加载优先级。
3. 如不可控，不 fork 第三方库前不做强改，避免维护成本不可控。

## 五、下一轮建议

优先级建议：

1. 先推进 `pointcloud_workflow + point_cloud_copc_generation` 最小闭环：`las|laz|e57|pcd|xyz` 生成 Manager 私有 COPC 快显 artifact，源 COPC 直接基础预览。
2. 城市级点云 3D Tiles 暂缓；后续只在明确“城市三维发布 / Cesium 场景集成”价值时再设计，不进入本轮。
3. `dae`：若继续扩展普通 mesh 格式，优先验证 `assimp` 或 Blender CLI 转自包含 GLB 的效果；它最容易复用现有 `model_3d_glb_generation + model3d_workflow` 主链路。
4. `ifc`：作为 BIM 专题，下一步补充更多失败边界样例和前端快显体验验证，不要把 IFC 当作普通 mesh。
