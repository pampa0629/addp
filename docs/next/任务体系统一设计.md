# ADDP 任务体系统一设计草案

> 状态：讨论稿。阶段 1 规范已沉淀到 [ADDP 任务体系规范](../spec/addp任务体系规范.md)。本文保留调研背景、已知冲突和后续改造顺序，用于继续讨论阶段 2 及之后的实现切分。

## 背景

ADDP 已经在多个模块中形成任务能力：

- Meta 负责元数据扫描任务。
- Transfer 负责数据搬运任务。
- Develop 负责查询、工作流和 Notebook 执行任务。
- Manager 负责 MVT、embedding 等派生产物任务。
- Orchestrator 负责任务级 DAG 编排。
- Monitor 查询统一执行记录。

当前方向是正确的：任务定义留在各 owner 模块，执行记录统一进入 `common.task_executions`。但现状仍存在枚举漂移、任务定义和执行记录混用、编排触发语义不清、Manager 即时任务与持久任务并存等问题。

本文先定义目标概念边界，后续实现必须以本文为准，不保留双轨兼容分支。

## 核心结论

ADDP 不建立统一任务总表。`Task` 是抽象概念，不是一个跨模块实体表。

| 概念 | Owner | 存储 | 含义 |
| --- | --- | --- | --- |
| 任务定义 | 业务 owner 模块 | owner 模块私有表 | 未来应该按什么策略处理什么对象 |
| 执行记录 | Common | `common.task_executions` | 某一次实际执行了什么、状态如何、结果如何 |
| 调度定义 | 任务定义 owner | owner 模块私有表 | 是否启用定时、Cron 表达式、下一次运行时间 |
| 运行时队列 | 执行 owner | Redis / Asynq / 进程内队列 / DB claim | 如何把一次 execution 投递给 worker |
| 产物状态 | 产物 owner 模块 | owner 模块私有表或 artifact manifest | 当前产物是否可用、在哪里、由什么配置生成 |
| 编排定义 | Orchestrator | `orchestrator.orchestrations` | 任务级 DAG，引用已有任务或声明允许的内联执行步骤 |

任务体系必须保持三条边界：

1. 统一执行记录不吞并各模块任务定义。
2. Orchestrator 只编排任务能力，不拥有业务任务定义。
3. Monitor 查询执行、调度、队列和产物状态，但不成为任务 owner。

## 总体模型

```text
owner task definition
  ├─ owner scheduler ───────────────┐
  └─ task provider API ─────────────┤
                                    ▼
                         common.task_executions
                                    │
                                    ▼
                         runtime queue or worker
                                    │
                                    ▼
                         owner artifact state

orchestrator DAG ──> task provider API
orchestrator DAG ──> common.task_executions

monitor <── common.task_executions
monitor <── owner scheduler
monitor <── runtime queue or worker
monitor <── owner artifact state
```

## 任务定义

任务定义表达可被再次执行的稳定配置。任务定义不保存每次执行历史，只保存最近执行摘要。

所有持久任务定义应具备最小公共字段：

| 字段 | 说明 |
| --- | --- |
| `id` | owner 模块内任务 ID |
| `tenant_id` | 租户 ID |
| `name` | 任务名称 |
| `description` | 任务描述 |
| `enabled` | 是否启用定时或自动触发 |
| `schedule` | Cron 表达式，空表示无定时 |
| `last_run_at` | 最近执行时间 |
| `next_run_at` | 下一次计划执行时间 |
| `last_execution_id` | 最近一次 `common.task_executions.execution_id` |
| `last_execution_status` | 最近一次执行状态 |
| `created_by` | 创建人 |
| `created_at` / `updated_at` / `deleted_at` | 审计字段 |

这些字段是概念基线，不要求抽取统一 DB 表。各模块可以按自身业务增加字段，但不得改变公共语义。

## 执行记录

`common.task_executions` 只记录 execution，不保存任务定义和调度定义。

目标字段语义：

| 字段 | 说明 |
| --- | --- |
| `execution_id` | UUID，全局唯一，跨模块追踪 |
| `tenant_id` | 租户 ID |
| `module` | 执行 owner 模块 |
| `task_type` | owner 模块内稳定任务类型 |
| `source` | 本次执行由哪个模块或入口触发 |
| `source_task_id` | owner 模块任务定义 ID；一次性执行可为空 |
| `source_task_name` | 任务名称冗余，用于展示 |
| `parent_execution_id` | 父 execution UUID，主要用于编排子步骤 |
| `status` | 执行状态 |
| `progress` | 0 到 100 |
| `current_step` | 当前步骤描述 |
| `trigger_type` | `manual` 或 `scheduled` |
| `triggered_by` | 触发用户 |
| `execution_config` | 本次执行快照配置 |
| `metadata` | 结果摘要、步骤结果、模块扩展信息 |
| `error_details` | 错误类型、消息和诊断信息 |
| `started_at` / `completed_at` / `execution_time_ms` | 执行时间 |

约束：

1. `trigger_type` 只允许 `manual` / `scheduled`。
2. `source` 表达触发来源，例如 `console`、`orchestrator`、`manager`、`meta`。
3. `task_type` 不表达触发方式。
4. `source_task_id` 不跨表建立 DB 外键，由应用层按 `module + task_type` 路由。
5. ad-hoc execution 可以没有 `source_task_id`，但必须在 `execution_config` 中保存本次执行所需的完整配置快照。
6. Orchestrator 子步骤必须写 `parent_execution_id`。

## 全局枚举

### 执行状态

只保留：

| 状态 | 说明 |
| --- | --- |
| `pending` | 已创建，等待运行 |
| `running` | 正在运行 |
| `success` | 成功完成 |
| `failed` | 失败完成 |
| `timeout` | 超时结束 |
| `cancelled` | 被取消 |

不得再使用 `completed` 表达执行成功。

### 触发类型

只保留：

| 触发类型 | 说明 |
| --- | --- |
| `manual` | 用户、API、Console、Orchestrator 或其他模块显式触发一次执行 |
| `scheduled` | owner 模块调度器按计划触发 |

`orchestrator`、`api`、`retry`、`system_immediate` 这类值不得进入 `trigger_type`。它们应进入 `source`、`metadata` 或明确的重试关联字段。

### 模块任务类型

第一版建议收敛为：

| 模块 | `task_type` | 任务定义 |
| --- | --- | --- |
| Meta | `scan` | `meta.scan_tasks` |
| Transfer | `import` | `transfer.transfer_tasks` |
| Develop | `query` / `workflow` / `script` | `develop.dev_tasks` |
| Manager | `mvt_generation` / `embedding` | `manager.mvt_tasks` / `manager.embedding_tasks` |
| Quality | `check` | `quality.check_tasks` |
| Graph | `kg_build` | `graph.build_tasks` |
| Orchestrator | `orchestration` | `orchestrator.orchestrations` |

阶段 1 暂不展开 Transfer 内部任务语义，对外先统一使用 `task_type=import`。后续如 Transfer 专题确认需要增加导出、同步等任务类型，必须先修订正式规范，再按 clean break 方式迁移；不应继续在不同文档中同时使用 `import/export/sync/transfer` 多套并行语义。

## 各模块边界

### Meta

Meta 只拥有扫描任务：

- `ScanTask` 定义扫描范围、深度、force、owner 绑定和 schedule。
- manual scan、item refresh 和 startup/unscanned execution 可以直接创建 ad-hoc execution。
- scan execution 可以在结果中暴露可消费事实，但不成为 MVT、embedding、thumbnail 等派生产物 owner。

Meta 不定义 Manager 派生任务，不清理 Manager 派生产物。

### Manager

Manager 拥有 MVT / QuickView / embedding 派生产物及其任务定义。QuickView 的 `ready`、`generating`、`preparing` 等状态属于 artifact state，不是 `common.task_executions.status`。旧 `/embedding` 与 `/embedding/tasks/{task_id}` 是前端即时向量化的内存轮询入口，不是 TaskProvider 标准任务定义入口；其 `task_status` 属于 execution-like 状态，成功态统一为 `success`，不得继续使用 `completed`。

### Graph

Graph 拥有图谱构建任务定义，阶段 1 以 `task_type=kg_build` 纳入 TaskProvider。`graph.build_tasks.status` 表达构建任务最近执行摘要，必须使用 `pending/running/success/failed/cancelled`；`graph.build_materials.status=completed` 仅表达材料处理完成，不属于统一 execution status。

### Transfer

Transfer 拥有数据搬运任务：

- 任务定义保存 source、target、transform、write policy、load strategy 和 schedule。
- execution 写入 `common.task_executions`。
- worker / Asynq 只是执行机制，不是任务定义。

Transfer 后续应先统一任务语义，再决定是否扩展新的 `task_type`。

### System cleanup

System cleanup 阶段 1 先跳过，不纳入 TaskProvider，也不进入 Orchestrator 编排。cleanup 从监控视角具有 execution 特征，但从编排视角属于系统级运维清理流程，不是用户数据处理流水线的一环。后续如果需要接入 `common.task_executions`，只能作为 `module=system` 的运维执行记录用于监控和审计，不能声明为可编排任务类型。

### Develop

Develop 拥有开发任务：

- `DevTask` 是可执行开发工件，类型包括 query、workflow、script。
- `script` 表示命令式代码开发任务，当前可由 Jupyter Notebook runtime 承载；Notebook 是脚本开发的实现形态和 UI 入口，不作为独立 `task_type`。
- 临时执行允许无任务定义，但必须保存完整 `execution_config`。
- 算子工作流属于 Develop 内部细粒度工作流，不等同于 Orchestrator 的任务编排流。

### Manager

Manager 拥有展示和检索派生产物任务：

- `MvtTask` 定义 MVT 生成策略。
- `EmbeddingTask` 定义向量化策略。
- QuickView 是产物状态，不是任务定义。
- embedding vector 是产物状态，不是 execution。

Manager 持久化 embedding 任务执行由 `EmbeddingTaskService` 创建主 execution，并把 execution context 传给 `EmbeddingService.EmbedDirectory` 复用；`EmbedDirectory` 仅在 ad-hoc 调用时自行创建 execution。一次用户意图只产生一条主 execution。

Manager ad-hoc embedding 可以保留，但必须满足：

- 只作为 ad-hoc execution，不产生 owner 任务定义。
- 没有 `source_task_id` 时必须写完整 `execution_config`。
- 内存 `TaskTracker` 只作为实时进度辅助，不是统一任务体系的长期状态来源。

### Orchestrator

Orchestrator 拥有编排定义：

- `Orchestration` 本身是一种任务定义。
- Orchestration execution 写入 `common.task_executions`，`task_type=orchestration`。
- Step 可以引用 provider 任务，也可以使用明确允许的 inline execution。
- Orchestrator 不直接写 owner 模块任务定义表。

Orchestrator 触发下游任务时：

| 字段 | 值 |
| --- | --- |
| `trigger_type` | 继承父编排触发方式，或显式 `manual` |
| `source` | `orchestrator` |
| `parent_execution_id` | 当前 orchestration execution UUID |

## Orchestrator 是否创建新任务

默认不支持 Orchestrator 创建 owner 模块持久任务。

理由：

1. 任务定义生命周期归 owner 模块。
2. 参数校验、权限、默认值、UI 回显和清理策略都在 owner 模块。
3. 编排创建任务会制造“任务到底归谁维护”的长期歧义。

Orchestrator 可以支持两类入口：

| 模式 | 是否持久化 owner 任务 | 说明 |
| --- | --- | --- |
| 任务引用 | 是，已由 owner 模块创建 | `provider + task_type + task_id` |
| 内联执行 | 否 | provider 明确声明支持一次性 execution spec，Orchestrator 只传执行配置 |

如果用户需要新建持久任务，Orchestrator 前端可以根据 TaskProvider capabilities 跳转到 owner 模块的 create URL。创建完成后再回到编排中引用该任务。

## TaskProvider 协议

TaskProvider 是模块的一种角色，不是独立业务 owner。System 可以保存 provider 注册信息，供 Orchestrator 和 Monitor 发现模块任务能力。

TaskProvider 按模块注册，不按任务类型注册。一个模块只有一个 provider，但 provider 可以声明多个 `task_types`。例如 Manager 作为一个 provider，同时声明 `mvt_generation` 和 `embedding`；Orchestrator 引用任务时必须同时保存 `provider + task_type + task_id`，不能只保存 `provider + task_id`。

第一版 TaskProvider 应提供：

| 能力 | Endpoint |
| --- | --- |
| 列任务 | `GET /tasks?task_type=` |
| 查任务 | `GET /tasks/{task_type}/{id}` |
| 执行任务 | `POST /tasks/{task_type}/{id}/execute` |
| 查执行 | `GET /executions/{execution_id}` |
| 取消执行 | `POST /executions/{execution_id}/cancel`，仅当对应 `task_type.supports_cancel=true` |

System 注册入口必须校验 TaskProvider 标准 endpoint：详情和执行 endpoint 必须包含 `{task_type}` 与 `{id}`，状态 endpoint 必须包含 `{execution_id}`，并拒绝 `/provider/tasks` 旧路径。Orchestrator 只替换 `{task_type}`、`{id}`、`{execution_id}`，不再支持 `:task_id`、`{task_id}`、`:run_id` 等旧占位符进入 provider endpoint。

执行请求体建议统一为：

```json
{
  "trigger_type": "manual",
  "source": "orchestrator",
  "parent_execution_id": "uuid",
  "parameters": {}
}
```

其中：

- `trigger_type` 只能是 `manual` / `scheduled`。
- `source` 表示触发来源。
- `parameters` 是本次执行覆盖或模板化参数，不得直接改写任务定义。
- 如果 provider 不支持参数覆盖，必须明确拒绝，不得静默忽略。

执行响应必须返回本次执行的统一 `execution_id`。标准最小响应为：

```json
{
  "execution_id": "uuid",
  "status": "running"
}
```

模块如使用 `{ status, data }` 包装响应，`data.execution_id` 必须仍然是同一条 unified execution；顶层保留 `execution_id` 是推荐形态，便于 Orchestrator 直接建立父子追踪。

### 多任务类型 Provider

多任务类型模块采用同一套 provider endpoint，通过 `task_type` 分派到 owner 模块内部不同任务表和服务。

以 Manager 为例：

| provider | task_type | 任务定义表 | 执行 owner | 产物状态 |
| --- | --- | --- | --- | --- |
| `manager` | `mvt_generation` | `manager.mvt_tasks` | Manager | `manager.quick_view` / MVT tiles |
| `manager` | `embedding` | `manager.embedding_tasks` | Manager | `manager.embeddings` |

调用方式：

| 操作 | 示例 |
| --- | --- |
| 列出全部 Manager 任务 | `GET /tasks` |
| 只列出 MVT 任务 | `GET /tasks?task_type=mvt_generation` |
| 查询 MVT 任务详情 | `GET /tasks/mvt_generation/{id}` |
| 执行 MVT 任务 | `POST /tasks/mvt_generation/{id}/execute` |
| 查询 embedding 任务详情 | `GET /tasks/embedding/{id}` |
| 执行 embedding 任务 | `POST /tasks/embedding/{id}/execute` |

约束：

1. `task_id` 只在 `provider + task_type` 命名空间内唯一。
2. `common.task_executions` 关联任务定义时必须同时依赖 `module + task_type + source_task_id`。
3. Orchestrator Step 必须保存 `provider`、`task_type` 和 `task_id` 三元组。
4. Monitor 展示任务详情时也必须按 `module + task_type + source_task_id` 回查 owner provider，不得只按 ID 查。
5. 不应为了多任务类型把 Manager 拆成多个 provider，例如 `manager_mvt`、`manager_embedding`；这会让模块身份、健康检查、权限和前端入口分裂。

不同 `task_type` 可以有不同参数 schema、创建 URL、编辑 URL、是否支持内联执行、是否支持取消和是否支持定时。这些差异应写在 capabilities 的 `task_types[]` 中，而不是提升为 provider 顶层字段。

### 任务类型发现

平台需要预先知道一个 provider 能产生哪些任务类型，但这个“知道”来自 owner 模块声明，不来自 Orchestrator、Monitor 或 Common 的硬编码。

TaskProvider 注册时必须声明稳定的 `task_types[]`。每个 `task_type` 至少应包含：

| 字段 | 说明 |
| --- | --- |
| `type` | 稳定任务类型，例如 `mvt_generation` |
| `display_name` | 展示名称 |
| `description` | 任务类型说明 |
| `definition_schema` | 任务定义 schema，用于创建或编辑持久任务 |
| `execution_schema` | 执行参数 schema，用于本次执行参数覆盖或 inline execution |
| `supports_schedule` | 该任务类型是否支持定时 |
| `supports_cancel` | 该任务类型是否支持真实取消；不能中断执行体时必须为 `false` |
| `supports_inline_execution` | 是否支持无持久任务定义的一次性执行 |
| `create_url` / `edit_url` | owner 模块前端入口；优先使用 Console 模块路由，例如 `/develop/tasks?action=create&task_type=query` |

用途：

1. Orchestrator 前端展示可编排任务类型。
2. Orchestrator 保存 Step 前校验 `provider + task_type` 是否存在。
3. Orchestrator 执行 Step 时按 `task_type` 选择正确 endpoint 和参数 schema。
4. Monitor 展示 execution 时按 `module + task_type` 路由到正确的任务详情或产物状态。
5. Console 或模块前端需要创建任务时，跳转到 owner 模块声明的入口。

约束：

1. `task_type` 是 provider 对外契约，不能随 UI 文案变化。
2. Common 不维护全量业务 `task_type` 枚举，只维护公共字段、状态和触发类型。
3. Orchestrator 可以缓存 TaskProvider capabilities，但必须能从 System 刷新，不得把模块任务类型写死在代码里。
4. 模块新增或删除任务类型时，应更新自身 capabilities、文档和 Swagger。
5. 历史 execution 中已经出现的 `task_type` 不应被 owner 模块静默移除；如任务类型废弃，应在 capabilities 中标记为 deprecated，直到历史查询和迁移完成。

## 调度体系

调度定义归任务 owner 模块。

| 对象 | 责任 |
| --- | --- |
| owner task | 保存 `schedule`、`enabled`、`next_run_at`、`last_run_at` |
| owner scheduler | claim due task、创建 execution、投递 worker |
| common scheduler | 提供 Cron 解析和进程内调度工具 |
| common execution | 记录调度触发产生的一次 execution |

长期建议以 DB-driven due task claim 为主，进程内 Cron 只作为触发器或辅助工具。这样才能支持多实例、重启恢复、漏跑补偿和调度审计。

## 监控体系

Monitor 不拥有任务定义。Monitor 的职责是聚合观察：

| 层级 | 来源 | 监控内容 |
| --- | --- | --- |
| execution | `common.task_executions` | 状态、耗时、进度、错误、父子关系 |
| schedule | owner 任务表 | 是否启用、下一次运行、最近运行摘要 |
| runtime queue | Asynq / Redis / DB claim | pending、active、retry、dead、延迟 |
| artifact state | owner 模块 | 产物是否 ready、缓存位置、版本、失败原因 |
| provider health | System TaskProvider / module health | 模块是否可调用 |

Monitor 可以查询 owner 模块公开的只读状态 API，但不能直接依赖 owner 私有表结构。

当前已补齐 parent / child execution 树的后端和前端入口：Monitor 通过 `GET /api/v1/monitor/executions/{id}/tree` 按 `execution_id` 与 `parent_execution_id` 连接统一执行记录，用于查看 Orchestrator 编排执行及其子模块执行链路。

## 当前收敛状态

阶段 1 和阶段 2 已完成以下收敛：

1. `common.task_executions.source_task_id` 已收敛为字符串软引用。
2. Transfer 对外纳入任务体系时统一使用 `task_type=import`；Provider 详情和执行入口已收敛到标准 `/tasks/{task_type}/{id}` 与 `/tasks/{task_type}/{id}/execute`。
3. Orchestrator 调用下游 provider 时不再把 `orchestrator` 写入 `trigger_type`，而是写入 `source`。
4. Orchestrator 和统一 execution 成功状态使用 `success`，不再使用 `completed` 表达执行成功。
5. Orchestrator TaskProvider 模式已标准传递 `trigger_type`、`source`、`parent_execution_id` 和 `parameters`。
6. Orchestrator 定时触发创建 `trigger_type=scheduled` 的 orchestration execution。
