# ADDP 任务体系统一设计

> 状态：任务体系主干阶段已验收。正式约束见 [ADDP 任务体系规范](../spec/addp任务体系规范.md)。本文只保留接续摘要、验收矩阵和专题入口，不再重复展开规范细节。

## 一、主干结论

ADDP 不建立统一任务总表。`Task` 是抽象概念，不是跨模块实体表。

| 对象 | Owner | 存储 | 说明 |
| --- | --- | --- | --- |
| 任务定义 | 业务 owner 模块 | owner 模块私有表 | 稳定配置，表达未来如何处理什么对象 |
| 执行记录 | Common | `common.task_executions` | 单次执行历史，记录状态、进度、结果和错误 |
| 调度定义 | 任务定义 owner | owner 模块私有表 | `enabled`、`schedule`、`next_run_at` 等 |
| 运行时队列 | 执行 owner | Redis / Asynq / DB claim / 进程内队列 | execution 投递和 worker 执行机制 |
| 产物状态 | 产物 owner 模块 | owner 模块私有表或 artifact manifest | 当前产物是否可用、在哪里、由什么配置生成 |
| 编排定义 | Orchestrator | `orchestrator.orchestrations` | 任务级 DAG，只引用已有任务定义 |

核心边界：

1. `common.task_executions` 只统一 execution，不吞并各模块任务定义。
2. Orchestrator 只编排已存在的 owner 任务定义，不创建业务任务。
3. Monitor 只聚合观察 execution、调度、队列、产物和 provider health，不成为任务 owner。
4. TaskProvider 按模块注册，一个 provider 可通过 `task_types[]` 声明多个任务类型。
5. Step 固定引用 `provider + task_type + task_id`。
6. `trigger_type` 只允许 `manual` / `scheduled`；跨模块来源写 `source`。
7. execution 成功态统一为 `success`，不得用 `completed` 表达执行成功。

## 二、当前任务类型矩阵

| provider | task_type | 任务定义 owner | create/edit 入口 |
| --- | --- | --- | --- |
| `meta` | `scan` | `meta.scan_tasks` | `/meta/scan` / `/meta/scan?task_id=:id` |
| `transfer` | `import` | `transfer.transfer_tasks` | `/transfer/tasks/create` / `/transfer/tasks/:id/edit` |
| `develop` | `query` | `develop.dev_tasks` | `/develop/sql?action=create` / `/develop/sql?action=edit&id=:id` |
| `develop` | `workflow` | `develop.dev_tasks` | `/develop/workflow?action=create` / `/develop/workflow?action=edit&id=:id` |
| `develop` | `script` | `develop.dev_tasks` | `/develop/notebook?action=create` / `/develop/notebook?action=edit&id=:id` |
| `manager` | `tile_cache_generation` | `manager.tile_cache_tasks` | `/manager/tile-cache?tab=tasks` / `/manager/tile-cache?tab=tasks&task_id=:id` |
| `manager` | `quick_view_optimization` | `manager.quick_view_optimization_tasks` | `/manager/quick-view-optimization?tab=tasks` / `/manager/quick-view-optimization?tab=tasks&task_id=:id` |
| `manager` | `embedding` | `manager.embedding_tasks` | `/manager/vectorization-tasks` / `/manager/vectorization-tasks?task_id=:id` |
| `quality` | `check` | `quality.check_tasks` | `/quality/check-tasks` / `/quality/check-tasks?task_id=:id` |
| `graph` | `kg_build` | `graph.build_tasks` | `/graph/graphs` / `/graph/graphs/:graph_id/build/tasks/:id` |
| `orchestrator` | `orchestration` | `orchestrator.orchestrations` | `/orchestrator/orchestrations` / `/orchestrator/orchestrations/:id/edit` |

验收口径：

- Orchestrator 任务库能发现 7 个 provider、11 个 `task_type`。
- 所有 provider 均使用标准 TaskProvider endpoint：`/tasks`、`/tasks/{task_type}/{id}`、`/tasks/{task_type}/{id}/execute`、`/executions/{execution_id}`。
- 当前没有 provider 声明标准取消能力；模块内部取消 API 不等于 TaskProvider 标准取消能力。
- `create_url` / `edit_url` 是 owner 模块专属页面入口，不指向任务管理集散页。

## 三、已完成收敛

### 规范和注册

- 正式规范已沉淀到 [ADDP 任务体系规范](../spec/addp任务体系规范.md)。
- `source_task_id` 已统一为字符串软引用，回查任务定义必须结合 `module + task_type`。
- System 注册入口已校验 TaskProvider 标准 endpoint 后缀。
- System 注册入口已校验 capabilities：稳定 `task_type`、对象 JSON Schema、inline 禁止、cancel endpoint 双向一致。
- 非标准 provider endpoint 已拒绝进入注册表，例如 `/provider/tasks`、`/scan/runs/{execution_id}`、`/tasks/{id}/run`。

### Orchestrator

- 保存编排时校验 `provider + task_type` 已由 capabilities 声明，且不得引用 deprecated 类型。
- 执行下游任务时传递 `trigger_type`、`source`、`parent_execution_id`、`parameters` 和 `X-Tenant-ID`。
- `depends_on` 已修正为“当前步骤依赖的前置步骤”，执行器先执行依赖，再执行当前步骤；缺失依赖直接失败。
- 已删除旧直连模块客户端，不再保留 `/api/scan/runs`、`run_id`、`/api/cache/tasks` 等非 TaskProvider 路径。
- Orchestrator 自身已作为 `task_type=orchestration` 的 TaskProvider，可被其他编排引用。

### Develop

- 对外只声明 `query` / `workflow` / `script` 三类任务。
- Notebook 是 `script` 的当前 UI 和运行时形态，不是独立 `task_type`。
- `/develop/tasks` 只作为任务定义集散页，不作为 TaskProvider 创建或编辑目标。
- TaskProvider 执行入口已校验路径 `task_type` 与真实 `DevTask.dev_type` 一致。
- 查询任务旧 `/query/tasks` CRUD 已删除，查询任务保存和列表改走统一任务定义路径。

### Manager

- Manager 作为单一 provider 声明 `tile_cache_generation`、`quick_view_optimization` 和 `embedding`，没有拆成 `manager_mvt` / `manager_quick_view` / `manager_embedding`。
- 标准 `/tasks` 入口作为 TaskProvider 任务库入口；模块私有 `/tile_cache_tasks`、`/quick_view_optimization_tasks` 和 `/embedding_tasks` 固定各自任务类型。
- 快显性能优化结果属于 `manager.quick_view_optimization` artifact state，不替代 `quick_view_optimization` execution。
- 持久化 embedding 任务执行复用任务服务创建的主 execution，避免一次用户意图产生多条主 execution。
- ad-hoc embedding 保留为 ad-hoc execution，不产生 owner 任务定义。
- QuickView 从“任务”命名收敛为 artifact state。

### Monitor 和 Console

- Monitor 已支持按全局 `execution_id` 查询详情和 parent / child execution 树。
- 各模块前端提交执行后统一调用 `common-frontend.openMonitorExecution(execution_id)`。
- Monitor 执行详情通过 TaskProvider capabilities 的 `edit_url` 回跳 owner 任务定义。
- Console 已支持 owner URL 深层路径和 query 透传。

## 四、已验证

运行态已验证：

- Orchestrator 任务库可发现 `meta`、`transfer`、`develop`、`manager`、`quality`、`graph`、`orchestrator` 七个 provider。
- Orchestrator 任务库可按 `scan/import/query/workflow/script/tile_cache_generation/quick_view_optimization/embedding/check/kg_build/orchestration` 返回可编排任务。
- 嵌套编排链路 `orch2 -> orch1 -> query` 可写入统一 execution 父子关系，Monitor 可通过 execution tree 查看链路。
- Orchestrator 执行列表、单编排执行列表和 Monitor 详情可从 `running` 刷新到最终状态。
- Develop 三类任务的 owner edit URL 已运行态验证能进入对应专属页面。

## 六、维护规则

- 主干规范改动先更新 [ADDP 任务体系规范](../spec/addp任务体系规范.md)，再同步实现。
- 模块内部语义、页面体验、产物状态和监控扩展不再继续堆回本文。
- 新增或删除任务类型时，必须同步 owner capabilities、Swagger、文档和 Orchestrator 任务库验证。
- Transfer 当前对外仍只声明 `task_type=import`；如需扩展导出、同步等类型，先进入 Transfer 专题确认。
