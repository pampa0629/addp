# 数据格式插件化架构设计

## 设计目标

统一 Manager、Meta、Transfer 三个模块对多种数据类型和文件格式的支持，通过插件化架构实现：
- ✅ **代码复用** - 避免重复实现相同的格式解析逻辑
- ✅ **易扩展性** - 新增格式支持只需实现插件接口并注册
- ✅ **职责清晰** - 每个模块专注自己的核心职能
- ✅ **开发友好** - 新开发者能快速上手添加新格式支持

---

## 当前架构分析

### 各模块的需求差异

| 模块 | 核心职责 | 对数据格式的需求 | 已有实现 |
|------|---------|----------------|---------|
| **Meta** | 元数据扫描和索引 | 需要**提取元数据**（字段、类型、统计信息）<br>不需要读取完整数据内容 | ✅ `scanner.MetadataExtractor` 注册表<br>位于 `meta/backend/internal/scanner/` |
| **Manager** | 数据预览和浏览 | 需要**预览部分数据**（前N条记录、缩略图）<br>需要展示目录结构 | ✅ `service.PreviewProvider` 注册表<br>位于 `manager/backend/internal/service/` |
| **Transfer** | 数据传输和转换 | 需要**完整读写数据**<br>支持批量处理和流式传输 | ✅ `pipeline.Reader/Writer` 注册表<br>位于 `transfer/backend/internal/connector/` |

### 当前实现对比

#### 1. Meta 模块：元数据提取器注册表

**位置**: `meta/backend/internal/scanner/`

**核心接口**:
```go
type MetadataExtractor interface {
    SupportedTypes() []string  // 支持的 MIME 类型
    Priority() int             // 优先级（高优先级优先匹配）
    Extract(ctx context.Context, input ExtractInput) (*Metadata, error)
}
```

**注册机制**:
```go
// 全局注册表（单例）
func Register(extractor MetadataExtractor)

// 在 init() 中自动注册
func init() {
    scanner.Register(&GeoJSONExtractor{})
    scanner.Register(&PDFExtractor{})
    scanner.Register(&ImageExtractor{})
}
```

**已实现的提取器**:
- ✅ GeoJSONExtractor - 地理空间数据
- ✅ CSVExtractor - 表格数据
- ✅ PDFExtractor - PDF文档
- ✅ ImageExtractor - 图像元数据
- ✅ SQLiteExtractor - SQLite数据库
- ✅ DefaultExtractor - 兜底处理器（通配符 `*/*`）

#### 2. Manager 模块：预览插件注册表

**位置**: `manager/backend/internal/service/`

**核心接口**:
```go
type PreviewProvider interface {
    Name() string
    Priority() int
    Supports(*PreviewRequest) bool
    Preview(context.Context, *PreviewRequest) (*models.TablePreview, error)
}
```

**注册机制**:
```go
// 实例化注册表
registry := NewPreviewRegistry()
registry.Register(provider)

// 按优先级自动排序
registry.Resolve(req) // 返回第一个支持的 provider
```

**已实现的提供者**:
- ✅ ObjectStoragePreviewProvider - 对象存储（MinIO/S3/OSS）
  - 支持文本、JSON、GeoJSON、图片、PDF、Office文档预览
  - 内部使用 `ObjectContentRegistry` 管理不同文件格式的处理器
- ✅ PostgresPreviewProvider - PostgreSQL 数据库表预览
- ✅ NodePreviewProvider - 目录/Schema 节点预览

#### 3. Transfer 模块：数据连接器注册表

**位置**: `transfer/backend/internal/connector/`

**核心接口**:
```go
type Reader interface {
    Open(ctx context.Context, config ConnectorConfig) error
    Read(ctx context.Context) (*DataBatch, error)
    Schema() (*Schema, error)
    Close() error
}

type Writer interface {
    Open(ctx context.Context, config ConnectorConfig) error
    Write(ctx context.Context, batch *DataBatch) error
    Close() error
}
```

**注册机制**:
```go
// 全局注册（启动时调用）
func MustRegisterReader(connectorType string, factory ReaderFactory)
func MustRegisterWriter(connectorType string, factory WriterFactory)

// 在 builtin_registration.go 中统一注册
func init() {
    MustRegisterConnector("shapefile", NewShapefileReader, NewShapefileWriter)
    MustRegisterConnector("geojson", NewGeoJSONReader, NewGeoJSONWriter)
    MustRegisterConnector("geopackage", NewGeoPackageReader, NewGeoPackageWriter)
}
```

**已实现的连接器**:
- ✅ ShapefileReader/Writer - Shapefile 格式
- ✅ GeoJSONReader/Writer - GeoJSON 格式
- ✅ GeoPackageReader/Writer - GeoPackage 格式
- ✅ JDBCReader/Writer - 数据库（PostgreSQL/MySQL等）
- ✅ S3Reader/Writer - 对象存储
- ✅ FileReader/Writer - 本地文件系统

## 统一插件化架构方案

### 架构原则

**三层架构 + 一个共享层**:

```
┌─────────────────────────────────────────────────────────┐
│                   Common Format SDK                     │
│              common/format/ (共享层)                    │
│                                                          │
│  - 格式识别工具 (MIME type detection)                   │
│  - 基础格式解析器 (可选的共享实现)                       │
│  - 统一的元数据模型 (schema definitions)                │
│  - 测试工具和mock                                        │
└─────────────────────────────────────────────────────────┘
           ▲                  ▲                  ▲
           │                  │                  │
┌──────────┴─────┐   ┌────────┴────────┐   ┌────┴────────────┐
│  Meta Module   │   │ Manager Module  │   │Transfer Module  │
│ (元数据提取)    │   │  (数据预览)     │   │  (数据传输)     │
│                │   │                 │   │                 │
│ Extractor      │   │ Preview         │   │ Reader/Writer   │
│ Registry       │   │ Registry        │   │ Registry        │
│                │   │                 │   │                 │
│ 专注：         │   │ 专注：          │   │ 专注：          │
│ - 快速扫描     │   │ - 部分加载      │   │ - 完整读写      │
│ - 统计信息     │   │ - 渲染友好      │   │ - 批量处理      │
│ - 索引构建     │   │ - 响应速度      │   │ - 流式传输      │
└────────────────┘   └─────────────────┘   └─────────────────┘
```

### 核心设计决策

#### ✅ 决策1：各模块保持独立的注册表

**理由**：
- Meta、Manager、Transfer 的需求差异巨大，无法用统一接口抽象
- 每个模块的性能优化目标不同（Meta注重速度、Transfer注重吞吐量、Manager注重响应）
- 模块间依赖最小化，便于独立部署和测试

**实现**：
- Meta: `scanner.MetadataExtractor` 接口 + 全局注册表
- Manager: `service.PreviewProvider` 接口 + 实例注册表
- Transfer: `pipeline.Reader/Writer` 接口 + 工厂注册表

#### ✅ 决策2：创建 common/format 共享层

**共享内容**：
1. **格式识别工具** (`common/format/detection.go`)
   - MIME type 检测（基于文件扩展名、magic bytes、内容检查）
   - 统一的格式类型常量

2. **可选的基础解析器** (`common/format/parsers/`)
   - 仅提供底层解析能力（不含业务逻辑）
   - 各模块可选择使用或自行实现

3. **统一的Schema模型** (`common/format/schema.go`)
   - 字段类型定义（string, int, float, geometry, etc.）
   - 数据类型映射（PostgreSQL → 通用类型 → Shapefile）

**不共享内容**：
- ❌ 不共享 Extractor/Provider/Reader/Writer 实现
- ❌ 不共享注册表逻辑
- ❌ 不共享模块特定的配置和缓存

#### ✅ 决策3：规范化格式支持矩阵

创建统一的格式支持文档，明确标注哪些格式在哪些模块中支持：

| 格式 | Meta (元数据) | Manager (预览) | Transfer (传输) | Common (解析器) |
|------|--------------|---------------|----------------|----------------|
| **Shapefile** | 🔵 计划中 | 🔵 计划中 | ✅ 已实现 | ✅ 已实现 |
| **GeoJSON** | ✅ 已实现 | ✅ 已实现 | ✅ 已实现 | 可选 |
| **GeoPackage** | 🔵 计划中 | 🔵 计划中 | ✅ 已实现 | 可选 |
| **CSV** | ✅ 已实现 | 🔵 计划中 | 🔵 计划中 | 可选 |
| **PDF** | ✅ 已实现 | ✅ 已实现 | - | 可选 |
| **Image** | ✅ 已实现 | ✅ 已实现 | - | 可选 |
| **SQLite** | ✅ 已实现 | 🔵 计划中 | 🔵 计划中 | 可选 |
| **PostgreSQL** | ✅ 已实现 | ✅ 已实现 | ✅ 已实现 | - |

package format

// FieldType 标准化字段类型
type FieldType string

const (
    FieldTypeString    FieldType = "string"
    FieldTypeInt       FieldType = "int"
    FieldTypeFloat     FieldType = "float"
    FieldTypeBool      FieldType = "bool"
    FieldTypeDate      FieldType = "date"
    FieldTypeTimestamp FieldType = "timestamp"
    FieldTypeGeometry  FieldType = "geometry"
    FieldTypeJSON      FieldType = "json"
)

// Field 字段定义
type Field struct {
    Name      string
    Type      FieldType
    Nullable  bool
    Size      int // 字符串长度或数值精度

// Schema 数据模式

    GeometryField  *string // 地理空间数据的几何字段名

## 最佳实践和开发规范

### 规范1：优先使用 common/format 工具

❌ **不好的做法**:
```go
// 在每个模块中重复实现格式检测
if strings.HasSuffix(filename, ".shp") {
    // ...
}
```

✅ **好的做法**:
```go
import "github.com/addp/common/format"

formatType := format.DetectFormat(filename, firstBytes)
if formatType == format.FormatShapefile {
    // ...
}
```

### 规范2：分离底层解析和业务逻辑

❌ **不好的做法**:
```go
// MetadataExtractor 中混杂大量文件格式解析代码
func (e *ShapefileExtractor) Extract(...) (*Metadata, error) {
    // 300行 Shapefile 解析逻辑
    // 50行元数据提取逻辑
}
```

✅ **好的做法**:
```go
import "github.com/addp/common/geo/shapefile"

func (e *ShapefileExtractor) Extract(...) (*Metadata, error) {
    // 使用共享解析器
    reader, err := shapefile.Open(filepath)
    if err != nil {
        return nil, err
    }
    defer reader.Close()

    // 专注元数据提取业务逻辑
    schema := reader.GetSchema()
    return &Metadata{
        BasicInfo: extractBasicInfo(reader),
        GeoInfo:   extractGeoInfo(schema),
    }, nil
}
```

### 规范3：保持各模块插件的自主性

- ✅ 各模块可以选择是否使用 common/format 的解析器
- ✅ 各模块可以根据性能需求定制实现
- ✅ common/format 仅提供**辅助工具**，不强制使用

### 规范4：统一错误处理

```go
// common/format/errors.go
package format

import "errors"

var (
    ErrUnsupportedFormat = errors.New("unsupported format")
    ErrInvalidSchema     = errors.New("invalid schema")
    ErrFormatDetection   = errors.New("format detection failed")
)
```

package extractors

import (
    "github.com/addp/meta/internal/scanner"
    "github.com/addp/common/format/parsers/parquet"

type ParquetExtractor struct{}

func (e *ParquetExtractor) SupportedTypes() []string {
    return []string{"application/x-parquet"}

    return 100
}

func (e *ParquetExtractor) Extract(ctx context.Context, input scanner.ExtractInput) (*scanner.Metadata, error) {
    reader, err := parquet.NewReader(input.TempFilePath)
    if err != nil {
        return nil, err
    }
    defer reader.Close()

    schema := reader.GetSchema()
    return &scanner.Metadata{
        BasicInfo: scanner.BasicMetadata{
            FileName: input.ObjectKey,
            FileType: "Parquet",
            // ...
        },
        CustomAttrs: map[string]interface{}{
            "row_count": reader.NumRows(),
            "columns":   len(schema.Fields),
        },
    }, nil
}

// 在 init.go 中添加注册
func init() {
    scanner.Register(&ParquetExtractor{})
    // ...
}

## FAQ

### Q1: 为什么不把所有格式解析器都放到 common？

**A**: 因为各模块的性能需求差异巨大：
- Meta 需要极快的扫描速度，可能只读取文件头部
- Transfer 需要高吞吐量，可能使用流式处理
- Manager 需要快速响应，可能使用缓存

强制共享实现会导致性能妥协。`common/format` 只提供**可选的**基础解析器。

### Q2: 如果同一格式在多个模块有不同实现，会不会导致行为不一致？

**A**: 通过以下方式保证一致性：
- ✅ 使用 `common/format/schema.go` 统一数据类型定义
- ✅ 编写集成测试验证跨模块行为
- ✅ 文档明确标注各模块实现的差异（如 Meta 只读前1000行）

### Q3: 新开发者如何知道某个格式是否已支持？

**A**: 查看 `docs/FORMAT_SUPPORT_MATRIX.md`（格式支持矩阵）

### Q4: 如何避免未来再次出现代码分散的问题？

**A**:
1. 所有新格式必须更新格式支持矩阵
2. PR Review 时检查是否可以使用 common/format
3. 每季度 Review 各模块的格式实现，合并重复代码

## 总结

### 架构核心思想

```
┌─────────────────────────────────────────────────────────┐
│             统一但不强制 (Unified but not Enforced)     │
├─────────────────────────────────────────────────────────┤
│ ✅ 统一格式识别                                         │
│ ✅ 统一数据类型定义                                     │
│ ✅ 统一文档和规范                                       │
│ ❌ 不统一业务逻辑                                       │
│ ❌ 不统一性能优化策略                                   │
│ ❌ 不统一实现方式                                       │
└─────────────────────────────────────────────────────────┘
```

### 开发者心智模型

**添加新格式支持时的思考流程**：

1. **这个格式需要在哪些模块支持？**
   - Meta: 需要元数据吗？
   - Manager: 用户需要预览吗？
   - Transfer: 需要导入导出吗？

2. **common/format 有可用的解析器吗？**
   - 有 → 使用它
   - 没有 → 评估是否值得添加（多模块复用？）

3. **在目标模块实现插件**
   - Meta → 实现 `MetadataExtractor`
   - Manager → 实现 `PreviewProvider`
   - Transfer → 实现 `Reader/Writer`

4. **注册插件**
   - Meta: 在 `extractors/init.go` 中调用 `scanner.Register()`
   - Manager: 在服务初始化时调用 `registry.Register()`
   - Transfer: 在 `builtin_registration.go` 中调用 `MustRegisterConnector()`

5. **更新文档**
   - 更新格式支持矩阵
   - 如果添加了 common/format 解析器，更新其 README
