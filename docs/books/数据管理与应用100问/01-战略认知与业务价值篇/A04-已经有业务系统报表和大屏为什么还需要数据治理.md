# A04 已经有业务系统、报表和大屏，为什么还需要数据治理？

已有建设是开展数据治理的重要基础。是否还需要补充治理工作，要看当前的数据能否满足使用要求，以及新的业务问题出现后，组织能否在已有成果上继续开展工作。

系统数量多、报表齐全，说明已经投入了不少资源，但不能仅据此判断数据使用中的问题都已解决。同样，也不能因为准备开展治理，就把原有建设一概否定。

## 已有系统各自解决了重要问题

业务系统承载日常办理，记录业务过程，也可能已经提供相应的分析能力。报表帮助人员查看结果，BI 支持查询、比较和下钻，大屏便于集中观察重要情况。这些能力都可以直接服务业务。

例如，合同系统记录签订和变更，项目系统管理交付过程，客户服务系统记录问题与处理情况。各系统围绕自己的使用者和业务要求组织数据，有各自的工作重点。

这些差异往往有合理原因。负责合同的人关心约定内容，交付人员需要掌握实施进度，服务人员则要跟踪客户反馈。把不同活动都放进一个系统，或者让所有人只使用同一张报表，未必能让工作更顺畅。

因此，治理首先需要了解已有建设：哪些数据已经可信，哪些规则已经明确，哪些能力可以继续使用，业务人员在哪些环节仍然需要额外收集和核对资料。已有成果应当成为后续工作的起点。

## 单个系统可用，跨系统分析还需要什么

以下用一个匿名的集团项目分析情境说明。

假设集团已有合同、项目交付和客户服务系统，各部门能够完成日常工作，也能生成自己的报表。现在，管理者希望按行业产品线了解项目交付情况，以及交付后出现的问题。

这个问题需要把几类记录联系起来。一个项目可能涉及多个合同或多个产品，客户反馈又可能以服务工单记录。如果各系统使用不同标识，就需要确认它们怎样对应。只有名称相近，未必足以证明是同一个项目。

即使对象已经关联，业务含义仍需澄清。不同记录中的“完成”，可能指不同事件：

| 记录 | 需要核对的业务含义 |
| --- | --- |
| 合同记录 | 合同签订、变更还是履行结束 |
| 交付记录 | 某个阶段完成、项目验收还是全部交付结束 |
| 服务记录 | 一次问题处理完成，还是服务期结束 |

这些状态可以各自正确，却不适合直接混合统计。分析前要明确本次关注哪一类事件，采用什么范围和时间口径。

产品归属也可能影响结果。若一个项目使用多种产品，一条问题记录应该关联到哪个产品，需要有具体依据。把项目中的所有问题都重复计入每条产品线，可能使比较失去意义。暂时不能明确归属的记录，应把缺口说明白。

把数据放进同一个大屏，可以让差异更容易被看到，却不会自动解决对象对应、状态含义和统计范围的问题。通过分析工具建立关联和计算时，也需要有人确认这些依据。

治理在这里要补足的是跨系统使用所需的共同认识与执行安排，同时保留各系统服务原有业务的能力。

## 在已有建设上补齐能力

围绕上述分析需求，可以先明确几个关键事项：项目与合同、产品和服务记录怎样关联，采用哪种交付状态，问题记录按什么规则归属，以及结果由谁核对。

再检查这些要求怎样进入已有数据链路。对象关系是否已有维护位置，相关字段能否取得，现有模型是否适用，报表计算是否遵循确认的口径。问题可能出在来源记录，也可能出在中间加工或最终统计，应当找到相应环节处理。

其中一部分能力可能已经具备，只是不同团队没有统一使用。比如，项目系统已经有稳定的标识，分析时就应优先利用；产品归属如果已有明确维护责任，就应从那里取得，而不让每个报表制作人员重新判断。

需要新增的能力也应与实际缺口对应。可能需要补充数据关联、质量检查或更新机制，也可能需要改进责任分工与变更通知。具体由哪个系统承担，要结合已有能力和后续维护条件决定。

业务系统可以包含分析与治理能力，BI 工具也可能支持模型、指标和权限管理。软件名称并不能代替实际能力评估。现有工具能够满足要求时，应当复用；只有发现明确不足，才需要进一步讨论扩展或新的建设。

因此，开展数据治理并不必然意味着再增加一套独立软件。平台是否需要建设、怎样组合，将在后面的平台篇讨论。本问首先关注的是业务要求有没有落实到数据与使用过程。

## 让分析结果回到业务工作

报表和大屏做好以后，还要观察使用者如何利用结果。

在这个情境中，假设某类项目的客户问题记录较多，业务人员应能够查看相关项目、产品和问题明细，核对是不是统计范围不同、记录方式不同，或确实存在值得调查的情况。

经过核实后，相关团队再判断需要改进什么。可能是产品本身的问题，也可能涉及实施方法、使用培训或服务安排。数据为这项判断提供依据，具体结论仍需要结合业务调查。

后续工作可以继续在已有系统中开展：产品团队维护改进任务，交付团队调整实施安排，服务团队跟进客户问题。处理结果再进入分析，帮助组织观察变化、评价改进，而不必把所有操作搬到治理平台里。

当项目关联、状态定义和问题分类逐步稳定后，同一批成果还可以支持其他分析。不同报表能够复用经过确认的数据和口径，减少各自取数、解释和计算的重复工作。新的使用需求也会帮助团队发现还需要补充哪些信息。

准备开展治理时，可以从一份业务人员真正使用的报表入手，沿着一个结果查回来源：它怎样计算，相关对象如何对应，异常在哪里处理，业务人员拿到后会做什么。哪些已有能力值得保留、哪些工作仍然缺失，会比只对照软件功能清单更容易看清。
