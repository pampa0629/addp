## 新书定位与本轮讨论

本书围绕业务需要介绍数据管理机制、技术能力与应用方法，帮助读者理解如何组织和使用分散在多个系统、多个来源中的数据，支撑业务协同、分析判断和智能应用，并持续探索新的价值。数据治理保持其决策权、责任、规则及落实监督的专业含义；建模、加工、服务和分析分别按其专业职责介绍，不一概改称治理。

本书聚焦数智化转型中的数据管理与应用，不承诺覆盖组织整体转型；数据中台作为可讨论的建设方式，不预设为必选路线。“增值”包括效率、判断、协同、风险控制和新业务机会，不限于数据交易或直接收入。

## 读者与用途

作者在专注时空相关行业的集团公司中负责数据平台产品研发，对具体项目主要提供产品与技术支撑；本次提供的几个项目并非作者直接参与实施。行业产品线与项目交付团队对数据治理的理解仍比较有限，本书首先服务于这些团队的科普和共同认知建设，同时面向部分重点客户发挥引领作用。

本书以时空行业实践为背景，讲清数据管理与应用如何进入产品规划和项目实施，以及数据治理在其中承担的职责。读者不需要预先具备完整的数据工程知识。

- 面向行业产品线：帮助理解业务问题、治理能力与产品价值的关系，支持需求判断和产品规划。
- 面向项目交付团队：帮助理解场景选择、实施范围、组织协作、验收和持续运营，支持项目落地。
- 面向重点客户：帮助建立合理预期，理解自身需要参与的决策、责任和长期投入。

工程技术内容保留，但以帮助读者理解方案、作出选择和开展协作为深度依据。时空数据、行业格式和多模态数据是本书的重要特色，既在相关专题中讲解，也通过案例贯穿全书。

## 已确认的写作与自查原则

以下原则来自作者对 08.12 和 01.01 的逐轮审阅，适用于后续新写、迁移和修改。每次开始书稿工作前先读本节，交稿前按文末自查项通读全文；不能只修作者标出的句子，而放过同类问题。

- 不再要求每问固定包含“一句话回答、分类、案例、误区、检查清单、小结”等全部栏目，结构由问题决定。
- 正文按内容层次分成小节，每节标题采用稍正式、简明的表达，概括本节内容，让读者浏览标题就能把握全文脉络；小节数量和名称随问题调整，案例在各节之间保持连贯。
- 开头呼应标题中的对象和问题，可以由具体现象自然引出疑问，再承接说明解决办法；保留帮助理解的重复与过渡，避免同一结论反复论述。
- 将抽象原则落实为具体参与者、动作、依据和结果，减少口号、排比和过度铺陈。
- 标题与正文都要避免歧义，不为简洁压缩动作、对象及其关系。例如，“复核改进效果，评估日常维护成本”应分别说明要复核什么、要评估什么；成本涉及哪些具体工作，在正文中交代清楚。
- 按中文阅读习惯组织句段：前后对象保持一致，指代清楚，因果、转折与递进交代自然。每段围绕一个重点，不为追求短句和省字切断意思；该重复主语、补充过渡或合并句段时就写完整。涉及困难或改进时，说明谁在获取、理解或使用数据的哪个环节遇到什么问题，不用“目前做什么不方便”“完成以后”等省略对象和条件的措辞代替。专业细节围绕本问取舍，详细旁支留给相应问题。
- 同一个案例贯穿全文时，在所有小节之前先用“以下用一个……的典型情境说明”自然引入，再交代业务背景和项目内容，作为全文的共同背景；背景介绍后补上承上启下的语句，说明案例中的问题与后文各节的关系，再展开分节讨论。正文不附“不对应某个真实项目”等额外声明，情境身份及素材来源继续在案例库中记录。
- 只保留影响判断的条件与例外，不为追求面面俱到不断扩展旁支。
- 强化案例中的真实困难、分歧、取舍、失败与限制，避免所有案例都顺利完成。
- 区分材料记述、典型情境和假设示例；允许补写讲解所需的过程，不冒充作者亲历或原项目实绩。
- 案例统一采用匿名表述，不涉及具体地方，即使是网上已有的公开资料，也不在书稿中引入具名地方案例或相应链接。
- 明确区分通行定义、作者观点和项目经验；涉及标准、政策或产品事实时，在修订相应内容时核实来源和适用时间。
- 体现作者在时空行业产品研发与项目支撑中的判断，不将本书写成具体产品的功能说明。
- 概念区分采用已讨论的口径：广义数据管理涵盖数据全生命周期，数据治理是其中的治理职责，数据处理是具体操作。三者都可以服务业务价值，不以静态与动态、一次性与持续性或是否修改源数据划分；本书围绕数据管理与应用介绍相关专业能力，治理承担其中的决策、责任、规则及落实监督，不把所有操作改称治理。

### 已出现的问题与改法

| 容易重犯的问题 | 已确认的改法 |
| --- | --- |
| 标题说“数据产品和服务”，开头却只写“服务上线了” | 开头写完整：“数据产品和服务上线后……”。随后若只讨论其中一种，交代转换原因，不能无意漏掉对象。 |
| 写完“业务人员仍每天自己拼表”，马上跳到价值评价 | 先承接现象：“这是为什么呢？”再引出办法：“一个简单有效的办法是……”。保留问题与回答之间的联系，不机械照抄这两个句式。 |
| 把贯穿全文的案例放在第一节内部 | 案例引入语、业务背景和项目情况放在所有小节之前，明确它是全文共同讨论的情境。 |
| 案例背景结束后直接出现小节标题 | 补上过渡，说明案例暴露了什么问题、后面准备从哪些方面讨论。标题不能代替正文的逻辑衔接。 |
| 小节标题过于口语化，或压缩成含混词组 | 标题稍正式，概括本节内容；正文自然易懂。例如用“复核改进效果，评估日常维护成本”，不用“事情有没有变省心”或“复核改进效果与维护投入”。 |
| 写“目前做什么事情不方便”“完成以后希望有什么变化” | 写明谁需要利用数据完成什么工作，困难在获取、理解还是使用数据，解决哪些问题后希望改善什么。不能让读者猜测条件和对象。 |
| 以大量短句、短段追求口语化 | 按中文习惯把因果、转折、递进讲完整；允许必要的主语重复和自然的长短句组合，不把相连的意思拆碎。 |
| 为显得专业，把所有注意事项都塞进一问 | 围绕本问讲清几个重要判断，复杂职责、技术细节和例外留给对应问题；减少密度不能靠省掉关键条件。 |

### 交稿前逐项自查

1. **先读标题和开头。** 对象是否一致？现象、疑问和办法能否自然接上？有没有突然出现、没有解释的概念或指代？
2. **再读案例与各节的连接。** 全文案例是否先交代背景？进入分节前是否有过渡？每节标题是否准确概括其内容，前后段落是否接得上？
3. **逐句检查歧义与信息密度。** 谁在做什么、为什么做、在什么条件下成立，是否交代清楚？“它”“双方”“这些工作”等是否有明确指向？如果有两种读法，应直接改写；如果一句塞入太多意思，应分开解释。
4. **最后从头连续通读。** 按面向行业产品线、交付团队和客户的中文科普文章来读，检查是否需要回读才能理解。发现一处问题，要检查全文同类表达，不能只依赖编号、链接或字数校验。

自查的目的是让文章自然、清楚、容易理解，不为每篇强加相同节数、字数或固定栏目。08.12 和 01.01 是已确认的参考稿，后续文章按各自主题安排。
