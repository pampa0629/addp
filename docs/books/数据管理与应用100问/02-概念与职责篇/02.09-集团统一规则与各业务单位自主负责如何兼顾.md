# 集团统一规则与各业务单位自主负责，如何兼顾？

集团希望统一数据标准、目录、权限和服务入口，业务单位却有自己的业务流程、专业术语和工作节奏。规则过于集中，业务单位觉得什么都要报批；完全各自负责，又容易出现重复建设、口径不一和数据无法共享。两种担心都是真实的，关键是先分清哪些事情必须统一，哪些事情应由业务单位自己决定。

以下用一个集团内部成果共享的典型情境说明。集团下属多个业务单位长期承担规划、设计和咨询任务，各单位积累了项目成果、空间资料、分析模型和业务模板。集团希望通过统一目录和共享入口，让其他单位能够找到并复用已有成果；业务单位则担心专业资料被脱离原有用途使用，也担心统一审批会拖慢项目进度。

最初的做法是由集团平台团队集中登记所有成果，业务单位提交材料后等待统一审核。结果是目录更新不及时，单位私下保留自己的清单；另一种做法是完全放开，各单位自行命名、发布和授权，使用者又很难判断不同成果能否互相替代。

这个情境中的矛盾，不是集团要不要管，也不是业务单位要不要自主，而是统一规则、授权范围、业务责任和技术支持没有分层安排。下面从统一边界、授权分工、例外处理、平台支撑和持续监督几个方面说明，怎样让集团形成共同约束，同时保留业务单位对专业工作的责任。

## 一、先确定必须统一的共同约束

集团统一的内容，应当是跨单位共享和风险控制所必需的共同约束。比如，成果必须有明确的名称、来源、更新时间、责任单位、适用范围和使用限制；涉及敏感资料时，访问主体、审批要求和审计记录应当遵循共同规则；跨单位共享的对象标识、目录分类和基本状态也需要有可识别的共同约定。

这些约束解决的是“能不能找到、能不能理解、能不能安全使用”的共同问题，不等于集团要统一每个单位的专业方法。统一目录字段和来源说明，不代表所有单位必须使用同一种分析模型；统一访问和审计要求，也不代表所有项目都采用同样的审批层级。

确定共同约束时，要说明它服务的具体风险和业务需要。没有明确用途的统一字段，最后往往变成填表要求；没有适用范围的统一分类，反而会掩盖不同专业对象之间的差异。集团应优先规定共享所需的最小规则，再根据实际问题逐步增加共同要求。

## 二、把决定权和执行责任分给合适的主体

集团层面适合决定跨单位的共同政策、最低要求、共享范围和重大例外；业务单位负责本单位专业对象的定义、数据更新、成果适用性和使用反馈；平台团队负责提供目录、权限、版本、日志和服务等共性能力。三类职责不能相互替代。

例如，集团可以规定所有共享成果必须记录来源和更新时间，但某类规划成果应采用什么专业分类、什么指标和什么分析方法，应由熟悉该业务的单位负责。平台团队可以提供模板和校验规则，却不能仅凭字段是否填满就判断成果是否适合某项业务。

还要明确“谁可以发布”和“谁可以使用”不是同一件事。业务单位可以负责发布本单位确认的成果，集团按共同规则检查共享条件；使用者仍需根据项目目的、时间范围和专业限制作出适用性判断。把发布责任交给单位，不等于集团放弃监督；保留集团监督，也不等于所有使用申请都由集团逐项代办。

## 三、允许业务差异，但要把例外说清楚

业务单位之间确实会有不同的对象、术语、流程和成果形式。集团不必为了表面一致而强行合并这些差异，但差异必须能够被说明和识别。可以在共同目录下保留专业分类，在统一字段之外增加单位自定义字段，在共同服务入口中标明不同适用范围。

例外也应有边界。某单位因专业原因不能采用集团统一分类时，要记录不一致的内容、适用场景、责任人和转换方式；某项成果只允许在本单位内部使用时，要明确访问范围和原因；临时项目需要使用特殊数据时，要规定有效期限和到期处理。没有期限和责任人的“暂时例外”，很容易变成长期分裂的另一套规则。

当不同单位对同一对象使用不同名称时，不一定要立即选出一个名称替代全部名称。可以先建立名称之间的映射关系，说明各自的业务含义和使用场景；只有在跨单位统计、服务或安全控制确实需要统一时，再由有授权的主体作出取舍。这样既保留专业语言，也避免使用者把相似名称误认为同一对象。

## 四、用平台能力减少集中审批，而不是代替治理决定

统一平台的作用，是把共同规则落实得更容易。例如，目录模板可以提醒发布者补充来源和更新时间，权限模型可以按组织和成果范围控制访问，版本记录可以保留修改依据，工作区可以支持单位先在内部整理，再按约定范围发布。平台把规则变成可执行的流程，减少重复沟通和人工检查。

但平台不能自行决定某项成果是否适合业务，也不能通过把所有操作集中到一个账号来解决责任问题。业务单位仍需确认内容和适用范围，集团仍需处理跨单位争议和重大风险，平台团队则要保证授权、记录和技术运行符合约定。系统显示“已发布”，只说明完成了发布动作，不代表所有使用者都可以直接采用。

为了减少集中审批，可以按风险设置不同流程：一般成果由业务单位确认后按模板发布；跨单位共享或涉及敏感内容的成果，增加必要审核；重大例外和争议事项再提交集团层面决定。审批级别应与影响范围匹配，不能把所有低风险资料都按最高级别处理。

## 五、通过使用反馈和定期复核调整边界

统一规则和自主责任都不是一次确定以后永远不变。集团可以观察哪些成果被重复建设、哪些共享资料长期无人维护、哪些规则经常被申请例外；业务单位可以反馈模板是否增加了不必要的工作、共享限制是否影响项目推进，以及其他单位使用时最容易误解什么。

如果很多单位都需要同一种转换，说明这项能力可能适合纳入集团共性服务；如果某个统一字段长期无人使用，或者不同专业单位始终需要不同含义，就应重新评估它是否应当作为强制要求。复核的重点是规则是否仍然支持共享、责任是否仍然清楚，而不是单纯统计发布了多少成果。

边界调整时，要记录生效时间、受影响的单位、历史数据是否需要补充以及旧版本如何使用。规则变化不能只在平台后台修改，相关责任人和使用者都应知道变化原因及过渡安排。这样，集团统一要求才能随着业务发展逐步调整，而不是在集中和放任之间反复摇摆。

集团统一规则与业务单位自主负责，可以分别解决共同风险和专业差异。集团负责共同约束、重大取舍和跨单位监督，业务单位负责专业定义、内容维护和使用反馈，平台团队提供可复用的目录、权限、版本和审计能力；例外要有范围、理由、责任人和期限。

判断一项规则应由谁决定时，可以先问三个问题：它是否影响跨单位共享或共同风险，是否需要专业判断，出了问题由谁能够及时处理。答案清楚以后，再安排统一要求、单位自主和平台支撑的边界，治理就不会被误解为把所有决定集中到一个部门。
