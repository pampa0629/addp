## 二 数据与业务的关系

<a id="fig04"></a>

![图 04：数据与业务的关系](时空实践配图/图04.png)

<a id="p022"></a>

要充分理解数据治理，首先我们还是要回顾一下数据和业务的关系，从而了解“数据治理”从何而来。

<a id="p023"></a>

最初，要做的事情叫做“信息化建设”。也就是建设应用系统，把纸面流程电子化，把信息存储到数据库中。这个过程是：“业务产生数据”。在这个阶段，实际上不需要数据治理。

<a id="p024"></a>

等到信息化建设有初步成效，尤其是有了多个业务系统后；把多个业务系统中存储的数据进行融合和挖掘，通过数据来创新，从而服务于业务。这时就必须打破数据孤岛、统一数据标准，这个时候，数据治理就显得尤为重要。

## 三 应用场景与业务价值

<a id="fig05"></a>

![图 05：寻找有价值的应用场景](时空实践配图/图05.png)

<a id="p026"></a>

数据治理要做到真正‘为业务“的关键，是要找到数据治理能实现的应用场景。如果没有具体的应用场景，数据治理过程中，无论是数据的传输、存储、计算，还是人员和设备的投入，都是巨大的成本。没有实际的价值产出，数据治理很容易虎头蛇尾，无疾而终。

<a id="p027"></a>

那么，如何才能找到应用场景呢？ 是根据现有数据来找应用场景，还是先明确有价值的场景，再来确定需要哪些数据？

<a id="p028"></a>

其实，这是一个双向奔赴的过程。我们通过几个例子来阐述。

<a id="p029"></a>

第一个例子。在一些办公楼或者酒店，电梯内需要刷卡。如果能将刷卡信息与电梯的调度系统关联，就不必再手动按楼层，提高了电梯的运行效率。

<a id="p030"></a>

第二个例子。电商商铺需要资金周全，可能只要几万块钱，那么借贷方如何判断商铺的信用呢？对于银行而言，一方面是审查成本过高，另一方面电商的小商铺也没有什么可抵押的。所以这笔生意做不成。

<a id="p031"></a>

但对于电商平台而言，可以使用利用“商铺答复问题的时间”来判断商铺的勤勉度，再结合其他数据指标，就能在几分钟之内自动计算出商铺的可贷款额度。

<a id="p032"></a>

第三个例子。经济发达地区的土地资源有限，需要对当前的城市用地情况做一个盘点，识别出低效用地。这里需要定义什么是“低效用地”，比如包括：批而未供、供而未建、建后利用率低等等。

<a id="p033"></a>

这些就需要统筹各个相关环节业务系统中的数据，同时还要获取到相应的社会经济生产数据来进行综合计算。

<a id="p035"></a>

找到对应的应用场景，即使一开始只有一两个，才能验证数据治理的成果，奠定一个良好的开端。随着容纳进来的数据维度越多，应用场景也会不断累积发展。所以说，数据治理只有起点、没有终点。

## 四 业务增值的具体举措

<a id="fig06"></a>

![图 06：业务增值的三类举措](时空实践配图/图06.png)

<a id="p038"></a>

实践中要让“业务增值”，可以分为三类举措。

<a id="p039"></a>

第一类：面向业务管理，构建业务实体。

<a id="p040"></a>

这里需要强调的是：”业务管理“，即必须服务于管理。

<a id="p041"></a>

举个不一定恰当的例子：疫情期间，小区需要做防疫管控，那么就得看如何定义“防疫小区”？它并不完全等同于住宅小区，而是需要有围墙和明确的出入口；同时还要考虑商场和写字楼。

<a id="p042"></a>

再举个例子：同样说的是”道路路段“，测绘行业关心的是道路的连续性，地图导航关心的是路口和交通规则，交警则关心的是交通的拥堵情况。对路段的定义和管理自然会有所不同。

<a id="p043"></a>

这一部分涉及到的技术是业务建模，构建业务实体。

<a id="p045"></a>

第二类，是做指标计算，面向精细管理。

<a id="p046"></a>

举个例子：某手机厂家拥有多个型号的手机，线上线下都有销售渠道。那么，不同渠道、不同地区、不同型号、不同时间段的销售增长率、销售占比是多少等，这些就都是指标。这些都需要通过指标来分析，从而调整和优化经营策略。

<a id="p047"></a>

这部分涉及的技术是维度建模，限于时间和篇幅，就不展开论述了，有很多专业的书籍可供参考。

<a id="p048"></a>

第三类：相对更复杂了，往往需要进行算法开发，以实现特定的能力。

<a id="p049"></a>

例如，我们通过天气预报预测一片区域在未来某个时间段的降水量，如何推算出河流水位呢？这需要结合地形、河道等，进行水动力模型的分析计算。之前提到的电商商铺的贷款额度，也是需要通过计算和综合来得出的。

<a id="p050"></a>

这部分涉及的技术是算法和数据开发。

## 五 数据来源与鲜活度

<a id="fig10"></a>

![图 10：从业务价值转向数据本身](时空实践配图/图10.png)

<a id="p063"></a>

小结一下，我们已经了解了数据和业务的关系是”业务产生数据、数据反哺业务“，数据治理的核心目标就是让数据能为业务增值，具体的举措包括：构建业务实体、指标计算和开发算法实现业务创新等。

<a id="p064"></a>

下面我们来关注和数据本身相关的三个问题，分别是：”数据从何而来、如何保持鲜活度“，”为何需要时空数据的治理“，以及”为何要关注数据的标准、质量和安全“。

<a id="fig11"></a>

![图 11：数据来源与鲜活度](时空实践配图/图11.png)

<a id="p067"></a>

首先是数据从何而来，又如何保持鲜活度。

<a id="p068"></a>

数据的来源，核心肯定是从已有的业务系统中来，另外还有公开的数据，或者能够协调共享的数据；当然，也有一些数据是需要采购的。

<a id="p069"></a>

从数据的实时性上看，有些数据是定期更新的，例如公开或采购的数据，而有些数据，如业务数据，则是实时更新的。

<a id="p070"></a>

做数据治理，非常重要的一点就是必须要“保持数据的鲜活度”。这是因为数据治理的成果是要为业务的应用场景服务的。如果数据过时了，得到的成果自然也是不可靠的。例如，最新天气预报提供降水量已经发生变化，自然得用新的数据重新计算预测河流的水位高度。

<a id="p071"></a>

因此，就必须按照一定周期进行数据的汇聚，以保证数据的鲜活度和业务效果。根据实际业务的不同，数据汇聚分为定时汇聚和实时汇聚。这些能力背后，需要一个调度系统来支撑。

## 六 时空与全域数据

<a id="fig13"></a>

![图 13：时空数据参与治理](时空实践配图/图13.png)

<a id="p078"></a>

那么，为什么需要时空数据参与数据治理呢？是不是仅作为底图就可以了吗？

<a id="p079"></a>

这肯定不行。因为在自然资源、住建、水利等多个行业，时空数据本身就是业务数据的一部分，就是业务所管理的对象。同时，如果把时空数据和其它业务分别治理，也容易造成两者的割裂和不一致，导致最后的业务场景不可用。

<a id="p080"></a>

故而，不能把空间数据与其他业务数据隔离开，需要空间数据与非空间数据一体化的数据治理。

<a id="p081"></a>

同时，由于时空数据的特殊性，包括数据类型、数据格式、质量规则、分析算法、空间服务、地图展示等多个方面，和一般的属性数据有所不同。因此，通用的数据治理软件和工具无法解决这个问题，需要GIS业界提供针对性的、一体化的数据治理平台。

<a id="p082"></a>

其实，再进一步思考，很多行业都有其独特的数据类型和分析算法等。例如，地质行业有地震波数据，气象行业也有自己特定的数据格式。一个特定的数据治理平台，也无法一开始就能支持所有的数据格式，而用户肯定希望能够一体化管理和治理自己所有的数据。

<a id="p083"></a>

因此，数据治理平台必须支持数据类型和数据格式的可扩展性，才能满足更多行业对全域数据治理的需求。

## 七 数据标准、质量与安全

<a id="fig15"></a>

![图 15：数据标准、质量与安全](时空实践配图/图15.png)

<a id="p089"></a>

我们将全域的数据汇聚后，为什么要关注数据的标准、质量和安全呢？

<a id="p090"></a>

数据标准问题的来源是：原始数据来自多个业务系统和渠道，天然就存在数据形式不一致的可能性；例如坐标系不统一、数字字典不一样等。为了后续工作有意义，必须将数据统一到一个标准体系下。

<a id="p091"></a>

数据要服务于业务，和AI一样，存在“垃圾进，垃圾出”的问题。因此，必须从源头抓好数据质量。数据质量和数据标准的问题有所不同。数据标准的问题可以在数据治理环节，通过数据转换统一到一个标准下。而数据质量问题，虽然是在数据治理环节发现的，但要解决，一般都需要回到数据源头，也就是数据生产方来解决。

<a id="p092"></a>

数据安全是数据治理的基本要求，其重要性堪比守护神。其他工作做得再好，也是加分项，而一旦数据安全出现大问题，成果将直接归零，甚至变成负分。因为其他业务系统即便数据泄露，也只是单个系统的问题，而数据治理是先汇聚或者能访问到各方面的数据，因此，数据安全方面万万不能出问题。

## 八 数据底座与 DataOps

<a id="fig19"></a>

![图 19：从数据问题转向支撑体系](时空实践配图/图19.png)

<a id="p102"></a>

介绍完数据本身的三个问题，我们继续最后几个问题，分别是数据底座软件和AI大模型在数据治理中发挥的作用，  以及数据治理体系还包括哪些内容。

<a id="fig20"></a>

![图 20：底座软件的适用条件](时空实践配图/图20.png)

<a id="p105"></a>

前面我们也看到了不少数据治理软件的截图。这类软件可能叫做“数据治理平台”、”数据治理底座“、”数据中台“或”数据资源平台“等等。那么，数据治理实施，能否不用这类软件，自己手搓，也就是手工治理或硬编码实现呢？

<a id="p106"></a>

其实也行，但只适合以下几种情况：一是数据治理链路不多，且不复杂，靠人工能管得过来；二是变化不大，要求相对固定；或者是运行的间隔长，比如每三个月才需要处理一次数据。这时，手动也是可以的。

<a id="p107"></a>

但一旦：数据源多了，数据治理链路复杂了；要求变化快，如新增指标或指标含义变化；或者需要T+1，隔天就要新的数据成果。那么，手动或自己硬编码，肯定是无法应对的。

<a id="p108"></a>

举个程序员懂的例子，就像写一个只有三五个代码文件的小程序，自己用记事本其实也没问题；如果要写十个人一起工作几个月，有上百个代码文件的软件，肯定得使用集成开发环境（IDE）。

<a id="p110"></a>

数据治理底座软件所发挥的作用，还有一个专门的术语，叫做：DataOps。

<a id="fig21"></a>

![图 21：底座软件发挥的作用](时空实践配图/图21.png)

<a id="p111"></a>

其核心就是做到下面六个目标：

<a id="p112"></a>

剥离：将数据治理链路与底座软件系统的开发分离开；

<a id="p113"></a>

专注：使得数据工程师只需关注数据汇聚、数据建模等业务作业，从而大幅度降低数据治理从业者的技术门槛；

<a id="p114"></a>

高效：同时，新增数据加工链路可以在数天到数周内完成，相比软件开发动辄所需数月的时间，效率大大提高；

<a id="p115"></a>

管理：所有数据加工链路可以集中运维和查看，业务方能有效管理数据治理的产出；

<a id="p116"></a>

溯源：由于数据链路都在一个底座之上，可以提供数据血缘，便于错误溯源和修改后的影响分析。

<a id="fig22"></a>

**图 22：数据加工链路管理（匿名文字说明，非原图）**

- 编排连接多个算子，任务列表展示运行状态；总览展示资源与任务信息，血缘图连接来源、处理和结果。

再看几个功能截图。 一个是数据加工链路，可以通过编排方式实现，降低技术门槛；二是所有数据加工链路统一管理和运维；三是数据治理的全貌也能一目了然地看到；最后一个，数据资产的血缘关系也能被提炼和记录下来。

## 九 AI 辅助数据工作

<a id="fig24"></a>

![图 24：AI 与数据工作的相互支撑](时空实践配图/图24.png)

<a id="p124"></a>

从前面的介绍能了解到，数据治理是一个庞杂而繁琐的工作。 虽然有了数据治理底座软件的协助，做好数据治理仍然需要大量的时间和精力。

<a id="p125"></a>

AI大模型这几年发展迅猛，其本质是要解决人的脑力劳动。因此，一方面，我们可以在数据治理中嵌入大模型能力，让大模型有效地辅助人的工作；另一方面，大模型也需要可靠的高质量数据集和知识库，这些都需要以做好行业数据治理为基础。

## 十 组织、实施与持续运营

<a id="fig27"></a>

![图 27：组织与实施保障](时空实践配图/图27.png)

<a id="p134"></a>

数据治理作为一个体系，除了前面提到的内容外，还有两个方面也非常重要。

<a id="p135"></a>

一方面是开展数据治理的组织必须从战略高度上重视。这不仅仅是规整数据的技术工作，由于数据治理和业务创新紧密关联，必然需要高层领导的鼎力支持。从组织文化上，也需要有共识和认知基础。还需要有实际承接工作的组织结构实体，否则容易落空。

<a id="p136"></a>

另一个方面是在实施过程中，若是首次开展数据治理工作，最好有一个咨询培训的过程，做好现状评估和顶层设计。实施时，除了引入实施团队外，业主单位也必须深度参与，只有业主才能评判应用场景和业务价值。同时，实施应分阶段进行，逐步投入，逐步见效。

<a id="p137"></a>

在运维方面，数据治理与一般的软件系统有一个显著的不同之处，那就是需要日常监控数据加工链路，确保能够持续产出合格的数据成果。这不仅仅是保证软件功能正常运行，因为定期汇聚数据本身也在刷新，而支撑数据汇聚和数据计算的软硬件软件也有可能出现问题，这些都需要持续监控和排查。

我们再整体回顾一下数据治理体系实现”让数据为业务增值“的九个问题。
