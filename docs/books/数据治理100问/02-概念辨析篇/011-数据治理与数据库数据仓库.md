# 011 数据治理与数据库、数据仓库是什么关系？

## 一句话回答

> 业务数据库负责支撑业务系统并记录业务事实，数据仓库负责面向分析重新组织来自多个系统的数据，数据治理则贯穿从数据产生、汇聚、建模到分析使用的全过程，确保数据含义统一、质量可靠、来源可追溯并持续服务业务。

数据库和数据仓库都是承载数据的技术系统，数据治理则不是另一种数据库。它决定哪些数据需要汇聚、如何统一、由谁负责、达到什么质量要求，以及最终形成的数据如何用于分析、服务和业务决策。

## 一、业务数据库是业务系统的后台

多数业务系统都需要数据库保存运行过程中产生的数据。例如，客户系统记录客户和联系活动，订单系统记录下单与履约，财务系统记录凭证和收付款，自然资源业务系统记录调查、登记、规划和审批事项。

这类数据库主要面向日常业务操作，通常称为联机事务处理系统，即 OLTP（Online Transaction Processing）。它需要支持：

- 大量用户同时查询和写入；
- 单条或少量记录的快速增删改查；
- 事务的一致性和完整性；
- 业务操作失败后的回滚和恢复；
- 当前业务状态的准确记录。

业务数据库首先服务本系统的业务流程。表结构、字段和状态通常围绕某个应用设计，不一定适合跨系统分析。

## 二、业务数据库通常是数据仓库的重要来源

数据治理和经营分析需要了解跨业务、跨时间的数据。例如，单个审批系统知道某次审批的状态，但土地全生命周期分析还需要关联调查、权属、规划、供地、建设、验收和利用评价等信息。

这些数据往往分散在不同业务系统的数据库中。因此，传统而常见的技术路径是：

```mermaid
flowchart LR
    A["业务系统"] --> B["业务数据库 OLTP"]
    B --> C["采集、汇聚与标准化"]
    C --> D["数据仓库 OLAP"]
    D --> E["指标、报表和数据服务"]
    E --> F["业务分析和管理行动"]
    F --> C
```

业务数据库是数据仓库最重要的来源之一，但不是唯一来源。文件、接口、消息队列、物联网数据、空间数据、影像、BIM、文档和外部数据也可能进入分析体系。

## 三、为什么不能直接在业务数据库上做所有分析

业务数据库当然可以执行查询和统计，但如果把复杂的跨系统分析直接压在生产数据库上，通常会遇到几个问题：

1. **影响业务运行**：大范围扫描、关联和聚合会消耗大量计算与存储资源；
2. **难以跨系统关联**：不同系统的编码、颗粒度和口径往往不一致；
3. **缺少历史变化**：业务表经常只保留当前状态，而分析需要了解一段时间内的变化；
4. **模型不适合分析**：面向事务设计的规范化表结构，可能需要多次复杂关联才能回答一个经营问题；
5. **权限边界不同**：业务系统权限面向具体操作，分析使用则可能需要跨部门、跨数据域重新授权。

数据仓库的作用，就是把分析负载从业务系统中分离出来，并围绕分析主题重新组织数据。

## 四、数据仓库面向分析组织数据

数据仓库通常用于保存经过汇聚、清洗、标准化和建模的数据，并保留必要的历史。它主要面向联机分析处理，即 OLAP（Online Analytical Processing）。

典型数据仓库会按照业务需要形成不同层次：

- 原始或贴源层：保留从业务系统采集的数据；
- 标准化和明细层：统一业务对象、编码和颗粒度，形成可复用明细；
- 汇总和语义层：按区域、时间、产品、项目等维度进行汇总；
- 指标和应用层：形成报表、数据服务和专题分析需要的结果。

这些名称并不是唯一标准，具体分层也不必机械照搬。分层的本质是保留来源和历史，减少重复加工，并让业务语义、明细事实和汇总指标具有清晰边界。

## 五、数据库和数据仓库的技术要求不同

| 维度 | 业务数据库 | 数据仓库 |
| --- | --- | --- |
| 主要用途 | 支撑业务系统日常交易 | 支撑跨系统分析和决策 |
| 数据特点 | 当前、明细、频繁增删改 | 历史、整合、明细和汇总并存 |
| 典型操作 | 单条查询、写入、更新和事务 | 大范围扫描、关联、聚合和指标计算 |
| 设计重点 | 一致性、低延迟、高并发、事务可靠 | 查询吞吐、历史追踪、维度分析和批量计算 |
| 常见建模 | 面向业务流程的关系模型 | 事实表、维度表、明细层和汇总层 |
| 常见优化 | 索引、事务、锁和规范化设计 | 分区、列式存储、预聚合和适度反规范化 |

因此，数据库和数据仓库虽然都保存表和记录，内部采用的存储结构、索引策略、建模方式和查询优化重点可能明显不同。

这也不是绝对的产品分类。现代数据库可能同时提供事务和分析能力，数据仓库也可能支持近实时写入。判断它们的核心依据仍然是主要工作负载和使用目标。

## 六、数据治理在这条链路中做什么

把数据从业务数据库同步到数据仓库，是数据集成或数据工程活动；只有进一步解决语义、责任、质量、变化和业务使用问题，才形成数据治理。

数据治理至少要回答：

### 1. 汇聚什么数据

从业务目标和应用场景出发，确定需要哪些业务系统、表、字段、文件和外部数据，避免没有用途的全量搬迁。

### 2. 哪个来源最权威

同一个客户、地块、项目或机构可能出现在多个系统中。治理需要确定各类属性的权威来源，并规定冲突时如何处理。

### 3. 如何统一业务含义

不同系统中的名称、编码、时间、状态和统计颗粒度可能不同。数据标准和模型需要将它们统一到能够共同分析的业务语义上。

### 4. 如何保证质量和鲜活度

治理需要设置完整性、一致性、准确性和及时性要求，明确质量责任，并监控数据是否按约定周期进入仓库。

### 5. 如何管理历史和血缘

使用者需要知道数据来自哪里、经过哪些加工、采用哪个版本，以及源系统变化会影响哪些指标和服务。

### 6. 如何进入业务场景

最终成果要被报表、分析、数据服务、模型或业务流程实际使用，并根据使用效果持续调整数据范围、模型和规则。

## 七、案例：土地全生命周期监管

土地调查、登记、规划、供地、审批、建设和利用评价通常由不同业务系统支撑，每个系统的数据库都准确记录自己的业务事项。

如果要分析一块土地从权属、规划到开发利用的完整过程，就需要把多个业务数据库中的数据汇聚到面向分析的数据仓库中，并围绕统一地块标识建立关联。

在这个过程中：

- 业务数据库继续负责记录正式的权属、用途、审批和项目状态；
- 数据仓库保存跨系统整合后的地块、项目和事件明细，以及历史变化；
- 分析层计算开发强度、闲置时间、审批进度和低效用地识别结果；
- 数据治理确定权威来源、业务口径、质量规则、更新周期、责任和使用边界；
- 业务人员根据分析结果开展规划审批、项目监管、盘活和再开发。

当某块土地的权属或利用类型发生变化，正式数据应由相应业务系统记录，仓库再捕获变化、保留历史、重新计算受影响的指标，并将结果传递给相关业务场景。

## 八、大数据平台处在什么位置

传统数据仓库可以建立在专门的分析型数据库上。随着数据规模、类型和处理方式增加，组织可能建设大数据平台，提供分布式存储、批量计算、流处理、资源调度和多类型数据管理能力。

大数据平台可以承载数据采集、数据湖、数据仓库、实时计算和分析任务，但它仍然是技术基础设施，不能自动完成业务语义统一、责任划分、质量整改和价值运营。

大数据平台、数据中台和数据治理平台之间的区别，将在下一问专门讨论。

## 九、常见误区

### 误区一：把业务数据库的数据全部复制过来就是治理

复制只完成了数据采集。没有业务目标、统一语义、质量规则和使用场景，数据仓库可能只是另一个更大的数据堆积区。

### 误区二：数据库中的数据正确，仓库结果就一定正确

源数据正确不代表跨系统关联、历史处理和指标计算正确。编码映射、统计颗粒度、时间口径和业务规则都可能产生差异。

### 误区三：建设数据仓库以后不再需要治理源头

数据仓库不能代替业务系统生产正确数据。源头问题需要回到责任部门和业务系统整改，不能长期依赖仓库中的修正逻辑掩盖。

### 误区四：数据治理就是建设数据仓库

数据仓库是治理成果的重要承载者，但治理还包括组织、责任、标准、质量、安全、运营和业务价值评价。

## 十、实践检查清单

1. 是否明确业务数据库和数据仓库各自承担的职责？
2. 是否知道每项分析数据的权威来源？
3. 汇聚范围是否由业务场景决定，而不是默认全量复制？
4. 是否统一跨系统对象、编码、时间和统计颗粒度？
5. 数据仓库是否保留必要的历史、版本和加工血缘？
6. 质量问题是否能够反馈到业务系统由责任人整改？
7. 分析结果是否进入实际业务场景并持续获得反馈？
8. 数据规模和处理要求是否真的需要大数据平台？

## 结语

业务数据库面向日常交易，负责准确记录业务事实；数据仓库面向分析，负责跨系统整合、保留历史并重新组织数据；数据治理则确保这条链路具有统一语义、可靠质量、清晰责任和实际业务价值。

数据库和数据仓库解决的是不同工作负载下如何保存和处理数据，数据治理解决的是这些数据为什么汇聚、如何被可信地理解和使用，以及业务变化后如何持续调整。
