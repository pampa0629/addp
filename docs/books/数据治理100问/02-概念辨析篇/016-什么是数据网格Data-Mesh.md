# 016 什么是数据网格（Data Mesh）？

## 一句话回答

> 数据网格是一种面向大型复杂组织的数据治理和数据架构思路。它不把所有数据建设责任都交给中心数据团队，而是让最了解业务的领域团队对本领域的数据产品承担端到端责任，同时由组织提供统一的自助式数据平台和联邦治理机制，使跨领域数据能够安全、可信地组合并服务业务。

Data Mesh要解决的核心问题不是“数据存在哪里”，而是“谁真正理解这些数据、谁对其质量和持续可用负责，以及如何在领域自主和全局统一之间取得平衡”。

如果说Data Fabric主要解决分布式数据如何在技术上被连接、发现、理解和访问，那么Data Mesh主要解决分布式组织中数据责任如何划分和协作。两者可以结合：Data Fabric提供技术能力，Data Mesh建立组织和运营方式。

## 一、为什么会出现数据网格

许多组织最初会建立中心数据团队，由它统一接入各业务系统、建设数据仓库、开发模型和指标，再向业务部门提供报表、数据集和数据服务。

这种集中建设模式在规模较小时具有明显优势：人员集中、标准统一、技术路线清晰，也便于控制安全和质量。但随着业务领域、数据源和应用需求不断增加，中心团队可能逐渐成为所有数据需求的必经环节：

- 每接入一个新系统，都需要中心团队理解新的业务语义；
- 每新增一个指标，都要在业务部门和数据团队之间反复沟通；
- 数据出了问题，中心团队知道加工链路，却不了解源头业务原因；
- 业务规则发生变化，数据模型和质量规则不能及时同步；
- 各部门都在等待中心团队排期，数据交付周期越来越长；
- 中心平台中的数据很多，但真正长期被使用的数据产品不多。

这里的根本矛盾是：业务知识分散在各领域，数据建设责任却集中在少数技术人员手中。中心团队可以掌握数据技术，却很难长期替所有业务部门理解客户、产品、合同、设备、供应链和财务规则。

Data Mesh由此提出：让数据责任更加接近业务知识和数据产生的地方，同时保留必要的组织级标准、平台和治理能力。

## 二、Data Mesh中的“领域”是什么

“领域”不是简单按照现有部门名称划分，也不等同于某一套业务系统。它通常是围绕一组相对稳定的业务能力、业务对象和规则形成的责任边界，例如：

- 客户与营销；
- 产品与定价；
- 订单与履约；
- 供应链与采购；
- 生产与设备；
- 财务与结算；
- 自然资源调查、规划、确权、供应和监管。

领域划分应回答：哪些业务事实在这里产生，哪些规则由这里掌握，哪些数据变化最先被这里感知，以及谁有权解释这些数据。

一个领域可能跨越多个组织部门和业务系统，一个大型部门也可能包含多个领域。因此，不能把组织架构图直接复制成Data Mesh架构。

Data Mesh强调领域，是因为数据含义首先来自业务。设备状态为什么变化、合同何时算生效、客户为什么被划入某个等级，只有掌握相应业务规则的领域人员才能作出权威解释。

## 三、Data Mesh的四项核心原则

Data Mesh通常包括四项相互依赖的原则。它们应当一起理解，不能只选择“领域自治”而忽略其他三项。

### 1. 面向领域的数据所有权

领域团队不仅负责业务系统和业务流程，也要对可供其他领域使用的数据承担责任，包括数据含义、质量、鲜活度、变更和使用支持。

这不是要求每个业务人员都成为数据工程师，也不是把中心数据团队的工作简单分摊给各部门。更合理的做法是建立包含业务负责人、数据管家和数据工程人员的领域数据团队，使业务决策权和技术实现能力能够协同。

### 2. 把数据当作产品

领域不能只把原始表、Excel文件或数据库账号交给使用者，而应提供可以持续使用的数据产品。

一个合格的数据产品通常需要：

- 服务明确的使用者和业务用途；
- 有清晰名称、业务定义、结构和访问方式；
- 有明确负责人和问题反馈渠道；
- 对质量、鲜活度和可用性作出承诺；
- 能够被发现、申请、访问和追溯；
- 有稳定标识、版本和变更说明；
- 符合安全、权限和合规要求；
- 能与其他领域的数据产品组合使用。

数据产品可以是一组经过治理的仓库表、主题数据集、指标、API、事件流、标签或模型结果。关键不在技术形态，而在于有人围绕使用效果承担持续责任。

### 3. 自助式数据平台

如果每个领域都要自行采购数据库、建设采集工具、开发权限系统和实现质量监控，Data Mesh只会造成大量重复建设。

组织需要提供统一的自助式平台能力，使领域团队能够在较低技术门槛下完成：

- 数据源连接、采集、同步和计算；
- 数据建模、调度、测试和发布；
- 元数据、目录、血缘和质量管理；
- 数据产品注册、授权和服务；
- 运行监控、版本管理和问题处理；
- 安全、审计和资源管理。

“自助”不是无人管理，而是把常见、重复的技术工作标准化和产品化，让领域团队不必每次依赖中心平台人员手工实施。

### 4. 联邦治理

完全中心化的治理响应缓慢，完全分散的治理又容易产生新的数据孤岛。联邦治理的目标，是共同制定组织级底线和互操作规则，同时允许领域在边界内自主决定本领域的细节。

例如：

| 适合组织统一的规则 | 可以由领域自主决定的内容 |
| --- | --- |
| 身份认证、分级分类和审计要求 | 领域内部的数据模型和加工实现 |
| 数据产品的登记、责任和版本要求 | 数据产品的具体发布节奏 |
| 客户、组织、地区、时间等公共标识 | 领域特有的业务属性和状态 |
| 跨领域指标和公共语义 | 仅在领域内部使用的指标 |
| 数据质量和服务等级的最低要求 | 高于最低要求的质量规则 |
| 跨领域变更和争议处理机制 | 不影响其他领域的局部变更 |

联邦治理并不是各领域派人开会即可。统一规则需要能够通过平台、数据契约、质量检测、权限控制和发布流程自动执行，否则很容易停留在制度文件中。

## 四、Data Mesh解决的是责任集中问题，不是数据集中问题

Data Mesh经常被误解为“数据必须分散存储”。实际上，它关心的是责任和产品归属，不规定数据必须采用某一种物理架构。

领域数据产品可以：

- 物理汇聚到统一数据仓库中，由领域负责模型和质量；
- 保存在领域自己的数据湖、数据库或专业引擎中；
- 通过API、事件流或联邦查询对外提供；
- 同时采用集中存储和分布式访问的混合方式。

因此，采用统一数据仓库并不妨碍实行Data Mesh。即使所有数据都存放在同一个分析平台中，只要不同领域对自己的数据产品承担清晰责任，并遵守统一治理规则，仍然可以采用Data Mesh的组织方式。

反过来，把数据库拆散到各部门也不等于Data Mesh。如果数据缺少产品责任、统一目录、质量承诺和跨领域标准，只是把原来的数据孤岛变成更多数据孤岛。

## 五、Data Mesh与Data Fabric有什么区别

两者都面对数据分散、中心团队难以覆盖全部需求的问题，但切入角度不同。

| 对比维度 | Data Fabric | Data Mesh |
| --- | --- | --- |
| 主要问题 | 分散数据如何被统一连接、理解和访问 | 分散领域如何承担数据责任并协作 |
| 主要视角 | 架构与技术能力 | 组织、责任和运营方式 |
| 核心手段 | 统一连接、元数据、语义、自动化和多种访问方式 | 领域所有权、数据产品、自助平台和联邦治理 |
| 对中心团队的改变 | 从集中搬运数据转向提供跨环境的统一能力 | 从代替领域交付数据转向建设平台、规则和协作机制 |
| 主要风险 | 连接很多，但语义、质量和业务使用不足 | 自治很多，但标准割裂、重复建设和责任推诿 |

Data Fabric可以为Data Mesh提供技术底座。例如，统一连接和目录帮助领域发现数据，逻辑汇聚帮助数据产品跨引擎组合，主动元数据帮助识别质量和变更影响。

Data Mesh则可以为Data Fabric提供责任主体。否则，即使平台已经连接所有数据源，仍然可能没人解释字段含义、处理质量问题或维护数据产品。

可以把二者的关系概括为：

```mermaid
flowchart LR
    A["业务领域：理解数据并承担产品责任"] --> B["Data Mesh：领域所有权与联邦治理"]
    B --> C["Data Fabric：统一连接、元数据、语义和访问"]
    C --> D["跨领域数据产品和业务应用"]
    D --> A
```

二者不是必须同时建设的固定套餐。规模较小、业务简单的组织，可能只需要中心数据团队和统一数据仓库；技术环境高度分散但组织职责清晰时，可以重点建设Data Fabric能力；组织领域复杂、中心交付成为瓶颈时，才需要认真考虑Data Mesh。

## 六、中心数据团队还需要做什么

Data Mesh不是取消中心数据团队，而是改变它的职责。

传统模式下，中心团队可能直接承接所有数据采集、建模、指标和报表需求。在Data Mesh中，它更适合承担：

- 建设和运营自助式数据平台；
- 提供通用连接、计算、质量、血缘和安全能力；
- 维护组织级术语、标准和公共数据模型；
- 组织跨领域规则制定、争议处理和变更协调；
- 指导领域建立数据产品和工程能力；
- 监控数据产品的质量、使用和服务等级；
- 处理单个领域无法独立完成的公共数据产品。

领域团队则负责：

- 定义数据产品服务的业务用途和使用者；
- 解释本领域的数据语义和业务规则；
- 确认权威来源、质量要求和更新周期；
- 参与或承担数据产品的建设、发布和运营；
- 响应使用者问题并管理变更影响；
- 衡量数据产品是否真正产生业务价值。

这种分工不是把技术工作全部交给业务部门，而是让中心团队提供规模化能力，让领域团队承担不能外包的业务责任。

## 七、案例：大型制造集团的设备全生命周期

某大型制造集团希望分析设备的综合效率、故障风险和全生命周期成本。相关数据分散在多个领域：

- 采购领域掌握供应商、采购合同、到货和质保信息；
- 资产管理领域掌握设备台账、编号、位置和资产状态；
- 生产领域掌握运行时长、负荷、产量和停机事件；
- 维修领域掌握点检、故障、工单、备件和维修结果；
- 财务领域掌握原值、折旧、维修费用和报废损益。

### 1. 全部交给中心团队会发生什么

中心数据团队可以把数据汇聚到仓库并建立设备主题模型，但很快会遇到业务问题：同一台设备在采购、资产和生产系统中的编号不同；生产停机不一定代表设备故障；维修完工时间与恢复生产时间含义不同；费用应计入设备、产线还是工厂存在业务判断。

中心团队可以实现规则，却不能长期替各领域决定这些规则。每次业务变化都依靠中心团队重新访谈、修改和发布，交付速度和责任都难以保证。

### 2. 采用Data Mesh如何分工

各领域可以分别建设和运营数据产品：

| 领域 | 数据产品示例 | 主要责任 |
| --- | --- | --- |
| 资产管理 | 设备主数据产品 | 统一设备标识、位置、分类和资产状态 |
| 生产 | 设备运行事件产品 | 提供运行、负荷、产量和停机事件，保证事件及时性 |
| 维修 | 设备维护历史产品 | 统一故障、工单、备件和维修结果语义 |
| 财务 | 设备成本产品 | 提供折旧、维修费用和报废损益口径 |
| 采购 | 设备采购与质保产品 | 提供供应商、合同、到货和质保期限 |

集团层面统一设备标识、数据产品登记规范、最低质量要求、权限和跨领域变更机制，并提供采集、建模、目录、质量、血缘和服务发布平台。

设备综合效率和全生命周期成本可以作为跨领域数据产品或业务应用，组合多个领域产品完成计算。发现设备匹配错误时，问题返回设备主数据产品；运行事件延迟时，由生产领域处理；维修费用口径争议则由财务和维修领域按联邦治理机制共同确认。

这样，业务知识和数据责任没有被推给中心团队，跨领域应用也不必直接理解每个源系统的内部表结构。

## 八、为什么Data Mesh在国内组织中更难落地

Data Mesh要求领域主动承担数据产品责任，而在国内不少组织中，数据文化尚未形成，部门墙又比较明显，常见困难包括：

- 业务部门仍把数据治理视为信息中心或数据中心的工作；
- 数据提供和质量整改被认为是额外负担，没有人员和考核支持；
- 部门愿意控制数据，却不愿承担对外服务和持续维护责任；
- 跨部门公共对象和指标缺少有权威的裁决机制；
- 领域团队缺少数据工程、产品运营和质量管理能力；
- 平台还不具备自助能力，所谓自治实际仍依赖中心团队手工支持。

在这种环境下直接宣布“领域自治”，很可能把部门墙合法化：各部门以自治为理由保留自己的编码、口径和平台，跨领域数据反而更难关联。

因此，Data Mesh尤其需要一把手和组织级治理机制推动。高层要明确数据服务于组织整体目标，对领域进行授权，也要求领域承担相应责任；对公共标准、资源投入、绩效机制和重大争议建立统一安排。

领域自治不是摆脱组织治理，而是在明确边界、公共规则和结果责任下获得自主权。

## 九、如何稳妥推进Data Mesh

Data Mesh不适合通过一次组织调整在全公司全面铺开。更可行的路径是从一个跨领域且价值明确的场景开始：

1. 选择涉及两个到四个领域的真实业务问题；
2. 明确每个领域掌握的业务事实和责任边界；
3. 识别首批需要复用的数据产品及其使用者；
4. 为数据产品确定负责人、质量、鲜活度和服务承诺；
5. 只建设试点所需的最小自助平台和统一规则；
6. 通过跨领域应用检验产品能否组合、问题能否闭环；
7. 衡量交付周期、复用次数、问题响应和业务效果；
8. 再将成熟的平台能力和治理规则推广到其他领域。

对于许多组织，第一阶段不必正式使用“Data Mesh”这个名称。先让业务领域真正参与数据定义、质量和产品运营，让中心团队从重复交付转向提供公共能力，往往比宣布一套新架构更重要。

## 十、常见误区

### 误区一：Data Mesh就是把数据平台拆给各部门

领域自治不等于各自建设平台。通用技术能力应由自助式平台提供，避免重复采购、重复开发和新的技术孤岛。

### 误区二：数据属于哪个部门，就由哪个部门说了算

领域有权解释本领域业务事实，但跨领域对象、指标和规则必须通过联邦治理达成组织级约定，不能以部门所有权阻碍共享和组合。

### 误区三：数据产品就是一张表或一个API

技术接口只是载体。没有使用者、业务定义、质量承诺、负责人、版本和持续运营，不能称为完整的数据产品。

### 误区四：领域自治以后不再需要中心数据团队

领域越多，越需要统一平台、公共标准、安全控制、能力辅导和跨领域协调。中心团队的职责发生变化，而不是消失。

### 误区五：Data Mesh天然能够打破部门墙

如果缺少共同目标、高层授权和责任机制，领域自治反而会强化部门墙。Data Mesh需要建立在组织协作意愿和数据文化基础上。

### 误区六：所有组织都应该采用Data Mesh

数据源少、业务领域简单、中心团队尚未成为瓶颈时，集中治理通常更加直接和经济。不能为了追求新概念而增加组织复杂度。

### 误区七：采用Data Mesh就不再需要数据仓库或Data Fabric

Data Mesh不规定数据存储方式，也不替代统一连接和治理技术。数据仓库、Data Fabric和Data Mesh解决的是不同层面的问题，可以组合使用。

## 十一、实践检查清单

1. 组织是否确实存在多个相对独立且复杂的业务领域？
2. 中心数据团队是否已经成为数据接入和交付瓶颈？
3. 领域边界是否根据业务能力和数据责任划分，而不是照搬部门名称？
4. 业务领域是否愿意并有能力承担数据语义、质量和运营责任？
5. 每个数据产品是否有明确使用者、负责人和价值目标？
6. 数据产品是否具备定义、质量、鲜活度、版本、权限和反馈机制？
7. 是否有能够降低领域建设门槛的自助式数据平台？
8. 哪些规则必须全局统一，哪些内容允许领域自主，是否已经明确？
9. 跨领域数据能否通过公共标识、语义和数据契约组合使用？
10. 部门争议是否有明确的升级和最终裁决机制？
11. 是否得到一把手对授权、资源、考核和跨部门协作的持续支持？
12. 是否通过交付效率、产品复用、质量改进和业务结果衡量成效？

## 结语

Data Mesh试图解决一个长期存在的矛盾：数据价值需要跨领域组合产生，但数据含义和质量责任又深深植根于各个业务领域。把所有责任集中给数据团队，业务知识不足；把所有事情分散给各部门，又可能形成新的孤岛。

它给出的答案是：领域负责数据产品，平台提供自助能力，组织通过联邦治理保持整体一致。领域获得的不是对数据的占有权，而是在公共规则下把本领域数据可靠地服务给其他使用者的责任和自主权。

对于数据文化尚未成熟、部门墙明显的组织，Data Mesh不能从“自治”开始，而要从共同业务目标、高层授权、责任机制和小范围数据产品试点开始。只有当领域责任和跨领域协作同时建立起来，数据网格才能真正帮助数据为业务增值。
