# 077 数据服务为什么需要独立的应用身份和应用授权？

## 一句话回答

> 数据服务由谁开发，与运行时由谁调用，是两种不同的关系。应用不能长期借用开发者、管理员或其他个人的账号，而应具有可独立识别、授权、限流、审计和撤销的应用身份。用户参与调用时，还要同时判断用户权限；后台自动调用时，应以应用身份授权和留痕，并由应用负责人及其所属组织承担相应责任。

数据治理平台可以把经过治理的数据发布为查询、指标、文件、模型或其他形式的数据服务，供业务系统、移动应用、分析工具和合作机构使用。服务一旦发布，调用关系就不应继续依附于开发者个人。

## 一、为什么不能用开发者账号调用数据服务

假设某位数据开发人员完成了一项客户统计服务，外部经营分析系统需要调用它。如果外部系统必须保存这位开发人员的平台账号和密码，甚至要求他登录外部系统以后才能调用，就会形成非常不合理的关系：

```text
开发人员离职或调岗
        ↓
个人账号停用或权限变化
        ↓
外部应用无法继续调用数据服务
```

还可能带来更多问题：

- 外部应用获得了开发人员与本次集成无关的其他权限；
- 多个应用共用同一账号，无法区分真正的调用来源；
- 所有调用都被记录成开发人员的个人行为；
- 某个应用发生风险时，只能停用个人账号，不能单独停用该应用；
- 账号密码长期保存在程序中，泄露后可能被用于登录平台；
- 服务的持续运行依赖某位员工，无法形成稳定的组织能力。

因此必须分开三种关系：

```text
开发者 ──负责开发、测试和维护──▶ 数据服务

服务负责人 ──负责发布、授权和运营──▶ 数据服务

应用 ──以自身身份、在获准范围内──▶ 调用数据服务
```

同一个人可以同时承担开发和管理职责，但这些职责仍不能成为应用的运行身份。

## 二、用户身份、应用身份、调用凭证和应用授权有什么区别

| 概念 | 主要回答的问题 | 示例 |
| --- | --- | --- |
| 用户身份 | 当前操作的人是谁 | 某分析人员、客服人员或审批人员 |
| 应用身份 | 当前请求来自哪个程序或系统 | 经营看板、移动客户端、合作方业务系统 |
| 调用凭证 | 应用怎样证明自己的身份 | 应用密钥、证书、签名或短期令牌 |
| 应用授权 | 该应用可以调用什么 | 指定服务、接口、数据范围和操作 |

日常所说的“应用鉴权”经常同时包含两层含义：

1. 验证应用身份，确认请求是否真的来自已经登记的应用；
2. 判断应用权限，确认该应用是否获准执行本次调用。

为了避免混淆，本问把前者称为应用身份验证，把后者称为应用授权。调用凭证只是证明身份的手段，并不天然代表全部权限。

## 三、为什么有用户权限还不够

用户权限回答“这个人可以使用哪些数据”，却不能完整回答“哪个程序正在代表他使用”。

如果只验证用户而不识别应用，可能出现：

- 任意程序取得用户凭证后都能发起调用；
- 一个用户通过不同应用访问数据，却无法区分风险较高的调用渠道；
- 低可信应用继承用户全部权限，读取超过自身业务需要的数据；
- 多个系统共用一个用户账号，审计记录无法说明由哪个系统发起；
- 无法为不同应用分别设置服务范围、调用频率和有效期限；
- 某个应用出现异常时，不能在不影响用户其他工作的情况下单独停用。

因此，一次数据服务调用至少可能需要回答：

```text
谁在使用？
通过哪个应用使用？
应用是否可信且仍然有效？
用户和应用分别获准使用哪些数据？
本次调用是否符合服务自身的限制？
```

## 四、外部应用应该怎样获得调用资格

外部应用需要调用数据服务时，应先建立独立的应用关系，而不是借用某个员工账号。

通常需要明确：

- 应用名称、用途和所属机构；
- 业务负责人和技术联系人；
- 需要调用哪些数据服务；
- 需要哪些数据和操作范围；
- 用于生产、测试还是其他环境；
- 调用期限、频率和总量；
- 凭证如何发放、保管、轮换和撤销；
- 异常、泄露和合作终止时怎样处置。

可以把这个过程理解为：

```text
应用登记
   ↓
申请数据服务和使用范围
   ↓
审核用途、数据范围和风险
   ↓
授予应用权限并发放调用凭证
   ↓
运行中的限流、监测和审计
   ↓
到期复核、续期或者撤销
```

应用身份不是另一种个人账号。它代表一套程序及其所属组织、负责人和用途，是可以独立管理的非个人调用主体。

## 五、外部应用中的用户怎样处理

外部应用是否还需要传递用户身份，要看具体服务场景。

### 1. 应用以固定业务范围调用

例如，合作机构每天自动取得已经约定的汇总数据。数据平台可以直接根据应用身份和应用授权判断，不需要虚构一个正在操作的个人用户。

### 2. 应用代表当前用户调用

例如，合作方工作人员在外部业务系统中查询与自己职责相关的数据。此时除了识别应用，还可能需要可靠地识别当前用户、组织、角色或其他业务范围。

最终范围可以简化为：

```text
本次有效权限
=
用户获准使用的范围
∩ 应用获准调用的范围
∩ 数据服务自身的安全策略
```

用户有权查询明细，不代表任何外部应用都能替他下载明细；应用获准调用某项服务，也不代表该应用中的所有用户都自动取得相同的数据权限。

如果外部应用只传来一个无法验证的用户名，数据平台也不能据此相信用户身份。双方需要建立可信的身份传递、委托或者映射关系。本问不展开具体技术协议，重点是不能把应用身份和用户身份混成一个共享账号。

## 六、平台内部应用是否可以直接使用平台账号

“使用平台账号”可能有两种不同含义，需要区分。

### 1. 复用平台统一登录

用户登录平台后进入数据分析、资产门户或其他内部应用，可以复用统一的用户身份和登录状态，不必在每个应用中重复输入账号密码。

这种方式是合理的，因为它仍然能够说明当前操作用户是谁。

### 2. 内部应用保存某个员工账号

如果内部应用在后台保存开发人员、管理员或普通员工账号，并长期冒充这个人调用服务，仍然是不合理的。内部应用同样会升级、下线、泄露或发生异常，也需要被单独识别和控制。

因此：

> 内部应用可以复用平台的用户登录体系，但不能用个人账号代替应用身份。

## 七、内部应用通常有哪些调用方式

### 1. 用户直接通过内部应用操作

例如，用户登录平台后，在内部分析应用中查询经营指标。

此时应同时保留：

- 当前用户身份；
- 内部应用身份；
- 被调用的数据服务；
- 用户和应用各自的权限范围。

审计记录应表达为“用户甲通过分析应用调用指标服务”，而不是只记录用户或者只记录应用。

### 2. 内部应用代表用户调用其他服务

内部应用可以在当前用户授权范围内继续调用后端数据服务，但不应取得或保存用户密码，也不能把用户全部权限无限制地传递下去。

### 3. 内部应用在后台自动运行

定时报表、自动告警、数据同步和监测程序没有实时操作用户，应使用应用或后台服务自身的身份，只获得完成任务所需的权限。

```text
自动报表应用
   └──只获准调用经营指标查询服务

监测应用
   └──只获准读取监测数据并提交告警结果
```

后台程序不应依赖某位员工保持在职、保持登录或者长期拥有某个角色。

## 八、内部应用和外部应用有什么异同

| 比较内容 | 平台内部应用 | 外部应用 |
| --- | --- | --- |
| 用户登录 | 通常复用平台统一登录 | 可以使用自身用户体系，也可以建立可信的联合身份关系 |
| 应用身份 | 仍然需要 | 必须明确登记 |
| 后台自动调用 | 使用应用或服务自身身份 | 使用应用自身身份 |
| 授权方式 | 可以根据平台职责预先配置或经过内部审批 | 通常需要正式申请、审核和协议约束 |
| 运行环境 | 一般更受平台控制 | 网络、终端和运维边界通常更复杂 |
| 限流与审计 | 仍然需要 | 通常需要更严格的控制 |
| 是否可以借用开发者账号 | 不可以 | 不可以 |

内部和外部应用的信任程度、接入流程和控制强度可以不同，但身份模型不应相互矛盾。

“内部应用”也不能自动等于“完全可信”。一个存在缺陷的内部程序同样可能批量读取数据、错误调用服务或扩大安全事件影响。

## 九、应用授权需要限定哪些内容

应用授权不能只设置一个笼统的“允许调用”。根据数据风险，可以限定：

| 授权维度 | 示例 |
| --- | --- |
| 服务范围 | 只能调用经营指标服务 |
| 接口和操作 | 可以查询，不能修改或批量导出 |
| 数据范围 | 只能访问华东区域汇总数据 |
| 字段和精度 | 返回统计结果，不返回客户明细 |
| 租户或机构 | 只能访问本机构获准的数据 |
| 使用目的 | 仅用于经营分析，不得转作营销 |
| 运行环境 | 仅限生产应用，从指定环境调用 |
| 有效期限 | 合作期内有效，到期复核 |
| 调用规模 | 每分钟和每日存在合理上限 |

应用权限应遵循最小必要原则。一个看板只需要汇总指标，就不应因为其用户中有人能够查看客户明细，而给看板开放明细下载接口。

## 十、应用身份与应用实例为什么还要区分

同一款应用可能部署在开发、测试和生产环境，也可能由多个机构分别运行。

如果所有环境和实例共用一套凭证，会造成：

- 测试环境泄露影响生产服务；
- 无法判断是哪一个实例发起调用；
- 一个合作机构出现问题时，需要停用所有机构；
- 测试程序可能误调用生产数据；
- 调用量和责任无法分别统计。

因此，可根据风险为不同环境、机构或重要实例分配可以独立识别和撤销的凭证。应用身份说明“这是什么应用”，实例信息进一步说明“由谁、在什么环境运行的这一份应用”。

这并不意味着凭证越多越好，而是重要的运行边界不能被一套共享凭证掩盖。

## 十一、调用凭证为什么需要生命周期管理

调用凭证相当于应用证明身份的钥匙。即使应用授权范围合理，凭证管理不当仍可能让他人冒充应用。

需要关注：

- 凭证由谁申请和领取；
- 是否存放在受控位置；
- 是否进入代码、前端页面或普通日志；
- 是否设置合理有效期；
- 是否定期轮换；
- 泄露时能否迅速撤销；
- 应用下线、合作结束或负责人变化时是否及时处理；
- 是否保留凭证使用和变更记录。

尤其不能把长期有效的应用密钥直接放进浏览器、移动应用安装包或公开代码中，因为这些运行环境很难真正保守一个固定秘密。

应用凭证被撤销，只是阻止该应用继续证明身份；应用已经取得的数据仍需要按照约定处置，不能假定撤销凭证就自动收回全部数据副本。

## 十二、为什么还需要限流、配额和异常控制

应用能够自动、高频、长时间运行。一个有合法权限但存在程序错误的应用，也可能在短时间内发起大量请求。

可能造成：

- 异常批量读取数据；
- 数据服务和底层计算资源被耗尽；
- 错误调用持续放大；
- 单个应用影响其他正常使用者；
- 调用规模超过原先批准的业务目的。

因此，需要根据应用和服务设置合理的调用频率、并发数量、每日配额、超时和异常告警。限流不是身份验证，也不能代替权限，但它能控制自动化调用的影响范围。

对高风险数据，仅限制请求次数也不够，还要关注单次返回量、累计数据量、查询范围和导出行为。

## 十三、审计为什么要同时记录用户和应用

对于用户参与的调用，审计需要回答：

> 哪个用户，通过哪个应用，在什么时间，以什么目的，调用了哪个服务，访问了哪些数据。

对于后台自动调用，则需要记录：

- 应用和实例身份；
- 所属机构和负责人；
- 调用的服务和数据范围；
- 请求时间、结果和数据量；
- 使用的凭证标识；
- 可以串联上下游记录的请求编号；
- 被拒绝、超限和其他异常行为。

审计不应记录完整密钥，也不应为了追踪而复制全部敏感数据。

识别应用以后，发生异常时可以单独限制、调查或停用某个应用，而不必笼统停用所有用户或把责任记到服务开发者名下。

## 十四、以经营分析看板为例

某企业发布了一项经营指标服务，供内部经营看板和外部合作机构使用。

### 1. 服务开发和发布

数据开发人员负责实现指标计算，服务负责人审核并发布数据服务。两人的个人账号都不作为运行凭证。

### 2. 内部看板调用

- 用户复用平台统一登录；
- 平台识别当前用户和经营看板；
- 看板只获准查询汇总指标；
- 用户能够看到哪些区域，还要结合其个人数据范围；
- 后台定时刷新使用看板自身的应用身份。

### 3. 外部合作方调用

- 合作方应用独立登记；
- 只获准查询约定机构和时间范围的指标；
- 使用独立凭证，不借用开发人员账号；
- 设置调用期限、频率和累计数据量限制；
- 合作结束后撤销应用授权和凭证。

### 4. 发生异常时

如果外部应用突然高频获取数据，平台可以根据应用身份限流、告警和暂停该应用，同时保留内部看板和其他应用的正常使用。

这个例子说明，应用身份既是安全控制需要，也是保证服务稳定运营和准确划分责任的基础。

## 十五、常见误区

### 误区一：谁开发服务，就用谁的账号调用

开发责任不等于运行身份。应用应以自身身份调用。

### 误区二：外部应用才需要应用身份，内部应用天然可信

内部应用也可能自动运行、发生缺陷或被滥用，同样需要被识别和控制。

### 误区三：用户已经登录，就不需要识别应用

用户身份不能说明请求通过哪个程序发起，也不能约束应用渠道。

### 误区四：应用获得授权后，应用中的所有用户都能访问相同数据

用户参与的场景还要判断用户权限，应用授权不能自动扩大个人数据范围。

### 误区五：用户权限很大，应用就应继承其全部权限

应用只能在自身获准范围内代表用户操作，最终权限通常受到双方范围共同限制。

### 误区六：系统间调用可以共用管理员账号

共享管理员账号会扩大权限、混淆责任，也无法分别停用不同系统。

### 误区七：有应用密钥就等于获得全部服务权限

调用凭证证明应用身份，具体能够调用什么仍由应用授权决定。

### 误区八：密钥足够复杂，就可以永久使用

凭证仍可能因人员、代码、终端或供应链问题泄露，需要轮换、到期和撤销机制。

### 误区九：调用有权限，就不需要限流

合法应用的程序错误和异常批量调用同样可能造成数据与运行风险。

### 误区十：撤销应用凭证，就等于收回已经提供的数据

凭证撤销只能阻止后续调用，已经交付的数据还需要按期限、用途和退出约定处置。

## 小结

数据服务由谁开发、由谁负责和由谁调用，应当清楚分开。服务发布以后，外部应用不能借用开发者账号，平台内部应用也不能用个人账号代替自身身份。

有用户参与时，需要同时识别用户和应用，在用户权限、应用授权与服务策略的共同范围内提供数据；没有实时用户参与时，后台程序应以自身应用或服务身份运行。内部应用可以复用平台统一登录，但仍需保留应用身份，外部应用则通常需要更加正式的登记、审核和接入控制。

应用身份只有与明确授权、凭证生命周期、限流、监测和审计结合，才能真正做到每个应用可识别、可控制、可追踪、可停用。这样既避免应用成为绕过用户权限的通道，也让数据服务摆脱对个人账号的依赖，成为能够长期稳定运营的组织能力。
