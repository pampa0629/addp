# 075 租户隔离、部门数据范围、角色权限和数据授权分别解决什么问题？

## 一句话回答

> 租户隔离回答“属于哪个独立组织空间”，部门数据范围回答“在组织内部默认管理和使用哪些数据”，角色权限回答“能够执行什么操作”，数据授权回答“可以对哪些具体数据、在什么范围和条件下执行这些操作”。四者逐层约束，再结合项目、期限、用途和安全策略，才能形成最终访问范围。

用户能够登录平台，只能说明身份已经得到确认，并不意味着可以查看所有数据。数据访问还需要回答：他属于哪个组织、承担什么职责、默认管理哪些业务范围、获得了哪些具体数据授权，以及当前使用场景是否符合要求。

## 一、用“园区—楼宇—楼层—项目室”理解四类边界

可以把统一的数据平台想象成一个园区：

```text
园区：统一数据平台
├── 楼宇A：租户A
│   ├── 楼层1：部门甲
│   ├── 楼层2：部门乙
│   └── 项目室：跨部门项目组
└── 楼宇B：租户B
    ├── 楼层1：部门丙
    └── 楼层2：部门丁
```

### 1. 园区代表共享的平台基础设施

各租户可以共同使用计算、存储、网络、监控和平台工具等基础能力，也可以使用经过明确发布的公共标准、参考数据和公共服务。

共享基础设施不等于共享业务数据。不同楼宇可以共用园区道路、供电和安保系统，却不能因此相互进入办公室和档案室。

### 2. 楼宇代表租户

租户是相对独立的身份、资源、配置、数据和责任边界。不同租户之间默认强隔离，跨租户数据流动必须经过明确建立的通道。

### 3. 楼层代表部门

部门是租户内部相对稳定的组织管理范围。楼层可以有门禁，但楼宇内部仍然需要电梯、会议室、档案借阅和跨楼层协作机制。

因此，部门数据范围主要确定默认边界，不应重新制造无法穿透的数据孤岛。

### 4. 项目室代表项目组

项目组通常由多个部门的成员围绕特定目标临时组成。它只获得经过选择的数据，并具有明确的期限、成员和退出方式。

加入项目组，不代表成员所在部门的全部数据自动进入项目。

## 二、四个概念分别解决什么问题

| 概念 | 主要回答的问题 | 典型边界 |
| --- | --- | --- |
| 租户隔离 | 这个用户和资源属于哪个独立组织空间 | 企业、客户机构、独立运营组织 |
| 部门数据范围 | 用户在组织内部默认可以管理或使用哪些业务范围 | 部门、下级部门、区域、业务域 |
| 角色权限 | 用户可以执行什么类型的操作 | 查看、开发、发布、审批、管理 |
| 数据授权 | 用户可以对哪些具体数据执行哪些操作 | 数据集、表、字段、文件、指标、服务 |

四者不是相互替代的四种权限方案，而是从不同角度共同确定访问边界。

## 三、租户为什么是强隔离边界

在为多个独立组织提供服务的平台中，不同租户通常需要做到：

- 用户和组织信息默认相互不可见；
- 数据、任务和服务默认不能跨租户查询；
- 配置和资源不能被其他租户操作；
- 租户管理员只能管理本租户；
- 权限判断不能因为用户知道资源地址而绕过租户边界；
- 跨租户共享必须形成明确的数据提供、交换或服务关系。

强隔离是一项安全要求，并不等于每个租户都必须单独部署服务器和数据库。物理基础设施可以共享，但身份、资源、数据、管理和审计边界必须可靠分开。

也不应把企业内部每个部门都建成独立租户。这样可能造成：

- 用户和资源重复管理；
- 跨部门协作困难；
- 数据目录、标准和指标重新形成孤岛；
- 统一治理能力被人为切碎；
- 日常协作被迫变成复杂的跨租户交换。

只有当身份、责任、资源、合规和运营边界都相对独立时，才适合使用独立租户。

## 四、部门数据范围为什么不是硬隔离

部门数据范围反映组织内部的管理关系和默认可见范围，例如：

- 只能查看本部门数据；
- 可以查看本部门及下级部门数据；
- 区域负责人可以查看所辖区域数据；
- 集团职能部门可以查看多个单位的汇总数据；
- 特定业务负责人可以管理某个数据域的数据。

但数据并不总是严格按照组织架构归属。一个客户可能同时涉及销售、服务、财务和风控；一项工程可能由多个部门共同负责；一个指标也可能汇总全组织的数据。

因此：

> 部门数据范围适合确定默认管理边界，不能成为数据归属和共享的唯一依据。

数据治理需要阻止未经授权的跨部门访问，也要支持目的明确、范围清楚、期限受控的跨部门协作。

## 五、项目组怎样形成临时协作边界

项目组不是另一个部门，也不是缩小版租户，而是租户内部围绕特定目的建立的临时协作空间。

项目创建时应明确：

- 项目目标和负责人；
- 参与部门和具体成员；
- 项目需要哪些数据；
- 成员可以执行哪些操作；
- 项目开始和结束时间；
- 数据能否导出、共享或用于其他目的；
- 项目成果由谁负责以及怎样退出。

数据可以这样进入项目：

```text
华东销售部 ──授权部分销售数据──┐
                                ├── 项目组
财务部 ─────授权部分回款数据───┤
                                │
客户服务部 ─授权部分服务数据───┘
```

成员共同使用的是经过选择的数据，而不是三个部门的全部数据。

项目结束后，成果可以分别处理：

- 临时中间结果：删除；
- 需要留存的过程材料：归档到项目；
- 具有长期复用价值的成果：进一步治理并发布为正式资产。

项目成员退出、项目到期或目标变化时，数据范围也应随之复核和回收。

## 六、角色权限主要解决“能做什么”

角色适合表达相对稳定的职责和操作能力。

| 角色示例 | 可能具备的操作能力 |
| --- | --- |
| 数据查看者 | 浏览目录、查看元数据、查询允许的数据 |
| 数据开发者 | 创建SQL、Notebook或工作流，运行开发任务 |
| 数据发布者 | 发布数据服务或数据资产 |
| 数据审批者 | 审批数据申请、发布或共享 |
| 数据管理员 | 维护目录、责任人和治理规则 |
| 平台管理员 | 管理用户、配置和平台运行 |

需要注意：

- 岗位名称不一定等于系统角色；
- 一个人可以承担多个角色；
- 同一角色可以分配给多个人；
- 角色定义操作能力，不自动意味着可以访问全部数据；
- 数据管理员可以维护元数据，不一定能查看数据明细；
- 平台管理员能够维护平台，也不应天然成为所有业务数据的超级用户。

角色应保持相对稳定。如果把地区、部门、数据集、项目和期限全部写进角色名称，角色数量会迅速失控。

## 七、数据授权主要解决“对哪些数据做什么”

一次完整的数据授权至少可能包括：

| 授权要素 | 示例 |
| --- | --- |
| 授权对象 | 用户、角色、用户组、部门、项目或应用 |
| 数据对象 | 数据集、表、字段、文件、指标、标签或服务 |
| 操作类型 | 查看、查询、下载、修改、发布、共享或管理 |
| 数据范围 | 全部、特定区域、部门、客户、时间或其他条件 |
| 使用目的 | 业务办理、分析研究、监管或项目协作 |
| 使用环境 | 生产环境、受控分析环境或指定终端 |
| 有效期限 | 长期、项目期间或临时授权 |
| 责任关系 | 谁申请、谁审批、谁负责 |
| 到期处理 | 怎样回收权限和处置临时副本 |

数据授权可以授予用户，也可以授予角色、用户组或项目。角色权限和数据授权不是只能二选一：

- 角色权限表达稳定的操作职责；
- 数据授权表达变化频繁的具体数据使用关系。

## 八、最终访问范围怎样形成

可以用一个简化流程理解：

```text
身份认证
   ↓
租户边界
   ↓
部门、业务域或项目数据范围
   ↓
角色允许的操作
   ↓
具体数据授权
   ↓
时间、用途、环境和数据级别等附加条件
   ↓
最终有效权限
```

进一步概括：

```text
候选能力 = 用户所承担角色权限的合并

最终权限 =
候选能力
∩ 租户边界
∩ 部门、业务域或项目范围
∩ 数据授权范围
∩ 场景和安全策略
```

同一层中的多个允许项可以合并，但外层安全边界会继续收缩范围；存在明确拒绝或更严格保护要求时，应优先执行限制。

例如，一名用户拥有数据开发者角色，只说明他可以创建和运行开发任务。如果没有客户数据授权，就不能查询客户数据；即使获得授权，也可能只能访问所属区域，并受到敏感字段和项目期限限制。

## 九、为什么不能只靠角色权限

如果把所有数据范围都塞进角色，很容易出现“角色爆炸”：

- 华东销售查询角色；
- 华北销售查询角色；
- 华东销售下载角色；
- 华东销售临时项目角色；
- 华东销售敏感字段查询角色。

随着部门、区域、数据集和项目增加，角色难以理解、复核和维护。

更合理的分工是：

- 角色表达稳定职责；
- 部门、区域或业务域表达默认范围；
- 项目和数据授权表达具体、临时的使用关系；
- 分类分级与场景策略施加附加限制。

## 十、部门和项目组之间的数据怎样共享

“所有需求都直接授权”和“所有数据都必须先上架资产”都过于绝对。应根据成熟度、使用范围、风险和复用程度选择不同路径。

| 使用情形 | 推荐方式 |
| --- | --- |
| 部门内部日常使用 | 继承部门默认数据范围 |
| 已知对象、短期、一次性协作 | 直接受控授权 |
| 跨部门临时项目 | 项目组数据授权 |
| 长期、稳定、多人反复使用 | 编目并发布为数据资产 |
| 全组织普遍需要的公共数据 | 组织内开放 |
| 跨租户或对外提供 | 正式交换、服务或资产供给流程 |

这些方式最终都要落实为某种数据授权，区别在于是否需要完整的资产生产、发现、申请和运营流程。

## 十一、什么情况下可以直接受控授权

以下场景可以采用较轻量的直接授权：

- 使用者和数据负责人彼此明确；
- 数据对象和使用目的清楚；
- 使用期限较短；
- 只服务一个具体任务或项目；
- 数据尚未形成成熟、可复用的数据产品；
- 不需要面向大量未知使用者持续提供；
- 风险处于可控范围。

直接授权不等于私下发送文件或口头同意，至少需要记录：

- 授权给谁；
- 授权哪些数据；
- 允许执行什么操作；
- 用于什么目的；
- 有效期到什么时候；
- 是否允许继续转交；
- 由谁批准；
- 到期后怎样回收和处置副本。

直接授权是一条轻量治理路径，不是绕开治理。

## 十二、什么情况下应该走资产管理流程

如果一份数据具有以下特征，就更适合经过治理、编目和上架：

- 会被多个部门反复使用；
- 使用者不再只是少数已知人员；
- 业务口径和数据含义已经相对稳定；
- 有明确的数据负责人；
- 质量、更新频率和服务方式可以说明；
- 需要被其他使用者搜索和理解；
- 需要统一申请、审批和评价；
- 需要长期运营和持续维护。

这时可以形成：

```text
数据整理与治理
      ↓
资源编目
      ↓
形成可复用的数据资产
      ↓
上架资产目录
      ↓
使用者查找和理解
      ↓
申请与审批
      ↓
产生具体数据授权
      ↓
使用、评价和持续运营
```

资产管理的价值是一次治理、多次复用，并让数据口径、质量、更新、申请和评价形成持续运营机制。

## 十三、为什么不能要求所有共享都先上架资产

如果短期项目使用的数据也必须完成完整的资产生产流程，可能导致：

- 项目等待时间过长；
- 临时数据和中间结果污染资产目录；
- 尚未稳定的数据被包装成正式资产；
- 数据负责人转向线下传递以绕开流程；
- 资产目录中充满无人维护、无人复用的数据。

因此，需要区分：

- 资源登记：让数据可识别、可管理、可追溯；
- 项目授权：让特定项目在限定范围内使用；
- 资产上架：把成熟、稳定、可复用的数据正式提供给更多使用者。

所有正式共享都应留下治理记录，但不是所有数据都必须成为上架资产。

## 十四、为什么也不能全部采用直接授权

如果长期、重复的数据需求始终采用点对点授权，也会出现：

- 相同申请反复审批；
- 使用者不知道组织已经有哪些数据；
- 数据说明、口径和质量信息分散；
- 每个部门形成自己的共享清单；
- 权限长期累积而无人复核；
- 同一数据被复制成多个不一致版本；
- 数据价值无法评价和持续运营。

一个实用判断是：

> 当同一份数据开始被多个部门反复申请时，就应考虑把它治理成可以持续提供的数据资产。

## 十五、组织内开放与对外公开有什么区别

对于企业内部适合广泛使用的数据，更准确的说法是“组织内开放”，而不是对外公开。

组织内开放适合：

- 标准代码和参考数据；
- 已发布的统一指标；
- 公共组织信息；
- 面向全体成员的基础数据服务；
- 经过评估、适合广泛复用的数据产品。

这类数据通常仍应编目，但可以通过组织级默认授权让符合条件的成员直接使用，不必每个人重复申请。

向社会公众或外部机构公开则是另一种处理活动，需要单独判断公开依据、数据内容、传播风险和责任，不能与组织内部共享混为一谈。

## 十六、跨租户共享为什么需要正式通道

不同租户相当于独立楼宇。确有协作需要时，可以设置受控通道，例如：

- 数据服务；
- 数据交换任务；
- 经过审批的数据包；
- 正式发布的数据资产；
- 合同约定的数据提供或委托处理；
- 经过治理的统计结果。

跨租户共享至少需要明确：

- 提供方和接收方；
- 数据内容、用途和期限；
- 双方责任；
- 是否允许继续转交；
- 数据更新、撤回和纠错方式；
- 到期后的删除或归还；
- 必要的安全和审计要求。

租户强隔离不等于永远不能交换数据，而是所有跨租户流动都必须经过明确建立的桥梁，不能依靠直接穿透边界的后台权限。

## 十七、管理权限为什么不等于数据访问权限

能管理平台，不等于能查看平台中的全部业务数据。

例如：

- 平台管理员可以配置系统，但不应默认查询客户明细；
- 租户管理员可以管理本租户账号，但不应自动取得所有敏感数据；
- 数据目录管理员可以维护元数据，但不一定能预览原始数据；
- 审批人员可以决定是否授权，但不一定需要读取全部内容；
- 运维人员可以维护数据库服务，业务数据访问仍应受到额外控制。

管理控制面与业务数据访问面适当分开，可以减少“技术超级管理员天然拥有一切”的风险，也有利于职责分离。

## 十八、怎样选择共享路径

```text
产生数据使用需求
        ↓
是否属于本部门或项目默认范围？
    ├── 是 → 按默认权限使用
    └── 否
         ↓
是否为已知对象、短期、特定目的？
    ├── 是 → 直接受控授权或加入项目组
    └── 否
         ↓
是否会长期、稳定、多人反复使用？
    ├── 是 → 治理并上架为数据资产
    └── 否 → 保留为受控资源，不强行资产化

如果跨越租户边界
        ↓
无论是否已经资产化，都要走正式的数据提供或交换流程
```

共享、授权、编目和资产管理分别处于不同层次：

- 共享：业务上允许其他主体使用数据；
- 授权：把共享决定落实为具体访问权限；
- 编目：说明数据是什么、在哪里、由谁负责；
- 资产上架：把成熟数据作为可发现、可申请、可运营的产品提供；
- 组织内开放：对符合条件的组织成员建立默认授权；
- 对外公开：向不特定外部对象提供数据。

资产申请最终仍然要产生数据授权；直接授权则不一定要求数据先成为上架资产。

## 十九、案例：集团销售分析怎样形成访问边界

某平台服务多个独立企业，每家企业是一个租户。甲企业内部包括华东销售部、华北销售部、财务部和客户服务部。

甲企业建立一个经营分析项目组，由华东销售、财务和客户服务人员共同参与。

某位项目成员的权限由以下条件共同形成：

1. 属于甲企业租户，不能访问乙企业数据；
2. 属于华东销售部，默认只能查看华东区域；
3. 拥有数据分析角色，可以查询和分析，但不能修改来源数据；
4. 项目获得部分销售、回款和服务数据授权；
5. 授权只在项目期间有效；
6. 敏感个人信息字段不默认提供；
7. 批量下载和对外提供受到额外限制；
8. 项目结束后回收权限并处置临时结果。

项目形成一项稳定的“区域经营分析数据集”后，多个区域和部门开始反复申请使用。企业不再逐一临时授权，而是明确口径、负责人、更新频率和使用条件，将其治理并上架为正式数据资产。

这个案例说明：租户提供强边界，部门提供默认范围，项目提供临时协作空间，角色决定操作能力，数据授权决定具体对象，成熟成果再通过资产管理形成规模化供给。

## 二十、常见误区

### 误区一：租户就是部门

租户通常是独立组织和责任边界，部门是租户内部的管理范围，不能为了省事相互替代。

### 误区二：部门越多，租户越多越安全

过多租户会切碎统一治理和内部协作，并不等于更安全。

### 误区三：部门数据范围意味着部门之间绝对不能共享

部门提供默认边界，合理的跨部门使用可以通过项目和数据授权实现。

### 误区四：加入项目组，就可以查看各成员部门的全部数据

项目只应获得实现目标所需的指定数据。

### 误区五：拥有角色就自动拥有全部数据

角色主要定义操作能力，具体数据仍受租户、组织范围和数据授权约束。

### 误区六：岗位名称可以直接复制为系统角色

岗位、职责、数据范围和期限需要拆开表达，否则容易形成大量难以维护的角色。

### 误区七：数据授权只需要确定“能不能看”

授权还要明确操作、范围、目的、环境、期限和到期处理。

### 误区八：管理员天然可以查看全部业务数据

平台管理权、租户管理权和业务数据访问权应当适当分开。

### 误区九：所有共享都必须先上架为数据资产

短期、明确、一次性的协作可以直接受控授权，不应把临时数据强行包装成资产。

### 误区十：长期共享一直采用点对点授权最灵活

重复需求长期依靠直接授权，会造成重复审批、权限累积和数据版本混乱。

### 误区十一：页面上隐藏按钮就完成了权限控制

访问边界必须在实际数据查询、服务调用和操作过程中得到执行，不能只依赖界面显示。

### 误区十二：跨租户共享只是增加一个账号权限

跨租户意味着跨越独立责任边界，需要正式的数据提供、交换或服务关系。

## 小结

租户是强隔离边界，不同租户默认互不可见；部门是租户内部的默认数据范围，不应成为阻止合理协作的硬墙；项目组是跨部门、面向特定目标和期限的临时协作边界；角色表达可以执行什么操作，数据授权则确定可以对哪些具体数据执行这些操作。

部门和项目组之间的数据共享也不应只有一条流程。临时、明确的需求可以直接受控授权，跨部门项目可以使用项目数据范围，成熟、稳定、多人反复使用的数据应通过资产管理形成规模化供给，跨租户数据则必须经过正式通道。

权限不是一张简单的用户—菜单对应表，而是租户边界、组织和项目范围、角色能力、具体数据授权以及场景条件共同计算出的结果。
