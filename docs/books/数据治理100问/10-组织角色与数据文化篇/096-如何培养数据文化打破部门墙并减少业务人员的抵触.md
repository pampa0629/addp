# 096 如何培养数据文化，打破部门墙并减少业务人员的抵触？

## 一句话回答

> 数据文化不是多宣传“重视数据”，而是让组织在目标、流程、责任、激励和日常决策中，形成愿意共享、正确使用、主动维护和共同改进数据的习惯。打破部门墙也不是让部门放弃职责，而是让各部门在共同目标和清晰边界下协作并看到数据带来的实际收益。

数据治理经常遇到一个看似态度、实则机制的问题：业务部门不愿意提供数据，不愿意承担质量责任，也不愿意参加标准和口径讨论。管理者可能把这种现象归因于“业务人员不重视数据”，然后通过发通知、开培训和增加考核推动执行。

但业务人员的抵触通常有现实原因：治理增加了工作量，却没有带来明确收益；共享数据可能暴露问题、增加风险或削弱部门控制；责任被分配了，权限和资源却没有跟上；过去的治理项目只留下了平台和表格，没有真正改善业务。要改变这种情况，不能只改变态度，还要改变组织目标、协作方式和工作条件。

## 一、什么是数据文化

数据文化可以从日常行为观察，而不是从口号判断。具有较好数据文化的组织通常会表现为：

- 管理者用数据支持目标、判断和复盘，而不是只在汇报时展示数字；
- 业务人员愿意说明数据含义、反馈问题并参与质量改进；
- 技术人员理解业务语义，不把数据治理简化为接口、脚本和页面；
- 数据使用者遵守授权、理解口径、验证结果并承担使用责任；
- 各部门把数据视为可以共同创造价值的资源，而不是只能由本部门控制的内部财产；
- 组织认可标准、质量、血缘、运营和问题整改等不容易被看见的基础工作。

数据文化不要求每个人都成为数据工程师，也不要求所有管理都完全依赖数字。它要求组织能够说明数据从哪里来、代表什么、适合怎样使用、出了问题谁负责，并把这些要求落实到实际工作中。

## 二、业务人员为什么会抵触数据治理

### 1. 治理被理解为额外工作

如果业务人员需要额外填写目录、补录元数据、参加多次会议，却看不到报表更快、审批更顺或问题更少，治理就会被视为项目组的负担。

### 2. 担心暴露问题后被追责

数据质量问题往往长期存在，源头人员未必有能力独自解决。如果组织只在发现错误时追究个人责任，业务部门自然会选择少提供、少共享和少登记问题。

### 3. 担心共享带来风险和失去控制

数据提供方可能担心误用、泄露、错误解读和责任追溯，也可能担心其他部门使用数据后获得收益，而本部门承担维护成本。没有明确用途、授权边界和反馈机制时，这种担心是合理的。

### 4. 责任增加但权限和资源没有增加

业务负责人被要求对数据质量负责，却没有查看数据结果、协调其他部门、安排整改人员和调整源头流程的权力，最终只能承担形式责任。

### 5. 治理项目缺少可信的业务结果

过去的项目可能重点展示平台上线、表数量和功能模块，却没有减少人工核对、解决口径冲突或支持真实业务决策。业务人员因此把新的治理要求看成又一轮短期运动。

### 6. 规则由技术部门单方面制定

技术人员可以提出结构、格式和实现建议，但不能独自决定业务对象、指标口径和质量目标。脱离业务语义的标准越多，业务人员越容易产生抵触。

## 三、从真实业务价值开始，而不是从宣传口号开始

培养数据文化应从一个业务人员确实关心的问题开始，例如：

- 减少经营报表的手工汇总和反复核对；
- 提前发现库存、交付或项目进度异常；
- 缩短审批、监管报送和客户服务所需时间；
- 减少同一指标在不同部门之间的争论；
- 提高新业务、新区域或新数据源接入的速度；
- 降低数据泄露、错误使用和重复建设风险。

推进时可以遵循以下路径：

1. 选择一个跨部门、影响明确且参与者愿意改善的业务场景；
2. 记录治理前的等待时间、人工工作量、质量问题和争议情况；
3. 让业务人员参与定义目标、口径、质量要求和验收方式；
4. 只建立解决试点问题所需的最小标准、规则和服务；
5. 让参与者看到报表更快、问题更少或业务决策更及时的变化；
6. 总结可复用的规则和协作方式，再逐步扩大范围。

治理的第一个成果应当是业务工作变得更容易，而不是增加一张新的治理报表。

## 四、管理层应该提供什么支持

一把手和各级管理者需要把一次性行政推动转化为稳定工作条件：

- 明确数据治理服务的业务目标，而不是只要求“建设数据平台”；
- 为跨部门协作、数据共享和口径冲突提供授权；
- 为数据责任、质量整改和日常运营配置人员、时间和预算；
- 要求业务部门参与数据定义、质量判断和应用反馈；
- 保护主动发现问题和如实报告风险的人员；
- 把数据使用和治理责任纳入经营管理、绩效评价和项目验收；
- 定期检查治理是否改善了业务结果，而不只检查平台进度。

管理层不应亲自决定每个字段，也不应把所有问题直接推给数据部门。它要做的是明确方向、授权资源、处理重大冲突并确保专业团队能够履责。

## 五、让责任、权限和收益匹配

数据文化很难在责任失衡的环境中形成。组织应明确：

| 责任对象 | 需要匹配的条件 |
| --- | --- |
| 数据责任人 | 能查看结果和影响范围，能够确认业务定义和整改要求 |
| 数据治理专员 | 有协调、跟踪、升级和维护治理记录的渠道 |
| 数据保管员和技术团队 | 有实现安全、备份、质量检查和运行变更的资源 |
| 数据资产运营者 | 能获得使用反馈、质量状态和服务运行信息 |
| 数据提供部门 | 能明确共享用途、授权边界、维护投入和业务回报 |
| 数据使用者 | 能获得清晰口径、质量状态、使用说明和反馈渠道 |

数据提供方不一定因为共享就失去控制权，但应接受明确的用途、权限和审计约束；数据使用方也不应把“共享”理解为可以随意使用和重新发布。

## 六、用机制改变日常行为

数据文化不能只依靠培训和倡议，还要进入日常工作机制：

- 在项目立项时明确数据对象、责任、质量和使用目标；
- 在系统建设和业务流程变更时同步评估数据影响；
- 在指标发布前完成定义、审核、版本和下游通知；
- 在发现问题后按照责任、优先级和时限形成闭环；
- 在数据共享前明确用途、授权、安全和反馈方式；
- 在数据资产运营中持续收集使用、质量和退出信息；
- 在考核、激励和问责中认可共享、维护、整改和复用行为。

好的机制应当让正确行为更容易发生，而不是让业务人员额外记住一长串制度名称。

## 七、建立跨部门的共同语言

部门墙不仅是数据没有打通，也包括概念、目标和利益没有对齐。可以通过以下方式降低理解成本：

### 1. 让业务人员参与定义

术语、数据标准和指标不能由技术部门单独编写。业务责任人需要说明数据代表什么、为什么重要、适用什么范围，以及什么结果才算正确。

### 2. 区分合理差异和真正冲突

销售客户、活跃客户和付费客户可能都是合理指标。治理要做的是规范名称和定义，而不是为了“统一”而删除业务差异。

### 3. 用案例说明影响

通过血缘、数据流和实际报表展示一个口径变化会影响哪些流程和决策，比抽象地要求“遵守标准”更容易建立共识。

### 4. 让技术人员理解业务语义

数据工程师、平台工程师和治理平台软件工程师需要理解处理的数据和业务规则，不能只关注任务是否成功、接口是否返回和页面是否展示。

共同语言不是让所有人使用完全相同的专业术语，而是让关键概念有清晰定义，分歧能够被准确表达和处理。

## 八、建立安全的反馈和试错环境

如果员工认为“谁发现问题谁倒霉”，组织就很难得到真实数据。应当建立以下区分：

- 发现并报告问题是治理能力，不等于造成问题；
- 首次发生、影响有限且及时整改的错误，应优先改进流程和培训；
- 由于系统缺陷、权限设计或资源不足造成的问题，不能简单归咎于个人；
- 故意隐瞒、越权修改、绕过安全控制和反复拒不整改，才应进入严格问责；
- 重大问题应有复盘、申辩和复核机制，避免形成“少说少错”的氛围。

安全反馈环境不等于没有责任，而是让组织能够获得真实信息，并把责任追究放在真正需要改进的行为上。

## 九、培训应该围绕岗位和场景

单独讲平台菜单和制度条文，通常难以改变行为。培训应结合角色和实际任务：

- 管理者学习数据治理的业务价值、授权方式和决策责任；
- 业务人员学习业务定义、指标口径、质量规则和数据边界；
- 数据治理专员学习标准、协作、问题闭环和影响分析；
- 技术人员学习业务语义、生命周期、质量和变更影响；
- 数据使用者学习查找、理解、授权使用和结果验证；
- 数据资产运营者学习服务说明、用户反馈、使用分析和退出机制。

培训最好使用组织自己的业务案例和数据问题，结合工作流程安排练习，并在一段时间后观察行为和结果是否发生变化。

## 十、如何评价数据文化是否在改变

可以从四个方面观察：

| 观察方面 | 可关注的变化 |
| --- | --- |
| 参与行为 | 业务人员参与定义、规则评审和质量整改的比例 |
| 协作行为 | 主动共享、问题报告、跨部门闭环和重复争议变化 |
| 使用行为 | 目录检索、资产复用、统一指标使用和反馈响应 |
| 业务结果 | 报表准备时间、人工核对、决策等待和风险事件变化 |

还可以通过访谈和案例复盘了解：业务人员是否清楚自己的数据责任，技术人员是否理解业务口径，发现问题后是否愿意升级，以及治理成果是否进入真实业务流程。

不能只统计培训次数、宣传文章数量、签署承诺数量和会议次数。这些可以说明组织做过动作，却不能证明日常行为已经改变。

## 十一、案例：从门店数据抵触到共同维护

某零售企业要求门店登记促销、缺货和客诉信息，总部用于分析销售波动和调整补货。但门店员工认为这只是给总部“填表”，录入项目多、规则不清，出错后还会被通报，因而经常延迟或随意填写。过去，总部只强调“提高数据意识”，却没有解决门店的工作量、反馈和收益问题。

组织随后选择“减少缺货并缩短门店补货等待时间”作为共同业务目标。运营部门与门店的数据责任人共同删减无用录入项，确认促销和缺货状态；数据治理专员组织标准和质量规则；技术团队自动带入已有信息，并把补货进度和异常原因反馈给门店；数据资产运营者收集使用反馈。管理层为源头改进安排人员和时间，不再只按错误数量评价门店。

在试点中，问题登记数量一度增加，因为过去被忽略的缺货和促销异常开始被真实记录；但无效录入时间、缺货时长和重复沟通逐步减少。组织没有把问题增加简单判断为治理失败，而是认可主动发现和解决问题的门店，并根据复盘结果优化流程和权限。

这个案例说明，数据文化的改变不是让业务人员突然“喜欢治理”，而是让他们看到共同目标、责任边界、资源支持和实际收益，并在真实工作中形成新的协作习惯。

## 十二、常见误区

### 误区一：数据文化就是多宣传、多培训

宣传和培训可以提供认知基础，但没有业务价值、机制、资源和激励，行为不会长期改变。

### 误区二：业务人员抵触是因为不懂技术

抵触往往来自额外工作、风险担忧、责任失衡、历史失信和看不到收益。先解决这些现实问题，比要求业务人员学习更多技术术语更有效。

### 误区三：用行政命令要求所有部门立即共享

共享必须有明确用途、授权边界、安全控制、责任安排和反馈机制。没有这些条件，行政命令只能带来一次性提供。

### 误区四：把数据文化交给数据治理部门负责

数据治理部门可以组织机制和提供支持，但管理层、业务部门、技术团队和数据使用者都要在日常工作中承担责任。

### 误区五：所有部门都必须使用同一种治理方式

组织可以根据业务特点采用不同流程和治理深度，但关键定义、责任、权限和安全边界必须能够协同。

### 误区六：不允许暴露问题才能维护部门形象

隐藏问题会让风险在下游扩大。组织应认可及时发现、报告和解决问题的行为，并对故意隐瞒和反复违规进行区分处理。

### 误区七：部门墙只靠多开协调会就能消失

会议只能提供沟通机会，真正改变部门墙还需要共同目标、管理授权、责任机制、资源投入、激励和业务结果。

## 小结

数据文化是一组可以观察和持续改进的组织行为：管理者用数据支持决策，业务人员参与定义和维护，技术人员理解业务语义，使用者遵守边界并反馈结果，各部门在共同目标下共享数据和承担责任。

培养数据文化应从真实业务价值开始，逐步建立清晰责任、匹配权限、稳定流程、合理激励和安全反馈环境。打破部门墙不是消除部门职责，而是让部门之间能够围绕同一业务结果协作，并且看到共享和治理带来的收益。

真正成熟的数据文化，不是所有人都喜欢治理工作，而是组织已经把数据治理融入业务流程：问题可以被发现，责任能够被承担，协作能够获得回报，数据能够持续为业务增值。
