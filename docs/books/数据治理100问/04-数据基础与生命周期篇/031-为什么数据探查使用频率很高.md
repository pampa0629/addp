# 031 为什么数据探查在数据治理中使用频率很高？

## 一句话回答

> 数据探查是在不了解或不完全信任数据时，通过元数据扫描、样本预览、统计剖析和关系分析等方式，快速弄清“数据实际上是什么样”的过程。数据接入、标准映射、建模、质量规则设计、问题排查和变更验证，都必须建立在对真实数据的认识之上，因此数据探查不是项目开始时的一次性工作，而是贯穿数据治理全过程的高频活动。

数据字典、接口文档和数据库结构描述的是数据“应该是什么样”，数据探查则帮助我们看到数据“实际上是什么样”。两者之间经常存在差异：声明非空的字段可能存在空字符串，文本字段可能混合日期和备注，所谓唯一编号可能重复，坐标字段可能采用了未注明的坐标系。

数据治理不能仅根据字段名称和设计文档制定标准、模型与质量规则。先观察事实，再与业务人员确认含义，才能避免把错误认识固化进后续治理链路。

## 一、什么是数据探查

本书所说的数据探查，是围绕一项数据及其业务用途开展的探索性认识过程。它通常综合使用以下手段：

- 扫描数据库、文件和数据项的结构及技术元数据；
- 查看有代表性的样本和具体记录；
- 统计空值、基数、值域、分布和模式；
- 识别候选主键、关联字段和实体关系；
- 检查时间范围、更新规律和数据断档；
- 观察空间范围、坐标、几何和拓扑特征；
- 与数据字典、标准、业务规则和其他来源进行比较；
- 针对发现的异常提出假设，再通过条件查询或全量计算验证。

数据探查的核心目的不是立即对数据作出合格或不合格的结论，而是回答：

- 这批数据包含什么；
- 数据真实采用了什么结构、格式和取值；
- 哪些字段可能具有业务含义；
- 哪些对象和记录可能相互关联；
- 数据中存在哪些规律、异常和未知问题；
- 下一步应该向谁确认，制定什么标准、模型或规则。

因此，探查是一种“先认识，再治理”的工作方式。

## 二、数据探查、数据剖析和质量检测有什么区别

这些概念常被混用，但它们解决的问题不同。

| 概念 | 主要回答的问题 | 典型结果 |
| --- | --- | --- |
| 元数据扫描 | 有哪些数据项、表、字段、类型和文件 | 数据目录、结构、类型和技术属性 |
| 数据预览 | 具体记录大概长什么样 | 少量样本、地图或内容片段 |
| 数据剖析 | 数据的完整性、基数、值域和分布有什么特征 | 空值率、唯一值数、频率、分位数和特征提示 |
| 数据探查 | 综合以上信息后，数据实际状况和潜在关系是什么 | 假设、问题线索、映射建议和待确认事项 |
| 数据质量检查 | 数据是否满足已经确定的正式质量规则 | 通过率、失败记录、质量问题和整改状态 |
| BI 分析 | 数据反映了什么业务现象和经营变化 | 指标、趋势、对比、洞察和决策依据 |

### 1. 数据探查是较宽泛的实践过程

探查可以包含元数据扫描、数据预览、数据剖析、查询验证、空间观察和业务访谈。它不一定对应一个独立软件模块，也不要求每次都执行所有步骤。

### 2. 数据剖析是探查中的统计量化能力

数据剖析（Data Profiling）通常面向表格型数据，通过受控采样或显式全量执行，分析字段完整性、基数、值域和分布特征。

例如，剖析发现某字段缺失率为36%、某个编码字段有127个不同取值、数值分布明显偏斜。这些是对数据特征的观察，不自动等于质量问题。是否不合格，还要看字段业务含义、适用场景和已经确认的规则。

### 3. 数据质量检查依据正式规则作出判断

如果业务已经确定“管线材质不能为空”“管径必须大于零”“管线起点和终点必须连接到管点”，质量检测就可以对全量适用数据进行检查，形成可追踪的问题并推动整改。

可以概括为：

> 数据探查用于发现线索、形成假设和帮助制定规则；数据质量检查用于按照已经确认的规则正式判断是否通过。

探查与质量检测会相互促进：探查发现新的异常模式，推动建立规则；质量检查出现大量失败时，又需要探查数据和规则是否发生变化。

## 三、为什么不能只看数据字典和表结构

数据字典很重要，但它通常描述设计意图，不能完全代表长期运行后的真实数据。

### 1. 数据类型不能说明真实语义

一个文本字段可能保存姓名、日期、金额、多个编码拼接结果或自由备注。即使两个系统都有名为 `road_id` 的文本字段，也不能据此判断它们使用同一套路段编码。

### 2. 数据库约束不一定覆盖业务约束

数据库允许为空，不代表业务允许缺失；数据库类型为整数，也不代表负数合理；没有外键约束，不代表两张表之间没有业务关系。

### 3. 历史数据可能没有遵守当前设计

系统升级、数据迁移、规则变化和人工补录，都可能让同一字段在不同时期使用不同格式或编码。只查看当前数据字典，可能看不到历史变化。

### 4. 空值有多种表现

实际数据中的“缺失”可能表现为数据库空值、空字符串、空格、`0`、`-1`、`未知`、`无`或某个默认日期。只统计数据库空值会低估缺失情况。

### 5. 文档可能已经过时

字段含义、枚举值和接口结构发生变化后，文档未必同步更新。探查可以发现文档与数据之间的差异，但最终含义仍需由业务和系统责任人确认。

因此，数据字典提供理解起点，数据探查提供事实证据，业务确认才决定最终语义。三者不能相互替代。

## 四、数据探查通常探查什么

### 1. 结构和规模

了解数据项、表、字段、数据类型、长度、主键、索引、分区、记录数和文件大小，判断数据的基本组织方式和处理成本。

需要注意，数据库声明的字段类型是结构事实，字段中的实际内容仍可能超出预期；估算行数也不等于精确行数。

### 2. 完整性

观察数据库空值、空字符串、占位值、缺失字段、缺失对象和缺失时间段，并按业务类别、区域或批次比较缺失分布。

全表平均缺失率可能掩盖局部问题。例如总体缺失率只有2%，但某个区县或某个汇交批次全部缺失。

### 3. 唯一性和重复

统计唯一值数量、重复比例和重复组合，寻找候选业务主键，并区分：

- 完全重复的记录；
- 同一对象被多次提交；
- 标识相同但属性冲突；
- 多字段组合才能唯一确定的业务事实。

字段当前没有重复，不等于它天然就是可靠主键。还要确认其生成规则、稳定性和未来是否可能重复。

### 4. 值域、分布和异常值

分析最小值、最大值、均值、分位数、高频值、长尾和异常点，观察数据是否符合基本业务认识。

异常值不一定是错误。极大管径可能是重要的主干管线，极长事件处置时间可能对应重大事故。探查的任务是发现并提供上下文，而不是未经确认就删除异常。

### 5. 格式和模式

识别日期、电话号码、证件号码、业务编码、地址和文本字段的常见模式，判断是否存在大小写、前导零、分隔符、字符集和多种格式混用。

例如，同一建设日期字段可能同时存在 `2025-01-08`、`2025/1/8`、`20250108`和“约2025年”等表达，不能只根据字段类型设计转换规则。

### 6. 关系和颗粒度

通过字段值重合、命名、唯一性和业务知识，识别潜在关联键、一对一、一对多和多对多关系，并检查孤立记录。

关系探查只能提出候选。两个字段值高度重合，可能因为使用同一编码，也可能只是巧合；是否构成正式业务关系，需要结合实体和业务过程确认。

### 7. 时间与鲜活度

查看最早和最晚事件时间、记录时间和更新时间，分析更新间隔、时间断档、未来时间、迟到数据和不同批次分布。

“最后更新时间为今天”不代表全部数据都更新到了今天。还要观察各区域、对象和分区的覆盖范围。

### 8. 空间数据特征

空间数据除了属性字段，还需要探查：

- 坐标参考和坐标范围是否合理；
- 几何类型是否与图层用途一致；
- 是否存在空几何、无效几何和异常坐标；
- 点、线、面是否落在预期区域；
- 管线端点是否与管点连接；
- 相邻区域是否存在缝隙、重叠和接边偏差；
- 空间范围、地图版本和采集精度是否一致。

坐标系元数据缺失时，可以根据数值范围和已知区域提出候选判断，但不能只凭猜测直接转换和覆盖数据。

### 9. 敏感性和使用风险

样本和取值模式可能帮助发现身份证号、电话号码、精确位置和其他敏感字段，但自动识别只能作为线索。数据分类分级仍需结合业务含义、关联风险和法规要求确认。

### 10. 数据倾斜和处理特征

某些字段存在极少数超高频值，某些区域数据量远高于其他区域，可能影响关联、分区、并行计算和指标解释。探查这些特征有助于设计合理的数据处理和计算方案。

## 五、为什么数据探查会反复发生

数据探查并不是数据接入时运行一次、生成一份报告就结束。它会出现在数据治理的多个阶段。

| 阶段 | 为什么需要探查 |
| --- | --- |
| 数据源识别 | 判断数据是否与目标场景相关，实际包含哪些内容 |
| 首次接入 | 核实结构、规模、格式、时间范围和已知问题 |
| 标准映射 | 观察真实取值，确定字段、编码、单位和格式如何映射 |
| 实体建模 | 寻找候选身份、属性、关系、状态和生命周期事件 |
| 维度建模 | 确认业务过程、事实颗粒度、维度取值和历史变化 |
| 质量规则设计 | 根据分布和异常模式提出规则，再由业务确认阈值 |
| 汇聚开发 | 决定全量、增量、分区、关联、转换和资源策略 |
| 源目标验证 | 比较数量、值域、分布、关联和关键指标是否一致 |
| 问题排查 | 指标异常或用户质疑时定位来源、批次和变化 |
| 结构变更 | 判断新增字段、编码或数据分布变化对下游的影响 |
| 产品上线 | 确认数据范围、质量和鲜活度能否满足服务承诺 |
| 持续运营 | 发现数据漂移、未知取值和原有规则失效 |

只要数据来源、内容、业务规则或用途发生变化，就可能需要重新探查。有些探查由人员主动发起，有些则可以根据新数据源、结构变更、质量异常或分布变化自动触发提示。

所以，“使用频率最高”不是指每次都运行最大规模的全量统计，而是指理解数据这一动作会在几乎所有治理环节不断出现。

## 六、数据探查如何转化为治理成果

探查的价值不在于生成更多统计图，而在于把发现转化为可以持续执行的治理成果。

```mermaid
flowchart LR
    A["扫描、预览和剖析真实数据"] --> B["发现规律、异常和未知问题"]
    B --> C["与业务和来源责任人确认"]
    C --> D["沉淀标准、模型、映射和质量规则"]
    D --> E["持续汇聚、检测和服务"]
    E --> F["变化或问题触发重新探查"]
    F --> A
```

### 1. 确定实体身份和候选主键

通过唯一性、稳定性和跨源重合情况，寻找客户、设备、管线、地块等实体的候选标识，再由业务人员确认其生命周期和生成规则。

### 2. 建立标准映射

根据字段含义、实际取值和分布，确定字段、代码、单位、日期格式和空间参考如何映射到统一标准，并识别不能自动映射的例外。

### 3. 修订数据模型

探查可能发现一张表混合了多种颗粒度、一个字段保存多个含义，或者原先认为的一对一关系实际上是一对多。这些发现会影响实体模型、事实表和维度设计。

### 4. 形成质量规则

高缺失、重复、异常范围和孤立关系可以成为质量规则候选。但规则阈值、适用范围和严重程度必须由业务确认，不能把一次样本观察直接发布为组织规则。

### 5. 推动源头整改

如果问题来自业务录入、设备采集或源系统约束，应反馈到责任方改善源头。探查工具不应长期通过下游修补掩盖源头问题。

### 6. 设计数据汇聚和处理方式

数据规模、更新规律、候选主键、分区和倾斜情况，会影响全量、增量、CDC、关联和计算方案。

### 7. 明确服务承诺和使用边界

数据覆盖范围、缺失情况、时间跨度和更新规律，是制定数据产品质量、鲜活度、适用范围和风险说明的重要依据。

### 8. 识别安全和权限要求

发现敏感字段、精确位置或可重新识别的信息后，应进入正式分类分级和权限评审，而不是由探查人员自行决定开放范围。

## 七、采样探查和全量探查如何选择

### 1. 采样适合快速认识和发现线索

面对大型表、文件或生产系统，受控采样可以较低成本观察字段格式、常见取值、基本分布和明显异常，适合首次认识和反复探索。

但“查看前100行”通常不是可靠采样。数据可能按时间、区域或主键排序，前部记录无法代表后续批次。更合理的方式包括随机采样、分区采样、分层采样和按条件探查。

### 2. 全量适合需要精确结论的检查

候选主键是否真正唯一、源目标是否完整一致、正式质量规则有多少失败记录，通常需要全量执行或具有等价保证的计算。

全量探查成本更高，还可能影响生产系统，因此要控制读取范围、并发、时间窗口和资源使用，必要时在经过授权的副本或分析环境执行。

### 3. 采样和全量不是二选一

常见路径是先用样本发现线索，再针对可疑字段、特定分区或重要规则执行条件探查和全量验证。没有必要每次都扫描所有数据，也不能用样本结果证明全量数据没有问题。

### 4. 必须记录本次探查范围

剖析结果应说明：

- 使用的是样本还是全量；
- 样本如何选择、数量是多少；
- 数据对应哪个稳定数据项和源版本；
- 是否限定了时间、区域或其他条件；
- 执行时间和配置是什么。

否则，不同时间产生的两份统计结果无法正确比较。

## 八、数据探查会不会修改数据

通常不会。数据探查原则上是只读分析，用于认识数据状况，而不是直接清洗或修正数据。

发现问题以后，应按问题性质进入不同路径：

- 业务事实错误，回到权威源系统由责任方整改；
- 编码、单位和格式不一致，在标准化和汇聚层进行可追溯转换；
- 可复用的质量要求，沉淀为正式质量规则并持续检查；
- 表结构或模型不合理，调整模型和数据链路；
- 样本或统计结果不确定，扩大范围或进行全量验证；
- 敏感信息暴露，进入分类分级、权限和脱敏流程。

不应让探查工具根据统计特征静默修改源数据。例如，发现大量空值后自动填零，可能把“未知”错误地变成真实数值；发现极端值后自动删除，也可能丢失重要业务事件。

探查需要足够权限读取数据，但应遵守最小必要原则。对生产数据、个人信息和敏感数据，应限制字段、样本数量、下载和结果保留，并记录探查执行和使用目的。

## 九、案例：不同区县汇交的地下管线数据

某城市需要汇聚各区县提交的给水、排水、燃气、电力、通信和热力等地下管线数据，支持统一管理、施工审批和风险分析。

数据可能以数据库表、Shapefile、GeoPackage、CAD图纸或其他专业格式汇交。即使各区县都声称遵循同一份标准，实际数据仍可能存在明显差异。

### 1. 先扫描和预览数据

首次接收时，需要了解：

- 每个批次包含哪些文件、图层和表；
- 管线、管点和附属设施如何组织；
- 字段名称、类型、长度和编码方式；
- 数据量、空间范围、坐标参考和几何类型；
- 汇交单位、采集时间、版本和覆盖区域。

样本预览可以帮助快速识别明显问题，例如点位落在城市范围以外、图层名称与内容不符、中文乱码或字段值全部相同。

### 2. 对属性数据进行剖析

对管线和管点属性进行剖析，可能发现：

- `pipeline_id`在部分区县唯一，在另一些区县重复；
- 管径分别使用毫米、厘米或带单位的文本；
- 材质存在“铸铁”“球墨铸铁”“铸铁管”和内部代码等多种表达；
- 建设年代大量为空，或者使用默认日期；
- 起点、终点编码存在，但无法在管点表中找到；
- 同一批次内出现完全重复或属性冲突的记录；
- 某些字段只在特定管线类型中适用。

这些结果不能直接证明数据不合格。例如，建设年代对于某类历史管线可能确实无法获得；管径为空是否允许，要根据管线类型和业务用途确认。

### 3. 对空间数据进行探查

空间探查可能发现：

- 文件没有声明坐标系，坐标数值与汇交说明不一致；
- 部分数据发生整体偏移或经纬度轴顺序颠倒；
- 管线端点没有落在对应管点上；
- 同一管段重复提交或相互重叠；
- 跨区县管线在边界处没有接上；
- 管线穿越建筑、水体或禁建区域，需要业务核查；
- 图形是二维线，但高程、埋深和管顶标高的语义不一致。

图形相交不一定表示管线实际连通，不同高程的管线可以在平面上交叉。因此，空间关系也必须结合专业业务语义判断。

### 4. 与业务和数据提供方确认

探查团队需要把发现整理为可验证的问题，而不是直接宣判数据错误。例如：

- 这个字段中的`0`表示未知、未测量还是实际为零？
- 管径单位是否随管线类型变化？
- 管线编码是全市唯一、区县内唯一还是批次内唯一？
- 建设日期采用竣工、验收还是入库时间？
- 跨区边界的管线由哪个区县负责维护？
- 空间偏移来自坐标转换还是采集误差？

由市级业务部门、区县数据提供方和专业人员共同确认后，才能确定标准和处理规则。

### 5. 将探查结果沉淀为治理能力

确认以后，可以形成：

- 统一的管线、管点和设施实体及编码规则；
- 字段、材质、管径单位和日期的标准映射；
- 坐标参考、空间精度和汇交范围要求；
- 完整性、唯一性、值域、关联和拓扑质量规则；
- 跨区接边和重复管线的核查流程；
- 汇交批次、数据版本、更新周期和问题责任；
- 面向施工审批和风险分析的数据产品说明。

下一批数据到来时，应重复必要探查，并与历史剖析结果比较。如果出现新的材质代码、字段结构或空间偏移模式，就要判断是合理业务变化、汇交方没有遵守标准，还是标准本身需要修订。

这个案例说明，探查不是为了“找错”而找错，而是帮助治理团队在接收数据时认识真实差异，并把一次发现沉淀为可以持续执行的标准、规则和流程。

## 十、AI 可以怎样辅助数据探查

AI 可以提高探查效率，例如：

- 根据字段名、样本和上下文推测业务含义；
- 推荐候选主键、关联字段和实体关系；
- 总结字段分布、异常模式和数据变化；
- 推荐标准字段、编码映射和质量规则候选；
- 生成探查 SQL、条件查询和结果说明；
- 帮助解释不同来源之间的结构差异；
- 从文档、图片和文本中提取可供进一步验证的信息。

但 AI 推荐不能直接成为正式治理结论：

- 字段名称可能具有行业特殊含义，AI 容易按常见含义误判；
- 样本可能不具有代表性；
- 值相关不等于存在业务关系；
- 异常模式不一定是质量问题；
- 业务规则、权威来源和质量阈值需要责任人确认；
- 敏感样本不能未经授权发送给外部模型；
- 生成的 SQL 要检查权限、执行成本和结果范围。

更合理的分工是：AI 帮助发现候选和解释线索，探查工具提供可验证的统计与样本，业务和数据人员确认语义，治理体系再把确认结果沉淀为标准、模型和规则。

## 十一、如何衡量数据探查是否有效

生成了多少份剖析报告、展示了多少张统计图，不足以说明探查产生了价值。可以观察：

| 方面 | 指标示例 |
| --- | --- |
| 数据理解 | 字段含义确认率、候选主键确认率、关系确认率 |
| 治理沉淀 | 被采纳的标准映射、模型调整和质量规则数量 |
| 接入效率 | 数据接入周期、业务确认时间、返工次数 |
| 问题预防 | 上线前发现问题比例、源目标核对问题数量 |
| 变化响应 | 结构或分布变化发现时间、规则调整周期 |
| 复用效率 | 重复探查 SQL 减少量、剖析结果复用次数 |
| 业务效果 | 因数据理解错误导致的报表、模型和服务问题减少量 |

这些指标也不能机械追求数量。质量规则增加很多，可能意味着数据复杂，也可能意味着规则重复。最重要的是探查结果是否帮助组织更快、正确地理解数据，并减少后续错误和返工。

## 十二、常见误区

### 误区一：数据字典完整，就不需要探查

数据字典描述设计和约定，探查验证实际内容。历史迁移、规则变化和录入问题都可能造成二者不一致。

### 误区二：预览几十行就是完成数据探查

样本预览只能帮助直观认识数据，无法准确判断唯一性、全局分布、局部缺失和罕见异常。

### 误区三：数据探查等于数据质量检测

探查发现特征和问题线索，质量检测依据正式规则作出判断。高缺失或异常值只有结合业务用途后，才能判断是否构成质量问题。

### 误区四：探查报告越多，治理效果越好

报告如果没有进入业务确认，没有沉淀为标准、模型、规则和整改行动，只会形成新的文档负担。

### 误区五：数据只需在首次接入时探查一次

来源、结构、取值和业务规则都会变化。变更、异常和新用途都可能触发重新探查。

### 误区六：探查发现的问题都可以自动修复

自动转换适合规则明确的格式和编码问题，业务事实、异常值和关系冲突通常需要责任人确认。未经确认自动修改可能制造新的错误。

### 误区七：数据量太大就无法探查

可以先使用统计信息、受控采样、分层采样和条件探查发现线索，再对关键问题进行全量验证，并合理安排资源和执行时间。

### 误区八：样本剖析结果可以代表全量结论

样本可能遗漏罕见异常、局部分区和历史批次。结果必须标注样本方法、范围、版本和限制。

### 误区九：字段值能够关联，就说明存在业务关系

值重合只能产生候选关系。正式关系还要确认对象、颗粒度、时间和业务规则。

### 误区十：AI 可以自动理解所有字段和规则

AI 能够辅助生成候选，但可能误解行业术语、忽略历史变化和适用边界。正式结论仍需事实验证和业务确认。

## 十三、实践检查清单

1. 本次探查要支持什么业务场景和治理决策？
2. 是否明确探查的数据项、源版本、时间、区域和业务范围？
3. 是否区分元数据扫描、预览、剖析、质量检查和 BI 分析？
4. 是否同时参考数据字典、系统文档和实际数据？
5. 样本如何选择，是否覆盖重要类别、区域、时间和批次？
6. 样本结果是否明确标注范围和限制，没有冒充全量结论？
7. 需要精确判断的唯一性、对账和质量规则是否经过全量验证？
8. 是否探查了结构、完整性、唯一性、值域、格式、关系和颗粒度？
9. 是否分析了事件时间、更新时间、断档、迟到和鲜活度？
10. 空间数据是否检查坐标、范围、几何、拓扑和空间精度？
11. 是否把统计特征与正式质量问题清楚区分？
12. 候选主键、关系、标准映射和质量规则是否经过业务确认？
13. 探查发现的源头问题是否反馈给正确责任方？
14. 探查结果是否沉淀为标准、模型、规则、汇聚方案或产品说明？
15. 是否记录探查配置、执行时间、数据版本和结果变化？
16. 探查查询是否控制了生产系统负载和执行成本？
17. 敏感数据是否限制样本、下载、共享和结果保留？
18. AI 推荐是否作为候选结果，并经过事实与业务验证？
19. 数据结构、分布或用途变化后，是否能够重新探查？
20. 是否用理解效率、问题预防和治理沉淀评价效果，而非报告数量？

## 小结

数据治理面对的不是设计文档中的理想数据，而是长期运行、不断变化并来自不同系统的真实数据。数据探查通过扫描、预览、剖析、关系分析和业务确认，让治理人员先看清实际情况，再决定如何制定标准、建立模型、设计质量规则和组织汇聚链路。

数据剖析是探查中的重要统计能力，但剖析结果只是数据特征和问题线索，不自动构成质量结论；数据质量检测则要依据经过业务确认的正式规则执行。把二者区分清楚，才能避免根据一次样本统计草率判断数据好坏。

从首次接入到持续运营，只要数据来源、内容、规则或用途变化，就需要再次理解数据。因此，数据探查会成为数据治理中使用频率最高的能力之一。只有把探查发现持续沉淀为标准、模型、质量规则和业务行动，它才不只是查看数据的工具，而是推动数据治理不断接近真实业务的基础方法。
