# 052 遇到不认识的行业特有数据格式，应该如何开展治理？

## 一句话回答

> 遇到不认识的行业格式时，不应立即改后缀、强行转换或自行猜测内容，而要先保留原始数据和文件关系，确认格式、版本、来源、业务语义及权威规范，再根据用途选择处理方式：由源头提供标准交换格式、扩展平台解析器、在数据流水线中调用专业计算引擎，或者暂时按原格式管理和交付。治理平台不必亲自解析所有格式，但必须能够管理数据身份、责任、版本、安全、处理过程、计算结果和完整血缘。

行业数据格式的复杂之处，不只是“软件能不能打开”，还在于数据是否被正确理解、是否保留了必要信息，以及能否持续进入业务流程。

## 一、为什么会有大量行业特有格式

不同行业需要表达的对象和计算方式差异很大：

- 建筑与工程需要表达构件、几何、材质和装配关系；
- 医疗影像需要同时保存图像、设备、检查和患者相关信息；
- 地球物理数据需要记录测线、采样、波形和专业解释参数；
- 遥感数据需要管理波段、分辨率、坐标和传感器信息；
- 工业设备数据可能由专用采集软件使用二进制格式保存；
- 三维、点云和仿真数据需要表达普通二维表难以承载的结构。

这些格式可能是国际或国家标准，也可能是行业标准、事实标准、厂商格式或组织内部格式。有些格式公开透明，有些依赖特定商业软件，还有些存在多个不完全兼容的版本。

因此，不能要求所有行业数据都天然以CSV、JSON或关系表形式出现。治理体系需要承认专业格式的合理性，同时建立可识别、可扩展和可追溯的处理机制。

## 二、先区分格式、结构和业务语义

面对陌生数据时，首先要区分三个层次。

### 1. 文件格式

文件格式说明字节怎样编码和组织，例如文件头、数据块、压缩方式、版本和校验规则。解析器主要解决这一层。

### 2. 数据结构

数据结构说明文件中包含哪些对象、属性、层级和关系。例如一个工程模型可能包含建筑、楼层、构件、材料和空间关系。

### 3. 业务语义

业务语义说明这些对象在行业中代表什么、使用什么单位、形成于哪个业务阶段、能支撑什么判断。

能够打开文件，只说明格式可能被识别；能够列出字段，也不代表已经理解数据。例如，解析器可以读出一个名为 `Status` 的属性，但它究竟表示设计状态、施工状态还是设备运行状态，仍然需要业务说明。

因此：

> 格式解析是行业数据治理的入口，不是治理的终点。

## 三、遇到陌生格式时首先应该做什么

### 1. 保留原始数据

在尚未确认格式和处理方法前，应保留：

- 原始文件内容和名称；
- 原始目录和文件之间的相对关系；
- 交付批次和文件清单；
- 文件大小、校验值和接收时间；
- 数据提供方和交付说明；
- 样例文件及其预期结果。

不要直接修改后缀、拆散文件组或覆盖原文件。很多行业数据由多个主文件、索引文件、配置文件和资源文件共同组成，任意移动或缺失其中一部分都可能导致数据无法读取。

### 2. 先进行安全隔离

来源未知的文件可能包含恶意内容、异常压缩包或解析器漏洞风险。在使用桌面软件或服务端解析前，应进行病毒检查、文件类型识别、大小和解压限制，并在受控环境中处理。

### 3. 联系数据提供方

数据源头通常最了解数据如何形成。应优先询问：

- 使用什么软件和版本生成；
- 格式名称和版本是什么；
- 是否有标准、数据字典或交换说明；
- 是否由多个文件共同组成；
- 是否能够导出开放或通用交换格式；
- 数据描述什么业务对象，单位和坐标是什么；
- 提供的样例应该呈现什么内容。

与其由下游反复猜测，不如把格式和语义说明纳入数据交付契约。

## 四、怎样识别一种陌生格式

文件后缀只是线索，不能作为唯一依据。可以综合判断：

- 扩展名和文件命名规则；
- 文件头或特征字节；
- MIME类型或媒体类型；
- 文本编码和内部标识；
- 文件中声明的格式版本；
- 同目录下的伴随文件；
- 生产软件、设备和操作系统；
- 官方标准、厂商文档和行业资料；
- 可靠工具对文件的识别结果。

识别后还要确认具体版本。有些工具虽然声称支持某种格式，却只支持旧版本或部分内容；同一后缀在不同软件中也可能代表不同格式。

对于具有权威标准的格式，应优先查阅正式规范和官方实现说明。对于私有格式，应确认授权、解析接口、软件依赖和长期可访问性，避免把重要数据锁定在即将停用的软件中。

## 五、治理行业格式的四条主要路径

治理平台不必采用唯一方式处理所有格式。应根据业务用途、格式开放程度和计算要求选择以下一种或多种路径。

### 1. 由数据源提供可识别的交换格式

最了解原生数据的软件或生产方，通常最适合执行第一次标准化导出。

例如，Revit原生模型可以由数据提供方导出IFC等开放交换格式，使下游不必直接依赖特定版本的原生软件和私有格式。

这种方式的优点包括：

- 数据提供方知道正确的导出范围和业务阶段；
- 可以利用原生软件自身的格式转换能力；
- 下游可以基于相对开放的标准建设通用能力；
- 有利于跨组织和跨软件交换。

但交换格式不一定完整保留原生格式的全部能力。Revit模型导出为IFC时，部分参数化行为、族信息、专用属性、显示效果或软件特有能力可能发生变化。

因此，数据交付还应明确：

- 原生软件、格式和版本；
- 交换格式及其具体版本；
- 导出范围、视图、参数和映射规则；
- 是否使用特定交换视图或行业约定；
- 已知的信息损失和使用限制；
- 原生文件与交换文件之间的对应关系；
- 导出结果是否经过业务和技术验证。

对于需要长期保存或可能重新处理的重要数据，通常应同时保留原生文件和交换成果。

### 2. 扩展治理平台的格式解析能力

如果需要在平台中直接完成以下工作，通常需要相应解析能力：

- 提取文件内部元数据；
- 展示结构和内容预览；
- 按属性、空间或时间进行检索；
- 执行内容级质量检查；
- 建立对象和字段级血缘；
- 将数据转换为其他格式；
- 直接提供查询或访问服务。

解析器不应散落在不同功能中硬编码，而应作为可扩展能力进行注册和管理。每个解析器至少需要说明：

| 内容 | 需要说明什么 |
| --- | --- |
| 格式标识 | 支持什么格式、扩展名和媒体类型 |
| 版本范围 | 支持哪些格式版本 |
| 识别方式 | 怎样根据文件头、清单或结构确认格式 |
| 解析能力 | 能提取哪些元数据、对象和属性 |
| 预览能力 | 能否生成缩略图、地图、模型或文本预览 |
| 转换能力 | 可以转换成哪些格式，是否有信息损失 |
| 质量能力 | 能执行哪些结构或内容检查 |
| 依赖与授权 | 需要哪些库、软件、许可证和运行环境 |
| 限制 | 不支持哪些内容、版本和边界情况 |

新格式可以通过增加解析器纳入体系，而不应修改所有目录、质量、资产和服务流程。

### 3. 在数据流水线中接入专用计算引擎

有些行业格式难以由通用平台解析，或者真正有价值的工作必须由专业软件和算法完成。此时，治理平台自身不一定需要理解文件内部全部结构。

只要数据流水线能够：

- 将原始数据可靠交给专业引擎；
- 传递必要的参数、规则和运行上下文；
- 启动并监控专业计算；
- 获取计算结果、派生成果或服务；
- 记录输入、输出、参数、版本和执行状态；
- 将结果继续交给后续治理和业务应用；

就可以让特有格式参与完整的数据生产过程。

例如：

- BIM专业引擎读取工程模型并计算构件工程量；
- 遥感处理引擎读取影像并生成分类或变化检测结果；
- 点云引擎读取激光雷达数据并提取地形或建筑物；
- 地球物理软件读取专业观测文件并形成解释成果；
- 工业仿真引擎读取模型和工况数据并输出性能指标。

平台可以把原始文件视为受治理的输入对象，通过位置或数据引用交给引擎，再接收表格、文件、指标、模型或服务形式的输出。

#### 专用计算引擎仍然需要被治理

平台不解析原始格式，不等于可以把计算过程当作黑盒。至少应记录：

- 输入数据的稳定标识、版本和校验值；
- 输入格式及其声明版本；
- 专用引擎、算法和软件版本；
- 执行参数、配置和必要环境；
- 运行时间、状态、日志和资源消耗；
- 输出清单、结构、业务含义和质量结果；
- 输入、计算过程和输出之间的血缘；
- 软件授权、安全和数据外发边界；
- 失败、重试、重算和结果失效机制。

只有这样，业务人员才能知道计算结果由什么数据、什么工具和什么参数产生，并在规则或引擎升级后重新计算。

### 4. 按原格式管理和交付

有些行业数据当前只需要归档、检索、申请和下载，并不需要在线预览或计算。也有些格式暂时没有可靠解析工具，但原始数据仍然具有保存和证据价值。

此时可以把文件作为暂时不透明的数据对象，先完成文件级治理：

- 数据名称和业务说明；
- 格式声明和已知版本；
- 文件清单和校验值；
- 来源、形成时间和责任人；
- 数据范围和交付批次；
- 密级、权限和允许用途；
- 保留期限和生命周期；
- 获取方式和使用软件说明。

按原格式管理不是放弃治理，而是在能力有限时先保证数据不丢失、可发现、可控制和可追溯。后续增加解析器或专业引擎后，可以继续补充内容级元数据和服务能力。

## 六、如何根据用途选择处理路径

| 业务需求 | 更合适的处理方式 |
| --- | --- |
| 只需归档、发现和下载 | 按原格式进行文件级治理 |
| 需要跨组织或跨软件交换 | 由源头提供标准交换格式 |
| 需要平台内检索、预览和质量检查 | 扩展格式解析能力 |
| 需要专业计算但无须通用解析 | 在数据流水线中调用专用计算引擎 |
| 需要保留最高信息完整度 | 保存原生格式，并同时提供适用的交换格式 |
| 需要长期复用计算结果 | 管理原始数据、引擎、参数和派生结果的完整血缘 |

这些方式可以组合使用。例如，一份Revit模型可以保留原生文件，同时提供IFC交换成果；平台解析IFC提取构件元数据，专业引擎读取模型计算工程量，最终将结构化结果提供给成本分析。

关键不是选择一种“最先进”的方式，而是以最低合理成本满足真实业务需要，并保证结果可信和可追溯。

## 七、为什么复合格式必须按数据集管理

有些行业数据不是一个独立文件，而是由一组文件共同构成。例如：

- 主数据文件、索引文件和属性文件；
- 模型文件、纹理图片和材质文件；
- 影像文件、坐标信息和元数据文件；
- 测量数据、设备配置和校准文件；
- 压缩包中的目录清单和分块文件。

治理时应识别“文件”和“数据集”两个层次：

- 文件是具体存储对象；
- 数据集是能够被完整理解和使用的一组相关文件。

需要记录主文件、伴随文件、必需项、可选项、相对路径和完整性规则。只登记主文件或把多个文件拆散存放，可能导致数据无法解析。

压缩包也不能天然视为一个完整数据集。需要确认其内部目录、文件数量、清单、嵌套压缩和解压安全，并验证解压后的组成是否符合格式规范。

## 八、为什么需要建立格式注册表

如果每次遇到新格式都由项目人员临时搜索工具、编写脚本，组织很难形成可复用能力。

格式注册表可以统一记录：

- 规范格式名称和常见后缀；
- 媒体类型、文件头和识别规则；
- 公开标准、厂商和参考文档；
- 格式版本和兼容范围；
- 单文件还是复合数据集；
- 对应的数据类型和业务领域；
- 可用解析器及其能力；
- 可调用的专业计算引擎；
- 支持的预览、转换和输出方式；
- 已知限制、安全风险和授权要求；
- 责任人和维护状态。

格式注册表管理的是组织“怎样认识和处理某种格式”的知识，不等于保存该格式的所有具体数据。具体数据仍需要自己的身份、元数据、权限、质量和生命周期。

## 九、格式转换怎样避免数据损失和失真

格式转换的目标不是让后缀看起来统一，而是让数据能够在目标场景中使用。

转换前应明确：

- 为什么要转换；
- 哪些内容必须保留；
- 目标格式能否表达原始对象、属性和关系；
- 转换是无损、近似还是明确有损；
- 谁负责确认转换结果可用于目标业务。

转换过程应记录：

- 原始文件和目标文件的标识与校验值；
- 转换工具、版本和参数；
- 字段、对象、单位和坐标映射；
- 被忽略、简化或无法表达的内容；
- 错误、警告和转换统计；
- 前后对象数量、范围和关键属性对比；
- 人工抽查或业务验收结果。

原始数据、标准交换数据和业务派生结果应作为不同数据对象管理，并通过血缘关联，不能用转换结果悄悄覆盖原始文件。

## 十、案例：BIM模型如何进入数据治理流程

某建设项目交付了一批由Revit形成的模型文件。后续需要完成模型归档、构件检索、工程量分析和跨软件共享。

### 1. 先明确交付内容

治理人员与提供方共同确认：

- Revit软件和原生文件版本；
- 模型对应的项目、专业、楼层和交付阶段；
- 外部链接、族、纹理和其他依赖文件；
- 坐标、单位和模型基点；
- 模型责任人和审核状态；
- 后续需要支持的业务用途。

### 2. 同时保留原生格式和交换格式

原生文件用于保留最高程度的模型能力和后续专业修改；提供方按约定导出IFC，用于跨软件交换和通用治理。

交付契约明确IFC版本、导出参数、属性映射、构件范围和已知损失，并对构件数量、空间范围和关键属性进行前后验证。

### 3. 解析器提供通用治理能力

平台通过IFC解析器提取：

- 项目、建筑、楼层和空间层级；
- 构件类型、标识和主要属性；
- 坐标、包围范围和模型版本；
- 构件之间的组成和空间关系；
- 可用于搜索和预览的索引。

这些信息进入目录、检索、权限和资产管理体系，但不能代替原始模型。

### 4. 专业引擎完成专业计算

数据流水线将模型交给BIM专业引擎，按照指定版本和参数计算工程量、模型检查结果或轻量化成果。

平台不需要重新实现全部BIM算法，但要记录：

- 使用了哪个模型版本；
- 调用了哪个引擎和算法；
- 使用了哪些计算参数；
- 生成了哪些表格、报告和模型成果；
- 结果是否通过业务校核；
- 模型变化后哪些结果需要重新计算。

### 5. 形成可持续使用的数据产品

经过治理后，使用者不仅可以下载模型，还能够：

- 按项目、楼层和构件类型检索；
- 查看模型版本和审核状态；
- 获取经过验证的工程量结果；
- 追溯结果使用的模型、引擎和参数；
- 在模型更新后识别受影响的计算成果。

这时，行业格式不再只是“能打开的文件”，而成为能够持续服务工程管理的数据资源。

## 十一、尚未理解内容时可以治理到什么程度

数据治理不必等到完全解析格式以后才开始。可以分阶段推进。

### 第一阶段：文件级治理

管理文件身份、清单、校验值、来源、责任、安全、版本和生命周期，保证数据不丢失、不混乱、可发现。

### 第二阶段：格式和结构级治理

识别格式、版本、组成和解析能力，提取可用的技术元数据，并验证文件是否完整、可读取。

### 第三阶段：内容和语义级治理

理解内部对象、属性、单位、空间、时间和业务关系，建立标准、质量和实体映射。

### 第四阶段：计算与服务级治理

将数据接入专业计算、转换、查询和业务服务，管理输入、输出、参数、质量和使用反馈。

这种分层方式既避免因暂时无法解析而放弃治理，也避免在没有业务需求时投入过高成本。

## 十二、哪些格式值得投入支持

平台支持的格式数量不是数据治理成效。决定是否增加解析或计算能力时，应考虑：

- 是否支撑明确的业务场景；
- 数据规模和更新频率；
- 使用部门和消费者数量；
- 数据是否具有长期保存价值；
- 不能处理时会造成什么业务风险；
- 是否已有可靠交换格式或外部专业引擎；
- 自研、采购、授权和长期维护成本；
- 格式是否仍在演进或已经停用。

低频、低价值且已有成熟专业软件的数据，可以先按原格式管理并提供受控下载；高频共享、影响关键业务的数据，才值得建设稳定的解析、计算和服务能力。

## 十三、常见误区

### 误区一：修改文件后缀就能转换格式

后缀只是名称的一部分，修改后缀不会改变内部编码，还可能掩盖真实格式。

### 误区二：能用软件打开就表示已经理解数据

能预览不代表知道对象含义、单位、版本、适用范围和业务限制。

### 误区三：统一治理就是全部转换成CSV或JSON

通用格式可能无法表达空间、三维、波形、部件层级和行业语义。转换必须服务具体用途并评估损失。

### 误区四：治理平台必须亲自解析所有格式

平台可以调用专业引擎完成处理，只要能够管理输入、参数、输出、运行状态和血缘。

### 误区五：调用外部引擎后就不需要治理过程

不记录引擎和参数，计算结果无法解释、复现和重算，也无法判断软件升级带来的影响。

### 误区六：交换格式与原生格式完全等价

交换过程可能丢失厂商特有属性、行为和表现能力。重要数据应保留原生文件并验证交换结果。

### 误区七：一个文件就是一个完整数据集

复合格式可能依赖多个文件、目录和资源。拆散或遗漏伴随文件会破坏完整性。

### 误区八：支持的格式越多，平台越先进

真正价值在于关键行业数据能否被可靠理解、计算和使用，而不是格式清单有多长。

## 十四、实践检查清单

1. 是否保留了原始文件、目录关系、清单、版本和校验值？
2. 是否从文件头、生产软件和规范确认格式，而不是只相信后缀名？
3. 数据源是否能够提供标准交换格式、数据字典和导出说明？
4. 是否根据用途选择原格式管理、交换格式、解析器或专业引擎？
5. 复合数据集的主文件、伴随文件和完整性规则是否得到管理？
6. 解析器和计算引擎是否记录支持版本、依赖、限制和授权要求？
7. 转换和计算是否保留工具、参数、输入输出、质量结果和血缘？
8. 是否根据业务价值和长期维护成本决定格式支持范围？

## 结语

面对行业特有数据格式，数据治理既不能因为“不认识”就将其排除，也不能简单转换成通用表格后宣称完成治理。格式只是数据的技术载体，真正需要保护和使用的是其中的业务对象、关系、精度、版本和专业语义。

治理平台可以让源头提供标准交换格式，可以扩展自己的解析器，也可以在数据流水线中调用专业计算引擎；暂时无法处理时，还可以先按原格式进行文件级治理。这些方式并不冲突，应根据用途组合使用。

平台不必理解每一种格式的全部细节，但必须知道数据是什么、由谁提供、怎样处理、产生了什么结果，以及结果能否被追溯和验证。当原始数据、专业计算和业务成果形成完整链路时，行业格式才真正进入数据治理体系并持续为业务增值。
