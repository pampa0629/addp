# 039 数据治理中的资产管理应该包括哪些内容？

## 一句话回答

> 数据治理的成果不仅包括数据表、文件和派生数据，还包括指标与标签、数据服务、模型与算法、数据产品与应用，以及可复用的数据标准、规则和契约等治理成果。只要这些成果具有稳定身份、明确责任、可控边界和复用价值，就应该进入统一资产管理体系，通过资产门户被发现、申请、授权、共享和评价；但不同成果必须分类管理，不必全部笼统地称为“数据资产”。

资产管理的目的不是给所有对象贴上“资产”标签，而是把组织中有价值、可复用的成果管理起来，让使用者能够找得到、看得懂、信得过、用得上，并有人持续负责。

## 一、为什么资产管理不能只管理数据

数据治理会产生数据，但成果并不止于数据。

业务系统中的数据经过汇聚、标准化、建模和计算，可以形成主题数据集、指标、标签和预测结果；这些成果进一步被封装后，还会形成数据服务、算法服务、报表、专题地图和分析应用。治理过程中也会沉淀企业数据标准、通用质量规则、数据契约和本体模型等可复用知识。

如果资产管理只登记数据库表和文件，就会出现一个明显问题：使用者虽然能看到“有哪些数据”，却找不到已经建设好的指标、服务、模型和应用，只能再次加工，造成重复建设。

反过来，也不能因为这些成果都值得管理，就把表、API、模型、报表、规则和应用全部称为同一种数据资产。它们的责任边界、版本方式、权限要求和使用方法并不相同。例如：

- 数据集通常用于查询、下载或分析；
- 数据服务通常由应用调用或订阅；
- 模型算法需要部署、编排或执行；
- 报表和应用面向具体业务人员和业务场景；
- 数据标准和规则需要被引用、执行和版本化。

因此，更合适的做法是：建立统一的资产管理体系和发现入口，同时对不同类型的成果分类管理、关联展示。

## 二、哪些成果应该进入资产管理体系

一个对象是否值得纳入资产管理，不取决于它是不是一张表，也不取决于能否在会计意义上入表。通常需要判断它是否具备以下特征：

- 有清楚的业务含义和使用场景；
- 有相对稳定的身份和边界；
- 有明确的数据责任人、维护者或服务责任人；
- 能够被其他人或其他系统发现和复用；
- 有可控的权限、版本和交付方式；
- 值得持续维护，并能够评价使用效果。

据此，资产管理体系可以重点覆盖以下五类可运营对象：

| 资产类型 | 典型对象 | 主要共享和使用方式 |
| --- | --- | --- |
| 数据内容资产 | 数据表、文件、空间数据、流数据、主题数据集、主数据 | 查询、下载、挂载、交换和订阅 |
| 指标、标签与派生数据资产 | 指标值、标签结果、画像、特征数据、评分和预测结果 | 指标查询、标签圈选、结果订阅和服务调用 |
| 数据服务资产 | 查询服务、空间服务、事件服务和数据交换服务 | 申请调用、应用鉴权、协议访问和事件订阅 |
| 模型与算法资产 | 数据模型、本体模型、算法模型、算子和可复用工作流 | 浏览定义、下载、部署、编排和服务调用 |
| 数据产品与应用资产 | 专题数据集、报表、大屏、专题地图和分析应用 | 申请访问、交互分析和嵌入业务流程 |

此外，可独立复用的数据标准、质量规则模板、数据契约和业务术语等治理成果，也应由相应的标准库、规则库或治理知识库管理，并通过资产门户提供统一检索和关联入口。

这是一套用于实践的分类框架，不是适用于所有组织的固定清单。制造、金融、自然资源和互联网企业的数据形态不同，可以调整分类，但需要始终保持对象边界和管理责任清楚。

## 三、数据内容资产不应只包括数据库表

数据内容是资产管理体系的基础，但不能将“数据”等同于关系数据库中的表。

### 1. 业务系统数据

客户、供应商、项目、合同、订单、付款、审批和设备记录等，都可以纳入资产管理。

不过，来源表只是技术存储单元。一项“合同履约主题数据资产”可能由合同、项目、进度、付款和验收等多张表共同组成，也可能只选择其中业务含义稳定的主表独立发布。

### 2. 文件和非结构化数据

文档、图片、音视频、电子表格、设计文件和扫描档案等都需要管理其集合边界、格式、版本、内容范围、版权或授权、保留周期和检索方式。

例如，一个 Shapefile 由 `.shp`、`.shx`、`.dbf` 和 `.prj` 等多个配套文件组成，业务上通常应作为一个完整数据项管理，而不是把每个文件分别登记成一项资产。

### 3. 时空数据和行业数据

矢量数据、遥感影像、点云、三维模型、BIM、轨迹和行业专有格式都可以进入资产管理体系。管理时应保留其数据类型、空间范围、坐标参考、精度、时间和行业语义，而不是为了进入目录强行拆成普通表。

### 4. 实时流和物联网数据

消息主题、设备观测和业务事件流也可以作为资产对象，但不能只登记一个消息队列地址。还需要描述事件结构、生产者、消费范围、产生频率、延迟、保留时间、顺序和重放能力。

### 5. 主数据、参考数据和主题数据集

经过统一身份、标准、质量和责任治理的主数据，正式发布的参考数据版本，以及面向稳定业务主题组织的数据集，通常具有较强的跨系统复用价值，是资产管理的重点对象。

## 四、指标、标签和派生结果应该怎样管理

指标、标签、画像、特征和模型输出都是数据治理形成的重要成果。管理这些对象时，关键是区分定义、计算结果和使用能力。

### 1. 指标

“合同回款率”的业务含义、计算公式、统计范围、时间粒度和责任人属于指标定义；按地区、产品和月份计算出的合同回款率属于指标结果；对外提供统一查询和订阅，则进一步形成指标服务或数据产品。

```text
指标定义：统一业务语义和计算口径
指标结果：根据定义计算形成的派生数据
指标服务或分析页面：面向用户提供的使用能力
```

这三个对象需要建立关联，但不能合并成一条含义模糊的目录记录。

### 2. 标签与画像

“重点客户”“高风险设备”等标签的业务定义、判断条件和生效规则属于标签定义；给具体客户或设备计算出的标签值属于派生数据；业务人员通过标签组合进行对象圈选和分析，则属于面向场景的数据产品能力。

画像通常围绕客户、设备、项目、地块等业务实体，将主数据、指标、标签、关系和行为事实组织起来。画像数据集、标签体系、刷新任务、查询服务和展示页面可以分别管理，并通过同一个画像主题建立关联。

### 3. 特征和模型输出

为算法训练和推理形成的特征数据集，以及风险评分、流失概率、影像识别结果等模型输出，都属于派生数据。它们需要说明数据来源、计算或模型版本、更新时间、有效期和适用范围，避免模型升级后仍使用已经失效的结果。

## 五、数据服务应作为一类独立资产管理

资产管理不仅要回答“有什么”，还要回答成果怎样稳定交付。数据服务正是将治理成果提供给业务系统、应用和外部授权用户的重要方式。

### 1. 数据服务不等于 API

数据服务是一项具有明确数据来源、目标用户、业务用途、输出契约、版本、权限和服务责任的持续交付能力。API 只是数据服务可能采用的一种接口和交付方式。

一项数据服务可以包含多个 REST、OGC 或其他协议接口，也可以通过事件订阅、SQL 查询端点或定期文件交付。资产门户应以数据服务作为主要管理单元，在具体服务版本下展示 API 端点、字段、鉴权、限流、可用性和变更说明。

### 2. 平台功能 OpenAPI 不是数据服务 API

数据治理平台常会提供用于系统集成的开放接口，产品中往往称为 OpenAPI。这类接口用于创建任务、触发扫描、管理用户、查询平台目录或操作平台配置，服务的是平台功能；数据服务 API 则用于向业务应用交付数据或派生结果。

| 对比维度 | 平台功能 API 或 OpenAPI | 数据服务 API |
| --- | --- | --- |
| 主要目的 | 操作和集成数据治理平台 | 获取或使用业务数据和派生结果 |
| 典型操作 | 创建任务、触发流程、管理用户 | 查询地块、获取指标、订阅设备异常 |
| 主要消费者 | 平台前端、运维工具和集成系统 | 业务系统、数据应用和授权用户 |
| 权限重点 | 平台功能权限和操作审计 | 数据权限、用途限制和调用审计 |
| 资产管理方式 | 通常作为平台技术接口管理 | 作为数据服务资产发布和运营 |

“OpenAPI”有时还特指 OpenAPI Specification，即描述 HTTP API 的技术规范。数据服务 API 可以使用这一规范描述，但不能据此判断一个 API 是否属于数据服务。

### 3. 事件订阅也是数据服务

库存不足、设备异常、项目延期等事件可以通过消息持续提供。事件内容属于数据，订阅契约和持续交付能力属于数据服务。因此，资产门户既要展示服务提供什么，也要说明怎样订阅、如何鉴权、能够保留和重放多长时间。

## 六、模型、算法、数据产品和应用也需要管理

### 1. 模型与算法

实体模型、维度模型、本体模型等描述业务概念和数据组织方式；算法代码、训练流程、模型文件、参数和评测报告用于实现分析、预测或识别能力。这些成果只要能够稳定复用，就应作为模型与算法资产管理其版本、负责人、输入输出、适用范围和运行环境。

模型使用的训练数据、验证数据和特征数据属于数据内容；模型产生的评分和预测结果属于派生数据；将模型封装为可调用能力，则形成算法服务。模型、数据、服务和结果之间需要建立关系，但各自仍应按照本身的类型管理。

一次性 SQL、临时调度配置和单次运行记录通常只是生产过程信息，没有必要都登记为独立资产；可复用算子、正式发布的工作流则可以纳入模型与算法资产管理。

### 2. 数据产品与应用

报表、大屏、专题地图和分析应用围绕明确用户和业务问题组织数据，是数据治理成果进入业务场景的直接载体，应作为数据产品与应用资产管理。

管理这些成果不能只登记页面名称，还应关联其目标用户、业务用途、指标口径、底层数据、质量状态、负责人和更新方式。否则，用户只能看到结果页面，却无法判断数据是否可信，也无法知道问题应由谁处理。

数据产品可以由数据集、指标、标签、服务、模型和交互应用共同构成。它们既需要作为整体运营，也需要保留下层组成对象的独立身份和责任。

## 七、治理知识和附属治理信息应如何管理

数据治理还会产生标准、规则、契约、元数据、质量结果和血缘等成果。它们都需要管理，但并非都适合作为独立资产发布。

### 1. 可复用治理成果进入专业知识库

企业数据标准、业务术语、通用质量规则模板、正式数据契约等，如果具有独立身份、版本、负责人和复用场景，可以由标准库、规则库或治理知识库管理，并通过资产门户被检索、引用和关联。

本体模型既是语义治理成果，也是一类可复用模型，可以由本体或模型模块维护，并在资产门户中作为模型资产展示。

### 2. 附属于资产的信息不必单独资产化

一项资产采用了哪些标准、绑定了哪些质量规则、当前质量如何、从哪里产生、由谁负责、谁有权限使用，这些信息对资产运营非常重要，但通常应附属于相应资产：

- 元数据描述资产是什么、在哪里、何时更新和怎样使用；
- 质量状态和检查结果说明资产是否符合要求；
- 血缘描述资产的来源、派生过程和影响范围；
- 权限、责任、版本、使用统计和评价支撑资产运营。

不应将每条元数据记录、规则绑定、质量检查结果或血缘关系都登记为独立资产。否则，目录数量会迅速膨胀，却不能增加实际可用成果。

质量规则可以分为三个层次：

```text
通用质量规则模板：可复用的治理成果
规则与某项资产的绑定：资产附属配置
质量检查结果和质量状态：资产运行信息
```

## 八、统一门户不等于建立第二套事实源

使用者希望在一个入口中同时找到数据、指标、服务、模型和应用，这是合理需求。但统一资产门户应当汇聚目录信息和关联关系，而不是把各类对象复制到资产模块重新维护。

较合理的职责划分是：

- 数据管理或元数据模块维护数据项及其技术事实；
- 标准模块维护数据标准、业务术语和指标定义；
- 质量模块维护质量规则、任务、问题和检查结果；
- 模型与开发模块维护数据模型、算法和工作流；
- 服务模块维护数据服务、版本和接口；
- 资产模块维护统一目录、发布状态、申请授权、使用评价和资产关联；
- 资产门户面向用户提供统一发现和访问入口。

例如，服务模块中的一项数据服务发布到资产门户后，服务定义和接口契约仍由服务模块维护，资产目录只保存稳定标识、分类、发布状态和关联信息。这样既能统一运营，又不会产生两套不一致的服务定义。

## 九、不同资产应采用不同共享方式

资产管理不仅要回答“有哪些成果”，还要回答“用户怎样获得和使用”。

| 资产类型 | 典型共享方式 | 需要重点说明的信息 |
| --- | --- | --- |
| 数据集 | 查询、下载、挂载、交换 | 范围、结构、质量、更新时间和权限 |
| 指标与标签 | 查询、圈选、订阅、服务调用 | 口径、对象、维度、周期和有效期 |
| 数据服务 | API、SQL 端点、事件订阅、文件交付 | 契约、版本、鉴权、限流和可用性 |
| 模型与算法 | 下载、部署、编排、在线调用 | 输入输出、版本、环境和适用范围 |
| 报表与应用 | 页面访问、嵌入、业务流程集成 | 目标用户、分析用途和负责人 |
| 标准与规则 | 浏览、引用、绑定和执行 | 适用范围、版本、责任和变更说明 |

统一门户可以让用户搜索一次就看到所有相关成果，但申请流程、授权粒度和交付方式必须与对象类型匹配。

## 十、资产颗粒度应该如何确定

资产颗粒度不能简单照搬数据库和文件系统的物理结构。

### 1. 一项资产可以包含多个物理数据项

“工程项目履约主题数据集”可能由项目、合同、进度、付款、变更和验收等多张表组成。用户关注的是完整业务主题，不一定需要逐张申请中间表。

### 2. 一个数据项可以支撑多个资产或产品

统一项目主数据既可以支撑履约分析，也可以支撑资金监管和风险预警。物理上只有一份数据，不代表业务上只有一种使用方式。

### 3. 字段通常不是独立资产

字段需要元数据、标准和权限管理，但默认不应把每个字段都作为一项资产。只有某个字段、指标或码值集能够被独立发布、复用和负责时，才有必要提升为独立管理对象。

### 4. 资产身份应比存储位置稳定

数据从来源库迁移到数据仓库，或者文件从一个版本更新到下一个版本，不应自动变成新的业务资产。资产需要稳定标识，并记录它与物理数据项、版本和服务之间的关系。

### 5. 以业务含义和责任边界为主要依据

合适的资产颗粒度通常能够同时回答：它描述什么业务对象或主题，由谁负责，服务哪些用户，怎样更新和授权。如果这些问题无法在同一边界内回答，资产可能拆得过细或合得过粗。

## 十一、案例：工程项目全过程资产目录

某企业围绕工程项目建立统一资产门户，相关数据来自项目管理、合同、采购、财务、质量、安全、GIS、BIM 和现场采集系统。

门户中可以纳入以下成果：

| 类型 | 示例 |
| --- | --- |
| 数据内容 | 项目与合同主数据、计划进度、成本付款、项目空间范围、BIM 模型、现场照片和设备事件 |
| 指标与派生结果 | 项目完成率、成本偏差、进度滞后标签、项目画像、延期概率和资金风险评分 |
| 数据服务 | 项目状态查询服务、项目空间服务、风险事件订阅服务 |
| 模型与算法 | 项目实体模型、进度维度模型、延期预测模型、空间叠加算子和正式工作流 |
| 数据产品与应用 | 项目经营分析报表、全过程驾驶舱和工程专题地图 |
| 治理知识 | 项目与合同数据标准、通用完整性规则、项目数据契约和工程领域本体 |

用户搜索“项目进度”时，可以同时找到进度主题数据集、完成率指标、滞后标签、项目状态查询服务、延期预测模型和经营分析报表。门户提供统一入口，但每类对象展示的信息和使用方式不同。

这些成果还要建立关系。例如，经营分析报表引用哪些指标，指标来自哪些主题数据集，主题数据经过哪些工作流加工，项目状态服务采用哪个数据版本，都应当能够追溯。

资产模块负责目录、发布、申请、评价和关联；数据、服务、模型、标准和质量等权威内容仍由所属模块维护。这样既能让治理成果被发现和复用，也能避免重复建设和责任混乱。

## 十二、常见误区

### 误区一：资产管理就是数据表和文件管理

数据内容是基础，但指标、服务、模型、产品和可复用治理知识同样是数据治理形成的重要成果。

### 误区二：进入资产门户的对象都必须称为数据资产

统一入口不代表统一类型。数据、服务、模型和应用可以共同进入资产管理体系，但应分别命名和管理。

### 误区三：每张表、每个文件和每个字段都要单独登记

资产颗粒度应以业务含义、使用方式和责任边界为依据，而不是机械复制物理结构。

### 误区四：API 就是数据服务

API 只是接口形式；数据服务还包括来源、用途、契约、版本、权限和服务责任，也可以通过事件订阅或文件交付。

### 误区五：平台 OpenAPI 都属于数据服务

创建任务、管理用户和触发流程的接口属于平台功能，不是向业务应用交付数据的数据服务。

### 误区六：模型、模型结果和模型服务可以合并管理

模型属于模型与算法资产，特征和预测结果属于数据，在线推理能力属于服务，三者应相互关联但分类管理。

### 误区七：每条质量结果和血缘关系都是独立资产

规则绑定、质量结果和血缘通常是资产的附属治理信息；可独立复用的规则模板才适合进入治理知识库。

### 误区八：纳入资产管理就必须复制到资产模块

资产模块负责目录和运营关系，各类成果的权威事实仍应由所属模块维护。

### 误区九：资产数量越多，资产管理成效越好

真正重要的是资产能否被使用和复用，能否稳定服务业务，而不是目录条目数量。

## 十三、实践检查清单

1. 资产管理是否覆盖数据、指标标签、数据服务、模型算法和产品应用？
2. 可复用的数据标准、规则和契约是否能够被统一发现和引用？
3. 是否按照业务含义和责任边界确定资产颗粒度，而不是机械复制物理结构？
4. 指标定义、计算结果和服务方式是否分别管理并建立关联？
5. 是否以数据服务为管理单元，并将 API 作为服务版本下的交付接口？
6. 是否区分平台功能 OpenAPI 与面向业务的数据服务 API？
7. 质量状态、血缘、权限和责任是否作为资产附属信息展示？
8. 资产门户是否保留各专业模块的权威事实来源，避免重复维护？

## 小结

资产管理应该覆盖数据治理形成的各类可复用成果，而不能只管理数据库表和文件。

数据内容、指标标签与派生结果、数据服务、模型算法、数据产品与应用，可以通过统一资产门户被发现、申请、授权、共享和评价；数据标准、规则和契约等治理知识也应进入专业知识库，并与相关资产建立关联。元数据、质量状态、血缘、权限和责任则通常作为资产的附属信息提供可信依据。

把这些成果纳入同一套资产管理体系，不意味着把它们全部改称“数据资产”，也不意味着复制到同一个模块。真正重要的是统一入口、分类管理、关系清楚、责任明确和持续运营，从而让已经形成的治理成果能够被业务真正使用。
