# 043 企业数据目录如何统一各类资源目录，并支撑数据资产目录？

## 一句话回答

> 各类专业资源目录提供数据、模型、指标和服务等对象的专业事实；企业数据目录通过统一对象身份、业务语义、关系、搜索和权限视图，把这些专业目录关联起来；数据资产目录则从企业数据目录中筛选出经过治理、审核和发布的可运营成果。

这里有一个容易被忽略的区别：专业资源目录和资产目录是不同的内容视图，企业数据目录则是一项跨目录的统一关联和发现能力。它不是把几棵目录树简单拼在一起，也不是与资源目录、资产目录并列的第三棵树。

## 一、为什么“目录”容易被混为一谈

在数据领域，“目录”至少有四种常见含义：

| 含义 | 典型例子 | 主要解决的问题 |
| --- | --- | --- |
| 存储命名空间 | 数据库、`schema`、表、文件夹、对象前缀、消息主题 | 数据存在哪里，如何定位和访问 |
| 分类体系 | 业务域、主题域、业务对象、业务场景 | 按什么逻辑组织和归类 |
| 资源清单 | 技术资源目录、模型目录、指标目录、服务目录 | 组织有哪些资源，如何搜索和理解 |
| 发布清单 | 数据资产目录、数据产品目录、数据市场 | 哪些成果可以申请、授权和使用 |

因此，目录不只是一个分层文件夹，也不只是某个系统中的一张表。现代企业数据目录通常同时包含：

- 一套或多套分类体系；
- 关键词、标签和分面筛选；
- 业务术语和语义关系；
- 来源、组成、派生和血缘关系；
- 责任、质量、权限和生命周期状态；
- 面向不同角色的搜索和导航视图。

同一份数据可以归属于一个主要业务主题，同时带有多个标签、安全等级、责任部门和适用场景。如果强行把这些维度都塞进一棵目录树，分类通常会失真。

## 二、数据源原生目录解决“数据在哪里”

数据库中的数据库名、模式名、表名和字段名，文件系统中的目录和文件名，对象存储中的桶和对象前缀，消息系统中的主题，都是数据源维护的原生命名空间。

它们主要服务于：

- 存储引擎的组织、隔离和权限控制；
- 数据管理员和应用程序的定位与访问；
- 物理容量、生命周期和连接管理；
- 计算引擎对表、文件或消息的识别。

原生目录是数据治理需要采集的事实来源，但不能替代企业数据目录。一个表名可以说明技术对象的名称，却不能说明：

- 这张表描述哪个业务对象；
- 字段的业务含义和统计口径是什么；
- 哪个部门负责解释和维护；
- 数据是否可信、是否及时；
- 哪些指标、报表和服务依赖它；
- 哪些人员可以因为什么目的使用它。

因此，`schema`或文件目录回答的是“数据在哪里”，而不是“数据对业务意味着什么”。

## 三、专业资源目录分别管理什么

企业中通常会存在多个专业资源目录。它们不一定都是独立的软件，但分别拥有不同对象的专业组织方式。

| 专业目录 | 主要对象 | 主要使用者 | 主要用途 |
| --- | --- | --- | --- |
| 技术资源目录 | 表、字段、文件、消息主题、接口和存储位置 | 数据工程师、数据管理员 | 盘点、定位、预览和变更识别 |
| 模型组织目录 | ODS、DWD、DWS、ADS、主题模型、事实表和维度表 | 数据工程师、建模人员 | 数据开发、分层组织和模型复用 |
| 指标与标签目录 | 指标、标签、业务口径、计算逻辑和适用范围 | 分析人员、业务人员 | 统一分析口径和自助取数 |
| 数据服务目录 | 查询服务、API、订阅、交换服务和服务版本 | 应用开发者、业务用户 | 发现和调用数据服务 |
| 算法与模型目录 | 算法、模型、特征、参数、版本和适用场景 | 算法工程师、分析人员 | 模型复用、评估和发布 |
| 主数据和参考数据目录 | 主数据实体、码表、参考数据和映射关系 | 数据治理人员、业务部门 | 统一身份、编码和基础口径 |

这些目录的专业事实应由各自的 owner 负责。例如，指标目录最清楚指标定义和计算逻辑，模型目录最清楚模型粒度和层次，技术资源目录最清楚表、字段和物理位置。

但专业目录之间必须能够相互关联，否则企业仍然无法回答：

> 这个指标来自哪些数据？这张数据表属于哪个业务实体？这个服务暴露了哪些指标？某个工作流产生了哪些数据？

## 四、企业数据目录不是另一棵目录树

业界所说的企业数据目录（Enterprise Data Catalog），重点不在于再建立一棵新的分类树，而在于把分散在不同系统中的元数据和治理信息组织成一个跨企业的发现层。

可以这样理解：

```text
专业目录事实
    + 跨目录统一对象身份
    + 业务语义和分类
    + 数据、模型、指标、服务之间的关系
    + 搜索、筛选和权限视图
    = 企业数据目录能力
```

企业数据目录通常关联：

- 技术位置、结构、格式和连接方式；
- 业务术语、主题域、业务实体和指标含义；
- 数据标准、数据元、码值和质量结果；
- 责任部门、业务负责人和技术维护者；
- 来源、加工过程、上下游血缘和影响范围；
- 安全等级、敏感信息、权限和授权条件；
- 更新时间、运行状态、使用频率和服务承诺；
- 数据项、模型、指标、标签、服务和应用之间的关系。

所以，企业数据目录更像是一个统一的元数据关联层和搜索入口，而不是所有专业资源的第二份副本。

## 五、企业数据目录应该如何组织资源

企业数据目录不应只按来源系统组织，也不应把所有内容塞进一棵树。比较实用的方式是“一个主分类轴、多个筛选维度、一个关系图”。

### 1. 主分类轴：业务语义

主导航可以采用：

```text
业务域
└── 主题域
    └── 业务对象或业务过程
        └── 业务场景
```

例如：

```text
交通
└── 道路运行
    └── 道路路段
        └── 拥堵分析
```

主分类轴应保持同一分类维度。业务域、用地类型、数据格式和安全等级不能随意混在同一级目录中。

### 2. 标签与分面

以下属性更适合作为标签或筛选条件：

- 数据集、数据项、实体、指标、标签、服务、模型和应用等类型；
- 来源模块、来源系统和技术路径；
- ODS、DWD、DWS、ADS等模型层次；
- 责任部门、数据负责人和服务负责人；
- 更新频率、鲜活度、质量状态和认证状态；
- 安全等级、敏感类型、授权范围和可见范围；
- 区域、时间范围、空间范围和适用场景。

同一个对象可以只有一个主要业务归属，同时拥有多个标签。这样既能保持目录结构稳定，也能支持从不同角度发现同一对象。

### 3. 关系图

目录树无法完整表达对象之间的派生和依赖关系，还需要维护关系图：

```text
业务实体 --推导出--> 逻辑模型
逻辑模型 --物化为--> 数据项
数据项 --支撑--> 指标
指标 --被暴露为--> 数据服务
工作流 --产生--> 数据项
资产 --组合--> 数据项、指标、服务和模型
```

关系还应记录来源、版本、采集时间和可信程度，才能支持异常排查、影响分析和变更通知。

## 六、企业数据目录和资源目录体系是什么关系

二者不是并列的两套目录，也不是严格的前后阶段。

可以这样区分：

- **资源目录体系**：企业有哪些专业资源，以及这些资源分别怎样组织；
- **企业数据目录**：怎样把这些资源统一关联、索引、搜索和导航；
- **资源目录视图**：在企业数据目录中查看所有已发现、已确认或正在治理的资源；
- **数据资产目录**：在企业数据目录中查看已经经过筛选、治理、审核和发布的成果。

因此，企业数据目录可以同时提供资源视图和资产视图。它覆盖资源的整个生命周期，而不是只在资源转化为资产之后才出现。

## 七、资源目录和资产目录有什么区别

| 比较维度 | 资源目录体系 | 数据资产目录 |
| --- | --- | --- |
| 覆盖范围 | 尽可能完整地盘点可发现资源 | 经过筛选并进入运营范围的成果 |
| 主要对象 | 表、文件、模型、指标、服务、算法等 | 数据集、指标、标签、服务、模型和数据产品等 |
| 主要用户 | 技术人员、治理人员、分析人员 | 业务用户、资产管理人员、服务使用者 |
| 组织方式 | 来源、模型层、主题、技术类型和专业分类 | 业务域、业务主题、场景、产品和服务类型 |
| 状态要求 | 可以是发现、待确认、开发中或受限状态 | 通常需要经过审核、发布和授权管理 |
| 描述重点 | 结构、位置、来源、加工和依赖 | 价值、用途、质量承诺、责任和使用方式 |
| 可见范围 | 可以只对内部技术和治理人员开放 | 按发布范围对目标用户开放 |
| 运营要求 | 重点是盘点、理解、开发和治理 | 还要评价使用效果、成本和用户反馈 |

资产目录不是资源目录的副本。资产上架后，底层技术信息、血缘和运行状态仍由相应的专业目录和元数据体系维护；资产目录增加的是业务发布、授权和运营信息。

## 八、资源如何进入数据资产目录

资源进入资产目录，不是把数据从一个目录搬到另一个目录，而是资源增加了明确的资产身份和运营条件：

```text
专业资源目录
    ↓ 企业数据目录统一关联
已发现或已确认资源
    ↓ 业务确认、价值筛选和必要治理
资产候选
    ↓ 确定资产边界、责任、质量、权限和使用方式
数据资产目录
    ↓ 面向目标用户发布
资产门户或数据市场
```

一项资源要进入资产目录，通常需要明确：

1. 业务含义、适用范围和使用场景；
2. 责任人和维护部门；
3. 来源、加工过程和版本；
4. 质量状态、更新频率和已知限制；
5. 权限、敏感性和申请条件；
6. 查询、下载、订阅、服务或应用入口；
7. 问题反馈、变更通知和持续维护机制。

资产可以由多个资源组合而成。例如，一个经营分析数据产品可能同时关联主题数据集、统一指标、标签服务和算法模型。

数据本身仍然可以留在来源数据库、数据仓库、对象存储或专业引擎中。资产目录维护的是资产说明、组成关系、发布版本、权限和使用入口，而不是复制底层数据。

## 九、应该建设一套目录，还是多套目录

这不是“所有内容集中到一个系统”与“每个部门各建一套系统”之间的二选一。

比较稳妥的原则是：

> **逻辑统一、专业分工、事实关联、视图分离。**

具体来说：

- 技术资源、模型、指标、服务和算法模型可以由各自专业系统维护；
- 企业数据目录统一关联这些对象的身份、语义、责任、质量和关系；
- 资产管理后台负责资产候选、编目、发布、授权、评价和下架；
- 资产门户负责向消费者展示当前允许发现和使用的资产；
- 各系统之间应建立可追溯的对象引用和关系，而不是交换互不更新的静态目录文件。

物理上可以有多个专业系统，逻辑上不能有多套互不相认的事实源。否则同一个指标可能在指标系统、资产系统和报表系统中各有一个版本，却无法判断哪个才是当前有效口径。

## 十、空间数据不需要另起一套治理主线

空间数据在技术侧应与其他数据一起纳入资源目录和企业数据目录。矢量、栅格、影像、三维模型和空间服务都可以统一管理：

- 来源、位置、结构和格式；
- 业务含义、责任和权限；
- 质量、版本、更新和血缘；
- 查询、下载、订阅和服务入口。

空间数据只需要增加类型专属的元数据和质量规则，例如：

- 坐标参考系和坐标精度；
- 几何类型和空间范围；
- 比例尺、分辨率和覆盖情况；
- 拓扑关系、几何有效性和接边情况；
- 时间有效性和空间版本。

这些是统一治理框架下的专业扩展，不代表空间数据必须拥有一套完全独立的技术目录和治理主线。

在业务侧，可以建立自然资源、交通、规划等专题分类；但这属于业务主题视图，不是另起一套空间数据治理体系。

## 十一、案例：城市交通运行数据如何进入企业数据目录

某城市希望形成交通运行分析和拥堵治理能力。数据分别来自公交、地铁、道路感知、交通事件和气象系统。

### 1. 专业目录中分别有什么

技术资源目录记录各系统中的表、文件、消息主题和接口；模型目录记录ODS、DWD和汇总模型；指标目录记录道路拥堵指数、公共交通准点率等定义；服务目录记录实时查询和交通事件订阅服务。

### 2. 企业数据目录如何关联

企业数据目录将这些对象关联起来：

- 道路运行实体与道路模型关联；
- 道路模型与实际数据项关联；
- 拥堵指数与事实模型和计算逻辑关联；
- 实时查询服务与指标或数据项关联；
- 交通事件工作流与产生的数据结果关联。

数据工程师可以按模型层查看，业务人员可以按交通主题搜索，治理人员可以按责任和质量筛选，分析人员可以沿关系查看指标来源。

### 3. 哪些内容进入资产目录

经过业务确认和必要治理后，组织可以发布：

- 城市交通运行主题数据集；
- 道路拥堵指数和公共交通准点率指标；
- 交通事件实时订阅服务；
- 面向交通分析的历史运行数据产品。

一次性导出的临时文件、调试缓存和没有明确使用场景的中间表，仍然可以在资源侧进行必要管理，但不必直接作为业务资产上架。

这个案例说明：企业数据目录负责把专业资源联系起来，资产目录负责把其中值得持续提供的成果发布出来。

## 十二、常见误区

### 误区一：把专业目录拼在一起就形成了企业数据目录

如果没有统一身份、业务语义、关系、搜索和权限过滤，只是多个目录的并列展示，仍然无法跨系统发现和理解资源。

### 误区二：企业数据目录要复制所有专业系统的数据

企业数据目录应保存必要的可检索投影和关联关系，详细事实仍由专业模块维护。复制完整事实会产生版本冲突和责任不清。

### 误区三：企业数据目录就是一棵更大的业务树

业务树只适合提供主要导航。标签、分面、语义关系和血缘关系同样重要，否则同一对象跨场景使用时会被迫重复登记。

### 误区四：所有资源都应该进入资产目录

资源目录可以覆盖发现、开发和治理中的对象，资产目录则需要经过价值筛选。临时表、中间结果、重复数据和低复用资源不一定适合面向业务发布。

### 误区五：资产上架就是复制一份数据

资产上架主要是增加业务身份、治理状态、权限和使用入口，不要求搬运或复制底层数据。

### 误区六：ODS、DWD和资产目录是同一种分类

ODS、DWD等主要描述数据加工阶段和模型组织；资产目录描述面向用户的业务成果和使用方式。二者可以关联，但不能互相替代。

### 误区七：空间数据必须独立于普通数据治理

空间数据应纳入统一治理体系，只在元数据、质量和专业服务方面增加必要扩展。

## 十三、实践检查清单

1. 是否区分了原生存储目录、专业资源目录、企业数据目录和资产目录？
2. 是否明确企业数据目录是统一关联和发现能力，而不是另一份专业事实库？
3. 是否把数据项、模型、指标、服务和开发成果通过稳定引用关联起来？
4. 是否采用业务主分类、标签分面和关系图，而不是只建设一棵目录树？
5. 是否明确哪些对象只是资源，哪些对象已经完成资产化并正式发布？
6. 资产目录是否复用了底层资源和元数据事实，避免维护第二套互相矛盾的技术信息？
7. 目录可见性是否与数据内容访问权限区分开，并经过 owner 授权判断？
8. 空间数据是否纳入统一目录体系，并补充必要的空间元数据和质量规则？

## 结语

企业数据目录不是专业资源目录的简单汇总，也不是数据资产目录的另一个名称。

专业目录分别维护技术资源、模型、指标、服务和算法等事实；企业数据目录将这些对象统一关联，提供业务语义、关系、搜索和权限视图；数据资产目录再从中筛选经过治理和发布的成果，面向业务用户提供稳定的使用方式。

目录建设的最终目的，不是登记更多对象，而是让数据更容易被理解、组合和使用，从而真正为业务增值。
