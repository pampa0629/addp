# 042 数据资源如何从盘点、治理、编目到发布，形成可运营的数据资产？

## 一句话回答

> 数据被扫描和登记以后，只是被发现的数据资源；只有经过业务价值与风险筛选、责任确认、必要治理、资产边界设计、编目和发布，并具备稳定使用方式，才成为可运营的数据资产。不是所有数据资源都需要成为资产，也不是完成编目上架就自然产生了业务价值。

从数据资源到可运营资产，不是一次格式转换，也不是把数据搬进数据仓库，而是组织选择哪些数据值得持续投入治理和运营，并为其建立业务含义、质量状态、责任、权限、版本和使用机制的过程。

## 一、为什么“发现了数据”不等于“形成了资产”

组织接入数据库、文件系统、对象存储和消息系统后，可以通过元数据扫描发现大量表、字段、文件、目录、消息主题和服务。

但被发现的数据可能存在以下情况：

- 不知道描述什么业务；
- 只有创建者知道怎样使用；
- 与其他系统中的数据重复；
- 来源、责任和授权范围不清；
- 质量和更新时间无法说明；
- 只是某次计算产生的临时表或中间文件；
- 没有明确用户和复用场景；
- 维护成本高于预期价值。

这些数据当然属于组织需要识别和管理的数据资源，但不能仅凭“扫描到了”或者“登记到目录中”，就宣布已经形成可运营的数据资产。

可以用下面的关系理解：

```text
被发现的数据资源
    + 明确业务价值
    + 责任和治理机制
    + 可控使用边界
    + 稳定交付方式
    = 可运营的数据资产
```

这里的加号不是固定审批清单，而是说明资产需要同时具备数据内容、业务语义和持续运营条件。

## 二、从数据资源到可运营资产要经过哪些环节

比较完整的过程可以概括为：

```mermaid
flowchart LR
    A["元数据扫描"] --> B["数据资源盘点"]
    B --> C["价值与风险筛选"]
    C --> D["标准、质量、责任和权限治理"]
    D --> E["确定资产边界与颗粒度"]
    E --> F["资产编目"]
    F --> G["审核与发布"]
    G --> H["提供稳定使用方式"]
```

每个环节解决的问题不同：

| 环节 | 核心问题 | 主要产出 |
| --- | --- | --- |
| 元数据扫描 | 技术上发现了什么 | 数据源、数据项、结构、格式和位置 |
| 数据资源盘点 | 组织拥有什么、谁负责、怎样产生 | 资源清单、来源、责任和现状 |
| 价值与风险筛选 | 哪些资源值得持续运营 | 资产候选、优先级和治理范围 |
| 必要治理 | 是否可信、合规并适合目标用途 | 标准、质量、责任、权限、血缘和更新机制 |
| 确定资产边界 | 应把什么作为一项资产 | 稳定资产身份、内容范围和组成关系 |
| 资产编目 | 怎样分类、描述和建立关系 | 资产卡片、分类、标签和关联信息 |
| 审核与发布 | 是否进入正式运营范围 | 发布版本、可见范围和使用条件 |
| 提供使用方式 | 用户怎样获得和使用 | 查询、下载、服务、订阅或应用入口 |

这些环节可以迭代进行，不要求建设一个覆盖全组织的线性“大工程”。实践中更适合从重点业务场景和少量高价值资源开始，逐步扩大范围。

## 三、元数据扫描解决技术发现

元数据扫描主要从数据库系统目录、对象存储、文件格式、消息系统和数据服务描述中，自动识别：

- 数据源和连接位置；
- 数据库、模式、表、视图和字段；
- 文件、对象、格式、大小和更新时间；
- 消息主题、事件结构和协议；
- 空间参考、空间范围和几何类型；
- 数据项的基础结构和部分统计特征。

扫描的优势是覆盖面广、自动化程度高，但它只能说明技术上存在什么，不能自动确认：

- 这项数据对业务有什么价值；
- 哪个部门承担业务责任；
- 哪种口径才是权威口径；
- 是否允许跨部门共享；
- 应当作为正式资产还是临时结果；
- 用户需要通过什么方式使用。

因此，元数据扫描是资源发现的起点，不是资产形成的终点。扫描结果更适合作为资源盘点和资产候选识别的输入。

## 四、数据资源盘点解决业务确认

资源盘点不是把扫描结果导出成一张表，而是让技术发现与业务事实相互核对。

盘点通常需要确认：

- 数据描述什么业务对象、事件或主题；
- 来自哪个系统、流程或外部单位；
- 来源是否合法，是否存在用途和授权限制；
- 由哪个部门产生，谁负责解释和维护；
- 怎样更新，业务上需要多高的鲜活度；
- 当前有哪些人员、报表、模型和应用在使用；
- 是否与其他数据重复、冲突或存在主从关系；
- 是否包含敏感、个人或受限数据；
- 当前质量是否满足已有用途。

扫描结果和盘点结果不能分别维护成两套互不关联的台账。较合理的做法，是让业务确认直接关联到稳定的数据项身份；底层位置和结构变化时，业务说明和责任关系仍能够被追踪。

盘点以后，组织得到的是更可靠的数据资源清单，其中既包括值得进一步治理和运营的候选资产，也包括临时数据、归档数据、重复资源和受限资源。

## 五、不是所有数据资源都需要成为资产

资产管理需要持续投入成本，包括质量维护、责任协调、权限管理、版本变更、服务保障和用户支持。如果把所有数据表、字段和文件都当作资产运营，目录会迅速膨胀，真正重要的数据反而难以发现。

选择资产候选时，可以重点判断：

1. 是否有明确的业务问题、用户或使用场景；
2. 是否具有跨人员、跨系统或跨部门复用价值；
3. 是否会持续产生、更新或被使用；
4. 是否能够明确来源、责任和合法使用边界；
5. 是否值得投入治理和服务成本；
6. 是否存在质量、安全或业务风险，需要纳入正式管理；
7. 是否已有同类资产，能够复用或合并；
8. 是否能够通过稳定方式提供给目标用户。

这并不意味着低价值或暂时无人使用的数据可以完全不管。它们仍需要保留必要的资源元数据、权限、保留期限和清理规则，只是不一定进入重点资产运营范围。

资产候选的优先级也不是永久不变的。新业务出现、法规调整或数据用途扩大以后，一项普通资源可能需要提升为重点资产；长期无人使用的资产也可能被降级或退出。

## 六、治理程度要与用途和风险匹配

数据成为可运营资产以前，需要完成与目标用途相匹配的治理，但不应要求所有候选资产达到同一套最高标准。

### 1. 业务语义和标准

明确业务名称、术语、实体、字段含义、码值、单位、指标口径和适用范围，避免用户只能看到技术表名和字段名。

### 2. 数据质量和鲜活度

说明当前质量状态、已知问题、更新时间和适用限制，为重点场景建立必要的质量检查和异常处理机制。

### 3. 责任机制

明确业务责任人、数据维护者和服务责任人。一个名称后面没有责任人的资产，出现问题时很难持续运营。

### 4. 安全和权限

完成必要的分级分类、敏感识别、用途限制、授权规则和审计要求。可发现不等于所有人都可以直接访问。

### 5. 来源、血缘和版本

记录资产来自哪里、经过什么加工、使用什么标准和规则、当前版本是什么，以及变化会影响哪些下游。

例如，公开统计数据集和包含个人信息的客户明细数据，治理深度和发布条件显然不同；供内部临时分析的数据与用于经营考核的正式指标，也不能采用完全相同的质量和责任要求。

治理的目标不是让数据达到抽象意义上的“完美”，而是让使用者知道它是否适合当前用途、存在哪些限制，并有人负责持续维护。

## 七、资产边界和颗粒度怎样确定

数据资产不能机械照搬数据库和文件系统的物理结构。

### 1. 一项资产可以由多个数据项组成

“设备运维主题数据资产”可能包含设备台账、运行观测、维修工单、故障记录和备件使用等多张表或数据集。

如果业务人员总是需要组合使用这些内容，并且它们具有统一责任和更新机制，将其组织成一个主题资产比逐张表上架更容易理解和使用。

### 2. 一个数据项可以支撑多个资产或产品

统一设备主数据可以同时支撑生产监控、维修管理、能耗分析和故障预测。底层数据保持一份，不代表只能有一种业务组织和使用方式。

### 3. 中间结果不一定需要独立发布

加工过程中的临时表、缓存、分区文件和运行产物需要技术管理、血缘和生命周期控制，但没有独立业务含义和复用场景时，不必都提升为资产目录中的独立条目。

### 4. 以业务含义、责任和使用方式为依据

合适的资产边界通常能够同时回答：描述什么、由谁负责、服务谁、怎样更新、如何授权和使用。如果这些问题无法在同一个边界内回答，资产可能拆得过细或合得过粗。

## 八、资产编目到底做什么

资产编目是将候选资产按照统一规则分类、描述并建立关系，使其可以被管理和发现。

一项资产的目录信息通常包括：

- 稳定标识、名称和版本；
- 所属业务域、主题和分类；
- 业务说明、适用场景和目标用户；
- 内容范围、组成数据项和颗粒度；
- 来源、血缘和加工过程；
- 质量状态、鲜活度和已知限制；
- 责任人和维护部门；
- 分级分类、权限和申请条件；
- 查询、下载、订阅、服务或应用入口；
- 变更记录、使用情况和评价信息。

编目不等于搬运数据。资产可以位于数据仓库，也可以仍然保存在来源系统、对象存储或专业数据引擎中，通过逻辑访问和数据服务参与业务场景。

编目也不等于治理完成。目录负责组织和呈现治理结果，如果业务含义、质量、责任和权限本身没有落实，再完整的资产卡片也只是包装。

第043问将进一步说明资源目录体系的组成，以及资源目录与数据资产目录的关系，本问只强调编目在资源转化过程中的作用。

## 九、发布意味着进入正式运营范围

候选资产完成编目后，可以进入审核和发布环节。发布不是简单地把一个开关从关闭改为开启，而是确认它已经具备面向目标用户持续提供的基本条件。

发布前通常需要确认：

1. 业务名称、含义、范围和用途清楚；
2. 资产身份、组成内容和版本稳定；
3. 来源合法，责任人和维护机制明确；
4. 质量与鲜活度能够满足声明的用途；
5. 敏感性、权限和申请条件已经确定；
6. 使用入口经过验证；
7. 上游变化、服务异常和版本调整有通知方式；
8. 已知限制能够向使用者清楚说明。

没有达到发布条件的候选资产仍可以留在资产管理后台继续治理，但不应为了增加“上架数量”而提前展示给所有用户。

发布以后，资产进入正式运营范围。资产门户如何展示已发布内容、用户如何申请和评价，以及后台如何处理审核和授权，将在第044问展开。

## 十、服务化是使用方式之一，不是必经步骤

数据资产最终需要有稳定使用方式，但并非都要封装成 API。

常见的交付方式包括：

| 资产类型 | 典型使用方式 |
| --- | --- |
| 数据表和主题数据集 | 查询、挂载、受控直连或交换 |
| 文件、影像和模型 | 下载、挂载、范围读取或专业软件访问 |
| 指标和标签 | 查询、圈选、订阅或分析页面 |
| 实时流数据 | 消息订阅和事件推送 |
| 数据服务 | API、SQL 端点、空间服务和文件交付 |
| 数据产品与应用 | 页面访问、交互分析和业务流程集成 |

服务化适合需要稳定契约、应用调用、权限控制和持续交付的场景，但也会带来版本、鉴权、限流、可用性和运维成本。

一份只供少数分析人员按月下载的正式统计文件，没有必要为了“资产化”强行开发 API；一个需要被多个业务系统实时调用的客户状态数据，则更适合发布为稳定数据服务。

因此，判断标准不是“有没有 API”，而是目标用户能否通过与场景匹配、稳定且可控的方式使用资产。

## 十一、发布时要为持续运营留下条件

第045问将专门讨论资产评价和持续运营，但在发布阶段就需要准备基本运营条件：

- 谁负责接收问题和用户反馈；
- 数据或服务按什么周期更新；
- 质量和可用性如何持续监测；
- 上游结构或口径变化怎样通知；
- 新版本怎样发布，旧版本如何退出；
- 使用情况和业务效果如何统计；
- 长期无人使用或成本过高时怎样调整。

如果这些问题完全没有答案，资产即使已经进入目录，也很容易在第一次变化或故障以后失去可信度。

## 十二、案例：设备运维主题资产如何形成

某制造企业希望利用设备数据优化维修计划、减少停机时间，并为故障预测提供数据基础。相关资源分散在设备管理、生产执行、物联网、维修工单和备件系统中。

### 1. 扫描发现资源

平台扫描出设备台账表、实时观测主题、维修工单、故障记录、备件领用数据和设备说明文件，并提取其结构、格式、位置和更新时间。

此时只是知道“有哪些技术对象”，还不能直接判断哪些内容应当发布给设备管理人员和数据分析人员。

### 2. 盘点确认业务事实

设备部门与数据团队共同确认：

- 哪个系统中的设备编号是当前主要身份；
- 各工厂和生产线由谁负责；
- 观测数据按照什么频率产生；
- 工单状态、故障类型和备件码值怎样解释；
- 哪些数据包含供应商限制或人员信息；
- 当前维修计划、停机分析和故障预测使用哪些数据。

### 3. 筛选和治理候选资产

企业选择设备台账、关键运行观测、维修工单和故障记录作为首批治理范围，暂不将一次性导出文件和设备调试缓存纳入资产运营。

治理工作包括：

- 统一设备身份并保留来源系统编码映射；
- 统一故障类型、工单状态、时间和计量单位；
- 检查设备缺失、重复观测、异常值和时间延迟；
- 明确设备部门、工厂和平台运维责任；
- 设置数据访问范围并记录加工血缘。

### 4. 组织并编目资产

企业没有把每张表都单独包装成一项业务资产，而是形成：

- 设备基础主数据；
- 设备运行观测主题数据集；
- 设备维修与故障主题数据集；
- 设备停机率和故障率指标；
- 面向故障预测的特征数据集。

每项资产都关联底层数据项、责任人、更新周期、质量状态、权限、血缘和适用场景。

### 5. 审核、发布和提供使用方式

设备主数据和主题数据集通过查询和受控下载提供，实时观测通过消息订阅提供，设备指标通过统一查询服务和运维分析应用提供。

设备原始观测并没有因为资产发布而被复制到资产管理模块。资产目录维护业务身份、发布状态和运营关系，底层数据和服务事实仍由各自负责的系统维护。

至此，分散的设备数据资源成为能够支持维修管理、停机分析和算法开发的可运营资产，而不仅是一份扫描清单。

## 十三、常见误区

### 误区一：扫描到的数据都是数据资产

扫描解决技术发现，不能自动确认业务价值、责任、质量和使用条件。

### 误区二：盘点就是导出一张资源清单

盘点还需要业务人员确认含义、来源、责任、更新、风险和实际用途。

### 误区三：所有数据资源都应该资产化

资产运营需要成本。临时、中间、重复和低复用数据可以保留必要管理，但不必全部进入正式资产目录。

### 误区四：把数据搬进数据仓库就形成了资产

物理汇聚解决存储和计算位置，不能替代业务语义、质量、责任、权限和运营机制。

### 误区五：完成编目就完成了治理

编目负责组织和展示治理信息，不能替代标准、质量、责任和安全治理本身。

### 误区六：上架就是向所有人开放数据

发布资产不等于取消权限控制。用户可以发现某项资产，但仍需按照分级、用途和授权规则获得访问权限。

### 误区七：数据资产必须发布 API

API 只是使用方式之一。下载、查询、挂载、订阅和应用访问都可能是合适的交付方式。

### 误区八：资产形成是一次性项目

业务、数据和使用需求持续变化。发布只代表进入运营阶段，不代表工作结束。

## 十四、实践检查清单

1. 是否将技术扫描、资源盘点、资产编目和正式发布区分为不同环节？
2. 是否由业务人员确认候选资产的含义、用途和责任？
3. 是否根据业务价值、复用需求、风险和维护成本选择资产候选？
4. 是否按目标用途确定标准、质量、鲜活度、安全和血缘要求？
5. 资产边界是否围绕业务主题、责任和使用方式确定，而不是机械复制物理表结构？
6. 编目信息是否关联权威数据项、服务和模型事实，避免建立第二套事实源？
7. 发布前是否验证业务说明、责任、质量、权限、版本和使用入口？
8. 是否根据资产类型提供查询、下载、订阅、服务或应用等合适方式？
9. 是否避免用扫描数量、编目数量和 API 数量代替资产价值评价？
10. 发布时是否已经明确更新、变更通知、问题反馈和版本退出机制？

## 小结

数据资源成为可运营的数据资产，需要经历从技术发现到业务确认、从价值筛选到必要治理、从确定资产边界到编目发布的过程。

元数据扫描回答“技术上发现了什么”，资源盘点回答“组织拥有什么、由谁负责”，治理回答“数据是否适合目标用途”，编目回答“如何组织和描述”，发布回答“是否进入正式运营范围”，交付方式回答“用户怎样使用”。这些环节互相关联，但不能互相替代。

真正的资产建设不是把尽可能多的数据放进目录，而是选择值得持续运营的数据，使其具备明确价值、可信状态、清楚责任和稳定使用方式，并最终进入业务场景。
