# 085 数据治理平台应该大而全吗，统一底座怎样与专业工具协同？

## 一句话回答

> 数据治理平台可以覆盖广泛的治理过程，但不应该重新实现所有专业能力。统一底座应负责跨领域共用的身份、对象、语义、规则、状态和审计，数据库、GIS、主数据、机器学习和隐私计算等专业工具则负责各自擅长的存储、计算和专业处理。真正的统一不是所有功能都由一套软件实现，而是各工具围绕同一治理对象和规则协同工作。

第084问说明，数据治理平台的核心能力不是模块数量，而是统一基础和治理闭环。本问继续回答：如果平台需要支撑目录、标准、质量、安全、开发、服务和运营，它是不是应该把所有功能都做进来？

答案不是简单的“要”或者“不要”。平台需要覆盖足够广的治理范围，也需要统一跨领域的共同基础；但如果它重新开发数据库内核、专业GIS、机器学习训练和各种行业算法，往往会变得庞大、迟缓，而且每一项专业能力都不够深入。

合理的方向是统一治理、专业执行、开放协同。

## 一、“大而全”其实包含哪些不同问题

“大而全”经常把四个问题混在一起：

1. **治理范围是否广泛**：是否覆盖目录、标准、质量、安全、开发、服务和运营；
2. **共同基础是否统一**：是否统一身份、对象、规则、状态和审计；
3. **专业能力是否全部内置**：是否自己实现数据库、GIS、机器学习等能力；
4. **技术部署是否必须一体化**：是否所有功能都在同一个程序和版本中发布。

这四个问题应分别判断：

- 治理范围可以比较广；
- 共同基础应尽量统一；
- 专业能力不必全部内置；
- 技术实现不必是不可拆分的单体。

所以，问题不在于平台功能“多不多”，而在于哪些能力必须统一，哪些能力应由专业工具承担，以及二者是否真正形成闭环。

## 二、统一底座应该负责什么

统一底座应优先管理跨领域共同使用的治理信息和控制能力。

### 1. 统一身份和组织边界

包括租户、部门、项目组、用户、角色、应用身份以及数据责任主体。

专业工具可以执行自身权限控制，但身份来源、组织范围和授权依据需要与底座衔接，不能每个工具维护一套相互矛盾的用户和部门。

### 2. 统一数据对象和标识

数据库表、文件、指标、模型、服务、地图和数据产品应具有稳定、可关联的标识。

专业工具可以提供不同视图，但不能把同一对象复制成互不关联的多份记录。

### 3. 统一目录、语义和责任

底座应统一管理或者关联：

- 数据名称和业务含义；
- 标准和指标口径；
- 分类分级；
- 数据来源和责任人；
- 版本和生命周期；
- 适用场景和使用条件。

### 4. 统一规则和策略

包括质量规则、安全策略、授权范围、发布条件和生命周期要求。

底座负责表达和传递规则，专业工具负责在实际执行环境中落实可以执行的部分，并把结果反馈回来。

### 5. 统一任务关系和状态入口

底座需要知道：

- 什么任务处理了什么对象；
- 由哪个工具或者引擎执行；
- 与哪些任务存在依赖；
- 当前处于等待、运行、成功还是失败状态；
- 产生了什么结果和血缘。

底座不一定替代专业工具内部的调度器，但应建立统一任务关系和可观察状态，避免多套任务互不知情。

### 6. 统一审计和运营视图

专业工具产生执行日志，底座关联用户、应用、数据对象、授权、任务和结果，形成跨工具的审计及运营视图。

## 三、哪些能力适合由数据库和计算引擎承担

数据库和数据仓库擅长：

- 数据存储；
- 事务和并发；
- SQL执行；
- 索引及查询优化；
- 备份和恢复；
- 数据库自身的安全控制。

汇聚和计算引擎擅长：

- 高吞吐数据传输；
- 批处理和流处理；
- 分布式计算；
- 计算资源调度；
- 算法、脚本和算子执行。

治理平台不应重新实现数据库和计算引擎内核，而应：

- 识别其中的数据对象；
- 管理标准、语义、责任和策略；
- 提交经过授权的任务；
- 记录输入、输出、版本和血缘；
- 汇总运行状态和质量结果；
- 把产生的数据重新纳入目录和生命周期管理。

## 四、哪些能力适合由专业工具承担

### 1. GIS专业工具

GIS工具更适合负责：

- 专业空间数据格式；
- 空间索引和空间计算；
- 地图配图和制图；
- 矢量及栅格瓦片生产；
- GIS服务发布；
- 坐标转换和专业空间分析算法。

### 2. 主数据管理工具

主数据工具更适合负责：

- 多源记录匹配和合并；
- 黄金记录生成；
- 生存规则；
- 编码映射；
- 主数据分发。

### 3. 机器学习和专业算法平台

机器学习及算法平台更适合负责：

- 模型训练和推理；
- GPU等计算资源；
- 特征处理；
- 算法实验；
- 模型评估；
- 专业运行环境。

### 4. 隐私计算工具

隐私计算工具更适合执行多方安全计算、联邦学习、可信执行环境或者其他具体隐私保护计算。

统一底座不需要重写这些能力，但应把专业工具中的数据、模型、任务、结果、责任和使用状态纳入整体治理。

如果专业领域已经存在成熟工具，重新实现一套能力较弱的替代品，通常既增加成本，也使平台难以跟上专业技术演进。

## 五、怎样理解治理控制与专业执行

可以用下面的结构理解二者关系：

```text
统一治理底座
身份、对象、目录、语义、规则、责任、版本、审计
                    ↓
         标准接口、任务和策略
                    ↓
数据库  汇聚引擎  GIS  主数据  机器学习  隐私计算
                    ↓
       状态、元数据、血缘和结果反馈
                    ↑
              统一治理底座
```

统一底座主要负责定义、协调和观察，专业工具主要负责存储、计算和专业处理。

这种分工不是“底座只管表单、工具只管执行”。底座中的身份、对象和规则必须能够向下传递，专业工具的状态、元数据、血缘和结果也必须能够向上反馈，才能形成治理闭环。

## 六、每类事实应该由谁负责

“统一平台”不意味着所有事实都必须由平台自己产生和保存。

更合理的是按事实类型确定权威来源：

| 信息 | 更适合的权威来源 |
| --- | --- |
| 数据库中的物理表结构 | 数据库及其元数据采集结果 |
| 数据业务含义和责任人 | 数据治理底座 |
| GIS数据格式和空间参考 | GIS引擎或者数据本身 |
| 任务实时执行状态 | 实际执行任务的引擎 |
| 数据质量规则和整改责任 | 数据治理底座 |
| 模型训练过程和性能结果 | 机器学习平台 |
| 企业统一用户和应用身份 | 统一身份体系 |
| 跨工具血缘和审计关系 | 治理底座汇总关联 |

底座不应复制专业工具中的状态后长期不更新，专业工具也不应自行维护一套企业级业务术语、部门和数据责任体系。

所谓“单一事实来源”，应理解为每一类事实都有明确的权威来源，而不是一套软件拥有全部事实。

## 七、统一底座与专业工具需要交换什么

双方至少需要交换六类信息：

1. **身份和授权上下文**：谁发起，以什么应用身份，允许访问什么；
2. **资源标识**：处理的是哪项数据、服务、模型或者地图；
3. **能力声明**：工具支持什么数据类型、格式、操作和计算能力；
4. **任务与状态**：怎样提交、取消和查询任务，当前是否成功；
5. **元数据和血缘**：输入、输出、结构、版本和上下游关系；
6. **日志、结果与审计**：产生什么结果，发生什么异常，留下什么证据。

还需要约定接口版本、错误处理、安全凭证和工具停用后的处理方式。

如果平台只能打开工具页面，却不能交换这些信息，二者仍然没有形成真正的治理协同。

## 八、集成可以分成哪些层次

集成深度可以分为：

| 集成层次 | 实现效果 |
| --- | --- |
| 入口集成 | 在统一门户中提供链接、菜单或者内嵌页面 |
| 身份集成 | 统一登录，并传递用户、租户和组织范围 |
| 任务集成 | 底座可以提交任务、查询状态和取得结果 |
| 对象集成 | 双方使用可关联的数据、模型、服务和任务标识 |
| 治理集成 | 规则能够向工具传递，血缘、审计、质量和使用状态能够返回 |
| 闭环集成 | 工具执行结果能够触发整改、发布、授权和运营流程 |

入口集成并非没有价值，它可以改善使用体验；但如果只有入口统一，就不能宣称已经完成一体化治理。

真正协同至少要根据实际场景达到任务、对象或者治理层面的集成。

## 九、专业工具的界面是否都要重做

不需要。

如果专业工具已经具备成熟而复杂的操作界面，例如：

- GIS桌面制图；
- 机器学习实验管理；
- 数据库运维；
- 专业仿真建模；
- 高级商业智能分析；

统一底座重新实现一套简化界面，通常成本很高、能力较弱，也容易落后于专业工具自身演进。

可以采用：

- 统一入口和身份；
- 携带数据对象、项目和任务上下文跳转；
- 在底座中完成通用审批与治理；
- 在专业工具中完成专业操作；
- 把结果、状态和元数据返回底座。

通用、频繁并且跨工具的操作可以由统一底座提供；高度专业的交互则保留在专业工具中。需要处理本地文件或者专业桌面引擎时，还可以采用第068问介绍的桌面端模式。

## 十、数据是否必须搬到统一平台

不必为了统一治理而统一存储。

数据可以继续保存在：

- 业务数据库；
- 数据仓库和数据湖；
- 对象存储；
- GIS数据库和文件系统；
- 实时消息系统；
- 专业计算环境；
- 受控数据空间。

统一底座主要管理数据对象、位置、语义、规则、责任和使用关系，根据任务需要调用相应工具。

只有在业务、性能、安全和处理方式确实需要时，才进行数据汇聚或者复制。不能为了让平台“看起来统一”，无条件把全部数据搬到一处。

## 十一、统一抽象怎样避免抹平专业能力

如果统一接口只保留所有工具都具备的最少功能，复杂专业能力就无法发挥作用。

更合理的是：

```text
共同能力
身份、对象、任务、状态、日志、血缘
          +
扩展能力
空间计算、模型训练、隐私计算、专业算法
```

所有工具遵守共同接口，同时通过能力声明和扩展接口暴露专业能力。

例如：

- 普通数据库声明查询和写入能力；
- 空间数据库进一步声明空间索引和空间SQL能力；
- GIS引擎声明瓦片生产、坐标转换和空间分析能力；
- 机器学习平台声明训练、评估和推理能力；
- 隐私计算工具声明其支持的联合计算方式。

这样既能保持统一治理，也不会把所有工具压缩成最低共同能力。以后出现新的数据类型、格式、专业算法或者计算引擎，也能通过扩展机制接入。

## 十二、局部调度与统一编排怎样协同

不同专业工具可能都有自己的定时任务和调度能力，统一底座也可能提供跨工具编排。

正确关系是：

- 工具内部的局部步骤可以由工具自身调度；
- 跨工具、跨模块的依赖由统一编排协调；
- 同一个业务链路确定一个主要触发入口；
- 工具把任务状态、结果和异常反馈给统一底座；
- 统一底座建立跨工具任务关系和整体监控；
- 避免底座和工具分别重复触发同一任务。

这与第062问的结论一致：局部定时与跨任务编排可以共存，但不能形成互不知情的双重调度。

## 十三、怎样判断应该内置还是集成

适合由底座统一提供的能力，通常具有以下特点：

- 多个领域共同使用；
- 需要形成企业级权威规则；
- 必须贯穿多个工具；
- 与身份、对象、流程和审计紧密相关；
- 需要保持长期一致。

适合集成专业工具的能力，通常具有以下特点：

- 专业门槛高；
- 已经存在成熟工具；
- 算法和技术演进快；
- 强依赖特定软硬件；
- 只服务特定专业场景；
- 重新实现成本高而附加价值有限。

如果一项能力既有通用部分又有专业部分，可以由底座提供身份、对象、规则、入口和治理流程，专业工具完成实际执行。

工具数量并不是越少越好。一个边界清楚、接口稳定、能够形成闭环的专业工具，通常比平台中一项长期落后的内置功能更有价值。

## 十四、接入新工具前应该回答什么

接入一个新专业工具以前，应先明确：

1. 它提供什么独特能力，是否与已有实现重复；
2. 它管理哪些专业对象；
3. 哪些事实由它负责，哪些由底座负责；
4. 怎样识别数据和任务；
5. 怎样传递身份、权限和使用策略；
6. 怎样提交任务并获取状态；
7. 怎样返回元数据、血缘、日志和结果；
8. 失败、升级、停用和替换时怎样处理；
9. 用户需要使用统一界面还是专业界面；
10. 接入以后形成了什么治理闭环。

如果只是把工具链接放进菜单，没有明确对象、规则和状态关系，就不能算真正接入治理底座。

## 十五、以GIS工具协同为例

支持空间数据治理时，没有必要让统一底座重新实现完整GIS平台。

### 1. 统一底座负责

- 空间数据集、地图和GIS服务的统一标识；
- 数据目录、业务语义和责任人；
- 数据标准、质量和分类分级；
- 使用申请和服务授权；
- 任务、结果、血缘和审计；
- 地图、瓦片和GIS服务的数据产品登记。

### 2. GIS工具负责

- 空间数据读写；
- 坐标转换；
- 空间计算；
- 桌面配图；
- 矢量和栅格瓦片生产；
- GIS服务发布。

### 3. 二者协同

```text
底座选择受治理的空间数据
          ↓
把任务和授权上下文交给GIS工具
          ↓
GIS工具执行空间计算或瓦片生产
          ↓
返回状态、结果、元数据和血缘
          ↓
底座登记结果并进入质量、发布和授权流程
```

这样既保留GIS工具的专业能力，也使其产出进入统一治理体系。

## 十六、常见误区

### 误区一：统一平台就应该自己实现全部专业能力

统一的重点是对象、规则和协同，不是重写数据库、GIS和算法引擎。

### 误区二：集成专业工具就是在菜单中增加一个链接

真正协同还需要身份、对象、任务、状态、规则和审计能够贯通。

### 误区三：所有数据都必须搬到统一存储才能治理

底座可以治理分散数据，数据是否移动应由业务、性能和安全要求决定。

### 误区四：每个专业工具都可以维护自己的用户和数据目录

专业对象可以由工具管理，但企业级身份、语义和责任不能相互割裂。

### 误区五：平台复制一份工具状态就实现了统一监控

复制后不能及时更新的状态会造成误导，应明确运行事实的权威来源和同步机制。

### 误区六：统一接口只能保留所有工具共有的最低能力

共同接口之外还需要能力声明和扩展接口，保留专业工具的独特能力。

### 误区七：专业工具足够成熟，所以不需要纳入统一治理

专业能力成熟不代表数据责任、授权、血缘、版本和使用状态能够跨工具贯通。

### 误区八：工具数量越少，平台架构就越先进

架构质量取决于边界是否清楚、是否减少重复以及能否形成闭环，不取决于工具数量本身。

## 小结

数据治理平台的治理范围可以比较广，但不需要把全部专业能力都内置。统一底座应负责身份、数据对象、语义、规则、责任、状态、版本和审计，数据库、计算引擎、GIS、主数据、机器学习和隐私计算工具负责各自擅长的专业处理。

真正的一体化不是统一菜单，也不是把所有数据搬到一处。底座与专业工具需要交换身份和授权上下文、资源标识、能力声明、任务状态、元数据、血缘、结果和审计，并明确每一类事实的权威来源。

平台建设应在共同接口和专业扩展之间保持平衡：统一治理所需的共同语言和控制机制，同时允许成熟工具独立演进。这样才能避免既大而不强，又多而不通，在统一治理和专业能力之间形成可持续协同。
