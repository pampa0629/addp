# 056 为什么说 SQL 是数据工程师的第一语言？

## 一句话回答

> SQL之所以被称为数据工程师的第一语言，不是因为数据工程师只需要SQL，而是因为它普及程度高、适用范围广，能够直接表达数据筛选、关联、转换、聚合和指标计算等核心工作。关系数据库、数据仓库、湖仓平台以及 Spark、Flink 等分布式计算平台普遍支持SQL，因此熟练使用SQL也成为大多数数据工程师岗位的必备技能。

SQL语法并不难入门，真正困难的是理解数据代表什么、应该怎样关联、按照什么粒度计算，以及怎样把业务口径转化为可持续运行的数据生产过程。

## 一、“第一语言”是什么意思

这里所说的“第一语言”，不是要争论SQL是不是传统意义上的编程语言，也不意味着SQL能够解决所有数据问题，而是强调它在数据工程工作中的基础地位：

- 使用频率高，日常数据开发大量依赖SQL；
- 覆盖范围广，多种数据库和计算平台都支持SQL；
- 学习迁移成本相对较低，核心查询思想可以跨平台复用；
- 接近数据模型，能够直接操作表、字段、关系和统计粒度；
- 便于审阅，业务规则和计算逻辑可以被相对直观地检查。

数据工程师可能还需要掌握Python、Java、Scala、Shell或其他语言，但这些技能通常是在SQL基础上补充复杂算法、工程控制、系统集成和平台开发能力。对大多数以结构化数据和分析计算为主的岗位而言，SQL是很难绕开的基本功。

## 二、为什么SQL如此普及

SQL最初主要用于关系数据库，后来逐步成为跨越多种数据系统的通用数据处理语言。

今天，SQL可以出现在：

- 业务系统使用的关系数据库中；
- 面向分析的数据仓库中；
- 分布式查询和大数据计算平台中；
- 数据湖与湖仓平台中；
- 流式计算平台中；
- BI、自助分析和指标平台中；
- 数据开发、质量检查和数据服务工具中。

例如：

- **Spark SQL**可以在分布式环境中查询和处理大规模结构化、半结构化数据，并与Spark的数据处理能力结合；
- **Flink SQL**可以基于动态表等机制表达持续变化的数据和流式计算逻辑，用于实时清洗、关联、窗口统计和结果更新；
- 许多湖仓和分布式查询引擎也提供SQL入口，让使用者不必直接编写底层分布式计算程序。

这说明SQL已经不只是“查询数据库表的语言”，还是多种计算引擎共同采用的数据处理抽象。平台可以更换，执行方式可以从单机变为分布式、从批量变为流式，但筛选、关联、分组和聚合等核心表达仍然可以使用SQL。

## 三、普遍支持不等于完全兼容

SQL有通用标准，常被称为ANSI SQL或ISO SQL，但不同产品通常会在标准基础上形成自己的方言。

常见差异包括：

- 字符串、日期和时间函数；
- 数据类型及其转换规则；
- 分页、采样和递归查询语法；
- 数组、JSON和嵌套数据处理；
- 地理空间函数；
- 流式窗口、时间属性和状态处理；
- 用户自定义函数和扩展机制；
- 表创建、分区、存储格式和性能提示。

Spark SQL、Flink SQL和关系数据库虽然都支持SQL，但面对的数据、执行过程和结果更新方式并不完全相同。例如，传统数据库查询通常面对某一时刻的有限数据集，而Flink SQL可能描述一条持续运行的计算逻辑：新事件不断到来，结果也随之更新。

因此，“掌握SQL”包含两个层次：

1. 掌握选择、连接、分组、窗口、集合运算等通用思想；
2. 理解当前计算引擎的数据模型、执行语义、方言和性能特点。

不应因为一段SQL能在某个平台运行，就默认它可以原样迁移到另一个平台，也不能默认相同写法一定得到完全相同的业务结果。

## 四、为什么SQL适合数据开发

### 1. SQL是声明式语言

使用SQL时，开发人员主要说明“需要什么结果”，而不是逐步规定“计算机怎样完成每一个动作”。

例如：

```sql
SELECT
    region_id,
    product_id,
    SUM(net_sales_amount) AS net_sales_amount
FROM sales_order_detail
WHERE business_date >= :start_date
  AND business_date < :end_date
GROUP BY region_id, product_id;
```

这段SQL表达了筛选范围、分组维度和汇总指标。至于先扫描哪张表、使用哪种连接算法、是否使用索引、怎样在多个计算节点之间交换数据，通常由数据库或计算引擎的优化器和执行器决定。

这种声明式方式使数据工程师能够更多关注业务规则和结果结构，也使平台有机会根据数据规模、存储方式和计算资源优化执行计划。

### 2. SQL天然面向集合处理

数据工程面对的通常不是单条记录，而是一批订单、一段时间的交易、所有客户的标签或一个区域内的设备事件。SQL擅长以集合为单位进行过滤、关联、聚合和窗口计算，与数据仓库和分析场景十分契合。

### 3. SQL贴近数据模型

表、字段、主键、关联、事实、维度和粒度都能够直接反映在SQL中。开发人员可以通过SQL把数据模型落地为实际的数据集，也可以根据业务维度组织指标计算。

### 4. SQL便于复核和协作

相对于封装在应用程序深处的计算逻辑，SQL通常更容易被数据工程师、分析人员和数据库人员共同查看。配合清晰命名、分层模型和指标定义，可以更直接地判断数据来源、过滤条件和计算方式。

## 五、SQL在数据治理中用来做什么

SQL在数据治理中的用途远不止临时查询。

### 1. 数据汇聚与转换

读取不同来源的数据，完成字段映射、格式转换、去重、增量合并和目标表写入。ETL和ELT都可能大量使用SQL。

### 2. 数据标准化

统一日期格式、计量单位、枚举码值、空值表示和业务标识，并记录不能正常转换的数据。

### 3. 数据建模落地

构建实体明细、事实表、维度表、汇总表和服务数据集，使业务模型和数据模型转化为可以持续计算的数据结构。

### 4. 指标与标签计算

按照统一的统计对象、时间范围、过滤条件和聚合方式计算指标，并根据规则为客户、产品、区域或其他实体生成标签。

### 5. 数据质量检查

检查非空、唯一、值域、引用关系、跨表一致性和业务逻辑。例如，可以通过SQL识别没有对应客户的订单、金额不平衡的交易或异常变化的每日数据量。

### 6. 数据核对和问题排查

在指标异常或上下游结果不一致时，逐层核对数据量、关键字段、关联关系和汇总结果，帮助定位问题发生在哪个环节。

### 7. 数据服务准备

为BI、API、标签画像、算法模型和业务应用准备结构稳定、口径统一、性能合适的数据集。

SQL贯穿了数据从源系统进入分析体系，再到形成模型、指标和服务的多个环节。这也是SQL成为数据工程师核心技能的重要原因。

## 六、会写SQL为什么还不够

SQL语法正确，只能说明查询可以执行，不能保证结果具有正确的业务含义。

一段SQL是否可信，还取决于开发人员能否回答：

- 每一行数据代表什么业务事实？
- 当前表的粒度是什么？
- 两张表是一对一、一对多还是多对多关系？
- 使用订单创建时间、支付时间还是完成时间？
- 退款、撤销和冲正应该怎样处理？
- 维度变化后，历史数据按照当时归属还是当前归属统计？
- 空值表示未知、不适用，还是数据缺失？
- 数据尚未完整到达时，是否允许发布指标？

很多错误SQL不会报错，甚至能够快速返回一个看似合理的数字。最危险的问题往往不是语法错误，而是关联造成数据重复、统计粒度混乱、业务口径遗漏或时间条件选择错误。

因此，优秀的数据工程师不仅要会写SQL，还要理解业务、数据模型、指标口径、质量规则和数据生命周期。

## 七、案例：一个销售汇总为什么可能算错

某集团希望按月份、区域、渠道和产品统计净销售额。这个需求看起来只需要把销售订单分组求和，但实际计算可能涉及：

- 一张订单包含多个产品明细，订单表与明细表粒度不同；
- 同一产品可能在统计期间调整产品线归属；
- 线上订单按照收货区域还是下单区域统计；
- 取消订单是否参与合同额统计；
- 退款发生在次月时，冲减原销售月份还是退款月份；
- 渠道信息缺失或后补时，历史结果是否重算；
- 订单表与回款表直接关联，可能因多次回款造成销售额重复；
- 不同系统对“净销售额”的含税和优惠处理方式可能不同。

假设一笔订单有3条产品明细和2笔回款。如果把订单、明细和回款直接连接，可能得到6行结果，进而重复累计订单金额。这种SQL完全可能成功执行，但结果是错的。

正确做法通常要先明确：

1. 每个指标采用什么统计粒度；
2. 订单、产品明细、回款和退款分别怎样汇总；
3. 不同粒度的数据在哪一层进行关联；
4. 维度归属和时间口径采用什么规则；
5. 哪些公共计算应沉淀为统一模型，而不是由每张报表重复实现。

这个案例说明，SQL是业务规则的实现工具，但不能替代业务定义和数据建模。数据治理要做的，是让不同开发人员在使用SQL时遵循相同的业务语义、数据标准和指标口径。

## 八、怎样避免SQL变成难以维护的脚本

### 1. 按数据层次和业务粒度拆分

不要把数据清洗、实体整合、指标计算和结果发布全部塞进一条超长SQL。合理的中间模型能够表达清楚的数据粒度和复用边界。

### 2. 避免硬编码

日期、区域、路径、阈值和运行批次等变化内容应通过参数传入；稳定的业务规则则应由指标、模型或规则定义统一管理。

### 3. 复用公共模型和指标

多个报表都需要订单净额时，不应各写一套退款和优惠计算。应形成统一的明细模型或公共指标，减少重复开发和口径分裂。

### 4. 为复杂逻辑增加测试

不仅要测试SQL能否运行，还要准备边界数据，验证重复关联、空值、迟到数据、退款、撤销和维度变化等情况。

### 5. 纳入版本和血缘管理

SQL、依赖的数据模型、指标定义和运行参数都可能变化。需要记录版本、发布过程、输入输出和影响范围，使结果可以解释、比较和回溯。

### 6. 根据引擎特点优化，而不是盲目套用语法

关系数据库、Spark和Flink的执行方式不同。开发人员需要理解数据规模、分区、数据倾斜、状态、窗口和资源消耗等问题，避免把能够执行误认为适合生产。

## 九、AI能够代替数据工程师写SQL吗

AI已经能够根据自然语言生成SQL、解释查询、补全语句和提出优化建议，这会显著降低SQL的编写门槛。但AI生成的SQL仍然依赖提供给它的表结构、业务语义和上下文。

AI可能写出语法正确却业务错误的SQL，例如：

- 选择了名称相似但含义不同的字段；
- 忽略表之间的一对多关系；
- 使用了错误的时间字段；
- 没有处理退款、撤销或迟到数据；
- 把当前维度归属用于全部历史数据；
- 生成目标引擎不支持或性能很差的写法。

因此，AI更适合作为SQL开发助手，而不是业务口径和数据责任的替代者。业务人员可以借助AI更方便地提出查询，数据工程师也可以减少机械编码，但仍然需要有人验证数据来源、关联关系、统计粒度、指标含义和执行成本。

AI让“写出一段SQL”越来越容易，也让“判断这段SQL是否可信”变得更加重要。理解SQL仍然是数据工程师审查和运用AI生成结果的基础。

## 十、常见误区

### 误区一：会使用SELECT就掌握了SQL

查询语法只是基础。复杂数据开发还需要理解连接、窗口、集合运算、事务或流式语义，并能判断粒度、口径和性能。

### 误区二：支持SQL的平台可以无缝替换

不同平台的方言、数据类型、函数、执行语义和性能特点存在差异。迁移时既要检查语法，也要验证结果和运行特征。

### 误区三：SQL能够运行，结果就是正确的

SQL引擎只能判断语法和部分类型是否正确，无法自行判断业务口径是否正确。

### 误区四：所有数据处理都应该使用SQL

复杂算法、非结构化数据处理、外部系统交互和特殊格式解析可能更适合脚本、Notebook或专用算子。SQL重要，但不是唯一工具。

### 误区五：AI会生成SQL，所以不再需要学习SQL

AI降低了编写难度，却不能替代对数据模型、业务语义和执行结果的判断。不会SQL，也就很难可靠地审查AI生成的SQL。

## 十一、实践检查清单

1. 开发人员是否理解SQL所处理数据的业务含义和粒度？
2. 是否核对了一对多和多对多关联可能造成的数据重复？
3. 指标计算是否采用统一的时间、过滤、维度和聚合口径？
4. SQL是否按数据层次合理拆分，并复用公共模型和指标？
5. 日期、区域、阈值和运行批次是否避免硬编码？
6. 是否针对空值、重复、迟到、退款和维度变化等情况进行测试？
7. SQL及其依赖是否纳入版本、血缘、调度和质量管理？
8. 在Spark、Flink等平台上运行时，是否理解相应方言和执行语义？
9. AI生成的SQL是否经过业务口径、数据结果和执行成本验证？

## 小结

SQL从关系数据库走向数据仓库、数据湖、湖仓、Spark和Flink等平台，已经成为跨数据系统的通用处理语言。它普及程度高、表达能力强，并直接面向表、关系、粒度和聚合，因此成为大多数数据工程师岗位的必备技能。

但数据工程师的价值不只是把需求翻译成SQL，而是理解业务事实和数据模型，把统一口径落实为可靠、可复用、可追溯的数据生产过程。SQL是第一语言，不是唯一语言；会写SQL是起点，能够用SQL持续产生可信的业务结果才是目标。
