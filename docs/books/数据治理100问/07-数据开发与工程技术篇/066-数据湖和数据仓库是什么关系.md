# 066 数据湖和数据仓库是什么关系？

## 一句话回答

> 数据湖和数据仓库是两种不同但可以互补的数据组织方式。数据湖更适合灵活保存大规模、多类型和暂未完全确定用途的数据；数据仓库更适合把经过整合、建模和质量控制的数据，稳定地提供给指标、报表和业务分析。企业可以同时建设两者，也可以只选择其中一种，不必把“湖加仓”当作所有项目的标准答案。

第011问已经介绍了业务数据库与数据仓库的区别。本问进一步讨论：当企业还要保存日志、文件、图片、音视频、物联网和其他多类型数据时，数据湖能够发挥什么作用，它与数据仓库应当怎样分工和协作。

## 一、什么是数据湖

数据湖（Data Lake）通常用于集中保存大规模、多种类型的数据，例如：

- 从业务数据库抽取的表数据；
- 日志、消息和事件数据；
- 物联网和实时流数据；
- 文档、图片、音频和视频；
- 空间数据、遥感影像和模型文件；
- 算法训练数据及中间结果。

数据进入湖中时，可以较多地保留来源格式和原始细节，不必在写入前就完成全部业务建模。这使数据湖比较适合：

- 保留来源数据和长期历史；
- 接纳暂时没有明确用途的数据；
- 支持数据探索和算法试验；
- 在规则修正后重新处理历史数据；
- 以相对灵活的方式扩展数据类型和规模。

“先保存、后理解”提供了灵活性，也带来了风险。如果只不断接收数据，却不说明数据是什么、能否使用和由谁负责，数据湖很快就会变成难以理解的数据堆积区。

## 二、数据湖是否就是对象存储

不是。对象存储是数据湖常用的底层存储方式之一，数据湖则是建立在存储、数据组织、元数据、治理和计算能力之上的数据管理体系。

对象存储主要负责保存文件或二进制对象，例如数据文件、日志、图片、视频、模型和压缩包。它通常具有容量容易扩展、适合保存多类型数据和单位存储成本相对较低等特点，因此很适合作为数据湖的存储基础。

但是，对象存储本身通常只直接管理：

- 对象的存储位置和标识；
- 文件大小、类型和修改时间；
- 少量对象级属性；
- 基本访问权限；
- 版本和生命周期等存储策略。

它并不天然理解某个文件属于哪个业务数据集、字段是什么意思、数据是否完整、由谁负责，以及应当怎样参与指标计算。

一个受治理的数据湖还需要：

- 清楚的数据集、目录和分区组织；
- 文件格式、数据结构和版本管理；
- 元数据采集、数据目录和检索；
- 数据来源、责任人和更新周期；
- 数据质量状态和适用范围；
- 分级分类、权限和敏感数据保护；
- 数据保留、归档和删除规则；
- 输入、处理和使用血缘；
- 能够读取和处理数据的计算引擎；
- 面向开发、分析和算法人员的使用入口。

可以用一个简化关系帮助理解：

```text
对象存储
  + 数据组织与格式
  + 元数据和目录
  + 权限、质量与生命周期
  + 计算和访问能力
  = 受治理的数据湖
```

这不是严格的技术公式，但说明了仅仅创建存储空间、上传大量文件，并不能自动形成数据湖。

数据湖也不一定只能使用对象存储。它还可以建立在分布式文件系统、网络文件存储或多种存储方式的组合上。真正的判断依据，是数据是否被作为统一的数据集合进行组织，是否具备元数据、权限、质量、生命周期和计算使用能力。

## 三、为什么数据湖容易变成“数据沼泽”

如果企业只是把各部门的文件不断放进集中存储，可能出现：

- 文件命名和目录结构各自为政；
- 同一数据存在大量重复副本；
- 不知道哪个版本可以使用；
- 文件结构变化后下游任务直接失败；
- 无法查询数据来自哪里、由谁负责；
- 敏感数据与普通数据混在一起；
- 数据长期无人使用却一直占用空间；
- 只有上传人员知道文件的实际含义。

这种状态常被形象地称为“数据沼泽”：数据很多，却难以发现、理解、信任和使用。

避免数据沼泽并不意味着必须在数据进入湖之前就完成全部建模，而是至少要在进入时记录来源、时间、格式、责任、权限和基本结构，并随着数据用途逐步补充质量、语义和服务要求。

## 四、什么是数据仓库

数据仓库（Data Warehouse）主要面向跨系统分析和稳定的数据交付。进入数据仓库的数据通常已经经过：

- 汇聚和清洗；
- 编码与业务含义统一；
- 事实、维度和主题建模；
- 历史变化处理；
- 指标口径落实；
- 数据质量检查；
- 面向查询和分析的性能优化。

数据仓库比较适合提供：

- 统一经营或管理指标；
- 报表、驾驶舱和专题分析；
- 跨业务主题分析；
- 面向业务人员的自助查询；
- 稳定的数据服务；
- 需要明确口径和服务水平的数据产品。

数据仓库的价值不只是把数据变成表，而是把来自不同系统的数据组织成可以稳定理解、重复计算和持续使用的业务事实。

## 五、数据湖与数据仓库有哪些典型差异

| 维度 | 数据湖 | 数据仓库 |
| --- | --- | --- |
| 主要目标 | 灵活接纳和保存多类型数据 | 稳定提供经过组织的分析数据 |
| 数据类型 | 结构化、半结构化和非结构化数据 | 以结构化、面向分析的数据为主 |
| 数据状态 | 原始、明细、中间和加工结果都可能存在 | 主要是经过整合、建模和验证的数据 |
| 结构要求 | 可以先保存，再逐步理解和建模 | 通常在稳定使用前明确结构和口径 |
| 主要使用者 | 数据工程师、算法和研究人员 | 分析人员、业务人员和应用系统 |
| 典型用途 | 探索、训练、历史重算和多类型数据处理 | 指标、报表、分析和稳定数据服务 |
| 查询体验 | 取决于数据组织和所连接的计算引擎 | 通常针对高频分析和并发查询优化 |
| 主要风险 | 数据堆积、语义不清和难以发现 | 重复模型、口径分散和分层膨胀 |

这些是典型差异，不是绝对的产品边界。现代数据湖也可以保存经过治理的结构化数据，数据仓库也可能设置贴近来源的数据层或接收部分半结构化数据。判断两者的重点，应是数据怎样组织和服务什么用途，而不是机械地根据文件或表进行分类。

## 六、如何理解“写入时定义结构”和“读取时解释结构”

数据仓库通常更强调在数据稳定进入分析体系前，明确数据结构、对象关系和业务口径。这种方式有时被称为“写入时模式”：数据需要满足预先定义的结构，才能进入相应的数据模型。

数据湖允许先保留来源数据，在具体分析或加工时，再根据用途选择适合的结构和解释方式。这种方式常被称为“读取时模式”。

但是，“读取时模式”不等于数据可以永远没有结构和语义。文件格式、字段、时间、对象标识和版本仍然需要基本说明；数据一旦进入稳定共享、指标计算或业务服务，就必须进一步明确业务含义、质量和使用边界。

数据湖允许延后部分建模工作，而不是取消建模。

## 七、数据湖和数据仓库怎样协同

一种常见协同方式是：

```text
业务系统、文件、日志、流数据和多媒体数据
                      ↓
               数据湖保存来源数据
                      ↓
           清洗、标准化、关联和建模
                      ↓
            数据仓库形成可信分析数据
                      ↓
           指标、报表、服务和业务应用
```

在这条链路中：

- 数据湖保留来源细节、历史数据和多类型数据；
- 数据仓库形成统一业务对象、事实、维度和指标；
- 湖中的历史数据可以支持问题核查和重新加工；
- 仓中的可信数据也可以用于算法训练和进一步分析；
- 数据从湖进入仓时，需要保留转换规则、版本和血缘。

这只是常见方式，并非所有数据都必须沿着同一条路径流动。结构清楚、用途稳定的业务数据可以直接进入数据仓库；湖中已经完成治理的数据，也可以直接提供给部分探索、算法和分析场景。

## 八、数据湖是不是数据仓库的前置必经阶段

不是。如果企业的数据主要来自结构化业务系统，数据规模适中，需求集中在稳定指标和报表，直接建设数据仓库通常更加简单。

只有在以下情况中，数据湖的价值才更明显：

- 数据类型复杂，文件和非结构化数据较多；
- 需要长期保留大量来源数据；
- 未来用途暂时无法完全确定；
- 算法探索和模型训练需求较多；
- 需要重放或按照新规则重算历史数据；
- 数据规模使传统仓库的存储成本较高。

没有这些需求，为了架构完整而增加数据湖，可能只会多建设一套存储、计算和治理体系。

## 九、数据仓库能否完全替代数据湖

数据仓库擅长提供稳定分析结果，却不一定适合承担所有来源数据和多类型数据的长期保存。如果所有数据都直接加工成仓库模型，可能出现：

- 暂无明确用途的数据难以接纳；
- 原始细节在加工过程中丢失；
- 新算法需要的数据没有保存；
- 规则出错后缺少来源数据进行重算；
- 文档、图片和视频等数据难以进入传统表模型；
- 保存大规模低频数据的成本过高。

因此，数据湖与数据仓库并不是简单的新旧替代关系。数据湖保留更广泛的数据可能性，数据仓库把其中具有明确价值的数据组织成稳定的分析能力。

## 十、数据进入湖后，谁是权威来源

把数据复制到数据湖，并不会自动改变数据的权威来源。业务系统仍可能是正式业务事实的权威记录，湖中保存的则是某个时间取得的数据副本、快照或事件记录。

治理中需要记录：

- 数据来自哪个系统、接口或设备；
- 在什么时间采集；
- 对应哪个批次和版本；
- 是否采集完整；
- 是否经过转换；
- 与来源系统发生冲突时以谁为准。

数据湖可以保留来源事实和历史变化，但不能因为保存的数据更多，就自动成为所有业务数据的权威系统。

## 十一、数据湖是否也需要分层

数据湖可以根据数据状态划分不同区域，例如：

- 来源或原始数据；
- 已完成基础校验和格式整理的数据；
- 已标准化并可以复用的数据；
- 面向算法、分析或共享的结果。

分层的目的，是说明数据当前处于什么状态、可以怎样使用以及由谁负责，而不是简单创建几个固定名称的目录。不同企业可以根据数据来源、处理过程和使用方式设计适合自己的层次。

“原始区”也不能成为治理空白。即使保留原始内容，仍然需要管理来源、格式、采集时间、权限、完整性和生命周期。

## 十二、数据湖和数据仓库怎样支持数据治理

数据湖可以为治理提供：

- 多类型数据的统一发现；
- 来源数据和历史细节保留；
- 规则修正后的重新处理能力；
- 算法探索和新用途发现的基础。

数据仓库可以为治理提供：

- 跨系统业务语义统一；
- 稳定的事实、维度和指标；
- 面向业务的数据质量和服务水平；
- 可复用的分析结果和数据服务。

数据治理贯穿两者。湖中的数据不能只存不管，仓中的数据也不能只建模不运营；同一数据在湖和仓中存在多个版本时，需要说明它们的来源关系、加工规则、质量状态和适用场景。

数据湖和数据仓库也不是数据治理本身。它们提供存储、组织和计算基础，数据治理还需要确定业务目标、权威来源、责任、标准、安全要求和价值评价。

## 十三、是否所有企业都需要同时建设湖和仓

答案是否定的。可以从实际需求出发判断：

| 主要需求 | 可以优先考虑 |
| --- | --- |
| 结构化数据、稳定指标和报表 | 数据仓库 |
| 多类型来源数据、探索和历史重算 | 数据湖 |
| 两类需求同时存在，并且规模与价值足够 | 数据湖与数据仓库协同 |
| 数据量有限、使用场景尚不明确 | 先解决具体业务需求，避免过早建设复杂平台 |

架构完整不等于业务有效。没有明确用途、责任和持续运营的数据湖或数据仓库，都可能成为昂贵的数据堆积区。

## 十四、案例：制造企业的质量分析

某制造企业的数据包括：

- 生产系统中的订单、工序和检验记录；
- 设备持续产生的传感器数据；
- 质检过程产生的产品图片和检测文件；
- 维修过程产生的文档和日志；
- 供应商提供的批次和材料证明文件。

企业使用数据湖保存这些多类型来源数据及其历史版本，并记录来源设备、生产批次、采集时间、格式、权限和保存期限。

经过清洗和关联后，产品、工序、设备、缺陷和质量结果进入数据仓库，形成统一的生产事实、质量指标和分析主题。管理人员通过仓库查看良品率、返工率和设备影响指标，算法人员则可以使用湖中的传感器数据和产品图片训练缺陷识别模型。

当质量规则或模型发生变化时，团队可以回到湖中的历史来源数据重新分析；经过验证的结果再进入仓库，为正式报表和质量管理提供服务。

这个案例中，数据湖负责保留广泛的数据可能性，数据仓库负责交付稳定的业务事实和指标。两者相互协作，却不承担相同职责。

## 十五、常见误区

### 误区一：数据湖就是对象存储

对象存储只是数据湖常用的底层存储方式。缺少数据组织、元数据、治理、计算和访问能力时，它仍然只是存储空间。

### 误区二：数据湖可以没有结构和治理

数据湖可以延后部分建模，但仍需要管理来源、格式、版本、权限、质量和生命周期。

### 误区三：数据湖比数据仓库更先进

两者解决的问题不同。稳定指标和报表可能更适合数据仓库，多类型数据保存和探索可能更适合数据湖。

### 误区四：建设数据湖以后可以取消数据仓库

如果业务需要统一模型、稳定指标和高质量分析服务，数据仓库的组织方式仍然有价值。

### 误区五：所有数据都必须先进入湖再进入仓

结构清楚、用途稳定的数据可以直接进入数据仓库，没有必要为了形式增加中间环节。

### 误区六：数据仓库只能保存汇总数据

数据仓库通常同时保存标准化明细、历史数据和汇总结果，并不只有报表汇总表。

### 误区七：原始数据进入湖后，湖就成为权威来源

复制数据不会自动转移业务权威。仍需明确来源系统与湖中副本各自的责任和使用边界。

### 误区八：把所有数据永久保存在湖中最保险

长期保存会增加成本和安全风险。数据仍需要根据业务价值、法规、审计和使用需求确定生命周期。

### 误区九：同时建设湖和仓就已经实现湖仓一体

把两个系统同时部署，只能说明湖和仓并存。它们是否共享数据、减少复制并形成一致的治理和计算体系，是下一问需要讨论的问题。

## 十六、实践检查清单

1. 企业需要保存哪些结构化、半结构化和非结构化数据？
2. 建设目标是稳定指标与报表，还是多类型数据保存、探索和重算？
3. 所谓“数据湖”是否只有对象存储，还是已经具备数据组织、元数据和治理能力？
4. 湖中每个数据集是否能够查询来源、责任人、格式、版本和更新时间？
5. 原始数据是否保留必要细节，同时受到权限和生命周期管理？
6. 哪些数据可以直接进入仓库，哪些数据确实需要先在湖中保存？
7. 数据从湖进入仓时，是否记录转换规则、版本和血缘？
8. 数据仓库是否形成稳定的事实、维度、指标和质量要求？
9. 同一数据在湖和仓中存在多份结果时，使用边界是否清楚？
10. 湖中副本与来源业务系统之间的权威关系是否明确？
11. 湖中的低频、过期和无人负责数据是否定期评估和清理？
12. 数据湖和数据仓库的建设及运营成本是否得到真实业务价值支撑？

## 小结

数据湖更擅长灵活接纳多类型数据、保留来源细节并支持探索和重算；数据仓库更擅长通过整合、建模和质量控制，形成稳定的业务事实、指标和分析服务。两者可以协同，但不构成必须同时建设的固定组合。

对象存储是数据湖常见的存储基础，却不等于数据湖。只有进一步建立数据组织、元数据、权限、质量、生命周期、血缘、计算和访问能力，存储中的文件才能成为可发现、可理解、可使用和可治理的数据集合。

企业应根据数据类型、分析目标、历史保留、算法探索、重算需求和运营能力选择湖、仓或二者协同。没有明确用途和治理责任，无论数据湖还是数据仓库，都可能变成新的数据堆积区。
