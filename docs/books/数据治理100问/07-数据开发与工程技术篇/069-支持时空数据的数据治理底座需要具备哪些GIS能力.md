# 069 支持时空数据的数据治理底座需要具备哪些 GIS 能力？

## 一句话回答

> 支持时空数据的数据治理底座，需要把空间数据读写、空间 SQL、Python 分析、工作流算子、空间质量检查和大规模空间计算纳入统一的数据开发过程，同时协调空间数据库、对象存储和不同 GIS 引擎。数据治理底座不一定要包含一套完整 GIS 平台，但必须让必要的 GIS 能力能够被稳定调用、扩展和追溯。

第050问已经介绍了时空数据的业务价值，第051问讨论了空间数据质量，第052问说明了行业格式的治理方法。本问不再重复这些内容，而是从工程角度回答：当空间数据进入统一治理范围时，治理底座需要具备哪些专业能力，这些能力与通用数据开发体系怎样协同。

## 一、数据治理底座为什么需要 GIS 能力

普通数据处理能力擅长读取表、关联字段、执行 SQL 和处理文件，但遇到以下问题时，需要专门的 GIS 能力：

- 一个地块是否与保护区相交；
- 某条道路周边一定范围内有哪些设施；
- 两个空间数据集是否存在重叠、缝隙或位置偏移；
- 不同坐标参考系的数据怎样正确叠加；
- 大幅影像怎样裁剪、重采样和分块；
- 不同时间的边界或影像发生了什么变化；
- 空间数据怎样生成可供浏览的地图或瓦片；
- 点云、三维和专业行业格式怎样读取和计算。

这些工作不是给普通字段再增加一个经纬度就能完成的。治理底座需要调用能够理解几何、坐标、空间关系、栅格和专业格式的引擎。

但是，需要 GIS 能力不等于必须建设一套大而全的 GIS 平台。空间数据库扩展、格式读写程序库、空间计算引擎和专业算法服务，都可能承担其中一部分工作。

## 二、先把 GIS 能力分成几个层次

| 能力层次 | 主要解决的问题 |
| --- | --- |
| 空间数据读写 | 怎样识别、读取和写入矢量、栅格、三维及行业格式 |
| 空间存储与 SQL | 怎样存储空间对象，并进行查询、关联和统计 |
| 空间计算 | 怎样进行坐标转换、叠加、缓冲、栅格和专业算法处理 |
| 空间质量 | 怎样检查几何、位置、拓扑和空间业务关系 |
| 地图与服务 | 怎样把数据表达为地图、瓦片或空间服务 |
| 专业桌面作业 | 怎样完成复杂编辑、制图、判读和本地设备操作 |

数据治理底座应根据真实业务选择所需能力，不要求一个引擎包揽全部工作。地图、瓦片、GIS 服务和完整 GIS 平台的治理边界，将在第070问集中讨论。

## 三、空间 SQL 应成为一等数据开发能力

第056问提出 SQL 是数据工程师的第一语言。空间数据进入治理体系后，也应尽量能够通过 SQL 完成常见开发工作，例如：

- 查询某个范围内的对象；
- 判断两个对象相交、包含、邻接或距离多远；
- 根据空间关系关联两个数据集；
- 计算面积、长度和对象数量；
- 生成缓冲区、交集或差集；
- 按行政区、网格或业务范围进行汇总；
- 转换坐标参考系；
- 使用空间索引优化查询。

这类能力通常由数据库的空间扩展承担，也可以由数据仓库、湖仓或其他计算引擎提供空间类型和函数。

例如，要统计各保护区内的建设项目数量，可以让项目数据与保护区数据根据空间相交关系进行关联，再按照保护区汇总。对数据工程师来说，这仍然是查询、关联和聚合，只是关联条件从普通编码扩展为空间关系。

空间 SQL 的意义，不只是少写一些程序代码，而是让空间关系进入可参数化、可复用和可调度的数据开发过程。

## 四、空间 SQL 不能替代所有 GIS 计算

空间 SQL 比较适合数据库中的结构化矢量数据和常见空间计算，但以下任务可能更适合 Python、工作流或专业引擎：

- 大规模遥感影像处理；
- 复杂栅格和地形分析；
- 点云和三维模型处理；
- 影像分类和变化检测；
- 需要特定行业程序库的专业算法；
- 依赖 GPU、专用设备或特殊运行环境的计算；
- 交互式制图和人工判读。

因此，治理底座需要提供稳定的空间 SQL 路径，但不应要求所有空间计算都改写为 SQL，也不应要求每个 GIS 引擎自己实现一套 SQL。

## 五、Notebook 应具备空间 Python 能力

Notebook 适合空间数据探索、算法试验和模型验证。一个可用的空间 Notebook 环境通常需要支持：

- 读取空间数据库、文件和对象存储中的数据；
- 操作几何对象和属性表；
- 进行坐标转换、空间关联、裁剪和叠加；
- 处理栅格、影像和多维数组；
- 调用统计、机器学习和专业算法；
- 展示地图、图表和中间结果；
- 把成熟代码沉淀为可重复执行的任务或算子。

这不意味着每个 GIS 引擎内部都必须使用 Python。Notebook 可以直接使用空间 Python 程序库，也可以通过数据库连接、Python SDK 或服务接口调用外部 GIS 引擎。

治理底座还需要管理 Python、空间程序库和底层原生依赖的版本。坐标转换库、几何计算库或格式驱动发生变化，都可能影响计算结果，不能只保存一段 Notebook 代码而忽略运行环境。

## 六、成熟空间处理应进入工作流

空间探索和人工试验可以在 Notebook 或桌面工具中完成，已经稳定、需要持续运行的过程则应能够封装为工作流算子或计算任务，例如：

- 坐标和格式转换；
- 空间关联和叠加；
- 缓冲区计算；
- 影像裁剪和重采样；
- 地形和栅格统计；
- 几何与拓扑检查；
- 空间指标计算；
- 变化检测和专业模型调用。

每个算子至少应说明：

- 接受什么数据类型和格式；
- 需要什么坐标、空间范围和参数；
- 使用哪个引擎、算法和版本；
- 产生什么数据和质量信息；
- 适用于什么规模和业务条件；
- 失败后能否重试或重新计算。

这样，空间计算才能与数据汇聚、质量检查、模型加工和指标计算衔接，而不是长期停留在某位专业人员的操作记录中。

## 七、GIS 导入导出与数据汇聚是什么关系

GIS 引擎通常能够在空间数据库、矢量文件、栅格影像、复合数据集和行业格式之间导入、导出和转换。这是空间数据物理汇聚的重要专业执行能力。

但是，人工执行一次“导入”或“另存为”并不等于形成了可持续的数据汇聚。只有进一步纳入参数、调度、质量、监控和血缘管理，导入导出才能成为稳定的数据汇聚过程。

可以简化为：

```text
数据汇聚体系
  ├── 管理来源、目标、参数、计划、状态和血缘
  └── 调用 GIS 引擎正确读取、转换和写入空间数据
```

具体的全量、增量、定时和逻辑汇聚方法，已经在第030问讨论，本问不再展开。

## 八、空间数据读写不能只看“能不能打开”

两个 GIS 引擎都能打开同一个文件，不代表它们能够完整、等价地读写这份数据。需要进一步确认：

- 支持的是哪个格式版本；
- 只能读取，还是可以创建和更新；
- 是否保留字段名称、类型、长度、编码和空值；
- 是否支持点、线、面、多部件和几何集合；
- 是否保留曲线、Z 值、M 值和三维信息；
- 是否正确处理坐标参考系和轴顺序；
- 是否保留栅格波段、颜色表、分辨率和无效值；
- 是否保留附件、关系、拓扑和扩展属性；
- 写入后是否仍能被原来的专业软件正确使用。

“成功生成目标文件”只能说明任务完成了技术写入，不能证明业务内容没有发生损失。

## 九、为什么不同 GIS 引擎之间的格式兼容特别困难

空间格式除了保存普通字段，还可能表达几何、坐标、栅格、三维、拓扑、样式和专业对象。同一种格式在不同引擎中也可能只得到部分支持。

常见问题包括：

- 一个引擎把曲线保留为曲线，另一个将其离散为折线；
- 一个引擎支持多个几何字段，另一个只识别一个；
- 同一坐标参考系在不同版本中采用不同表达；
- 某些字段、关系和扩展信息只能被原生产软件理解；
- 一个引擎能够读取，却无法无损写回；
- 数据能够交换，但地图符号和标注无法完整交换；
- 文件格式相同，实际采用的扩展和约定却不同。

因此，跨引擎兼容不能只维护一张“支持格式清单”，还要说明具体支持哪些能力、版本和限制。

## 十、不要寻找一种万能空间格式

一种格式很难同时满足专业编辑、数据库查询、大规模分析、离线交换、云端访问、Web 地图发布和长期归档。

更合理的做法是：保留权威原始数据，再根据用途形成受治理的物理表达。例如，同一个道路数据集可以同时具有：

- 生产数据库中的权威版本；
- 面向离线交换的便携文件；
- 面向大规模分析的列式数据；
- 面向 Web 地图的矢量瓦片；
- 面向应用系统的数据访问接口。

这些不应被登记为五份毫无关系的数据，而应视为同一个逻辑数据集的不同分发形式，并分别记录格式、位置、用途、更新周期、生成方式和版本关系。

格式统一的目标不是让所有数据只剩一个后缀，而是让不同引擎能够选择适合的表达，同时知道它们来自同一份受治理的数据。

## 十一、需要建立格式注册表和引擎能力矩阵

格式注册表管理组织对各种空间格式的认识，包括：

- 格式名称、版本和识别方式；
- 单文件还是复合数据集；
- 可以表达哪些矢量、栅格、三维或专业对象；
- 坐标和时间信息怎样保存；
- 是否支持属性、附件、关系和样式；
- 已知限制和信息损失；
- 推荐用途和可用转换方式。

引擎能力矩阵则记录每个 GIS 引擎：

- 能够识别、读取、创建和更新哪些格式；
- 支持哪些格式版本和数据类型；
- 能否保留坐标、三维和扩展信息；
- 能否直接访问数据库、对象存储或服务；
- 需要什么操作系统、程序库和软件许可；
- 存在哪些已知兼容问题。

有了这两类信息，任务在运行前就能够判断由哪个引擎执行、是否可能有损，以及输出能否继续交给下一个引擎。

## 十二、格式转换应成为受治理的显式任务

不同引擎之间的转换不应隐藏在某个导入按钮背后。一个可治理的转换过程通常包括：

```text
识别来源格式、版本和数据集组成
                ↓
检查目标引擎和目标格式的能力
                ↓
声明字段、几何、坐标和对象映射
                ↓
执行转换
                ↓
核对数量、范围、结构和质量
                ↓
登记新分发形式、转换报告和血缘
```

转换后应根据用途检查记录数量、几何类型、空间范围、坐标参考系、字段结构、关键统计、栅格尺寸和分辨率等内容。对于已知有损转换，应提前说明损失内容和适用边界。

还应尽量避免“格式 A 转为 B，B 再转为 C，C 又转为 D”的长链路。每次转换都可能增加信息损失。更合理的方式是从权威来源直接生成所需表达，并保留完整来源关系。

## 十三、空间数据库和对象存储应怎样分工

支持空间数据并不意味着只能选择空间数据库，也不意味着所有数据都应放入对象存储。两者适合不同工作负载。

| 需求 | 更适合的存储方式 |
| --- | --- |
| 空间 SQL、关联查询和索引 | 空间数据库 |
| 高频新增、修改和事务控制 | 空间数据库 |
| 多人持续编辑和版本冲突处理 | 空间数据库或专业编辑环境 |
| 大规模影像、点云和三维文件 | 对象存储 |
| 原始数据、历史版本和低频成果 | 对象存储 |
| 矢量瓦片、栅格瓦片和派生文件 | 对象存储 |
| 面向多个计算节点共享的大文件 | 对象存储 |

常见做法是让空间数据库保存需要持续查询、关联和编辑的数据，让对象存储保存大规模文件、影像、历史版本、瓦片和派生成果。二者协同使用，不必互相替代。

对象存储只是存储基础。只有进一步具备数据集组织、元数据、权限、质量、生命周期和计算能力，才可能形成受治理的数据湖。这一边界已在第066问展开。

## 十四、GIS 引擎怎样才算真正支持对象存储

如果 GIS 引擎每次都先把整个对象下载到本地，完成计算后再整体上传，只能算基本兼容，还没有充分发挥对象存储的价值。

更完整的支持包括：

- 使用稳定对象地址直接读取和写入；
- 按空间范围、数据分块或文件分区读取必要内容；
- 支持局部、分块和并行读取；
- 支持大文件分段上传、失败重试和完整性校验；
- 识别由多个对象共同组成的数据集；
- 处理临时结果、中间结果和正式成果的不同生命周期；
- 让不同计算节点共享同一数据位置；
- 在任务完成后发布经过验证的新数据版本。

格式也需要适应对象存储。大规模影像可以采用支持分块、概览和局部读取的格式，大规模矢量分析可以采用支持分区和并行读取的表达，Web 发布成果可以采用矢量或栅格瓦片。没有一种格式适合所有数据。

## 十五、对象存储上的数据需要版本化发布

对象存储通常不适合像数据库记录一样频繁进行原位置修改。写入正式空间成果时，可以采用：

1. 写入一个新的数据版本；
2. 检查对象清单、数量、范围、格式和校验值；
3. 确认整个数据集写入完整；
4. 发布新的正式版本或数据清单；
5. 再让服务和下游任务使用新版本；
6. 按生命周期清理失败结果和过期版本。

这种方式可以避免下游读取到尚未写完的数据，也有利于历史查询和回滚。需要频繁修改的数据可以先在空间数据库中完成编辑，形成稳定版本后再发布到对象存储。

对象存储中的路径也不能替代数据身份。治理体系仍要说明一组对象属于哪个数据集、处于哪个版本、覆盖什么范围、由谁形成，以及与哪些任务和成果相关。

## 十六、对象存储访问也要纳入权限管理

GIS 桌面、Notebook 和工作流不应把长期访问密钥直接写入地图工程、代码或任务参数。更合理的方式，是根据用户、任务和数据权限提供短期凭据、受控数据地址或限时访问能力。

需要控制和记录：

- 可以访问哪些数据集或对象范围；
- 是否允许读取、写入和删除；
- 访问能力在什么时间内有效；
- 是否允许把数据下载到本地；
- 跨网络和跨安全域的数据传输；
- 对象读取、写入和删除的审计记录。

不同 GIS 引擎应使用稳定的数据引用，而不是依赖某台服务器上的本地挂载路径。这样，同一份受治理的数据才能在不同计算环境中被正确识别和授权。

## 十七、空间质量、版本和血缘仍要统一管理

GIS 引擎可以执行几何、坐标、位置、拓扑和空间业务关系检查，治理体系则负责定义规则、安排执行、分派问题和形成整改闭环。具体规则已在第051问展开。

空间数据还需要管理：

- 边界和属性版本；
- 调查、观测、生效和失效时间；
- 对象分割、合并和边界调整；
- 历史版本查询；
- 数据变化对指标和下游结果的影响。

每次空间计算至少应记录：

- 输入数据及版本；
- 坐标参考系和空间范围；
- GIS 引擎、算法和程序库版本；
- 缓冲距离、拓扑容差、重采样方式等参数；
- 执行时间、责任主体和运行状态；
- 输出数据及其质量结果；
- 输入、过程和输出之间的血缘。

这样，同一项分析才能被复核和重新计算，而不是只剩一个无法解释的输出文件。

## 十八、大规模空间计算应尽量靠近数据

大规模矢量、影像、三维和点云数据不适合全部下载到个人桌面处理。GIS 引擎应能够部署在数据所在网络，由 SQL、Notebook、工作流、Web 或桌面入口提交任务，直接读取被授权的数据，并只返回必要结果。

本地 GIS 桌面仍然适合复杂编辑、专业制图、人工判读、本地设备和小范围文件处理。服务器端计算和桌面专业作业应根据数据位置、规模和操作方式分工，而不是相互替代。

第068问已经讨论了 Web、桌面端和外部专业工具的选择，本问只强调：数据不能离开受控网络时，空间计算也应移动到数据附近。

## 十九、GIS 能力需要可扩展，而不是绑定单一产品

不同领域可能不断出现新的空间格式、三维模型、遥感算法、点云处理方式和专业计算需求。治理底座不应假定一种 GIS 产品可以永久承担所有任务。

可以组合使用：

- 数据库空间扩展；
- 文件和格式读写程序库；
- 通用 GIS 计算引擎；
- 遥感、点云和三维专业引擎；
- 面向大规模数据的空间计算引擎；
- 外部算法服务和专业桌面工具。

新增引擎时，应声明它支持的数据、格式、算法、运行环境和限制，并纳入统一的身份、权限、参数、任务、状态和血缘管理。

同一引擎内部的多个处理步骤可以利用内存传递和统一优化。不同引擎之间则通常通过稳定的数据结果和任务编排衔接，不宜依赖相互不可见的临时内存状态。

## 二十、案例：建设项目与管控范围叠加核查

某管理机构需要核查建设项目是否进入特定管控范围，并计算相交面积和占比。

完整过程可以是：

1. 治理底座确定建设项目、管控范围和行政区数据的有效版本；
2. 汇聚任务取得或更新相关空间数据；
3. 空间数据库通过 SQL 完成常见范围筛选和空间关联；
4. GIS 引擎统一坐标参考系，执行叠加和面积计算；
5. 空间质量规则检查几何、拓扑、容差和面积合理性；
6. Notebook 用样例数据验证算法和异常情况；
7. 成熟逻辑封装为工作流，按照项目更新情况重复执行；
8. 结果记录输入数据、参数、引擎版本和质量状态；
9. 核查结果进入审批或监管流程，并形成可以追溯的数据成果。

如果管控范围更新，系统可以根据依赖关系识别受影响项目，并对相应范围重新计算，而不必由专业人员重新逐个打开桌面软件操作。

这个案例说明，GIS 引擎并不是孤立的地图工具，而是数据治理生产链路中的专业计算能力。

## 二十一、常见误区

### 误区一：只要能在地图上显示，就已经支持空间数据治理

地图显示只是使用方式之一，还需要读写、计算、质量、版本、权限和血缘能力。

### 误区二：支持空间数据就必须建设一套完整 GIS 平台

治理底座可以按需组合空间数据库、格式程序库、计算引擎和专业工具。

### 误区三：空间 SQL 可以完成所有 GIS 工作

复杂影像、三维、点云和专业算法仍可能需要 Python 或其他引擎。

### 误区四：两个引擎都能打开同一格式，就能够无损交换

读取、写入、格式版本和扩展能力可能不同，必须通过能力矩阵和转换验证判断。

### 误区五：找到一种开放格式，就可以统一所有空间数据

编辑、分析、交换、云端访问和 Web 发布需要不同的数据表达。

### 误区六：格式转换任务成功，数据就一定正确

还需要核对结构、坐标、范围、数量、质量和已知信息损失。

### 误区七：GIS 导入导出工具就是完整的数据汇聚体系

导入导出是专业执行能力，还需要参数、调度、监控、质量和血缘管理。

### 误区八：对象存储能够替代空间数据库

对象存储适合大文件和派生成果，空间数据库更适合 SQL、事务和持续编辑。

### 误区九：把文件放进对象存储，GIS 引擎就能高效处理

还需要适合局部读取的格式、合理分区、直接访问和并行处理能力。

### 误区十：多个引擎能够读取同一数据，就可以同时任意写入

共同读取可以减少复制，写入仍应有明确责任、稳定路径和版本发布规则。

### 误区十一：空间计算只需保存最终结果

没有输入版本、算法、参数和环境，结果难以复核和重现。

## 二十二、规划 GIS 能力时应回答哪些问题

1. 当前需要治理哪些矢量、栅格、三维和专业格式？
2. 哪些任务适合空间 SQL，哪些需要 Python 或专业引擎？
3. 哪些过程需要进入工作流持续运行？
4. 每种格式由哪些引擎读取、写入和验证？
5. 格式转换可能丢失哪些信息？
6. 同一数据的不同物理表达怎样关联到一个逻辑数据集？
7. 哪些数据适合空间数据库，哪些适合对象存储？
8. GIS 引擎能否直接、局部和并行读取对象存储？
9. 空间质量规则、版本和历史变化怎样管理？
10. 空间计算怎样记录输入、参数、引擎和结果血缘？
11. 大规模和敏感数据应在哪个网络和计算环境处理？
12. 新格式、新算法和新引擎怎样接入，而不破坏已有体系？

这些问题比“采购哪一种 GIS 产品”更接近空间数据治理的本质。

## 小结

支持时空数据的数据治理底座，需要让 GIS 能力进入汇聚、SQL、Notebook、工作流、质量、存储和血缘体系，使空间数据能够像其他业务数据一样持续生产、验证、使用和追溯。

空间数据库适合 SQL、事务和持续编辑，对象存储适合大规模文件、影像、历史版本、瓦片和派生成果；不同 GIS 引擎之间应通过格式注册、能力声明、显式转换和结果验证协同，而不是追求一种万能格式或依赖某个产品包揽全部能力。

数据治理需要的不是一套更大、更全的 GIS 平台，而是一套能够稳定调用、持续运行、统一管理并保留专业扩展能力的 GIS 能力体系。
