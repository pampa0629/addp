# 070 地图、GIS 服务和 GIS 平台应该怎样纳入数据治理？

## 一句话回答

> 地图是空间数据经过选择、组织和表达形成的产品，GIS 服务是数据、地图或空间计算的使用入口，GIS 平台则是专业生产与应用环境。三者都应纳入统一的目录、版本、权限、质量、血缘和生命周期管理，但不能与权威来源数据混为一谈，也不能因为组织已经建设 GIS 平台，就认为已经具备完整的数据治理底座。

第069问讨论了数据治理底座需要的空间 SQL、Python、工作流、格式、存储和计算能力。本问进一步回答：GIS 桌面制作的地图怎样管理，矢量与栅格瓦片是什么性质，传统 GIS 服务与现代 Web API 怎样选择，以及 GIS 平台能否承担数据治理底座的作用。

## 一、先用四个层次理解地图和 GIS 平台

地图相关成果容易被统称为“图层”或“地图服务”，但治理时需要区分四个层次：

| 层次 | 典型内容 | 治理重点 |
| --- | --- | --- |
| 来源数据 | 矢量、栅格、业务属性和统计数据 | 权威来源、质量、版本、权限和责任 |
| 地图定义 | 地图工程、图层组合、过滤、样式、标注和版式 | 数据引用、配置版本、软件环境和审核 |
| 发布成果 | 地图、图集、PDF、图片、矢量瓦片和栅格瓦片 | 生成过程、适用范围、表现质量和有效版本 |
| 服务与应用 | 要素服务、地图服务、瓦片服务和业务地图应用 | 鉴权、服务版本、监控、审计和生命周期 |

GIS 平台可能参与这四个层次，却不意味着四者是同一个对象。来源数据发生变化，地图和服务不一定已经同步更新；地图显示正确，也不证明来源数据本身没有质量问题。

## 二、地图与来源数据有什么区别

地图不是把数据原样放到屏幕上。制作一张地图通常需要：

- 选择哪些数据参与表达；
- 按空间范围、时间和属性过滤数据；
- 确定地图投影、比例尺和显示层级；
- 对数据进行分类和符号化；
- 设置颜色、线型、透明度和图层顺序；
- 配置名称、数值和其他标注；
- 处理注记避让和重要对象突出；
- 增加图例、比例尺、指北针和说明；
- 根据使用对象决定保留或隐藏哪些信息。

同一份数据可以形成多张用途不同的地图。例如，同一组道路数据可以用于交通运行图、应急疏散图和设施维护图。来源数据相同，地图选择的字段、分类规则、颜色和重点却不同。

因此，地图应被看作基于数据形成的表达产品。地图不能代替完整来源数据，来源数据也不能自动解释地图所表达的业务结论。

## 三、GIS 桌面形成的地图工程是什么

GIS 桌面软件通常会保存一个地图工程，其中可能包含：

- 数据源、图层和表的引用；
- 图层顺序和可见范围；
- 查询、过滤和关联条件；
- 符号、颜色、标注和注记；
- 坐标参考系和地图范围；
- 图例、页面和制图版式；
- 字体、图标、图片和其他外部资源；
- 脚本、模型或专业工具配置。

地图工程不只是普通文档，也不一定包含它所引用的全部数据。它更像一份“地图生产配方”：说明哪些数据按照什么规则组合和表达，最终怎样生成地图。

这与 Notebook 和工作流有一定相似之处。地图工程本身不一定保存大量数据，却决定了输出结果；软件版本、数据引用或样式变化，都可能让同一工程产生不同地图。

## 四、治理平台不能预览和编辑地图工程，是否还能管理

可以。数据治理并不要求所有专业文件都必须在浏览器中直接打开和编辑。

即使治理平台暂时不能理解地图工程内部结构，也可以先完成文件级治理：

- 保存原始文件和校验值；
- 记录格式、GIS 软件和版本；
- 管理作者、责任单位、权限和审核状态；
- 记录形成时间、适用范围和有效期；
- 登记主要来源数据及其版本；
- 保存预览图片、PDF 或正式输出成果；
- 记录地图工程、来源数据和发布成果之间的关系。

这与第052问中“暂时按原格式管理”的原则一致：不能在线解析，不等于无法治理。

## 五、地图工程可以怎样查看和编辑

根据集成程度，可以采用以下方式：

### 1. 使用原 GIS 桌面软件

用户从治理平台取得经过授权的地图工程，在原专业软件中打开和编辑，完成后再登记新版本和成果。这是最简单的方式。

### 2. 提供预览成果

在保存或发布地图工程时，同时生成缩略图、图片或 PDF。普通用户可以在平台中理解地图内容，专业人员仍然使用 GIS 桌面继续编辑。

### 3. 在 GIS 桌面中安装治理插件

插件可以帮助用户登录治理服务、查询目录、取得授权数据、登记地图版本和回传成果。地图编辑仍由成熟 GIS 桌面完成，治理能力嵌入专业人员原有工作环境。

### 4. 提供平台桌面客户端

当确实需要本地文件、本地算力、专用 SDK 或统一离线能力时，可以由平台桌面客户端集成 GIS 引擎。第068问已经讨论了这种形态的适用边界。

治理平台不应仅仅为了在线编辑某一种地图工程，就重建一套完整 GIS 桌面软件。应根据使用人数、专业复杂度和集成价值选择合适方式。

## 六、地图工程中有哪些容易忽视的风险

地图工程可能包含：

- 只能在制作者电脑上成立的本地绝对路径；
- 已经失效的网络共享目录；
- 没有稳定身份的数据表和图层；
- 数据库地址、用户名甚至敏感凭据；
- 其他终端没有安装的字体和符号；
- 特定软件版本才能识别的样式或扩展；
- 未经登记的脚本和外部程序；
- 已经更新却没有重新确认的来源数据。

治理时应尽量使用稳定的数据引用，不把长期账号密码直接保存在地图工程中，并记录字体、图标、程序库和软件版本等必要依赖。

如果地图工程只能在某位制作者的电脑上正确打开，它虽然已经被保存，却还没有成为可持续复用的组织成果。

## 七、栅格瓦片应怎样看待

栅格瓦片是把已经渲染好的地图切分为不同层级和行列的小图片，适合快速在线浏览。它的优势是：

- 不同终端看到的颜色、符号和标注相对一致；
- 浏览器只需取得当前范围和层级的图片；
- 适合在对象存储和内容分发网络中保存；
- 客户端不需要理解复杂制图规则；
- 可以承载专业制图软件已经渲染好的效果。

栅格瓦片可以被数据治理底座作为一套数据集或地图产品管理，但不应把每一张小图片登记为独立资产。

一套瓦片需要记录：

- 来源数据和版本；
- 地图工程或样式版本；
- 坐标参考系和瓦片矩阵；
- 空间范围和最小、最大层级；
- 图片格式和生成时间；
- 生成任务和质量检查；
- 对应的地图服务；
- 缓存刷新和失效规则。

栅格瓦片是派生缓存，不是权威来源数据。它已经固定了显示效果和分辨率，也不能替代对象级查询、编辑和高精度空间计算。

## 八、为什么通用 Web 地图常采用矢量瓦片加前端样式

矢量瓦片把经过分块、裁剪和简化的空间对象及必要属性发送给客户端，再由前端根据样式配置进行绘制。

这种方式比较适合通用交互地图，因为：

- 同一套瓦片可以使用不同颜色和样式；
- 可以按照缩放层级动态调整显示内容；
- 用户可以点击和识别地图对象；
- 地图旋转、倾斜和动态高亮更加灵活；
- 样式可以独立修改和发布；
- 矢量内容在不同缩放下通常更加清晰。

治理时需要把矢量瓦片和样式配置分别管理，同时记录二者的版本绑定关系。样式使用的字体、图标集合和其他外部资源，也应纳入依赖管理。

矢量瓦片同样不是完整来源数据。为了传输和显示，它可能已经：

- 简化了几何；
- 裁剪到瓦片边界；
- 删除了不用于展示的字段；
- 按层级过滤了部分对象；
- 将多个来源图层组织成发布结构。

因此，矢量瓦片适合浏览和交互，不应默认用于权威数据交换、精细编辑或高精度分析。

## 九、专业级地图是否应该采用栅格瓦片

对于要求符号、注记、压盖关系和制图效果严格一致的在线专业地图，可以由服务端统一渲染，再通过地图图片或栅格瓦片发布。这样能够减少不同客户端字体、样式解释和渲染能力造成的差异。

但是，专业地图不能只剩下一套栅格瓦片。正式成果还可能包括：

- 权威矢量和栅格来源数据；
- 地图工程和标准图式；
- 专业符号、注记和制图编辑成果；
- 高分辨率地图图片；
- PDF 或其他正式出版成果；
- 面向在线浏览的栅格瓦片。

可以按照用途选择：

| 使用场景 | 更适合的表达 |
| --- | --- |
| 通用交互式 Web 地图 | 矢量瓦片加前端样式 |
| 要求效果严格一致的在线专业地图 | 服务端渲染的地图或栅格瓦片 |
| 正式制图、印刷和归档 | 地图工程加 PDF、图片或其他正式成果 |
| 空间查询和计算 | 权威矢量、栅格数据或数据服务 |
| 后续专业编辑 | 原始数据和地图工程 |

选择栅格还是矢量瓦片，首先取决于地图用途，而不是简单判断哪一种技术更加先进。

## 十、地图产品应作为一组关联成果治理

一张正式地图通常不是一个孤立文件，而是一组相互关联的成果：

```text
权威来源数据
      ↓
地图工程、过滤规则、样式和标注
      ↓
PDF、图片、矢量瓦片或栅格瓦片
      ↓
地图服务和业务应用
```

治理平台可以把它们组织成一个地图产品，或者通过稳定关系连接起来。关键是能够回答：

- 这张地图依据什么数据形成；
- 使用了哪个时间和空间范围；
- 采用哪个地图工程和样式版本；
- 是否经过专业审核；
- 哪些发布成果和服务来自它；
- 来源数据变化后，哪些地图和服务需要更新；
- 哪个成果具有正式效力。

统一治理不要求把所有对象物理打包成一个文件，而是要求它们不再成为互相无法解释的孤立资源。

## 十一、GIS 服务可以分成哪些类型

不同 GIS 服务解决的问题不同，不能都笼统称为“地图服务”。

| 服务类型 | 主要用途 | 用户得到什么 |
| --- | --- | --- |
| 要素或数据访问服务 | 查询、筛选或编辑空间对象 | 几何和属性数据 |
| 地图服务 | 按范围和样式生成地图 | 已渲染的地图图片 |
| 瓦片服务 | 快速分发分块空间内容 | 栅格或矢量瓦片 |
| 覆盖数据服务 | 访问影像、栅格和连续空间数据 | 覆盖数据及其子集 |
| 空间处理服务 | 调用叠加、转换和专业算法 | 计算状态或结果 |
| 元数据发现服务 | 查询空间数据、地图和服务说明 | 资源及其元数据 |

地图图片适合查看，却不能代替要素数据；矢量瓦片适合交互，却不一定保留完整精度和字段；处理服务能够调用算法，却不一定提供来源数据本身。

发布服务时，应先明确用户需要浏览、查询、下载、编辑还是调用计算，再选择合适的服务类型。

## 十二、OGC API 与传统 WMS、WFS 应怎样选择

较新的 OGC API 系列采用更符合现代 Web 开发习惯的资源化接口，并可以使用 OpenAPI、JSON、HTML 等常见技术表达空间数据、地图、瓦片、覆盖数据、处理过程和元数据。对于新建系统，它通常更容易与 API 网关、开发者门户和普通 Web 应用衔接。

但是，不能由此得出 WMS、WFS 已经不适合数据治理的结论。

### 1. WMS 适合地图展示

WMS 主要返回已经渲染的地图图片。它适合跨系统叠加和展示，不适合代替原始空间数据查询。

### 2. WFS 仍然是数据访问方式

WFS 可以提供要素级查询，部分实现还支持编辑。它的接口和数据表达对普通 Web 开发人员可能不如现代 API 直观，但已有系统和专业软件仍可能大量使用。

### 3. OGC API 更适合新建的现代接口

要素、地图、瓦片、覆盖数据和空间处理可以按照不同资源组织，并与通用 API 管理方式衔接。新系统可以优先评估相应的 OGC API 标准。

因此，较合理的策略是：新建服务优先考虑现代接口，已有 WMS、WFS 根据使用范围、客户端依赖和改造价值继续治理或逐步演进，而不是仅为了名称和形式统一全部重建。

## 十三、符合 OGC 标准是否就完成了服务治理

没有。OGC 标准主要解决不同系统怎样交换和使用空间信息，数据治理还要解决服务由谁提供、依据什么数据、允许谁使用以及怎样持续运营。

无论采用 OGC API、WMS、WFS 还是其他接口，都需要管理：

- 服务名称、业务说明和责任主体；
- 来源数据、地图工程、样式和版本；
- 用户和应用鉴权；
- 数据分类分级和允许用途；
- 服务申请、审批和授权期限；
- 调用频率、配额和服务水平；
- 数据质量、空间范围和精度说明；
- 服务上线、变更、下线和废弃；
- 调用日志、异常监控和审计；
- 服务与数据、任务和应用之间的血缘。

接口符合标准，说明它具有一定互操作性；是否可信、可控和可持续使用，仍取决于完整的服务治理。

## 十四、GIS 服务必须绑定明确的数据和样式版本

一个长期不变的服务地址，背后引用的数据、地图和样式仍可能不断变化。仅登记访问地址，无法解释用户在某个时间看到的内容。

治理体系需要记录：

- 服务当前引用哪个数据版本；
- 使用哪个地图工程或样式版本；
- 空间范围、比例尺和精度是否变化；
- 数据更新后服务是否同步发布；
- 栅格和矢量瓦片是否需要重新生成；
- 旧缓存何时失效；
- 接口或字段结构是否发生变化；
- 哪些客户端和业务应用会受到影响。

对于正式地图和关键业务服务，还需要能够回溯某个历史时间对外提供的版本。

来源数据更新并不意味着所有服务都应立即“一动皆动”。平台应根据依赖关系、业务时效、质量验证和发布规则，决定自动更新、审核后更新还是保持既有正式版本。

## 十五、地图表达本身也需要质量和安全治理

地图来源数据正确，不代表地图表达一定正确。还可能出现：

- 分类区间和颜色含义设置错误；
- 重要对象被其他图层遮挡；
- 标注错位、重叠或遗漏；
- 比例尺不适合表达数据精度；
- 坐标或投影选择造成明显变形；
- 图例、单位和时间说明不完整；
- 瓦片未更新，仍然展示旧数据；
- 客户端样式版本不一致；
- 对敏感位置显示了过高精度；
- 地图图片间接暴露了受限信息。

正式地图需要检查内容、制图表达、时间版本和使用边界。矢量瓦片由前端渲染时，还要验证支持的客户端是否能够一致解释样式；对具有正式效力的地图，可以固定样式和渲染环境，或者使用经过审核的服务端渲染成果。

## 十六、GIS 门户与数据资产门户有什么区别

GIS 门户通常围绕地图、图层、空间服务和地图应用组织内容，便于用户浏览地图、组合图层和创建空间应用。

数据资产门户则面向更广泛的数据消费者，除了空间资源，还可能包括：

- 数据库表和文件数据集；
- 指标、标签和实体画像；
- 文档、图片和音视频；
- 数据服务和算法模型；
- 数据产品及其申请、授权和评价。

GIS 门户可以成为数据资产门户中的空间资源入口，也可以保持独立专业界面并与统一目录连接。两者不必强行合并，但同一空间数据、地图和服务不应在两个门户中形成无法对应的重复身份。

第044问已经讨论了资产管理后台与资产门户的分工。GIS 门户更接近面向空间资源的专业使用入口，不能自动替代资产管理、审核和持续运营能力。

## 十七、GIS 平台能够承担哪些治理工作

成熟 GIS 平台通常能够提供：

- 空间数据库和文件管理；
- 空间数据编辑和版本生产；
- 坐标、格式和空间分析；
- 地图工程和制图；
- 地图、要素和瓦片服务发布；
- GIS 用户、资源和应用管理；
- 面向空间资源的目录和门户；
- GIS 应用开发能力。

因此，GIS 平台完全可以承担空间数据治理的重要组成部分。已有成熟平台时，数据治理底座应尽量连接它的目录、身份、数据、任务和服务，而不是重新建设低水平的替代能力。

## 十八、GIS 平台能否直接成为数据治理底座

需要根据治理范围判断。

如果一个组织规模较小，核心数据几乎都是空间数据，主要需求集中在空间数据生产、地图服务和 GIS 应用，已有 GIS 平台可能成为治理建设的起点。

但是，面向全域数据的数据治理底座通常还需要覆盖：

- 普通业务数据库、数据仓库和数据湖；
- 文档、图片、音视频和实时流；
- 业务术语、数据标准和指标口径；
- 跨系统元数据和企业数据目录；
- 通用质量规则和问题整改闭环；
- SQL、Notebook、可视化工作流和任务调度；
- 数据模型、指标、标签和数据产品；
- 跨引擎血缘、权限和运行监控；
- 资产编目、申请、授权、评价和运营。

传统 GIS 平台往往以图层、地图、服务和空间应用为核心。如果直接把它称为全域数据治理底座，容易把所有业务数据都按照 GIS 的资源方式组织，而忽略业务实体、指标、文档、流数据和其他专业引擎。

因此，判断标准不是产品是否叫“GIS 平台”，而是它是否真正覆盖组织需要的治理范围，并能与其他数据和计算体系协同。

## 十九、GIS 平台与数据治理底座怎样协同

一种较清晰的分工是：

```text
数据治理底座
  ├── 统一身份、目录、语义、权限、质量、任务和血缘
  ├── 汇聚、SQL、Notebook、工作流和数据服务治理
  └── 连接 GIS 平台
        ├── 空间数据生产和专业编辑
        ├── 地图工程和专业制图
        ├── 空间分析与计算
        ├── 地图、要素和瓦片服务
        └── GIS 门户和空间应用
```

这里的“连接”不是简单增加一个菜单链接，而是尽量贯通：

- 用户和组织身份；
- 数据和服务的稳定标识；
- 目录和业务元数据；
- 数据授权和使用范围；
- 地图、服务与来源数据的关系；
- 任务状态、日志和计算结果；
- 质量、版本和发布状态；
- 重要操作和服务调用审计。

统一治理不等于统一界面，也不要求取消 GIS 平台自己的专业目录和门户。关键是同一资源在不同入口中仍然能够被识别、控制和追溯。

## 二十、案例：国土空间规划成果的地图发布

某管理机构需要发布国土空间规划成果，既供专业人员核查，也供普通用户浏览。

治理过程可以这样组织：

1. 规划范围、用途分区、控制线和行政区等权威数据具有明确来源、版本和审核状态；
2. 专业人员在 GIS 桌面中制作地图工程，配置标准图式、注记、图例和版式；
3. 地图工程作为专用文档登记，并关联使用的数据和软件版本；
4. 面向普通交互浏览的内容生成矢量瓦片，并绑定经过审核的前端样式；
5. 对要求显示效果严格一致的专业地图，由服务端统一渲染并生成栅格瓦片；
6. 正式成果同时保留地图工程、PDF、必要图片和权威来源数据；
7. 要素查询、地图浏览和瓦片分发采用适合的服务类型，并纳入统一鉴权和审计；
8. 来源数据更新后，根据依赖关系判断哪些地图和服务需要重新生成；
9. 新版本通过质量检查和专业审核后正式发布，旧版本按照保留要求归档或下线。

这样，专业制图、通用浏览和数据查询可以使用不同技术形式，但它们仍然属于同一套受治理的规划成果。

## 二十一、常见误区

### 误区一：地图就是来源数据

地图是选择、过滤、符号化和版式处理后的表达产品，不能代替完整权威数据。

### 误区二：地图工程不能在浏览器中编辑，就无法治理

可以先进行文件、版本、权限、预览、依赖和血缘管理，专业编辑继续使用原 GIS 桌面。

### 误区三：栅格瓦片是正式空间数据的唯一保存形式

栅格瓦片适合浏览，却不能替代来源数据、地图工程和正式出版成果。

### 误区四：矢量瓦片就是完整矢量数据

矢量瓦片可能经过裁剪、简化和字段筛选，通常不适合权威交换和高精度计算。

### 误区五：矢量瓦片一定比栅格瓦片先进

矢量瓦片更灵活，栅格瓦片更容易保证显示一致。应根据交互、专业制图和发布要求选择。

### 误区六：符合 OGC 标准就已经完成服务治理

互操作标准不能替代权限、版本、质量、申请、审计和生命周期管理。

### 误区七：WMS、WFS 已经过时，必须全部替换

已有服务仍有明确用途，应根据客户端依赖和改造价值逐步演进。

### 误区八：GIS 平台已有图层目录，就等于企业数据目录

图层目录主要组织空间资源，企业目录还要连接业务实体、指标、文档、服务和其他数据类型。

### 误区九：统一治理要求所有地图和服务只能从一个门户进入

专业门户可以保留，关键是身份、目录、权限、版本和血缘能够贯通。

### 误区十：建设 GIS 平台以后，不再需要数据治理底座

GIS 平台能够承担空间专业工作，但通常不能自动覆盖全域数据和完整治理过程。

## 二十二、规划地图和 GIS 服务治理时应回答哪些问题

1. 哪些是权威来源数据，哪些是地图和派生发布成果？
2. 地图工程由什么软件和版本创建，怎样打开和继续编辑？
3. 地图工程引用的数据、字体、符号和外部资源是否完整？
4. 哪些地图适合矢量瓦片，哪些需要服务端渲染和栅格瓦片？
5. 瓦片、样式和来源数据的版本怎样绑定？
6. 用户需要地图浏览、数据查询、数据编辑还是空间计算服务？
7. 新建服务是否适合采用相应的 OGC API，已有 WMS、WFS 是否确有改造价值？
8. GIS 服务怎样进行用户与应用鉴权、监控和审计？
9. 来源数据变化后，地图、缓存和服务怎样更新？
10. GIS 门户与企业数据目录、资产门户怎样对应？
11. 已有 GIS 平台能够承担哪些专业工作，缺少哪些全域治理能力？
12. 地图、服务和应用怎样与来源数据、任务和责任主体建立血缘？

只有这些问题得到回答，地图和 GIS 服务才不只是“能够发布”，而是成为可信、可控、可以持续运营的数据产品。

## 小结

地图是空间数据经过选择、组织和表达形成的产品。地图工程是专业生产配置，矢量瓦片和栅格瓦片是面向不同用途的派生发布成果，GIS 服务则提供浏览、查询、下载、编辑或计算入口。它们都需要与来源数据建立明确的版本和血缘关系。

GIS 平台能够承担空间数据生产、专业编辑、制图、分析和服务发布，是数据治理体系的重要专业组成部分；但除非治理范围主要局限于空间数据，并且平台已经补齐全域目录、语义、质量、开发、权限、血缘和资产运营能力，否则不宜直接把 GIS 平台等同于数据治理底座。

统一治理不要求所有工作都在一个界面完成。真正需要统一的，是数据、地图、样式、服务和应用之间的身份、权限、版本、质量、责任和追溯关系。
