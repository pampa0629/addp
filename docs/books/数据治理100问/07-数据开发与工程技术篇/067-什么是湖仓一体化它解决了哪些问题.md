# 067 什么是湖仓一体化，它解决了哪些问题？

## 一句话回答

> 湖仓一体化的经典含义，是在数据湖的共享数据基础上补充可靠表管理、事务一致性、结构约束、版本管理和高性能分析等数据仓库能力，让数据工程、算法和 BI 分析尽量使用同一套数据。它不是简单的“数据湖加数据仓库”，也不一定比湖仓分立更适合所有企业。

第066问介绍了数据湖与数据仓库的典型分工：湖更适合灵活保存多类型数据和来源细节，仓更适合形成稳定的事实、指标和分析服务。湖仓一体化试图减少两套体系之间的重复和割裂，但也会引入新的工程与运营要求。

## 一、传统“湖+仓”为什么会出现

当企业既要保存日志、文件、图片、音视频等多类型数据，又要为指标、报表和自助分析提供稳定的结构化数据时，常见做法是同时建设数据湖和数据仓库：

```text
业务系统、文件、日志和多媒体数据
                ↓
              数据湖
                ↓ 再次复制、转换和装载
          独立数据仓库
                ↓
        指标、报表和数据服务
```

在这种结构中，湖负责接纳和保留广泛的数据，仓负责稳定的数据建模和分析服务。两者职责清楚，但湖到仓之间形成了新的数据搬运与同步链路。

随着数据规模和使用场景增加，可能出现：

- 同一数据在湖和仓中保存多份；
- 湖中数据已经更新，仓中结果仍然滞后；
- 算法和报表使用了不同的数据版本；
- 湖到仓的任务增加了失败点和维护成本；
- 湖和仓分别维护元数据、权限和质量规则；
- 新增使用场景时，又要设计新的复制和转换过程；
- 出现问题后，难以判断哪一份结果可以作为依据。

湖仓一体化首先要解决的，就是这些因湖与仓分离而产生的重复、延迟和不一致。

## 二、“湖+仓”为什么不等于湖仓一体

“湖+仓”表示企业同时拥有数据湖和数据仓库，两者通常通过数据复制和加工进行衔接：

```text
湖中保存来源数据
        ↓
复制到独立仓库
        ↓
仓库提供分析结果
```

经典的湖仓一体化则以湖中的共享数据为基础，在其上补充仓级的数据管理和查询能力：

```text
湖中共享的数据基础
        ↓
可靠表管理、版本、一致性和查询优化
        ↓
SQL、算法、批处理和其他分析共同使用
```

因此，同时采购或部署数据湖和数据仓库，只能说明湖仓并存。只有两者真正共享数据基础、管理规则和治理能力，减少了不必要的复制，才体现出“一体化”的含义。

## 三、湖仓一体有哪些不同理解

湖仓一体在行业中已经出现狭义和广义两种用法。

### 1. 狭义、经典的湖仓一体

以数据湖为基础，为湖中的数据增加可靠表管理、结构约束、数据版本、高性能 SQL 查询和统一治理，使其能够承担过去主要由数据仓库完成的部分或大部分工作。

本问主要采用这一含义，也就是“在湖上补齐仓能力”。

### 2. 广义的湖仓一体

有些架构并不取消独立数据仓库，而是通过统一目录、权限和查询入口，把数据湖、数据仓库以及其他数据源连接起来。数据仍然位于不同系统，但使用者可以统一发现和访问。

这种方式能够降低访问割裂，却不一定减少物理数据复制。如果湖和仓仍然分别保存、分别治理，它更接近湖仓协同或联邦访问。

讨论具体方案时，应先说明使用的是哪种含义，不能只根据产品名称判断是否已经实现湖仓一体。

## 四、在数据湖上需要补充哪些仓能力

对象存储中的文件能够被查询，不代表已经具备数据仓库能力。要让湖中数据稳定承担分析和交付任务，通常还需要：

### 1. 可靠的表和结构管理

明确数据表、字段类型、分区和结构版本，防止不符合要求的数据在没有提示的情况下破坏下游任务。

### 2. 一致的数据写入和更新

一次写入、更新或删除要么完整成功，要么不对外生效。下游不能读到“一半新、一半旧”的结果。

### 3. 并发读写协调

多个任务同时读取或修改数据时，需要避免相互覆盖、读取中间状态或产生无法解释的结果。

### 4. 数据版本和历史回溯

记录数据在不同时间的有效版本，支持核查变化、查询历史状态和在必要时恢复或重算。

### 5. 查询和性能优化

管理分区、文件布局、统计信息和常用计算结果，减少不必要的数据扫描，为稳定的 SQL 分析提供性能保障。

### 6. 数据发布与服务管理

区分原始、加工、验证和正式发布的数据，明确哪些数据可以用于探索，哪些可以用于正式指标和业务服务。

### 7. 统一治理

统一管理元数据、目录、权限、质量、血缘、生命周期和审计，使不同计算方式遵循相同的数据边界。

湖仓一体不是在对象存储上简单增加一个查询入口，而是让湖中数据从普通文件提升为可靠、受管理、能够持续交付的数据集合。

## 五、湖仓一体的价值不只是一份存储

### 1. 减少不必要的数据复制

算法、SQL 分析和数据加工可以围绕共享数据基础工作，减少为了使用不同工具而反复搬运全量数据。

### 2. 提高数据鲜活度

数据进入统一基础并完成必要处理后，可以更快被不同场景使用，不必总是等待湖到仓的下一次同步。

### 3. 保持数据版本一致

算法训练、历史分析和管理报表可以明确使用同一个数据版本，减少“模型看到的数据”和“报表看到的数据”不一致。

### 4. 减少加工链路和故障点

少一次不必要的数据复制，就少一组任务、存储副本、同步延迟和失败风险。

### 5. 支持历史查询和恢复

通过数据版本和快照，可以核查某次计算使用的数据状态，并在规则出错后重新处理受影响的数据。

### 6. 支持多种计算方式

SQL 查询、批量处理、流处理、算法和模型任务可以使用适合的计算引擎，同时访问受统一管理的数据。

### 7. 统一治理边界

数据不再因为分别位于湖和仓中，就需要维护两套相互脱节的目录、权限、质量和血缘信息。

### 8. 扩大数据使用范围

来源数据可以逐步加工为可信数据，同一数据基础既支持探索和算法，也能支持稳定的指标和服务。

## 六、湖仓一体是否意味着只有一份物理数据

不应绝对承诺“全系统只有一份数据”。湖仓一体更合理的目标是：以一套共享数据基础为主，减少没有必要、无法追踪和容易失去同步的数据复制。

现实中仍可能因为以下原因产生副本：

- 查询缓存和性能加速；
- 面向报表的预聚合或物化结果；
- 跨地区或跨安全域隔离；
- 备份和灾难恢复；
- 外部交换和数据发布；
- 不同保留周期与成本分层。

每一份必要副本仍应记录来源、版本、用途、更新规则和生命周期。不能为了宣传“一份存储”而隐藏真实存在的数据复制，也不能因为存在缓存或备份就认为一体化完全失败。

## 七、基于湖的仓能力与独立数据仓库有什么差异

不宜把独立数据仓库称为“真正的数据仓库”，因为现代数据仓库也可能采用存储与计算分离，并把数据保存在云端分布式存储中。两者的差异更多体现在数据访问、管理完整度、工作负载和运营方式上。

| 维度 | 基于湖构建的仓能力 | 成熟独立数据仓库 |
| --- | --- | --- |
| 数据基础 | 通常基于可直接访问的文件和湖中表 | 通常由仓库系统统一管理和优化 |
| 数据类型 | 更容易同时覆盖表、文件和多类型数据 | 主要面向结构化和半结构化分析数据 |
| SQL 能力 | 完整性取决于表管理和查询引擎 | 通常具有成熟、完整的 SQL 能力 |
| 更新与并发 | 可以提供可靠能力，但不同实现差异较大 | 通常是原生、稳定的核心能力 |
| BI 查询性能 | 依赖文件布局、统计信息、缓存和引擎 | 通常针对高并发分析长期优化 |
| 算法与多引擎 | 直接访问和扩展通常更加灵活 | 主要围绕仓库接口和受支持能力 |
| 运维方式 | 需要协调存储、表管理、目录和引擎 | 托管仓库通常封装了更多维护工作 |
| 使用体验 | 数据工程和算法人员通常更灵活 | SQL 和 BI 人员通常获得更成熟的体验 |

这些是典型差异，不代表所有湖仓平台的性能都低于独立数据仓库，也不代表所有仓库都缺少算法和多类型数据能力。判断时应比较实际功能、服务水平和总体成本，而不是只比较架构名称。

## 八、湖仓一体会带来哪些新负担

在湖上补充仓能力，会把部分复杂度从“湖到仓的数据复制”转移到“湖表、目录、引擎和性能维护”。常见工作包括：

- 选择并维护表、结构和版本管理方式；
- 管理多个任务的并发写入和数据一致性；
- 定期合并大量小文件；
- 清理过期快照、无效文件和多余元数据；
- 优化分区、文件布局和查询统计信息；
- 保证多种计算引擎支持相同的数据功能；
- 验证不同引擎的 SQL 和结果语义；
- 在多种访问方式下统一权限与审计；
- 为高并发 BI 增加缓存、预计算或物化结果；
- 迁移原有仓库模型、任务和使用工具；
- 培训开发和运维人员处理新的故障类型。

开放格式降低了数据被封闭在单一系统中的风险，却不能自动消除工具依赖和兼容问题。不同引擎对同一种表管理能力的支持范围、版本和语义仍可能不同。

如果企业缺少持续维护这些能力的团队，湖仓一体的实际复杂度可能高于一套成熟的数据仓库。

## 九、哪些情况下“湖+仓”反而更合适

湖+仓不是落后架构。如果职责清楚、同步稳定且成本可控，它可能比湖仓一体更加简单可靠。

适合继续使用湖+仓的情况包括：

- 湖主要保存原始文件、多媒体和低频历史数据；
- 仓主要承担稳定指标、报表和高并发 BI；
- 湖到仓按小时或按天更新已经满足业务需要；
- 数据复制成本和同步延迟可以接受；
- 现有数据仓库已经成熟稳定；
- 算法和报表本来就使用不同的数据层次；
- 团队没有维护湖表和多引擎一致性的能力。

这时如果为了采用“更先进”的名称而改造，可能增加：

- 新的数据表和目录体系选型；
- 原有仓库模型与任务迁移；
- 多引擎兼容和权限统一；
- 文件、快照和元数据维护；
- 为达到仓库性能新增的缓存和物化结果；
- 新旧系统并行期间的数据核对；
- 开发、运维和使用人员的学习成本。

如果湖到仓的数据延迟不是业务问题，数据副本也没有造成明显成本和口径混乱，湖仓一体可能是在用更复杂的技术解决一个并不存在的问题。

## 十、哪些情况下值得考虑湖仓一体

- 湖和仓之间的复制量、同步成本已经很高；
- 数据延迟影响了业务决策和服务；
- 算法与 BI 经常使用不同的数据版本；
- 多类型数据、算法分析和 SQL 分析需要紧密协同；
- 多种计算引擎需要共享大量数据；
- 需要对历史数据统一核查、重算和回溯；
- 现有数据湖需要更可靠的表管理和查询能力；
- 团队具备维护统一数据基础的工程能力；
- 带来的收益能够覆盖迁移和长期运营成本。

湖仓一体是否值得建设，不能只看技术是否可行，还要看当前湖仓分离究竟造成了多大问题。

## 十一、湖仓一体与其他“一体化”有什么区别

| 概念 | 主要解决的问题 |
| --- | --- |
| 湖仓一体 | 数据湖与数据仓库怎样共享数据基础和数据管理能力 |
| 流批一体 | 实时流处理与周期批处理怎样共享规则并保持结果一致 |
| 多计算引擎 | 不同计算任务怎样使用适合的引擎并统一管理 |
| 数据治理 | 怎样统一业务语义、质量、责任、安全和价值要求 |

这些能力可以组合使用，但不能相互替代。湖仓一体可以为流处理和批处理提供共享数据基础，却不会自动统一两种计算的窗口和时间规则；多种引擎可以读取共享数据，也仍要验证各自的执行语义。

## 十二、湖仓一体解决不了哪些问题

湖仓一体能够减少技术割裂，却不能自动解决：

- 源系统数据错误；
- 业务术语和指标口径冲突；
- 主数据身份不一致；
- 数据责任人不明确；
- 敏感数据被不当使用；
- 数据开发逻辑本身错误；
- 数据没有真实业务用途；
- 部门之间不愿共享和协作。

统一技术基础不能让原始文件自动变成可信指标，也不能替代业务建模、质量整改和责任落实。

## 十三、案例：保险理赔数据的湖仓选择

某保险企业需要处理：

- 客户、保单、案件和赔付等结构化数据；
- 客户提交的图片、视频和证明文档；
- 呼叫中心录音与沟通记录；
- 维修机构提供的报价和维修资料；
- 风险识别模型使用的历史训练数据。

最初，企业把多媒体和来源数据保存在数据湖，把结构化数据和指标加工到独立数据仓库。风险模型主要使用湖中数据，经营报表主要使用仓中数据。

随着实时反欺诈和模型分析增加，团队发现：案件状态从湖同步到仓存在延迟，模型与报表使用的数据版本也经常不同。于是，企业考虑在湖中为案件、客户和赔付数据增加可靠表管理、版本和 SQL 查询能力，让算法、数据工程与部分分析场景共享明确版本的数据。

原始、标准化和可信业务数据仍然按照状态分层；面向高并发管理报表的必要汇总和缓存也仍然保留，但来源、版本和更新关系必须清楚。

企业并没有因为采用湖仓一体思路就立即取消原有仓库。对于已经稳定、同步要求不高的财务报表，继续由成熟仓库提供服务更加稳妥；对于算法和分析紧密协同、版本不一致问题突出的理赔风险场景，则逐步使用湖上的仓能力。

这个案例说明，湖仓一体可以按实际问题逐步采用，不需要把整个平台一次性推倒重建。

## 十四、常见误区

### 误区一：湖加仓就是湖仓一体

湖和仓分别保存数据并通过复制衔接，只是湖仓并存。经典湖仓一体是在共享数据基础上补齐仓能力。

### 误区二：对象存储加 SQL 查询就是湖仓一体

能够查询文件只是第一步，还需要可靠更新、结构和版本管理、性能优化及统一治理。

### 误区三：湖仓一体保证全系统只有一份数据

缓存、汇总、备份和安全隔离仍可能产生必要副本，关键是减少无必要和不可追踪的复制。

### 误区四：湖仓一体以后不再需要建模和分层

底层统一不能替代业务对象、事实、维度、指标、质量和发布状态的组织。

### 误区五：湖仓一体就是流批一体

前者主要统一数据基础和管理，后者主要统一实时与周期计算方式。

### 误区六：湖仓一体只允许一种计算引擎

统一数据基础可以被多种引擎使用，但需要控制权限、版本和语义差异。

### 误区七：湖仓平台一定比成熟仓库性能更好

性能取决于数据组织、查询引擎、并发管理和优化方式。成熟仓库在稳定 BI 场景中可能更有优势。

### 误区八：湖仓一体能够自动完成数据治理

它可以统一治理入口，却不能自动确定业务口径、数据责任和使用价值。

### 误区九：湖+仓已经过时

当数据同步满足业务要求、职责清楚且成本可控时，湖+仓仍然是合理选择。

### 误区十：产品名称中有“湖仓”就已经实现一体化

应检查是否真正共享数据基础、减少复制，并具备可靠表管理、多种计算和统一治理能力。

## 十五、实践检查清单

1. 当前采用的是湖+仓、湖上补仓能力，还是统一访问多个独立系统？
2. 湖与仓之间存在多少数据复制、同步延迟和失败任务？
3. 算法、报表和数据服务是否经常使用不同数据版本？
4. 湖中数据是否具备可靠的结构、更新、版本和并发管理？
5. SQL 分析能否达到实际需要的功能、性能和并发要求？
6. 多种计算引擎是否能够使用一致的数据结构和版本？
7. 元数据、权限、质量、血缘和生命周期是否统一管理？
8. 必要的数据副本是否记录来源、用途、更新规则和生命周期？
9. 是否建立小文件、快照、无效文件和元数据维护机制？
10. 现有成熟仓库解决了哪些湖上能力暂时无法替代的问题？
11. 采用湖+仓是否已经能够满足业务时效和成本要求？
12. 湖仓一体解决的是实际业务问题，还是只为了采用新技术名称？
13. 迁移成本、新旧并行和人员学习成本是否经过评估？
14. 是否可以从问题突出的场景逐步采用，而不是一次性重建全部平台？

## 小结

湖仓一体化的经典思路，是在数据湖的共享数据基础上补齐可靠表管理、结构约束、数据版本和高性能分析等数据仓库能力，而不是简单地同时建设湖和仓。

它的价值不只是减少存储副本，还包括提高数据鲜活度、保持版本一致、减少加工链路、支持历史回溯、多引擎共享和统一治理。但它也会增加湖表、目录、文件、快照、多引擎兼容和性能优化的维护负担。

对于已经拥有成熟仓库、湖到仓同步能够满足需求的企业，湖+仓仍然可能是更简单可靠的选择。是否采用湖仓一体，应由实际复制成本、数据延迟、算法与 BI 协同需求、团队能力和总体成本决定，而不是由技术先进性的宣传决定。
