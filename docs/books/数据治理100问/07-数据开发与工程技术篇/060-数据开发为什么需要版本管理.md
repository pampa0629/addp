# 060 数据开发为什么需要版本管理？

## 一句话回答

> 数据结果不只由一段代码决定，而是由代码、数据模型、指标口径、业务规则、参数、依赖环境和输入数据共同产生。版本管理是为了准确回答某次结果由哪一组定义产生，并在内容变化时支持比较、测试、发布、追溯、影响分析和恢复。

对于一次性的个人探索，也应尽量保留必要记录；只要开发成果需要多人协作、测试、复用、发布或持续运行，版本管理就不再是可选项。

## 一、什么是版本管理

版本管理不是在文件名后面加上“最终版”、“最终版2”，也不是只为当前内容标记一个版本号。它需要：

- 为每次有意义的变更建立可识别的版本；
- 保留变更前后的内容及其差异；
- 记录谁在什么时间、为什么进行了修改；
- 说明版本之间的继承、替代和分支关系；
- 标明哪个版本处于开发、测试、发布、生效或停用状态；
- 将每次运行与实际使用的版本关联起来。

版本标识可以是递增序号、发布时间、代码提交标识、内容指纹或其他能够唯一定位内容的值。不必强制 SQL、工作流、数据模型和指标全部采用相同的版本号规则。比编号形式更重要的是，版本必须唯一、不可混淆并且能够追溯。

## 二、为什么只保存“当前版”不够

如果数据开发只保留最新内容，每次修改都覆盖旧内容，就会产生一系列问题：

- 无法解释历史数据当时按什么逻辑生成；
- 多人修改时容易相互覆盖，也无法可靠合并；
- 发布失败后，找不到上一个经过验证的稳定版本；
- 指标口径变化后，无法比较新旧结果的差异来源；
- 算子升级后，不知道影响了哪些工作流和输出；
- Notebook 中保留的实验结果无法按原方法重现；
- 发生质量问题时，无法判断问题从哪一版开始；
- 重算历史数据时，无法决定应采用当时口径还是当前口径。

版本管理的价值因此不只是防止文件丢失，而是维持数据结果的可解释性、可比较性和可信度。

## 三、哪些内容需要版本管理

数据开发版本不能只包括代码。需要管理的内容可以从四类理解：

| 类型 | 需要管理的内容 |
| --- | --- |
| 开发成果 | SQL、脚本、Notebook、算子、工作流和测试 |
| 业务与数据定义 | 数据模型、字段映射、指标口径、质量规则和标签规则 |
| 运行基础 | 参数定义、固定参数配置、程序库、容器、算法模型和其他依赖 |
| 输入与结果 | 输入数据批次、快照或表版本，输出数据批次及运行记录 |

这些内容不一定使用同一种版本工具。代码可以使用代码仓库，工作流可以使用平台版本，算法模型可以有模型版本，数据则可以通过批次、分区、快照或时间点识别。关键是这些版本能够在某次运行中被准确关联起来。

## 四、版本、运行实例、数据批次和状态有什么不同

这几个概念经常同时出现，但它们回答的问题不同。

| 概念 | 回答的问题 | 例子 |
| --- | --- | --- |
| 版本 | 这项定义或成果具体是什么内容 | 工作流v3、指标口径v2 |
| 运行实例 | 哪个版本在什么条件下执行了一次 | 9月1日的日指标计算 |
| 数据批次 | 本次输入或输出数据属于什么范围 | 2026年9月1日业务批次 |
| 生命周期状态 | 这个版本当前处于什么阶段 | 草稿、测试中、已上线、已下线 |

例如，同一版本的日指标任务连续运行30天，会产生30个运行实例和30个输出批次，而不是30个代码版本。

参数定义与运行参数值也应该区分。参数的名称、类型、合法范围或含义改变时，应形成新的参数定义版本；每天运行时传入不同业务日期，只需记录实际参数值，不意味着每天创建一个参数定义版本。

## 五、不同数据开发成果如何管理版本

### 1. SQL 与脚本

除了代码内容，还应关联依赖的数据模型、参数定义、测试和发布记录。只保存一份 SQL 文件，却不知道它针对哪一版表结构和指标口径，仍然无法可靠使用。

### 2. Notebook

Notebook 需要管理代码单元、说明、必要输出、执行环境和依赖。Notebook 中经过验证的逻辑被提取为函数、程序包、算子或正式任务后，还应记录探索版本与生产实现版本之间的关系。

### 3. 算子

算子版本不只包括内部代码，还包括输入输出契约、参数定义、程序库、容器、算法或模型等运行依赖。即使输入输出字段不变，算法结果语义发生变化时，也应建立新版本并说明影响。

### 4. 可视化工作流

工作流版本应包括节点拓扑、实际使用的算子版本、参数映射、输入输出和发布状态。如果一个已发布工作流始终引用“最新版算子”，算子升级后，工作流自身没有变化却可能生成不同结果。正式发布的工作流应能够确定实际使用的算子版本。

## 六、数据模型、指标和规则为什么也要有版本

数据模型可能发生的变化包括：

- 实体、事实表或数据集的粒度改变；
- 主键、关联关系或历史处理方式改变；
- 字段增加、删除、改名或业务含义改变；
- 源数据到目标模型的映射变化；
- 数据分层、分区或存储方式的调整。

指标、标签和质量规则可能发生的变化包括：

- 统计对象、数据粒度或适用范围改变；
- 分子、分母、聚合方式或判定逻辑改变；
- 统计时间字段、时间窗口或时区口径改变；
- 过滤、排除条件、阈值或参考规则改变；
- 允许使用的维度和展示方式改变。

这些变化不能只体现为一段 SQL 被修改。技术实现变化但业务含义不变时，可以升级代码或任务版本，同时保持原有指标定义版本；业务口径发生变化时，即使只改了一个数字或条件，也应建立新的业务定义版本。

## 七、参数、运行环境和数据如何进入版本链

第059问已经区分参数定义、参数配置和每次运行的实际参数值。参数的名称、类型、默认值、合法范围和业务含义需要版本；固定配置改变时需要保留配置版本；每次实际参数值则应进入运行记录。

编程语言、程序库、数据库驱动、计算引擎、容器、操作系统、算法模型和硬件环境变化，都可能影响任务能否运行或结果是否一致。因此，关键依赖需要能被唯一识别。密码、令牌和私钥不能作为版本内容保存，只记录所使用的受控凭据引用和必要审计信息。

数据版本也不等于每次运行都必须完整复制全部源数据：

- 持续变化的业务数据库可以通过业务日期、批次、事务时间点或增量范围识别输入；
- 支持快照或表版本的数据平台，可以直接记录查询时所使用的版本；
- 模型训练数据、正式发布数据集和高价值决策结果，通常需要更强的快照或数据版本能力；
- 数据保留范围需要结合业务追溯、安全合规、存储成本和数据生命周期确定。

关键不是无限保留所有中间数据，而是对重要结果能够说明某次计算实际读取了什么数据。开发、测试和生产环境的具体隔离将在第061问讨论。

## 八、为什么需要形成每次运行的版本快照

一个正式数据结果应能关联产生它的完整版本组合：

```text
开发任务版本
+ 数据模型版本
+ 指标、标签或规则版本
+ 参数定义与实际参数值
+ 算子、算法模型和依赖版本
+ 输入数据批次、快照或时间点
+ 运行环境与执行信息
= 本次运行的版本快照
```

这里的“版本快照”不一定是一份物理文件，也可以是一组不会随后续修改而改变的关联记录。它回答的是：

> 这次结果究竟由哪一组内容共同产生？

只记录Git提交标识、工作流版本或一个指标版本，都不足以单独回答这个问题。

## 九、版本如何进入发布流程

版本不是到准备上线时才创建。开发和测试过程中就要保留可识别的变更，再从中选择某一版作为发布候选：

```text
开发过程中形成可识别版本
        ↓
选择发布候选版本
        ↓
使用该候选版本完成测试和评审
        ↓
冻结候选版本
        ↓
批准发布、部署并正式生效
```

测试通过后，候选版本不应再被静默覆盖。如果又修改了内容，就应形成新候选版本，并根据变更影响重新完成必要验证。否则，最终上线的内容可能并不是当初通过测试的内容。

### 1. 到哪个阶段就不能再原地修改

数据开发不会因为建立了版本就停止演进。不能继续改变的，是已经被识别、引用和验证的那一个确定版本。

| 阶段 | 能否直接修改当前内容 | 正确做法 |
| --- | --- | --- |
| 个人草稿或开发工作区 | 可以继续修改 | 对有意义的变更保留开发记录或提交 |
| 进入正式测试的候选版本 | 不应原地覆盖 | 修改后形成新候选版本，重新验证受影响内容 |
| 已批准发布的版本 | 不能修改 | 基于已发布版本创建新版本，重新评审和发布 |
| 已部署但尚未生效的版本 | 不能修改 | 发现问题时停止生效计划，修改后形成新候选版本 |
| 已上线并产生正式结果的版本 | 不能修改 | 创建新版本，完成测试、发布和切换，必要时重算数据 |
| 已下线或归档的版本 | 不能修改历史内容 | 保留历史证据，只追加停用、归档和替代关系等状态记录 |

最清晰的冻结点是：

> 一旦某个版本进入正式测试，就应冻结其内容，让测试结果与被测试内容一一对应。测试中发现问题后可以继续开发，但修改内容应形成新候选版本。

这里所说的“不能修改”指版本内容不能被原地替换，包括代码、工作流、算子契约、数据模型、指标口径、参数定义和依赖等。测试结果、批准状态、部署环境、上下线时间、替代关系和问题记录等生命周期信息，则可以继续追加。

### 2. 版本冻结后还需要修改怎么办

已发布或已上线的内容发生变化时，应基于当前正式版本开始新一轮开发：

```text
当前正式版本v2
       ↓
基于v2修改并形成候选版本v3
       ↓
测试与影响分析
       ↓
批准发布v3
       ↓
部署并设定正式生效时间
       ↓
v3产生新的正式结果，v2停止新的正式运行
```

紧急修复也不应直接在生产环境中修改当前版本并沿用原版本号。可以根据事件严重程度缩短测试和审批流程，但仍应从当前正式版本创建独立的紧急修复版本，完成必要的针对性验证，再发布和切换。否则，历史上会出现两份内容不同、却使用同一版本标识的正式实现。

### 3. 每次发布应该记录什么

每次发布至少应记录：

- 发布内容及其完整版本组合；
- 变更原因、内容和与上一版的差异；
- 评审、测试和批准结果；
- 影响范围和下游通知；
- 部署环境、发布时间和业务生效时间；
- 历史数据是否需要重算；
- 发布失败时的恢复目标和处置方式。

## 十、版本与发布、部署、上线和下线是什么关系

不同组织和平台对这些术语的使用不完全相同。为了理清关系，可以按照它们回答的问题来区分：

| 概念 | 回答的问题 |
| --- | --- |
| 版本 | 这份代码、模型、指标或工作流具体是什么内容 |
| 发布 | 哪个版本已经通过评审和测试，可以正式使用 |
| 部署 | 哪个版本被安装或放置到了哪个运行环境 |
| 上线或生效 | 从什么时间开始，正式任务或业务用户实际使用哪个版本 |
| 下线 | 从什么时间开始，不再允许该版本产生新的正式结果或被继续使用 |

因此，一项内容应在上线前就已经形成明确版本。上线时需要做的，是冻结并记录正式生效的版本组合，即发布基线或上线快照，而不是到上线时才开始版本化。

例如，某次上线基线可以记录：

```text
工作流版本：v3
算子版本：v1.4
数据模型版本：v5
指标口径版本：v2
参数配置版本：v6
运行环境标识：2026.09
正式生效时间：2026-09-01 00:00
上一正式基线：工作流v2及其关联版本
```

这里还需要注意几个边界。

### 1. 版本与状态是两个维度

同一版本可能先后经历草稿、测试中、待发布、已发布、已上线、已下线和已归档等状态。版本标识内容，状态说明它当前处于哪个阶段。

不是每个版本都会上线，失败或被放弃的候选版本也可以保留。同一版本先部署到测试环境，再部署到生产环境，通常不需要因为换了环境而改变内容版本。同一版本重新部署、重启或重新运行，也通常不会产生新的内容版本。

### 2. 部署时间不等于业务生效时间

新版本可能在8月28日已经部署到生产环境，但到9月1日才由正式调度开始使用。因此需要分别记录发布时间、部署时间、正式生效时间、停止生效时间，以及实际使用该版本的第一个和最后一个运行实例。

对指标和业务规则而言，业务生效时间尤其重要。代码在什么时候部署，不能自动决定新口径应从哪一天开始适用，也不能自动决定是否重算历史数据。

### 3. 下线不等于删除

一个版本下线后，通常仍需保留版本内容、修改记录、生效与失效时间、历史运行实例、输出结果的关联，以及它被哪个版本替代。下线表示不再产生新的正式结果，不代表可以立即删除历史证据。

当然，版本也不必无限保留。组织应根据业务追溯、安全合规、存储成本和数据生命周期确定归档和删除策略。

### 4. 多个版本存在不等于有多个“当前版”

新版本已部署但尚未生效、新旧结果并行核对、按组织分批切换或保留恢复目标时，多个版本可能在一段时间内同时存在。但对同一业务范围和生效时间，应清楚标明哪个版本是正式版本，哪些结果只用于验证，不能让使用者自行猜测。

## 十一、版本变化时如何进行影响分析

一个算子、数据模型或指标口径改变时，不应只检查本身能否运行，还应回答：

- 哪些下游表、指标、标签和报表依赖它；
- 哪些工作流使用了被升级的算子；
- 哪些数据服务、算法模型和业务应用会受到影响；
- 变更是否改变字段、粒度、口径或结果分布；
- 历史数据是否需要重算，新旧结果能否直接比较；
- 哪些数据消费者需要知道变更原因、时间和影响。

影响分析需要版本、数据血缘和任务依赖共同支持。血缘说明数据从哪里来、到哪里去，版本则说明具体是哪一版内容发生了变化。

## 十二、为什么回滚不只是把代码改回去

版本管理可以保留恢复依据，但不会自动恢复所有数据和业务影响：

- 回滚代码版本，不会自动撤销已经写入的错误数据；
- 指标口径改变后，恢复旧 SQL 不一定能恢复当时结果；
- 表结构已经改变时，旧程序可能无法在新结构上运行；
- 错误结果已被报表、数据服务或业务人员使用时，还需要更正、重算、补偿和通知；
- 数据已被覆盖且没有快照或可恢复记录时，可能根本无法回到原状态。

因此，恢复一个旧版本时，需要同时考虑版本状态、程序、数据、结构、下游消费和业务处置。如果旧版本内容没有变化且仍能运行，可以将它重新设为正式生效版本，通常不必为了“版本号更新”而复制一份内容相同的新版本。如果旧版本已不能适配当前数据结构或环境，就需要形成经过修正和验证的新版本。

## 十三、案例：供应商准时交付率口径升级

某制造企业使用“供应商准时交付率”评估供应商，并将结果用于采购看板、供应商评级和交付风险预警。

### 1. 发现旧口径不再符合业务实际

原指标按采购订单最初约定日期判断是否准时。业务部门后来发现，采购方与供应商可能多次确认交付窗口，一条订单明细也可能分多个批次到货。继续只用最初日期和订单明细判定，会将采购方已批准的延期误认为供应商迟交，也无法正确反映分批交付。

### 2. 分别升级业务定义、模型和代码

新指标口径改为根据最终有效的确认窗口和实际交付批次判定，并明确分批交付的分子、分母和数量权重。这导致：

- 指标口径由v1升级为v2；
- 数据模型增加承诺变更事件和交付批次，形成新版本；
- 字段映射、质量规则和 SQL 计算逻辑分别形成新版本；
- 组合这些内容的工作流也形成新的发布候选版本。

这些版本相互关联，但不是同一个版本。业务人员需要了解指标含义改变，数据工程师需要管理模型和代码变更，平台则需要将这些内容组合成可测试、可发布的确定基线。

### 3. 上线前进行影响分析

项目组检查发现，采购看板、供应商评级、风险预警和月度考核都使用该指标。新旧口径的数值不能直接混合比较，企业因此需要确定：

- 新口径从哪个业务日期正式生效；
- 历史结果是保留v1，还是使用v2统一重算；
- 如果不重算，报表如何标明口径断点；
- 供应商评级和考核是否允许在期中切换口径；
- 哪些使用者和下游系统需要提前获得通知。

完成评审和测试后，企业冻结新口径所使用的指标、模型、规则、代码、工作流和配置版本，形成正式发布基线，并记录生效时间和恢复目标。

### 4. 运行时记录完整版本快照

新版本正式生效后，每次指标计算都记录所使用的发布基线、实际参数、输入数据批次和输出结果。当供应商对评级提出异议时，采购人员可以说明该结果使用了哪个指标口径、承诺窗口、交付批次和处理任务。

如果新版本上线后发现严重错误，可以停止它继续生成新结果，恢复经过验证的旧发布基线。但已经生成的供应商评级和风险预警，仍需要重算、更正并通知使用者，不会因为恢复了旧代码而自动消失。

## 十四、常见误区

### 误区一：版本管理就是使用Git

Git擅长管理代码和文本变更，但数据开发还涉及模型、指标、规则、参数、算子、依赖和数据批次。使用Git只是实现部分版本管理的手段，不等于已经建立完整版本链。

### 误区二：文件名加上“最终版”就能追溯

文件名无法可靠记录内容差异、修改原因、发布状态和运行关系，也无法防止同名文件被覆盖。

### 误区三：只有代码需要版本

业务口径变化可能只导致代码中一个数字被修改，却会改变指标、评级和业务决策。模型、指标、规则和配置同样需要版本。

### 误区四：每次运行都要创建一个代码版本

同一代码版本可以多次执行。每次执行需要建立运行实例并记录版本快照，而不是为没有变化的代码重复创建版本。

### 误区五：已发布工作流始终使用最新版算子最方便

引用“最新版”会使工作流在没有发布记录的情况下改变运行结果。正式工作流应固定经过测试的算子版本，升级时形成新发布候选。

### 误区六：版本应该到上线时才创建

开发和测试阶段就需要版本。上线时要记录的是已经验证的正式版本组合和生效时间，而不是到最后一刻才给当前内容命名。

### 误区七：回滚代码就能恢复所有结果

已经写入的数据、修改的结构和被下游消费的错误结果，不会因为代码回滚而自动恢复。

### 误区八：版本保留得越多越好

保留版本会消耗存储和管理成本，其中还可能包含不应长期保留的敏感数据。应根据追溯价值、法规、安全和数据生命周期确定保留策略。

### 误区九：有版本号就能复现结果

只有某个孤立版本号，没有与其他定义、依赖、数据和运行信息形成版本快照，仍然不足以重现结果。

### 误区十：版本不能修改，就意味着数据开发不能继续演进

不能修改的是已经被识别、测试或发布的那个确定版本，而不是禁止继续开发。新需求和问题修复应以原版本为基础形成新版本。

### 误区十一：只是一个小问题，可以直接修改线上版本

问题大小可以影响测试和审批范围，却不应改变“一个版本只对应一份确定内容”的原则。紧急修复仍应形成新版本，否则无法准确追溯和恢复。

## 十五、实践检查清单

1. SQL、Notebook、算子、工作流和测试是否有明确版本？
2. 数据模型、指标、标签和质量规则的业务变化是否被独立记录？
3. 参数定义版本、配置版本和每次实际参数值是否已经区分？
4. 已发布工作流是否固定了实际使用的算子、模型和依赖版本？
5. 每次正式运行是否能关联完整的版本快照和输入数据范围？
6. 候选版本进入正式测试时，是否已经冻结并禁止原地覆盖？
7. 测试中修改候选内容后，是否形成新版本并重新验证受影响内容？
8. 上线时是否记录了完整发布基线、部署环境和正式生效时间？
9. 是否明确同一业务范围和时间内哪个版本是正式版本？
10. 版本改变前是否分析了下游表、指标、服务、报表和业务应用的影响？
11. 是否明确新版本的生效时间、历史重算策略和下游通知方式？
12. 线上紧急修复是否仍然形成独立版本并完成必要验证？
13. 版本下线后，是否仍能解释它产生的历史数据结果？
14. 恢复旧版本时，是否同时考虑了已生成数据、结构变化和下游业务影响？
15. 版本、数据快照和运行记录是否有合理的归档与删除策略？

## 小结

数据开发的版本管理不是只管理代码，而是管理产生数据结果的完整版本链。SQL、Notebook、算子和工作流要有版本，数据模型、指标口径、业务规则、参数定义、运行依赖和输入数据同样要能被准确识别。

版本标识内容，运行实例记录一次执行，数据批次界定输入输出范围，生命周期状态说明版本是否已经发布、上线或下线。这些概念相互关联，但不能混为一谈。

版本应该在开发和测试阶段就开始形成。上线时要做的是冻结经过验证的版本组合，记录发布基线和正式生效时间，而不是到上线时才开始版本化。下线表示不再使用某个版本产生新结果，不代表可以立即删除解释历史结果所需的版本和运行记录。

只有把每次运行与确定的版本快照关联起来，并在变更前分析影响、变更后监测结果，数据成果及由其形成的数据产品才能在持续演进中保持可解释、可比较和可恢复。
