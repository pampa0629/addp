# 065 什么是计算引擎，为什么数据平台可能需要多种计算引擎？

## 一句话回答

> 计算引擎是实际执行数据筛选、关联、聚合、转换、算法和模型等计算任务的软件系统。数据平台可能需要多种计算引擎，是因为结构化查询、海量批处理、实时流处理、机器学习和空间分析等任务对数据类型、计算方式、响应时间和运行资源的要求不同；但引擎并非越多越好，应以少而够用、可以扩展和统一治理为原则。

人们在 SQL 编辑器、Notebook 或可视化工作流中设计数据处理逻辑时，通常关注“想对数据做什么”。真正读取数据、分配资源并完成计算的，则是背后的计算引擎。

## 一、什么是计算引擎

一次数据计算可以简化为：

```text
人员通过 SQL、Notebook 或可视化工作流表达处理逻辑
                         ↓
                  数据平台提交任务
                         ↓
                  计算引擎执行计算
                         ↓
                  读取数据并写出结果
```

例如，使用者编写一段“按地区汇总销售额”的 SQL。SQL 表达了筛选条件、分组维度和计算公式，计算引擎则决定怎样读取数据、怎样关联表、是否并行执行以及使用多少CPU和内存。

计算引擎接收任务和参数，把处理逻辑转化为可以执行的步骤，并协调计算资源完成任务。它不是一个简单的“代码启动器”，而是数据处理真正发生的运行环境。

## 二、计算引擎与其他系统有什么区别

| 概念 | 主要职责 |
| --- | --- |
| SQL、脚本和 Notebook | 表达或编写数据处理逻辑 |
| 可视化工作流 | 通过算子组合数据处理过程 |
| 任务调度与编排 | 决定何时执行以及多个任务怎样协作 |
| 计算引擎 | 真正执行筛选、关联、聚合、算法和模型等计算 |
| 数据库、数据仓库和数据湖 | 保存和组织数据，也可能同时提供计算能力 |
| 监控系统 | 观察任务状态、耗时、资源和异常 |

调度器可以启动一项任务，却通常不亲自完成数据计算；Notebook 是交互式开发入口，也不等于某一种计算引擎。

存储系统和计算引擎的边界并不总是完全分开。关系数据库和数据仓库通常既保存数据，也包含 SQL 查询与计算能力；有些计算引擎则主要负责计算，需要从外部存储读取数据并将结果写回。

因此，判断一个系统扮演什么角色，不能只看产品名称，而要看它在本次数据处理中究竟负责保存数据、执行计算，还是协调任务。

## 三、计算引擎通常完成哪些工作

不同计算引擎的能力各不相同，但通常会承担以下部分职责：

- 解析 SQL、脚本、算子或任务计划；
- 根据数据规模和存储方式选择执行方法；
- 把复杂计算拆分为多个执行步骤；
- 分配CPU、内存、GPU或集群资源；
- 在多个计算节点之间分发任务和交换数据；
- 管理中间状态、临时结果和故障恢复；
- 写出计算结果并记录运行状态；
- 提供日志、耗时、数据量和资源使用信息。

开发人员通常不需要亲自指定每一条数据怎样在CPU和内存之间移动，但需要理解所选引擎的基本特点，避免把“能够运行”误认为“适合生产”。

## 四、不同计算任务有什么差异

企业数据并不只有数据库表，计算任务也不只是运行 SQL。

| 任务类型 | 主要特点 |
| --- | --- |
| 关系型查询 | 重视表的筛选、关联、分组、聚合和交互式响应 |
| 大规模批处理 | 面向大量历史数据，重视并行计算和处理吞吐量 |
| 实时流处理 | 持续处理事件，重视低延迟、窗口、状态和故障恢复 |
| 机器学习 | 涉及特征处理、训练和推理，可能需要GPU与专用程序库 |
| 图计算 | 处理节点、边、路径、社区和多跳关系 |
| 空间计算 | 处理坐标、拓扑、栅格、轨迹和空间关系 |
| 多媒体计算 | 处理图片、音频和视频，常依赖专业算法与硬件 |

一种引擎可能支持多类任务，却通常有自己更擅长的数据模型、计算方式和运行规模。能够完成某项计算，不代表它在性能、成本和维护方面都是最合适的选择。

## 五、数据平台为什么可能需要多种计算引擎

如果强行让一种计算引擎承担所有任务，可能出现：

- 结构化查询可以完成，但海量历史处理效率很低；
- 批处理能力很强，却难以持续处理实时事件；
- 通用数据计算可以运行，却缺少专业空间或图算法；
- CPU任务运行稳定，但模型训练需要GPU；
- 为适应一种特殊任务而复杂改造通用引擎，成本反而更高。

因此，数据平台可能选择由不同引擎承担不同类型的计算：通用引擎覆盖主要工作，专用引擎解决确有需要的特殊问题。

多引擎的目标不是展示技术种类，而是让每类任务由更适合的运行环境完成。

## 六、计算引擎为什么需要可扩展

企业当前使用的计算能力，不可能覆盖未来出现的所有数据和算法。后续可能出现：

- 新的数据类型和文件格式；
- 新的空间、图、遥感、仿真或多媒体数据；
- 新的行业专业算法和机器学习模型；
- 新的GPU或其他专用硬件要求；
- 只能在特定操作系统或运行环境中执行的软件；
- 受到商业许可、知识产权或安全要求限制的能力；
- 新的数据规模、性能或实时性要求。

因此，数据平台不应把所有任务固定到一种计算引擎，也不应把可使用的引擎类型写死。新增引擎时，至少需要说明：

- 能够处理什么数据和任务；
- 接受什么输入，产生什么输出；
- 支持哪些参数和运行方式；
- 需要什么计算资源、依赖和许可证；
- 如何提交、查询、取消和重试任务；
- 怎样获得状态、日志和错误；
- 如何管理版本、权限、安全和资源配额。

可扩展并不意味着无限增加引擎，而是新需求出现时，平台能够以统一、受控的方式增加必要能力。

### 新算法是否一定需要新引擎

答案是否定的。面对一项新算法，可以依次判断：

1. 现有引擎是否已经支持；
2. 能否通过程序库、函数或算子扩展现有引擎；
3. 能否把算法封装为容器或受控服务，由现有任务体系调用；
4. 只有运行方式、数据模型、资源要求或专业能力明显不同时，是否才需要接入新引擎。

例如，一个新的统计模型可能只需要增加程序库，一项普通空间计算可能只需增加算子；需要专用GPU环境、商业许可证或独立集群的大型专业算法，才更可能需要独立的计算引擎。

## 七、同一引擎内部怎样连接多个步骤

同一个计算引擎执行一项多步骤任务时，通常能够理解整条处理过程：

```text
读取数据 → 筛选 → 关联 → 聚合 → 写出结果
```

引擎可以根据任务和资源决定：

- 多个步骤是否形成流水线连续执行；
- 中间结果是否直接在内存中传递；
- 哪些步骤可以并行；
- 何时需要重新分区或交换数据；
- 哪些中间结果可以复用；
- 内存不足时是否写入临时存储；
- 失败后从哪里恢复。

在内存中传递中间数据可以减少反复读取和写入，提高处理效率，但不能假定所有步骤都只使用内存。数据量过大、多个节点需要交换数据或任务需要故障恢复时，引擎仍可能使用磁盘或其他临时存储。

因此，更准确的说法是：同一计算引擎能够统一优化完整处理过程，并在条件适合时使用内存流水线、并行执行和中间结果复用等方式提高性能。

## 八、不同计算引擎之间怎样衔接

不同计算引擎通常具有独立的进程、集群和运行环境，不能直接共享各自内部的内存对象。它们更常通过稳定的数据结果和任务编排进行衔接：

```text
任务A由计算引擎一执行
          ↓
把结果写入表、文件、对象存储或消息流
          ↓
任务编排确认A成功，并取得结果位置
          ↓
任务B由计算引擎二执行
```

这里有两种不同职责：

- 数据接口负责交接结果；
- 任务编排负责协调执行顺序、参数、状态和失败处理。

编排过程通常传递数据位置、数据集标识、分区、版本和业务日期，而不是把一个引擎中的内存数据直接交给另一个引擎。实时场景也可以通过消息流衔接，但仍要明确事件格式、时间、顺序、重复处理和状态管理规则。

通过稳定的数据边界衔接，可以让上下游分别重试和恢复，也更容易记录输入输出、运行状态和血缘。当某一引擎需要更换时，下游只要继续获得符合约定的数据结果，就不必了解上游的内部执行方式。

| 情况 | 主要衔接方式 | 特点 |
| --- | --- | --- |
| 同一引擎内的多个处理步骤 | 由引擎统一执行和优化 | 可以使用内存流水线、并行执行和中间结果复用 |
| 不同引擎完成的多个任务 | 通过稳定数据接口和任务编排衔接 | 边界清楚，便于重试、替换、审计和血缘追踪 |

一条数据开发工作流如果能够由同一个引擎执行，可以作为一个完整任务统一优化；如果处理过程需要跨越多个引擎，通常应划分为多个可独立执行的任务，再由任务编排连接起来。

## 九、多种计算引擎应该怎样统一管理

多种引擎各展所长，不应变成多个相互隔离的技术烟囱。数据平台需要尽量统一管理：

- 每种引擎能够执行哪些任务；
- 引擎适合的数据类型、数据规模和响应时间；
- 任务需要的CPU、内存、GPU和其他资源；
- 数据连接、账号、权限和受控凭据；
- 任务参数、版本、依赖和运行环境；
- 执行状态、日志、耗时和错误；
- 实际输入、输出和运行血缘；
- 资源配额、任务优先级和使用成本；
- 引擎版本、升级计划和责任人。

可以把目标概括为：

> 底层允许多种计算引擎各展所长，上层仍应提供一致的开发、治理和运行管理体验。

统一管理不等于强行把所有引擎包装成完全相同。不同引擎的窗口、状态、空间精度、GPU资源和失败恢复等专业能力仍应如实呈现。

## 十、怎样为任务选择计算引擎

选择计算引擎时，可以依次考虑：

1. 处理的是表、流数据、图、空间数据还是多媒体数据？
2. 数据规模有多大，单机能否完成？
3. 需要秒级响应、分钟级处理还是日级批量结果？
4. 任务是一次性查询、周期任务还是持续运行？
5. 是否需要保存大量计算状态？
6. 是否需要GPU、专业算法库或特殊许可证？
7. 数据存放在哪里，移动数据的成本有多高？
8. 团队是否具备相应的开发和维护能力？
9. 结果是否需要与其他引擎保持一致？
10. 建设和运行成本是否符合业务价值？

### 尽量让计算靠近数据

如果为了使用某种引擎，需要把大量数据跨系统或跨网络搬移，可能导致：

- 数据传输时间超过实际计算时间；
- 产生多份难以同步的数据副本；
- 扩大敏感数据暴露范围；
- 增加网络、存储和处理成本；
- 原数据变化后，副本不能及时更新。

因此，选择引擎不仅要看“能不能算”，还要看数据存在哪里。能够在数据所在环境完成的筛选、聚合和计算，应尽量就近执行，只传递必要的结果。

## 十一、同一段逻辑能否随意切换引擎

通常不能简单假定可以。不同引擎可能在以下方面存在差异：

- SQL 语法和支持的函数；
- 空值、时间和字符处理方式；
- 数值精度和计算顺序；
- 流处理的窗口与状态语义；
- 空间坐标、拓扑和精度处理；
- 程序库、驱动和运行版本；
- 并发、失败和重试方式。

因此，引擎类型和版本应作为任务运行环境的一部分。任务更换引擎后，需要重新验证功能、性能和结果，不能因为两个引擎都支持 SQL，就默认它们可以无差别替换。

## 十二、计算引擎如何支持数据治理

计算引擎在运行过程中会产生许多重要事实：

- 本次任务读取了哪些数据；
- 使用了什么任务版本、参数和运行环境；
- 生成了哪些结果；
- 处理了多少数据，耗费了多少资源；
- 是否发生失败、重试或数据倾斜；
- 哪些人员和任务使用了敏感数据；
- 一项结果能否按照相同条件重新计算。

这些信息可以支撑血缘、审计、质量监控、成本分析和问题定位。多种引擎应按照统一要求提供必要的运行记录，否则平台虽然能够启动任务，却无法完整回答数据从哪里来、由什么产生以及为什么发生变化。

计算引擎可以证明一项任务怎样执行，却不能自行判断业务口径是否正确。业务定义、数据标准和结果验收仍然需要业务、治理和数据人员共同负责。

## 十三、案例：城市运行数据的多种计算需求

某城市运行管理部门需要同时处理：

- 人口、法人和事件工单等结构化数据；
- 持续到达的交通、环境和设备事件；
- 大量历史运行数据；
- 视频识别和趋势预测模型；
- 地图叠加、轨迹和空间关系分析。

如果要求一种引擎承担全部计算，可能很难同时满足交互式查询、实时处理、历史吞吐、GPU训练和空间算法等要求。因此，平台让通用 SQL 计算、流处理、批量计算、模型计算和空间计算分别使用适合的引擎。

使用者仍然通过统一入口管理数据任务、参数、权限、版本和运行状态。能够在同一引擎内完成的多个步骤由引擎统一优化；需要跨引擎的处理过程，则把上游结果写入约定的数据位置，再通过任务编排启动下游任务。

例如，实时事件处理形成需要重点关注的区域后，空间计算任务读取区域和相关对象进行分析，最终结果再进入城市运行专题数据和服务。各引擎负责自己擅长的计算，平台则记录完整的输入、输出和运行关系。

多引擎解决的是不同计算问题，统一管理解决的是避免多引擎形成多个相互割裂的烟囱。

## 十四、常见误区

### 误区一：计算引擎就是数据库

数据库通常包含查询和计算能力，但有些计算引擎不负责长期保存数据，需要从外部存储读取和写回结果。

### 误区二：Notebook 或可视化工作流本身就是计算引擎

它们主要用于表达和组织处理逻辑，实际计算可能发生在本地运行环境、数据库或其他计算引擎中。

### 误区三：调度器负责执行所有数据计算

调度器负责触发和协调任务，真正的数据读取、转换和算法计算由相应引擎完成。

### 误区四：一种先进引擎能够取代所有其他引擎

引擎通常有自己的优势场景。通用能力强不等于在每一种数据、算法和资源条件下都最合适。

### 误区五：引擎越多，平台能力越强

每增加一种引擎都会增加部署、学习、权限、监控和维护成本。没有明确价值的引擎只会增加复杂度。

### 误区六：出现新算法就必须增加新引擎

很多算法可以通过现有引擎的程序库、函数、算子、容器或受控服务实现，只有运行要求明显不同时才需要新引擎。

### 误区七：同一引擎中的所有步骤都只在内存中传递数据

引擎可以在条件允许时使用内存提高性能，但大数据交换、资源不足和故障恢复仍可能需要临时存储。

### 误区八：不同引擎可以直接传递内部内存对象

不同引擎通常通过表、文件、对象或消息等稳定数据接口交接结果，再由任务编排协调执行顺序。

### 误区九：都支持 SQL，任务就能无差别迁移

语法、函数、精度、时间和执行语义可能不同，更换引擎后仍需重新验证。

## 十五、实践检查清单

1. 是否区分了数据开发工具、任务编排、计算引擎和数据存储？
2. 当前计算引擎主要适合哪些数据、任务规模和响应时间？
3. 引入多种引擎是否有明确的能力、性能、时效或成本理由？
4. 新算法能否通过程序库、函数、算子或受控服务在现有引擎中实现？
5. 平台是否能够以统一、受控的方式接入真正必要的新引擎？
6. 新引擎是否明确输入、输出、参数、资源、状态、日志和错误？
7. 同一引擎内的多个步骤是否尽量由引擎整体优化？
8. 跨引擎任务是否通过稳定数据结果和任务编排衔接？
9. 数据交接是否记录数据集、分区、版本和业务日期？
10. 是否避免为了使用某种引擎而无必要地搬移大量数据？
11. 引擎的账号、权限、凭据、配额和成本是否统一管理？
12. 更换引擎或升级版本后是否重新验证功能、性能和结果？
13. 多种引擎是否提供统一要求的运行记录和血缘信息？
14. 团队是否具备维护现有引擎种类的能力？

## 小结

计算引擎负责把 SQL、脚本、算子和模型等数据处理逻辑真正转化为计算结果。不同数据类型、计算规模、响应时间和算法要求可能需要多种引擎各展所长，但每增加一种引擎都会增加新的复杂度。

成熟的数据平台应以少而够用为原则，同时保留接入新引擎的扩展能力。面对新算法，应优先判断能否扩展现有引擎，只有运行方式、数据模型或资源要求明显不同时，才增加新的计算引擎。

同一引擎内部可以统一优化多个处理步骤，并在适合时通过内存流水线、并行计算和中间结果复用提高性能；不同引擎之间则通常通过稳定的数据结果和任务编排进行衔接。平台还需要统一管理权限、版本、资源、运行、日志和血缘，避免多引擎演变为多个技术烟囱。
