086 高可用和弹性伸缩是否是数据治理平台的必备能力？

一句话回答

高可用和弹性伸缩不是所有数据治理平台在一开始都必须具备的同等能力。是否建设、建设到什么程度，应根据平台承担的业务责任、服务连续性要求、数据规模、并发峰值、故障影响和恢复目标决定。对于承担统一身份、目录、授权、任务编排和数据服务入口的平台，高可用通常是规模化运行后的基础要求；弹性伸缩则应针对实际峰值和可扩展的执行环节建设，不能把所有组件都简单做成自动扩容。

数据治理平台经常被要求“高可用”“支持集群”“能够弹性扩展”。这些要求有合理的一面：平台一旦承担统一身份、目录、审批、授权、任务入口和数据服务，平台故障就可能影响多个部门和业务流程。但这些词也容易变成脱离场景的技术口号。

一个只服务少数人员的治理试点，和一个承载多个租户、持续运行的数据服务平台，不能使用同一套可用性目标。平台本身能够切换，也不代表外部数据库、计算引擎和专业工具都能继续工作；增加节点，也不代表系统能够正确处理重复任务和状态一致性。

判断高可用和弹性伸缩是否必要，首先要回到平台实际承担的责任，再决定技术投入的程度。

一、高可用、弹性伸缩、灾备和可扩展性有什么区别

这些概念经常一起出现，但解决的问题不同：

概念 主要解决的问题 需要关注的结果
高可用 部件故障时服务能否继续或较快恢复 服务中断时间、故障切换和降级能力
弹性伸缩 负载变化时能力能否增加或释放 峰值承载、资源利用率和扩容速度
灾备 较大范围故障后能否恢复业务和数据 恢复时间目标（RTO）和恢复点目标（RPO）
可扩展性 数据、用户、引擎和功能增长后能否继续演进 容量上限、扩展方式和改造成本

高可用不等于绝对不停机。它通常意味着在约定的故障范围内，服务能够继续提供，或者在可接受时间内恢复。弹性伸缩也不等于无限扩容，系统仍会受到数据库、网络、存储、许可证和外部引擎能力的限制。

高可用主要应对局部故障，灾备则要考虑机房、区域、误删除和重大灾难。一个系统即使部署了多个服务节点，如果没有可靠备份和恢复演练，仍然不能称为完整的业务连续性方案。

二、是否必备，取决于平台承担的业务责任

可以从以下问题判断建设优先级：

  1. 平台是否是统一登录、目录、授权或数据服务的必经入口？
  2. 平台中断时，数据生产、质量检查、审批和共享是否会立即停止？
  3. 平台服务的是少数试点人员，还是多个组织、租户和外部应用？
  4. 元数据扫描、质量检查、数据开发和服务调用是否存在明显的并发峰值？
  5. 故障后允许多长时间不能使用，允许丢失多少运行状态和业务数据？
  6. 组织是否有能力承担冗余基础设施、监控、演练和持续运维成本？

不同阶段可以采用不同的目标：

使用场景 可采用的起步方式 逐步提高的重点
小范围试点 单实例、定期备份、人工恢复 验证真实场景和最小治理闭环
部门级持续运行 核心服务避免单点，任务和结果可恢复 统一监控、自动重试和故障切换
企业级治理平台 为身份、目录、授权、任务入口设定可用性目标 多节点、可靠存储、分级灾备和定期演练
公共服务或关键业务平台 按业务和监管要求定义连续性目标 跨故障域恢复、容量预案和全链路演练

因此，“数据治理平台必须高可用”不能脱离规模和责任简单回答。小规模试点不必一开始就建设复杂集群，但当平台成为多个业务流程的共同依赖时，高可用就从优化项变成基础能力。

三、平台的不同部分，可靠性要求并不相同

数据治理平台不是一个单一的无差别组件。可以结合治理控制层、数据执行层和观察反馈层分别判断。

1. 治理控制层

身份、目录、标准、责任、授权、审批和任务入口属于治理控制层。它们通常不直接保存全部业务数据，却决定谁能发现、开发、使用和发布数据。

如果控制层短时间不可用，数据可能仍然保存在原系统中，但新的授权、审批、服务调用和治理任务可能无法进行。因此，规模化平台应优先保证控制层的服务连续性，并保留必要的只读、缓存或受控降级能力。

2. 数据执行层

数据库、数据仓库、对象存储、汇聚引擎、计算引擎、GIS 工具和主数据工具负责实际存储与处理。平台服务本身高可用，不能替代这些系统的高可用设计。

平台需要明确每项任务由谁执行、任务状态由谁负责、失败后如何重试，以及外部工具不可用时是否排队、暂停或降级。否则，平台页面虽然能够访问，真正的数据生产仍然可能中断。

3. 观察反馈层

质量结果、问题整改、血缘、运行日志和审计记录需要可靠保存。对于这些信息，持久性、一致性和可恢复性有时比页面瞬时可用更重要。

例如，一次质量检查暂时不能展示结果，通常可以稍后查询；但如果任务已经执行过，却因为故障丢失了输入版本、规则版本和结果记录，后续就无法判断数据是否通过检查，也无法完成审计和追责。

四、高可用建设不只是增加几个服务节点

高可用至少要处理以下问题：

1. 消除关键单点

需要识别服务、数据库、消息队列、对象存储、网络、凭证服务和外部连接器中的单点。并不是每个组件都必须采用相同的冗余方式，但关键路径不能只有一个无法替代的实例。

2. 保证状态和版本一致

目录、标准、授权、任务状态和审计记录不能因为切换而各自出现不同版本。需要明确哪些状态由权威系统保存，哪些信息可以缓存，以及缓存失效后如何重新获取。

3. 让任务能够恢复和重试

任务提交、文件生成、质量检查和服务发布都可能在执行中断开。系统应区分“未开始”“执行中但状态未知”“已成功”和“已失败”，不能把所有异常都当成失败后无条件重跑。

重试还必须考虑幂等性。相同任务重复执行不应造成重复写入、重复发布或重复扣减；无法做到幂等时，应通过任务锁、结果校验或人工确认控制风险。

4. 支持合理降级

部分依赖不可用时，可以让目录暂时只读、允许已批准任务继续查询状态、暂停新的高风险导出，或者把任务放入队列等待执行。降级应由业务规则决定，不能为了“页面能打开”而绕过权限和审计。

5. 监控并验证切换结果

高可用设计只有在故障时真正生效才有意义。应监控服务健康、任务积压、连接失败、存储容量、数据延迟和审计写入状态，并定期演练节点故障、依赖不可用、任务中断、备份恢复和权限服务故障。

五、弹性伸缩应该用在哪里

弹性伸缩最适合负载有明显波峰波谷、任务可以拆分、执行节点可以相对独立的场景，例如：

  • 定期扫描大量数据库、文件和对象存储资源；
  • 集中执行数据质量检查、血缘计算和敏感数据识别；
  • 多个部门同时提交数据开发或计算任务；
  • 数据服务在特定时段出现大量并发调用；
  • 新增数据源或引擎时，需要短期增加采集和适配资源。

实现时可以采用无状态服务横向扩展、任务队列和工作节点、按数据分片处理、异步执行以及资源配额等方式。对于长时间运行的任务，还应保存进度和中间状态，避免扩容或故障后只能从头开始。

但不是所有组件都适合自动扩容：

  • 有状态数据库需要重点解决一致性、容量和备份，而不是简单增加实例；
  • 对象存储的扩展方式与计算服务不同；
  • GIS、仿真和机器学习工具可能受专用硬件或软件许可证限制；
  • 外部系统的接口限流，可能成为平台扩容后的新瓶颈；
  • 没有合理队列和配额时，自动扩容可能把下游系统压垮。

所以，弹性伸缩应服务于明确的业务峰值和资源约束，不能作为脱离任务模型的基础设施口号。

六、用 RTO、RPO 和服务目标确定建设程度

平台建设前应先定义可验证的目标：

  • RTO（Recovery Time Objective）：发生故障后，业务恢复到可用状态允许花费多长时间；
  • RPO（Recovery Point Objective）：恢复时最多可以接受丢失多长时间范围内的数据或运行记录；
  • 服务目标：在约定时间内，接口、目录、任务和数据服务应达到怎样的可用性、响应时间和处理时效。

例如，目录查询短时间中断可能只影响发现数据，而统一授权服务中断可能阻断所有新数据服务调用。质量检查结果可以允许延迟，但审计记录不能悄悄丢失。不同能力应分别设定目标，而不是给整个平台套一个脱离实际的百分比。

目标越高，通常需要更多冗余、监控、演练和运维投入。组织还应把外部数据库、计算引擎、网络和身份系统纳入依赖分析，否则平台自身的指标再好，也无法保证完整业务链路。

七、一个治理任务中断的例子

某组织每晚对多个业务系统执行元数据扫描和质量检查。治理平台负责登记任务、分配执行引擎、记录规则版本和汇总结果，实际扫描由不同连接器和计算引擎完成。

如果只追求“平台页面可访问”，可能出现以下问题：

  1. 平台节点故障后，任务已经提交但状态无法判断；
  2. 运维人员手工重跑，造成重复扫描和重复写入；
  3. 质量结果写入失败，但页面显示任务成功；
  4. 外部引擎恢复后，平台没有办法确认应继续、重试还是跳过；
  5. 最终目录显示了新结构，却没有留下对应的规则版本和审计证据。

更合理的设计是：任务提交后生成稳定标识，保存输入对象、规则和参数；执行引擎反馈可关联状态；中断时进入“状态未知”或“待恢复”，由系统依据幂等规则处理；结果和审计记录可靠落库；短时高峰通过队列和工作节点扩展，而不是让所有请求直接冲击下游系统。

这个例子说明，高可用和弹性最终要落实到任务、数据、状态和证据，而不只是部署图上的节点数量。

八、常见误区

误区一：数据治理平台不是交易系统，所以不需要高可用

平台虽然不一定处理每一笔业务交易，但可能是目录、授权、审批、任务和数据服务的共同入口。是否需要高可用，应看故障影响而不是看系统名称。

误区二：部署了集群，就自动实现了高可用

如果数据库、消息、凭证、任务状态或外部引擎仍然是单点，集群只能提高部分服务的存活能力，不能保证完整链路可用。

误区三：平台高可用等于所有数据和计算都高可用

平台只能协调和观察外部能力。数据存储、计算引擎、GIS 服务和业务系统仍需分别定义可靠性目标，并通过接口反馈真实状态。

误区四：自动扩容越多越好

没有队列、配额、幂等和下游保护的自动扩容，可能制造更多重复任务、连接拥塞和数据不一致。

误区五：高可用只关注接口能否返回

治理平台还必须保证任务状态、质量结果、版本、血缘和审计证据不会在故障中失真或丢失。

误区六：高可用建设完成后就不需要演练

没有切换、恢复和数据校验演练的方案，只是设计文档，不能证明真实故障时能够工作。

小结

高可用和弹性伸缩不是数据治理平台的统一门槛，而是应随业务责任、规模和风险逐步提高的工程能力。小范围试点可以先用简单部署、备份和人工恢复验证治理闭环；当平台成为多个组织和数据服务的共同依赖时，应为身份、目录、授权、任务入口、元数据和审计等关键能力设定明确的可用性与恢复目标。

弹性伸缩应针对扫描、质量检查、批处理和服务调用等实际峰值，结合任务队列、幂等执行、资源配额和故障隔离建设。平台高可用不能替代数据库、计算引擎和专业工具自身的可靠性，增加节点也不能代替备份、灾备和恢复演练。

最终要评价的不是平台是否拥有一张复杂的集群架构图，而是发生故障和负载变化时，数据、任务、规则、权限、结果和审计是否仍能按照业务要求继续运行、恢复和追溯。
