091 数据治理需要哪些关键角色，如何分工协作？

一句话回答

数据治理在责任上需要决策与协调、业务责任、治理协作、技术执行和数据使用与反馈等多类角色共同参与；在专业能力上，还需要数据分析、科学、算法、工程、运维和软件产品开发等岗位支撑。治理责任与专业岗位可以交叉，但不能相互替代，也不能把治理工作压缩成一个部门的任务。

数据治理经常被简单归类为某个部门的工作：有的组织交给信息技术部门，有的组织交给数据中心，还有的组织设立一个治理办公室，要求它解决所有数据问题。这些安排都可能提供一个起点，但数据治理涉及数据含义、业务规则、技术处理、权限安全、问题整改和价值评价，单一部门通常无法独立完成。

更合理的做法是先明确需要哪些责任，再决定由哪些部门、团队或个人承担。角色是责任边界，不必机械对应固定岗位；小组织中一个人可以承担多个角色，大型组织中一个角色也可能由多个团队共同承担。

一、为什么数据治理不能只交给一个部门

一项数据治理工作至少要回答这些问题：

  • 数据代表什么业务对象或事实；
  • 数据应该满足什么质量要求；
  • 哪些用户和应用可以使用；
  • 数据怎样采集、存储、开发和发布；
  • 发现问题后由谁整改，谁负责复核；
  • 治理后的数据是否真正改善了业务工作。

业务部门最了解数据的含义和使用目标，但未必能完成数据接入、计算和权限控制；技术团队能够建设系统和任务，但不能独自决定业务口径和质量标准；管理部门能够推动协作，却不能替代专业判断。

因此，数据治理不是“业务提需求、技术做系统”这么简单，而是多个角色围绕同一数据对象和业务结果共同工作。

二、数据治理需要哪些类型的角色

1. 决策与协调角色

负责确定治理方向、重点领域、资源优先级和跨部门协作规则，并在出现重大分歧时推动处理。它可以由治理委员会、分管负责人或治理办公室承担，具体组织形式取决于组织规模和管理方式。

本问只说明它在角色体系中的位置。治理委员会如何议事、如何形成有效决策，第093问再详细讨论；多个部门口径冲突时谁拥有最终裁决权，第094问再展开。

2. 业务责任角色

负责说明数据代表什么、为什么重要、怎样使用以及什么结果才算正确。它需要确定业务目标、质量要求、可接受风险和优先级，并对业务含义作出判断。

业务责任角色可以由业务负责人、领域负责人或数据责任人承担。数据责任人、数据治理专员等概念的边界，第092问会进一步区分。

3. 治理协作角色

负责把业务要求转成可以共同执行的标准、指标、质量规则、责任关系和问题流程，并组织跨部门沟通、跟踪整改和维护治理记录。

这类角色常见于数据治理专员、领域协调人等岗位。它们不一定拥有所有业务决策权，但要能够推动规则落地、发现责任空缺并把问题带回正确的决策链路。

4. 技术执行角色

负责数据接入、存储、开发、计算、质量检查、服务、权限、血缘和运行保障，把已经确认的业务规则落实到系统和任务中。

数据架构师、平台工程师、数据库和计算引擎负责人、专业工具负责人都可能属于这一层。技术执行角色要对执行结果的可靠性负责，但不能代替业务决定数据含义。

5. 数据使用与反馈角色

负责实际使用数据集、指标、标签、服务或数据产品，并反馈数据是否可理解、质量是否满足要求、结果是否及时以及能否支撑业务工作。

数据使用者不是治理流程之外的旁观者。没有真实使用和反馈，组织无法判断治理成果是否产生了业务价值，也无法发现目录、口径和服务中的实际问题。

三、治理责任角色和专业岗位不是同一个维度

数据治理中的“角色”通常表达责任边界，数据相关“岗位”则更多表达专业工作。二者可以交叉，但不能混为一谈。

1. 治理责任角色

治理责任角色回答“谁对什么作出判断、承担什么责任”，例如：

  • 首席数据官（Chief Data Officer，CDO）或数据治理负责人，负责总体方向、组织推动和治理能力建设；
  • 数据责任人，负责特定数据域的业务含义、质量要求和使用边界；
  • 数据治理专员，负责标准、规则、问题和跨部门协作的日常推动；
  • 数据保管员，负责数据存储、访问、备份和运行环境等保管责任；
  • 数据资产运营者，负责数据资产的发布、申请、使用反馈、评价和退出；
  • 安全、合规和审计人员，负责风险、控制和责任证据。

这些角色不一定都是专职岗位，也不一定由同一个组织层级承担。第092问将进一步区分其中几类容易混淆的概念。

2. 专业岗位角色

专业岗位回答“需要什么专业能力完成数据工作”。常见岗位包括：

专业岗位 主要工作侧重
数据分析师 理解业务问题，开展统计分析、指标分析和结果解释
数据科学家 统计建模、机器学习、大数据分析和实验验证
算法工程师 将算法设计实现为可运行、可测试和可部署的程序
数据工程师 数据接入、数据建模、数据生产、计算任务和数据管道
数据运维工程师 数据生产任务、存储计算环境、监控、备份和故障处理
数据治理平台软件工程师 负责目录、标准、质量、权限、流程、血缘和审计等治理平台能力的软件设计、开发、测试和维护
数据产品开发工程师 将数据、指标、模型和服务封装为面向业务用户的数据产品

首席数据官也可能同时承担管理岗位和治理责任，但不能据此把其他专业岗位都理解为从属的低端执行岗位。一个数据产品要真正产生价值，分析、科学研究、算法实现、数据生产、运行保障和产品开发都可能不可缺少。

四、数据治理“铁三角”

“数据治理铁三角”不是数据治理领域定义统一、所有组织都必须采用的正式行业标准。不同资料中对“铁三角”的含义并不相同。本问借用这一说法，只用来概括业务责任、治理协作和技术执行三个核心责任面，不能把它当作完整的岗位清单或固定组织模板。

如果用它来概括数据治理的核心协作面，可以表达为：

                 业务责任
        数据为什么这样定义，什么结果才算正确
                  /       \
                 /         \
       治理协作 ----------- 技术执行
  怎样形成标准、规则、责任       怎样接入、处理、保护、
       和问题闭环              发布和持续运行

三角的三个顶点不是三个部门，而是三类相互约束、相互反馈的责任面：

  • 承担业务责任的角色提出目标并判断结果是否符合业务要求；
  • 治理协作者组织口径、规则、流程和责任关系；
  • 技术执行者把规则落实到数据源、任务、服务和权限控制中；
  • 执行结果再反馈给业务和治理角色，推动调整和改进。

完整的数据治理还需要决策与协调、专业岗位、数据使用、安全合规和资产运营等角色参与。数据治理铁三角只能说明核心责任关系，不能替代完整的组织和岗位体系。

五、角色如何围绕一个业务场景协作

以供应商交付分析为例，业务负责人希望准确判断供应商是否按约定时间交付。不同角色可以这样协作：

  1. 业务责任角色说明订单、发货、到货和验收的含义，确定“准时交付”的业务口径和使用目标；
  2. 治理协作者梳理相关数据对象、责任部门、标准、质量规则和问题处理流程；
  3. 技术团队接入采购、仓储和财务数据，实现计算任务、质量检查和指标服务；
  4. 数据使用者验证结果是否能够支撑供应商评价、采购调整和经营分析；
  5. 发现日期缺失、口径不一致或结果异常时，业务责任角色、数据治理专员、数据工程师、数据使用者以及相关技术和专业岗位共同定位来源，决定修复规则、任务还是源头流程；
  6. 修订后的定义、规则和任务形成新版本，并记录影响范围和验证结果。

这个过程的成果，不是把若干角色名称写进组织架构图，也不是简单增加几个数据岗位，而是让业务目标、数据定义、治理规则、技术任务和使用反馈真正连接起来。最终要看到的是供应商评价更及时、口径争议更少、人工核对更少，并且出现问题时能够找到责任和原因。

六、数据相关岗位是不是天然低端岗位

数据岗位没有天然的高低之分。数据录入、清洗、标注和基础运维可能有较强的重复性，但它们仍然需要准确性、规范性和责任意识；数据建模、指标设计、质量治理、数据架构、数据工程、算法工程和治理决策，则承担不同层次的专业判断和业务影响。

不能只用是否开发面向用户的页面、代码量多少或岗位名称来判断工作档次。数据工程师需要理解数据结构、业务语义、计算逻辑、质量风险、性能、权限和生命周期；一项看不见的标准或血缘改进，可能直接影响经营分析、监管报送、风险控制和智能应用。

可以从这些维度评价数据工作的专业价值：

片面评价方式 更合理的评价方式
是否写复杂页面 是否解决了复杂的数据和业务问题
代码量多少 规则、模型和任务是否可靠、可复用
是否直接面对用户 是否影响关键决策、服务和风险控制
录入或清洗工作“低端” 工作是否需要准确性、业务理解和责任承担
功能模块越多越高级 数据质量、使用效果和问题闭环是否改善

还要区分岗位价值、具体工作层级、个人能力和业务影响。同一岗位可以有机械执行、专业判断、方案设计、跨部门治理和战略决策等不同层次，不能用岗位名称替代对实际工作的评价。

数据治理成果还具有基础性和长期性。标准、口径、质量、血缘和责任做得好时，问题可能不容易被看见；一旦缺失，错误指标、重复建设和错误决策才会集中暴露。因此，组织不能只奖励看得见的新功能，也要认可让数据稳定、可信和可复用的工作。

本问只说明这种专业价值观。如何通过考核、激励和问责把它落实到管理制度中，第095问再讨论；如何改变组织文化、减少业务人员抵触，第096问再讨论。

七、角色边界如何避免重叠和空缺

每项关键治理活动都应明确：

  • 谁作出业务决策；
  • 谁维护定义和规则；
  • 谁负责技术执行；
  • 谁批准上线、共享或发布；
  • 谁处理异常和整改；
  • 谁验证结果；
  • 谁承担最终责任。

例如，数据工程师可以实现“准时交付率”的计算逻辑，但不能自行改变准时交付的业务定义；数据治理专员可以组织规则讨论和问题跟踪，但不能在没有授权的情况下替业务部门作出重大口径裁决；平台运维可以恢复任务和服务，但不能把技术恢复直接当成业务结果正确。

角色边界清楚后，还要保证角色之间能够获得完成责任所需的权限、数据和信息。只给数据治理专员分派问题，却不给他协调部门和升级问题的渠道；只要求业务负责人负责质量，却不给他查看结果和影响范围的能力，都会让责任变成形式。

八、常见误区

误区一：数据治理就是数据部门或技术部门的工作

技术和数据团队可以提供平台、方法和执行能力，但业务含义、质量要求和使用价值必须由业务共同判断。

误区二：设立一个治理负责人后，其他部门可以退出

治理负责人负责推动和协调，不能替所有部门承担业务决策、数据整改和使用反馈。

误区三：“数据治理铁三角”是行业统一标准

数据治理铁三角更适合作为解释协作关系的管理比喻，不能代替组织结合自身规模、行业和治理成熟度定义角色。

误区四：数据工程师只负责写脚本，不需要理解业务

脱离业务语义的技术实现可能运行成功，却产生错误结果。数据工程师需要理解自己处理的数据和规则边界。

误区五：业务人员只提需求，不需要参与质量判断

业务人员必须参与口径、质量和价值判断，否则技术团队只能按照不完整的假设执行。

误区六：数据录入、清洗和运维工作天然低端

基础工作不等于没有价值，专业价值应结合复杂度、准确性要求、责任范围、业务影响和可复用成果评价。

误区七：角色越多，治理越成熟

角色数量不能代替责任清晰、协作有效和问题闭环。过多重叠角色反而会增加推诿和沟通成本。

误区八：所有组织都必须照搬同一套角色名称

组织规模和管理方式不同，可以采用不同岗位名称，但不能缺少决策、业务、治理协作、技术执行和使用反馈这些基本责任。

小结

数据治理需要多类角色共同参与：决策与协调角色确定方向和优先级，业务责任角色定义含义和质量，治理协作角色组织标准、规则和问题闭环，技术执行角色保证数据和平台可靠运行，数据使用者通过真实使用提供反馈。

数据治理铁三角可以帮助组织理解业务责任、治理协作和技术执行之间的关系，但不是数据治理领域统一的行业标准，也不是完整的岗位清单。角色可以由岗位、团队或兼职人员承担，关键是责任、权限、信息和反馈能够匹配。

数据相关工作也没有天然的高低之分。组织应根据问题复杂度、专业判断、责任范围、业务影响、可复用能力和持续改进成果评价岗位价值，而不能只看页面、代码和短期可见成果。后续还需要通过考核激励和数据文化，把这种认识落实到组织日常工作中。
