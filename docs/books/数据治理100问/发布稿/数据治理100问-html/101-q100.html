100 知识库、知识图谱和向量数据库如何协同支持 AI 开展数据治理？

一句话回答

知识库、知识图谱和向量数据库不是三种相互替代的方案：知识库沉淀制度、标准、术语、规则和经验，知识图谱组织实体、关系、血缘和责任，向量数据库帮助 AI 按语义发现相关内容。更可靠的做法，是根据问题类型组合原文检索、知识编纂、图谱查询、结构化计算和工具调用，让 AI 既能找到资料、理解关系，也能回到可验证的事实和受控的行动。

第099问已经讨论了 AI 问数如何做到准确、可靠和可追溯。可靠问数不仅需要指标和结构化数据，也常常需要从制度、标准、文档和对象关系中获得解释与证据。当 AI 进一步参与标准配置、建模、质量治理和问题处理时，它还需要组织内部的业务知识、历史经验和当前运行状态。

过去常见的做法，是把文档切成片段、生成向量并建立检索增强生成（Retrieval-Augmented Generation，RAG）知识库。它降低了从大量资料中寻找相关内容的成本，但实践也表明，仅靠“切片—向量检索—生成答案”的朴素 RAG，难以稳定支持跨文档综合、实体关系分析、精确计算和高风险治理决策。

因此，真正需要建设的不是一个能够回答问题的文档库，而是一套能找证据、编知识、查关系、算数据、记状态并接受人工校验的治理知识系统。

一、先区分知识库、知识图谱、向量数据库和 RAG

这几个概念经常同时出现，但它们不在同一个层面。

概念 主要作用 数据治理中的典型内容
知识库 保存和组织可供人或 AI 使用的知识 制度、标准、术语、规则、模型说明、案例、操作手册
知识图谱 以实体、关系、属性和事实组织知识 业务实体、表、字段、指标、责任人、血缘、治理问题之间的关系
向量数据库 保存向量表示并支持相似度检索 文档、知识页、字段描述和历史案例的向量及其元数据
RAG 在生成答案前检索外部证据的一种应用模式 从原始制度、标准和文档中找到相关片段，再辅助模型回答

向量数据库可以支撑 RAG，但 RAG 不一定只使用向量检索，也可以组合关键词检索、元数据过滤、图谱遍历和结构化查询。知识库也不等于向量数据库：即使没有向量索引，一套经过分类、链接、评审和持续维护的文档或知识页面，仍然可以构成知识库。

同样，知识图谱也不是把所有文档改成节点和边。它更适合表达身份明确、关系稳定、需要查询和约束的对象与事实。

二、AI 开展数据治理需要哪些知识和证据

AI 参与数据治理时，面对的并不只是文档问答。它至少需要以下几类内容：

  • 规范性知识：国家标准、行业规范、组织制度、数据标准和安全规则；
  • 业务语义：术语、实体、事件、状态、维度、指标和适用范围；
  • 技术事实：表、字段、接口、任务、代码、血缘、质量结果和运行状态；
  • 组织责任：数据责任人、数据治理专员、维护团队、审批人和使用权限；
  • 历史经验：过去的治理问题、裁决、整改方案、实施结果和失败案例；
  • 当前状态：正在处理的任务、已完成的步骤、人工确认结果和待办事项。

这些内容的性质不同，不能全部切成文本片段后交给相似度检索。制度条款适合回到原文取证，实体和血缘适合通过图谱或元数据系统查询，指标需要由指标平台计算，当前任务状态则需要由 Agent 的工作记忆和业务系统提供。

三、RAG 的价值仍然是“从原始资料中取证”

RAG 最适合解决的是：资料很多，模型不可能全部放入上下文，需要在回答时找到与当前问题相关的原始证据。

在数据治理中，它适合处理：

  • 定位某项制度或标准的具体条款；
  • 查找某个术语、数据元或质量规则的正式定义；
  • 从产品手册和操作规程中寻找处理步骤；
  • 查找历史问题的整改记录和审批依据；
  • 为 AI 生成的建议提供原文引用和版本信息。

RAG 的重要价值并没有因为新的知识组织方式而消失。特别是在资料规模大、问题具有长尾性、内容变化快的场景中，不可能提前整理所有潜在问题和关系，按需检索仍然是必要的基础能力。

但是，“检索到了相似片段”只表示系统找到了候选证据，不表示答案已经正确。模型还可能忽略适用条件、混淆版本、误解条款，或者在生成时说出证据没有支持的内容。

四、为什么朴素 RAG 难以支撑复杂治理任务

朴素 RAG 通常把文档切成固定长度的片段，生成向量，召回若干相似片段，再让模型生成答案。这种方法容易遇到以下问题。

1. 切片可能破坏完整语义

定义、前提、例外、附表和适用范围可能分布在不同段落。只召回其中一片，模型就可能把有条件的规则解释成普遍规则。

2. 相似不等于适用

语义相似的条款可能属于不同地区、业务范围、组织层级或历史版本。向量相似度无法独立判断哪一项当前有效。

3. 难以完成跨文档和多跳分析

“这个指标为什么变化”“某项标准调整会影响哪些模型和报表”通常需要先识别对象，再沿关系寻找多个证据。单轮检索容易找到局部事实，却找不齐完整链路。

4. 无法代替精确计算和状态查询

制度文档可以说明指标如何定义，却不能提供指标的当前数值。实际结果必须由指标平台、数据库或业务服务按正式口径计算。

5. 引用了资料也可能超出证据

模型可能在正确引用之后加入没有依据的推断。评价答案时应把答案拆成关键论断，检查每条论断是否真的得到相应证据支持。

6. 内容更新容易造成多层不一致

原文更新后，旧切片、向量索引、摘要、缓存和历史知识页可能仍然存在。若没有版本和失效传播机制，AI 会继续引用已经撤回的内容。

所以，需要改进的不是“要不要 RAG”，而是不能把最简单的向量检索链路当成完整的企业知识系统。

五、从资料仓库走向可持续编纂的治理知识层

近期出现的 LLM Wiki 思路，提出让模型不只在每次提问时临时拼接片段，而是在新资料进入时，持续更新一组相互链接的知识页面：整理概念、实体、比较、冲突、决策和待核验问题，并记录它们与原始资料的关系。

对数据治理而言，这种思路的价值在于把知识库从“保存以后可能被检索到的资料”，推进为“持续编纂、可以复用和修订的知识产品”。例如可以维护：

  • 术语和概念页，记录统一定义、同义词、适用范围和版本；
  • 业务实体页，记录属性、状态、关系和主数据标识；
  • 指标页，记录口径、维度、时间、过滤条件和责任人；
  • 标准与规则页，记录规则内容、来源、例外和适用对象；
  • 决策页，记录口径冲突、裁决依据、参与人和后续影响；
  • 问题页，记录已知矛盾、待核验内容和整改进展。

但 LLM Wiki 目前更适合作为一种新兴的知识编纂思路，而不是已经形成统一定义和成熟标准的产品类别。Markdown 文件夹本身也不是 LLM Wiki；如果没有增量更新、交叉链接、冲突管理、版本记录和回源定位，它仍然只是笔记目录。

更重要的是：知识页是派生知识层，原始资料才是事实来源。 每条重要论断都应保留来源标识、原文位置、版本、生效时间和确认状态，并区分：

  • 原始资料直接陈述的事实；
  • AI 跨来源形成的综合或解释；
  • 模型推断但尚未核验的候选结论；
  • 已由业务专家或数据责任人确认的治理结论。

知识编纂可以减少每次回答都从零开始理解资料的成本，但也会带来“二手知识污染”的风险：一次错误摘要可能被后续页面反复引用。因此应从少量高价值材料和明确场景开始，先建立页面规范、回源规则、评审流程和抽样核验，再逐步扩大范围。

六、知识图谱怎样补足实体和关系能力

治理知识页适合人和模型阅读，知识图谱则更适合表达和查询明确的对象关系。例如：

业务术语 ─定义→ 数据标准 ─约束→ 数据元
数据元 ─落实到→ 字段 ─属于→ 数据表
字段 ─参与计算→ 指标 ─服务于→ 业务场景
数据表 ─产生于→ 数据任务 ─负责团队→ 组织
质量问题 ─影响→ 指标 ─责任人→ 数据责任人

借助这些关系，AI 可以：

  • 识别同一业务对象在不同系统中的名称和标识；
  • 从一个字段追踪到上游来源、下游指标和使用场景；
  • 判断标准变更可能影响哪些模型、接口、报表和责任人；
  • 在质量问题发生时分析传播路径和整改责任；
  • 结合本体中的关系类型和约束，减少只凭名称猜测语义。

图谱中的关系也不能被视为天然正确。每个事实仍需要来源、时间、版本、置信状态和责任，尤其要区分系统采集的事实、规则推导的关系、模型预测的关系和人工确认的结论。

七、向量数据库是发现工具，不是真相来源

向量数据库擅长按照语义相似度寻找候选内容。例如用户询问“客户流失”，它可以召回使用“客户沉默”“续约下降”或“用户流失”等不同表达的资料。这对于术语不一致、自然语言表达丰富的知识发现很有价值。

但向量本身不是人可以直接核验的业务事实。可靠系统必须保留向量与原文、知识页、实体、版本、权限和业务对象之间的关联。

向量检索通常还应与其他方法组合：

  • 用关键词或 BM25 检索专有名词、编号和精确条款；
  • 用元数据过滤组织、地区、版本、时间和权限；
  • 用重排序模型重新判断候选内容与问题的相关性；
  • 用父子分块或层级检索恢复章节和条款上下文；
  • 用知识图谱约束实体范围并寻找多跳关系；
  • 用结构化查询获取精确数值和当前状态。

什么时候需要向量数据库，应由资料规模、表达差异和检索效果决定。对于几十份结构清楚的核心制度，目录、全文搜索和明确链接可能已经够用；如果一开始就部署复杂的向量基础设施，反而可能掩盖知识结构、来源和责任没有理清的问题。

八、根据问题类型选择知识路径

更成熟的知识系统，应先判断问题是什么类型，再选择相应的证据和工具，而不是让所有问题都进入同一条 RAG 链路。

问题类型 首选路径 示例
单项事实、条款和出处 原始资料 RAG 某项标准的正式定义是什么？
跨文档比较、冲突和综合 治理知识层 + 查询分解 + 回源核验 两个部门的客户定义有哪些冲突？
实体关系、血缘和影响分析 知识图谱或元数据系统 修改字段会影响哪些指标和报表？
数值、状态和指标 指标平台、数据库或业务 API 本月及时交付率是多少？
用户偏好、任务进度和历史行动 Agent Memory 与流程系统 上次整改进行到哪一步？
治理方案设计 多种知识与工具组合 + 人工确认 应如何建立供应商质量指标体系？

复杂问题还可以先拆成多个子问题，分别检索、查询和计算，再合并证据。例如“某指标异常的原因及影响”可以拆为指标口径、实际数值、上游变化、血缘范围、相关制度和责任人等多个可验证步骤。

九、它们如何帮助 AI 完成具体治理工作

1. 数据标准和术语配置

AI 可以从行业规范、组织制度和历史标准中提取候选术语、定义、数据类型、枚举值和校验规则；通过知识图谱发现同义、上下位和引用关系；再由数据责任人确认业务内容，由数据治理专员组织评审和发布。

2. 实体建模

AI 可以综合业务资料、表结构、接口、主数据和知识图谱，识别候选实体、属性、关系、事件和生命周期。它还可以提示同名异物、异名同物和身份映射问题，但最终业务边界仍需业务专家判断。

3. 维度建模和指标体系

AI 可以根据分析主题、事实事件、粒度、历史变化、报表和已有 SQL，提出事实表、维度、层级和指标口径候选。涉及精确结果时，必须通过语义层、指标平台或受控查询进行验证。

4. 数据质量治理

AI 可以结合标准规则、历史案例、当前质量结果和血缘图谱，分析可能根因、影响范围和整改路径。相似案例可以提供参考，但不能直接证明当前问题具有相同原因。

5. 元数据、资产和安全治理

AI 可以补全资源描述、关联业务术语、识别潜在敏感字段、推荐责任人和使用场景。权限授予、分类分级定级和高风险资产发布仍应由有权角色确认。

6. 持续运营

AI 可以发现知识页长期未复核、标准互相冲突、图谱存在孤立节点、原文已经更新但索引未同步，以及用户频繁纠正的答案，并将问题送入正式治理流程。

十、一个更可靠的协同架构

                         ┌─ 原始资料 / Source RAG ── 原文证据
用户问题 ─ 问题分类 ────┼─ 治理知识层 ─────────── 概念、综合与冲突
                         ├─ 知识图谱 / 元数据系统 ─ 实体、关系与血缘
                         ├─ 指标平台 / 数据库 ───── 精确数值与状态
                         └─ Agent Memory / 流程 ─── 任务状态与历史行动
                                      ↓
                         证据融合、逐项校验和权限检查
                                      ↓
                         回答、候选治理方案或受控行动
                                      ↓
                         人工确认、执行结果和知识回流

这套架构的重点不是把所有技术都部署一遍，而是建立清晰的知识分工和问题路由。对于简单场景，全文检索加原文引用可能已经足够；只有在关系复杂、资料量大或需要持续综合时，才逐步增加图谱、向量检索和知识编纂能力。

十一、案例：AI 辅助建设供应商质量治理体系

某制造企业希望让 AI 协助建立供应商质量标准、指标和整改机制。企业已经积累了采购制度、质量标准、合同模板、供应商资料、质检记录、会议纪要和历史整改案例。

原始资料保留在只读来源库中，记录版本、生效时间和权限。RAG 用于定位质量标准和合同条款；治理知识层持续整理“供应商”“缺陷”“退货”“整改”等概念，记录制度冲突和已经确认的口径；知识图谱关联供应商、合同、订单、物料、质量事件、指标和责任人；指标平台计算缺陷率、按时交付率和整改完成率。

AI 根据业务问题选择不同路径：查合同依据时回到原文，分析某供应商影响范围时查询图谱，计算风险指标时调用指标平台，设计质量规则时综合行业标准和历史案例。它提出候选标准、实体关系、指标定义和整改建议，并逐项列出来源、冲突和不确定内容。

质量负责人和数据责任人确认后，正式标准和指标才进入发布流程。执行结果、用户纠错和新出现的例外又回流到知识页、图谱和评测集中。这样形成的不是一个会聊天的文档库，而是一套能够持续支持治理设计和执行的知识系统。

十二、如何评价这套系统是否有效

不能只看回答是否流畅，应分别评价：

  • 检索质量：是否召回正确、完整且当前有效的资料；
  • 知识质量：知识页是否准确、无冲突、可回源并经过适当确认；
  • 图谱质量：实体和关系是否正确、及时、完整且有依据；
  • 论断质量：答案中的每个关键结论是否被证据直接支持；
  • 计算质量：指标口径、粒度、时间和结果是否正确；
  • 权限质量：原文、知识页、关系、检索结果和最终答案是否遵守权限；
  • 拒答质量：证据不足、版本冲突或权限不够时能否澄清、降级或拒答；
  • 业务效果：是否减少治理设计和问题处理成本，是否真正改善数据和业务结果；
  • 系统成本：模型、嵌入、重排、存储、时延和人工复核是否可接受。

近期关于向量 RAG 与 LLM 编纂 Wiki 的对照研究，为跨文档连接和逐论断引用提供了一些值得关注的证据，但相关研究仍可能存在语料规模小、预印本、主要依赖模型评委等限制。组织不能依据单项实验认定一种架构普遍优于另一种，仍应使用自己的制度、标准、元数据和治理问题建立评测集。

十三、常见误区

误区一：上传文档、建立向量索引，就拥有了可信知识库

没有来源、版本、权限、适用范围和持续维护，文档数量越多，冲突和过期内容可能越多。

误区二：LLM Wiki 会全面取代 RAG

知识编纂适合持续综合和关系沉淀，RAG 仍适合从大规模原始资料中按需取证。高风险结论通常需要知识层导航与原文核验结合。

误区三：Markdown 文件夹就是 LLM Wiki

知识编纂层还需要增量更新、交叉链接、冲突处理、来源锚点、确认状态和质量检查。

误区四：向量相似度就是事实正确度

向量检索只能发现候选内容，不能独立判断对象身份、版本有效性、业务口径和结论真伪。

误区五：知识图谱中的关系天然可信

图谱中的实体和关系同样需要来源、版本、时间、责任和质量治理。

误区六：所有问题都应该通过知识库问答解决

精确问数应调用指标或数据服务，关系分析应查询图谱，任务状态应访问流程系统，不能让模型从文档中猜测。

误区七：有引用就代表回答正确

必须检查引用是否直接支持对应论断，尤其不能把模型自己的综合和推断伪装成原文结论。

误区八：让 AI 自动更新知识，知识库就会越来越好

未经校验的错误可能持续传播。重要知识需要变更记录、抽样核验、人工确认和回滚能力。

误区九：技术组件越多，知识系统越先进

应从问题、规模、风险和价值出发选择最小可用组合。没有明确知识边界和责任，再多组件也只是新的孤岛。

小结

知识库、知识图谱和向量数据库可以共同帮助 AI 参与数据标准、建模、指标、质量、元数据、安全和持续运营，但三者承担的职责不同。RAG 负责从原始资料中寻找证据，治理知识层负责持续整理概念、综合和冲突，知识图谱负责实体与关系，向量数据库负责语义发现，结构化系统负责精确事实和行动状态。

RAG 没有过时，真正需要淘汰的是把“文档切片、向量召回、模型生成”当作完整知识治理的方法。更可靠的路径，是根据问题类型组合混合检索、知识编纂、图谱查询、结构化计算、逐项核验和人工确认。

成熟的、面向 AI 的数据治理知识系统，不是让模型记住更多材料，而是让它知道应该去哪里找资料、怎样连接知识、何时回到原文、哪些结果必须计算、哪些判断需要人来定夺，并让每一项重要结论都可以验证和追溯。
