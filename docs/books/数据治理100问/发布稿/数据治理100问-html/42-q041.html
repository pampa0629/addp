041 数据血缘是什么意思，它与任务依赖关系有什么区别？

一句话回答

数据血缘描述数据从哪里来、经过什么处理形成、又被哪些指标、服务和应用使用；任务依赖描述任务按照什么顺序执行、一个任务开始前必须等待哪些任务完成。任务依赖可以为血缘采集提供线索，但不能直接等同于数据血缘。

当一个指标或报表出现异常时，数据血缘还可以帮助团队沿着数据来源和加工过程向上追溯，定位问题最早出现的环节；也可以向下分析异常会影响哪些指标、模型、服务和业务流程。

一、数据血缘到底要回答什么问题

数据血缘（Data Lineage）是对数据来源、派生、引用和服务关系的记录与展示。它主要回答：

  • 这项数据来自哪些来源；
  • 经过哪些复制、转换、关联、聚合或算法处理；
  • 形成了哪些数据集、指标、标签和模型结果；
  • 被哪些服务、报表、模型和应用使用；
  • 某个上游发生变化时，会影响哪些下游；
  • 当前关系是设计上声明的，还是实际运行中发生过的；
  • 这项关系在哪个时间、哪个版本和哪次执行中成立。

数据血缘不是一张装饰性的流程图，也不是把所有系统和任务连接起来的关系图。它需要说明关系的对象、方向、粒度、时间和证据。

例如，以下关系可以属于数据血缘：

客户主数据 + 订单数据
    -> 客户订单主题数据集
    -> 客户价值指标
    -> 客户分析服务和经营报表

这里既有数据项之间的派生关系，也有指标、服务和产品对数据的使用关系。

二、任务依赖关系是什么

任务依赖关系描述任务或工作流步骤之间的执行前后关系，主要回答：

哪个任务必须先完成，另一个任务才能开始？

例如，一个工作流可能规定：

采集订单数据 -> 标准化订单数据 -> 计算订单指标 -> 刷新报表

任务依赖通常用于：

  • 任务调度和拓扑排序；
  • 判断某个步骤是否具备执行条件；
  • 失败阻断和重试；
  • 传递上游任务声明的输出参数；
  • 展示工作流的执行进度。

任务依赖是一种执行控制关系。它描述的是任务如何协作，不一定描述任务实际读写了哪些数据。

三、两者的关键区别

对比维度 任务依赖 数据血缘
关注对象 任务、步骤和执行节点 数据项、字段、指标、服务和产品
核心问题 谁必须先执行 数据从哪里来、形成了什么、影响了谁
主要用途 调度、拓扑排序、失败阻断和重试 来源追溯、影响分析、质量定位和审计
关系来源 工作流配置和调度定义 数据映射、SQL、模型、服务定义和实际执行
是否代表真实读写 不一定 应尽量具有真实读写或明确声明证据
典型粒度 任务或工作流步骤 数据集、表、文件、字段、指标和服务
时间属性 主要描述计划执行关系 还要记录版本、执行批次和关系有效时间

最重要的一点是：

“任务 A 先于任务 B 执行”，不能证明“任务 B 的输出数据来源于任务 A 的输出”。

任务 B 可能只是等待任务 A 完成环境准备、文件解压或权限检查，也可能根本没有读取任务 A 产生的数据。

反过来，一个视图、数据服务或人工导入的数据可能具有清楚的数据血缘，却没有进入统一调度工作流，也就不存在相应的任务依赖。

四、用一个例子理解两种关系

以城市交通拥堵指数为例。平台需要汇聚道路路网和设备观测，计算道路分段速度，进一步形成区域拥堵指数，并通过服务和报表提供给业务人员。

1. 任务依赖关系

工作流可以编排为：

更新道路路网 --\
                 +--> 计算道路分段速度 -> 质量检查 -> 计算拥堵指数 -> 发布交通查询服务
汇聚设备观测 --/

它表达的是：计算道路分段速度之前，需要道路路网和设备观测两个任务完成；计算拥堵指数之前，需要速度计算和质量检查完成。

2. 数据血缘关系

数据血缘更接近：

道路路网数据 + 设备观测数据
    -> 道路分段速度数据
    -> 区域拥堵指数
    -> 交通查询服务和运行分析报表

其中：

  • 质量检查任务属于任务依赖链，但如果没有修改或产生新的业务数据，就不形成普通的数据派生关系；
  • 发布服务可能没有产生新的物理数据，但形成“数据项被某个已发布服务提供”的服务依赖；
  • 道路分段速度任务到底读取了哪些数据，应以输入输出映射和实际执行事实为依据，而不能仅从任务前后顺序猜测。

这个例子说明，任务依赖和数据血缘在图形上可能有重合，但节点类型和关系含义不同。

五、数据血缘有哪些常见层次

1. 系统级血缘

描述业务系统、数据仓库、数据平台、外部服务和业务应用之间的数据流向，适合管理者了解整体架构和数据流通范围。

2. 数据项级血缘

描述表、视图、文件、对象、消息主题、主题数据集和模型结果之间的来源和派生关系，是最适合优先落地的基础层次。

例如：

订单来源表 -> 订单标准化表 -> 订单主题数据集 -> 经营分析报表

3. 字段级血缘

描述来源字段经过映射、转换和计算后形成目标字段。

例如：

order.amount + order.tax
    -> fact_order.total_amount

字段级血缘对指标口径、敏感字段传播和问题排查很有帮助，但实现成本高。SQL 中的别名、CTE、通配符、表达式、存储过程、Notebook 和自定义代码，都可能使自动解析变得不可靠。

4. 业务级血缘

描述业务事实、指标、标签、报表、模型和业务决策之间的关系。

例如：

订单和签收事实
    -> 订单及时交付率
    -> 履约分析报表
    -> 供应链调度决策

业务级血缘可以让业务人员理解“一个指标从哪里来、用于什么决策”，但它不能替代底层技术血缘。

实践中，不需要一开始就追求所有层次同时完整。通常应先建立重点数据项级血缘，再为核心指标、敏感字段和复杂转换补充字段级和业务级关系。

六、设计血缘、静态血缘和运行血缘

血缘还可以按照证据来源进行区分。

1. 设计血缘

设计血缘来自数据模型、字段映射、工作流配置、数据契约和服务定义，表达“计划怎样产生和使用数据”。

它可以在程序尚未运行时帮助团队进行方案评审、变更影响分析和依赖检查。

2. 静态解析血缘

静态解析血缘通过解析 SQL、脚本、Notebook、配置或模型定义，推断其中的输入、输出和字段关系。

它适合补充设计血缘，但解析能力受数据库方言、动态 SQL、变量、用户自定义函数和运行分支影响。无法可靠确定的关系应标记为不完整或待确认，不能用猜测制造“看起来很完整”的血缘图。

3. 运行血缘

运行血缘来自一次实际执行时记录的输入、输出、写入方式和版本，表达“这一次实际上发生了什么”。

运行血缘适合审计、问题定位和历史追溯。例如，一次任务虽然按照同一份工作流定义运行，但由于条件分支和数据范围不同，实际读取的来源可能与设计血缘不完全相同。

4. 三种血缘应当并存但不能混为一谈

设计血缘适合回答“如果修改这个对象，可能影响谁”；运行血缘适合回答“某次结果实际使用了谁”；静态解析血缘则是从代码和配置中获取证据的一种方式。

当三者不一致时，应保留来源、采集方式、版本和时间，供治理人员判断，而不是简单覆盖成一条没有证据等级的关系。

七、任务依赖可以帮助采集血缘，但不能替代血缘

任务依赖与数据血缘通常存在联系：工作流中的输入输出声明、步骤参数绑定和执行结果，可以为血缘采集提供重要线索。

但应当遵循以下原则：

  1. 只有任务依赖，没有输入输出数据绑定，不能自动产生数据血缘；
  2. 任务执行器应记录实际读取和写入的数据项，而不是让血缘模块猜测；
  3. 任务失败或取消时，可以保留诊断信息，但不能伪造已经成功产生的派生关系；
  4. 数据服务、视图和外部系统依赖不应因为没有工作流任务而被遗漏；
  5. 编排器负责任务顺序，真实读写模块负责提供血缘事实，血缘模块负责统一解析、保存和查询。

在平台实践中，比较可靠的链路是：

任务或服务实际执行
    -> 记录输入、输出、操作和版本事实
    -> 血缘采集器解析资源身份
    -> 保存关系证据
    -> 生成当前血缘投影和历史查询结果

这比让平台根据 depends_on 配置直接拼接一张血缘图更加可靠。

八、数据血缘如何帮助排查计算结果异常

这是数据血缘最实用的价值之一。

1. 从异常结果向上追溯

发现指标、报表或模型结果异常后，可以沿着血缘反向追溯，逐层定位问题最早出现的位置。

例如，区域拥堵指数突然异常，可以沿着以下路径排查：

拥堵指数异常
    -> 区域汇总结果
    -> 道路分段速度
    -> 设备观测汇聚
    -> 原始设备数据或道路路网数据

沿途可以依次检查：

  • 指标计算是否使用了正确的规则和版本；
  • 区域汇总是否遗漏了某些道路或时间分区；
  • 道路速度计算是否出现异常值；
  • 设备数据是否延迟、重复或大幅减少；
  • 路网数据是否发生结构、空间范围或坐标参考变化；
  • 哪一次任务、哪批数据或哪个字段最早出现异常。

血缘把“结果异常”连接到可能的来源和处理节点，使排错不必从最后一个报表任务开始盲目翻日志。

2. 从异常来源向下分析影响

如果发现设备数据缺失、路网字段变更或某项标准规则错误，可以沿着血缘向下查看它影响了哪些：

  • 主题数据集；
  • 指标和标签；
  • 报表和大屏；
  • 模型和算法结果；
  • 数据服务和业务应用。

这类分析常用于决定是否暂停服务、重新计算、通知使用者或安排专项修复。

3. 血缘不能单独完成排错

血缘告诉我们“应该沿哪条路径排查”，但不能单独告诉我们“问题一定发生在哪里”。实际排错还需要结合：

  • 运行元数据：任务状态、处理量、耗时和延迟；
  • 数据质量规则：完整性、准确性、一致性和有效性检查；
  • 数据剖析结果：空值率、数据分布和异常值；
  • 执行日志、错误信息和资源使用情况；
  • 数据版本、代码版本和配置版本；
  • 节假日、政策、活动等业务事件。

另外，排错必须使用与异常发生时间对应的历史血缘。如果只看当前血缘，可能出现这样的误判：今天的指标已经更换来源，但异常发生在昨天，当前关系无法准确解释昨天的结果。

九、血缘关系应该如何采集和维护

1. 在工作流和数据开发中显式记录

可视化工作流、SQL 任务、数据模型和正式工作流应明确声明输入、输出、操作和写入方式。这样可以形成稳定的设计血缘，并为运行时记录提供结构。

2. 在执行成功后记录实际事实

真实读写数据的模块应记录本次执行实际使用的来源、产生的目标、输入输出端口、写入方式和版本。只有成功提交的数据结果，才适合建立有效的派生关系。

3. 由服务发布记录服务依赖

一个查询服务、空间服务或瓦片服务可能没有创建新的物理数据，但它会读取并对外提供某些数据项。发布服务时应保存来源数据、发布版本和依赖快照，形成数据项到已发布服务的服务依赖。

4. 对外部和人工过程受控补录

如果来源系统没有被平台观测，或者数据经过人工整理和线下交换，可以由责任人补充声明血缘，但需要标记来源、责任、时间和证据等级，不能把人工估计伪装成运行事实。

5. 持续处理变更和历史

血缘关系会随着数据重命名、来源切换、模型版本和服务发布而变化。平台应保留关系证据和时间状态，既能查询当前有效关系，也能回答历史批次使用过哪些来源。

十、血缘关系的粒度和可信度如何控制

1. 不要把每个字段都当成独立数据对象

字段通常是数据项内部的结构内容，不应因为需要字段级血缘，就把每个字段登记成一个独立数据项。字段关系应绑定到数据项和对应的结构版本。

2. 不可靠的推断要明确标记

SQL 动态拼接、通配符、存储过程和 Notebook 代码可能无法被完整解析。对于不能可靠确认的关系，应标记为“不完整”“待确认”或仅保留候选证据，不能用任意的置信度数字掩盖事实不确定性。

3. 资源身份要稳定

血缘需要使用稳定的数据项标识、定位信息和必要的指纹。单纯依赖当前表名、文件路径或展示名称，无法支撑重命名、迁移和历史查询。

4. 关系视图不能成为第二套事实源

血缘模块负责统一保存关系证据和查询投影，但数据项身份由元数据模块维护，任务定义由任务所属模块维护，服务发布事实由服务模块维护。血缘查询不能复制各模块的主数据。

十一、案例：从交通指标异常到根因定位

某城市交通平台每天计算区域拥堵指数。某天上午，管理人员发现几个区域的拥堵指数突然同时下降，但现场反馈道路并没有明显变得通畅。

1. 先沿血缘向上追溯

平台从拥堵指数进入区域汇总，再追到道路分段速度，发现异常区域的速度数据量比平时少了约一半。继续追溯后发现，部分设备观测没有进入当天的汇聚结果。

2. 再结合运行信息排查

运行元数据显示，汇聚任务状态为“成功”，但本次处理的设备分区数量明显减少；任务日志显示某个上游接口返回了不完整的分页结果。

如果只有任务依赖图，平台只能看到“汇聚任务成功，指标任务成功”；如果有数据血缘并关联运行元数据，就能够发现“结果异常来自输入数据覆盖不足”。

3. 分析下游影响

沿血缘向下检查后，平台确认交通查询服务、拥堵日报和信号配时分析都使用了该批结果，于是：

  • 暂停发布这批不完整的指标结果；
  • 保留上一批经过验证的数据供查询；
  • 修复接口分页问题并重新汇聚；
  • 重新计算受影响区域和时间窗口；
  • 将该异常沉淀为数据量和覆盖范围检查规则。

这个案例说明，血缘不是排错工具本身，但它能够把结果、来源、处理过程和下游影响连接起来，是数据问题定位和业务风险控制的重要导航。

十二、常见误区

误区一：工作流图就是数据血缘

工作流图展示任务和步骤，数据血缘展示数据关系。二者可以关联，但不能互相替代。

误区二：前后执行的任务一定存在数据派生关系

任务依赖只说明执行顺序，必须结合实际输入输出或明确的数据声明才能建立派生血缘。

误区三：任务成功就证明数据结果正确

任务成功只能说明程序完成了技术执行。数据是否完整、是否符合业务口径，还需要质量规则、运行信号和业务判断。

误区四：血缘只能记录表到表

文件、对象、空间数据、消息主题、字段、指标、模型和已发布服务都可能参与血缘，但需要有稳定身份和清楚的关系语义。

误区五：SQL 解析出来的关系一定准确

动态 SQL、存储过程、Notebook 和自定义代码可能无法被完整解析。不确定关系应明确标记，不能伪装成确定事实。

误区六：血缘只保留当前关系就够了

数据来源、模型和服务都会变化。没有历史证据，就无法解释过去某批结果使用了什么来源。

误区七：有了血缘就不需要日志和质量检查

血缘负责关系追溯和影响分析，日志负责运行诊断，质量检查负责判断数据是否符合要求，三者需要配合。

十三、实践检查清单

  1. 是否明确区分任务依赖关系和数据血缘关系？
  2. 重点数据项、指标、服务和应用是否能够查询上下游关系？
  3. 血缘关系是否记录来源、方向、粒度、时间和证据？
  4. 是否区分设计血缘、静态解析血缘和实际运行血缘？
  5. 数据执行是否记录真实输入、输出、写入方式和版本？
  6. 失败或取消的任务是否不会伪造成功的派生关系？
  7. 是否支持从异常结果向上追溯根因，并向下分析影响范围？
  8. 字段级血缘是否绑定数据项和结构版本，而不是把字段伪装成独立数据项？
  9. 无法可靠解析的关系是否明确标记为不完整或待确认？
  10. 是否结合运行元数据、质量规则、日志和业务事件完成问题排查？

小结

任务依赖解决“任务什么时候执行、谁必须先完成”，数据血缘解决“数据从哪里来、经过什么处理、影响了什么结果”。任务依赖可以为血缘采集提供线索，但只有真实输入输出、明确映射和可追溯证据，才能形成可信的数据血缘。

数据血缘的价值不仅是画出上下游关系，更在于支持两类实际工作：从异常结果向上追溯根因，从异常来源向下分析影响。它需要与元数据、运行监控、数据质量、日志和业务事件结合，才能真正帮助组织排错、变更和控制业务风险。
