048 什么是数据契约（Data Contract），它如何降低上下游协作成本？

一句话回答

数据契约是数据生产者和消费者围绕共享数据形成的明确、可验证、可持续维护的约定。它不仅规定字段结构，还应说明业务语义、质量、鲜活度、交付方式、安全要求、责任人、版本和变更机制，使上游知道自己承诺提供什么，下游知道可以依赖什么，并让不符合约定的变化尽可能在影响业务之前被发现。

数据契约要解决的，不只是“数据能不能传过去”，而是“这份数据能不能被下游长期、稳定、正确地使用”。

一、为什么需要数据契约

在许多组织中，上游业务系统只对自己的功能负责，下游数据团队则通过数据库表、接口、文件或消息获取数据。双方可能从未明确约定：

  • 哪些字段可以长期依赖；
  • 每个字段的业务含义是什么；
  • 哪些值允许为空；
  • 枚举值会不会增加；
  • 数据什么时候能够到达；
  • 出现迟到、重复和缺失时由谁处理；
  • 上游修改结构或口径时怎样通知下游；
  • 变化发生后需要给下游多长迁移时间。

结果是，上游一次看似普通的系统升级，可能造成一连串影响：

  • 字段改名，数据汇聚任务直接失败；
  • 字段类型变化，部分记录无法写入数据仓库；
  • 新增订单状态，下游仍按旧枚举计算；
  • 金额含义从“含税”变成“不含税”，任务正常运行但报表结果错误；
  • 数据到达时间推迟，晨会使用了前一天的不完整指标；
  • 删除一个“不再使用”的字段，却导致多个模型、报表和服务异常。

这些问题的根源通常不是技术不会处理，而是上下游之间没有形成稳定、透明并能够执行的约定。

二、什么是数据契约

数据契约可以理解为数据生产者与消费者围绕某项共享数据签订的“工作协议”。它明确：

  • 生产者提供什么数据；
  • 消费者可以怎样理解和使用；
  • 数据需要达到什么质量和时效；
  • 双方分别承担什么责任；
  • 结构和语义发生变化时怎样协商；
  • 如何检测违约并进行处置。

契约对象可以是：

  • 一张或一组共享数据表；
  • 数据仓库中的主题数据集；
  • 文件及其清单；
  • API 提供的数据；
  • 持续发布的事件流；
  • 指标、标签或模型结果；
  • 作为数据产品对外提供的数据成果。

契约可以使用文档描述，但仅靠一份长期不更新的文档通常不够。成熟的数据契约应尽量结构化，使字段、类型、质量、鲜活度和兼容性等要求能够被系统自动检查。

三、一份数据契约应该包括什么

数据契约没有唯一固定格式，但通常应覆盖以下内容。

内容 需要回答的问题
身份与范围 契约约束的是哪项数据、哪个版本和哪些使用场景
生产者 谁产生数据，谁有权解释业务含义
消费者 谁正在使用数据，关键用途是什么
结构 字段、类型、主键、是否允许为空、枚举和嵌套结构是什么
业务语义 每个字段和事件表示什么，使用哪个时间、单位和统计口径
质量要求 完整性、唯一性、有效性、一致性和准确性达到什么要求
鲜活度 数据以什么频率更新，最晚何时到达，允许多大延迟
交付方式 通过表、文件、API 还是事件流提供，怎样访问和确认交付
安全与合规 数据敏感等级、允许用途、访问范围、脱敏和保留要求是什么
版本与变更 哪些变化兼容，哪些必须升级版本，如何通知和迁移
可观测性 怎样监测到达、数量、结构、质量和分布变化
事件处置 违约后怎样告警、阻断、降级、修复和复盘
服务责任 负责人、支持渠道、响应时间和维护状态是什么

并非每份契约都必须写成庞大的规范。关键数据需要较完整的约定，普通内部数据可以采用简化模板，但最基本的结构、语义、责任和变更规则不能缺失。

四、数据契约不只是Schema

Schema通常定义字段名称、数据类型、是否必填、嵌套结构等技术内容，是数据契约的重要组成部分，但不是全部。

例如，下面两个版本在Schema上可能完全相同：

order_amount: decimal(18, 2)

但它的语义可能从“订单原始含税金额”变为“扣除优惠后的不含税应付金额”。字段没有改名，类型也没有变化，所有技术校验都能通过，下游经营分析却会得到错误结果。

因此，数据契约至少还要说明：

  • 金额是否含税；
  • 是否扣除折扣和退款；
  • 使用什么币种；
  • 金额对应订单的哪个状态；
  • 业务口径从何时开始生效。

结构兼容不等于语义兼容。很多最难发现的数据事故，恰恰发生在“任务没有报错、数据也正常到达，但含义已经变化”的情况下。

五、数据契约与其他概念有什么区别

1. 与数据标准的区别

数据标准提供可以被多个系统和模型复用的统一要求，例如客户编码规则、行政区划码值、金额单位和日期格式。

数据契约针对具体的数据交付关系，说明某项数据采用哪些标准、达到什么质量、何时交付以及怎样变更。

可以理解为：

数据标准提供公共规则，数据契约把相关规则落实到一次持续的数据供给中。

2. 与 API 契约的区别

API 契约主要规定接口地址、请求参数、响应结构、状态码、鉴权和调用方式。数据通过 API 提供时，API 契约可以成为数据契约的技术组成部分。

但数据契约的范围更广：

  • 数据可能通过表、文件或事件流交付，并不存在 API；
  • API 契约不一定完整描述字段的业务口径、数据质量和鲜活度；
  • 数据契约还要说明生产者责任、消费者用途和变更机制。

因此，不能把数据契约简单等同于接口文档。

3. 与 SLA 的区别

服务级别协议（Service Level Agreement，SLA）主要约定可用性、响应时间、恢复时间或数据到达时限等服务指标。

SLA 可以成为数据契约的一部分，但它通常不负责完整定义数据结构、业务含义和质量规则。

4. 与数据质量规则的区别

质量规则用于检查数据是否满足特定要求，例如订单编号不能为空、金额不能小于零、每日重复率不得超过某个阈值。

数据契约说明为什么需要这些要求、由谁承担责任、违反后如何处置，并把质量规则与结构、语义、鲜活度和版本放在同一约定中。

5. 与数据共享或使用协议的区别

组织之间的数据共享协议、授权文件和法律合同，重点解决权利、义务、用途限制、保密、合规和法律责任。

数据契约可以引用这些要求，并将部分内容转化为权限和使用规则，但不能替代正式的法律协议。

6. 与数据产品的关系

数据产品需要有明确用户、用途、质量、访问方式、责任和持续运营机制。数据契约正是数据产品向消费者作出稳定承诺的重要组成部分。

但一份契约本身不等于一个完整的数据产品。数据产品还要能够被发现、申请、使用、支持和评价。

六、生产者、消费者和治理方各自负责什么

数据契约不是下游单方面向上游提出要求，也不是治理部门替双方写一份文件。

1. 数据生产者

生产者通常最了解数据产生的业务过程，应负责：

  • 说明数据的业务含义和产生条件；
  • 提供符合约定的结构、质量和鲜活度；
  • 在发布前检查不兼容变化；
  • 提前通知计划变更；
  • 对源头业务问题进行解释和修复；
  • 维护负责人、版本和支持渠道。

2. 数据消费者

消费者应负责：

  • 说明关键使用场景和真正依赖的内容；
  • 不依赖契约之外的临时字段和内部结构；
  • 按约定方式访问和使用数据；
  • 反馈质量问题和新增需求；
  • 在约定期限内完成版本迁移；
  • 不把一次性分析要求无限扩大为生产者的永久承诺。

3. 数据治理与平台团队

治理和平台团队主要提供公共机制：

  • 契约模板和最低要求；
  • 统一的数据标准和质量规则；
  • 契约登记、检索、版本和审批能力；
  • 自动化Schema校验、质量检测和兼容性检查；
  • 血缘、影响分析、可观测性和通知机制；
  • 跨领域争议协调和企业级规则执行。

治理团队不应替代业务领域解释数据，也不应成为每一次上下游沟通的人工中转站。

七、数据契约如何进入数据生产流程

只有在数据发布和运行过程中得到执行，契约才能真正降低协作成本。

识别生产者、消费者和关键场景
        ↓
共同定义结构、语义、质量和鲜活度
        ↓
登记契约、责任人和初始版本
        ↓
在开发和发布前进行自动校验
        ↓
数据交付后持续监测履约情况
        ↓
异常告警、处置和根因复盘
        ↓
变更评估、版本升级和消费者迁移

1. 尽量在生产端提前检查

如果数据进入数据仓库以后才发现字段类型变化，所有下游任务都已经暴露在风险中。更好的做法是在上游发布接口、消息或共享表之前进行契约校验。

生产端无法完成全部检查时，也应在数据进入公共链路的最前端检测，而不是等报表出错后才由业务人员发现。

2. 运行中持续检查

发布时结构正确，不代表以后一直符合契约。运行过程中还要监测：

  • 数据是否按时到达；
  • 记录数量是否异常；
  • 关键字段是否缺失；
  • 枚举、分布和业务口径是否变化；
  • 质量规则是否持续满足；
  • 服务是否可访问。

数据契约说明“应该是什么样”，数据可观测性帮助判断“现在是不是仍然这样”。

3. 利用血缘评估影响

契约变更前，应通过数据血缘识别受影响的模型、指标、报表、数据服务和消费者。没有消费关系和影响分析，所谓提前通知很容易变成向一个无人维护的群组发送消息。

八、违反契约是否必须中断流水线

不应把所有契约违约都设计成“一律阻断”或“一律放行”。处置方式取决于问题是否会导致错误决策、数据泄露或不可恢复的污染。

问题类型 典型情况 建议处置
安全与合规风险 敏感字段未脱敏、越权交付 立即阻断并升级处理
破坏性结构变化 删除必需字段、关键字段类型不兼容 阻断发布或隔离异常批次
关键业务错误 主键大面积缺失、金额口径与契约不符 阻断关键消费，保留现场并修复
严重鲜活度问题 日报数据未到齐却将被用于经营决策 标记不可用，阻止发布正式结果
一般质量波动 非关键字段完整率小幅下降 记录、告警并限期处理
轻微分布变化 数量或分布偏离历史基线但尚未确认异常 持续运行并触发调查
契约外新增字段 新增可选字段且不影响现有消费者 允许发布，更新版本和说明

即使不中断，也不能悄悄忽略。系统应记录违约时间、影响范围、责任人、处置结果和是否需要调整契约或观测基线。

对于关键链路，还可以预先约定降级方式，例如继续提供上一个完整批次、将结果标记为“数据未完整”或暂停对外发布指标。降级必须对消费者可见，不能让过期数据伪装成最新结果。

九、数据契约如何管理版本和变化

数据不会永远不变。契约的目标不是冻结上游，而是让变化可预期、可评估、可迁移。

1. 兼容性不能只看字段增删

通常情况下，新增一个可选字段比删除字段更容易兼容，但仍需结合消费者判断：

  • 新增枚举值可能使下游程序进入未知分支；
  • 扩大字段长度通常兼容，改变单位却可能不兼容；
  • 字段名称和类型不变，业务含义变化仍属于破坏性变化；
  • 提前或推迟数据到达时间，也可能影响关键业务流程。

2. 破坏性变化应发布新版本

删除字段、修改关键类型、改变统计口径或调整事件含义时，通常需要：

  1. 识别现有消费者和影响范围；
  2. 说明变化原因和新旧差异；
  3. 发布新的契约版本；
  4. 提供明确、有限的迁移期限；
  5. 跟踪关键消费者完成迁移；
  6. 到期后停止旧版本，避免长期双轨运行。

版本机制不等于永久维护所有历史接口。迁移期是为了控制业务风险，最终仍应收敛到当前有效版本。

3. 紧急变化也要留下记录

安全漏洞、监管要求或严重业务缺陷可能无法等待完整迁移周期。此时可以执行紧急变更，但仍应记录决策人、影响、替代方案和后续修复计划，不能把“紧急”变成绕过契约的常态。

十、案例：电商订单事件怎样建立数据契约

某电商企业的订单系统持续发布订单事件，供多个下游使用：

  • 仓储系统根据已支付订单安排出库；
  • 财务系统进行对账和收入处理；
  • 客服系统查询订单状态；
  • 数据仓库计算销量、销售额和退款率；
  • 风控系统识别异常交易。

1. 没有契约时发生了什么

订单系统升级时，将状态 PAID 拆分为 PAID 和 PARTIALLY_PAID，并把金额字段从订单原价改为优惠后实付金额。

消息结构没有明显错误，大多数下游任务继续运行，但产生了不同问题：

  • 仓储系统不认识新状态，部分订单没有出库；
  • 财务系统继续把金额当作含税原价；
  • 经营报表中的销售额突然下降；
  • 风控规则误判部分分期订单；
  • 各团队分别排查，花费大量时间才发现同一个源头变化。

2. 契约需要明确什么

订单事件契约应至少说明：

  • 事件名称、业务含义和触发时点；
  • 订单、客户和商品的标识规则；
  • 事件唯一标识和去重方式；
  • 订单状态的完整枚举及转换含义；
  • 金额是否含税、是否扣除优惠、使用什么币种；
  • 订单时间、支付时间和事件产生时间的区别；
  • 允许迟到和乱序的范围；
  • 交付频率、可用性和保留期限；
  • 敏感字段、允许用途和访问权限；
  • 负责人、版本和变更通知方式。

3. 变化应怎样处理

新增支付状态前，订单团队先发布候选契约版本并进行兼容性检查。血缘和消费者登记显示仓储、财务、风控和经营分析都依赖订单状态。

各方共同确认：

  • 新状态的业务定义和状态转换规则；
  • 哪些消费者必须修改逻辑；
  • 旧版本保留到什么时间；
  • 怎样验证新旧版本的金额和订单数量；
  • 切换失败时怎样回退或暂停消费。

完成迁移后，旧版本按计划停止，而不是长期维护两套含义不同的订单事件。

4. 业务价值怎样衡量

数据契约的价值可以通过以下指标观察：

  • 上游变化导致的下游事故次数；
  • 不兼容变化在发布前被发现的比例；
  • 事故定位和恢复时间；
  • 数据问题跨团队沟通耗时；
  • 关键数据按时、按质交付的比例；
  • 契约变更后消费者按期迁移的比例。

十一、数据契约与数据网格（Data Mesh）是什么关系

数据契约经常与数据网格（Data Mesh）一起讨论，因为 Data Mesh 强调领域团队对本领域的数据产品承担端到端责任，并将其持续提供给其他领域。不同领域要独立演进，又要让数据产品能够跨领域组合，就必须明确数据结构、语义、质量、责任和变更规则。

这里的“数据网格”不是传输数据的计算机网络（Network），也不是用网络设备把数据库连接起来。Data Mesh 是一种面向大型复杂组织的数据治理和数据架构思路，重点解决领域责任、数据产品、自助式平台和联邦治理问题。其完整概念可参见第016问。

在 Data Mesh 中，数据契约主要发挥三方面作用：

  1. 让领域数据产品对消费者作出明确承诺；
  2. 让跨领域统一规则能够被自动验证；
  3. 在领域自主变化与企业整体稳定之间建立边界。

但数据契约并不是 Data Mesh 专属能力。

集中式数据仓库中，源业务系统与数据仓库之间需要契约；数据仓库与 BI、算法和数据服务之间也需要契约。数据中台、数据编织（Data Fabric）以及普通的系统集成，同样需要稳定的数据交付约定。

Data Mesh 让数据契约受到更多关注，但只要存在持续的上下游数据依赖，就可能需要数据契约。

十二、数据契约怎样降低协作成本

1. 把隐含依赖变成明确约定

下游不再依赖“这个字段一直存在，所以以后应该也不会变”这样的经验，而是知道哪些内容得到正式承诺。

2. 把事后排错前移到发布检查

结构和兼容性问题可以在上线前发现，减少错误进入多条下游链路以后再逐级排查。

3. 减少重复沟通

业务含义、负责人、质量和鲜活度有统一入口后，新消费者不必反复寻找知情人员询问同样的问题。

4. 缩短故障定位时间

契约、血缘和可观测性结合后，可以快速判断谁违反了哪项约定、影响哪些消费者以及应该由谁处理。

5. 让变化成为可管理过程

上游仍然可以升级，但需要经过影响分析、版本发布、通知和迁移，而不是把变化成本突然转嫁给下游。

6. 形成相互约束而非单向索取

生产者承诺稳定供给，消费者也要遵守允许用途、访问方式和迁移期限。双方围绕真实使用关系协作，而不是无边界地互相提要求。

十三、哪些数据需要建立契约

并非所有数据都值得建立正式契约。以下数据通常应优先考虑：

  • 被多个系统或团队持续使用；
  • 支撑经营、财务、监管或关键业务流程；
  • 以数据产品形式对外提供；
  • 结构或业务规则变化较频繁；
  • 出错后影响范围大、定位成本高；
  • 需要明确质量和鲜活度承诺；
  • 跨领域、跨组织或跨企业共享。

个人临时分析表、短期中间结果和无人消费的数据，不宜全部纳入复杂审批。

可以先选择少量关键共享数据，从最小契约开始：明确生产者、消费者、结构、语义、质量、鲜活度和变更规则。随着使用范围和风险增加，再逐步补充安全、可观测性和服务等级等内容。

十四、常见误区

误区一：有了表结构定义就有了数据契约

表结构不能完整说明业务含义、质量、鲜活度、责任和变更机制。

误区二：数据契约就是 API 文档

API 只是数据交付方式之一，表、文件和事件流同样可以建立数据契约。

误区三：契约由数据治理部门单独制定

治理部门可以提供模板和公共规则，但业务语义和供给承诺必须由生产者、消费者共同确认。

误区四：违反任何规则都必须阻断流水线

应根据安全风险、业务影响和可恢复性分级处置，同时保证所有违约都有记录和责任闭环。

误区五：契约签订后上游不能再变化

数据契约管理变化，而不是禁止变化。关键是进行影响分析、版本管理和有期限的迁移。

误区六：每个消费者都建立一份完全不同的契约

契约应尽量围绕稳定的数据产品形成共同承诺。确有不同服务等级或使用限制时可以扩展，但不应重新制造大量相互矛盾的定义。

误区七：数据网格就是传输数据的网络

数据网格（Data Mesh）是一种组织和治理思路，不是计算机网络（Network）。数据契约也不只适用于 Data Mesh。

误区八：契约文档发布后就完成了

没有自动校验、运行监测、变更通知和责任运营的契约，很容易迅速过期。

十五、实践检查清单

  1. 关键共享数据是否明确了生产者、消费者、业务用途和责任人？
  2. 契约是否同时覆盖结构、语义、质量、鲜活度和安全要求？
  3. 契约中的关键要求是否能够在发布前或运行中自动检查？
  4. 是否根据问题影响区分阻断、隔离、告警和记录？
  5. 契约变化前能否通过血缘和消费者登记评估影响范围？
  6. 是否明确兼容规则、版本、通知方式和有限迁移期限？
  7. 违约事件是否能够进入问题处置、根因分析和持续改进闭环？
  8. 是否优先治理高价值、高复用和高风险数据，避免把契约变成形式化负担？

小结

数据契约的本质，不是给上下游增加一份审批材料，而是把原本隐含在代码、经验和口头沟通中的数据依赖，变成明确、可验证和可维护的共同约定。

它让生产者知道自己需要稳定提供什么，让消费者知道自己能够依赖什么，也让结构、语义和质量变化不再悄无声息地穿过整个数据链路。

当数据契约与标准、质量、血缘、可观测性和版本管理结合起来时，上下游协作才能从“出了问题再找人”转变为“变化之前评估、运行过程监测、发生问题闭环”。这正是数据治理降低协作成本、保障数据持续为业务增值的重要方式。
