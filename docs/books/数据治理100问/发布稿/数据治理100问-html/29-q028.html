028 数据从何而来？

一句话回答

数据来自业务活动和现实世界被记录下来的事实，也来自对既有数据进行关联、计算和推断形成的派生结果。组织获得数据的主要来源包括业务系统、设备与传感器、人工采集、文档与多媒体、合作共享、公共开放和商业采购等。数据治理不仅要知道“数据存在哪里”，还要弄清它由谁、在什么业务过程中、依据什么规则产生，谁是权威来源，是否有权使用，以及怎样持续更新。

数据库、文件、API、消息队列和数据仓库经常被称为“数据源”，这种说法在技术实施中没有问题。但从治理角度看，它们更多是在说明数据的存储位置、传输通道或访问方式，尚未回答数据真正从哪项业务活动或现实观察中产生。

例如，数据仓库中的“月度有效销售额”来自订单、付款、退货和组织数据按照指标规则计算，而不是数据仓库自己创造的业务事实。只有追溯到这些事实的产生过程，才能判断数据含义、责任、质量和可用范围。

一、为什么“数据从何而来”不是一个简单问题

在一个业务系统中查看某个字段，似乎很容易知道数据来源于哪张表。但进入跨系统的数据治理以后，同一个事实可能出现多个记录：

  • 客户名称同时存在于 CRM、合同、财务和售后系统；
  • 商品价格同时出现在产品主数据、报价单、订单和发票中；
  • 土地用途可能分别记录现状用途、规划用途、批准用途和登记用途；
  • 设备状态可能来自控制系统、传感器、维修工单和人工巡检；
  • 地址可能来自用户填写、行政区划库、地图服务和空间定位结果。

这些数据未必互相矛盾。它们可能描述不同时间、不同业务阶段或不同含义下的事实。如果只根据字段名称选择一份数据，就容易把“当前客户地址”当成“订单发生时的收货地址”，或者把“规划用途”当成“当前利用现状”。

因此，治理数据来源至少要回答四个问题：

  1. 事实来源：这项数据由什么现实对象、业务事件或观察活动产生？
  2. 记录来源：哪个组织、岗位、设备或系统负责记录？
  3. 取得来源：治理体系通过数据库、文件、API、消息还是其他方式获得？
  4. 派生来源：如果它是计算结果，使用了哪些上游数据、规则和模型？

只记录一个数据库连接地址，远远不能完成数据来源治理。

二、数据产生的主要来源有哪些

按照事实如何被记录和获得，可以把常见来源概括为以下几类。这些类别并非互相排斥，同一项业务事实可能同时涉及多个来源。

1. 业务系统持续记录的数据

企业和政府的信息化系统，是数据治理最重要的数据来源之一。例如：

  • ERP 记录采购、生产、库存和财务活动；
  • CRM 记录客户、商机和销售过程；
  • 电商系统记录浏览、下单、支付和退货；
  • 政务系统记录申请、受理、审批和监管；
  • 自然资源系统记录调查、规划、供地、登记和利用变化；
  • 医院系统记录诊疗、检验、用药和费用。

这类数据通常随着业务办理持续产生。其优势是与具体对象、事件、人员和流程关联紧密，能够反映业务运行；其局限是每个系统往往只记录本环节需要的事实，口径、标识和颗粒度也可能不同。

业务系统是数据的重要来源，但不意味着系统中的每个字段都是全组织唯一权威。例如，CRM 中的客户联系信息可能适合营销，财务系统中的开票主体才适合结算，订单中保存的地址则可能是交易发生时的历史快照。

2. 设备、传感器和机器自动产生的数据

现实世界可以通过各类设备被持续感知，例如：

  • 工业设备的温度、振动、电流和运行状态；
  • 车辆和船舶的位置、速度和轨迹；
  • 气象、水文、环境和管网监测数据；
  • 摄像头、遥感卫星、无人机和雷达数据；
  • 门禁、闸机、智能电表和物流温控设备数据；
  • 应用程序、服务器和网络设备产生的日志。

这类数据通常频率高、数量大，并带有明确的时间或空间属性。自动采集可以减少人工录入，却不等于天然准确。设备校准、安装位置、采样频率、通信中断、时钟偏差和固件升级都会影响结果。

治理时不仅要保存测量值，还应尽可能记录设备身份、测点位置、采集时间、单位、精度、状态和校准信息，否则很难判断数据是否可比、异常究竟来自业务还是设备。

3. 人工录入、调查、检测和核查数据

并非所有事实都能由系统自动产生。大量重要数据仍来自人的观察和判断，例如：

  • 客户填写的资料和业务人员录入的信息；
  • 问卷调查、访谈和统计填报；
  • 现场测绘、抽样、盘点和巡检；
  • 实验室检验和质量验收；
  • 专家认定、风险评估和执法核查；
  • 对算法识别结果的人工复核。

人工采集可以处理复杂情境和非标准问题，但可能受到定义理解、操作习惯、主观判断和工作压力影响。治理重点包括统一表单和术语、设置必要校验、记录采集人与时间、保留证据，以及对重要认定设置复核与变更流程。

“人工产生”不代表数据不可靠，“系统自动产生”也不代表数据一定可靠。可靠性取决于产生过程是否受控、责任是否明确以及结果能否验证。

4. 文档、图片、音视频和专业数据成果

组织中的很多事实并不以数据库记录存在，而是保存在：

  • 合同、报告、政策、档案和会议纪要；
  • 图片、录音、视频和扫描件；
  • CAD图纸、BIM 模型和三维场景；
  • GIS 图层、遥感影像和测绘成果；
  • 地震波、气象格点、医学影像等行业数据；
  • 邮件、工单描述和客服对话。

这些数据可能由业务过程直接形成，也可能是一项专业采集和加工的成果。治理不能只关注文件名和存放目录，还要识别内容描述的对象、时间、空间范围、版本、形成单位、审批状态和适用用途。

通过文字提取、图像识别、语音转写和多模态模型，可以从非结构化内容中派生实体、关系、标签和摘要。但机器提取结果应与原始内容区分，并记录模型、规则、置信度和人工确认状态。

5. 其他组织共享或交换的数据

跨部门、上下级单位、合作伙伴和产业链之间经常需要共享数据，例如：

  • 集团总部与子公司共享经营和主数据；
  • 政府部门之间共享登记、监管和公共服务数据；
  • 供应商、制造商和物流企业交换订单及履约数据；
  • 医疗机构之间在合规范围内共享诊疗信息；
  • 可信数据空间中的参与方按规则提供数据产品。

共享数据的难点不只在于接口能否连通，还包括：提供方是否有权提供、接收方可以用于什么目的、字段和口径如何理解、多久更新、出现错误由谁处理，以及共享关系结束后如何处置。

即使数据来自组织内部的另一个部门，也不能默认可以无限制使用。组织边界以内仍然存在职责、权限、个人信息和商业秘密等约束。

6. 公共开放数据

政府、国际组织、科研机构和公共服务平台可能发布行政区划、人口经济、气象环境、交通、地图、政策法规等开放数据。

公共可访问不等于没有使用条件。使用前仍需确认：

  • 发布主体和原始出处是否可信；
  • 数据许可是否允许复制、加工和商业使用；
  • 更新日期、覆盖范围和统计口径是否清楚；
  • 接口是否稳定，历史版本是否保留；
  • 数据是否经过匿名化，能否与其他数据重新识别个人；
  • 引用、署名或再发布是否有特定要求。

从网页下载到的数据不一定是开放数据；搜索引擎能够找到，也不代表组织依法有权采集和使用。

7. 商业采购和授权使用的数据

当内部数据和开放数据不能满足需要时，组织可能购买地图、遥感影像、企业信息、市场研究、信用、气象或行业数据库等数据服务。

治理时要同时关注数据内容和合同权利：

  • 可以由哪些部门和系统使用；
  • 是否允许生成派生产品或提供给客户；
  • 是否限制下载、缓存、复制和训练模型；
  • 更新频率、质量标准和故障责任如何约定；
  • 合同终止后原始数据和派生结果如何处理；
  • 供应商更换后，历史数据和业务连续性如何保障。

采购费用只能说明获得了某种使用权，不能自动证明数据准确、适用或可以任意再分发。

8. 根据既有数据计算形成的派生数据

指标、标签、画像、评分、预测、识别结果、专题图和汇总表，都不是直接从现实活动中原样记录的，而是根据来源数据和规则产生的派生数据。

例如：

  • 销售增长率由不同时期的销售指标计算；
  • 高价值客户标签由消费、利润和活跃度规则生成；
  • 设备故障风险由传感器、维修记录和算法模型预测；
  • 低效用地识别结果由地块、规划、供地、项目和利用数据综合计算；
  • 影像变化图斑由多期遥感影像和识别算法产生。

派生数据同样可以成为重要业务依据，但不能把它伪装成原始事实。治理时需要记录上游数据、计算口径、规则或模型版本、执行时间、适用范围和质量状态，并在上游变化后判断是否需要重新计算。

9. 模拟数据、合成数据和 AI 生成数据

有些数据并非现实业务事件的直接记录，而是为了测试、训练、推演或保护隐私而生成，例如：

  • 软件测试使用的模拟订单和客户；
  • 数字孪生或科学模型生成的仿真结果；
  • 根据统计分布生成的合成数据；
  • 生成式 AI 创建的文本、图片或样本；
  • 为少见故障和极端事件构造的训练数据。

这类数据有明确价值，但必须与真实观测数据清楚区分。使用者需要知道生成方法、参数、假设、与真实分布的差异及可用范围，不能把模拟结果当成已经发生的业务事实。

三、数据的业务来源、技术来源和取得方式有什么区别

实践中经常把以下三类信息都写在“数据来源”字段里，导致描述含混。

层次 要回答的问题 示例
业务来源 什么对象、事件或观察产生了事实 客户付款、设备测温、现场检验
记录来源 谁负责记录，哪个系统保存权威记录 财务系统、温控设备、质检人员
技术来源 当前从哪里读取数据 PostgreSQL 表、对象存储文件、Kafka主题、第三方 API
取得方式 数据怎样进入或被访问 批量文件、数据库同步、CDC、API 调用、消息订阅、联邦查询
派生来源 结果依据哪些数据和规则产生 上游表、指标公式、算法模型和版本

例如，“订单数据来自MySQL 数据库”只说明了技术来源。更完整的描述应是：订单由客户下单行为产生，电商交易系统负责记录，某订单库是当前权威记录位置，治理平台通过变更数据捕获持续获得订单变化。

数据库迁移、接口改造或存储更换以后，技术来源可能改变，但订单的业务来源并没有改变。把这些层次分开，才能在系统变化时保持业务语义和责任稳定。

四、什么是权威来源

权威来源是组织针对某项业务事实，正式确认其定义、记录和变更责任的来源。它有时也被称为记录系统或事实来源。

权威不等于“系统最大”“数据最多”或“最先接入数据仓库”，而是该来源在指定业务语境下有责任和权限维护这项事实。

例如：

  • 财务系统可能是实际回款和开票状态的权威来源；
  • 人力资源系统可能是员工任职状态的权威来源；
  • 登记系统可能是当前不动产权利状态的法定记录；
  • 订单系统保存成交时商品价格和收货地址的交易快照；
  • 产品主数据系统维护当前产品分类和标准名称。

1. 权威来源需要限定事实和时间

不能笼统地说“客户数据以 CRM 为准”。客户营销等级、合同主体、开票信息、收货地址和售后联系人可能分别由不同系统负责。

当前值和历史快照也可能由不同记录承担。产品主数据中的当前价格，不能覆盖历史订单成交价格。

2. 权威来源不一定只有一个系统

一个完整业务实体可能由多个来源分别维护不同属性。治理需要划分属性级或事实级责任，并通过统一实体身份组织它们，而不是强行把所有字段都归给同一个系统。

3. 权威来源也可能出错

权威表示责任边界，不表示永远正确。发现问题后，应由有权业务人员按照流程在权威来源中修正，并保留变更历史；治理平台不应静默维护另一套“更正确”的事实。

4. 无法立即确定权威来源时怎么办

可以先记录各来源及其差异，明确临时使用规则、风险和待确认责任，而不应偷偷按“非空优先”“最新优先”或某个系统优先进行拼接。最终仍需由业务责任方裁定事实含义和使用范围。

五、原始数据和派生数据应该怎样区分

原始数据通常指治理体系从来源取得、尽量保留其原有结构和值的数据。它不一定是世界上最初产生的数据，也不一定未经来源系统处理。例如，第三方提供的日报文件对接收方来说可以是落地原始数据，但其中的数字可能已经由提供方计算过。

因此，“原始”是相对于当前数据链路而言的。治理时更重要的是区分：

  • 来源记录：上游系统或提供方交付的内容；
  • 标准化数据：经过编码、单位、格式和标识映射的数据；
  • 整合或明细数据：跨来源关联后按统一业务颗粒度组织的数据；
  • 汇总和指标数据：根据维度和口径计算的结果；
  • 规则或模型结果：标签、评分、预测和识别结论。

每一层都可以有价值，也都可能需要治理。关键是保留它们之间的血缘、转换规则和版本，避免最终用户把推断结果当成原始记录，或者把来源系统的一次修正误认为所有历史结果都已自动更新。

六、数据通过哪些方式进入治理体系

确定数据来源以后，还要根据业务时效、数据规模、源系统能力和使用边界选择取得方式。

取得方式 适用特点 需要关注的问题
批量文件或数据库抽取 周期性、批量和历史数据 全量或增量范围、重复、断点和版本
数据库CDC 持续捕获新增、修改和删除 初始快照、顺序、重复消费和源表变更
API 调用 按需查询或按契约交换 版本、限流、分页、权限和服务可用性
消息或事件订阅 低延迟地接收业务变化 事件语义、顺序、幂等、丢失和重放
设备协议或边缘采集 连接传感器和工业设备 时钟、离线缓存、校准、采样和设备身份
人工填报或文件上传 非自动化、低频或补充采集 模板、校验、责任、证据和重复录入
联邦查询或数据服务 数据不搬迁、使用时访问 跨源性能、可用性、权限和语义一致性

选择方式时不应盲目追求实时。月度统计数据通过受控文件交换可能足够；库存预警和设备异常则可能需要CDC或事件流。更新速度要由业务用途决定。

数据也不一定必须全部复制到数据仓库。治理体系既可以通过物理汇聚保存数据，也可以通过逻辑汇聚在使用时访问分布式来源，或者将两者结合。无论采用哪种方式，来源、语义、质量、权限和变更责任都不能缺失。

七、来源不同，质量责任有什么不同

数据治理不能把所有质量问题都交给数据平台统一清洗。不同来源应承担不同责任。

1. 内部业务系统

业务部门和系统负责人应确保事实在源头正确记录，数据团队负责发现问题、反馈影响和验证整改结果。

2. 设备和传感器

设备管理方应负责安装、校准、维护和时钟同步；数据团队负责监测异常、断流和数据漂移，不能只靠算法长期猜测真实值。

3. 人工采集

采集组织应统一定义、培训、校验和复核，保留采集人员、时间和证据。发现系统性问题时要改善采集过程，而不是只修补结果。

4. 共享、开放和采购数据

提供方应按协议说明范围、口径、质量和更新；使用方仍要进行适用性验证，并记录接收状态。外部来源质量不可控时，要设置降级、替代或停止使用机制。

5. 派生和 AI 生成数据

规则制定者、模型负责人和数据产品负责人应对计算逻辑、验证、版本和适用范围负责。来源数据正确，不代表派生结果一定正确。

治理的目标不是寻找一个可以承担所有问题的团队，而是让问题能够追溯到真正有能力和权限整改的环节。

八、案例：食品冷链质量追溯的数据从哪里来

某食品企业希望对一批冷藏产品从原料入厂、生产、仓储、运输直到门店验收进行质量追溯，并提前发现温控风险。

1. 内部业务系统数据

  • 采购系统记录供应商、原料批次和采购合同；
  • 生产系统记录生产批次、工艺、产线和成品批次；
  • 质量系统记录抽检项目、结果和放行结论；
  • 仓储系统记录库位、入库、出库和库存状态；
  • 订单系统记录客户、商品、数量和交付要求。

这些系统分别记录业务过程中的不同事实。要完成追溯，需要统一供应商、原料批次、生产批次、成品批次和订单之间的关系。

2. 设备和传感器数据

冷库、冷藏车和保温箱中的设备持续记录温度、湿度、位置、开关门和设备运行状态。这些数据频率高，还可能因网络中断延迟上传。

治理时要区分测量发生时间和数据到达时间，记录传感器属于哪辆车或哪个箱体，并确认设备校准状态。否则，一个迟到的温度值可能被误认为当前异常。

3. 人工检测和业务确认

原料入厂检验、装车核对、门店验收和异常处置仍可能由人员完成。检验人员、检测方法、样本、时间、照片和签字记录，都是判断结果是否可信的重要依据。

4. 合作伙伴数据

第三方物流企业可能提供车辆轨迹、交接、运输状态和温控数据。企业需要通过合同和数据接口明确设备编码、数据频率、异常补传、质量责任和可使用范围。

5. 公共和外部数据

天气、道路通行和交通管制数据可以帮助解释运输延迟及外界高温风险，但它们不是产品箱内温度的替代来源。不同数据只能回答各自范围内的问题。

6. 派生数据

治理体系可以在以上事实基础上形成：

  • 每个批次经历的时间、位置和温度链路；
  • 超温持续时间、运输时效和质检合格率等指标；
  • 温控异常、重点检查批次等标签；
  • 根据温度、时长和产品特性计算的质量风险评分；
  • 面向召回和责任追溯的批次关系图。

风险评分不是传感器直接测量的事实，而是来源数据经过规则或模型形成的判断。产品特性、阈值、模型版本和计算时间都要保留。

7. 形成持续闭环

如果系统发现某批次存在较高风险，业务人员还要完成复检、隔离、放行或召回，并记录实际结果。这些行动数据会反过来验证温控规则和风险模型。

冷链追溯的价值不在于把所有数据搬到一个平台，而在于来源清楚、批次可以关联、状态持续更新、结果能够追溯，并最终支持质量处置。

九、建立数据来源清单时应该记录什么

一份可用的数据来源清单不应只有“系统名称、数据库类型、IP地址和表数量”，还应至少包括：

内容 需要说明的问题
业务对象与事件 数据记录了什么事实，采用什么颗粒度
来源组织与系统 谁产生和维护，哪个系统负责记录
权威范围 哪些属性、状态和时间范围以此为准
技术位置 数据库、文件、接口、消息或服务位于哪里
取得方式 全量、增量、CDC、事件、API 还是逻辑访问
更新机制 多久更新，如何判断新增、修改和删除
质量状态 已知缺陷、质量规则和问题责任人
使用权利 使用目的、访问范围、许可、期限和再分发限制
历史与版本 是否保留历史，变更如何识别和追溯
下游影响 被哪些模型、指标、产品和业务流程使用

对于重点业务场景，可以先建立最小来源清单，再随治理深入补充。没有必要一开始穷尽全组织所有数据库，但首期使用的数据必须把来源和责任查清楚。

十、发现多个来源不一致时怎么办

多来源不一致是数据治理中的常态，不应通过简单覆盖掩盖。

  1. 先确认它们是否真的描述同一个对象、属性、时间和业务状态；
  2. 查明每个来源的产生过程、责任和更新时间；
  3. 区分当前值、历史快照、业务认定和算法推断；
  4. 由有权业务方确定权威来源或正式匹配规则；
  5. 无法裁定时保留差异、标记风险，不生成虚假的唯一真相；
  6. 将问题反馈到正确来源修正，并重新处理受影响的下游结果；
  7. 记录选择依据、生效时间、版本和例外情况。

“取最新值”“非空优先”“某系统优先”可以成为经过业务确认的规则，但不能由技术人员在不了解语义时自行设为通用原则。

十一、常见误区

误区一：数据库就是数据的来源

数据库说明数据存在哪里。真正的来源还要追溯到产生事实的业务活动、设备、人员或外部机构。

误区二：数据仓库是所有数据的权威来源

数据仓库可以成为经过治理的分析数据交付位置，但其内容仍来自业务系统和其他来源。源事实需要在有权业务过程中修正，不能只修改仓库结果。

误区三：系统自动采集的数据一定客观准确

设备故障、采样偏差、系统规则和日志缺失都会造成问题。自动产生不等于无需质量治理。

误区四：人工数据质量一定很差

有明确标准、专业方法、证据和复核的人工调查，可能比未经校准的自动采集更可靠。关键在于过程是否受控。

误区五：公开可访问的数据可以随意使用

公开网页、开放许可和合法使用不是同一件事。仍需核实授权、用途、个人信息、署名和再发布条件。

误区六：采购数据就是购买了所有权

多数情况下获得的是合同约定范围内的使用权。缓存、派生、共享、训练和合同结束后的处置都可能受到限制。

误区七：多个来源不一致时选择最新记录即可

最新记录可能是迟到数据、错误修改，也可能描述另一种业务状态。必须先统一对象、语义和时间，再确定选择规则。

误区八：指标、标签和 AI 结果不需要追溯来源

派生结果越接近决策，越需要说明上游数据、计算逻辑、版本和适用边界。只保留最终结论，会让错误难以解释和修正。

误区九：把所有来源接入平台以后就完成了治理

接入只解决访问。数据是否权威、可理解、可靠、合法、鲜活并能支持业务，还需要标准、质量、建模、权限和持续运营。

十二、实践检查清单

  1. 数据描述了什么业务对象、事件或现实观察？
  2. 由哪个组织、岗位、设备或系统负责产生和记录？
  3. 是否区分业务来源、记录来源、技术位置和取得方式？
  4. 哪些属性、状态和时间范围以该来源为准？
  5. 同一事实存在多个来源时，差异和选择规则是否经过业务确认？
  6. 数据是来源记录、标准化结果、汇总指标还是模型推断？
  7. 派生数据能否追溯到上游、规则、模型版本和计算时间？
  8. 数据通过何种方式获得，是否满足业务时效和规模要求？
  9. 是否能够识别新增、修改和删除，并妥善保留必要历史？
  10. 来源发生中断、延迟、结构变化或质量异常时，由谁处理？
  11. 外部数据是否具有明确许可、使用目的、期限和再分发边界？
  12. 人工、设备和系统采集过程是否有相应校验和责任机制？
  13. 模拟、合成和 AI 生成数据是否与真实业务事实清楚区分？
  14. 是否知道该来源被哪些指标、模型、数据产品和业务流程使用？
  15. 是否从真实业务场景出发选择必要来源，而不是无目的接入全部数据？

小结

数据首先来自业务活动和现实世界：人办理业务、系统记录交易、设备进行观测、专业人员开展调查、组织之间交换信息。指标、标签、评分和预测，则是在这些来源数据之上通过规则和模型形成的派生结果。

从技术角度看，数据可能来自一张数据库表、一个文件、一个 API 或一个消息主题；从治理角度看，还必须继续追问：事实如何产生、谁负责记录、哪一部分以谁为准、是否有权使用、多久更新，以及结果怎样追溯。

把来源查清楚，不是为了制作一份静态台账，而是为了在数据发生错误、延迟或变化时找到正确责任，判断影响并推动更新。只有来源可信、权责清楚、获取合规、变化可持续传递，数据才能长期服务业务。
