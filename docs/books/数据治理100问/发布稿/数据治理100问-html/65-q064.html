064 什么是流批一体化，它是否适用于所有场景？

一句话回答

流批一体化是在尽可能统一的数据、规则和工程体系下，同时支持流处理与批处理，让实时结果和周期结果保持一致，并能够使用历史数据纠错和重算。它不是所有场景的必选方案；如果业务只需要按天、按周处理数据，批处理通常更加简单、稳定和经济。

“流批一体化”常被当作数据平台先进程度的标志，容易让人产生一种印象：批处理已经落后，所有数据都应该实时处理。实际上，流处理和批处理服务于不同的业务时效，一体化的价值不是把所有任务都改成实时任务，而是减少两套体系之间的重复和不一致。

一、流处理和批处理有什么区别

1. 批处理面对有明确范围的数据

批处理通常在数据范围已经确定后集中计算，例如：

  • 汇总前一天的订单；
  • 计算上个月的经营指标；
  • 对历史数据进行全量质量检查；
  • 按新规则重新计算过去一年的结果。

一批数据可以按日期、文件、分区或其他业务范围划定。任务开始前，通常能够说明本次要处理哪些数据，以及何时可以认为处理完成。

2. 流处理面对持续到达的数据

流处理面对持续产生、暂时没有天然终点的数据，例如：

  • 持续接收支付交易并识别风险；
  • 实时监测设备温度和运行状态；
  • 根据用户行为更新推荐结果；
  • 根据车辆位置变化判断是否偏离路线。

流处理需要在数据不断到达的过程中持续计算。它通常使用事件、时间窗口或业务状态划定阶段性范围，并处理迟到、乱序和重复等问题。

因此，流处理和批处理的根本区别不只是速度快慢，而是所面对的数据是否持续到达、计算范围是否已经确定。

二、为什么需要流批一体化

同一项业务经常同时需要实时观察和周期汇总。例如，零售企业既希望在促销期间实时查看销售额，也要在日终结合退款和迟到订单形成正式经营报表。

过去，企业可能分别建设两套数据链路：

实时事件 → 流处理逻辑 → 实时看板

历史数据 → 批处理逻辑 → 日报和月报

两条链路独立建设，容易带来以下问题：

  • 相同的业务规则被重复开发；
  • 实时指标和日终指标使用不同口径；
  • 规则变化时只修改了其中一条链路；
  • 实时处理出现错误后，难以使用历史数据重算；
  • 元数据、质量规则、血缘和监控分散在两套体系中；
  • 开发人员需要掌握和维护两套完全不同的过程。

流批一体化首先要解决的，就是这种重复建设和结果不一致。它希望同一份数据、同一项业务规则可以同时服务即时处理和历史分析，而不是长期维护相互割裂的“实时版”和“离线版”。

三、“一体化”主要统一什么

1. 统一数据定义

流数据和批数据应使用一致的字段含义、业务对象、事件定义和指标口径。例如，订单完成、退款成功和有效销售额不能在实时链路与批量链路中各自解释。

2. 统一主要处理逻辑

过滤条件、关联规则、计算公式和质量要求应尽量复用。同一指标规则发生变化时，实时结果和周期结果都应使用经过确认的新版本。

3. 统一数据基础

持续到达的原始事件通常还需要可靠保存。这样既可以支持实时计算，也可以进行历史查询、问题核查、规则验证和重新计算。

4. 统一工程和治理过程

流任务与批任务都需要参数、版本、测试、发布、调度、监控和告警，也都应受到数据标准、质量、安全、血缘和审计要求的约束。

因此，流批一体化不只是让某个计算工具同时运行两种任务。即使使用同一种工具，如果两条链路仍然采用不同的数据定义、计算规则和治理过程，也不能认为真正解决了一体化问题。

四、一体化是否意味着流和批完全相同

流处理与批处理可以共享数据定义和主要业务逻辑，但不能消除所有差异。

批处理面对的通常是已经划定范围的数据；流处理则要在数据持续到达时判断时间窗口、保存计算状态，并处理迟到和乱序。相同的销售额规则，在批处理中可以一次读取某日全部订单，在流处理中却需要随着下单、支付、取消和退款事件不断更新。

因此，不宜把流批一体化简单理解为：

编写一份代码，就能在所有流处理和批处理场景中得到完全相同的结果。

更准确的说法是：

在数据定义和业务规则上尽量统一，在时间、窗口、状态和结果确认方式上保留必要差异。

实时结果与最终结果

实时结果反映的是当前已经到达的数据，后续可能因退款、迟到数据或规则修正而变化。周期处理可以在约定的数据基本到齐后进行核对，形成相对稳定的确认结果。

“确认结果”也不代表永远不能改变。业务更正、历史补录和规则调整仍可能引发重算。重要的是明确告诉使用者：当前看到的是持续变化的实时结果，还是已经按照约定完成核对的周期结果。

五、流批一体化是否适用于所有场景

答案是否定的。是否采用流处理或流批一体化，应从业务需要出发，而不是把技术形态当作建设目标。

1. 适合采用流批一体化的场景

  • 同一批业务数据既要实时分析，又要长期汇总；
  • 同一指标同时用于实时看板、日报和月报；
  • 实时结果需要使用历史数据进行纠错或重算；
  • 业务既要立即响应事件，又要进行周期性复盘；
  • 现有流处理与批处理存在大量重复逻辑；
  • 迟到数据和规则变化可能影响已经发布的结果。

风险控制、设备监测、实时营销、物流调度和大型促销分析等场景，通常同时需要即时响应与历史分析，比较适合考虑流批一体化。

2. 优先采用批处理的场景

  • 源系统每天或每月才提供一次数据；
  • 业务可以容忍一天或更长时间的延迟；
  • 数据规模和处理频率较低；
  • 计算结果不会立即触发业务行动；
  • 团队缺少持续维护实时链路的能力；
  • 实时建设和运行成本明显高于业务收益。

例如，年度预算分析、月度财务结算、长期档案统计等工作，通常没有必要为了追求“实时”而增加持续运行的流处理体系。

3. 只采用流处理的场景

有些场景主要关心事件发生后的即时行动，例如接收到安全告警后立即通知值班人员。但只要还需要审计、分析、规则验证或问题重放，相关原始事件和处理结果仍然应被保存。只处理当前消息、不保留必要历史，通常难以满足后续治理要求。

六、“一动皆动”是否必须采用流批一体化

一些组织，特别是政府部门，希望基础数据发生变化后，相关数据、指标、报表、地图和服务都能及时更新，通常把这种目标称为“一动皆动”。

“一动皆动”不是一种确定的技术架构。它首先要求建立四项能力：

  1. 发现权威数据发生了什么变化；
  2. 根据血缘和依赖关系识别受影响的下游；
  3. 触发需要执行的数据处理、索引更新或服务刷新；
  4. 记录更新结果，并向相关责任人或使用者反馈。

如果数据变化频率不高，业务允许在几分钟、几小时或一天内完成更新，可以在发现变化后通过任务编排启动增量批处理，没有必要建设持续运行的流处理链路。

如果数据持续、高频变化，并要求在事件发生后立即更新风险判断、监测态势或在线服务，就可能需要流处理。只有当业务既需要即时联动，又需要周期汇总、历史核对、纠错重算和统一口径时，流批一体化才更有价值。

“皆动”也不能理解为所有下游都自动覆盖。不同数据应采用不同的更新规则：

  • 缓存、检索索引和普通数据副本可以自动更新；
  • 分析指标和专题数据可以根据依赖关系重新计算；
  • 已经正式发布的统计结果应形成新版本，并按要求重新审核；
  • 已归档或具有法律效力的记录应保留原始版本，不能静默修改；
  • 已经执行的通知、扣款、发货或行政行为，不能因为历史数据重放而再次触发。

因此，更准确的目标不是“一处变化，所有数据立即改变”，而是：

一处变化能够被发现，影响范围能够被识别；需要更新的结果按照相应规则及时更新，需要审核的结果形成新版本并进入审核。

七、应该怎样选择处理方式

可以依次回答以下问题：

  1. 业务最晚什么时候必须得到结果？
  2. 数据是持续到达，还是定期集中提供？
  3. 结果是否会立即触发告警、拦截、推荐或调度？
  4. 是否还需要历史分析、纠错和重算？
  5. 实时结果与周期结果是否必须保持同一口径？
  6. 团队是否有能力持续维护和监控实时任务？
  7. 业务收益能否覆盖实时系统的建设和运行成本？

由此可以形成一个简单判断：

业务需要 优先考虑的方式
只需要周期性结果 批处理
需要在事件发生后立即行动 流处理
既要即时响应，又要历史分析、纠错和统一口径 流批一体化

“实时”也不是只有一种标准。秒级、分钟级和小时级可能分别满足不同业务。有些场景使用短周期批处理就能达到要求，没有必要为了理论上的更低延迟承担更高复杂度。

八、流批一体化需要治理什么

第054问已经介绍了事件时间、窗口、迟到乱序和流数据质量等问题。在流批一体化体系中，还要特别关注两种处理方式之间的一致性：

  • 流数据与批数据是否采用统一的数据定义和业务口径；
  • 实时结果与确认结果是否有清楚标识；
  • 规则变化是否能够追踪版本和影响范围；
  • 历史重算是否会重复触发通知、扣款或设备控制；
  • 质量检查是否同时覆盖实时异常和周期完整性；
  • 血缘是否连接原始事件、实时结果、周期结果和业务行动；
  • 实时链路失败时，是否明确降级、等待或补偿方式；
  • 同一业务结果由流和批重复写入时，是否会相互覆盖或产生重复。

尤其需要区分“重新计算数据结果”和“重新执行外部动作”。历史订单可以重算销售指标，但不能因为重放订单事件而再次扣款、发货或发送营销短信。

九、案例：促销活动的实时观察与日终核对

某零售企业在大型促销期间，需要实时观察订单量、销售额和库存变化，以便及时补货和调整活动；活动结束后，还要结合退款、取消订单和迟到数据形成正式经营报表。

最初，实时看板和日终报表由两个团队分别开发。实时看板收到支付事件就增加销售额，日终报表则会排除已经退款和取消的订单。由于两边的有效订单定义不同，同一天的销售额经常对不上。

团队随后按照流批一体化思路进行调整：

  1. 统一订单状态、退款规则和销售指标定义；
  2. 流处理持续计算当前订单量、销售额和库存变化；
  3. 保存原始订单、支付、取消和退款事件；
  4. 实时看板明确标识结果仍可能变化；
  5. 日终在数据基本到齐后，按照同一口径核对并形成确认结果；
  6. 迟到数据或规则修正出现时，能够对受影响日期重新计算；
  7. 历史重算只更新分析结果，不再次触发支付、发货和营销动作。

这样，实时结果帮助企业在促销过程中采取行动，周期结果则服务于正式核算和复盘。二者承担不同职责，但使用相同的数据定义和业务规则。

十、常见误区

误区一：流批一体化就是把所有批处理改成流处理

一体化强调两种处理方式共享数据、规则和治理体系，并不要求取消批处理。

误区二：流处理一定比批处理先进

技术是否合适取决于业务需要。没有实时价值的场景采用批处理，反而更简单可靠。

误区三：流批一体化意味着所有场景只写一份代码

业务规则可以尽量复用，但流处理仍然需要处理窗口、状态、迟到和乱序，不能强行抹平执行差异。

误区四：实时结果就是最终结果

实时结果基于当前已到达的数据，可能因退款、补录或迟到数据而变化。使用者需要知道结果处于什么状态。

误区五：数据进入消息系统就已经完成流处理

消息系统负责传递持续到达的数据，业务计算、状态管理、质量检查和结果输出仍需要相应的数据处理过程。

误区六：使用同一种计算工具就实现了流批一体化

如果流任务和批任务仍然采用两套口径、规则和治理过程，仅仅使用相同工具并不能解决结果不一致。

误区七：实时性越高，业务价值越大

如果业务每天才做一次决策，把数据延迟从十分钟降低到一秒通常不会带来相应价值，却会增加成本和维护难度。

十一、实践检查清单

  1. 业务需要秒级、分钟级、小时级还是日级结果？
  2. 数据是持续到达，还是按固定周期集中提供？
  3. 实时结果是否会触发明确的业务行动？
  4. 同一数据是否还需要历史查询、核对和重算？
  5. “一动皆动”中的数据变化、影响范围和更新时间是否已经明确？
  6. 哪些下游可以自动更新，哪些正式结果需要形成新版本并重新审核？
  7. 实时指标与日报、月报是否采用统一口径？
  8. 实时结果和确认结果是否有清楚标识？
  9. 业务规则变化时，流任务和批任务能否同步更新？
  10. 原始事件是否在必要期限内可靠保存？
  11. 历史重算是否会重复触发外部业务动作？
  12. 实时链路异常时是否有告警、降级或补偿方案？
  13. 流处理和批处理是否纳入统一的质量、血缘、安全和审计管理？
  14. 实时能力带来的业务收益是否能够覆盖建设和运行成本？

小结

流批一体化的价值，不是让所有数据都变成实时数据，而是让流处理与批处理尽量共享一致的数据定义、业务规则和治理体系。它可以减少重复开发，降低实时结果与周期结果不一致的风险，并支持使用历史数据核查、纠错和重算。

流处理与批处理仍然具有不同的时间和执行特点。一体化应统一可以统一的部分，同时保留窗口、状态、迟到处理和结果确认等必要差异。

企业是否采用流批一体化，应由业务能够容忍的延迟、是否需要即时行动、结果一致性、历史重算需求、团队能力和成本共同决定。只需要周期性结果时，批处理往往就是更合适的选择。
