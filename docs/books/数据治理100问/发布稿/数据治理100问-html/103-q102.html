102 AI Agent 如何参与数据治理的设计与执行？

一句话回答

AI Agent 可以根据行业知识库、组织标准和实际数据，参与标准配置、实体建模、维度建模、指标体系设计，也可以在受控条件下执行数据探查、开发、质量检查和问题处理；但它输出的首先是候选方案和受控动作，涉及业务语义、生产数据、权限、安全、共享、删除和重大风险的事项，必须由相应责任人审批、验证并承担责任。

前面的讨论分别说明了 AI 可以辅助哪些治理工作，以及 AI 就绪数据需要哪些基础。AI Agent 更进一步：它不只回答问题或生成一段文本，还可以理解目标、分解任务、调用工具、检查结果，并根据中间结果继续执行后续步骤。

这使 Agent 有机会参与完整的数据治理过程。例如，它可以从行业标准、业务文档、数据库结构和样例数据中提出数据标准、实体模型、维度模型和指标体系的候选方案，再在测试环境中生成配置、规则和任务，最后提交给责任人审核。

但“能够自主执行”不等于“拥有无限授权”。Agent 执行的是组织预先开放的能力，必须受到知识依据、权限范围、运行环境、审批流程、质量门禁、审计记录和回滚机制的约束。

一、Agent 在数据治理中可以承担什么角色

1. 治理设计助手

根据行业知识库、组织标准、业务文档和实际数据，生成标准、实体、维度、指标和质量规则的候选方案。

2. 治理执行助手

调用数据探查、建模、开发、调度、质量、工单和目录工具，完成已经明确且授权的任务。

3. 治理验证助手

检查生成的 SQL、模型、规则、数据结果和影响范围，比较基线和历史结果，发现异常并提出暂停或回滚建议。

4. 治理协作助手

整理问题、变更、会议和历史决策，生成影响分析、工单、审批材料和复盘报告。

这几种角色可以组合在一个 Agent 中，也可以由不同 Agent 分担。无论采用什么架构，都要明确每一步是建议、模拟执行、待审批还是正式执行。

二、Agent 如何参与治理设计

Agent 的重要价值不只是执行已经确定的规则，还可以参与治理方案和模型的设计。

1. 标准配置

Agent 可以根据行业标准、组织规范、字段元数据和样例数据：

  • 推荐数据元、编码、单位、格式和质量规则；
  • 生成标准映射、码值转换和配置草稿；
  • 识别不同系统中可能对应的字段和术语；
  • 检查标准之间的冲突、缺项和影响范围；
  • 为标准条目生成示例、测试数据和符合性检查。

但 Agent 不能自行决定组织最终采用哪个标准。外部标准的适用范围、企业内部扩展、历史兼容和业务例外，都需要数据责任人和治理机制确认。

2. 实体建模

Agent 可以从业务文档、系统表结构、接口、SQL 和样例数据中：

  • 识别候选业务实体和事件；
  • 推荐实体属性、业务标识、生命周期和关系；
  • 发现不同系统中可能属于同一实体的对象；
  • 提示实体边界、主标识和关系定义中的歧义；
  • 生成实体模型草图、映射关系和测试样例。

实体边界、唯一标识、合并规则和生命周期属于业务判断。Agent 可以列出多种方案及其影响，却不能仅凭字段相似度决定两个对象在业务上就是同一实体。

3. 维度建模

面向经营分析和指标服务时，Agent 可以根据业务场景推荐：

  • 事实表、维度表、事实粒度和度量；
  • 维度层级、下钻路径和一致性维度；
  • 可加、半可加和不可直接相加的度量；
  • 多对多关系、历史变化和快照需求；
  • 模型草图、字段说明、测试数据和查询样例。

最低事实粒度、历史处理方式、快照策略和性能取舍，仍需要数据架构师、数据责任人和使用团队共同确认。模型结构合理，不代表它自动满足所有业务场景。

4. 指标体系构建

Agent 可以从制度、报表、业务文档、已有 SQL 和会议材料中：

  • 提取候选指标、指标别名和业务定义；
  • 推荐统计对象、公式、维度、时间口径和数据来源；
  • 识别重复指标、同名不同义和指标依赖；
  • 生成指标目录、血缘关系和质量检查规则；
  • 比较不同部门现有指标并整理争议点。

哪个指标是组织级权威口径、适用于哪些管理场景，以及多个合理指标是否需要并存，仍应由数据责任人、相关业务部门和治理委员会确认。Agent 不能因为某个公式在历史报表中出现次数最多，就自动将其升级为正式标准。

三、行业知识库在 Agent 设计中的作用

行业知识库可以提供概念、标准、规则、案例、模型模板和历史决策，帮助 Agent 减少无依据的猜测。但知识库中的内容不能等量齐观，应明确权威层级：

  1. 法律法规和强制性要求；
  2. 国家、行业和地方标准；
  3. 组织已经批准的数据标准、术语和指标；
  4. 经过确认的行业知识和业务规则；
  5. 历史案例、报表和已有实现；
  6. Agent 根据资料生成的推断和建议。

越靠前的内容，越适合作为约束和依据；越靠后的内容，越适合作为参考和候选方案。Agent 必须说明使用了哪些知识、采用了哪个版本、做了哪些假设，以及哪些地方需要人工判断。

行业知识库本身也需要治理：来源、版本、生效时间、适用范围、冲突关系、责任人和撤回机制都要清楚。一个过期或来源不明的知识库，可能让 Agent 快速生成一整套过时的标准和模型。

四、哪些任务适合较高程度自动执行

  • 只读数据探查和统计摘要；
  • 元数据草稿、标签和目录描述生成；
  • 质量规则候选、异常分类和问题聚合；
  • 测试环境中的 SQL、转换逻辑和质量脚本生成；
  • 影响分析、问题分派建议、报告和工单草稿；
  • 对低风险、范围明确、可重复和可回滚的标准操作执行。

这些任务仍需要记录输入、知识依据、工具调用、结果和失败情况。低风险不等于没有风险，只是错误影响有限、操作可逆且容易复核。

五、哪些任务适合人工确认后执行

  • 发布标准映射、质量规则和资产说明；
  • 将问题分派给责任团队；
  • 在测试环境运行数据修复或转换；
  • 创建数据开发任务、调度任务和服务配置；
  • 提交变更、生成审批材料和准备发布计划；
  • 将 Agent 生成的实体模型、维度模型和指标方案提交评审。

这里要区分四种状态：建议、模拟执行、待审批和正式执行。用户看到 Agent 生成了 SQL 或模型草图，不代表系统已经修改数据或发布配置。

六、哪些任务必须严格审批或禁止 Agent 直接执行

  • 修改生产数据、主数据和关键历史记录；
  • 修改业务口径、指标定义、组织级数据标准和权限策略；
  • 发布、共享、导出或删除敏感数据；
  • 改变生产调度、接口、服务和访问控制；
  • 执行不可逆的数据清洗、销毁、迁移和批量合并；
  • 代表组织接受重大风险、批准合规结论或作出跨部门裁决。

Agent 可以准备方案、模拟影响、生成脚本和列出风险，但不能替代数据责任人、治理委员会、安全合规人员和系统负责人作出正式决定。

七、Agent 自动执行的前提

Agent 只有同时满足以下条件，才适合执行自动化动作：

  • 任务目标、范围、输入和预期输出明确；
  • 使用的数据、知识、工具和环境已经登记并获得授权；
  • 权限遵循最小权限、短期凭证和作用域限制；
  • 操作在沙箱、测试环境或受控任务环境中运行；
  • 有质量规则、资源限制、敏感数据控制和失败处理；
  • 执行前可以预览计划、查询和影响范围；
  • 执行后能够验证、审计、暂停、回滚和追责。

如果任务目标本身含糊、数据范围不清或业务口径未确认，Agent 应先澄清或暂停，而不是自行补全关键假设。

八、Agent 执行链路如何控制

可以把一次受控执行表示为：

用户或系统提出目标
          ↓
Agent 分解任务并生成计划
          ↓
策略引擎检查权限、风险、数据范围和工具
          ↓
模拟或测试环境执行
          ↓
质量、权限、资源和安全检查
          ↓
自动执行、人工审批或拒绝
          ↓
正式执行、结果验证和审计记录
          ↓
异常暂停、隔离、回滚和升级

策略引擎不能只检查用户是否登录，还要检查 Agent 试图访问什么数据、调用什么工具、产生什么副作用，以及当前任务是否有相应的业务授权。

九、Agent 的工具调用必须受控

每个工具都应明确：

  • 名称、用途、输入、输出和副作用；
  • 可以读取和修改的数据范围；
  • 所需身份、权限和审批条件；
  • 资源、网络、文件和执行时限限制；
  • 失败、超时、重试和回滚方式；
  • 需要记录的日志和审计证据。

默认应提供只读工具，写操作单独授权。不能让 Agent 通过先读取配置、再组合多个低权限工具的方式绕过整体安全边界，也不能让 Agent 自己创建高权限账号或修改审计策略。

十、如何验证 Agent 生成和执行的结果

1. 验证设计结果

检查标准、实体、维度、指标和质量规则是否有清晰依据，是否存在假设、冲突和未解决的歧义。

2. 验证查询和代码

检查语法、类型、数据范围、粒度、关联路径、资源消耗和安全风险。

3. 验证数据结果

检查变更数量、异常值、质量指标、影响对象和与基线、历史结果或独立规则的差异。

4. 验证生产变更

先小范围、灰度或分批执行，保留快照和备份，确认结果后再扩大范围。失败后保留现场、日志和中间结果，便于复盘和恢复。

十一、责任和审计如何落实

一次 Agent 操作至少要区分：

  • 任务发起人；
  • 数据责任人；
  • 方案审批人；
  • Agent 使用的模型和提示词；
  • Agent 调用的工具和服务账号；
  • 实际执行人或执行任务；
  • 结果验证人和异常处理人。

审计记录应包含目标、上下文、知识依据、数据版本、Agent 计划、实际工具调用、拒绝、重试、人工干预、变更影响、验证结果、回滚和通知。

Agent 不是法律和组织意义上的责任主体。所谓“Agent 自主执行”，不能变成出了问题就没有人负责的理由。

十二、案例：Agent 参与跨区域物流状态治理

某物流企业接入了多家承运商，各方对“已揽收”“运输中”“派送失败”和“已签收”的编码、时间和业务条件定义不一致。Agent 先从承运商接口文档、行业知识库、历史运单和已处理争议中，识别状态候选定义、映射关系和冲突，并提出运单、运输节点、状态事件的实体关系，以及签收及时率的候选口径。

数据责任人确认业务状态、例外和指标适用范围，数据治理专员组织评审状态标准、码值映射和质量规则。技术团队让 Agent 在测试环境生成候选配置，回放历史运单，比较映射前后的状态分布、指标变化和异常记录。数据保管员检查权限、版本和回滚条件，审批后再将已确认的映射发布到生产。

规则发布后，Agent 持续检查未知码值、状态跳转异常和指标偏差，生成复核报告。若新承运商出现未识别状态，系统自动暂停该映射并升级，而不是自行归入最相似的标准码值。数据资产运营者随后更新数据服务说明和质量状态。

这个案例中，Agent 参与了标准配置、实体建模、指标候选设计、测试和运行监测，但没有直接决定业务语义，也没有在无人评审的情况下发布新规则。

十三、风险分级与自动化程度

风险等级 典型任务 控制要求
低风险 只读探查、摘要、草稿、可重复且可回滚的操作 记录来源和版本，抽样复核
中风险 测试环境写入、规则发布、工单分派、有限服务变更 责任人确认，测试、审批和审计
高风险 生产数据、权限、安全、共享、删除、业务口径和重大决策 严格审批、最小权限、备份、回滚和人工复核

风险分级不能只看操作名称，还要考虑数据敏感性、影响范围、错误成本、可逆性、用户数量和下游依赖。相同的“修改字段”操作，在测试数据和监管报送数据上的风险完全不同。

十四、常见误区

误区一：Agent 能执行就应该拥有高权限

Agent 的价值在于调用受控能力，不在于拥有超级账号。权限越大，越需要缩小作用域和加强审批。

误区二：生成计划就是获得执行授权

计划、脚本和模型草图只是候选方案。正式执行仍需经过权限、审批、测试和验证。

误区三：只记录最终结果，不记录中间调用

没有计划、上下文和工具调用记录，就无法判断 Agent 为什么做出某个决定，也无法复盘错误。

误区四：让 Agent 直接修改生产和主数据

生产变更必须经过测试、审批、备份、最小权限和回滚安排。

误区五：用模型准确率替代变更审批

历史评测结果不能证明当前数据、当前权限和当前任务一定安全。执行仍需针对具体变更验证。

误区六：认为回滚代码就能恢复错误数据

已经写入的数据、修改的结构和被下游消费的结果，不会因为 Agent 或代码回滚而自动恢复，需要独立的数据恢复和结果处置方案。

误区七：让 Agent 自己修改权限、审计和安全策略

安全控制不能由同一个自动化主体自行放宽，否则会形成无法制衡的权限闭环。

误区八：所有任务都强制人工审批

低风险只读和草稿任务全部人工审批，会降低效率并鼓励绕开正式流程。应根据风险设置分级控制。

误区九：所有任务都自动执行

自动化不是目标本身。不可逆、高影响、涉及业务定义和权利责任的任务必须保留人工判断。

小结

AI Agent 可以参与数据治理设计，也可以在受控条件下执行数据探查、数据开发、质量检查和问题修复。它尤其适合根据行业知识库、组织标准和实际数据生成标准配置、实体模型、维度模型和指标体系的候选方案，再通过测试、审批和验证逐步落地。

Agent 的自主性必须建立在明确目标、可靠知识、受控工具、最小权限、隔离环境、质量门禁、完整审计和可回滚机制之上。涉及生产数据、业务口径、权限、安全、共享、删除和重大风险的事项，必须由相应责任人和决策机制作出最终判断。

真正成熟的 Agent 不是无人负责的自主治理者，而是能够把行业知识、数据事实和执行工具连接起来，帮助人更快完成治理设计和受控操作，同时让每一步都可解释、可验证、可暂停和可追责。
