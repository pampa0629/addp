063 什么是 DataOps，它如何改进数据开发和交付过程？

一句话回答

DataOps 是一套面向数据开发和交付的协作与工程方法。它把需求、开发、验证、发布、运行和反馈连接成持续改进的过程，帮助数据团队更快响应业务需求，更稳定地交付数据，并让每次变更都可以检查、追踪和恢复。

企业中的数据需求很少是一次性的。业务规则会调整，源系统会变化，指标口径会修订，数据任务也要不断更新。如果每次变化都依靠人员传递文件、手工修改脚本和临时登录生产环境执行，数据交付就会越来越慢，风险也会越来越高。

DataOps 希望改变的，正是这种依赖人工接力的数据生产方式。

一、传统数据开发和交付存在哪些问题

在一些企业中，数据开发采用类似下面的流程：

业务人员提出需求
        ↓
开发人员编写 SQL 或脚本
        ↓
测试人员集中验证
        ↓
运维人员手工发布
        ↓
生产出现问题后逐层排查

这个过程看起来分工明确，实际却容易出现许多断点：

  • 需求在业务、开发、测试和运维之间反复传递；
  • 指标口径只存在于聊天记录或个人文档中；
  • SQL、脚本和配置通过复制文件进行交接；
  • 开发、测试和生产环境存在差异；
  • 数据问题直到报表发布后才被发现；
  • 生产任务失败后，很难快速确定变更内容和影响范围；
  • 问题虽然得到修复，却没有形成能够预防再次发生的规则。

数据交付时间长，并不一定是因为编写 SQL 很慢，更多时候是等待确认、人工交接、重复验证和故障返工占用了时间。

二、DataOps 究竟是什么

DataOps 中的“Ops”容易让人联想到系统运维，但 DataOps 并不只是保证服务器和任务正常运行。它关注的是数据从需求提出到持续可用的完整过程。

它通常包含三层含义。

1. 一种跨角色的协作方式

业务人员、数据开发人员、治理人员、测试人员和运行维护人员不再只负责自己的一段工作，而是共同对最终的数据结果负责。

业务人员需要说明口径和使用条件，开发人员需要保证逻辑可以验证和重复运行，治理人员需要把质量、安全和标准要求嵌入过程，运行维护人员则要把生产中的异常及时反馈给开发和业务。

2. 一套规范化的工程过程

数据逻辑不再通过临时文件和口头说明交付，而是通过参数、版本、环境、测试、发布记录、调度和监控等机制进行管理。

这些能力并不是彼此孤立的：版本说明本次发布了什么，测试说明它是否符合预期，环境隔离降低生产风险，调度让任务持续运行，监控则判断结果是否按时产生。

3. 一个持续改进的循环

DataOps 不把“任务发布成功”视为终点。生产运行中的延迟、失败、质量问题和业务反馈，都会回到下一轮需求和开发中，推动规则、测试和流程不断完善。

因此，DataOps 不是一款软件，也不是增加一个岗位就能完成的转型。平台可以提供工具，但企业仍需建立共同责任、工作规则和反馈机制。

三、DataOps 如何形成数据交付闭环

DataOps 可以概括为下面的循环：

明确需求和数据口径
          ↓
      开发数据逻辑
          ↓
      验证数据结果
          ↓
      审核并发布
          ↓
      持续生产数据
          ↓
      监控与业务反馈
          └────────→ 进入下一轮改进

1. 需求阶段

不仅要说明“需要一张报表”或“增加一个指标”，还要明确数据来源、计算口径、更新周期、质量要求、使用对象和责任人。这样才能判断什么结果才算真正交付。

2. 开发阶段

SQL、脚本或可视化工作流应进行参数化和版本管理，避免为每个日期、地区或环境复制一套逻辑。开发过程中的变更应留下记录，便于比较和追踪。

3. 验证阶段

验证不只是检查程序能否运行，还要检查数据结构、数据质量、指标口径和预期结果。越早发现问题，修复成本越低。

4. 发布阶段

通过清楚的发布流程，把经过验证的版本从开发环境逐步交付到生产环境。重要变更可以设置审核和确认，不应由个人随意替换正在运行的任务。

5. 运行阶段

通过定时和任务编排持续执行数据任务，记录每次运行的版本、参数、状态和结果。任务失败、数据延迟或质量检查不通过时，应及时告警并阻止错误继续扩散。

6. 反馈阶段

技术监控可以发现任务失败和运行延迟，业务反馈则可能发现口径不合理、结果难以理解或数据不再满足需求。两类反馈都应进入下一轮改进，而不是只做一次临时修补。

四、DataOps 如何改进数据开发

1. 从大批量交付转向小步改进

把很大的数据项目拆分为较小、可以验证的变更，能够更早获得业务反馈，也能降低一次修改过多所带来的风险。

2. 从人工复制转向可重复过程

通过参数化、版本管理和环境隔离，同一套逻辑可以在不同日期和环境中重复执行，减少手工修改造成的错误。

3. 从事后检查转向尽早验证

在开发和测试阶段就检查数据结构、计算逻辑和质量规则，避免问题进入生产后才由报表使用者发现。

4. 从分段负责转向共同负责结果

任务成功运行并不等于业务获得了正确数据。DataOps 要求业务、开发、治理和运行维护人员围绕最终数据结果协作，减少“我的环节已经完成”的责任割裂。

五、DataOps 如何改进数据交付

数据交付不只是把 SQL、脚本或任务部署到生产环境。真正的交付还意味着：

  • 数据按照约定周期产生；
  • 数据结构和业务口径符合约定；
  • 结果通过必要的质量与安全检查；
  • 下游使用者能够知道数据是否可用；
  • 变更内容、发布时间和责任人可以查询；
  • 出现问题时能够定位影响并恢复处理。

DataOps 通过规范和自动化减少等待、交接和重复劳动，因而能够缩短从提出需求到数据真正可用的时间。同时，版本、测试、审核和监控又为快速变化设置了安全边界。

它追求的不是“发布得越快越好”，而是在风险可控的前提下，更快、更稳定地持续交付数据。

六、DataOps 与DevOps有什么关系

DataOps 借鉴了DevOps中的协作、版本管理、自动测试、持续交付和运行反馈等方法，但不能简单地把DevOps改一个名字。

软件程序没有变化时，通常可以反复得到相同的处理逻辑；数据生产却还会受到源数据、数据结构、业务口径和更新时效的影响。即使任务代码没有修改，也可能因为上游少传了一批数据、字段含义发生变化或者业务规则调整而产生错误结果。

因此，DevOps主要关注软件怎样可靠地开发和运行，DataOps 还必须持续关注：

  • 输入数据是否完整、准确和及时；
  • 数据结构变化是否会影响下游；
  • 指标和业务规则是否仍然适用；
  • 数据结果是否满足使用者的真实需求。

DataOps 继承了部分软件工程方法，又根据数据不断变化、依赖关系复杂和质量需要持续检查等特点进行了扩展。

七、DataOps 与数据治理是什么关系

数据治理与 DataOps 并不相互替代。

数据治理回答的是：数据应该遵守哪些标准和质量要求，谁对数据负责，哪些数据可以被谁使用，过程需要留下哪些审计记录。

DataOps 关注的是：怎样把这些要求落实到每一次需求、开发、验证、发布和运行中。

例如：

  • 数据标准可以转化为开发阶段的字段和命名检查；
  • 数据质量规则可以成为发布前和运行中的检查步骤；
  • 数据安全要求可以成为环境、权限和发布审核的一部分；
  • 元数据和血缘信息可以随任务变更和运行过程持续更新；
  • 责任人和服务要求可以用于告警通知与问题处理。

如果没有 DataOps，治理要求容易停留在制度文件和上线前的人工检查中；如果缺少数据治理，DataOps 又可能只关注交付速度，持续、快速地产生不符合要求的数据。

可以把两者的关系概括为：

数据治理明确“应该遵守什么要求”，DataOps 帮助这些要求在日常数据生产中持续落地。

八、自动化是否意味着取消人工判断

DataOps 提倡减少重复人工操作，但自动化并不意味着所有变更都应直接进入生产。

适合自动化的工作包括：

  • 检查 SQL、脚本和配置的基本错误；
  • 执行已经定义的数据质量规则；
  • 在测试环境中运行验证任务；
  • 记录版本、参数和发布过程；
  • 按计划运行生产任务；
  • 发现失败、延迟或质量异常后发出告警。

涉及核心指标口径、敏感数据、访问权限和重大生产变更时，仍然需要业务或管理人员审核。自动化负责稳定地执行明确规则，人工判断负责处理重要决策和规则之外的复杂情况。

九、案例：新增门店经营指标

某零售企业希望增加“活跃会员客单价”指标。过去，业务人员通过聊天工具说明需求，开发人员修改一份 SQL 文件，手工替换日期后直接在生产环境运行。指标出现异常时，团队很难确认使用的是哪个口径，也不知道修改影响了哪些报表。

采用 DataOps 方式后，团队调整了交付过程：

  1. 业务人员和数据人员共同确认活跃会员的定义、计算周期和验收结果；
  2. 开发人员在受控环境中修改计算逻辑，并保存新的版本；
  3. 日期、门店范围和运行环境通过参数传入，不再修改 SQL 正文；
  4. 测试过程检查样例结果、历史数据差异和异常值；
  5. 业务人员确认指标口径和测试结果后，再发布到生产环境；
  6. 指标任务进入正式编排，按统一周期持续运行；
  7. 系统监控运行状态、数据质量和更新时间，异常时及时告警；
  8. 业务使用中的新问题继续进入下一轮需求和改进。

这套过程并没有消除沟通和审核，而是让沟通围绕明确的口径、版本和结果进行，也让重复检查和发布操作更加规范。团队交付的不再只是一段 SQL，而是一个能够持续、稳定产生结果的指标。

十、常见误区

误区一：DataOps 就是数据运维

运行维护只是 DataOps 的一部分。DataOps 覆盖需求、开发、验证、发布、运行和反馈的完整过程。

误区二：购买一套 DataOps 平台就完成了转型

工具能够提供版本、测试、发布和监控能力，但不能代替跨角色协作、责任划分和工作流程改进。

误区三：DataOps 只与技术部门有关

如果业务人员不参与口径确认和结果验收，技术流程再自动化，也可能更快地产生不符合业务需要的数据。

误区四：自动化程度越高，DataOps 就越成熟

没有清楚规则和责任边界的自动化，只会更快地放大错误。重要变更仍然需要必要的审核和控制。

误区五：任务发布并成功运行，就表示数据已经交付

数据只有按时产生、质量合格、口径正确并能被下游正确使用，才算完成交付。

误区六：DataOps 只追求交付速度

DataOps 同时关注速度、质量、稳定性和可追踪性。牺牲治理要求换取短期速度，不属于成熟的 DataOps 实践。

十一、实践检查清单

  1. 数据需求是否明确了口径、更新周期、质量要求和责任人？
  2. 业务、开发、治理和运行维护人员是否共同对数据结果负责？
  3. SQL、脚本、工作流和配置是否进行版本管理？
  4. 日期、地区和环境等变化是否通过参数控制？
  5. 是否区分开发、测试和生产环境？
  6. 数据变更是否经过必要的程序检查、质量检查和结果验证？
  7. 发布过程是否能够记录版本、时间、人员和审核结果？
  8. 数据任务是否通过清楚的调度和编排持续运行？
  9. 任务失败、数据延迟或质量异常时是否能够及时告警？
  10. 是否能够判断一次变更影响了哪些数据和下游使用者？
  11. 生产问题和业务反馈是否会转化为新的规则、测试或改进任务？
  12. 自动化和人工审核的边界是否明确？

小结

DataOps 不是一个产品，也不只是数据运维。它是一套贯穿需求、开发、验证、发布、运行和反馈的数据协作与工程方法。

通过参数化、版本管理、环境隔离、测试、发布控制、调度编排和运行监控，DataOps 让数据变更可以重复、验证、追踪和恢复；通过业务、开发、治理与运行维护人员的共同参与，它又让团队从“完成各自环节”转向“共同交付可用数据”。

DataOps 最终要建立的是持续改进的数据生产闭环：更快响应需求，更早发现问题，更稳定地交付结果，并让数据治理要求落实到每一次变更和运行中。
