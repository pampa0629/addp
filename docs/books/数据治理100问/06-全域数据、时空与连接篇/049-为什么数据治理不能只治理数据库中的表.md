# 049 为什么数据治理不能只治理数据库中的表？

## 一句话回答

> 数据库表是数据治理的重要对象，但不是业务数据的全部。文档、图片、音视频、空间数据、遥感影像、三维模型、事件流和物联网观测等数据，同样记录着业务事实。数据治理需要按照不同数据的特点管理其语义、身份、质量、鲜活度、安全、血缘和生命周期，并让它们围绕业务实体和事件发生关联，而不是把所有数据强行转换成表或集中到同一种存储中。

如果治理范围只覆盖关系数据库和数据仓库中的表，组织可能拥有一套整齐的表目录，却仍然无法完整回答真实业务问题。

## 一、为什么数据治理长期以表为中心

传统信息系统通常使用关系数据库保存业务数据，数据仓库和BI也主要围绕表开展汇聚、建模和指标计算。因此，早期数据治理的常见对象是：

- 数据库、Schema和表；
- 字段、类型和长度；
- 主键、外键和索引；
- 数据元、码值和字段标准；
- 表级、字段级数据血缘；
- SQL质量规则；
- 表和字段的访问权限。

这种方式具有充分的现实基础。订单、客户、合同、库存、财务凭证等大量核心业务事实，确实主要保存在数据库表中；表结构清晰，也便于查询、关联、检查和统计。

问题不在于治理表，而在于误以为“治理了表，就治理了全部数据”。随着业务数字化范围扩大，越来越多重要信息并不适合用普通二维表完整表达。

## 二、业务数据远不只有数据库表

现实业务中常见的数据形态包括：

| 数据形态 | 典型内容 | 主要特点 |
| --- | --- | --- |
| 关系表和分析表 | 客户、订单、合同、库存、指标明细 | 结构明确，适合关联和聚合计算 |
| 半结构化数据 | JSON、XML、日志、消息报文 | 具有结构，但字段可能嵌套或频繁变化 |
| 普通文件 | CSV、Excel、压缩包和交换文件 | 以文件交付，版本和内容可能分离 |
| 文档 | 合同、报告、制度、审批材料和巡查记录 | 业务含义主要存在于自然语言和上下文中 |
| 图片、音频和视频 | 现场照片、录音、监控视频和遥感影像 | 内容需要识别、标注或模型分析才能利用 |
| 空间数据 | 矢量、栅格、地址、轨迹、地图和空间关系 | 具有坐标、范围、精度、拓扑和时态特征 |
| 三维和工程数据 | 点云、三维模型、BIM和倾斜摄影成果 | 包含几何、部件层级、材质和专业语义 |
| 实时流和物联网数据 | 设备测点、告警、交易事件和位置流 | 持续产生，强调顺序、延迟、窗口和状态 |
| 图数据 | 人、组织、设备、事件和关系网络 | 重点表达多跳关系和连接结构 |
| 服务返回数据 | API查询结果、外部数据服务和模型输出 | 按契约动态获得，未必长期落入本地表中 |

这些数据有的产生于业务系统，有的来自专业采集设备，有的来自人工文档，有的由算法和模型生成。只要它们能够影响业务判断、流程和结果，就属于数据治理需要关注的范围。

## 三、结构化、半结构化和非结构化只是一个观察角度

人们经常把数据分为结构化、半结构化和非结构化三类：

- 结构化数据具有相对固定的字段和类型，例如关系数据库表；
- 半结构化数据具有标签或层次结构，但结构可能灵活变化，例如JSON和XML；
- 非结构化数据通常没有固定的二维表结构，例如文档、图片、音视频。

这种分类便于入门，但不能完整决定治理方式。

例如：

- 遥感影像是规则的栅格矩阵，却不能只按普通表格理解；
- 轨迹点可以存入表中，但顺序、时间和路径关系同样重要；
- BIM文件内部具有严密的对象和层级结构，却不是普通关系表；
- 文档正文是自然语言，但文件名、作者、版本、审批状态和密级具有明确结构；
- JSON存入数据库字段后，仍然可能具有动态、嵌套的半结构化特征。

因此，“是否存入数据库”和“是否属于结构化数据”不是同一个问题。治理方法还要考虑数据的业务语义、空间特征、时间特征、产生方式、更新方式和使用方式。

## 四、为什么不能把所有数据都转换成表

把数据转换为表，有时能够降低查询和统计门槛。例如，可以从文档中提取合同编号和甲乙方，从视频中提取车辆数量，从轨迹中计算行程指标。

但提取出的结构化结果不能完全替代原始数据。

### 1. 文档的上下文可能丢失

从合同中提取“合同金额”和“签订日期”以后，原文中的附加条件、例外条款、修订内容和签章信息仍然可能影响业务解释。

### 2. 图片和视频的证据价值可能丢失

算法识别出“发现积水”只是一个派生结果。原始图片或视频仍然用于确认积水位置、范围、严重程度和识别结果是否可靠。

### 3. 空间关系不能简化为几个坐标字段

一个面状区域不仅包含坐标，还涉及坐标参考系、边界、面积、邻接、包含、相交和空间精度。只提取中心点可能改变业务事实。

### 4. 实时流的顺序和过程可能丢失

把设备数据定期汇总成日均值，无法还原告警发生前后的瞬时变化、事件顺序和持续时间。

### 5. 三维模型的部件和几何关系可能丢失

把BIM模型导出为一张构件属性表，无法完整保留空间几何、装配关系、模型层级和专业表达。

正确做法通常是保留适合业务使用的原始或权威数据，同时提取索引、标签、特征、实体、关系和指标，形成便于检索、关联和分析的派生数据，并记录二者之间的血缘。

## 五、不同类型的数据需要不同治理方法

所有数据都需要被理解、找到、访问和使用，但具体治理要求并不完全相同。

| 数据类型 | 需要特别关注的治理内容 |
| --- | --- |
| 数据库表 | 字段语义、主外键、码值、完整性、唯一性和模型关系 |
| 文件 | 格式、编码、清单、校验值、版本、目录和完整交付 |
| 文档 | 文种、主题、作者、正文版本、审批状态、密级和有效期 |
| 图片和视频 | 编码、分辨率、拍摄时间、位置、内容标签、版权和隐私 |
| 空间数据 | 坐标参考系、空间范围、精度、拓扑、时态和空间关系 |
| 三维和BIM数据 | 坐标、模型版本、细节层级、部件身份和专业语义 |
| 实时流数据 | 事件结构、事件时间、顺序、迟到、重复、断流和重放 |
| 物联网数据 | 设备身份、测点含义、单位、采样频率、校准和时钟同步 |
| 图数据 | 节点身份、关系语义、关系方向、来源和有效时间 |
| 服务数据 | 接口契约、版本、权限、限流、可用性和返回语义 |

一套只会检查非空、唯一和取值范围的表格质量工具，无法直接判断遥感影像是否缺少波段、视频是否中断、传感器是否漂移或空间数据是否存在拓扑错误。

统一治理必须允许不同数据类型扩展自己的元数据、质量规则、处理方式和服务能力。

## 六、统一治理不等于统一存储

扩大治理范围以后，一个常见误解是：既然要统一治理，就必须把所有数据搬到一个平台、一个数据库或一种存储格式中。

这并不现实，也没有必要。

- 关系数据适合存放在关系数据库或分析仓库中；
- 大规模文件、影像和视频适合存放在对象存储中；
- 高频时间序列可能使用时序存储；
- 复杂关系查询可能使用图数据库；
- 空间数据可以使用具有空间能力的数据库或专业引擎；
- 实时事件通常通过消息和流处理系统持续传递；
- 部分外部数据只能通过服务按需访问。

治理需要统一的是这些数据之间的管理关系，而不是强制统一物理位置。

可以统一的内容包括：

- 稳定的数据身份和引用方式；
- 业务术语、实体和事件语义；
- 元数据和目录入口；
- 来源、转换和使用血缘；
- 质量状态和适用限制；
- 分级分类、权限和使用政策；
- 责任人、版本和生命周期；
- 服务、申请和反馈方式。

数据可以继续存放在适合自己的引擎中，再通过物理汇聚或逻辑访问参与业务场景。统一治理的目标是让它们可发现、可理解、可关联、可控制和可使用。

## 七、全域数据不是“收集所有数据”

本书所说的全域数据，是指突破单一数据库、单一系统和单一数据类型的限制，治理与目标业务场景有关的各类数据。

“全域”强调治理视野，而不是要求组织无边界地采集和保存一切数据。

是否纳入治理，应考虑：

- 是否支撑明确的业务对象、事件或决策；
- 是否有合法、必要的数据来源；
- 是否有持续使用者和责任人；
- 是否能够改善业务结果或降低风险；
- 治理和存储成本是否合理；
- 是否满足安全、隐私和合规要求。

没有用途、无人负责、长期不更新的数据，即使被集中保存，也不会自然产生价值，反而会增加成本和风险。

## 八、数据的价值来自跨类型关联

单独管理每种数据，只解决“数据存在”的问题。数据治理更重要的价值，是让不同来源和类型的数据围绕业务实体、业务事件和时空范围发生关联。

例如，一个设备实体可以关联：

- 设备台账表中的型号和责任部门；
- 物联网系统中的实时测点；
- BIM模型中的空间位置和组成部件；
- 巡检文档中的问题描述；
- 现场图片和维修视频；
- 告警、故障和维修工单；
- 使用手册、维修规程和历史案例。

只有这些数据能够被正确识别为“描述同一台设备或同一次故障”，业务人员才能形成完整设备视图、分析故障原因并优化维护计划。

因此，全域数据治理不能停留在“分别建立几个文件目录和数据库目录”，还要解决跨类型数据的身份、语义、关系、版本和血缘。

## 九、案例：城市防汛为什么不能只看数据库表

城市防汛需要回答的不是“系统中有多少张表”，而是：哪里可能积水、风险何时发生、会影响哪些道路和居民、应该怎样调度处置力量。

### 1. 防汛需要哪些数据

| 业务信息 | 可能的数据形态 |
| --- | --- |
| 易涝点、泵站和排水设施台账 | 关系表 |
| 河道、管网、道路、建筑和行政区 | 矢量空间数据 |
| 地形高程、降雨雷达和遥感影像 | 栅格和影像数据 |
| 雨量、水位、流量和泵站状态 | 物联网实时流数据 |
| 车辆和人员位置 | 时空轨迹数据 |
| 现场监控和巡查照片 | 视频和图片 |
| 应急预案、巡查记录和历史报告 | 文档数据 |
| 天气预报和外部水文信息 | API或外部服务数据 |
| 历史积水、处置过程和影响结果 | 事件和分析数据 |

如果只治理设施台账、雨量记录和处置工单等表格数据，仍然很难判断：

- 降雨落在哪个汇水区域；
- 地形和排水管网如何影响积水；
- 哪些道路、地下空间和社区可能受影响；
- 现场视频是否验证了模型预测；
- 处置方案是否符合当前有效的应急预案。

### 2. 怎样建立关联

治理工作需要统一或映射：

- 设施、道路、社区、监测站和风险点的身份；
- 坐标参考系、空间范围和位置精度；
- 观测时间、预报时间、事件时间和处置时间；
- 降雨、水位、积水深度等指标的单位与口径；
- 视频、图片和巡查记录对应的位置与事件；
- 应急预案的版本、适用范围和生效时间。

这些数据可以分别保存在数据库、对象存储、空间引擎、消息系统和外部服务中，但必须通过统一语义、标识、时空范围和血缘建立关系。

### 3. 怎样服务业务

经过治理后，可以形成持续运行的业务链路：

```text
气象预报和实时降雨
        ↓
结合地形、河道和排水管网分析
        ↓
识别可能积水的位置和时间
        ↓
关联道路、社区、地下空间和重要设施
        ↓
使用视频和巡查数据验证现场情况
        ↓
匹配应急预案并形成调度建议
        ↓
记录处置结果，修正模型和治理规则
```

这里既需要表格数据，也需要空间、影像、实时流和文档数据。任何一种数据都不能独立完成整个业务闭环。

## 十、原始数据与提取结果应该怎样管理

针对文档、图片、视频和三维数据，治理过程中经常会提取：

- 文档中的实体、日期、金额和条款；
- 图片中的对象、位置和状态；
- 视频中的事件、轨迹和时间片段；
- 音频中的文字、说话人和主题；
- 模型中的构件、属性和空间关系。

这些提取结果有利于搜索、关联和计算，但应与原始数据明确区分，并记录：

- 来源文件或数据对象；
- 提取时间和处理任务；
- 使用的规则、算法或模型版本；
- 置信度和质量状态；
- 是否经过人工确认；
- 结果的有效范围和版本。

原始数据记录当时获得的内容，提取结果是基于特定方法形成的派生认识。算法更新后，提取结果可以重新计算，但不能悄悄覆盖原始证据。

## 十一、怎样逐步开展全域数据治理

### 1. 从业务场景而不是存储清单出发

先明确需要解决的问题、采取的行动和衡量结果，再识别需要哪些实体、事件和数据类型。

### 2. 盘点数据及其真实形态

除了数据库，还要检查文件系统、对象存储、专业系统、消息主题、设备平台和外部服务，了解数据是否持续更新、由谁维护以及怎样使用。

### 3. 保留适合数据特点的存储和处理方式

没有必要为了目录统一而把所有数据复制到一种存储，也不应为了能够使用SQL而丢失原始结构和专业语义。

### 4. 建立共同身份和业务关系

围绕客户、设备、土地、道路、项目和事件等业务对象，建立跨系统、跨格式的标识映射和关系。

### 5. 同时管理通用与专业元数据

所有数据都需要名称、来源、责任、时间、版本、权限和生命周期；不同类型还需要坐标、分辨率、编码、采样频率等专业元数据。

### 6. 建立适合数据类型的质量规则

通用的完整性和鲜活度要求可以复用，但空间拓扑、视频完整性、传感器漂移和文档有效性需要各自的检查方法。

### 7. 让数据进入服务和反馈闭环

通过查询、文件、API、事件订阅、地图、模型或分析应用向业务提供数据，并根据使用效果持续修订模型、规则和服务方式。

## 十二、常见误区

### 误区一：只有进入关系数据库的内容才算数据

数据是否重要取决于它记录的业务事实和用途，不取决于是否存入关系数据库。

### 误区二：文件、图片和视频只是表的附件

它们可能是业务证据和主要分析对象，不能只作为一个下载地址附属于表记录。

### 误区三：统一治理就是把所有数据转换成统一格式

统一的是身份、语义、规则和管理关系，不是消除不同数据类型的专业特点。

### 误区四：全域数据必须集中到一个平台

不同数据可以保留在适合的存储和引擎中，通过元数据、目录、逻辑访问或必要的物理汇聚实现统一使用。

### 误区五：非结构化数据无法建立标准和质量规则

文件格式、版本、分辨率、内容完整性、提取准确率和有效状态都可以形成标准与质量要求，只是不能照搬关系表规则。

### 误区六：建立文件目录就完成了治理

目录只能帮助发现。还需要说明业务含义、责任、版本、质量、权限、血缘和使用方式，并与相关实体和事件建立关系。

### 误区七：先把所有数据收进来，再考虑业务用途

无边界收集会增加存储、安全和治理成本。应从高价值场景开始确定治理范围。

## 十三、实践检查清单

1. 数据盘点是否覆盖数据库以外的文件、服务、流数据和专业数据？
2. 是否根据业务实体和事件识别数据，而不只是按存储位置分类？
3. 是否保留了原始数据与派生结果之间的区别和血缘？
4. 不同数据类型是否具有相应的元数据、质量规则和版本要求？
5. 统一治理是否避免强制统一存储、格式和处理引擎？
6. 跨类型数据是否通过身份、时间、空间和业务语义建立关联？
7. 数据是否能够通过合适的服务方式进入实际业务流程？
8. 治理范围是否由业务价值、风险和持续责任决定，而不是追求数据规模？

## 结语

数据库表是现代数据体系的重要基础，数据仓库和维度建模仍然是经营分析与指标计算的核心能力。扩大治理范围，并不是否定表的价值。

真正需要改变的是“只有表才值得治理”的认识。文档记录规则和证据，空间数据描述位置和关系，实时数据反映正在发生的变化，图片和视频呈现现场状态，三维模型表达复杂对象，外部服务提供组织之外的信息。它们共同构成业务世界的数据映射。

全域数据治理不要求把所有数据放到一个地方，而是让不同类型的数据能够被发现、理解、关联、控制和使用。只有这些数据围绕业务实体和事件形成完整链路，数据治理才能突破“整理表结构”的局限，持续为业务判断和行动增值。
