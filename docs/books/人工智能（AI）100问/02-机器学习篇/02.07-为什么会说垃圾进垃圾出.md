# 为什么会说“垃圾进，垃圾出”？数据质量怎样影响结果？

配送公司用过去一年的订单训练超时预警模型。模型在测试中表现不错，上线后却经常漏掉雨天订单。开发者检查后发现，训练数据里的天气字段大多取自配送结束时的记录；系统真正发出预警时，只能取得下单时的天气信息和预报。模型在训练中学到的关系，不能按原样用于实际预测。“垃圾进，垃圾出”提醒人们检查这种问题，但它不是说只要清洗掉空值，模型就一定可靠。

## 数据质量首先要符合任务

业务人员和开发者要问的不只是“有多少条数据”，还包括数据代表了什么。订单的出发地写错，属于准确性问题；部分订单没有送达时间，属于完整性问题；不同系统对“超时”采用不同承诺时限，属于一致性问题；天气记录晚于预警时刻才产生，属于及时性与可用性问题。

即使每条记录都填写完整，样本仍可能缺乏**代表性**。如果历史订单主要来自城区平日白天，而系统今后要处理郊区夜间配送，测试集里缺少后一种情况，模型的好成绩就不能说明它适合新场景。少数特殊订单也可能被平均成绩掩盖。团队需要按地区、时段、天气和订单类型分别检查效果，而不能只看一个总分。

## 标签错误会改变模型“学会了什么”

假设有些延误订单被人工改记为“客户原因取消”，训练数据便可能把真实的配送问题排除在“超时”之外。模型学到的不是业务人员原本想识别的风险，而是历史记录的填写习惯。标签质量包括定义是否清楚、记录是否准确，以及争议样本怎样处理。

偏差还可能来自收集过程。如果公司只保存已完成订单，模型就看不到中途取消或异常终止的订单；这些订单恰好可能与配送风险有关。团队需要追问数据是怎样产生、哪些情况未被记录，不能把数据库里有的记录当成现实的全部。

## 更好的数据也要持续核查

开发者可以检查字段错误、修订标签规则、补充缺失场景，并在新订单上重新评价模型。但数据质量没有一个脱离任务的万能分数：某个字段对预测配送时长很关键，对识别邮件垃圾信息却可能毫无意义。模型上线后，业务流程、服务区域或交通条件变化，团队还要继续观察输入和结果是否偏离训练时期。

“垃圾进，垃圾出”也不能成为把模型失败全推给数据的借口。错误的任务目标、不合适的评价指标、模型和部署方式，同样会造成坏结果。团队需要沿着“业务目标—数据—训练—评价—使用”的链路定位原因。
