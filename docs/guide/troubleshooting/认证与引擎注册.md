## macOS 询问 Python 访问 `addp-cli` 钥匙串密码

### 问题现象

执行 `addp auth login`、`addp auth status` 或需要刷新登录会话的 Tool 命令时，macOS 显示系统弹窗：

```text
Python 想要访问你的钥匙串中的密码“addp-cli”。
若要给予许可，请输入“登录”钥匙串的密码。
```

选择“拒绝”或未通过系统验证后，CLI 返回：

```json
{"error":{"code":"authentication_unavailable","message":"无法访问操作系统凭据存储"}}
```

登录阶段可能使用 `authentication_failed`，但消息相同。

### 根本原因

正式 `addp` CLI 由 Python wheel 安装并通过 macOS Keychain 保存 Refresh Token。macOS 会按请求访问钥匙串条目的应用身份实施访问控制；首次访问已有条目，或 Python、pipx 环境、可执行文件身份发生变化后，系统可能要求当前用户再次确认。弹窗中的请求方因此显示为 `Python`。

这是 macOS 对“登录”钥匙串的本地授权，不是 ADDP OAuth 登录、ADDP 账号密码或 System 服务故障。OAuth 主路径和凭据存储边界不变：Refresh Token 只进入 OS Keychain，Access Token 只存在于当前进程内存。

### 正确处理

1. 确认弹窗来自 macOS，访问的条目名是 `addp-cli`，当前执行的命令确实是已安装的 `addp` CLI。
2. 只在该系统弹窗中输入当前 macOS 用户的“登录”钥匙串密码，通常就是系统登录密码；不要把密码输入终端或浏览器授权页。
3. 正常首次使用选择“允许”完成单次授权。项目不默认建议对通用 `Python` 进程选择“始终允许”。
4. 重新执行状态检查：

   ```bash
   addp --version
   addp auth status
   ```

5. 如果状态检查正常执行但返回 `authenticated:false`，说明此前登录未能保存 Refresh Token，重新执行：

   ```bash
   addp auth login
   addp auth status
   ```

6. 完成临时验收后需要撤销会话时，使用正式退出命令：

   ```bash
   addp auth logout
   ```

### 禁止的处理方式

- 不使用 `security find-generic-password -w` 等命令把 Refresh Token 输出到终端。
- 不把 Refresh Token 复制到文件、环境变量、命令参数或日志。
- 不删除整个“登录”钥匙串，也不把删除 `addp-cli` 条目作为常规授权处理。
- 不配置明文文件 Keyring 降级，不新增手工 Token、密码、Client Secret 或 API Key 登录路径。

## 模块注册与心跳失败

先区分模块实例注册／续租与 Workflow Engine 注册；请求字段、稳定错误码、五态生命周期和重试／终止条件统一见[模块注册契约](../../concepts/modules/Gateway注册与路由.md#核心机制说明)。诊断须能关联具体操作与实例；结构化错误不等于注册成功、租约恢复、Ready 或实际请求已经验收。

Token Endpoint 的成功响应含凭据，诊断只能记录稳定错误码、可重试性、响应体字节数、Content-Type 和不含值的字段校验原因，禁止记录原始响应体或任何 Token 值。同样不得记录 Client Secret。模块注册 API 的受限错误正文与 Token Endpoint 的凭据成功响应分别处理，不能把前者的 `response_body` 规则套用于后者。

日志包含 `service_token_response_invalid` 且 `response_reason="expires_in"` 时，继续按[服务令牌有效期排查](#服务令牌有效期越界导致模块退出)核对；Workflow 引擎的具体身份或代理问题沿本文对应的 [401/403](#工作流-runtime-注册失败-401403)与 [502](#workflow-引擎注册失败-502) 专题排查。

## 服务令牌有效期越界导致模块退出

后端出现 `service_token_response_invalid`、`response_reason="expires_in"` 及 `module registration lifecycle failed; stopping process` 时，核对签发和校验使用的时间基准。

Client Credentials 的过期点由数据库时间设置；如果响应剩余秒数却用应用时间计算，数据库与应用的时钟偏差可能使结果超出服务客户端的 1–300 秒契约。System 在现有签发事务中使用数据库 `clock_timestamp()` 计算响应有效期并扣除签发耗时；剩余不足 1 秒、超过 5 分钟或查询时间失败时回滚，返回可重试的 503 / `temporarily_unavailable`，不放宽客户端校验或返回过期令牌。

只读比较主机 UTC 与 PostgreSQL `clock_timestamp()`，关联模块就绪端点和注册心跳。没有实际响应秒数的历史日志不能证明具体时差或根因。诊断字段与敏感信息边界见[模块注册与心跳失败](#模块注册与心跳失败)；不要修改主机或共享数据库时钟做验证。

回归使用测试连接的时间投影，入口为 `make test-system-iam-postgres`，本地仅使用 `addp_iam_test`。需要恢复开发服务时，遵循[生命周期与保活边界](开发服务与构建.md)。

## Workflow 引擎注册失败 502

若 Runtime 注册返回 502，System 却没有对应请求，而直接连实际 System 地址的诊断正常，应检查请求是否被系统 HTTP 代理截获。`requests` / `urllib` 读取的代理来源可能与诊断命令不同；不能只凭 curl 成功断定所有客户端都直连，也不能把所有 502 都归因于代理。

身份与注册主路径见[Runtime 注册规范](../../spec/workflow/Runtime注册与扩展.md#引擎注册)；先核对生产内置 Runtime 是否复用[OAuth 注册助手](../../../common-python/addp_common/client/runtime_registration.py)，其 HTTPX 客户端固定 `trust_env=False`。

再查看代理配置和失败响应来源。macOS 可只读检查系统代理：

```bash
networksetup -getwebproxy Wi-Fi
```

其他 Python 请求需按实际客户端检查代理环境；仅设置 `NO_PROXY` 不能替代内置注册助手的固定边界。不要打印可能包含凭据的完整代理环境变量，也不在各 Runtime 复制 Token 请求、代理绕过或注册 URL。

注册结果与运行状态统一按[验证修复](#验证修复)核对。

## 工作流 Runtime 注册失败 401/403

### 问题现象

启动 GeoPython、Spark、Model3D 或 PointCloud Workflow Runtime 后，日志显示 OAuth Token 请求或 Runtime 注册返回 401/403，System 中没有对应内置 Runtime。

### 问题根因

Runtime 没有使用与自身 `engine_type` 一一绑定的 Platform Service Principal，或对应 `*_WORKFLOW_SERVICE_CLIENT_SECRET` 与 System provision 的 Confidential OAuth Client Secret 不一致。System 只接受短期 Platform Service Access Token，并校验 `system.runtime_registry.update` 与 Runtime 身份归属。

### 技术细节

生产内置 Runtime 的固定 Client ID：

- GeoPython: `addp-geopython`
- Spark: `addp-spark`
- Model3D: `addp-model3d`
- PointCloud: `addp-pointcloud`

Math Workflow 是协议参考实现，需要时通过 System 引擎管理按扩展引擎手动注册。

### 解决方案

1. 确认 `.env` 中对应 Runtime Secret 非空且至少 32 字节。
2. 确认 System migration 已 provision 对应 Service Principal、OAuth Client 和 Platform Runtime Role。
3. Runtime 必须调用 `register_runtime_engine(system_url, client_id, client_secret, payload)`，不得自行拼接注册路由。
4. 注册请求的 `engine_type` 必须与 Service Principal 固定归属一致。

### 验证修复

需要重启时，由用户在自己的终端执行受影响 Runtime 的标准重启命令，再检查实际注册日志。以下以 GeoPython 为例：

```bash
./scripts/dev/restart.sh -geopython-workflow
tail -n 100 logs/geopython-workflow-engine.log
```

在 System 引擎管理页核对已启动 Runtime 的注册与连接状态；注册请求被接受不等于连接已在线。需要修改身份、权限或协议时，先查[Runtime 注册规范](../../spec/workflow/Runtime注册与扩展.md#引擎注册)，不增加共享密钥或另一条注册路径。

## 资源搜索提示“授权服务暂时不可用”

先核对 `error_code`。`authorization_service_unavailable` 表示未取得有效 System AuthContext，不表示用户无权限；其他 HTTP 503 须另辨原因。资源树搜索调用 Meta `/api/v1/meta/resource-tree/:engine_id/search`，共享认证中间件向 System `/api/v1/system/auth/context` 获取当前授权上下文；上游失败或超时使该次业务请求失败。

System 对非预期的会话凭据投影失败记录 `event=iam.auth_context.resolve_failed`，沿用当前 `request_id`，包含总耗时、当前阶段耗时、安全错误分类及合法 SQLSTATE。无效、过期或撤销凭据等预期认证拒绝不记为内部故障；诊断不含令牌、Hash、授权快照、SQL 参数或原始错误正文，不改变 HTTP 错误和权限判断。

连接建立失败记为 `database_connection`；可确认时细分为 `connection_refused`、`connection_reset`、`connection_closed` 或既有超时／取消分类。pgx 多地址连接按最后一次尝试分类，避免将 IPv6 快速拒绝误当成随后 IPv4 的超时；不记录地址、凭据或原始错误正文。

解析阶段依次为 `transaction_begin`、`credential_snapshot`、租户上下文的 `departments`／`project_groups`、`role_permissions`、`projection`、`transaction_commit`。阶段耗时含失败后的事务收尾，不是数据库独立执行时间。`transaction_begin` 可能等待连接或建立事务，不能据此断言连接池耗尽。

`pool_open`、`pool_in_use`、`pool_idle`、`pool_max_open` 是故障时的进程连接池状态，`pool_max_open=0` 表示最大连接数不限。`pool_wait_count_total` 与 `pool_wait_duration_total_ms` 是整个进程连接池的累计值，不是该请求独有的等待时间；读取统计不创建额外数据库连接。

**修复版本。** 受控 Fosite 的错误分类会影响共享服务令牌客户端的重试和模块注册生命周期：

| 版本 | 行为与处理要求 |
| --- | --- |
| `v0.50.0-addp.2` | 客户端查询的任意 Storage 错误均被包装为 `invalid_client` / HTTP 401，按不可重试错误处理，可能使模块退出。 |
| `v0.50.0-addp.3` | 未覆盖撤销／内省响应器边界，不应部署，应直接升级 `.4`。 |
| `v0.50.0-addp.4` | 客户端不存在（含停用）仍拒绝认证；查询超时、连接断开或内部存储错误返回 `temporarily_unavailable` / HTTP 503，由既有链路重试，错误密码仍被拒绝。撤销／内省响应器不再将服务器故障吞成 HTTP 200，撤销事务或审计失败不再报成功。 |

此修复不证明历史资源树 503 必然经过该分支，也不消除数据库或 Docker VM 的响应停滞。

**现场证据与判断边界。** 同一请求 ID 的 System 连接拒绝，若同时对应 Docker Desktop 事件流断开、多个 Infra 容器启动时间同步变化和 PostgreSQL 崩溃恢复，可将该窗口判为基础设施中断；不能据此解释所有历史 503。

PostgreSQL 容器未重启也可能发生实例级崩溃恢复。2026-10-21（北京时间）记录了两次后端进程 `exit code 2` 及恢复窗口：09:24:20–09:24:47、15:32:17–15:32:28。后一次恢复中，System 查询 `addp-gateway` 客户端返回 SQLSTATE `57P03`，旧版 Fosite 误报为 401，Gateway、Develop、Monitor 因不可重试的 `invalid_client` 退出。恢复后原 Gateway 配置凭据仍可获取令牌并读取模块注册表，不应补权限或重置 Secret；应核对运行构建包含 `.4`，再由用户通过标准生命周期入口恢复已退出模块。`StartedAt` 不变、`RestartCount=0` 不能排除 PostgreSQL 内部恢复。

该现场证明了数据库中断到模块退出的链路，未解释后端进程最初为何退出。只有退出码，缺少连接身份或信号来源，不能归因于某个 SQL、测试会话、OOM 或手工信号；也不能替代对 2026-10-18 原始停滞的调查。数据库未重启、连接已建立但握手或查询停滞时，仍需当时的数据库等待和宿主机／虚拟机调度证据。

**账号与权限保留回归。** 独立入口为 `make test-system-iam-postgres SYSTEM_IAM_POSTGRES_TEST_ARGS='--test database-crash-recovery'`，完整 System IAM 门禁与 CI 也执行此回归。该 T2 仅操作自建一次性容器，验证后端 SIGQUIT 内部恢复、容器 SIGKILL 后启动；对含三员、MFA、本地账号、租户成员和角色分配的夹具逐表对账，复核原账号凭据、授权上下文与未提交授权回滚。不触碰个人 Infra，不替代磁盘损坏、丢失数据卷或跨模块 Online 验收。

Console 的持久化用户名仅用于展示，不证明当前会话有效。静默恢复失败且内存中尚无 Access Token 时，同样必须显示授权确认失败及重试入口；重试期间隐藏业务内容，成功读取当前 AuthContext 后才判断是否真的没有可用模块。不能把网络断开、Gateway 不可用或授权服务 5xx 显示成账号缺少权限。

排查时以请求 ID 关联消费方和 System，结合数据库当时的连接、等待事件和阻塞者，再与同一时间窗口的运行环境指标对照。应用事件时间与采集时间需要分开，采集积压时不能按落盘先后推断因果。历史高负载与超时同时出现只能形成线索；没有等待状态或进程级证据时，不归因到具体 SQL 或测试任务，不通过延长超时、缓存旧权限或自动重试掩盖问题。

诊断回归使用 `make test-module MODULE=system GO_ONLY=1`，覆盖真实 `database/sql` 连接等待取消、错误保持、安全分类和日志脱敏；这是 Go T1，不替代 PostgreSQL T2 或真实运行验收。现有 Go workspace CI 自动发现这些测试。诊断代码更新后，用户在自己的终端执行 `./scripts/dev/restart.sh -system` 使其生效；AI 不自行重启服务。
