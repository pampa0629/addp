# 元数据扫描与检索故障排查

[返回常见故障排查](../addp常见故障排查.md)

## Manager 刷新 item 成功但属性未更新（item 刷新误走 catalog scan）

### 问题现象

- 点击 Manager 的“刷新数据项”按钮后，接口提示成功。
- 但 item 的属性仍然缺少新的能力或索引信息，例如 `access_index` 仍为空。
- 现象在 Shapefile 这类 multi-ref item 上最容易暴露，但根因不局限于某一种格式。

### 根本原因

item 刷新原先复用了 catalog scan 的入口，把 `item_id` 先转换为 catalog paths，再从目录或对象路径重新发现 item。

这会混淆两类输入：

1. catalog scan 的输入是扫描范围和候选资源集合，用于发现 item。
2. item refresh 的输入应是已知 item descriptor，用于基于现有 `layout`、`format`、`refs` 和 `storage` 刷新属性。

对于 multi-ref item，如果把 `refs` 当作多个扫描路径，会破坏原本的候选集合，复合识别入口无法再次获得完整 refs。于是刷新流程可能正常结束，但没有真正重算并落盘该 item 的深度属性。

### 修复方案

- Manager 的 item 刷新只通过 Meta client 调用 Meta item refresh 能力。
- Meta 的已知 item refresh 路径：从标准 attributes 还原 item descriptor，再按 format provider 能力刷新属性并落回同一个 item。
- catalog scan 继续负责发现 item；item refresh 不再通过 `item_id` 反推父目录，也不通过 `refs` 反推扫描范围。

### 预防措施

1. 新增或修改 item refresh 能力时，先还原标准 item descriptor，不要在 Manager 或具体扫描服务中重复格式识别。
2. `refs` 只表示 item 的组成内容，不应直接作为 catalog scan target。
3. `layout=multi` 的 item refresh 应使用已落库 `attributes.item.refs`，不得把父目录或 `storage.physical_path` 目录当作普通文件读取。
4. 如果 item 刷新成功但属性未变化，先检查该 item 的 `attributes.item.layout / item.format / item.refs / storage` 是否足以打开内容。

## Manager 上传成功，但文件只有扫描目录后才显示

先关联上传响应的 execution、执行终态和目录刷新请求，再比较 item 的 `full_name` 与父 node 的 `full_name`。例如文件为 `addp/doc/文件.md` 却挂在 `addp` bucket 下，资源树按父节点读取时就会显示到错误层级；不能只归因于格式不支持或前端刷新太早。

对象归属必须从 bucket 内规范父路径建立同一条 prefix 链，扫描范围只限制枚举和扫描状态。写入前校验身份与父节点，目录扫描纠正既有错挂记录时不能因内容未变化而跳过。不通过前端多刷新、补扫整个父目录或直接 SQL 改 `node_id` 掩盖归属错误。树顶部刷新只回读元数据，节点扫描才重建目录事实；已存在错挂数据需在部署修复后显式扫描受影响目录。

目录内容、数量和大小均由有效父子关系中的逻辑 item 事实计算。Meta 按关系批量聚合，不恢复 node 统计列、“上传后加一”或扫描后覆盖祖先统计。上传引用组、known-item refresh、删除和局部扫描不能冒充完整范围扫描；计数也不能由 Manager 当前分页行数代替。

若当前目录数量已更新，切换上级却仍显示旧数量，核对 `loadNodeChildren(locator, true)` 是否回读 ancestors、合并节点事实并使失效链上的 children 缓存失效，同时保留 sibling、展开和选择状态。回归必须覆盖“上传后直接切换上级”，不能只验证整页重载。

验证入口为 `make test-module MODULE=meta`、`make test-meta-postgres` 和 `make test-manager-frontend`；涉及 PostgreSQL 时先核实实际端口，只使用 `addp_test`。数量聚合无需重新扫描业务存储；涉及 Meta 持久化变更时，需用户一起重启 Backend 与 Worker，避免旧进程继续写已删除的统计列。

## 目录仍显示扫描失败，或失败子目录反而显示已扫描

node 的最近范围扫描状态与当前数据可用性、item 数量不同。单文件刷新成功不会覆盖父范围扫描结果，不能为消除失败提示自动补跑整桶扫描或把父目录置为成功。

按本次覆盖节点与完整失败路径统一核对收尾：失败只影响覆盖范围内相关节点，正常兄弟范围独立成功，empty prefix 和枚举失败也必须收尾。执行报告中限量、截断的失败样本不能用于状态归属。

Manager 分别展示最近范围扫描状态、已完成深度和最近成功扫描时间；共享资源树传递并保护 `scanned_depth`，不能从数量、属性或本地化旧状态猜测。开始和失败不修改 `scanned_at`。迁移 025 已将旧 running / failed 记录中无法还原的时间置空，不改内容、状态或深度；之后由成功扫描建立可信时间。旧代码误标成功的目录须通过受影响范围的显式扫描重建事实，不由兄弟或单项结果反推。

验证入口为 `make test-module MODULE=meta`、`make test-manager-frontend` 和共享消费方 `make test-go`；迁移用例由 `make test-meta-postgres` 覆盖。PostgreSQL 仅用已核实端口上的 `addp_test`。部署涉及 Backend / Worker 或共享代码时，按生命周期规范由用户重启相关服务，不能只刷新浏览器。

## NFS 深度扫描长时间无新进展，或完成数大于最终数据项数

关联同一 execution 的进度事件、`scan_progress` 快照和 Manager 内容索引删除请求，区分属性采样、内容哈希、索引投影及旧组件清理。Worker 租约正常只证明仍持有执行，不证明实际工作有新进展。

排查重点：

- 物理文件与逻辑数据项不是同一分母。whole / multi 合并后，计划按规范 fingerprint 去重；非 whole 项归主文件实际父目录，不能被祖先、中间目录和父目录重复处理，force 回收也消费同一归属结果。
- 旧组件清理在原事务中按精确 ID 分批删除元数据，事务外按每批最多 100 个精确 fingerprint 调用 Manager 唯一删除入口。`cleaning_index` 只累计实际确认与未确认的批次，不按目录前缀扩大范围，不自动重试未决投递，不把索引未确认算作 item 扫描失败。
- 属性进度只统计实际返回的范围字节和定位读取次数；顺序头部读取、空读、EOF 和心跳不制造范围进度。每次范围打开和读取前检查取消，切换操作或数据项时清零；范围数不能当作文件完成比例。
- 内容指纹读取字节与属性范围字节分别展示；总量未确定时显示不定进度。终态保留快照并独立回读资源树，距最近进展时间不等于执行失败判定。

PLY 采样复用本次属性提取已经打开的完整内容流的原生 `io.ReaderAt`；NFS 在现有文件句柄上定位读取并恢复顺序游标。没有原生能力的引擎使用 `common/contentio.NewReaderAt` 适配既有范围读取，Parquet 共用该适配。原生读取失败不切换另一条路径，不跨任务缓存句柄，不改变 8,192 个均匀采样的位置、数量、边界或全文哈希。

NFS 只读范围不重复查询无用的文件大小，关闭只读流不发送写入 COMMIT；写入流关闭仍提交，普通内容流保留支持 SeekEnd 所需的大小。不得把低效的“每点重新打开/关闭一次”固定为测试契约。

验证入口：

```bash
make test-module MODULE=common GO_ONLY=1
make test-module MODULE=meta GO_ONLY=1
make test-meta-postgres
make test-manager-postgres
make test-manager-frontend
make test-go
```

PostgreSQL 使用已核实端口上的 `addp_test`，Manager 门禁管理独占 Meilisearch fixture。涉及 Common 的运行复验，须用户重启全部模块；比较同一数据集的名称、类型、大小、完整 attributes、内容指纹、采样数量和边界值，并检查取消、进度与终态。

单次耗时或日志中的阶段窗口不代表独占函数/RPC 耗时；并发负载、缓存与 SQL 等待未控制时，不宣称固定提速比例。未发生旧组件索引删除的扫描也不能证明该清理路径的业务性能。

稳定语义见[元数据扫描机制规范](../../spec/addp元数据扫描机制规范.md)，读取能力见[内容 I/O 抽象规范](../../spec/addp内容IO抽象规范.md)。

## SQLite 扫描要求 table option，或 Excel 父文件被识别为 table

统一内容增强若把“格式插件提供 TableInfoProvider”误当作“父文件可以转成表”，SQLite 容器会拒绝缺少 table option 的读取，Excel 却可能默认选取首张工作表并掩盖误判。

`EnrichResourceAttributes` 先确认 single 文件身份；容器按格式声明保持 container，只有 document 可经内容进一步识别为 table。known-item refresh 走同一入口，纠正旧 Excel 父类型并清理旧表字段、行数及派生索引，保持 item ID 和逻辑数量。读取或解析失败必须报错，不覆盖已有成功元数据，不默认首表、不吞错返回空容器。

部署后由用户重启 Meta Backend 与 Worker，只刷新受影响条目并核对类型和 children，不重扫整个 bucket 或直接改业务表。标准入口为 `make test-module MODULE=meta`，PostgreSQL 使用已核实端口的 `addp_test`。回归必须覆盖统一入口的容器类型矩阵和 known-item 刷新持久化，不能只调用子容器辅助函数。

## Meta 已登记 DataItem，但 Manager 搜索不到

元数据持久化、搜索投递和外部索引完成是三个不同事实。曾出现 MongoDB collection 扫描保存 Meta 后遗漏 Manager 技术投影提交，关系表却可检索；同样的症状也可能来自租户／引擎过滤、投递失败或搜索出口隔离，不能只凭 Meta 中存在条目就认定索引已完成。

先只读核对当前 Tenant、Engine、fingerprint、名称及已登记结构，再沿正式 Manager 投递记录核对关联、外部任务终态和出口状态，最后用同租户、同引擎搜索验证。无投递记录时检查扫描、未变化路径及单项刷新是否调用统一技术投影；有投递而未收敛时按持久投递恢复契约排查，不清空记录、盲目重发或手工解除隔离。

修复遵循[元数据扫描机制规范](../../spec/addp元数据扫描机制规范.md#dataitem-技术元数据搜索投影)：Meta 只提交已登记技术事实，Manager 独占索引；技术与正文分别幂等更新并存。历史集合补录使用规范中的精确 `basic + force=true` 正式入口，先说明范围并确认，不用可能采样的 deep 单项刷新代替。禁止直接写 Meilisearch、在 Agent 增加枚举兜底或绕过 Security。复验走 Meta/Manager PostgreSQL 与 Manager 前端标准门禁；扫描 execution 成功不代替索引终态和实际召回。
