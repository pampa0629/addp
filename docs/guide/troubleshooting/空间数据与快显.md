## Transfer 写出 Shapefile 后资源树看不到 `.prj`

### 问题现象

- Transfer 空间表导出到对象存储 Shapefile 后，执行记录显示任务成功。
- 对象存储目标实际包含 `.shp/.shx/.dbf/.prj/.cpg` 等组件，或 `common.task_executions.metadata.target_refs` 已包含 `.prj`。
- 但 Manager / Meta 资源树或 item 属性中 `attributes.item.refs` 缺少 `.prj`，`format_info.shapefile.has_prj=false`。
- Meta worker 日志可能出现类似 `bucket=gis path=a2.shp`、`The specified bucket does not exist` 的错误。

### 根本原因

外部 content path 与内部 object key 的分工统一见[Meta scan 内部路径语义](../../spec/addp存储引擎路径体系规范.md#meta-scan-内部路径语义)。本问题的关键是 `.prj` 对外引用须为 `addp/gis/a2.prj`；若把 bucket 内 object key `gis/a2.prj` 提交给 Meta，`gis` 会被拆为 bucket，`a2.prj` 被拆为 object key，扫描便指向错误 bucket。

另一类常见原因是字段映射 transform 只复制了几何列类型和 SRID，没有保留 `SpatialInfo.CRSRef/CRSDefinitions`。这种情况下 Shapefile writer 没有 CRS WKT 文本，也不会生成 `.prj`。

### 排查顺序

以下 SQL 供具备相应数据库读取权限的运维排查持久事实；用户页面和 API 读取仍遵守[专业响应的身份、权限与安全投影](../../../transfer/docs/tables/task_executions表.md#六api)，不能据此直接公开原始 metadata。

1. 查 Transfer execution：
   ```sql
   select id, execution_id, status, metadata->'target_refs'
   from common.task_executions
   where module='transfer' and source_task_id='<task_id>'
   order by id desc limit 5;
   ```
   对象存储 Shapefile 的 refs 应为 `bucket/object_key`，例如 `addp/gis/a2.prj`，不能是 `gis/a2.prj`。

2. 查 Meta item：
   ```sql
   select id, full_name,
          attributes->'item'->'refs' as refs,
          attributes->'format_info'->'shapefile' as shapefile_info
   from meta.meta_item
   where engine_id=<engine_id> and full_name='<bucket/object.shp>' and deleted_at is null;
   ```

3. 查日志：
   - `logs/transfer-bounded-worker.log`：确认 `target_refs` 是否包含 `.prj`。
   - `logs/meta-worker.log`：如果看到把 object key 第一段当 bucket 的错误，优先检查 Transfer 提交的 `ref_groups.path`。

4. 不要用 MinIO 容器内 `/data/...` 文件系统形态判断对象是否存在。MinIO 后端存储布局可能把对象表现为目录；应通过项目 content reader、MinIO API 或 Meta/Transfer 执行元数据确认。

### 修复原则

- 产物引用沿[扫描请求路径规范](../../spec/addp存储引擎路径体系规范.md#扫描请求路径字段)；bucketless 错误在 Transfer 对外边界修正，不增加 Meta 兼容路径。
- 扫描范围沿[写后 Meta 扫描](../../../transfer/docs/transfer-基本概念及配置说明.md#十一写后-meta-扫描)，Shapefile 只提交实际生成的 refs group，不补不存在的 sidecar，也不扩大到父目录。
- 字段映射 transform 必须保留空间 CRS 事实，尤其是 primary geometry column 的 `CRSRef` 和 `SpatialInfo.CRSDefinitions`。

### 验证命令

环境前提、门禁范围与固定版本证据分别见[Transfer 验证入口](../../../transfer/README.md#启动与验证)和[Meta 模块入口](../../../meta/README.md)。下列命令不是本次已运行的证据，模块门禁通过也不替代目标内容及资源树实测。

```bash
make test-module MODULE=transfer
make test-module MODULE=meta
```

按[执行与恢复边界](../../../transfer/docs/tables/tasks表.md#执行恢复与验收边界)选择获授权的重新执行方式后，应同时核对下列结果。扫描提交成功不等于扫描完成，扫描失败也不回滚已写产物，见[产物扫描来源契约](../../spec/tasks/生产来源与产物扫描.md#生产执行与后台扫描的来源)：

- `common.task_executions.metadata->'target_refs'` 包含 `bucket/.../*.prj`。
- `meta.meta_item.attributes.item.refs` 包含同一个 `.prj`。
- `meta.meta_item.attributes.format_info.shapefile.has_prj=true`。

## MVT 物化视图准备失败 - column "id" does not exist

### 问题现象

历史实现曾在瓦片缓存生成任务中隐式准备 3857 物化视图。遇到混合大小写主键或几何列时，可能报错：

```text
物化视图创建失败: ERROR: column "id" does not exist (SQLSTATE 42703)
```

### 当前状态

该旧准备路径已经删除。瓦片缓存生成任务不再隐式创建物化视图、空间索引或执行准备检查；3857 矢量物化视图目标只能由 `vector_materialized_view_generation` 任务显式创建和刷新。

当前排查方式：

1. 在空间预览页看到源表转换慢路径、动态 MVT 超时或优化建议时，先进入“矢量物化视图”。
2. 创建并执行 `vector_materialized_view_generation` 任务。
3. 确认 `manager.vector_materialized_view.status=ready` 后，再生成瓦片缓存。
4. 若仍有大小写字段相关错误，检查 `manager/backend/internal/service/vector_materialized_view_task_service.go` 和 `common/spatial` 是否使用 PostGIS 标识符引用函数。

### 验证命令

```bash
make test-module MODULE=manager
```

## PostgreSQL 混合大小写字段报 column does not exist

混合大小写字段如 `SmGeometry`、`OBJECTID`、`SHAPE` 未经正确标识符引用，可能在动态 MVT、物化视图或要素查询中被折叠成小写。先比对真实 schema、表名、主键和几何列，再核对生成 SQL 的每处标识符；不要假定几何列总叫 `geom`。

按职责定位：

- 跨 SQL 引擎的标识符引用、表名拼接和基础 SELECT / COUNT / 分页使用 `common/query`；方言由插件的 `SQLDialectProvider` 声明，不在通用代码中固定 PostgreSQL。
- PostGIS 空间表达式、MVT、物化视图和 GiST 索引使用 `common/spatial`。动态 MVT 只消费已解析目标，不隐式创建 3857 派生对象。
- Manager 重点检查 `vector_materialized_view_task_service.go`、`unified_mvt_service.go` 与 `common/spatial/mvt.go`；Service 检查 `ogc_features_handler.go` 与 `query_executor_service.go`。
- 列名、schema 和表名是标识符，值条件使用参数绑定；不以手工 `fmt.Sprintf` 拼双引号代替方言的引用与转义函数，也不维护第二套 PostgreSQL SQL 构建包。

自动验证走 `make test-module MODULE=manager`、`make test-module MODULE=service`，共享实现变更加 `make test-go`。运行验收在授权的隔离数据范围中覆盖混合大小写列的预览、矢量物化视图、瓦片缓存及当前 Service 要素查询；记录实际结果，不把步骤列表中的勾号当作执行证据。

相关边界见[数据库大小写处理规范](../../spec/addp数据库大小写处理规范.md)、[common/query](../../../common/query/) 和 [common/spatial](../../../common/spatial/)。

## 点云 COPC 快显生成失败

### 现象

LAS / LAZ / E57 / PCD / XYZ 数据项在 Manager 数据探查中点击“生成 COPC 快显”后失败，Manager 日志中可能出现：

```text
direct workflow operator laz_to_copc is unavailable
```

Runtime 已监听但 PDAL 不可用时，`GET /health` 返回 HTTP `503` 和 `status=unhealthy`，并在 `dependencies.pdal` 中提供结构化依赖事实；System 将实例观测为 `offline`。监听后仍会异步登记身份，不能用注册成功代替可执行状态，详见 [Runtime 注册规范](../../spec/workflow/Runtime注册与扩展.md#引擎注册)。

### 根因

点云 COPC 转换依赖运行时独立环境内的 PDAL。普通 Python venv 只隔离 Python 包，不能提供 PDAL/E57 的原生库。开发入口统一创建独立 Conda 前缀并验证实际驱动和 COPC 转换；不得手工指向系统 `pdal`，也不得继承 Conda base 的 GDAL/PROJ 插件和资源路径。

原生开发环境需要更新依赖时，由用户在终端通过标准入口重启；入口先停止所选 Runtime，再准备独立 Conda 环境并验证原生能力：

```bash
./scripts/dev/restart.sh -pointcloud-workflow
```

检查 `logs/pointcloud-workflow-engine.log` 与实际端口的 `/health`；就绪必须满足 HTTP `200` 和 `status=healthy`，System 中实例还须为 `online`。原生开发的连接信息应使用宿主机实际地址与端口。

环境更新失败、原生库无法加载或插件缺失时，准备门禁阻止开发服务启动。已有服务运行时禁止就地改依赖，须通过上述入口先停止后准备。开发入口拒绝非 Conda 前缀，不自动删除未知环境或接管外部监听者。PDAL 与原生包声明见[运行时 README](../../../engines/pointcloud-workflow/README.md#开发启动)；产品容器的构建与部署见[产品部署](../../../engines/pointcloud-workflow/README.md#产品部署)。

COPC 始终先写入 `POINTCLOUD_WORK_HOST_PATH` 指定的受控工作目录，再按 access plan 上传；大文件需要足够磁盘空间。
