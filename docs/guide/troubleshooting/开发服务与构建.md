## Codex 等托管命令环境中 restart.sh 退出后服务立刻不可用

若启动脚本内 `/health/ready` 通过，命令结束后实际端口却立刻不可用，而日志显示曾正常响应，先检查托管执行环境是否回收了派生的后台进程树。不要仅凭端口消失判断服务自行崩溃。

普通终端使用标准 `start.sh` / `restart.sh`。用户已在外部终端运行环境时，需要局部重启，由用户在原终端执行：

```bash
./scripts/dev/restart.sh -orchestrator
```

确需在托管命令环境保持服务存活时，`keepalive.sh` 调用既有生命周期入口，并以前台阻塞进程承载服务：

```bash
# 仅在用户明确允许本次保活操作后执行，并保持命令前台运行
bash scripts/dev/keepalive.sh restart -all
# 退出会停止当前工作区整套开发服务，单模块托管也相同
```

使用边界：

- AI 执行 `keepalive.sh` 前必须告知原因、涉及模块与清理范围，并取得用户对本次操作的明确许可；一般开发、测试、验收或提交授权不包含这项许可。
- `keepalive.sh start/restart` 的启动范围沿用相应入口的参数语义；退出清理调用不带模块参数的 `stop.sh`，停止当前工作区整套开发服务，即使只托管单模块也相同。不得用局部保活接管用户外部终端已经运行的整套环境。
- 整个托管周期持续持有工作区生命周期锁，退出清理后才释放；其他生命周期操作必须拒绝干预。
- 按 `Ctrl+C` 或收到 TERM 会触发上述全量清理；不要把命令退出后的不可用当作服务故障。
- 不并发执行外部终端与托管环境中的生命周期操作。一次性测试、构建无需为此重启服务；Common 变更确需运行验收时，由用户重启全部模块。

参数、构建与就绪规则见[开发服务生命周期规范](../../spec/addp开发服务生命周期与构建身份规范.md)。

## restart.sh 误报端口被浏览器占用

如果启动提示 Chrome 等浏览器占用了服务端口，但没有对应监听者，检查端口探测是否误把出站连接当成监听。`lsof -ti :<port>` 还会匹配 ESTABLISHED 等连接；浏览器的临时出站端口可能恰好等于服务端口。

先根据标准启动输出和 `.dev-state/ports.env` 核实实际端口，再只读检查监听者：

```bash
# 先将 ADDP_CHECK_PORT 设置为已核实的实际端口
lsof -nP -iTCP:"${ADDP_CHECK_PORT:?请先设置已核实的实际端口}" -sTCP:LISTEN
```

当前启动脚本按 LISTEN 状态判断占用。若问题重现，应核对实际执行的脚本及监听进程归属，不终止仅有出站连接的浏览器。

## restart.sh 报告 ADDP 旧进程未清理

若 `.dev-bins/addp-*` 占用端口、PID 文件不存在，杀死后又出现新 PID，检查是否曾通过 `launchctl submit` 注册 `com.addp.codex.*` KeepAlive 作业。只杀进程会触发 launchd 重新拉起。

当前 `stop.sh` 在 macOS 上先枚举该类作业，只卸载命令包含当前仓库绝对路径的条目，再执行常规清理。卸载失败会返回非零并中断重启。沿标准脚本日志核对作业与工作区归属，不按相似名称卸载其他工作区作业；需要停止或重启时由用户操作。

## 停止或重启提示“无法发布计划停用，尚未停止服务”

标准开发／生产停止入口必须先成功写入服务组的计划停用声明，再卸载托管作业、停止进程或执行Compose down。发布失败时会立即退出；重启也随之中断，保留仍在运行的服务，不把计划停机误报成失联。

按根 `.env` 与标准入口输出核对 `ADDP_DEPLOYMENT_DISCOVERY_DIR`（未配置时为工作区 `.dev-state/deployment-discovery`），检查Python 3、目录与文件归属／私有权限、磁盘空间及受管声明是否完好。修复发布来源后由用户重试原标准命令；不删除清单绕过错误、不放宽文件权限，也不提供跳过发布的停止参数。该声明只记录运行意图，不证明停止或启动已成功，不等于告警已恢复。

## 部署发现停止提示“进程尚未退出，不删除运行记录”

先保留退出码和脱敏诊断，不删除 `observer.json`、扩大停止等待或直接重试来掩盖问题。`term_caught=true`只说明内核记录了信号处理器，不证明处理器已执行；结合当前归属、进程状态、等待点和直接子进程数判断，不能凭单一字段认定Docker或Python卡死。

已确认一种失效路径：旧处理器异步抛`SystemExit`，若SIGTERM命中`Popen.__del__`，退出异常会成为被忽略异常，随后观察器可能继续30秒休眠。受控单信号用例在Linux/Python 3.12复现了`owned/S/hrtimer_nanosleep`、零子进程和实际接收但被忽略的异常；原CI未保留处理器栈，不能断言每次同类错误都发生于该析构点。Python的[信号异常说明](https://docs.python.org/3.12/library/signal.html#note-on-signal-handlers-and-exceptions)及[析构器异常规则](https://docs.python.org/3.12/reference/datamodel.html#object.__del__)解释了该机制。

当前处理器只锁存请求并唤醒空闲等待，退出由主循环及读取检查点执行；Docker读取取消时回收自有子进程。控制器仍只向已核验的自有观察器发一次SIGTERM，未确认退出仍报错并保留记录。标准验证为 `make test-deployment-discovery` 与 `make test-infra-runtime-log-lifecycle`，包括析构边界、读取中止、子进程回收、锁竞争和不误停外来进程。只有标准启动创建的新观察器采用新实现；个人服务的停止或重新启动仍由用户操作。若修复后仍复发，保全新诊断继续定位，不把本机制当作所有失败的兜底解释。

## GeoPython Workflow 依赖安装失败

若安装日志停在 NumPy 等包的源码构建并报错，先区分 Python 解释器不匹配、没有适用 wheel、原生库不匹配和下载失败，不直接升级全部依赖或清空正在使用的环境。

当前原生开发入口见 [geopython-workflow.sh](../../../scripts/dev/geopython-workflow.sh)：

- 使用 Python 3.12 的独立 `venv`，禁止继承系统 site-packages。
- 依赖范围以 [requirements.txt](../../../engines/geopython-workflow/requirements.txt) 为准，由共享依赖同步流程安装，不另维护版本矩阵或一组临时升级命令。
- GDAL 与 PyArrow 同进程报 `Attempted to register factory for scheme 'file'` 时，检查 Arrow 原生来源。Homebrew GDAL 已链接 Arrow 时，普通 PyArrow wheel 可能携带另一套库；改导入顺序或使用内存缓冲区写入不能代替修复。标准准备按系统 Arrow 版本源码构建 PyArrow，禁止打包第二套 Arrow；临时独立构建 venv 声明 Cython 3.1.8、CMake 4.4.0 和 NumPy 2.2.6，并将库真实路径和 SHA256 纳入缓存指纹。准入验证两种导入顺序、实际加载库来源和含空值大整数/布尔值的 Parquet 文件重读；失败不会留下成功准备记录。临时编译发生在既有依赖安装锁内，不修改 Homebrew，也不为 Manager Raster Mosaic 添加 PyArrow。
- GDAL Python binding 必须匹配已安装的原生库；准备流程还核验 PGeo / OpenFileGDB、GTiff / COG 驱动与 PROJ 坐标系解析。
- 旧环境不符合要求时，先确认对应 Runtime 已停止，再按标准入口重新准备；不在运行中就地改依赖。

需要重启时由用户在自己的终端执行：

```bash
./scripts/dev/restart.sh -geopython-workflow
```

依赖声明和运行环境约束见[技术栈规约](../../spec/addp技术栈规约.md)。准备成功和服务就绪仍须分别核对，不能只以 pip 安装成功认定 Runtime 可用。

## Document 镜像下载 Debian 依赖失败，阻断全量启动

`restart.sh -all` 在 Runtime 并行启动阶段报 `apt-get` 退出码 `100` 时，先查看 Docker 构建日志：

```bash
docker buildx history logs "${ADDP_BUILD_RECORD:?请先设置构建记录ID}"
```

若 `deb.debian.org` 的 HTTP 索引或依赖包请求出现 `502 Bad Gateway`、`Connection failed`，失败发生在构建网络链路，尚未进入 Document 服务启动。索引下载失败后还可能出现 `repository ... is not signed`，不能据此关闭签名校验。

本地曾在 Docker Desktop 配置 HTTP/HTTPS 代理的环境中复现：相同基础镜像的构建过程下载同一 Noto 字体包时，HTTP 超时，官方 HTTPS 请求成功。Document Dockerfile 因此统一使用 Debian 官方 HTTPS 源，保留原有 `Signed-By` 和 TLS 校验；索引更新与依赖安装均设置最多 5 次重试，索引更新使用 `APT::Update::Error-Mode=any`，避免部分索引失败却继续安装。重试耗尽仍必须阻止启动，不能跳过 Document 或忽略构建失败。

修复后通过标准入口验证：

```bash
make test-document-workflow
make build-images IMAGE_BUILD_ARGS="--verify --services document-workflow-engine"
bash scripts/dev/restart.sh -all
```

上述重启由用户在自己的终端执行；托管命令环境的保活必须先取得本次明确许可，见[保活边界](#codex-等托管命令环境中-restartsh-退出后服务立刻不可用)。若 HTTPS 仍失败，继续检查 Docker Desktop 的实际代理、代理监听端口和构建容器到软件源的连通性，不应关闭证书或包签名校验。

## Python 镜像首次构建耗时过长

### 现象

通过标准入口构建 Python 产品镜像时，日志长时间停留在 Debian 软件包或 Python wheel 下载、安装阶段，即使该引擎的业务源码没有变化。先按层日志区分下载等待、依赖编译和构建失败；原生开发服务的依赖准备按对应 Runtime README 排查。

### 根因

镜像是否重建由输入和构建脚本决定，不由“本次是否修改了该引擎业务代码”单独决定。`common-python` 负载、Python requirements、JupyterLab 扩展源码或 Dockerfile 变化可能影响相关构建层；镜像重新构建不表示所有依赖层都重新下载，整镜像复用与层缓存统一见[缓存边界](../../../scripts/build/README.md#镜像复用与缓存边界)。

Jupyter 镜像还需要构建 `@addp/notebook-bridge` 扩展。Node/npm 只属于扩展编译阶段，不应安装到 Python 运行镜像；如果把 Debian `nodejs npm` 放在最终 Python 阶段，会额外引入庞大的系统依赖树。

### 正确排查

在仓库根目录用标准单服务入口复现 Jupyter 产品镜像构建，避免复制 Dockerfile 和构建上下文命令：

```bash
make build-images IMAGE_BUILD_ARGS="--services jupyter-engine --verify --jobs 1"
```

该入口执行真实构建并将产品镜像保存在本机；`--verify` 的 Registry 访问、基础镜像准备及操作范围见[构建模式说明](../../../scripts/build/README.md#docker-daemon-配置边界)，不是只读诊断。单并发日志、退出结果与摘要的范围见[构建结果](../../../scripts/build/README.md#构建结果与摘要)。

- 看到大量 `apt` 包下载：检查 Dockerfile 的系统依赖和 `--no-install-recommends`。
- 看到 Python wheel 下载：确认 requirements 或基础镜像层是否变化，并区分网络慢与构建错误。
- 看到 Node/npm 下载：应只发生在 Jupyter 扩展构建阶段；最终 Python 镜像不应包含 `node` 或 `npm`。
- 缓存是否可用以实际层日志为准；强制进入构建不等于禁用层缓存，不以暂时没有输出判定卡死或构建成功。

Jupyter 的 Node 构建阶段与 Python 运行阶段已在 [Dockerfile](../../../engines/jupyter/Dockerfile) 中分离。需要检查最终镜像时，先从本次构建输出核对完整 Registry、标签和平台，再将 `ADDP_JUPYTER_IMAGE` 设置为该镜像的完整引用或本机镜像 ID，执行：

```bash
docker image inspect "${ADDP_JUPYTER_IMAGE:?请先设置本次构建的完整镜像引用或镜像ID}"
docker run --rm --pull=never --network none --entrypoint jupyter "$ADDP_JUPYTER_IMAGE" \
  labextension list
docker run --rm --pull=never --network none --entrypoint sh "$ADDP_JUPYTER_IMAGE" \
  -lc '! command -v node && ! command -v npm'
```

须在 `labextension list` 输出中核对 `@addp/notebook-bridge` 的登记及状态，不能仅凭命令零退出认定扩展已安装。以上检查启动短期容器，只核对指定镜像的扩展登记及 PATH 中 Node/npm 的可执行发现；不挂载业务数据、不运行 Runtime 默认入口，镜像缺失时禁止自动拉取。未发现命令不证明镜像中不存在任何 Node 相关文件。

检查成功也不证明交互会话认证、HTTP/WebSocket 代理、插入单元或真实 Notebook 执行通过；对应能力与确定性测试边界见 [Jupyter README](../../../engines/jupyter/README.md)，各层结果按[测试与验收规范](../../spec/addp测试与验收规范.md)分别记录。


## Docker Desktop 共享目录原子替换后容器读不到文件

现象：宿主将完整的新文件通过同目录 `rename`／`os.replace` 发布后，宿主可读新内容，容器却暂时打不开同名文件，或仍看到旧inode／大小。新文件名可能可读；枚举目录后原路径也可能恢复。本机 Apple Virtualization framework＋VirtioFS 已通过同进程、等时和正反目录枚举对照复现；该结果指向共享视图更新，不能直接认定某个内核缺陷、稳定TTL或确定的已修复版本。

先运行无数据库的标准最小复现：

```bash
make test-monitor-metrics MONITOR_METRICS_TEST_ARGS=--case=directory-publication
```

该入口仅在一次性容器中运行既有固定镜像的Bash，不启动数据库、不执行SQL，不读取ADDP配置、账号或HBA，不开放端口／网络；文件、容器及临时目录退出清理。JSON中的后续枚举结果只用于诊断，发布后首次未读到新内容仍返回失败，不能凭最终可读判环境通过。需要外部复现时，将 `scripts/test/directory-publication-probe.py` 单文件复制到系统临时目录；它只依赖Python标准库及Docker。仓库验证继续使用上述唯一标准入口。

处理建议按证据推进：

1. 保留产品的原子发布、版本校验和精确读回；不可见时继续拒绝启用采集来源，避免以成功写宿主文件冒充配置生效。禁止用固定sleep、循环重试、先ls再读或原地覆盖HBA掩盖一致性缺口。
2. 先保存当前版本、VMM、共享实现及最小复现JSON。Docker官方[发行说明](https://docs.docker.com/desktop/release-notes/)曾记录VirtioFS缓存／宿主变更通知相关修订，但不能据此承诺本例升级即修复。优先在独立机器或明确授权的维护窗口验证候选受支持版本，先保持原VMM／VirtioFS不变；只有同一最小复现及原目录HBA、真实重载、来源恢复门禁都通过，才认定本例闭合。重启本身即使暂时缓解，也不等于根因修复。
3. 如果候选版本仍复现，再单独比较共享实现。当前官方[设置说明](https://docs.docker.com/desktop/settings-and-maintenance/settings/#general)在Apple Virtualization framework下列出VirtioFS／gRPC FUSE；切换会涉及VM和容器，必须先确定维护窗口，不能边运行共享业务边试。每轮只改一个因素，不同时换VMM；osxfs已从后续版本移除，不建议作为长期路线。gRPC FUSE也须用相同门禁验证，不默认更可靠。
4. 如果开发环境长期无法提供可靠的跨宿主原子更新，应先讨论将动态认证文件放入Linux VM内的受管卷，由部署侧受限发布器在同一文件系统内更新、业务数据库只读挂载的方案。它改变发布职责、目录所有权、版本／锁和回滚边界，需要单独设计确认；不能直接改成双轨认证路线，也不能把Docker socket交给Monitor或业务数据库。原生Linux部署的验证结果仍须单独获得，不能从Desktop失败外推。

查看共享设置、复现与保存报告不需要修改设置或重启。版本升级、共享切换和实际服务应用均由用户另行确认并通过标准生命周期入口操作；诊断不得自动上传日志或向上游发消息。原始证据见[Monitor来源与引擎指标历史证据](../../spec/testing/evidence/Monitor采集来源与引擎指标历史证据.md)。
