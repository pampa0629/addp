# 数据库迁移故障排查

[返回常见故障排查](../addp常见故障排查.md)

## System Backend 因数据库迁移版本超前而启动超时

### 现象

`scripts/dev/start.sh` 在“等待 System Backend 就绪”阶段超时，`logs/system-backend.log` 中出现：

```text
IAM 数据库迁移失败: database migration version <database_version> is newer than embedded version <code_version>
```

或出现已执行迁移的 checksum 不匹配错误。

### 根因

System 会在启动时校验数据库迁移版本和已执行 SQL 的 checksum。某个迁移一旦已被任何持久化环境执行，其版本号、文件名和内容就是不可变历史。合并、删除、重命名或改写已执行迁移，都会使代码与数据库的历史不一致，System 因此拒绝启动。

### 正确处理

1. 先核对 `system.schema_migrations` 和 `system.schema_migration_checksums`，再与 `system/backend/internal/migration/sql/` 中的迁移目录比较。
2. 如果仓库错误改写了已执行迁移，应恢复当时已执行的原始文件；新变更只能使用新的递增版本前向迁移。
3. 如果数据库确实来自更新版本的代码，应切换到包含该迁移的同版或更新代码。
4. 只有明确不需要数据的一次性开发或测试库，才可在确认数据丢失范围后重建。

不要手工修改 `schema_migrations` 或 `schema_migration_checksums` 来绕过校验；这会伪造迁移历史，并可能让结构或授权数据与声称版本不一致。

2026-10-14 的 `000207_source_dataitem_boundary_bindings` 曾因执行后改写路径约束而阻止 System 启动。正确原文 SHA-256 为 `558122ca553b3ffdd60264186af4c531359a21bb219ce4eb233691ecd94abbb7`；恢复原文后，约束修正由 `000208_source_dataitem_boundary_identity` 前向执行。该故障发生在启动迁移校验，不是 Go 编译失败。回归固定原文摘要，并从真实 207 状态升级、重复运行至 208；使用标准 System IAM PostgreSQL 门禁的 `--package migration --test source-grant-relations` 分组验证。不要将一次性测试库从零迁移成功等同于已有开发库可重启。

### 75 号迁移的定向恢复

`000075_iam_execution_audience_model_materialization` 是已发布的特殊缺陷：存在历史 `audience=addp-quality` 时，其规范化 `UPDATE` 会被 execution authorization 不可变触发器拒绝，从而留下 `75/dirty`。该迁移已在其他环境登记 checksum，不得改写原文件。

只有在日志确认为该错误后，才可停止 System 及其他应用进程，加载当前开发环境配置并执行：

```bash
make build-iam-migration-repair
dist/release-$(go env GOOS)-$(go env GOARCH)/addp-iam-migration-repair --migration 75 --apply
```

该命令不是通用 force：它只接受 `schema_migrations=(75, dirty)`、checksum 恰好到 74、旧约束与不可变触发器均存在、且至少一条 `addp-quality` 的精确状态。它在单一串行化事务中暂停该触发器、规范化历史 audience、立即恢复触发器，并将已回滚的迁移状态恢复为 `74/clean`；不修改 checksum、不跳过 75。命令成功后正常重启 System，由唯一 Migration Runner 重新执行 75 及后续迁移。

### 113 号迁移的定向恢复

Security 模块首次开发迁移如果在事务内失败，PostgreSQL 会完整回滚业务事实，但 Migration Runner 保留 `113/dirty` 阻止自动重试。只有在已确认 Security Permission、runtime Role、Service Principal、OAuth Client 和 Role Assignment 均未落地，且 `standard.classification.*` 仍保持迁移前状态时，才可执行：

```bash
make build-iam-migration-repair
dist/release-$(go env GOOS)-$(go env GOARCH)/addp-iam-migration-repair --migration 113 --apply
```

该命令只把精确的 `(113, dirty)` 恢复为 `(112, clean)`，不删除 System 事实、不修改 checksum，也不会标记 113 已成功。任一前置事实不匹配都会拒绝。成功后正常重启 System，由 Migration Runner 重新执行修正后的 113 及后续迁移。

### 130 号迁移的定向恢复

Security 原值访问申请权限迁移如果因非法权限状态等原因在事务内失败，PostgreSQL 会完整回滚权限事实，但 Migration Runner 保留 `130/dirty` 阻止自动重试。只有在已确认三个 `security.protection_access_request.*` Permission 均未落地、旧 `security.protection_exemption.create|update` 仍为 active，且两个内置治理角色的四条旧绑定仍完整时，才可执行：

```bash
make build-iam-migration-repair
dist/release-$(go env GOOS)-$(go env GOARCH)/addp-iam-migration-repair --migration 130 --apply
```

该命令只把精确的 `(130, dirty)` 恢复为 `(129, clean)`，不修改任何 Permission 或 RolePermission，不修改 checksum，也不会标记 130 已成功。任一前置事实不匹配都会拒绝。成功后正常重启 System，由 Migration Runner 重新执行修正后的 130。

### 240 号进程内核身份声明迁移的定向恢复

本批迁移若因 JSONB 子对象减键表达式的运算符优先级失败，日志为 `operator is not unique: unknown - unknown`，旧声明约束会随事务完整回滚，但 `240/dirty` 阻止重试。须先确认 checksum 完整到 239、没有 240 记录、旧声明 CHECK 与不可变触发器仍完整，才可使用限定恢复；不得手改迁移表、修改 checksum 或将 240 标为成功。

停止应用后，在用户终端加载当前环境，使用 `bash scripts/infra/status.sh` 核实实际端口并显式设置 `POSTGRES_PORT`，执行标准构建及恢复入口：

```bash
make build-iam-migration-repair
dist/release-$(go env GOOS)-$(go env GOARCH)/addp-iam-migration-repair --migration 240 --apply
./scripts/dev/restart.sh -all
```

240 案例在串行化事务中锁定迁移状态、checksum 和实例表，逐条校验 1—239 的文件名／SHA-256，以及原 CHECK 和触发器函数；任一不符即拒绝。唯一修改是失败标记 `240/dirty → 239/clean`，不改声明行、约束、角色、权限或 checksum。重启后由唯一 Runner 正常执行已修正的 240。该命令需用户对本次开发库恢复明确授权或自行执行；构建、隔离测试及只读现场核对不等于已执行恢复。
