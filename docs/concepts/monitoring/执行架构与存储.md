[返回监控与执行体系](../addp监控与执行体系图.md)

## 监控体系概述

租户任务执行诊断采用“Owner 产生事实并裁决读取 → Common 统一执行身份与安全契约 → Monitor 聚合展示”的职责链。Monitor 的详情只展示安全概览、已有步骤、错误与有界诊断摘要；专业结果返回所属模块。平台服务进程日志由 System 管理，操作审计使用独立事实源。过程事件与分期沿[租户执行诊断规范](../../spec/tasks/执行监控.md#租户执行诊断)，保留与释放沿[概览保留契约](../../spec/tasks/执行监控.md#概览保留与清理契约)；30 天事件清理、180 天概览只读评估及周期验收的区别统一见[模块留存导航](../../../monitor/docs/Monitor模块架构说明.md#执行留存与验收)，本页不重复维护状态。

`common.task_executions` 统一保存 execution，不保存任务定义或调度定义；模块及类型按 Owner 当前声明解释。跨模块读取仍须当前 Tenant、入口 Permission 和 Owner 逐请求裁决，见[读取时序](执行诊断与租户告警.md#跨模块监控集成)。

### task_executions 表结构

完整字段语义、状态推进和租约约束以[执行记录规范](../../spec/tasks/执行记录与租约.md#执行记录规范)及[共享模型](../../../common/execution/task_execution.go)为准，索引以模型与标准存储入口为准。本页按职责定位，不重复维护字段类型或模块／状态枚举。

| 范围 | 概念与读取边界 |
| --- | --- |
| 执行身份与归属 | `id` 是存储行身份，`execution_id` 是跨模块执行 UUID；Tenant、Owner 模块与稳定类型沿正式记录契约，不因统一存储扩大授权。 |
| 任务、来源与执行关联 | `source_task_id` 是可空的任务定义软引用；触发类型、父子关系和重试来源分别沿[来源与状态契约](../../spec/tasks/执行记录与租约.md#记录关联与状态推进)及[Owner 类型声明](执行状态与任务类型.md#各模块任务类型)，不能混作同一身份。 |
| attempt、租约与时间 | 领取次数、最大尝试及当前 attempt 的开始时间沿[租约契约](../../spec/tasks/执行记录与租约.md#bounded-execution-领取租约和恢复契约)；`lease_owner` 仅用于观测，不能替代写入凭据。 |
| 持久事实与公开诊断 | `execution_config`、`metadata`、`error_details` 是持久字段，不等于公开 DTO。成功 execution 的 `error_details` 仍须为空；通用详情只消费[安全诊断投影](../../spec/tasks/执行监控.md#租户执行诊断)，不公开原始配置、metadata、错误正文或租约 Token。 |

Manager／Develop 代发的一次性导出仍由 Transfer 独占 execution。导出 owner 从认证用户上下文保存发起用户，并在派发前将导出会话绑定到唯一 Transfer execution UUID 和不可变请求摘要。Transfer 根据认证服务 Client 推导 owner，用自己的租户服务令牌向 owner 的 `POST /runtime/export-sessions/{id}/execution-source` 核验会话、租户、UUID、摘要与待执行状态，然后只将核验得到的用户写入 `triggered_by`。Monitor 继续通过统一 OwnAdHoc 读取范围允许发起用户查看临时执行；来源事实不授予执行或数据权限，不复制用户 Token、Membership 或 Execution Authorization。没有导出会话来源的机器执行不声明人类发起用户，旧执行也不推测或回填归属。

### 执行运行时角色矩阵

bounded execution worker 与 Backend 内嵌 execution supervisor 共用[PostgreSQL claim／execution lease 契约](../../spec/tasks/执行记录与租约.md#bounded-execution-领取租约和恢复契约)。领取、heartbeat、进度和终态的 fencing 统一由该契约维护；已接入的过程事件，其事务与预算沿[执行监控规范](../../spec/tasks/执行监控.md#租户执行诊断)。是否可重放仍由 Owner／Provider 的提交协议决定；continuous runtime、delivery 和维护循环分别使用自身机制。

| 角色与 Owner 正文 | 进程边界 | 职责及独有的租约／恢复约束 |
| --- | --- | --- |
| [Quality execution worker](../../../quality/CLAUDE.md#唯一领域主线) | 独立 `quality-worker` | 执行质量检查、评分和 Issue reconcile；有界槽位，结果、问题及终态在有效 lease 下原子提交，恢复按 Owner 契约。 |
| [Meta scan worker](../../../meta/CLAUDE.md#meta-扫描分层约定) | 独立 `meta-worker` | 执行扫描与当前投影更新；有界槽位，领取和终态沿公共协议，是否恢复取决于扫描提交协议。 |
| [Security discovery worker](../../../security/CLAUDE.md#运行角色) | 独立 `security-worker` | 仅扫描显式纳管目标、生成 Finding，不承担全量 Meta 遍历；有界槽位，恢复受最大 attempt 约束，旧或过期 lease 不得写回。 |
| [Transfer bounded worker](../../../transfer/CLAUDE.md#执行规则) | 独立 `transfer-bounded-worker` | 有界槽位，承担 snapshot、watermark 和 bounded replay，不承载 continuous session；仅明确可安全重放的模式允许自动恢复。 |
| [Develop execution supervisor](../../../develop/CLAUDE.md#统一执行架构) | 内嵌 `develop-backend` | Workbench、任务定义和 TaskProvider 的 `query/workflow/script` 统一领取，按类型独立容量；失联收敛失败、不自动重放，不证明远端程序已停止，详见[监督与授权规范](../../spec/tasks/模块任务契约.md#develop-执行监督与授权)。 |
| [Manager bounded execution supervisor](../../../manager/CLAUDE.md#领域事实与任务边界) | 内嵌 `manager-backend` | 执行 API 只入队；派生任务与 ad-hoc 执行同一监督器，结果、摘要与终态受 lease 约束。失联／缺失租约收敛失败、不自动重放，详见[Manager 监督规范](../../spec/tasks/模块任务契约.md#manager-执行监督与-pptx-预览生成)。 |
| [Model materialization runner](../../../model/CLAUDE.md#模块概述) | 内嵌 `model-backend` | 按冻结逻辑表版本创建／校验正式表，不执行数据加工；使用 bounded claim，过期 attempt 收敛失败，不自动重放。定义与目标归属见[物化约束](../../../model/docs/model概念与数据约束规范.md#目标物理表建表)。 |
| [Orchestrator execution supervisor](../../../orchestrator/CLAUDE.md#开发规则) | 内嵌 `orchestrator-backend` | 按冻结计划有界推进步骤、独立续租，等待不占整条流程执行槽；保留步骤、事件和子执行引用。失联／不确定派发不重放，不代替下游执行或取消，详见[编排可靠性](../../spec/tasks/编排与调度.md#orchestrator-执行可靠性)。 |
| [Transfer continuous worker](../../../transfer/CLAUDE.md#执行规则) | 独立 `transfer-continuous-worker` | 消费 `transfer.runtime_leases` 与 Kafka／CDC position；capacity、heartbeat、fencing 沿[continuous 契约](../../spec/tasks/Transfer同步执行.md#transfer-continuous-sync-v1-契约)，恢复创建新的 recovery execution。`sync_states` 是业务 committed position，不替代执行历史。 |
| [Webhook／Email dispatcher](../../../monitor/CLAUDE.md#核心边界) | 内嵌 `monitor-backend` | 从独立 delivery outbox 领取并在事务外至少一次投递，使用投递租约、指数退避与 dead 终态；不创建或改写业务 execution，详见[租户通知契约](执行诊断与租户告警.md#租户外部通知契约)。 |

**角色边界**:

- execution worker 与 execution supervisor 负责“执行什么以及如何完成”，差别仅在独立进程或 Backend 内嵌的部署边界；owner scheduler 只负责“何时创建 execution”；dispatcher 只负责“如何投递通知”。
- Orchestrator scheduler、Manager embedding scheduler、Meta lineage collector 和各模块 cleanup 属于 scheduler/maintenance loop，不自动等同 execution worker。
- Quality、Meta、Security、Transfer bounded 只使用 PostgreSQL claim 单一路线；Backend 只创建 execution，不执行 bounded 业务逻辑，也不保留 Asynq 或本地 channel fallback。
- 领取与写入所有权统一沿上述公共租约契约；Worker 名称、消息 active 状态或容量不能替代当前 attempt／token 校验，也不能把租约过期直接解释为可安全重放。
- `common.background_runtime_heartbeats` 只回答后台运行组件是否仍在上报，以及其容量与当前占用；Monitor 必须把它与 execution lease、continuous runtime lease 和 delivery lease 分开展示。实例心跳过期不能直接改写任何业务 execution。
- Monitor 对外只投影 `lease_owner`、`lease_expires_at`、attempt、排队/执行时长和恢复原因等安全观测字段，绝不返回 `lease_token` 或 continuous fencing token。

矩阵说明职责与协议，不证明当前实例在线或相应角色已完成验收。执行诊断、Owner 撤权及 Worker 恢复分别见[执行监控证据](../../spec/testing/evidence/Monitor执行监控与留存历史证据.md)；多 Worker、主机绑定与容器证明见[实例证据](../../spec/testing/evidence/Monitor实例与服务发现历史证据.md)。各 Owner 的业务及专业结果仍须对应独立证据，T1／T2／受控页面 T3 不代替真实链路 T4 或 T5，固定版本、失败、清理和未覆盖项按原记录认定。
