## 响应格式规范

### 灵活响应策略（推荐）

ADDP 根据接口语义选择响应格式，简单场景直接返回数据，确需分页或附加信息时再包装；内部与外部 HTTP API 均遵循此原则。

#### 核心原则

1. HTTP 状态码表达请求结果，不在 body 中重复状态码或强制套用 `{code, message, data}`。
2. 查询、创建和更新直接返回数据或资源对象；管理分页、业务 cursor、OGC 和 TaskProvider 各按自己的契约返回，见[分页规范](分页与查询.md)。
3. 错误返回清晰的 `error`，需要机器判别时再按下文提供稳定 `error_code`。

#### 设计决策说明

响应包装由调用方需要的业务信息决定，不为格式统一增加冗余层。具体 DTO、状态码和字段在 Swagger 中明确声明；客户端读取 HTTP 状态码与已声明字段，不猜测另一种包装格式。共享处理能力见[文档与实施规范](文档与实施.md#共享响应处理)。

### 成功响应示例

表格结果的 JSON 单元格按字段类型表达精确数值：`bigint` 一律使用十进制字符串，包括位于 JavaScript 安全整数范围内的小整数；`decimal` 使用精确十进制字符串。列元数据仍声明原本的 `bigint` / `decimal` 类型，null 保持 null，其他整数类型继续为 JSON number。不按数值大小切换两种表示，不经浮点转换。此规则只作用于 HTTP 结果边界，Provider 和 Transfer 内部继续使用原生精确值；字段保护先于序列化，遮盖后的文本保持文本。当前 Manager 表格预览与 Develop 共享 SQL Runtime 已复用同一编码实现；Develop 的真实输出字段事实贯穿默认结果观察 DTO 及当前授权读回。不同接口的代码、集成测试和真实 Hosted 验收分别记录，不能将尚未验证的接口计为已完成。

常见成功状态与 body 形式统一见[响应格式对照](#b-响应格式对照)。可变持久化主资源的 `version`、聚合版本与写入结果遵循[并发更新规范](资源版本与并发更新.md)，不能用简化响应示意省略端点必需的版本字段。

删除成功使用 HTTP 200 时，可返回简洁的 `message` 或空响应；也可使用不带 body 的 HTTP 204，但仍不推荐，避免前端额外处理。

### 错误响应格式

错误使用 `{error}`，由 HTTP 状态码表达错误类别，例如 HTTP 400：

```json
{
  "error": "参数错误：用户名不能为空"
}
```

`error` 应是可展示、已按请求语言翻译的文案；运行时翻译要求见[国际化规范](../addp国际化开发规范.md#handler-使用)。开发或测试环境可按需附加安全的 `detail`，生产环境应隐藏该字段，不暴露凭据、原始 SQL 或其他敏感底层详情。

供 SDK、Runtime 或多跳代理消费且调用方必须区分会话失效、权限拒绝、资源不存在、不支持和瞬时上游故障的接口，应在 `error` 之外返回稳定的 `error_code`。`error_code` 使用小写下划线命名，不国际化，不包含动态文本，也不重复 HTTP 状态码；SDK 只能按 HTTP 状态码与 `error_code` 分支，不能解析本地化 `error` 文案。


例如 HTTP 504：

```json
{
  "error": "读取引擎目录超时",
  "error_code": "engine_catalog_timeout",
  "error_type": "transient"
}
```

`error_type` 和 `retry_after` 遵循[Agent 与 SDK 的 HTTP 重试提示](AI-Agent友好性.md#agent-与-sdk-错误响应增加-error_type)；同一个 `error_code` 的重试类别必须稳定。简单 CRUD 接口不需要为包装一致性强行增加 `error_code`。

## HTTP 状态码规范

### 状态码语义

成功响应的 200、201、204 与 body 对应关系统一见[响应格式对照](#b-响应格式对照)。错误状态按以下语义选择：

| 状态码 | 含义 | 适用场景 |
| --- | --- | --- |
| 400 | Bad Request | JSON 格式错误、缺少必填参数、参数类型或取值不合法 |
| 401 | Unauthorized | 登录失败、Token 无效或过期等认证失败 |
| 403 | Forbidden | 已认证但权限不足 |
| 404 | Not Found | 请求资源不存在 |
| 409 | Conflict | 资源重复、资源版本等冲突；版本冲突按并发规范返回稳定错误码 |
| 422 | Unprocessable Entity | 业务校验失败，可选；端点也可统一使用 400 |
| 500 | Internal Server Error | 服务内部错误，如数据库连接失败 |
| 502 | Bad Gateway | 网关错误或下游调用失败 |
| 503 | Service Unavailable | 服务不可用 |
| 504 | Gateway Timeout | 上游调用超时，例如读取引擎目录超时 |

### 常见场景的状态码选择

用户名密码错误和 Token 失效使用 401；请求格式、必填项或类型错误使用 400；已认证但无权访问使用 403。业务校验采用 400 还是 422 由端点统一声明，不随调用方或文案变化。资源版本冲突使用 409，响应及客户端处理见[并发更新规范](资源版本与并发更新.md#冲突响应与前端体验)。

### 错误处理原则

1. 共享 HTTP 状态映射、错误写回和国际化能力，不在各 Handler 重复实现，也不把共享 helper 当作自动翻译或脱敏保证。
2. `error` 清晰说明安全可展示的原因；原始内部错误不能未经处理就返回给用户，生产响应隐藏 `detail`。
3. 客户端按 HTTP 状态码与稳定 `error_code` 分支，不解析本地化文案；`error_type` 与 `retry_after` 只在契约明确的场景使用。
4. 健康检查、协议专用错误等遵循自身明确的契约，例如[健康端点](健康与平台控制面.md#进程存活与模块就绪端点)不套用通用 `{error}` 响应。

## B. 响应格式对照

下表为成功响应的结构示意，实际字段、精确数值和版本要求仍由对应端点契约约束；错误体与错误状态码分别见[错误响应格式](#错误响应格式)和[状态码语义](#状态码语义)。

| 场景 | HTTP 状态 | body 形式 |
| --- | --- | --- |
| 单个资源查询 | 200 | 直接返回资源对象 |
| 无分页列表 | 200 | 直接返回数组 |
| 管理分页列表 | 200 | `{data, total, page, page_size, total_pages}`；其他列表契约见分页规范 |
| 创建成功 | 201 | 返回新创建的资源对象 |
| 更新成功 | 200 | 返回更新后的资源对象；聚合子资源写入按并发规范至少返回新聚合版本 |
| 删除成功 | 200 | 简洁的 `{message}` 或空响应 |
| 删除成功且无 body | 204 | 空响应，不推荐 |
