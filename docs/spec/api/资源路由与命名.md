## RESTful 设计规范

### 资源命名规则

资源使用复数名词，URL 的资源段采用小写与 snake_case，例如 `/api/v1/system/platform/users`、`/api/v1/system/platform/identity_changes`。普通 CRUD 通过 HTTP method 表达操作，不再使用 `getUsers`、`create_user` 等动词资源名；动作接口按[特殊操作规则](#特殊操作的-restful-化)处理。

### HTTP 方法语义

查询、创建、完整更新、部分更新和删除的方法、路径与常用状态码统一见[HTTP 方法对照](#a-http-方法对照)。错误与删除响应的具体结构见[响应规范](响应与错误.md)，资源写入的版本、冲突及原子性见[并发更新规范](资源版本与并发更新.md)。

### 标准资源操作

集合路径为 `/api/v1/{module}/resources`，单资源路径追加 `/:id`。列表是否支持分页、过滤、排序或搜索必须由端点明确声明，参数和响应遵循[分页与查询规范](分页与查询.md)，不能由通用示例推定所有端点支持同一能力。

### 子资源设计

```
GET    /api/v1/{module}/{parents}/:parent_id/{children}           # 获取父资源下的子资源
POST   /api/v1/{module}/{parents}/:parent_id/{children}           # 创建父子关系或子资源
DELETE /api/v1/{module}/{parents}/:parent_id/{children}/:child_id # 删除父子关系或子资源
```

**规则：**
- 子资源深度建议不超过 2 层
- 超过 2 层时考虑使用查询参数：`GET /api/v1/{module}/{children}?parent_id=1`

### 特殊操作的 RESTful 化

动作名称以可读性和实际业务语义为准。测试、扫描、执行、部署、认证及批量命令可以保留动词，不为命名形式额外制造没有独立生命周期的资源。

以下是现行路由示例，不构成其他 owner 的固定接口清单：

| 场景 | 路由 |
| --- | --- |
| 测试已登记引擎 | `POST /api/v1/system/engines/:id/test` |
| 登记前测试连接 | `POST /api/v1/system/engines/test-connection` |
| 触发扫描任务 | `POST /api/v1/meta/scan/tasks/:task_id/trigger` |
| 用户登录、会话刷新 | `POST /api/v1/system/login`、`POST /api/v1/system/refresh` |

修改密码、导出等操作同样按 owner 的真实资源、效果和协议选择 method 与路径，不为“RESTful 化”改造已明确的业务语义。认证端点及多阶段登录流程见[登录规范](../addp登录认证的统一要求.md)；批量写入的成员版本和整批回滚要求见[并发更新规范](资源版本与并发更新.md)。

## API 版本控制

### 版本策略

ADDP 控制面 API 统一使用 `/api/v1/` 前缀，例如 `/api/v1/system/platform/users`。API 的 `v1` 标识接口契约版本，与产品发布号 `v0.x` 无关，不随每次产品迭代变更；资源并发字段 `version` 也不是 URL 版本。

### 版本演进规则

- 当前积极开发阶段采用 clean break，不保留旧路径、旧字段、旧 query 或双轨兼容分支；旧 `/api/{module}` 路径不再使用。
- 契约变化先同步规范、Swagger 和调用方，再一次性切换到新的唯一主路径。
- 未来若已对外发布稳定 API，且确实需要长期并行两个契约，必须先形成明确设计文档，再决定引入 `/api/v2/`；这不是当前默认路线。

### 路由前缀要求

| 位置 | 控制面要求 |
| --- | --- |
| Go / Gin | 模块路由组使用 `/api/v1/{module}`，与 Swagger `@BasePath` 一致 |
| Python / FastAPI | 模块 Router 使用相同版本和模块前缀，OpenAPI 描述反映真实路由 |
| Gateway | 按 `/api/v1/:module` 及其子路径代理到目标 owner，不另建旧前缀兼容路由 |
| 前端 | 最终请求使用 `/api/v1/{module}/...`；共享客户端前缀与调用参数各自只拼接一次 |

正式 Query、OGC、瓦片等数据面协议入口按[Gateway 路由平面](../../../gateway/docs/gateway架构说明.md#2-路由平面)维护，不套用控制面前缀。接口注解、生成与覆盖要求见[Swagger 指南](../addp-Swagger集成指南.md#路由注解一致性)。

## 命名规范

### 字段命名

API JSON 字段统一使用 snake_case。Go 结构体字段可使用语言自身的导出命名，通过 JSON tag 明确输出字段名；不因前端变量采用 camelCase 就改变传输契约。

```json
{
  "user_id": 1,
  "created_at": "2024-01-01T12:00:00Z",
  "is_active": true,
  "engine_type": "postgresql",
  "status": "active"
}
```

#### 命名规范的权衡说明

snake_case 用于保持 API 字段、数据库命名和跨模块调用契约一致。语言内部变量遵循各自代码规范；需要映射时在已有 API 适配边界处理，不由服务端同时输出两套字段，也不要求所有前端调用重复转换命名。

### 时间格式

时间统一使用带时区的 ISO 8601 字符串，UTC 使用 `Z`，也可以明确时区偏移，例如 `2024-01-01T12:00:00+08:00`。Go `time.Time` 字段使用 snake_case JSON tag；序列化示例不替代接口对时间语义的声明。

### 布尔值

JSON 布尔值使用 `true` / `false`，不使用 `1` / `0` 或字符串 `"true"` / `"false"`。

### 枚举值

使用具有稳定含义的字符串常量，例如 `engine_type: "postgresql"`、`status: "active"`，不使用数字枚举。允许值由对应资源契约和 Swagger 明确声明。

## A. HTTP 方法对照

| 操作 | 方法 | 路径 | 幂等语义 | 常用成功码 |
| --- | --- | --- | --- | --- |
| 列表 / 详情查询 | GET | `/api/v1/{module}/resources`、`/api/v1/{module}/resources/:id` | 幂等 | 200 |
| 创建 | POST | `/api/v1/{module}/resources` | 不默认保证幂等 | 201 |
| 完整更新 | PUT | `/api/v1/{module}/resources/:id` | 幂等 | 200 |
| 部分更新 | PATCH | `/api/v1/{module}/resources/:id` | 不默认保证幂等，取决于操作定义 | 200 |
| 删除 | DELETE | `/api/v1/{module}/resources/:id` | 幂等 | 200 |

PATCH 不因方法名而天然幂等，见 [RFC 5789 第 2 节](https://www.rfc-editor.org/rfc/rfc5789.html#section-2)。方法幂等不等于每次请求返回相同状态码，也不授权客户端自动重试版本冲突；ADDP 写入仍按[并发更新规范](资源版本与并发更新.md)校验请求版本。

## C. 命名规范对照

| 类型 | 规范 | 示例 |
| --- | --- | --- |
| URL 资源段 | 小写与 snake_case | `/api/v1/system/platform/identity_changes` |
| JSON 字段 | snake_case | `user_id`、`created_at` |
| 时间 | 带时区的 ISO 8601 字符串 | `2024-01-01T12:00:00Z` |
| 布尔值 | JSON 布尔值 | `is_active: true` |
| 枚举值 | 稳定字符串 | `engine_type: "postgresql"` |
