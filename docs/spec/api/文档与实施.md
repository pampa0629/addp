# API 文档与实施规范

[返回 API 设计规范](../addp-API设计规范.md)

定义 OpenAPI 注解、HTTP 文档入口、新接口实施与共享响应处理；生成、覆盖检查和版本依赖由[Swagger 集成指南](../addp-Swagger集成指南.md)统一维护。

阅读导航：[文档规范](#文档规范)、[实施指南](#实施指南)、[内部 HTTP API](#内部-http-api)。

## 文档规范

**统一使用 Swagger/OpenAPI 自动生成 API 文档，废弃手写的 api-manifest.json。**

### Go 端（swaggo/swag）

在模块启动入口声明总注解，在真实 Handler 上维护端点注解，并在 Router 注册 Swagger 文档路由。`@BasePath`、相对 `@Router`、method 与真实路由保持一致；注解中的 DTO 必须匹配实际请求与响应。

依赖版本、接入步骤、双语注解及 IAM 扩展统一见[Swagger 集成指南](../addp-Swagger集成指南.md)。生成与覆盖检查使用其中的[标准入口](../addp-Swagger集成指南.md#强制同步要求)，Go 三份生成产物随契约变更提交，不复制另一套 Handler 或生成模板。

### Python 端（FastAPI 原生）

FastAPI 从真实路由、请求/响应模型和端点描述生成 OpenAPI；按实际认证方式维护 `openapi_extra` 中的 IAM 声明。使用所属模块唯一的 venv，通过相同标准入口导出并提交 `backend/openapi.json`，再与实时 `app.openapi()` 比较。

环境准备、导出边界与检查失败语义见[FastAPI 与统一检查要求](../addp-Swagger集成指南.md#强制同步要求)，不能用手写接口清单替代。

### Swagger UI 访问入口

日常通过 Console 的 API 文档中心选择模块；其[入口配置](../../../console/frontend/src/views/ApiDocs.vue)区分开发代理与生产路由。地址使用本次部署或启动解析结果，不在本规范维护固定宿主端口表。

| 模块文档 | 模块自身路由 |
| --- | --- |
| Go Swagger UI | `/swagger/index.html` |
| FastAPI Swagger UI / ReDoc | `/docs` / `/redoc` |
| FastAPI 文档源 | `/openapi.json` |

上述为模块内路径，统一入口下的代理前缀由 Console 与部署路由配置决定；端口规则见[端口规范](../addp端口分配.md)。UI 可访问不代表生成产物、路由覆盖或接口行为已验收。

### 接口文档要求

每个应纳入文档的接口必须说明：

1. Summary、Description 与领域 Tags；描述实际行为、参数来源及必要的调用限制。
2. path / query / body 参数的类型、必填性、枚举和校验约束。
3. 成功与失败的状态码、真实响应结构及安全示例；分页、资源版本和并发冲突按对应契约声明。
4. 实际认证方案、`x-addp-auth-mode` 与适用 Permission；不能将所有接口都描述为 User Bearer，也不能用注解代替服务端授权。
5. 面向人的注解使用 `中文 | English`；运行时错误翻译仍由[国际化规范](../addp国际化开发规范.md)约束。

应覆盖与可排除的路由以[文档边界](../addp-Swagger集成指南.md#文档边界)为准，接口授权声明见[IAM 扩展](../addp-Swagger集成指南.md#iam-授权扩展)。

## 实施指南

### 新接口开发

1. 先确认模块 owner、资源与权限边界，再按[资源路由与命名](资源路由与命名.md)采用 `/api/v1/` 版本前缀、snake_case 与清晰的资源/动作命名。
2. 按[响应与错误](响应与错误.md)选择直接响应或必要包装，不为格式一致强加 `code/message/data`。
3. 列表分页与业务 cursor 按[分页规范](分页与查询.md)区分；写入版本和冲突语义按[并发更新规范](资源版本与并发更新.md)声明。
4. 同步真实路由、Handler、DTO、调用方、Swagger/OpenAPI 及生成产物，执行标准覆盖与授权门禁。

模块接入步骤见[新模块开发指南](../addp新模块开发指南.md)，测试范围与门禁选择见[测试与验收规范](../addp测试与验收规范.md)。

### 后端实现分层与共享能力

各服务的后端实现应遵循 `Handler -> Service -> Repository -> Database` 的分层思路：

1. **Handler** 负责 HTTP 请求解析、参数绑定、认证上下文读取、响应写回和 Swagger 注解维护。
2. **Service** 负责业务规则、事务边界、跨 Repository 编排和领域错误返回。
3. **Repository** 负责数据访问封装，避免在 Handler 或 Service 中散落 SQL/GORM 细节。
4. **Database** 表示具体数据库、外部存储或引擎调用边界。

后端通用能力应优先沉淀到 `common/`，不要在各模块重复实现。适合放入 `common/` 的能力包括统一响应、错误映射、认证上下文、分页模型、通用客户端、存储路径与指纹等跨模块复用逻辑。

### 共享响应处理

复用 `common/api` 的既有能力，不在各模块复制实现。以下是现有函数的职责，响应与分页契约仍以对应规范为准：

| 能力 | 作用与边界 |
| --- | --- |
| `RespondSuccess` / `RespondCreated` | 直接写回数据，分别使用 HTTP 200 / 201 |
| `RespondError` | 使用指定状态码写回 `{error}`；传入的文案应已完成必要翻译与安全处理 |
| `NoStore` | 写出响应前设置 `Cache-Control: no-store`，防止当前响应被 HTTP 缓存保存；不写出状态或正文，不替代当前授权复核 |
| `RespondOrError` | 成功时返回 200，失败时映射状态码并写回 `err.Error()`；不自动翻译、脱敏或补充稳定错误码 |
| `RespondPaginated` | 写回 `data/total/page/page_size/total_pages`；适用于该管理分页契约，不用于业务 cursor、OGC 或 TaskProvider 专用响应 |
| `MapErrorToHTTPStatus` | 识别共享业务错误，映射为 400 / 401 / 403 / 404 / 409；未知错误映射为 500 |

响应实现见[共享 Handler 工具](../../../common/api/handler_helpers.go)，错误映射见[共享业务错误](../../../common/api/errors.go)。Repository 边界通过[WrapDBError](../../../common/repository/errors.go)把 GORM 的未找到、重复键和外键冲突转换为共享业务错误；Handler 不再重复匹配这些 GORM 错误。

Service 返回领域结果与错误，Handler 或统一响应层按请求语言翻译用户可见文案，并处理不宜暴露的底层详情。不能把状态码映射当作安全展示错误的保证，具体遵循[国际化错误边界](../addp国际化开发规范.md#service-层错误)及[错误响应规范](响应与错误.md#错误响应格式)。需要机器判别的接口按规范提供稳定 `error_code`，不能让客户端解析本地化文案。

## 内部 HTTP API

内部 HTTP API 同样遵循资源命名、响应、错误与文档要求；服务身份和执行授权遵循[认证授权规范](认证授权.md)。是否纳入 OpenAPI 按显式文档边界判定，不能仅因路径含 `internal` 就省略应有检查。
