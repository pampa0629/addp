# 内置格式：表格与矢量交换

[返回内置格式规范](../addp内置数据类型与文件格式规范.md) · [通用写入与消费约束](../addp内置数据类型与文件格式规范.md#通用写入与消费约束)

CSV / TSV、JSON、GeoJSON、Shapefile 与矢量交换容器的识别、行值和读取边界。各格式的数据类型以识别表或对应章节为准。

阅读导航：[CSV / TSV](#csv--tsv)、[JSON](#json)、[GeoJSON](#geojson)、[Shapefile](#shapefile)、[KML / GML / TopoJSON](#kml--gml--topojson)。

## CSV / TSV

### 识别与组织

| 维度 | CSV | TSV |
|---|---|---|
| `layout` | `single` | `single` |
| `data_type` | `table` | `table` |
| `format` | `csv` | `tsv` |
| 主资源 | `meta_item.full_name` 指向文件资源 | `meta_item.full_name` 指向文件资源 |

CSV / TSV 是单资源表格文件。默认按首条记录为表头读取；调用方显式声明既有 `ParseOptions.HasHeader=false` 时，parser 按首条记录的列序号生成 `Column1`、`Column2` 等稳定列名，首条记录仍属于数据并参与类型推断、行数统计、样本、连续读取及稀疏行索引。该声明不根据内容猜测。字段类型来自采样推断。

UTF-8 输入允许文件起点的 BOM；BOM 不属于首列字段名，也不影响带引号表头的解析。稀疏行索引中的 `header_bytes` 和 anchor 偏移仍按源文件字节计算，包含被跳过的 BOM；从 anchor 定位的数据行不得再次执行文件头 BOM 处理。带 BOM 的 UTF-16LE / UTF-16BE 在同一 CSV / TSV 读取入口解码，实际编码写入 `format_info.<format>.encoding`（`utf-16le` / `utf-16be`）；已知端序可通过同名 `ParseOptions.Encoding` 明确指定。UTF-16 解码后的偏移不是源文件字节偏移，因此不生成 `access_index`，分页从文件起点按逻辑数据行读取。Manager 消费已识别编码，不提示这类文件刷新创建索引。Transfer 的 CSV / TSV encoded source 在本次任务未显式声明 `source.options.encoding` 时，复用 Meta `format_info.<format>.encoding`，再交给同一共享 table reader；任务的显式读取参数仍按现有执行契约生效，不回写 Meta，不根据 MIME 或字段内容猜测编码。无 BOM 且未声明编码时按 UTF-8 读取，不自动猜测 GBK。已有明确编码声明的输入可通过 `ParseOptions.Encoding=gbk` 解码 CSV / TSV，实际编码写入 `format_info.<format>.encoding=gbk`；编码名称忽略首尾空格和大小写，文件起点的 Unicode BOM 优先于参数声明。GBK 同样不生成 `access_index`，分页从起点按逻辑数据行读取。UTF-32 与 GB18030 不支持。写出仍为 UTF-8，不据此声明 UTF-16 或 GBK 写出能力。

CSV / TSV 的编码和表头选择通过已知 item 的同一深度刷新提交，`encoding` 与可选布尔 `has_header` 可以单独或共同声明；显式 `false` 不得按“未提交”处理。编码、实际表头模式与新表结构、索引在成功后同时生效；失败保留上次成功摘要。后续单项刷新和目录重扫复用已扫描的编码及 `type_info.table.native.has_header`，没有已知表头模式时默认 `true`。Manager 在同一原刷新入口提交读取设置，预览只消费 Meta 事实，不提供独立临时表头模式；具体执行与请求约束见元数据扫描机制规范。

### attributes 写入

| 分区 | 写入内容 |
|---|---|
| `item` | `layout`、`data_type`、`format` |
| `type_info.table` | `fields`、`row_count`、`primary_key`、`native.delimiter`、`native.has_header`、`native.quote_char`、`native.escape_char` |
| `format_info.csv` / `format_info.tsv` | `encoding`、`line_ending`、文件级解析摘要等格式私有信息 |
| `capabilities.statistics` | 字段结构推断所用的采样规模、是否采样、平均记录大小等 Meta 扫描过程事实；不得写入空值率等数据剖析结果 |

### 格式约束

- 不得把 CSV / TSV 放入 `document`，除非明确按文档而不是表格消费。
- 分隔符和表头判断以 `type_info.table.native` 为准；编码以 `format_info.csv|tsv` 为准，不在消费者侧二次猜测。

## JSON

### 识别与组织

| 场景 | `layout` | `data_type` | `format` |
|---|---|---|---|
| records array | `single` | `table` | `json` |
| JSON Lines | `single` | `table` | `json` |
| 任意对象、配置文件、嵌套文档 | `single` | `document` 或 `container` | `json` |

`.json` 后缀不能直接等同于表格。必须验证内容结构，并按平台消费方式确定 `data_type`。如果 `.json` 文件内容前缀能严格证明其为 GeoJSON `FeatureCollection`，Meta deep scan 应升格识别为 `format=geojson`，由 GeoJSON 小节处理。

### attributes 写入

| 分区 | 写入内容 |
|---|---|
| `item` | `layout`、`data_type`、`format` |
| `type_info.table` | records / JSON Lines 的字段、行数 |
| `type_info.document` | 文档型 JSON 的标题、语言、编码、页数、字数、大小等通用文档结构信息 |
| `type_info.container` | 容器型 JSON 的内部对象摘要、默认入口、子对象数量 |
| `format_info.json` | `structure`、编码、对象层级摘要等格式私有信息 |
| `capabilities.spatial` | 仅记录值中严格解析出 WKB / EWKB 等几何字段时写入空间能力 |
| `capabilities.statistics` | 是否采样、采样规模、动态结构推断方式等 Meta 扫描过程事实 |

### 格式约束

- 不得只按扩展名把 JSON 判为 `table` 或 `spatial`。
- `.json` 文件中出现严格 GeoJSON `FeatureCollection` 结构时，应识别为 `format=geojson`，不得继续写入 `format_info.json`。
- 不得把 JSON 私有结构字段写入 `capabilities.spatial`。
- 记录集合中已识别的几何字段若在任一记录中缺失或为 `null`，对应 `type_info.table.fields` 字段必须声明 `nullable=true`；连续读取合并字段结构时不得收紧该声明。仅含空值的同名属性不另生成重复几何字段。
- records JSON 的几何样本当前输出 GeoJSON 对象；尚未声明空间行编码能力，不承诺 EWKB 连续输出或空间目标写入。普通非空间 records JSON 的批量传输不受此限制。
- 插件推导出来的记录数、几何类型、bbox 等归一事实不得写入 `format_info.json`；记录数进入 `type_info.table.row_count`，空间范围进入 `capabilities.spatial.extent`。

## GeoJSON

### 识别与组织

| 维度 | 取值 |
|---|---|
| `layout` | `single` |
| `data_type` | `table` |
| `format` | `geojson` |
| 主资源 | `meta_item.full_name` 指向 GeoJSON 文件资源 |

GeoJSON 是单资源空间矢量表格式。`.geojson`、`application/geo+json`、`application/vnd.geo+json` 是强识别事实；`.json` 只是普通 JSON 后缀，只有内容前缀严格匹配 GeoJSON `FeatureCollection` 结构时，才识别为 `format=geojson`。Meta deep scan 对 `.json` 表格候选必须读取内容前缀后调用统一格式探测，不得只按后缀固定为 JSON provider。

当前内置 GeoJSON table 只支持 `FeatureCollection.features` 记录集合。单个 `Feature`、`GeometryCollection` 或任意带 `geometry` 字段的 JSON 对象是否进入 GeoJSON table 主路径，需要先补规范再实现。

### attributes 写入

| 分区 | 写入内容 |
|---|---|
| `item` | `layout`、`data_type`、`format` |
| `type_info.table` | `properties` 字段、平台统一几何字段、`row_count` |
| `format_info.geojson` | `structure`、原文显式 `bbox` / `crs`、`coordinate_range_out_of_wgs84`、属性摘要等 GeoJSON 格式私有事实 |
| `capabilities.spatial` | 实际记录中发现 geometry 时写入几何字段、SRID / CRS、extent 等空间能力 |
| `capabilities.statistics` | 是否采样、采样规模、动态结构推断方式等 Meta 扫描过程事实 |

### 格式约束

- GeoJSON 类似 Shapefile，默认是 `data_type=table`；但 spatial 仍是横切能力，只能来自解析结果。
- 不得因为 `format=geojson` 直接写入 `capabilities.spatial`。FeatureCollection 没有有效 geometry 时，不写空间能力。
- 按 [RFC 7946 §3.2](https://www.rfc-editor.org/rfc/rfc7946#section-3.2)，`geometry=null` 的 Feature 仍保留为记录，计入行数；与实际几何混合时，统一几何字段声明 `nullable=true`。扫描与连续分批读取遵循同一空值规则，不因批次顺序改变最终声明；全部为空时不虚构几何字段或空间能力。
- 不得把 GeoJSON 私有结构字段写入 `format_info.json`；格式私有事实进入 `format_info.geojson`。
- 记录数进入 `type_info.table.row_count`，空间范围进入 `capabilities.spatial.extent`。只有 GeoJSON 原文显式声明的 `bbox` 可作为格式事实保留在 `format_info.geojson.bbox`。
- 没有显式可解析 CRS / SRID 时，只有实际或显式 bbox 落在经纬度范围 `x=[-180,180]`、`y=[-90,90]` 内，才可按 GeoJSON 默认语义写入 `EPSG:4326`。bbox 明显越界时不得默认写入 4326，应保留 `capabilities.spatial.extent`，省略 SRID / CRS，并在 `format_info.geojson.coordinate_range_out_of_wgs84=true` 标记。
- `format_info.geojson.structure` 应来自 GeoJSON provider 的格式私有事实；`.json` 后缀被升格为 GeoJSON 时，也只能写入 `format_info.geojson`，不得同时写入 `format_info.json`。

### 空间行值编码

| 方向 | 支持的 geometry encoding | 默认 encoding | native encoding | 说明 |
|---|---|---|---|---|
| read | `geojson`、`ewkb` | `geojson` | `geojson` | `geojson` 用于预览、调试和格式本地场景；`ewkb` 用于 Transfer 跨格式 / 跨 engine 链路。 |
| write | `geojson`、`ewkb` | `geojson` | `geojson` | writer 可把 `ewkb` 转为 GeoJSON geometry object，但不执行 CRS 转换。 |

GeoJSON 标准导出前，Transfer 必须保证传入 writer 的几何坐标已经满足 4326 / WGS84 经纬度约束。GeoJSON source 如果没有可识别 CRS 且坐标范围明显越界，不得被当作 4326 source 直接导出；需要用户补充 source CRS 后再由 planner 选择源端 transform 或 `vector_reproject`。

## Shapefile

### 识别与组织

| 维度 | 取值 |
|---|---|
| `layout` | `multi` |
| `data_type` | `table` |
| `format` | `shapefile` |
| 主资源 | `.shp`，即 `meta_item.full_name` |
| 必需 refs | `.shp`、`.shx`、`.dbf` |
| 可选 refs | `.prj`、`.cpg`、`.sbn`、`.sbx` |

Shapefile 是空间矢量表，不是单个 `.shp` 文件。ref 匹配规则是同目录或同 prefix 下相同 basename；不得跨目录递归匹配；不独占目录。

### attributes 写入

| 分区 | 写入内容 |
|---|---|
| `item` | `layout=multi`、`data_type=table`、`format=shapefile`、`refs`、`file_count` |
| `type_info.table` | `.dbf` 非空间字段、平台统一几何字段、`row_count`、`primary_key`、`native.shape_type`、`native.dbf_version`、`native.encoding` |
| `format_info.shapefile` | `base_name`、`ref_extensions`、`has_prj`、`has_cpg`、文件组件级摘要 |
| `capabilities.spatial` | `geometry_columns`、`primary_geometry_column`、`srid`、`crs_ref`、`crs_definitions`、`extent`、`has_spatial_index` |

字段规则：

- `.dbf` 提供非空间字段。
- DBF `N` 字段的小数位数大于 0 时，沿用 `decimal` 字段声明，样本、分页与连续读取直接返回去除字段填充空白后的十进制文本，不经过浮点转换；precision/scale 保留原有字段事实，不补零或舍入源值。全空字段仍为 `null`。`N` 整数字段与 `F` 浮点字段保持各自既有映射，不能将 Decimal 降为浮点以绕过精确 JSON 编码。
- `.shp` 提供平台统一几何字段。
- 平台统一几何字段的字段类型为 `geometry`。默认 sample 行值为 WKT 字符串；连续读取可通过 `ParseOptions.GeometryEncoding` 请求 `wkb` 或 `ewkb`，行值为 `[]byte`。
- `ewkb` 可以携带 SRID；Shapefile 的 SRID / CRS 事实仍以 `.prj` 解析结果和 `capabilities.spatial` / `TableInfo.SpatialInfo` 为准。
- Shapefile 原生 shape type 是格式事实，写入 `format_info.shapefile.shape_type` 或 `type_info.table.native.shape_type`；平台标准几何拓扑必须写入 `capabilities.spatial.geometry_columns[].geometry_type`。
- Shapefile `Point` family 归一为 `Point`，`MultiPoint` family 归一为 `MultiPoint`，`PolyLine` family 归一为 `MultiLineString`，`Polygon` family 归一为 `MultiPolygon`。`NullShape` 不生成空间字段；其他未纳入标准主路径的 shape type 必须返回明确 unsupported 或落为 `Geometry`，不得伪造成具体拓扑。
- 字段类型映射为 ADDP 通用字段类型。原始 DBF 类型属于 Shapefile format plugin 内部事实；如需给 Manager 展示，只能写入只读 attributes，不能进入 Transfer / engine / format writer 的执行决策。
- 记录数来自真实 Shapefile 记录数，不写固定占位值。
- 写出 `.prj` 时，format writer 只接受 `WriteOptions.ExtraParams["crs_definition"]` 作为 CRS 定义文本；该字段表达定义内容，不得写成 `format` 或 PostGIS `spatial_ref_sys`。

### 空间行值编码

| 方向 | 支持的 geometry encoding | 默认 encoding | native encoding | 说明 |
|---|---|---|---|---|
| read | `shapefile_shape`、`wkt`、`wkb`、`ewkb` | `wkt` | `shapefile_shape` | 默认 `wkt` 服务 sample / preview / 调试；Transfer 跨格式链路优先请求 `ewkb`。 |
| write | `shapefile_shape`、`wkt`、`wkb`、`ewkb` | `wkt` | `shapefile_shape` | `shapefile_shape` 只用于 Shapefile 同构且无需 CRS 转换的 native passthrough。 |

Shapefile 的 `.shp` 原生 shape record 对用户有格式语义价值，因此可以作为 `shapefile_shape` 暴露；但非 Shapefile writer 不应消费该编码。跨 format、写入 native table 或需要 CRS 转换时，Transfer 应切换到 portable encoding，第一阶段优先 `ewkb`。

### 标准写入示例

```json
{
  "schema_version": 1,
  "storage": {
    "physical_path": "/shp/",
    "total_size": 3069403
  },
  "item": {
    "layout": "multi",
    "data_type": "table",
    "format": "shapefile",
    "refs": [
      {"path": "/shp/farmland.shp", "role": "main", "required": true, "primary": true, "extension": ".shp"},
      {"path": "/shp/farmland.shx", "role": "index", "required": true, "extension": ".shx"},
      {"path": "/shp/farmland.dbf", "role": "attributes", "required": true, "extension": ".dbf"},
      {"path": "/shp/farmland.prj", "role": "projection", "extension": ".prj"}
    ],
    "file_count": 4
  },
  "type_info": {
    "table": {
      "fields": [
        {
          "name": "geometry",
          "type": "geometry",
          "native_type": "Polygon",
          "nullable": false
        }
      ],
      "row_count": 1234,
      "primary_key": []
    }
  },
  "format_info": {
    "shapefile": {
      "base_name": "farmland",
      "ref_extensions": ["dbf", "prj", "shp", "shx"],
      "has_prj": true,
      "has_cpg": false,
      "shape_type": "Polygon"
    }
  },
  "capabilities": {
    "spatial": {
      "geometry_columns": [
        {
          "name": "geometry",
          "geometry_type": "MultiPolygon",

        }

      "primary_geometry_column": "geometry",
      "extent": null,
      "has_spatial_index": false
    }
  }

```

### ref 读取

Manager 内容读取必须使用 `meta_item.full_name` 作为主内容路径，并使用 `attributes.item.refs` 读取相关内容。Transfer 写出 Shapefile 时必须明确 ref 提交边界，不能只写 `.shp`。

### 格式约束

- 不得把 `.shp` 单独作为完整 Shapefile item。
- 不得把 Shapefile 作为 whole scope detector。
- 不得把 `base_name`、`ref_extensions`、`has_prj`、`has_cpg` 写入 attributes 顶层或长期写入 `format_info.unqualified`。

## KML / GML / TopoJSON

三种矢量交换文件统一为 `layout=single + data_type=container`，格式分别为 `kml`、`gml`、`topojson`。KML 的 Folder、GML 的 feature type 和 TopoJSON 的命名 object 通过受控 GDAL Runtime 转为轻量图层 children；选择图层后复用 scope table Provider、EWKB 和 Manager 的地图＋属性表，不合并各图层字段，不新增空间数据类型。KML 不再按文本文档读取。

- `.kml`、`.gml`、`.topojson` 声明专用扩展名；通用 `.json` 只有内容前缀确认为根 `Topology` 且具有 `objects` 对象时精化为 TopoJSON 候选，完整 `objects` / `arcs` 结构由 Runtime 校验，不占用 JSON 的扩展名或 MIME。通用 XML 仍归 XML。
- 唯一原生读取路线为已有 GeoPython Runtime 的 GDAL `KML`、`GML`、`TopoJSON` 驱动，Meta / Manager 不嵌入 GDAL；首期只读，不提供这三种格式的写出 Provider。
- GDAL vector dataset 算子在 Runtime 内通过同一 Python 环境的新进程执行原生操作，沿用矢量瓦片的原生隔离方式，避免在 Gunicorn fork 后的 HTTP 线程中首次初始化 PROJ／系统 SQLite。访问计划只经标准输入传递，不进入进程参数；不新增服务、平台接口或失败后的回退路线。真实 Gunicorn HTTP 回归须覆盖三种交换格式的 inspect／read_open／read_batch／read_close 及 Worker 身份保持，不能仅以进程内函数测试替代。
- 容器 attributes 只保存图层名称、数量和轻量定位；字段、几何、范围与 CRS 在选择 child 后取得。源文件只读，解析副文件位于可回收的隔离临时目录。
- KML 的简单要素按格式规定使用 EPSG:4326。GML 保留 GDAL 从 `srsName` 识别的 CRS 和标准轴序；未知 CRS 不默认米或经纬度。TopoJSON 标准允许投影坐标，不能把 GDAL 的默认 WGS84 当作源声明；没有明确 CRS 时只展示属性和源几何，地图按既有 `unknown_crs` 契约暂停定位。
- 用户可以在共享表格地图预览中临时声明 EPSG:4326 或 EPSG:3857，默认不选，明确选择后才绘图；只用于解释当前响应的源坐标，不覆盖已识别 CRS 或后端已转换的几何。声明不进入 URL、持久视图、Meta 或源文件，同一资源／图层翻页时保留，切换资源、图层、组件或重新打开时清除。清除选择后恢复未知 CRS 的地图暂停状态；显示坐标仍走唯一的共享 CRS registry，不另建 TopoJSON 地图转换路线。
- 首期支持简单要素与图层读取，不承诺 KML 样式、嵌套 Folder 层次和描述语义的完整还原；Model、Overlay、NetworkLink、gx Track 不作为普通矢量静默处理。TopoJSON 首期只支持二维位置，非法弧索引、额外维度、null object 和嵌套 GeometryCollection 明确拒绝，避免驱动静默丢失；GML 接受普通 schemaLocation 注记，但明确禁用 schema 下载／导入，在隔离副本中按要素推断字段；仅接受标准 EPSG / OGC CRS84 标识，不读取自定义 CRS 外部链接；不支持 XLink、越界 schema 路径或应用 schema 的完整业务语义；XML DTD 和实体声明拒绝读取，不回源下载链接内容。

临时 CRS 交互沿用 `make test-common-frontend` 的共享策略 T1 和 `make test-manager-frontend` 的页面组合 T3，覆盖中英文选择、实际绘图、容器／单文件翻页、清除与重新打开、资源／图层切换，以及声明不进入 API 或持久视图。既有共享表格消费者由 `make test-service-frontend` 验证；已有自动发现和 Platform CI 登记覆盖新增测试，不增加专用服务或 workflow。确定性页面夹具不替代真实扫描、Runtime 读取和 Hosted T4。

三格式的 S3 兼容跨模块验收使用隔离 Business MinIO，不将该结果登记为外部云 S3 认证；扩展既有 `manager-internal-artifact-lineage` Hosted suite，不新增自定义服务、用户权限或部署路线。隔离环境须先启动已有 Security 模块，并由标准身份夹具的 `--wait-protection-owners manager` 观察 Manager 持久保护投影完成初始化，再执行场景；预检同时核对 Security 的健康和源码身份，不写入或跳过保护检查。初始化或启动失败须终止场景并沿用所有权清理。Business 夹具拥有三份固定字节／哈希的双图层源文件；既有普通 User 通过真实 Meta 扫描、GeoPython 原生 Runtime、Manager 和 Console 核对图层、中文属性、源几何／轴序、地图实际要素、未知 CRS 默认暂停及临时选择的清除／图层切换／重开行为、普通刷新和源下载哈希。Owner/v11 与 browser/v13 报告必须包含三份独立来源和逐层证明，旧报告或缺项拒绝；只扩展格式消费断言，不改变血缘产品实现。清理沿用现有领域清理和 disposable Business／Infra 零残留核验。`make test-manager-online-runner` 覆盖确定性夹具、报告拒绝边界、登记和浏览器语法；正式 T4 结果须在对应源码的 Hosted 运行结束后单独登记，不能由 runner 通过推定。

最小验证使用 `make test-geopython-workflow`（真实原生驱动、多图层、坐标／轴序、TopoJSON 量化与反向弧、未知 CRS 和拒绝边界）、`make test-go`（格式注册、Meta 和 Manager 路由／读取协议），沿用 Platform CI 已登记的 Go 和 GeoPython 门禁。上述门禁不等同于跨模块 T4 或真实页面验收。升级后，已有 KML 文档项应通过父目录的强制扫描重新发现为容器；known-item refresh 只重建既有身份，不能代替格式分类重识别。
