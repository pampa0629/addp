# ADDP 模块服务运行日志规范

本文定义已实现的模块进程运行日志、可信来源目录、授权查询及日志链路观测契约。概念与职责见[监控与执行体系图](../concepts/monitoring/平台日志与运行观测.md#模块服务运行日志与链路告警)，尚未闭合的验收见[运行日志专题](../next/ADDP模块服务运行日志设计.md)。通用平台告警由 Monitor 统一管理，本规范只说明日志来源及其通知语义，不另建日志专用告警管理路线。

## 一、范围与职责

运行日志用于排查模块进程的启动输出、运行消息和异常堆栈，覆盖 Backend、Worker、Scheduler、Gateway 的 Go/Python 实例。操作审计、任务执行记录及过程事件使用各自事实源；引擎运行时、数据库等 Infra 与浏览器日志不冒充模块实例日志。

唯一正文路径为“受控实例文件 → Alloy → Loki → System 授权查询”。本地与 Docker 使用相同输出契约，System 不远程读取业务节点文件，浏览器不访问 Loki。

| 所有者 | 职责 |
| --- | --- |
| Common / common-python | 消费统一进程身份并输出结构化日志；Common 提供共享输出接收器 |
| 标准启动脚本与容器入口 | 创建启动身份、连接输出接收器，保持业务 PID、UID、信号和退出语义 |
| Infra | 节点文件、Alloy、Loki、独立 MinIO bucket、轮转清理、可信来源发现与链路观测 |
| System | 实例登记及可信来源目录、Platform 正文授权与查询、日志抽屉和链路诊断 |
| Monitor | 日志观测裁决、统一平台告警事实、通知目标、投递及重投；不读取节点日志文件 |

日志故障不进入业务 Ready、租约或 UP/DOWN 判定。应用停止或重启不停止日志 Infra，不删除日志卷。首版是允许明确缺口的故障排查日志，不保证零丢失归档、完整自动重放或高可用。

## 二、进程身份与输出

### 2.1 启动与实例关联

标准入口在执行每个业务进程前生成一次 `ADDP_PROCESS_INSTANCE_ID`，登记、健康响应、应用日志和接收器消费同一身份。同进程重新登记保留身份，真正重启产生新身份；独立 Worker、Scheduler 和 Python 多进程分别启动及登记，不能共享实例 ID。任务执行租约 owner 不替代进程身份。

启动器建立输出通道后直接 exec 业务进程，保留业务 PID 与信号语义；独立接收器不登记成业务实例。业务启动时间来自实际进程，不采用接收器或脚本时间。接收器可捕获登记前输出，但建立通道前的可执行文件查找、管道错误可能只有启动终端记录。

root 业务容器中的独立接收器按受控源目录所有者降权，业务进程身份保持原样。宿主启动的观察器、清理器和接收器使用同一调用用户 UID/GID；目录 `0700`、文件 `0600`，不得以放宽权限或递归 chown 修复既有个人目录。部署细节见[生命周期规范](addp开发服务生命周期与构建身份规范.md#进程身份与运行日志)和[配置规范](configuration/Monitor与运行观测.md#模块服务运行日志配置)。

### 2.2 唯一输出与有界接收

Go/Python 应用统一向 stdout 输出 JSON，取消应用文件 Handler 与固定模块文件双写。stderr 和第三方文本由同一接收器捕获，按 `logs/runtime/<module>/<instance_id>/<segment>.jsonl` 保存；这是受控部署路径，不能由 API 指定。段只追加，轮转创建新文件，禁止截断旧段或 copytruncate；无实例身份的历史文件不推断归属。

接收器使用 16 MiB 实际消息缓冲预算、最多 8192 条队列；每批最多 64 条或 64 KiB，安静时每 50 ms 刷新，写入仍在节点锁下核对磁盘额度。写入失败或额度耗尽时继续消费输出并计数，不能无限缓存或持续阻塞业务。源目录损坏时，失败计数也可能无法写入该目录。

共享 Go 日志初始化忽略 SIGPIPE，接收器退出不能直接终止业务，写入仍可能返回 EPIPE。EOF 后释放段文件；容器结束或 SIGKILL 前尚未刷新的输出不保证保留。

Python HTTPX 的成功例行请求仅在 DEBUG 输出：范围限于 POST 模块心跳、POST OAuth 令牌获取和 GET 健康检查的 2xx。失败、重定向、异常、业务请求及注册/恢复/注销事件保留。Uvicorn 的 error/access logger 传播到共享 JSON Handler，不另装文本 Handler；应用显式日志级别继续控制阈值，异常堆栈保持一个事件。System GORM 默认 Warn，保留错误与慢查询，避免成功认证 SQL 淹没队列。降噪在生产端执行，不回写历史或在查询层隐藏记录。

### 2.3 字段与索引

| 字段 | 语义 |
| --- | --- |
| `module_name`、`role`、部署标识 | 启动配置中的低基数索引标签 |
| `instance_id`、`node_name` | 可信启动身份及部署节点，存为结构化元数据 |
| `entry_id` | 实例 ID 与实例内递增接收序号组合，用于精确排序、重复采集识别 |
| `timestamp`、`event_time` | 前者为接收器 UTC 检索时间，后者保留应用原始时间 |
| `level` | 结构化声明的规范级别；普通文本为 unknown，不从正文前缀猜测 |
| `channel` | stdout 或 stderr；stderr 不自动等于 ERROR |
| `message`、`stack` | 文本正文及堆栈，不执行 HTML |
| `request_id` | 可选关联字段，不作为索引标签 |
| `trace_id`、`span_id` | Go HTTP／执行短阶段 Context 的规范关联字段，32/16 位小写十六进制且非零；作为结构化元数据，不作索引标签、不派生授权 |

执行短阶段的固定检查点可在正文属性保存规范 execution UUID、phase、attempt、outcome，复用当前阶段 Context 的 trace/span 关联；UUID 不作索引，不新增 Tenant 投影，不携带 SQL、参数、结果、原始异常或主体身份。仅在阶段真实结束时幂等记录，不用心跳／等待日志替代执行事实。

正文同名字段不能覆盖可信身份；超长事件带明确截断标记。解析和截断由接收器计数，发送重试与丢弃由 Alloy 指标观测。TSDB Schema 支持结构化元数据；实例、事件、请求 ID 及分段路径不得成为 Loki 高基数索引标签。

## 三、设施、容量与可靠性

### 3.1 部署与选择

每个应用节点使用独立 Alloy 只读采集源目录，不挂载 Docker Socket。Loki 采用单进程部署，复用 Infra MinIO 的独立日志 bucket 与最小权限凭据，不额外部署 Grafana 页面。Alloy positions、Loki WAL、Compactor 工作目录和源目录持久化，不能依赖容器可写层；备份范围按 Infra 指南执行。

组件固定版本、镜像 digest、架构、端口、网络和健康检查纳入标准 `up/down/status/ports`。读写入口仅向受控调用方开放，跨节点接入要求认证和 TLS；Loki tenant header 不替代 ADDP 用户授权。

集中日志按 `ADDP_OBSERVABILITY_LOGS_ENABLED` 独立选择。关闭时不创建集中日志组件，保留数据卷，源接收器和清理器继续受限工作；正文查询返回未接入，不能改成直接读文件。暂停观测不产生恢复事件，重新启用先重建计数基线与连续采样。具体配置、凭据撤销及部分启动失败行为唯一遵循[配置规范](configuration/Monitor与运行观测.md#模块服务运行日志配置)。

开发只初始化缺失秘密，不自动轮换已有值；Online 使用仓库外 owner-only `ADDP_ONLINE_ENV_FILE`，不生成根 `.env`，退出删除秘密目录，凭据不进入 Artifact。标准启动先创建宿主日志父目录，再启动 bind mount 容器；个人数据卷删除保护保持有效。

### 3.2 默认限额

以下是配置默认值，不是性能或完整性承诺。

| 项目 | 默认约束 |
| --- | --- |
| 集中保留 | 168 小时，由 Loki Compactor 清理 |
| 业务节点源保留 | 最长 48 小时，同时受磁盘额度限制 |
| 段 / 实例 / 节点额度 | 50 MiB / 1 GiB / 10 GiB |
| 单事件 | 64 KiB，超限显式截断；元数据另受限 |
| API 批次 / 正文 / 超时 | 默认 200 条、最多 1000 条、2 MiB、整次查询最多 10 秒 |
| Alloy 指标读取 / 来源扫描 | 2 MiB / 10000 个文件项 |

清理只删除已关闭段，按年龄处理，额度优先于时长，并记录提前清理。源清理不是送达回执，可能删除未采集输出。Compactor 到期标记与物理删除异步执行，不给整个 bucket 设置粗粒度过期而误删索引。

### 3.3 投递探针与缺口

常驻观察进程在启动时建立一个技术探针接收器，逐轮复用来源身份和递增序号；每轮生成独立消息标记，查询同时匹配身份与本轮标记，旧成功不能证明新投递。单次 `runtime-log probe` 检测结束后关闭接收器。

技术源 `runtime-probe` 的已关闭段按最后写入时间最多保留一小时，业务源配置更短时取较短值，持续技术段每小时轮转。标准清理器使用非阻塞段锁，仅清理关闭段；删除段和过期空目录共用节点锁，保护活跃接收器与业务源。不得保留每轮新建来源或另加旁路删除命令。

positions 表示读取位置，不表示远端持久化确认。首版不默认启用实验发送队列，未读取且仍保留的源可恢复采集，已读取后发送失败不能仅凭源文件宣称会补齐。极端断连、提前清理、接收器故障、机器损坏与未刷新缓冲均可能产生缺口；近期探针健康不证明所有实例或历史日志完整。

## 四、可信来源目录

未登记来源具有可信模块、角色、节点、实例和采集时间，但查询时尚未关联 System 登记事实。它不是 DOWN 或启动失败，首次采集时间不是业务启动时间，输出 EOF、error 或未登记都不能裁决退出结果。

Infra 独立上报来源元数据，System 保存目录并关联登记事实，Monitor 健康接收器列表不承载历史目录。来源记录不加入运行实例统计，不伪造地址、端口或运行时长；登记查询失败显示状态未知，不能解释为未登记。

```text
POST /api/v1/system/runtime/module-log-source-observations
GET  /api/v1/system/platform/module-log-sources
```

上报仅接受绑定节点的非委托 `addp-log-observer` Platform Service 与 `system.module_log_source.create`。报告唯一协议为 `addp.log-sources/v2`，最多 2048 个来源、2 MiB 请求；必需 `issues` 数组，完整扫描为空，不完整扫描包含合法原因及有界正整数次数，不支持 v1。节点、模块、角色、实例、接收器建立时间不可变，boot 与单调序号执行幂等、冲突和乱序校验。

诊断原因固定为 `metadata_missing`、`metadata_invalid`、`entry_unreadable`、`unsafe_entry`、`scan_limit`、`source_limit`。次数只表示本次有限扫描已发现的次数，不估算未扫描数量，不发送路径、正文或 OS 错误。旧元数据缺字段不推断可信身份，也不证明一定来自旧版本。

目录最多保留 16384 条有效来源，目录时间采用 UTC 微秒，正文保留纳秒。目录按最后来源观测加实际集中保留时长过期，重复扫描旧文件不延长期限；源文件已清理不立即删除仍在集中查询窗口内的目录。尚未发现便被清理的来源不承诺恢复。

目录读取复用 `platform.module_log.read`，按模块、节点、角色、首次采集时间筛选并使用管理分页；只列当前未关联登记的来源。`discovery_issues` 用 `observer_unobserved` 表示未收到报告、`observer_stale` 表示超过 120 秒未更新、`diagnostics_unavailable` 表示缺少诊断证据，否则返回本次扫描原因；诊断针对整次绑定节点扫描，不随列表筛选改变。过期问题不冒充当前证据，缺少诊断不能推断扫描完整。

选中来源复用既有日志抽屉与正文查询，授权依据为登记身份或有效可信来源，均绑定可信节点。目录存在不代表正文已送达；来源过期、权限消失或身份不匹配时不能继续读取。

## 五、正文查询与历史分页

### 5.1 API 与授权

唯一正文接口为：

```text
GET /api/v1/system/platform/modules/{module_name}/instances/{instance_id}/logs
```

接受 `from/to/level/keyword/limit/trace_id`，续批在同一路由携带服务端 `cursor`。trace_id 是可选的规范 32 位非零小写十六进制精确过滤，绑定游标指纹，不提供跨实例全局日志搜索。范围采用 UTC `[from,to)`，关键字为最多 128 字符的字面量，自定义窗口最长 7 天；不得提交正则、任意 LogQL、文件路径、远端 URL 或自报节点。

System 先校验 Platform Context 与 `platform.module_log.read`，再核验模块、实例和可信节点，最后生成受限 LogQL；离线登记仍可作为身份依据。新权限默认仅授予平台系统管理员，安全/审计/租户管理员、Runtime Service 与仅有模块读取权的用户不自动取得正文权限。

响应包含 `entries`、实际窗口、`returned`、`has_more/next_cursor`、查询时间和有证据的提示。不执行精确 COUNT，不显示总页数，不保存数据库正文副本。

| 情况 | HTTP 状态 |
| --- | --- |
| 参数 / 游标无效 | 400 |
| 未认证 / Context 或 Permission 不满足 | 401 / 403 |
| 已授权但实例或来源不存在、不匹配 | 404 |
| 同时间戳安全容量无法完整核对 | 422 |
| 未接入 / 上游失败 / 超时 | 503 / 502 / 504 |

失败不伪装成 200 空列表。Swagger、调用方、国际化错误和参数白名单与唯一契约同步维护。

### 5.2 游标与边界完整性

首批固定实际 UTC 窗口，批内按接收时间与精确 uint64 序号排序。续批先读取上一边界时间戳未返回记录，再向更早时间推进；不得把最早时间减 1 ns 跳过同时间戳记录，也不得将序号或纳秒时间转换为 float64 排序。Loki 使用排他 `end=to`，不额外减 1 ns。

游标通过 `common/opaquetoken` 进行完整性保护，复用 ENCRYPTION_KEY 的用途派生，绑定 Platform User、模块/实例/节点、窗口、筛选指纹、批大小、协议版本及排序边界，自首批起有效 30 分钟。每批重新核对当前 Permission 与身份，曾成功读取不授予后续访问权。

Loki 候选单次最多 1001 条；只有完整取得边界候选才生成稳定下一游标。同时间戳饱和、冲突身份、存储结果不一致或边界无法证明时明确失败，不能跳过记录或伪造末页。重复采集去重，响应按字节预算缩短时只越过实际返回条目。

查询不提供存储快照或采集完整性保证；迟到至已读位置的记录需刷新补查，保留删除可能改变重查结果。任意密度完整查询或一致快照如成为需求，须先另行确认存储与资源预算。

### 5.3 页面状态与交互

System 服务实例的 UP/DOWN 均可打开日志抽屉，固定模块与实例，显示角色、节点和时间。UP 默认最近 15 分钟；DOWN 默认离线判定前 15 分钟至后 5 分钟，结束不晚于当前时刻，注明租约判定不是真实崩溃时间。未登记入口显示采集及来源观测时间，启动结果未确认。

时间、级别、关键字、批大小变更回到首批并查询；关键字防抖 300 ms，Enter 立即查询。提供更早一批、返回上一批、回到最新，每次仅渲染当前批并保存浏览位置；筛选、实例变化与关闭清空位置。翻页失败保留当前批和位置，筛选变化清空旧结果，迟到响应不得覆盖新上下文。

自动跟随默认关闭，开启后每 3 秒替换最近批次；页面隐藏、关闭或浏览历史时暂停，回到最新重新固定窗口。它不是连续全量尾随。正文纯文本，支持堆栈展开和单条复制；关闭抽屉保留外层实例列表筛选和页码。

状态必须区分未接入、当前条件无匹配、超出配置保留窗口、查询不可用和采集完整性未知。空结果不证明未输出、未采集或已删除；已知节点丢弃不能推断某实例的精确丢失条数。失败保留同一查询上次结果并标为过时，链路健康不能替代完整性提示。

## 六、日志链路观测与告警

### 6.1 观测契约与权限

Infra 每 30 秒执行一轮不重叠观测，探针最长 20 秒，上报最多两次尝试。节点由部署与控制面绑定，独立非委托 `addp-log-observer` Platform Service 通过 `monitor.log_observation.create` 上报 `/api/v1/monitor/platform/log-observations`；User、其他服务或委托身份不能伪造。

载荷只含节点、观察进程 boot、单调序号、采样/接收时间、组件状态、探针结果/延迟及安全计数，不含任意指标标签、日志正文、令牌、业务参数或租户数据。Monitor 检查幂等、旧 boot、乱序、时钟边界和新鲜期，以接收时间裁决过期；上报失败不无限缓存或重放历史。

接收器按实例、Alloy 按本次启动比较计数，重启、下降或基线不可比时重建基线；首次历史累计值不算新增故障。已结束源的过期状态不触发当前接收器失联，登记不可得标为依据不足。普通文本、未知级别或一段时间无业务输出都不是丢弃证据。

日志策略与健康诊断使用 `monitor.log_pipeline.read/update`；统一平台事件使用 `monitor.platform_alert.read/update`，通知管理使用 `monitor.platform_alert_notification.read/update`，写操作同时要求对应读权限。管理限非委托 Platform User，默认平台系统管理员；正文独立由 System 授权。

### 6.2 默认裁决规则

策略默认失败及恢复窗口均为 3 个完整采样，过期 120 秒，投递延迟阈值 15 秒，容量预警 80%、恢复低于 70%。具体策略由 Monitor 统一管理，不散落于模块。

| 信号 | 打开条件与固定严重级别 | 恢复依据 |
| --- | --- | --- |
| 接收器写失败/丢弃、Alloy 发送丢弃 | 可比较新增立即 critical | 连续 3 个有效样本无新增 |
| Alloy 持续重试 | 连续 3 轮新增，warning | 连续 3 轮无新增 |
| 日志接口、探针、采集指标或来源观测失败 | 连续 3 轮失败，critical | 连续 3 轮有效成功 |
| 当前已登记实例的接收器缺失/过期 | 登记与来源证据有效且连续 3 轮缺失，critical | 连续 3 轮有效成功 |
| 清理观测失败 | 连续 3 轮失败，warning | 连续 3 轮有效成功 |
| 投递延迟升高 | 连续 3 轮超过阈值，warning | 连续 3 轮不高于阈值 |
| 观测缺失 | 超过新鲜期，critical，健康 unknown | 连续 3 轮有效上报 |
| 源容量预警 | 连续 3 轮达到 80%，warning | 连续 3 轮低于 70% |
| 源额度耗尽 | 连续 3 轮有效清理观测确认耗尽，critical | 连续 3 轮有效证据确认不再耗尽 |
| 源提前清理 | 可比较证据有新增立即 warning | 连续 3 轮有效样本无新增 |

提前清理、解析与截断分别保留风险计数，不能把解析或截断推断为整条丢弃。未知/失败样本不证明无新增或恢复，缺失不填零，部分成功不抵消其他环节失败。

平台事件按来源类别、主体类型、主体 ID、信号去重，有证据的实例另保留身份；同一身份最多一个活动告警。容量预警与耗尽分别打开、处理及恢复，不将同一信号升级。生命周期与订阅仅 `opened/resolved`，不接受 `escalated`；确认表示接手，限时抑制仅控制通知，恢复由有效事实裁决。

### 6.3 页面与领域事实

System 提供日志健康摘要、来源策略、活动数量和上下文跳转，完整告警、确认、抑制、通知目标与重投唯一入口为 Monitor `/platform-alerts`。观测新鲜、所需证据完整且无活动异常时才显示健康；存在活动告警显示告警，过期或证据不足显示未知并保留历史事件。

日志节点/策略事实与平台 incident/event/destination/delivery 分别由 Monitor 持久保存；平台事件不绑定虚构 Tenant 或任务，不能写入租户执行告警表。事件与通知 outbox 同事务，告警事实不依赖 Loki。Monitor 整体不可用的外部自监控与高可用不属于首版保证。

## 七、通知与最终失败重投

### 7.1 唯一管理与安全传输

平台通知共用 Monitor 的 Webhook、SMTP Relay、企业微信发送能力与有界重试，使用统一 `/api/v1/monitor/platform/alert-notification-destinations`、`alert-notification-deliveries` 及其凭据/测试/重投操作。日志不保留旧专用通知权限、管理路由或 System 管理表单；目标需显式订阅日志来源类别及 opened/resolved。

新目标先停用，凭据独立加密设置后再启用。测试正文使用 `addp.platform-alert-notification-test/v1`，不创建正式告警或 outbox，成功仅证明该次连接及接收。无目标或 SMTP 未配置明确显示未配置，不算已通知。

发送在事务外执行，claim/lease 栅栏仅允许当前领取者完成；发送前核对当前目标、订阅及抑制。网络请求已经发出时可能完成，不承诺恰好一次或取消送达。最终失败留 dead 记录；投递读取只公开安全状态、当前目标、事件及计数，不暴露地址参数、密钥、正文或 claim。

### 7.2 通用 Webhook

正式 POST 使用 JSON，日志正文 `schema=addp.platform-log-alert/v1`，仅包含 `event_id/event_type/incident_id/node/signal/instance_id/severity/occurred_at`，没有日志正文或租户数据。

| 契约 | 要求 |
| --- | --- |
| `X-ADDP-Webhook-ID` | 投递 UUID；同一重试保持 ID 和正文，恢复使用新投递 |
| `X-ADDP-Webhook-Timestamp` | 本次发送 Unix 秒，重试更新，不改原事件发生时间 |
| `X-ADDP-Webhook-Signature` | `v1=` 加小写 HMAC-SHA256，输入为 `timestamp + "." + raw_body` |
| 接收方 | 以原始字节和恒定时间比较验签、校验时间窗口、按投递 ID 去重，持久接受后返回 2xx |

默认公网 HTTPS；受管内网按 `MONITOR_WEBHOOK_ALLOW_PRIVATE_NETWORKS` 部署配置开放，页面不能绕过。TLS、DNS/IP 校验、禁止重定向与超时统一由受控 HTTP 客户端承担。打开/恢复可能乱序，接收方按事件 ID、告警 ID 及发生时间维护状态，不仅按到达顺序。

### 7.3 企业微信

`channel=wecom` 的 URL 与 recipients 为空，服务端保存固定官方 HTTPS 端点。完整机器人地址只经独立凭据接口写入；精确核对官方域名、路径、唯一 key 及无用户信息/端口/片段，提取 key 后用 ENCRYPTION_KEY 加密。读取只提供端点与 `secret_configured`，编辑留空不覆盖凭据，轮换受版本控制。

发送时才解密并拼接 key，不采用 ADDP HMAC 接收协议。只有 HTTP 2xx、有效有界 JSON 与整数 `errcode=0` 同时成立才记送达；拒收、限流、无效响应和网络失败使用安全原因，不回显 URL、key 或 errmsg。

Markdown 包含安全异常摘要、节点、严重级别、有证据的实例、原发生时间和告警/事件/投递 ID，不输出日志正文、不自动 @ 全员。至少一次投递可能重复或乱序，机器人接受不等于群端已读；独立测试、正式发送与群端接收分别验收。

### 7.4 手动重投

唯一重投接口为 `POST /api/v1/monitor/platform/alert-notification-deliveries/{id}/retry`，同时要求通知 read/update。只接受已有投递 ID、明确提交的 `expected_manual_retry_count`（首次 0 合法）与 `destination_version`，不接受地址、正文、事件类型或凭据。

仅 dead 可重投；目标仍存在、启用、订阅原事件类别及类型，渠道配置可用，关联告警未被抑制。按目标 SHARE → 告警 SHARE → 投递 UPDATE 锁顺序核对状态、版本和预期次数，原子递增人工次数并重新入队；并发、延迟旧请求不能重复开启周期。

保留原投递/事件/正文/发生时间，使用原目标当前配置，不迁移到新目标。`attempt_count` 是累计领取数，不等于接收方请求数；`manual_retry_count` 记录人工周期，以 `retry_base_attempt_count` 为本轮基线重新计算上限和退避。成功清除凭据，达到上限或最后领取过期再次 dead，不能无限发送。

成功 HTTP 200 只表示重新入队；状态、版本或当前资格变化 409，不存在 404，格式错误 400，无权 403。页面确认展示当前目标、原事件和告警状态，允许补发已恢复告警的历史失败事件，明确历史提示，保留原时间；迟到打开消息不能重新判故障。失败保留提示，成功刷新当前页，不提示已送达。

沿用 System 平台操作审计，仅追加操作者、事件/投递/目标 ID、前后次数及结果，不保存正文、关键字或密钥；跨服务审计不宣称与 Monitor 入队原子。历史失败确认、批量重投、自动补发抑制/取消记录和完整逐次网络历史不属于此能力。

## 八、验证与 CI 边界

文档整理不替代产品验收。代码变更按[测试与验收规范](addp测试与验收规范.md)选择现有标准入口，源文件与 CI 登记同步更新，不新增旁路测试或单次数据库。

| 层级 | 覆盖范围与标准入口 |
| --- | --- |
| T0 | 身份/权限、Swagger、配置/端口、生命周期及 CI 输入；`make test-platform` |
| T1 | 身份/脱敏、有界队列与清理、精确分页/令牌、观测基线及竞态；`make test-go`、`make test-common-python` 与实际消费者 owner 门禁 |
| T2 日志 | `make test-system-runtime-log` 自建 MinIO/Loki/Alloy/代理/观察器/清理器，验证持久化、断连恢复、节点/实例隔离、分页、SIGKILL 后已送达日志、额度与过期对象清理 |
| T2 控制面 | `make test-system-iam-postgres` 验证来源/权限；`make test-monitor-postgres` 验证并发去重、事件/outbox、真实受控 Webhook/企业微信 TLS、重试与手动重投 |
| T3 | System 正文/来源/诊断与 Monitor 告警页面、Console 跳转、固定窗口/跟随/迟到响应；对应模块标准门禁 |
| T4 | 真实模块登记/租约/异常退出/页面旧实例查询，多节点及故障恢复，按已登记 Online 入口明确选择场景 |

日志 T2 沿既有 System runtime log CI Job，Monitor 通知沿既有 PostgreSQL Job；共享变更按真实依赖扩散，工作区默认 `make test-changed`，明确 owner 时 `make test-module MODULE=<owner>`。本地 PostgreSQL 仅允许标准入口管理的 `addp_test/addp_iam_test`。

故障注入、超额、旧时间戳、通知接收及容器 UID 验证只在 disposable 夹具内执行，不停止个人服务、不向真实群或邮箱发送测试。退出核验自建容器、网络、卷、源目录与秘密零残留。旧时间戳和短删除调度证明 Compactor 机制，不等于自然等待满 7 天；隔离 SIGKILL 查询不等于真实业务登记/租约/浏览器 T4；Orchestrator Hosted 生命周期通过不扩大为所有日志专项通过。
