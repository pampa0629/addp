## Develop 执行策略

本节导航：[字段与范围](#develop-配置字段与范围)、[租户展示](#develop-租户展示与默认值)、[并发热更新](#develop-并发热更新)、[执行快照](#develop-执行快照与部署边界)、[验证与证据](#develop-验证入口与证据边界)。

### Develop 配置字段与范围

Develop 配置统一由 `develop.execution_policy` 持久化。平台管理员维护默认查询超时、最大超时、预览行数、单 Backend 查询总并发（默认 20）、单 Engine Instance 查询并发（默认 5）、Workflow 并发（默认 2）和 Notebook 并发（默认 1）；Tenant 只能覆盖默认超时，不能改写平台上限。全部并发数必须为正整数；Workflow 与 Notebook 各在 1–1000 内，单引擎上限不得大于总并发。

### Develop 租户展示与默认值

Develop 租户配置页只读展示当前最大查询超时、结果预览上限、总查询并发、单引擎查询并发、Workflow 并发和 Notebook 并发；这些并发额度均为每个 Backend 内跨租户、跨来源共享的上限，不是租户独享配额。默认超时标注继承平台默认或本租户已设置，保存提示只说明租户默认超时作用于新建执行，不暗示租户能够调整并发。读取与保存继续使用唯一 `/settings/execution-policy` 接口。

### Develop 并发热更新

并发采用 `hot_reload`：每次调度从平台策略读取一组完整的三类执行并发预算，默认每秒检查一次；本进程保存后唤醒调度器，其他实例在下一轮读取生效。调高增加可领取数量；调低不取消已运行执行，活动数低于新上限后再领取。Query 按 execution 冻结的 Runtime `engine_id` 分组，不按租户或 source 分裂。同一实例内所有来源共享限额；部署多个 Backend 时各实例独立应用上限。Monitor 心跳报告最新应用容量与真实活动数，缩容期间允许活动数暂时高于容量。

Develop 私有文件执行在业务终态之后，若原本地源 RPC 或原 Runtime 在途操作尚未证实停止，仍计入本实例的 Workflow 活动数，阻止超过原额度继续领取；确认运行体均已停止、仅文件删除待清理时不占计算名额。该私有核清复用原监督器恢复轮次及原实例批次，不延长业务截止、不续跑或复活执行，也不改变 Query／Notebook 的活动数。跨实例或丢失原会话不据持久路径接管清理，仍保留未核清事实；当前实例不伪造对其他实例运行体的活动观察。精确读写及停止证据边界见[Develop 私有文件执行](../addp授权上下文规范.md#524-develop-geopackage-工作流的精确读写)。

队列的唯一领取路径、类型额度隔离、交互 Session 排除和失联不重放统一见[执行监督与授权](../tasks/模块任务契约.md#develop-执行监督与授权)；容量展示不授予执行权限，也不证明远端已经停止。

### Develop 执行快照与部署边界

超时、结果预览采用 `execution_snapshot`：创建 execution 时解析平台策略及租户默认超时，固化有效 `timeout` 和 `query_result_limit`；查询授权预算、实际执行及结果裁剪都消费该快照。配置读取失败必须返回错误，不回退环境变量。并发不是 execution 快照，pending 查询按领取时策略调度。缺少必需快照的 execution 明确失败，不保留旧运行路径。

这些普通运行配置不再提供环境变量入口。租约、心跳和领取轮询仍属于进程部署参数。`hot_reload` 与 `execution_snapshot` 的通用定义沿[生效与变更规则](配置归属与生效.md#生效与变更规则)。

### Develop 验证入口与证据边界

测试分层及公共入口遵循[测试与验收规范](../addp测试与验收规范.md#三标准入口)。相关门禁各自验证：

| 标准入口 | 覆盖职责 |
| --- | --- |
| `make test-module MODULE=develop` | Develop 配置解析、执行快照与监督器的模块门禁；仅 Go T1 定位可用 `GO_ONLY=1`，不计为完整模块门禁。 |
| `make test-develop-postgres` | 策略持久化、单向迁移及查询／执行队列的 PostgreSQL 集成回归。 |
| `make test-console-frontend` | 配置页展示、来源标注、只读权限、刷新与保存字段白名单的受控浏览器回归及构建；现有 Platform CI 调用同一入口。 |

监督器的历史门禁、失败记录、修复与未覆盖项见[阶段性验证证据](../testing/evidence/引擎与空间计算历史证据.md#2026-10-13-执行监督器第一期工作区验证尚未发布)，按其所列版本与实际场景认定。配置保存、受控浏览器、局部 Go／PostgreSQL 通过不替代真实身份、Gateway、Runtime 与远端效果的完整链路验收；Notebook 排队派发和撤权闭环仍沿[当前授权边界](../tasks/模块任务契约.md#develop-执行监督与授权)，不能由已保存的容量或内容摘要推定已开放。

## Transfer continuous 运行观测配置

本节导航：[归属与生效](#transfer-配置归属与生效)、[观测身份](#transfer-观测链路与访问身份)、[阈值校验](#transfer-运行阈值校验)、[DLQ 部署治理](#dlq-reconciler-部署配置)。

### Transfer 配置归属与生效

Transfer continuous 的 diagnostics、retention、checkpoint 和 recovery 属于 Transfer-owned 平台运行配置，在“连续任务策略”Tab 维护；保存后的版本对新建或重新启动的 continuous runtime 生效。这些普通运行策略不通过环境变量注入，不写入用户 task config，也不按任务开放第二条判定路径。

Infra Kafka 连接、topic 保留容量和 DLQ reconciler 的采样细节仍属于部署配置。Kafka 连接、开发与生产部署、凭据分离及 Capture Supervisor 参数见[Kafka 与 Capture 部署](Kafka与Capture部署.md)，DLQ 采样参数见[下文](#dlq-reconciler-部署配置)。

### Transfer 观测链路与访问身份

分区位置、lag、retention 恢复窗口的采集主体和 Monitor 读取边界统一见[采样与健康诊断](../tasks/Transfer同步执行.md#continuous-采样与健康诊断)。PostgreSQL CDC consumer 使用 Infra Kafka 独立 `transfer` principal，读取 `INFRA_KAFKA_BOOTSTRAP_SERVERS`、`INFRA_KAFKA_TRANSFER_PASSWORD`、`INFRA_KAFKA_SECURITY_PROTOCOL` 和相同 TLS 配置；这些部署字段不进入 System Engine 或任务 JSON。

### Transfer 运行阈值校验

critical 阈值必须小于 degraded 阈值；checkpoint 停滞阈值必须大于 diagnostics 采样间隔。恢复初始退避不得大于最大退避，最大连续失败次数必须为正，circuit 冷却时间和稳定运行阈值必须为正。这些阈值属于 Transfer runtime 统一运维策略。

### DLQ reconciler 部署配置

以下参数只用于 Transfer 部署治理，不进入任务 JSON：

```bash
# DLQ payload availability 低频核验。仅属于 Transfer 部署治理，不进入任务 JSON。
TRANSFER_DLQ_RECONCILE_INTERVAL=1m
TRANSFER_DLQ_RECONCILE_BATCH_SIZE=100
TRANSFER_DLQ_RECONCILE_TIMEOUT=10s
TRANSFER_DLQ_RECONCILE_FETCH_MAX_BYTES=10485760
```

DLQ reconciler 的 interval、timeout、batch size 和 fetch bytes 必须为正；batch size 最大 1000，fetch bytes 不得超过 Kafka 客户端的 `int32` 上限。精确 payload reference 核验、CAS、瞬时失败保留与恢复主路径见[availability 治理契约](../tasks/Transfer-Kafka与DLQ.md#dlq-payload-availability-治理)；不读取业务 Kafka、不提交消费位点，也不把原始 payload 写入日志或 API。

## Service 运行计划

Service 的健康检查与元数据刷新计划属于 Service-owned `platform_only` 普通运行配置，保存后按受控重启生效。

## 禁止暴露的旧变量

以下变量没有形成实际运行路径，禁止继续暴露在配置页面：`COPILOT_ENABLE_STREAMING`、`COPILOT_MAX_TOKENS_PER_DAY`、`COPILOT_RATE_LIMIT`、`DISABLE_SSL_VERIFY`、`WORKER_COUNT`、`TASK_QUEUE_NAME`、`MAX_RETRIES`。Meta 与 Transfer 的 worker 并发和重试等待使用模块独立的部署参数，不再共享 `CONCURRENT_TASKS`、`RETRY_DELAY`。

## 模块拥有的运行策略

配置管理页面只承载模块自己拥有、可以在运行时安全生效的策略。System 只保存模块注册的入口声明，不保存业务配置键和值。

当前模块级入口下的运行策略：

| 模块级入口 | 所有者 | 内部配置域 | 平台级字段 | 租户级字段 |
| --- | --- | --- | --- | --- |
| `develop.configuration` | Develop | `execution_policy` | 最大查询超时、结果预览上限与三类执行并发 | 默认查询超时 |
| `manager.configuration` | Manager | `embedding`、`quick_view_policy` | 向量化策略、FlatGeobuf 行数上限、动态 MVT 超时预算、重试等待时间 | 向量化模型绑定及租户覆盖 |
| `copilot.configuration` | Copilot | `inference_bindings`、`matching_policy` | 匹配阈值、候选数量上限 | 推理场景绑定、匹配阈值、候选数量上限 |

模块数据库保存配置事实并使用版本号进行并发更新；密钥类字段必须使用专用加密凭据，不通过普通键值配置返回。
