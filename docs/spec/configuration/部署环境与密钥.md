## 当前部署配置说明

`ADDP_DEPLOYMENT_DISCOVERY_DIR` 是部署侧 Infra/Business 自动发现快照的绝对目录，发布入口留空时使用仓库 `.dev-state/deployment-discovery`；开发启动将实际目录注入 System，其他部署须显式配置 System 的读取位置，未配置不会猜测路径。目录必须归当前部署用户所有、权限 0700 且不是符号链接，快照以 0600 原子替换；两个作用域各用独立文件与锁。快照不含凭据或租户信息，不是 System 纳管授权；发现失败写入明确的不可用结果，不沿用旧成功候选，也不阻断核心服务启动或停止。System 只读固定作用域文件，120 秒后清除有效候选，最多允许来源时钟领先 30 秒。当前由 Infra 生命周期管理独立来源观测进程，Business 和开发启动幂等确保其存在；每轮完成后间隔 30 秒刷新，停止时清除有效来源。进程不继承 ADDP／SQL 凭据或开发生命周期锁，未知 PID 不操作；Infra 停服仍执行，无法核验观测进程退出则单独返回清理失败。页面批量确认和专业采集仍在后续专题实施。

共享 Meilisearch 固定使用 `1.54.3` 的多架构镜像摘要与独立命名卷 `meilisearch_data_v1543`。旧版本的 `meilisearch_data` 卷只作为历史回滚材料保留，不再作为当前 Compose 挂载路径；升级必须从已核验 dump 导入空的新卷，不能让新二进制打开旧卷。镜像与卷绑定均由基础设施 Compose 唯一定义，不新增运行时配置或双轨服务。迁移阶段、验证和回滚边界见[旧 Meilisearch 卷迁移与回滚](../../../scripts/infra/docs/备份恢复与搜索迁移.md#旧-meilisearch-卷迁移与回滚)。

HDFS 首版固定 Simple 开发实验模式。引擎连接的 `webhdfs_endpoint`、`rpc_uri`、`root_path`、`authentication`、`user` 由插件 `ConnectionSpec` 唯一定义；首版 RPC 必须为具体 `hdfs://host:port`，不支持 HA nameservice。Spark 应用部署以 `HADOOP_USER_NAME` 固定 Hadoop 用户，不能按资源切换共享会话的身份；读取前验证当前 Java UGI 用户与引擎 `user` 一致。Business 本机 Docker Desktop 实例的四个监听端口归 `business/.env`，均发布到 `127.0.0.1`；DataNode 公布 `host.docker.internal`，宿主机通过 `/etc/hosts` 的回环映射消费同一主机名，容器使用 Docker 内置解析。删除 `HDFS_SHARED_HOST` 与局域网 IP 自动检测，不保存随换网变化的地址；启动前验证宿主机映射。部署地址不进入平台普通配置，也不保存到工作流任务。Simple 的用户名声明不构成安全认证。

PointCloud、Document 的 HTTP 监听地址由部署入口通过 `WORKFLOW_BIND_HOST` 注入，默认 `0.0.0.0`，用于普通 bridge/Compose 容器内监听。Hosted Online 原生 Linux 使用宿主网络时，标准开发入口固定注入 `127.0.0.1`，并以 `PORT` 指定实际开发端口；`RUNTIME_HOST` 与 `RUNTIME_PUBLIC_PORT` 仍只负责自注册地址，不用于控制监听。该配置随进程启动生效，不保存到业务配置或根 `.env`。

GeoPython 原生开发入口固定 HTTP 监听回环与实际 `PORT`，不注入容器的 loopback 地址改写；GDAL/PROJ 路径从原生安装派生，Runtime 专属 `ODBCSYSINI` 存在于 `.dev-state/geopython-odbc`，不会修改系统 ODBC 配置。产品 Compose 使用服务名，Hosted 栅格产品 Runtime 独立使用宿主网络与回环源地址。

Spark Workflow 原生开发启动固定注入 `WORKFLOW_BIND_HOST=127.0.0.1` 与实际 `PORT`，Java 11 只注入 Spark 子进程。`SPARK_WORKFLOW_SHARED_HOST` 声明 Driver/Executor 共用的地址：macOS 默认为 `host.docker.internal`，需在本机 `/etc/hosts` 配置 `127.0.0.1 host.docker.internal`，容器继续使用 Docker 内置解析；Hosted Linux 为 `127.0.0.1`，普通 Linux 使用路由接口地址。远程部署按实际拓扑显式配置。开发启动不构建镜像，不依赖 Docker Desktop host networking；生产 Compose 按自身网络部署。

本机 Business 的回环地址与 `host.docker.internal` 必须直连。Spark 原生启动入口读取所选 Java 11 的有效 `http.nonProxyHosts`，保留现有条目并补齐 `localhost`、`127.*`、`[::1]` 和 `host.docker.internal`，仅在该 Runtime 子进程的 `_JAVA_OPTIONS` 中设置合并值；Python 的 `NO_PROXY` / `no_proxy` 同样合并本机地址。外部下载仍使用既有代理，不修改 macOS 全局代理或 System 中的引擎连接。配置在 Runtime 重启后生效；远程引擎不自动加入直连名单。


## 平台关系数据库选型

`ADDP_INFRA_DATABASE_PROVIDER` 是平台关系库消费者的部署输入，在进程启动时确定。Go Backend、Worker、System IAM 与部署工具、以及 Python Agent 和 Copilot 从各语言的 Common Infra 入口选择实现。默认和当前支持值均为 `postgres`，未知值在建连前拒绝。Compose 与 K3s 试点入口分别向各自消费者注入同一选型和 `TZ`，PG 会话时区默认 `Asia/Shanghai`。Agent 的历史消息和会话使用无时区时间戳，Agent 会话沿用 PG 默认时区，保证既有记录与新写入使用同一基准。Swarm 使用执行 `docker stack deploy` 时的环境变量。沿用各进程的端点、凭据、逻辑库、命名空间、连接期限及故障处理。Gateway 在访问日志数据库故障时沿用既有告警和降级行为。System Infra 原生配置管理使用专用管理身份，用户注册的业务 Engine 使用各自实例配置。

### 基础设施运行配置接入

部署运维按需向 System 注入 `ADDP_INFRA_PG_CONFIG_PASSWORD` 和 `ADDP_INFRA_REDIS_CONFIG_PASSWORD`。两者使用各组件独立的 `addp_infra_config` 身份，绑定 System 启动时选定的端点。未注入凭据时对应配置区显示未接入。部署参数和凭据的维护沿现场部署流程。

PostgreSQL 运维在实际连接库中用授权管理员准备角色，并通过 `psql` 的 `\password addp_infra_config` 交互设置密码。角色仅用于读出显式参数和应用下列设置，保持无超管权限。若现场已收紧数据库 CONNECT，需允许该角色连接 System 使用的数据库。

```sql
CREATE ROLE addp_infra_config LOGIN;
GRANT ALTER SYSTEM ON PARAMETER work_mem, maintenance_work_mem, log_min_duration_statement, log_lock_waits TO addp_infra_config;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_reload_conf() TO addp_infra_config;
```

内置 PostgreSQL 的部署配置文件统一提供 `max_connections=200`、`shared_buffers=256MB`、`work_mem=32MB` 和 `maintenance_work_mem=128MB`。前两项由部署维护，修改后需重启 PostgreSQL 生效。后两项可在线修改，由数据卷的 `postgresql.auto.conf` 优先应用。Redis 的同名管理用户由内置启动脚本按 `ADDP_INFRA_REDIS_CONFIG_PASSWORD` 创建，用原生配置文件 `/data/infra-redis.conf` 保留在线修改。ACL 与认证继续由部署脚本准备。Redis 管理身份仅交给 System 和部署凭据管理者，参数授权由 System 白名单裁决。Redis 的原生重写会保存当前实例配置，运维应通过同一持久化流程维护参数，避免同时进行只希望暂时保留的实例级修改。

首次接入由运维在维护窗口用标准部署入口应用 Infra 和 System 的启动定义。现有容器需要应用新的 Compose 定义，单独重启旧容器不会换用新定义。后续页面内可修改的参数按[生效规则](配置归属与生效.md#基础设施运行配置)在线应用，组件本身不需要重启。平台管理员应结合 Monitor 观察变更效果。

Copilot 的平台 PostgreSQL 连接只消费部署注入的 `POSTGRES_*`，使用数据库用户名／密码认证；开发入口不另建 `DATABASE_URL` 覆盖。其 libpq 连接显式使用 `gssencmode=disable`，不尝试依赖宿主机 Kerberos 票据和 KDC 的 GSSAPI 加密协商；密码认证和 SSL 协商规则保持生效。该参数控制传输协商，不关闭数据库身份认证。

### MySQL 8 平台会话验收

Common 的 MySQL 8 会话适配器连接一个已部署的物理 database，使用 `utf8mb4`，把 IANA 时区同时应用到服务器会话和 Go 时间值解码。部署须为 MySQL 安装命名时区表。连接输入采用独立的地址、端口和凭据字段，TLS 模式为 `disable` 或 `verify-full`。使用实际 MySQL 8 验证两条物理连接、事务回滚和约束错误翻译，统一入口为 `make test-common-mysql-data-protection COMMON_MYSQL_TEST_ARGS='--local-disposable --test platform-database'`。生产启动的 `ADDP_INFRA_DATABASE_PROVIDER` 继续只接受 PostgreSQL，待共享与模块迁移通过后登记 MySQL。MySQL DDL 的提交边界由后续迁移实现负责。

### MySQL 启动迁移与版本核验

Common `schema.MigrateMySQL` 在 owner 已选定的物理 database 内，通过同一条连接持有启动迁移锁。先持久登记待迁移版本，再执行模块的可重复迁移，全部成功后才更新完成版本。`schema.RequireMySQL` 只读取版本，待迁移期间拒绝启动 Worker，包括仍要求旧版本的 Worker。迁移失败时保留待迁移版本，由相同目标版本重新执行。模块负责识别已提交的 DDL，并用事务处理需要原子提交的业务数据修补。Common 会话和迁移协调共用 MySQL 8 实库门禁。生产启用另须完成各模块迁移、命名空间映射和数据核对。 [MySQL DDL 的隐式提交](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html) · [同连接命名锁](https://dev.mysql.com/doc/refman/8.0/en/locking-functions.html)

新装 MySQL 时，安装进程负责建立模块表、存储过程、触发器和结构版本。System 与 Worker 分别使用运行账号，只读取相应模块的结构版本，并按职责读写业务表。安装凭据仅注入安装进程。审计写入需要向 `system.audit_logs` 追加记录，运行账号没有修改、删除、截断该表或改写版本的权限。Meta Worker 无需 System 的安装或审计写权限。

System 的 MySQL 新装使用同一条命令，分别记录 IAM、授权请求锁、目标锁、模块注册表、引擎父表和源授权表的结构版本。安装账号在预建的 `system` 库内建立表和过程，持有本库的 `SELECT, INSERT, UPDATE, CREATE, REFERENCES, INDEX, ALTER, TRIGGER, CREATE ROUTINE, EXECUTE` 权限。MySQL 8 默认启用 binlog 并限制触发器创建，部署 DBA 在同一目标库执行安装入口输出的 SQL，每个触发器的 DEFINER 都是安装账号。该账号需保留，应用进程只使用运行账号。安装入口按各自的版本核对触发器定义、顺序和归属。请求锁结构就绪后可以独立完成；IAM 与注册表分别在所需触发器齐备后提交各自的数据和完成版本。[MySQL 二进制日志与触发器](https://dev.mysql.com/doc/refman/8.0/en/stored-programs-logging.html)

安装机从密钥管理注入 `ADDP_MYSQL_INSTALL_USER` 和 `ADDP_MYSQL_INSTALL_PASSWORD`，指定 `ADDP_INFRA_DATABASE_PROVIDER=mysql`、`ADDP_MYSQL_HOST`、`ADDP_MYSQL_PORT`，远程 TLS 校验使用 `ADDP_MYSQL_SSLMODE=verify-full`。使用与 System 同版本的服务二进制执行 `system-server install-mysql-system > triggers.sql`。退出码 3 表示仍有待 DBA 创建的触发器，输出同时列出 IAM 和注册表缺少的定义。DBA 审阅后在同一实例执行，并重跑同一命令。只执行清单的一部分时，重跑仅输出仍缺的定义。退出码 0 表示上述分项结构版本均已完成，其他非零码表示失败。生产 System 服务和 Worker 的完整启动仍随各自所需的表和授权入口验收。独占实库入口为 `make test-common-mysql-data-protection COMMON_MYSQL_TEST_ARGS='--local-disposable --test platform-system-install'`。

### MySQL Common 执行存储

DBA 预建 `common` 库，向部署程序单独注入该库安装账号的 `ADDP_MYSQL_INSTALL_USER` 和 `ADDP_MYSQL_INSTALL_PASSWORD`。部署程序从同版本包执行 `system-server install-mysql-common`。该命令只调用 Common 的执行、事件和运行健康迁移。System 安装命令继续只连接 `system`，两条命令各使用本库账号。System 和 Meta Worker 通过自己的运行连接对 `common.startup_schema_revision` 执行 `SELECT`。版本缺失、与进程期望不符或仍有待完成版本时，检查失败。业务表的读写权限按进程职责授予。实库入口为 `make test-common-mysql-data-protection COMMON_MYSQL_TEST_ARGS='--local-disposable --test platform-common-install'`。

MySQL 8.0 新装试点由部署预建 `common` database。Common 通过相同的事务与执行接口提供执行记录、事件和后台运行心跳。MySQL 使用 InnoDB、原生 JSON、微秒精度时间列及对应的约束。租约取得行锁后从数据库采样时间；后续写入以数据库时间检查租约或授权截止点。平台 MySQL 会话使用 Read Committed，并返回匹配行数以保持相同的条件写入契约。[MySQL InnoDB 隔离级别](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)

Common 实库门禁使用 `make test-common-mysql-data-protection COMMON_MYSQL_TEST_ARGS='--local-disposable --test platform-execution'`。通过启动迁移入口准备执行存储，再按同一 `execution_id` 核对领取、`started`、终态和租约失效。System 和 Meta 的真实进程启动与任务提交单独验收。

#### System 和 Meta Worker 的 MySQL 启动检查

选定 `ADDP_INFRA_DATABASE_PROVIDER=mysql` 时，这两个进程读取 `ADDP_MYSQL_HOST`、`ADDP_MYSQL_PORT` 和 `ADDP_MYSQL_SSLMODE`。System 使用 `ADDP_MYSQL_SYSTEM_USER`／`ADDP_MYSQL_SYSTEM_PASSWORD` 连接固定的 `system` 库，Meta Worker 使用 `ADDP_MYSQL_META_WORKER_USER`／`ADDP_MYSQL_META_WORKER_PASSWORD` 连接 `meta` 库。主机、端口、账号及密码必须显式注入。每个账号以 SELECT 读取本库和 Common 的安装版本。

System 的检查覆盖 IAM、请求锁、注册表、引擎父表和 Common。当前安装器尚缺源授权等业务结构，上述检查通过后仍在签发凭据、启动 HTTP 和后台维护前退出，提示缺少的业务结构。Meta Worker 检查扫描任务和 Common 的版本，并要求 Meta 整库版本匹配；只有扫描任务表时，在注册和领取前退出。安装或修复由部署账号执行。其他模块仍按各自已接入的数据库范围启动。

Meta 扫描事实的分项安装版本为 `meta_scan_catalog`。节点和条目以 `(tenant_id, engine_id)` 引用 System 引擎，条目保留全局指纹唯一性；对象索引删除登记沿用扫描事务与原操作 ID。该版本只覆盖这三张表。完整 Meta 版本还依赖 Catalog 变更、授权依据版本及血缘等结构。独占 MySQL 门禁从真实源库扫描并经租户限定的仓储读回；父表与子表均由各自服务的正式安装命令建立。验证入口为 `make test-common-mysql-data-protection COMMON_MYSQL_TEST_ARGS='--local-disposable --test platform-meta-scan'`。

MySQL 新装先完成 `system-server install-mysql-system`，由 System 发布 `system_engine_catalog` 并建立 `system.engines (tenant_id, id)` 唯一键。同一租户与引擎类型下，尚未删除的实例地址保持唯一，平台共享引擎另有独立的地址范围；删除墓碑保留 ID 并释放地址。

随后 DBA 在同一实例预建 `meta` 库。Meta 安装进程使用本库安装账号（本库 `SELECT, INSERT, UPDATE, CREATE, INDEX, ALTER, REFERENCES`），沿用上述安装机连接变量。DBA 仅在这次安装窗口临时授予该账号对 `system.engines` 单表的 `REFERENCES`。部署程序执行 `meta-server install-mysql-scan` 安装扫描任务和事实表。退出码 0 表示已核对节点、条目的两列外键与级联删除规则。DBA 随即撤销单表授权；安装失败也应先撤权，查明原因后重新授权续办。命令中的账号和来源主机替换为实际部署值。

```sql
GRANT REFERENCES ON `system`.engines TO 'meta_installer'@'install-host';
-- 在安装机运行 meta-server install-mysql-scan，记录退出结果后收回授权。
REVOKE REFERENCES ON `system`.engines FROM 'meta_installer'@'install-host';
```

Meta 运行账号仅获业务所需权限。已有外键在安装授权收回后继续校验租户与引擎归属。扫描安装命令只发布分项版本；完整 Meta 服务仍按整库版本判断就绪。

### MySQL System 授权请求锁与目标锁

System 签发和履约沿同一事务锁定 `request_id`。MySQL 使用 `system.engine_access_request_locks` 的 InnoDB 主键在首次签发时建立锁定记录，复用同 ID 的事务等待该记录。记录的变更与外层事务提交或回滚。首次任务产出和上传使用 System 按各自完整结果键派生的签发 request_id，成功和拒绝在同一键上串行。实库门禁覆盖同 ID 等待、不同 ID 可同时处理，以及回滚后同 ID 可继续。System IAM 完整迁移与签发流程另行验收。

不同请求对同一目标的签发、撤权与履约，在调用方的同一事务中再取得目标锁。System 从租户和规范化目标构造与 PG 相同的键，MySQL 以其 SHA-256 摘要作为 `system.engine_access_target_locks` 的 InnoDB 主键。节点与数据项沿用各自的身份规则。事务首次插入或命中现有行时取得排他锁，由提交或回滚释放。已提交的锁行可复用，不参与授权判断。

`system-server install-mysql-system` 安装目标锁表。DBA 仅向 System 运行账号授予写入键和重复命中时更新标记的列权限，将下例账号及来源主机替换为实际部署值。过程定义者和 Meta Worker 沿用既有授权。

```sql
GRANT INSERT (target_key), UPDATE (lock_marker)
ON system.engine_access_target_locks TO 'system_runtime'@'system-host';
```

#### Catalog 履约回执

System 在履约事务内追加 `accepted` 或 `closed` 回执和对应审计，按同一请求及原始绑定读回历史结果。DBA 在 System 安装完成后按下例授权，账号和来源主机取实际部署值。回执的 UPDATE 和 DELETE 由不可变触发器拒绝。Meta Worker、离线三员初始化账号和签发过程定义者均无需回执表授权。

```sql
GRANT SELECT, INSERT ON system.engine_access_fulfillment_outcomes
TO 'system_runtime'@'system-host';
```

已接受的回执在有效期内可供 Catalog 签发使用，已关闭的回执不能产生 Grant。Grant 和两张首次签发结果表继续由受限过程写入。

#### 引擎管理委托

`system-server install-mysql-system` 在 IAM 和引擎目录之后安装 `system.engine_access_delegations` 及其守卫。System 使用原有的创建、读取、撤销流程，核验操作者权限和成员有效期，在同一事务更新接收方授权版本、撤销活跃凭据族并追加审计。履约接受时检查委托是否仍有效。已撤销和已过期的委托保留历史。

DBA 将下例账号替换为实际 System 运行身份。新委托必须从有效状态和版本 1 开始。插入守卫先锁定已有成员行，再以锁定读检查同一租户、引擎和成员的委托区间，覆盖该成员尚无委托的首次并发创建。撤销只允许更新以下五列，且版本必须递增 1。Meta Worker 和签发过程定义者无需此表权限。

```sql
GRANT SELECT, INSERT, UPDATE (status, version, revoked_by_principal_id, revoked_at, revoked_reason)
ON system.engine_access_delegations TO 'system_runtime'@'system-host';
```

#### 源 Grant 撤销历史

System 将撤销人、租户成员、数据库时间、原因和同次撤销的 Grant ID 追加到 `engine_access_grant_revocations`。查询有效授权关系时排除已有撤销记录的 Grant。原签发和原回执保留历史；同一关系重新签发使用新请求 ID。DBA 仅给 System 运行账号下列权限。既有安装账号定义来源校验和不可变触发器；签发过程定义者和 Meta Worker 无需新增授权。

```sql
GRANT SELECT, INSERT ON system.engine_access_grant_revocations TO 'system_runtime'@'system-host';
```

#### System 清理协调器

System 安装程序建立 `system.cleanup_requests`。协调器从 Common 执行表查找属于已受理请求的父执行，以一次写入的 cutoff 固定清理范围。协议正文与请求范围按原始文本存储。DBA 仅给 System 运行账号以下表权限。签发过程定义者和 Meta Worker 沿用原授权。

```sql
GRANT SELECT, INSERT, UPDATE (cutoff) ON system.cleanup_requests TO 'system_runtime'@'system-host';
```

#### 首次源授权的 MySQL 过程与部署身份

System 领域服务在原事务中完成身份、租户、来源、目标和有效期检查，取得请求锁，写签发审计，执行提交前复核，最后决定提交或回滚。PG 用延迟外键将 Grant 和成功结果成对保存。MySQL 的设计采用一个 System 私有、定参的 `SQL SECURITY DEFINER` 过程；成功结果以立即生效的外键引用已经插入的匹配 Grant。过程只执行静态 DML。

| 身份 | 写入权限及责任 |
| --- | --- |
| 部署 DBA | 审阅过程定义、固定 DEFINER 和逐对象授权。部署时核对账号实际权限及继承角色。 |
| 过程定义者 | DBA 在全新实例按 `mysql_source_grant/create_definer.sql` 创建并保留锁定的 `'addp_system_source_grant'@'localhost'`。如同名账号已存在，先核对归属。核对父表、守卫与过程后，按同目录 `authorize_definer.sql` 授予 Grant 表和两张结果表的 INSERT、指定过程的 EXECUTE。应用无需登录密钥。 |
| System 运行账号 | 原有读取和追加审计按职责授权。源 Grant 和两类首次结果均走指定过程的 EXECUTE。对其基表不授直接写入、DDL、过程管理或转授权。 |
| Meta Worker、其他模块和离线三员账号 | 不授源签发过程的 EXECUTE 或基表写权限。 |

`task_production` 沿用租户、生产 Owner、execution ID、result ID 标识一项结果；`upload_creation` 沿用租户、upload ID、Item 指纹。成功写入 Grant 和一条 `issued` 结果，拒绝仅写原有原因的 `denied` 结果。签发主体与成员身份、业务采样的记录时间、数据库产生的 Grant 时间各自保留。`catalog` 和 `independent` 共用 Grant 基表，正式接入时也须通过同一受限写入口，仅保存各自原有 Grant。四种业务的鉴权仍由原来的 System 入口负责。

过程先确认调用处有可用的事务保存点，再执行 DML。第二笔写入冲突时回到本次调用前的保存点并向外抛错；审计或提交前资格复核失败时，System 回滚整个事务。仅持有 EXECUTE 的数据库连接本身不代表某个租户身份，过程也不能强制应用追加审计。正式接入仍需从原服务入口验证租户、身份、幂等、资格复核和审计。

DBA 在核对运行账号只能通过过程签发、部署账号分工符合上表后，用自己的临时连接环境运行 `system-server verify-mysql-source-grant`。命令使用安装命令的连接变量，仅在该离线进程中提供 DBA 凭据。它读取实际过程正文、参数顺序与类型、安全模式、定义者的锁定状态和完整授权，再发布 `system_source_grant_procedure` 版本。新装缺少此记录时 System 拒绝启动。过程或授权有变更时，部署方须先停止消费该安装版本，再执行核验。

System 安装命令在 IAM 和引擎父表之后安装 `system_source_grant_catalog`，包括 Catalog 履约回执、Grant 主表以及两类首次结果表。DBA 沿用已有安装账号作为来源校验及不可变触发器的定义者。Catalog 字段取自有效期内的已接受回执，独立签发核对当前用户及接收方，任务产出和上传核对当前用户及相应租户中的签发服务。此结构版本仅供安装程序核验；数据目标完整性和有效授权关系的守卫齐备后才能开放运行签发。

节点 Grant 的路径规则与 PG 相同。System 按租户中的实际业务引擎核对节点类型：PostgreSQL 接受服务器或 schema，NFS 接受根或目录，MinIO 接受服务、桶或前缀。MinIO 服务根要求递归授权。安装程序核对节点触发器正文并记录结构版本。受限运行账号通过现有签发过程写入，外层事务仍由 System 控制。

权限验证使用 `make test-common-mysql-data-protection COMMON_MYSQL_TEST_ARGS='--local-disposable --test platform-source-grant-boundary'`。门禁直接加载 System 的 `persist_source_grant.sql` 和两张首次结果表的结构，检验完整结果键、两种普通签发、错账号、事务外调用、重复结果和外层审计回滚。门禁另以受限 System 账号调用 Go 仓储，按任务产出结果键读回数据库生成的签发时间和原目标，按上传结果键读回拒绝原因。此门禁通过正式安装命令创建 IAM、引擎、履约回执、Grant 和结果表。租户、任务及上传身份为独占测试数据，审计失败由夹具表触发。目标和关系守卫、过程安装核验与完整应用签发入口仍须验收，之后再向运行账号开放过程。[MySQL 存储对象的权限](https://dev.mysql.com/doc/refman/8.0/en/stored-objects-security.html)

### MySQL System IAM 主体与用户首批迁移

MySQL 8.0.29 及以上的新装试点从 System 自有的主体与用户表开始。迁移使用 Common 的待迁移版本核验，在部署预建的 `system` database 内执行可重入 DDL。复合外键保证 User 只能引用 User 类型的 Principal，并阻止已绑定用户的主体更改类型。授权版本、主体状态与停用时间约束沿现有规则。此批覆盖主体与用户基础结构，后续 IAM 迁移继续补齐租户成员、凭据和治理审计，再开放 System 进程启动选型。

实库入口为 `make test-common-mysql-data-protection COMMON_MYSQL_TEST_ARGS='--local-disposable --test platform-system-iam-foundation'`。门禁检查空库初始化、重复迁移、部分 DDL 后续跑、类型和状态约束以及事务回滚。

### MySQL System 租户与成员

System 在同一 `system` database 的 IAM 版本 2 建立租户与成员基础表。租户代号沿用现有规范化，MySQL 保存原规范化文本，并为其 SHA-256 生成值建立唯一索引，避免将 InnoDB 索引键长度作为产品输入长度。代号正文使用 `utf8mb4_0900_bin` 严格比较。摘要碰撞时拒绝写入。成员状态、来源、时间以及两个成员唯一键均由 System DDL 保证。新增、修改或删除成员在同一事务内提高该主体的授权版本，回滚同时恢复成员事实和授权版本。成员标识不可更换。

此版本只验证租户和成员基础事实。系统租户初始化要求保有有效管理员，服务主体的成员范围取决于所有权，两项随角色和服务主体迁移完成。由临时 MySQL 运行既有 `platform-system-iam-foundation` 门禁，验证从版本 1 升级、中断后续跑、租户代号唯一、成员约束与授权版本回滚。

### MySQL System 本地密码与 TOTP 凭据

IAM 版本 3 保存本地账号的密码哈希与 TOTP 加密凭据。账号继续按现有 NFKC 和大小写折叠规则生成规范化用户名。MySQL 用该全文的 SHA-256 生成值约束唯一性，仓储按摘要索引查找后仍校对规范化全文。原密码校验、账号锁定及密码更换的上层事务继续复用。TOTP 凭据保持同用户同方式只有一条处于启用态，保留停用历史。数据库拒绝更改凭据身份、重新启用、回退计数和逐行删除。正式运行账号的 DDL 权限隔离须在启用 MySQL 启动前落实，防止通过截断表移除历史。

同一 `platform-system-iam-foundation` 实库入口覆盖当前版本升级、查询与校验密码、重复账号冲突、TOTP 密文和计数、替换凭据与事务回滚。挑战、会话、OAuth 服务凭据和恢复流程仍需各自迁移与实际启动验证。

### MySQL System 租户管理员约束

IAM 版本 4 建立角色和角色分配的基础结构，并保护已初始化且未关闭租户的有效管理员。资格按数据库当前时间和已有角色、分配、成员、主体事实计算。合格者须持有当前生效且无结束时间的内置租户管理员分配，成员须有效且无过期时间，主体和角色均须启用。

InnoDB 在可能使资格失效的 SQL 写入结束前检查该规则，以共享锁读取足以继续满足约束的记录，锁保留到事务结束。租户初始化和重新开启前须已存在有效管理员。同一事务更换管理员时先建立有效的接任方，再撤销原分配。检查失败随原写入回滚；若同时写入形成锁环，由 InnoDB 回滚其中一笔事务，应用沿现有错误路径处理。验证复用 IAM 门禁，用两条物理连接执行两位管理员的并发撤权，并检查成员、主体和角色的失效写入。

该阶段覆盖管理员保留和角色分配基本生命周期。权限发布、角色互斥、平台变更审批和 OAuth 尚须单独迁移验收，生产启动选择仍由已具备完整支持的 Provider 决定。

MySQL 新装的 System IAM v12 增加权限定义与角色绑定结构。System 按当前身份、平台或租户上下文、角色有效期和权限状态读取授权投影。产品绑定只能写入内置角色，租户自定义角色仅可绑定可定制权限，创建人须有本租户有效成员身份。权限或绑定变更按既有规则更新相关身份的授权版本。此结构版本不分配生产权限。

### MySQL System OAuth 客户端和服务主体

IAM 版本 5 持久化服务主体和 OAuth 客户端。平台服务主体和租户服务主体均关联相应类型的 Principal。租户服务主体须经同租户成员绑定才能建立，客户端绑定和所有权在创建后保持稳定。存储沿用现有客户端 ID、凭据类型与秘密哈希；服务主体客户端仅允许既有 `client_credentials`、`client_secret_basic` 和 `addp.api` 组合。OAuth 存储接口通过同一模型返回 Fosite 客户端，MySQL 客户端描述符的列表用 JSON 存储，PG 继续读取原生数组。

现有 IAM 实库门禁验证有效客户端解析、bcrypt 哈希校验、停用拒绝、服务主体与租户所有权匹配，以及不合法的客户端类型、授权范围和绑定变更。完整轮换需与已有 Token 撤销及写审计处于同一事务，会话和审计接通后验证此事务。

### MySQL System Token 会话存储

IAM 版本 6 迁移 Token 家族、访问 Token 和刷新 Token。沿用既有随机凭据的哈希存储、主体授权版本、租户成员与平台 Scope、绝对过期时间及单向撤销。当前 Token 的唯一性使用生成列唯一键实现，刷新后的父子绑定保留在同一事务。OAuth 服务身份沿现有 Fosite Storage 读取数据库时钟及主体事实，保留 `addp.api` 作用域和服务 Token 的有效期。MySQL 的会话到期判断和批量撤销取同一数据库时钟，避免宿主进程发生时钟偏移时使撤销写入早于签发。

复用 IAM 实库门禁验证服务凭据建立 Token 会话、授权版本变化和撤销后的拒绝，并验证刷新链及其事务回滚。浏览器 MFA、授权码、刷新轮换协议、审计和运行时启动需要后续接通与验收。

### MySQL System Access Token 鉴权快照

Access Token 鉴权沿用原仓储联查，在一条查询内取回 Token、家族、主体、成员和租户事实。MySQL 使用当前语句的微秒时间，并从原字段读取 JSON 字符串列表。鉴权快照保留失效 Token 的历史事实，供领域层按数据库时间、撤销时间和主体授权版本判定。

### MySQL System 服务凭据签发、轮换与审计

IAM 版本 7 为 MySQL 补齐只追加的审计日志和敏感字段约束。沿用现有服务凭据配置入口、OAuth Fosite 事务与 AuditWriter。配置同一个秘密值保持幂等。更换秘密在同一事务中更换 bcrypt 哈希、推进主体授权版本、撤销活动 Token 家族并追加一条审计；审计写入失败时一起回滚。运行账号的权限不得包括能够截断和改写审计历史的数据库管理权限。

实库门禁覆盖同一配置值无重复写入、轮换后旧会话失效、审计失败整笔回滚，以及嵌套敏感键拒绝和历史保护。浏览器登录、配置内置客户端与权限目录、正常进程启动仍需后续验收。

### MySQL System 登录 MFA 挑战

System IAM 的登录和升阶挑战绑定用户、主体授权版本、认证方式与过期时间。登录挑战的来源会话为空，升阶挑战绑定来源 Token 家族。MySQL 以 JSON 保存有序的认证方式，失败次数最多为五次。消费挑战、推进 TOTP 计数并写审计沿用同一业务事务。正常登录还需要上下文选择及浏览器会话。

### MySQL 单租户浏览器会话

拥有一个有效租户上下文的用户沿用 System 的直接签发流程。服务在同一事务内写入 Token 家族、访问及刷新 Token、每个已配置模块的资源票据和签发审计。资源票据绑定签发家族与模块，在库中仅保存哈希，同一家族的每个模块同时只允许一张有效票据。家族撤销须在同一事务撤销派生凭据。实库门禁核对正式模块清单的票据、数据库鉴权快照及撤销。多上下文选择、完整权限投影和 Gateway 登录须分别验收。

### MySQL 多租户登录选择

一个用户有多个有效上下文时，System 返回短期选择票据和本次可选的上下文。数据库保存票据哈希、签发时的授权版本、认证方式和选项。消费时沿用同一事务重新检查主体、有效成员或平台角色，签发所选上下文的会话。实库验收覆盖未列入的成员被拒、拒绝后仍可合法选择、成功后重复消费返回冲突。

### MySQL 租户组织与浏览器身份解析

System IAM v13 安装部门、项目组及各自的成员关系。复合外键约束租户边界，同一成员最多有一个有效主部门。System 通过已有浏览器访问令牌读取当前身份、角色权限和组织关系。两种数据库按从根到父节点的顺序返回部门祖先。成员关系变更、部门禁用及项目组关闭沿用授权版本失效规则。

### MySQL 平台机器身份初始化

System IAM 安装版本 14 在 DBA 触发器核验完成后，按同版本新装 PG 的目录初始化 54 个平台服务主体及其 OAuth 客户端，并登记公开客户端 `addp-cli`。机器客户端初始禁用、密钥为空，部署使用原凭据配置流程逐个启用。安装器只创建机器身份已有的平台角色绑定。Meta 运行身份使用 `platform.meta_runtime`，声明发布身份使用 `platform.module_publisher`。`addp-system` 初始没有平台角色绑定。租户成员和租户角色由租户初始化流程负责。

机器身份、权限、角色及绑定与安装完成版本在一个事务内提交。安装失败后保留待完成版本，修正原因后重跑安装入口。已完成版本再次运行时保留现有主体、凭据和授权状态。

System IAM 安装版本 15 补齐租户初始化实际使用的内置角色模板，即初始管理员和 24 个运行身份的租户角色，权限集合与新装 PG 一致。创建模板时租户成员数和租户授权数均不增加。租户初始化由 System 原领域事务完成，按既有名单绑定管理员和运行身份，随后写入初始化状态和审计。发布身份继续只持平台角色。

MySQL 安装版本 16 建立离线三员初始化使用的单行状态表。新装时该表为空。准备阶段保存一次性 Secret 的哈希和有效期，完成时在同一事务清除哈希并记录完成时间。数据库约束保持准备事实不可改、完成状态不可恢复、状态行不可物理删除。安装时只创建三员角色、权限和互斥关系。离线 CLI 使用 DBA 单独授权的临时账号，配置在 `ADDP_MYSQL_BOOTSTRAP_USER` 和 `ADDP_MYSQL_BOOTSTRAP_PASSWORD`，沿用安装目标主机、端口和 TLS 配置。三员凭据由原交互式 CLI 采集，身份、MFA、角色、审计和完成状态在同一事务提交。操作员退出 CLI 后由 DBA 收回临时账号。

安装版本 17 预置其余已核对的 18 个租户内置角色模板，也安装模块声明和租户授权所用的全部已对齐启用权限。该版本共包含 78 个内置角色、497 项启用权限。运行中由租户按成员和作用域分配角色，权限、角色描述及绑定与同版本 PG 一致。授权事务在获取主体及租户锁后读取数据库时钟，用于分配、撤销和有效期判断。实库门禁将 `tenant.data_steward` 分配给普通租户成员，核对其密码登录后取得的扫描权限。`tenant.ai_user` 涉及待单列的 `copilot.sql.execute` 委托差异，继续保留评审状态。

System 模块注册仓储单独记录 MySQL 结构版本 `system_module_registry`。初始路由修订号为 1，模块定义由相应发布身份登记。运行身份随后登记和续租进程实例。节点归属按当前节点允许名单计算；进程指标声明和首次登记的节点身份由数据库约束保护。外部发现按模块独占同一物理连接，发布快照及推进修订号在同一事务内完成。相同快照保留原修订号，断开的旧连接失去发布能力。实库门禁为 `make test-common-mysql-data-protection COMMON_MYSQL_TEST_ARGS='--local-disposable --test platform-system-registry'`。

### MySQL Meta 扫描领取与任务摘要

Meta 的 MySQL 扫描任务迁移使用部署预建的 `meta` database，Worker 在同一 MySQL 实例访问 `common` 执行和事件表。Meta 维护扫描任务表与候选依赖表达式，复用 Common 的领取、租约和事件。在同一事务内领取、写入 `started` 并更新任务摘要；完成时同一事务更新摘要、事件与执行终态。实库门禁覆盖基础扫描完成后深度扫描才可领取，以及同一 `execution_id` 和 attempt 的任务摘要、`started`、`completed` 与终态。

## 根目录环境配置唯一路径

生产 Compose 的 `ADDP_SUPERMAP_WORKFLOW_ENABLED` 属于部署输入，默认 `true`，仅接受 `true` / `false`，由发布准备流程冻结到清单。未提供原生 amd64 SDK 和镜像时，amd64 节点显式设为 `false`，本次不构建、导出或启动 SuperMap；以后提供对应制品后再选择并验收。启用时必须核对 `SUPERMAP_WORKFLOW_PLATFORM` 与目标架构，不能把跨架构模拟或跳过失败计为原生部署通过。变更该选择须先用旧发布标准入口停止，再重新准备发布；不由 System 配置接口下发，也不改变本地开发脚本的 Runtime 选择规则。

- 根目录 `.env.example` 是 ADDP 基础设施和模块进程环境变量的唯一模板；独立 Business 容器使用 `business/.env.example`。
- ADDP 基础设施和模块进程实际配置统一使用根目录 `.env`；生产环境也不使用 `.env.prod` 或其他平行文件。
- 本地 Business 引擎容器由 `business/.env` 独立配置；根 `.env` 不保存 Business PostgreSQL、Business MinIO 的账号和密码。辅助脚本从 `business/.env` 读取这些凭据，容器实际映射端口以 Business Compose 为准；Engine Instance 连接信息由 System 管理。
- 模块进程可以接收容器或启动脚本显式注入的模块配置，但不再维护独立的长期 `.env` 路径。
- 模块代码不得硬编码 `../../.env` 等相对路径，也不得加载 `.env.local` 形成覆盖层；标准启动脚本负责把根 `.env` 注入进程环境。
- `.env` 和任何 Secret 不得提交到 Git；模板中只保留开发默认值、空值或明确的占位值。
- 只有模块连接 owner 持久化存储之前就必须知道的配置才能保留在环境变量中；普通运行配置不得因为读取失败退回环境变量。

`SYSTEM_URL`、`GATEWAY_URL`、`MANAGER_URL`、`META_URL`、`TRANSFER_URL`、`DEVELOP_URL`、`STANDARD_URL` 和 `MODEL_URL` 是部署级模块地址，不是 System 下发配置。本地开发模板使用显式回环地址，容器与生产编排必须覆盖为该部署内的实际地址。Meta Backend 与 Meta Worker 均须注入 `TRANSFER_URL`，生产 Compose 使用 `http://transfer-backend:8083`，用于反查 Transfer 已提交成果回执；不能使用 Meta 容器自己的回环地址。缺失此连接会阻塞产物身份识别、初始授权与自动补扫，即使 Transfer 物理写入已成功。T4 专用 Runner 的仓库外环境文件必须显式提供参与套件的地址；进程乱序套件至少需要前三项，且通用预检拒绝非回环目标。专用 Runner 不得把仓库根 `.env` 作为第二条配置路径。

Catalog 当前使用 `CATALOG_SOURCE_SYNC_INTERVAL`、`CATALOG_PROJECTION_INTERVAL` 和 `CATALOG_RESPONSIBILITY_RECONCILIATION_INTERVAL` 控制进程内后台调度周期，默认分别为 `30s`、`2s` 和 `5m`。责任对账周期只决定 Catalog 何时批量复核 System 主体引用，不改变责任关系或治理任务的事实语义；System 暂时不可达时对账延后，不影响 Catalog Ready。这些变量必须由部署环境在进程启动前确定，不由 System 下发，也不能在运行中形成另一套动态值。

IAM 环境密钥边界：

- ADDP 只签发随机 opaque Token，不签发或解析用户 JWT，因此禁止配置 `JWT_SECRET`。
- 三员账号只能通过离线 IAM Bootstrap 建立；Bootstrap Secret、三员密码、TOTP Secret 和验证码均不得进入环境变量。
- `OAUTH_USER_CODE_PEPPER`、`IAM_MFA_ENCRYPTION_KEY` 和各业务模块独立的 `*_SERVICE_CLIENT_SECRET` 是生产环境必需的 IAM Secret。`SYSTEM_SERVICE_CLIENT_SECRET` 是明确的可选项：用于 System 以独立 `addp-system` Tenant Service 身份读取 Meta 授权边界事实及反查 Catalog 的持久办理依据；未配置不阻断 System Ready 或历史核清，但依赖 Meta 的授权事实／源读取核验返回 `503 authorization_facts_unavailable`，Catalog 新受理返回 `503 fulfillment_capability_unavailable`。不借用其他 Secret，不改变目标批准要求，不推导 Catalog 已退出。
- 全新生产配置生成独立 System Secret；已有配置只校验，缺失时不静默增加或轮换。非空值同样必须为独立的 32–72 字节 Secret。移除配置时，启动 Provisioner 将该 OAuth Client 停用并撤销其旧会话；重新配置走同一凭据路线。Catalog URL 来自 `CATALOG_URL`，不作为 System Ready 探测前置。
- `OAUTH_PREVIOUS_USER_CODE_PEPPER` 只能在受控轮换窗口临时设置，轮换完成后必须删除。
- `ENCRYPTION_KEY` 用于引擎连接信息等平台数据加密，不是 Token 签名密钥，不得与上述 IAM Secret 复用。

AI 推理密钥边界：

- 在线厂商 API Key 或内网模型服务凭据属于 Inference owner 的 Provider Connection credential，不再由 Agent、Copilot、Manager 的环境变量注入。
- Inference 使用部署级 `ENCRYPTION_KEY` 加密凭据；该 Key 仍由部署系统注入，不进入数据库或配置页面。
- 凭据设置和轮换使用专用操作，普通 Provider 更新 API 不接受 credential 字段。
- 任何读取 API 只返回 `configured` 和单调递增 `version`，不得返回明文、掩码值、末尾字符或可复用密钥引用。

## Ontology FalkorDB 部署配置

Ontology Backend 使用 `ONTOLOGY_BACKEND_PORT=8195`、`SYSTEM_URL` 和既有独立 `ONTOLOGY_SERVICE_CLIENT_SECRET`。`INFRA_FALKORDB_ADDRESS` 在宿主开发默认为 `127.0.0.1:16479`，容器部署显式覆盖为 `falkordb:6379`；密码只读取 `INFRA_FALKORDB_PASSWORD`。这些配置在启动前生效，不接受用户 API 修改。

此 Infra FalkorDB 实例是 Ontology 私有依赖，不进入 System Engine 注册，也不复用 Infra Redis。用户单独接入的业务 FalkorDB 由 System Engine 管理，与本实例的端点、凭据和数据隔离。根 `.env` 的 `INFRA_FALKORDB_PASSWORD` 是独立 Secret，必须非空；生产初始化生成随机值，禁止使用模板开发密码或复用 Redis 密码。宿主开发连接首选 `127.0.0.1:16479`，端口冲突时由 Infra 启动入口解析实际端口并注入 `INFRA_FALKORDB_ADDRESS`；容器通过 `falkordb:6379` 连接。不开放 Browser。

`scripts/infra/falkordb.yml` 是正式 Compose 与 disposable T2 共用的服务定义，随现有 Infra 打包路径发布，固定镜像 digest、非零查询预算、线程/查询内存/队列上限和容器资源限制。`/data` 使用独立 `falkordb_data` 卷，采用 RDB 快照；PG 仍是恢复权威，RDB 不能替代发布摘要校验与重建。此单机配置只用于本地开发/受控同机网络，未声明生产 TLS、HA 或灾备认证。

## Business FalkorDB 部署配置

业务 FalkorDB 由 `business/docker-compose.yml` 的 `falkordb` 服务管理，容器为 `business-falkordb`，使用固定 4.20.6 镜像摘要、独立 `falkordb_data` 卷和 Business 网络。`business/.env` 中配置 `BUSINESS_FALKORDB_PORT=6381` 与非空独立 `BUSINESS_FALKORDB_PASSWORD`；端口只绑定回环，首次避让及后续固定复用沿用 Business 端口解析。通过 `business/scripts/start.sh -falkordb` 启动；日常启动不复制 Infra 数据。

用户明确要求查看 Infra 图内容时，可一次性导出 Infra 的 RDB 快照到仓库外私有临时目录，在业务容器首次启动前导入其空数据卷。只能恢复到未启动的全新目标，不覆盖已有业务数据，不共享源数据卷或凭据，不更改 Ontology 的运行连接。复制的是当时的数据副本，后续不自动同步。System 只登记业务实例，由 Graph 的显式目录路径选择具体图；若启用推导字段的全文搜索，由 Graph 在业务副本维护所需索引；源库索引不受影响。

## 平台对象区域部署配置

`ADDP_INFRA_OBJECTSTORE_PROVIDER` 首期仅支持 `minio`；`ADDP_INFRA_OBJECTSTORE_BINDINGS` 为空时逻辑区域映射到同名桶。例外使用逗号分隔的 `区域=物理桶名`，只允许 `standard`、`develop`；未知区域、重复项、空项和非法桶名均拒绝。Develop Notebook 与受管 Jupyter Runtime 在启动时绑定同一 `develop` 区域，默认使用同名桶。Manager 导入及 Manager／Develop 导出中转使用 `manager`，由 Manager、Develop、Transfer Backend／Bounded Worker、Meta 即时识别在启动时绑定。部署须向这些进程提供一致的 `MINIO_ENDPOINT`、`MINIO_ROOT_USER`、`MINIO_ROOT_PASSWORD`、`MINIO_USE_SSL` 和对象选型配置。`manager` 的其他预览和派生产物尚未全部迁移，配置 `manager=其他桶` 会被拒绝。

内部引用采用 `addp-infra://object/<区域>/<相对键>?type=object|prefix`，不含实际桶名或存储产品。升级前暂停相关新提交、排空在途执行，等待旧版本短期导出会话到期并完成原路径清理。Manager 上传记录与 Transfer 任务定义由各自启动迁移转换；完成全部 owner 升级及一致性核对后开放入口。历史执行、审计和授权摘要不改写；定时任务经原入口重新授权后恢复。完整清单见[解耦设计第 4.4 节](../../next/平台数据库与对象存储解耦设计.md#44-manager-导入暂存与导出中转已批准实施)。

平台对象区域以 S3 协议装配 Go 会话。RustFS 平台协议门禁复用 Business 所维护的镜像版本，在门禁独占实例上验证私有桶、写入、范围读取、列表、删除及对象不存在时的错误映射。Standard 的文档生命周期也用同一服务用例在 PostgreSQL＋MinIO 和 PostgreSQL＋RustFS 上验证，RustFS 入口为 `make test-common-rustfs COMMON_RUSTFS_TEST_ARGS="--test platform-standard"`，需按标准门禁设置 PostgreSQL 测试连接。Manager 和 Develop 导出共用同一套 PG＋S3 生命周期用例，RustFS 入口为 `make test-common-rustfs COMMON_RUSTFS_TEST_ARGS="--test platform-export"`。核对 CSV 下载、租户和用户隔离、保护失效及过期清理。Worker 调度和 Gateway 身份链路另做 HTTP 验收。待部署建桶、Python 和所有平台桶读写及清理入口核齐后，再开放生产 RustFS 选型。

## Standard 文档文件部署配置

Standard 请求逻辑区域 `standard`。平台对象存储选型 `ADDP_INFRA_OBJECTSTORE_PROVIDER` 默认且仅支持 `minio`。可选部署映射 `ADDP_INFRA_OBJECTSTORE_BINDINGS` 为空时使用同名桶。仅允许 `standard` 和 `develop` 的映射项，例如 `standard=project-a-standard-docs,develop=project-a-notebooks`。一项也是同一语法，不设置模块专属桶变量。Infra 初始化与 Standard Backend 启动时读取同一配置，文档读写、后台文件清理与租户物理清理共用绑定。改绑已有区域前需将仍被引用或待清理的对象按原键准备到目标桶。仅修改映射不会移动数据。

以下参数控制文档文件大小与存储操作超时。

```bash
# 单个文档文件最大字节数，默认 100 MiB。
STANDARD_DOCUMENT_MAX_FILE_SIZE=104857600

# 单次 MinIO 上传、预检、下载或删除操作的超时。
STANDARD_DOCUMENT_STORAGE_TIMEOUT=30s
```

上传采用唯一对象 Key；数据库成功切换 `standard.document_revisions.file_key` 后，旧对象进入 `standard.document_file_cleanups` 持久化补偿队列。该队列只记录已经失效且等待物理删除的对象，不是文件引用的第二事实源。

## 模块运行节点标识

`ADDP_HOST_NODE_ID` 是可选的稳定节点 UUID，由 Platform User 通过 System 节点台账 API 创建后配置。单节点 Compose 将它传入各模块；多节点编排必须为每个进程注入所属节点 ID，Docker Desktop 的 Linux VM 使用独立虚拟节点。Go/Python 共享登记只接受显式 UUID，不从名称/IP/容器主机名计算或自动创建；非法环境值仅输出 `host_node_id_invalid` 安全诊断并省略声明，不中断登记或业务 Ready。未配置表示未关联。

System 从已验证服务身份取得登记 Client ID，以节点当前 `allowed_module_bindings` 校验 Client/模块对。节点未知、禁用或不允许该来源时，登记和心跳仍正常，关联投影为 rejected；节点声明第一次登记即固定，同 instance_id 恢复不能补填或改挂，迁移或首次新增声明需新进程实例。配置修改在下次进程启动生效，部署前应先创建节点并明确允许对应 Client/模块。System 节点 API 不执行 SSH、修改防火墙或直接采集主机指标。Monitor 已提供主机采集配置、认证发现和资源查询；指标来源由 Infra 独立部署，节点登记或绑定不代表采集已成功。身份与绑定规则见[平台运行观测规范 4.1](../addp平台运行观测规范.md#41-主机与服务绑定)，采集与发现规则见[4.3](../addp平台运行观测规范.md#43-采集目标与认证发现)。

`ADDP_HOST_NODE_IPS` 是逗号分隔的宿主节点 IP 列表，由部署明确指定，不从服务 URL、DNS、容器主机名或客户端连接推断。只接受不带端口、网段或 zone 的 IPv4/IPv6 字面地址；登记时规范化并去重，IPv4 映射 IPv6 统一为 IPv4。未配置登记为空数组，非法配置不能静默丢弃。它仅用于观测，不改变 `SERVICE_HOST` 或 Gateway 转发地址。地址变化后通过正常重新登记更新，已有离线记录保留原值。

System 的模块登记请求与实例响应统一使用 `host_node_ips: string[]`。平台实例查询新增 `node_ip`，按规范化后的 IP 在集合中精确匹配，并与其他条件取交集；非法 IP 返回 400。页面在运行节点中显示该集合，提供独立的宿主节点 IP 查询框，沿用文本防抖查询和 URL 状态恢复。

`ADDP_HOST_NODE_NAME` 是可选的部署参数，用于向 System 登记进程所在宿主节点。多节点部署必须由编排为每个进程注入实际所属节点名；单节点 Compose 从根环境配置传入。容器内的自动 `runtime_hostname` 仅表示运行环境，不能替代宿主节点名。本地开发未配置时，仍能通过自动采集的运行环境主机名定位本机；宿主节点字段保持空值。该参数不影响服务端点、路由、Ready 或健康租约。

本地开发需要按宿主节点查询模块实例时，在根 `.env` 显式填写 `ADDP_HOST_NODE_NAME=<本机节点名>`，由标准启动、重启脚本导出给 Backend、Worker、Gateway 和 Python 模块。macOS 可先用 `scutil --get LocalHostName` 核对本机名称；不要将通用的 `localhost` 用作区分不同机器的节点标识。配置在进程下次启动时生效，已有离线记录保留原登记信息。

## 平台审计归档配置

MySQL 新装默认关闭长期审计归档。System 的事务审计写入仍为必需。启用 binlog 采集前，部署方须明确接受采集身份能读取实例级复制流的范围，并由 DBA 给独立采集账号单独授权。归档器只选取审计表写入受保护对象，表过滤无法收窄数据库授予的复制权限。System、Worker 和结构安装账号均不继承这项授权。MySQL 归档开放还须验证同一快照基线、提交顺序、断点恢复和对象版本保留。[MySQL 8.0 复制权限级别](https://dev.mysql.com/doc/refman/8.0/en/grant.html)

System 的 `addp-audit-archive` 复用 Infra 对象存储的平台管理桶，推荐现有 `system` 桶，固定写入 `audit/` 区域；不要求独立虚拟机或日志接收端 B。采集／审计两类私有文件与权限分离，目标必须 HTTPS，来源 PostgreSQL 必须完整服务端证书校验；不复用 `POSTGRES_*`、共享 MinIO root 或模块凭据，不从根 `.env` 自动加载秘密。保留天数、来源 UUID、复制槽／publication、平台桶由批准的部署配置固定，默认不启用、不创建或改造桶、不分发角色。只读 `check-store` 检查版本和 Object Lock 状态，失败不自动修改现场；平台桶其他对象不套用审计对象的20年保护。配置字段、命令和标准验证以 [System 平台审计归档](../../../system/README.md#平台审计归档) 为唯一入口，三员／密钥／访问日志及最高 Infra 管理员信任边界见 [审计表契约](../../../system/docs/tables/audit_logs表.md#八平台审计归档部署契约)。
