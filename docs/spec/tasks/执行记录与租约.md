## 执行记录规范

`common.task_executions` 只保存 execution，不保存任务定义和调度定义。

目标字段语义：

| 字段 | 类型建议 | 说明 |
| --- | --- | --- |
| `id` | bigint | 执行记录自增 ID |
| `execution_id` | string | UUID，全局唯一，跨模块追踪 |
| `tenant_id` | integer | 租户 ID |
| `module` | string | 执行 owner 模块 |
| `task_type` | string | owner 模块内稳定任务类型 |
| `source` | string | 本次执行由哪个模块或入口触发 |
| `source_task_id` | string | owner 模块任务定义 ID；一次性执行可为空 |
| `source_task_name` | string | 任务名称冗余，用于展示 |
| `parent_execution_id` | string | 父 execution UUID，主要用于编排子步骤 |
| `status` | string | 执行状态 |
| `progress` | integer | 0 到 100 |
| `current_step` | string | 当前步骤描述 |
| `trigger_type` | string | `manual`、`scheduled` 或 `event` |
| `triggered_by` | integer | 触发用户 |
| `execution_config` | jsonb | 本次执行快照配置 |
| `metadata` | jsonb | 结果摘要、步骤结果、模块扩展信息 |
| `error_details` | jsonb | 错误类型、消息和诊断信息 |
| `lease_token` | UUID | 当前 bounded attempt 不可复用的所有权 token；不对普通业务 API 暴露 |
| `lease_owner` | string | 当前 Worker 实例和槽位的观测身份，不作为唯一 fencing 条件 |
| `lease_expires_at` | timestamp | 当前 bounded attempt 的租约截止时间 |
| `attempt` | integer | 当前 execution 已发生的运行尝试次数 |
| `max_attempts` | integer | 该 execution 允许自动恢复的最大 attempt 数 |
| `started_at` | timestamp | 当前 attempt 的真实开始时间；等待领取的 `pending` 为 null |
| `completed_at` | timestamp | 完成时间 |
| `execution_time_ms` | bigint | 执行耗时 |

## 执行显示语言

`execution_config.display_language` 是执行显示语言的唯一持久事实，取规范码 `zh-cn` 或 `en`，不新增数据库列，也不放入任务模板、业务参数或授权摘要。Develop 执行和进入该链路的 Orchestrator 父、子执行必须在创建 execution 前冻结该字段。

根执行从提交请求经公共 i18n 中间件规范化后的语言冻结；无用户请求的定时或事件根执行使用平台默认 `zh-cn`。等待审批的 workflow.run 在最初提交时将相同语言保存于审批请求快照的 `display_language` 并纳入请求指纹，消费时转入 execution 快照，审批消费不得改用批准人或后续请求的语言。新的人工重跑是新的 execution，重新按本次提交语言冻结；同一 execution 的排队、领取、Worker 重启和安全恢复不得改变语言。

子执行从已验证的同租户、由 `parent_execution_id` 指向的父执行快照继承语言，不接受调用方另传语言覆盖父项。Common 只提供冻结、读取和继承的纯值校验，owner 负责读取父记录、验证来源并创建子执行；公共仓储不反向查询或理解模块任务。

冻结值不可更改；缺失、非字符串或非规范语言码均拒绝派发，不从当前请求、Worker 环境或查看偏好补值。Worker 必须读取持久快照恢复标准 `context.Context` 中的语言，再交由 Common Provider 通过 `Accept-Language` 发送给 Runtime。Runtime 按提交时的语言生成并保存当次失败文本；后续状态查询的语言不得重新翻译或覆盖已有执行事实。公开观测仍遵守安全投影，不因语言贯通而暴露 Runtime 原始响应、凭据或内部错误详情。

最小验证：Common 的规范化、冻结不可变及同租户父子继承测试；Develop 的提交、审批、持久快照重新加载、Worker 派发和相反查看语言回归。沿用 `make test-go` 和 `make test-develop-postgres`，真实低磁盘双语链路由既有专项 Hosted 验收确认，确定性测试不冒充 T4。

## 执行追踪的私有关联

2026-10-23 用户确认首接 Orchestrator → Develop bounded query 的短阶段追踪。业务身份、父子关系、attempt、租约、状态和总耗时仍以 execution 为准；追踪为可选技术观测，不参与执行准入、所有权裁决或恢复决策。缺失、非法、关闭或导出失败不能阻断业务，不由请求 payload 补造引用。

唯一纯值类型归 `common/execution/observability`，只校验引用，不依赖父 execution、HTTP、数据库或 IAM；父 execution 提供持久 map 的 copy-on-write 辅助，`common/httptrace` 复用纯值子包创建实际 Span，避免父 execution 经认证 Client 对 httptrace 的循环依赖。引用固定六字段 `trace_id/span_id/module_name/role/instance_id/started_at`，ID 为合法非零规范十六进制，开始时刻为真实 UTC RFC3339Nano。无 Tenant、User、SQL、参数、结果或业务 execution UUID。

`execution_config.observability` 唯一格式为 `{"schema":"addp.execution-trace/v1","enqueue":<引用>}`，入队事务内冻结真实 enqueue Span，不可改写。`metadata.observability` 唯一格式为 `{"schema":"addp.execution-trace/v1","latest":<引用>}`，只保留最新一个阶段；观测引用自身的更新不得清除其他业务 metadata；业务终态显式替换业务 metadata 时仍沿 owner 原替换／清空语义，仅保留权威私有观测 namespace，不将旧 outputs 或 result 永久合并。不保存无限阶段历史。Owner 创建快照前剥离用户输入中的保留观测键；后续只接受权威记录和 SDK 生成引用，未知字段、重复键、畸形或过大引用不得覆盖已有观测事实。未接入的 execution 缺键为正常情况，不反填旧记录，也不从进程当前请求猜测入口。

引用与所描述状态在同一原有 owner 事务／租约围栏内持久，最外层事务提交后才结束成功阶段；提交失败或租约拒绝用 `rejected` 表达阶段动作未提交，不伪造任务失败。有效恢复只沿原有 expired fencing 推进，不能借追踪放宽 attempt 或租约。enqueue 的 attempt 为 0；其余阶段必须使用真实 attempt ≥1，无租约历史修复不伪造领取。公开 `Observation` 继续显式白名单，配置与私有观测 namespace 不向 Tenant 输出。

短阶段检查点日志可用规范 execution UUID 作为平台日志正文关联键，仅附固定 phase／attempt／outcome；不得向 Span／索引／Tenant DTO 扩散 UUID 或执行配置。日志与原阶段结束共用幂等结果，成功仍以后端最外层事务提交为准。

阶段、属性、采样及平台查询契约见[运行观测规范 6.5](../addp平台运行观测规范.md#执行短阶段与-trace-link第三批)。

## 记录关联与状态推进

约束：

1. `source_task_id` 是字符串软引用。数值型任务 ID 应按十进制字符串写入。
2. `source_task_id` 不建立跨 schema DB 外键。
3. 查询任务定义时必须按 `module + task_type + source_task_id` 路由到 owner 模块。
4. ad-hoc execution 可以没有 `source_task_id`，但必须在 `execution_config` 中保存本次执行所需的完整配置快照。
5. Orchestrator 子步骤 execution 必须写 `parent_execution_id`。
6. execution 完成后不得再被重用；重试必须创建新的 execution。
7. `pending` 表示 execution 首次创建或允许安全恢复后等待 worker、runner 或 runtime claim，`started_at` 必须为空；恢复排队时清空上一 attempt 的开始时间，`created_at` 仍为 execution 原创建时间，不能冒充执行开始时间。
8. 每次合法 claim 真正开始工作时，必须原子完成 `pending → running` 并写入当前 attempt 的真实 `started_at`，不是 execution 首次开始时间。同一 attempt 内的重复进度或 heartbeat 更新不得覆盖它。
9. `success|failed|timeout|cancelled` 终态必须写 `completed_at`；当前 attempt 有有效 `started_at` 时，按 `completed_at - started_at` 写 `execution_time_ms`。尚未领取或恢复排队期间终止时，不能借用旧 attempt 的开始时间或时长冒充本次运行。失败和超时必须写安全的 `error_details`。
10. owner 若在执行前排队、跨进程投递或等待 lease，既有排队指标仍用 `created_at → started_at`，不能提前写 `started_at` 来隐藏排队时间。该差值针对 execution 原创建时间和当前 attempt 开始时间；自动恢复后可能包含先前 attempt 的运行区间，不等于各 attempt 独立等待时间之和，不据此推导首次启动或跨 attempt 累计运行时长。
11. owner 任务定义上的最近执行摘要或运行状态若随 execution 状态推进，必须与对应 execution 的 claim、`pending → running` 和终态更新分别位于同一数据库事务；不得先推进公共 execution、再单独更新 owner 表，或反向操作。
12. 对已有任务定义发起 execution 时，owner 必须在任务定义行锁保护下检查 active execution，并在同一事务创建唯一 pending execution。重跑还必须在该事务中完成运行材料、待处理结果和任务摘要的重置，不能先重置再进入第二次 claim。
13. 已启动 execution 的取消操作只有在 owner 能定位并中断真实运行体、等待其停止并核清在途外部效果后，由当前合法所有者写入 `cancelled` 终态时才能成功；取消意图已受理不等于已取消。Graph 新持久队列另允许在同一事务锁定 execution、证明 `pending + attempt=0`、从未创建运行体或外部操作并阻断并发 claim 后直接取消：开始时间和运行耗时保持空，不增加 attempt。证据不完整、历史无租约记录或曾启动记录不能走此例外。该 Graph 规则为2026-10-29已确认设计、尚未实施，不改变其他 Owner 的取消契约；具体事务与锁序见[Graph 构建任务](模块任务契约.md#graph-构建任务)。
14. 子 execution 的授权事实只允许三个完整状态：尚无身份血缘和执行授权、仅有完整 `actor_principal_id + actor_tenant_membership_id + issued_authorization_version` 身份血缘、已附加 `execution_authorization_id + authorization_expires_at` 的完整执行授权引用。`common.task_executions` 不复制 Engine Access Scope；精确范围只由 System 的不可变 Execution Authorization 保存和校验，禁止保留会丢失引擎与效果对应关系的 `authorization_effects` 摘要。任意残缺组合必须由数据库约束拒绝。owner 可在创建子 execution 的事务中先固化父执行身份血缘，提交后再由 System 沿 `parent_execution_id` 校验并签发 Execution Authorization。静态资源绑定应在 claim 前完成签发，失败的 pending execution 不得进入 worker；只有资源身份必须由当前 lease attempt 的受控 owner API 动态解析时，worker 才可在 claim 后、任何数据访问前签发，并提交当前 `attempt + lease_token`。System 必须直接校验子 execution 仍为 `running`、attempt/token 精确匹配且租约未过期，将二者固化为不可变授权边界，并在每次授权消费时复核仍为当前租约。owner 只能以同一 lease 条件附加授权；安全恢复为新 attempt 时必须清除子 execution 上一 attempt 的两个授权字段（保留身份血缘）并签发新授权，旧授权保留审计但不再可消费。失败时由当前 lease 收敛为终态。

## Bounded execution 领取、租约和恢复契约

Quality `quality_plan`、Meta `scan`、Transfer `runtime.boundary=bounded`、Develop 全部 `query | workflow | script` bounded execution、Manager bounded execution 和 Model `logical_table_materialization` 必须遵守同一个公共所有权协议：

1. 合法执行方使用 PostgreSQL `FOR UPDATE SKIP LOCKED` 从 `common.task_executions` 领取本模块、task type、可选触发 `source` 和满足本模块授权前置条件的最早 `pending` execution。合法执行方可以是规范明确的独立 Worker，也可以是 owner Backend 内嵌监督器。Develop Query Execution Supervisor 固定领取全部 `module=develop + task_type=query`：`source=develop` 必须在入队前保存完整且未过期的 Execution Authorization 引用，`source=orchestrator` 必须保存完整父执行身份血缘并在 claim 后按当前 lease 派生授权；任何其他 source 或残缺授权状态均由当前 lease 收敛失败。
2. 每次 claim 必须原子完成 `pending → running`、写入当前 attempt 的 `started_at`、递增 `attempt`、生成新的随机 `lease_token` 并写入 `lease_owner + lease_expires_at`。恢复后的 claim 使用新的开始时间，不保留上一 attempt 的 `started_at`；`lease_owner` 只用于观测，不能替代 token。
3. 未取得 claim 的运行体必须 fail-closed；不得执行外部读取、写入、扫描、结果 reconcile 或进度更新。
4. heartbeat、进度和终态写入必须同时匹配 `execution_id + status=running + attempt + lease_token`。租约过期、被新 attempt 接管或 token 不匹配的旧运行体必须停止，且任何迟到写回都必须被拒绝。
5. owner task 最近执行摘要若随 claim、恢复或终态推进，owner 必须在同一个数据库事务中组合公共 execution 条件更新和 owner 私有表更新。公共仓储不反向理解 owner 表。
6. lease 过期只表示当前 attempt 已失去所有权，不自动证明业务可以安全重放。owner 必须按 execution config 和实际提交协议明确本次 execution 是否允许自动恢复；默认不可安全重放。
7. 只有在尚未产生不可逆外部提交，或者 Provider 使用稳定 operation identity、staging、target ledger、CAS/fencing 等协议保证重复尝试可安全吸收时，recovery 才能把同一未终态 execution 返回 `pending`，在该恢复事务中清空 `started_at`，并由下一次 claim 增加 attempt、写入新的开始时间；execution UUID 与 `created_at` 保持不变。
8. 无法证明安全重放、达到 `max_attempts` 或发现外部提交状态不明确时，recovery 必须把原 execution 收敛为带稳定错误原因的 `failed`，不得盲目再次执行。
9. 自动 recovery 复用的是同一未终态 execution；用户或 API 发起 retry 必须创建新的 execution，并显式保存原 execution 关联，不能把 retry 降格为同一 execution 的下一次 attempt。
10. Worker 优雅停机先停止 claim 新 execution，再取消或收敛当前运行体；不能通过清空 lease 冒充业务已经停止。

公共 `common/execution` 只提供 claim、lease token、heartbeat、带所有权条件的更新和过期领取等通用原语。具体 execution 是否可恢复、owner task 摘要事务、外部副作用幂等和提交边界归 owner/Provider 实现；公共层不承诺跨系统 exactly-once。

Graph `kg_build` 与 Cleanup 父子 execution 的公共队列接入为2026-10-29已确认、尚未实施的目标契约，不将其计入上文已接入 Owner 的实现清单。Graph API 仅创建 pending，Backend 内嵌监督器沿同一公共 lease 领取；Graph 失联不自动重放。Graph 私有取消意图、准入关闭及外部效果核清不成为公共状态或另一套队列。公共原语必须允许 Owner 外层事务按[Graph 锁序](模块任务契约.md#graph-事务与锁顺序)组合，并在取得所需锁后、提交前重新核验权威时钟和当前 lease，不能使用等待锁前的时间放行；公共时钟与原语由 Common 主责统一实现，Owner 不复制算法。

Cleanup 由 System 同事务预建父、子 pending，只有对应 Owner 领取和推进子项。父协调恢复仅可重新汇总，不能重置已开始的子项。标准完成回执使用子项类型化 metadata，与终态和可原子提交的 Owner PG 事实一起提交；不新增公共结果表、inbox/outbox 或回执队列，具体权限、截止及保留规则以[Cleanup 正式契约](../addp-cleanup体系规范.md#持久队列与完成回执)为唯一事实源。

Develop 查询在入队前冻结 content、engine_id、timeout 和有效输入；Orchestrator 来源还必须冻结 target_locator 和 write_mode。监督器不得读取可变任务定义。Develop 关系查询写入通过执行契约显式配置固定正式表 `target_locator` 与 `write_mode=overwrite|append`。所有输入和输出必须位于同一 PostgreSQL Engine，输出不得同时作为输入。overwrite 在一个事务内锁定目标、删除旧记录并插入完整计算结果；失败或取消回滚该表写入。append 只追加。多个任务分别提交，不保证跨任务、多表同时可见。

ad-hoc execution 的 `task_type` 仍必须是 owner 模块内稳定的业务执行类型，但稳定 execution type 不等于 TaskProvider task type。只有 owner 已提供可保存的任务定义、标准任务列表 / 详情 / 执行接口并允许 Orchestrator 引用时，才能把该类型加入 `task_capabilities[]`。

### 公共写入入口与权威时间

2026-10-29 已批准 Common 先实施、Graph／Cleanup 随后接入。生产 PostgreSQL 以 `clock_timestamp()` 为唯一墙钟，不使用事务开始时间、进程时间或调用方提供的时间判断所有权。lease 有效条件严格为 `lease_expires_at > now`，相等即过期。取得 execution 与必需 Owner 锁后重新核验，最终条件更新仍检查数据库当前时间，随后立即提交，不插入外部调用或等待；保留调用方附加的领域查询条件。

1. `ClaimNext` 与精确候选领取共用 claim 算法。精确候选同时绑定 UUID、Tenant、module、task type、source，不得在持父／领域锁后改选另一条 execution。Common 生成 started_at、attempt、新 token 和到期时间，提交后才启动运行体；Cleanup 在 P→C→领域锁后核对固定 deadline 及父协调 lease。
2. claim／过期发现不接受调用方时钟；续租接收正租期，由 Common 生成到期。完成／过期失败／重排队不接受调用方完成时刻或耗时。SQLite 单元夹具可设置初始数据库事实，不通过生产 API 注入假时间。
3. 过程／完成负载封闭为 `progress/current_step/rows_affected/records_read/records_written/bytes_read/bytes_written/error_details/metadata`，未知字段拒绝，原 map 不被改写。身份、来源、关系、冻结配置、全部生命周期时间、attempt、lease、授权引用只能由专用入口维护。私有观测 namespace 按既有规范保留；Cleanup receipt 仅经类型化完成协议写入，普通 metadata 更新不能注入或替换。
4. 完成与过期失败从持久 started_at 生成 completed_at 和当前 attempt 时长，清空 lease；缺开始事实不造时长。恢复 pending 清空 started_at、completed_at、execution_time_ms 与 lease，保持 UUID／created_at。业务计数／结果重置由 Owner 在同事务明确决定，不一律清空。
5. 授权附加与动态 attempt 授权清理使用独立条件入口，保留现行 System 签发／身份血缘边界。Graph 首次 pending 取消与 Cleanup 未领取拒绝各有严格前置证明，不开放任意无 lease 终结，不伪造 attempt／事件／回执。
6. continuous 仍由 Owner runtime 裁决，经显式受控适配维护公共事实；不能从上下文缺 bounded lease 推断写权。实际消费者迁移完毕后删除通用 Save、无条件状态写入及隐式 fallback，不保留兼容包装或双轨生产路径。

Transfer continuous 的后续 Schema Change 审批与 Meta 扫描来源沿既有 `AppliedSchemaChangeScanOrigin` 契约维护。它是 Owner 专业事实的目的限定发布，不是 execution 重新运行：只能由已锁定真实审批／扫描 claim 的 Owner，经类型化专用入口维护该来源及对应安全投影；首次持续任务的目标扫描沿已锁定的task scan claim发布其专用投影，不能借扫描提交更新其他公共事实；保留原终态、开始／完成／耗时、execution actor、其余 metadata 与观测 namespace，不允许修改 Cleanup receipt。不得用通用进度写入或缺少 bounded lease 推导该权限；Meta 继续核验原有请求、目标、审批人来源及当前扫描 claim 绑定，不增加旧格式或新 HTTP 旁路。

最小验证：封闭字段及原 map 不变、真实 PG 双连接唯一领取、等待锁跨 lease 到期、错 Tenant／owner／attempt／token 和 continuous 边界拒绝、完成时长、恢复重新领取及旧实例拒绝、Owner 私有事实／事件整体回滚。新增 `TestExecutionLifecycleAgainstPostgres` 沿 Common PG 标准门禁运行，SQLite 不代替并发证据。

### Cleanup父子准入组合（已确认设计，未实施）

2026-10-29父关闭／子领取细则已获用户确认、未实施，唯一状态与锁序见[Cleanup父子协议](../addp-cleanup体系规范.md#父关闭与子领取协议)。仅适用于合法 `system/cleanup → Owner/cleanup_executor`，不改变普通父子execution的授权或取消规则。候选发现不加锁，真正领取按父P→精确子C→必需Owner锁组合；System关闭只取P，已领取子结果路径不反向取P。Common须支持在外层事务中对同一精确候选执行公共claim，不能让现有先锁子项的 `ClaimNext` 绕过父条件，也不能为Cleanup复制token／attempt／时钟算法。所有必需锁取得后重新核验权威时间，父未到固定deadline且仍持有效协调lease才可准入。

永久关闭下未领取子项的拒绝是另一条有严格前置证明的 `pending→failed` 条件转换：仅Owner、attempt0、无开始／耗时／lease和运行效果，父子可信绑定完整；不claim、不增加attempt、不生成运行lease或cleanup执行回执。它不是任意 `UpdateFields`、`CompleteWithLease` 的无lease替代路径，也不允许把曾运行后恢复的pending当作从未启动。Common提供中性事务原语与保护字段校验，System负责父事实，Owner证明未运行并提交固定安全拒绝原因；具体规则不在本节复制。暂时无父lease不等于永久关闭，子已运行则仍走自身lease／失联围栏。

## 执行状态枚举

只允许以下状态：

| 状态 | 说明 |
| --- | --- |
| `pending` | 已创建，等待运行 |
| `running` | 正在运行 |
| `success` | 成功完成 |
| `failed` | 失败完成 |
| `timeout` | 超时结束 |
| `cancelled` | 被取消 |

不得使用 `completed` 表达执行成功。

## 触发类型和来源

`trigger_type` 只允许：

| 触发类型 | 说明 |
| --- | --- |
| `manual` | 用户、API、Console、Orchestrator 或其他模块显式触发一次执行 |
| `scheduled` | owner 模块调度器按计划触发 |
| `event` | owner 或平台生命周期事件触发；当前用于 System cleanup 等事件驱动运维执行 |

`source` 记录触发来源模块或入口，例如：

| source | 说明 |
| --- | --- |
| `console` | Console 触发 |
| `meta` | Meta 自身触发 |
| `manager` | Manager 触发 |
| `transfer` | Transfer 触发 |
| `develop` | Develop 触发 |
| `orchestrator` | Orchestrator 触发 |
| `system` | System 生命周期或内部动作触发 |

约束：

1. `orchestrator`、`api`、`retry`、`system_immediate` 不得进入 `trigger_type`。
2. 编排触发下游任务时，`source=orchestrator`，`trigger_type` 仍为 `manual` 或 `scheduled`。
3. 重试来源应进入 `metadata` 或后续专门重试关联字段，不得扩展 `trigger_type`。
4. `event` 只表达真实事件触发，不得用来代替 `source`，也不得把普通 API 调用、重试或即时执行伪装成事件。
