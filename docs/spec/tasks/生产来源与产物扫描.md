## 生产执行与后台扫描的来源

执行来源描述真实触发模块、直接因果关联与发起 User 主体事实。来源不授予数据访问、执行或子执行读取权限。普通人工执行、持续同步的人工启动和人工恢复均从本次已验证 User AuthContext 固化 `triggered_by`、`actor_principal_id`、`actor_tenant_membership_id`、`issued_authorization_version`，四项必须完整且发起人与 Principal 一致；不得使用任务创建者或客户端自报字段补充来源。Common 只负责共同事实校验与复制，领域模块继续拥有状态、产物与读取裁决。

Transfer 编排子执行复用 Common 父执行核验，在创建事务中继承完整来源。持续同步自动恢复在已锁定的同租户、同任务上一轮 execution 上核验来源，保留 `retry_of_execution_id` 与恢复原因，并复制上述四项事实；不复制执行授权 ID、有效期或 lease，不把自动恢复伪装为新的人工操作。人工恢复则使用本次操作者。缺失或矛盾来源不能通过猜测身份补齐，也不回填历史记录。

Manager 导入在同步 User 请求内向 Transfer 创建并启动持久同步任务：入口先检查 `manager.data_item.create`、`transfer.task.create` 和 `transfer.task.execute`，再执行文件写入；只在当前调用栈转发用户 Bearer，由 Transfer 独立认证及授权。不得使用 Manager Service Principal 代替操作者，不保存用户凭据、不在后台续用凭据，也不跟随携带凭据的重定向。

导入暂存文件按上传者私有。Manager 在全部组件上传成功后保存不可变的 `upload_uuid + tenant_id + uploader_id + source_locator`，创建 Transfer 任务后只允许从未绑定状态原子绑定一次 `transfer_task_id`，绑定成功后才能启动任务。用户请求不能自报上传者，不保存 User Token。来源事实与持久导入任务的暂存文件使用同一生命周期，不引入短期导出会话语义。

Transfer 读取 Infra 导入来源前，必须持有当前 bounded lease，从同租户 running sync execution 核验完整 User 来源和真实任务 ID，再用 `addp-transfer` Tenant Service Client、`manager.import_provenance.read` 调用 Manager `POST /runtime/import-sources/verify`。Manager 严格匹配 Tenant、上传者 Principal、绑定任务和完整 source locator；未绑定、未知、其他上传者、跨租户或来源不符均拒绝。Transfer 核对响应与当前请求一致后，仍通过原有通用 content／format reader 读取；业务引擎来源继续执行 Security 保护，不把 Infra 定位符交给业务 ResourceLocator 解析器。该核验不签发 Engine Grant、不返回文件或凭据，也不代替目标引擎写入授权。其他用户可以具备任务操作权限，但不能借此读取原上传者的暂存来源。

Infra 文件的即时元数据识别也属于来源读取。Meta `POST /inspect` 仅允许持有 `meta.inspect.execute` 的 `addp-transfer` Tenant Service 调用，Transfer 必须在调用前完成上述执行身份和 Manager Owner 核验。该 Permission 只授予 `tenant.transfer_runtime`，不可委托、不可租户定制，Scope 仅为 Tenant；普通 User、第三方 OAuth 和其他 Service 均不能直接识别 Infra 文件。存量普通角色及租户自定义角色的该项授权必须清除并推进受影响主体的授权版本，不保留用户读取旁路。

后台产物扫描须核验真实已保存产物及其来源。结构变更扫描的来源关联本次经审批并实际应用的变更事实，独立于最初启动同步的用户，不制造父执行。扫描 `source` 统一使用 `develop`、`transfer`、`manager` 模块名，具体产物类型由已核验的来源事实决定，不使用附加类型后缀。用户同步请求可无父执行；后台 Service 提交必须有可验证的父执行或已应用结构审批事实，缺失来源必须拒绝。Transfer bounded 先在当前执行租约内保存实际输出与实际内容引用，再提交直接父执行 UUID；Meta 核对同租户 running sync 执行、完整主体和精确输出，不从任务配置推断产物。扫描失败保存明确反馈，不回滚已经写入的产物。

结构审批补扫通过既有 Meta 手动扫描入口提交 `source=transfer` 与 `schema_change_source={execution_id,request_id,claim_token}`，与 `parent_execution_id` 互斥。这里的 execution 只定位触发结构阻塞的历史记录，不是补扫父执行。Transfer 在审批实际应用的同一事务中，将审批请求、task/generation/revision、实际目标表 locator、应用时间及本次审批 User 的完整来源保存为 Common execution 私有 `metadata.schema_change_scan_origin`；原执行来源保持不变。既有 `metadata.continuous.schema_change` 继续只投影安全状态，不能泄漏审批主体、claim token 或授权。

Transfer 在既有扫描 claim 状态变化事务中同步这份来源的 claim token、attempt 和期限。Meta 仅允许 `addp-transfer` 提交该来源，在扫描创建事务内锁定同租户 Transfer continuous sync 的结构阻塞历史记录，核验已应用请求及 revision、完整审批主体、有效且匹配的 claim、唯一精确目标表和 `deep + force`，然后只复制审批来源并记录结构审批关联，不复制旧执行身份、授权或 lease，不设置父 execution。缺失事实、过期 claim、错 Tenant、错请求、父范围或额外目标均拒绝；Meta 不跨读 Transfer 私有表。重复审批及 claim 接管仍由 Transfer 原有单一路径裁决，扫描反馈失败不回滚已经应用的结构变更。

持续同步初次扫描在实际目标结构准备完成后，由 Transfer 在当前私有 runtime lease 的 fencing 校验事务内保存目标 locator 和当前 execution 关联，再携带该父 execution 提交。Meta 只读取 Common 中的已保存来源及 running 状态，不跨读 Transfer 私有租约表。Manager 矢量瓦片集同样在当前 Common lease 内保存实际 PMTiles 路径和 attempt，再按精确文件内容引用提交；它不使用 mosaic 的 whole 回执与完成语义。

## Develop 产物自动扫描的执行归属

Develop 工作流生成实际产物后，先在本次 running workflow execution 的 `metadata.outputs` 保存标准产物 ResourceLocator，再通过既有 Meta 手动扫描入口提交 `source=develop` 与 `parent_execution_id`。该后台产物归属请求只允许具有 `meta.scan_task.execute` 的 `addp-develop` Service Principal 提交；User、其他服务和缺少父执行的请求不得声明该父子产物关系。

Meta 必须在创建子 execution 的同一事务中读取并锁定同 Tenant、`module=develop`、`task_type=workflow`、running 状态的父 execution，核验完整且正数的 Principal、Membership、授权版本和一致的 `triggered_by`。扫描请求目标必须精确匹配父 execution 已保存的一个实际产物，不能另行提交引擎全量、目录范围或未声明的内容引用。请求目标绑定与实际扫描规划是两个边界：执行配置保留完整叶子目标，Worker 只解析和扫描该产物及其明确内容引用，不展开到所属 schema／database，也不清理兄弟项或将父范围标为完成。Meta 从父记录继承 `triggered_by` 和三项主体来源事实，保存直接父执行 UUID；不接受客户端自报主体，不复制父 Execution Authorization ID 或授权有效期，不将执行归属当作数据访问授权。专用机器 Permission 保持独立；实际资源访问授权与 Worker 重核由后续 System 契约衔接，不以本期精确扫描替代。

该扫描没有 ScanTask 定义，读取仍遵守 Meta Owner Permission 加本人一次性执行条件；父执行可读不能自动授予 Meta 读取权限。其他 User、跨 Tenant、无主体来源的历史继续不可见，不回填历史身份。自动扫描提交失败只作为工作流产物的扫描反馈，不回滚已生成产物或把成功工作流改为失败。Monitor 复用直接父子关系、Common Observation 与现有事件接口展示该扫描，配置、任意 metadata 和执行授权信息不得进入通用诊断响应。

## Manager 栅格 mosaic 产物自动扫描的执行归属

Manager 产物扫描统一使用 `source=manager`。`manager/raster_mosaic_generation` 的普通用户提交时由 Manager 从已验证的当前 User AuthContext 固化 Principal、Tenant Membership、授权版本和一致的 `triggered_by`；TaskProvider 继续沿已验证的 Orchestrator 父执行继承，不接受客户端自报主体。Runtime 实际生成成功后，Manager 在当前有效 lease 下先持久化产物事实及 `metadata.produced_target`（`engine_id/catalog_path/manifest_ref/attempt`），再经现有 Meta 手动扫描接口携带直接父 execution UUID 提交。该事实仅描述本次生成成功的 dataset 根和 manifest，不是任务定义中的预期产物或新的授权。

Meta 仅接受有 `meta.scan_task.execute` 的 `addp-manager` Service Principal 提交该后台产物归属请求；在创建事务中锁定同 Tenant、Manager mosaic 类型、running 且 lease 有效的父执行，核验完整主体、产物 attempt 与父执行一致、实际 manifest 及请求的唯一目录精确匹配。请求固定 `deep + force`，不得追加 targets、ref_groups、node/item 或其他目录，不扩大到父目录或其他产物。继承发起人与直接父 UUID，不复制执行授权或租约凭据。子扫描无任务定义，用户读取仍需 Meta Owner 读取权限及本人一次性执行归属；父执行读取权不传递给子扫描，既有无主体历史不回填。该契约不替代后续源数据访问授权及 Worker 重核。

mosaic 父执行在原 lease、执行槽位和超时内等待上述子扫描完成。Meta 在扫描成功收尾时，从本次已扫描的精确 dataset 根 whole DataItem 生成正式资源树 locator，并与扫描终态一并保存身份回执；manifest 仅为 primary content，Runtime 的 GDAL 物理路径仅作私有事实。Manager 持久保存子扫描关联后，通过 `GET /runtime/mosaic-scans/{execution_id}/result?parent_execution_id=...` 读取回执，取得实际 whole 身份并写入唯一输出血缘后才成功，执行耗时包含扫描等待。读取仅接受 `addp-manager` 和既有 `meta.scan_task.execute`，重新核对同 Tenant、当前有效父执行/attempt、精确目标、专用来源和直接父子关联；不开放通用执行读取或 TaskProvider 权限。响应闭合为扫描 UUID、父 UUID、状态和成功时的 locator/item ID/fingerprint，不包含执行配置、metadata、凭据、授权、lease 或原始错误。扫描失败、依赖读取失败或超时使父执行明确失败/超时，保留已生成物理文件及子扫描关联，不自动重放、不承诺子扫描已停止，也不在终态后后台补写血缘。其他 Manager 任务不改变成功条件。

## `lineage_facts` 执行结果契约

当一次 execution 实际读取、写入或发布了可治理的数据资源时，真实读写 owner 必须在 `metadata` 的结果结构中写入 `lineage_facts`。该字段使用版本化结构，统一记录 `inputs`、`outputs`、`operations`、运行时执行引用和 Meta scan 引用；资源身份使用标准 ResourceLocator，并在可用时携带 item fingerprint。完整字段和关系语义见 [数据血缘能力规范](../addp数据血缘能力规范.md) 中的“统一执行事实”。

约束如下：

1. Runtime 只返回节点、端口和运行摘要，不构造 ADDP locator、Meta item 或 Asset 身份。
2. owner 负责把实际资源绑定、`produced_targets`、写入模式和成功提交事实写入 `lineage_facts`；失败或取消不能伪造成功关系。
3. Meta collector 以 `lineage_facts` 为输入，解析并保存关系证据和当前投影；它不解析各模块私有 metadata，也不反向抓取 Runtime 状态。
4. Orchestrator 只通过 `parent_execution_id` 提供父子执行上下文，不重复生成 data item 之间的关系。
5. `lineage_facts` 不得包含连接凭据、Token、临时挂载路径或完整大对象。

## 血缘采集通知

当 owner 成功完成 execution 结果持久化后，应立即通知 Meta 采集该 execution 的血缘事实：

```http
POST /api/v1/meta/lineage/executions/{execution_id}/collect
```

该接口由 Meta 提供，仅接受对应 owner 的 Service Principal；Develop 使用 `addp-develop`，并要求 `meta.lineage.create` Permission。通知必须发生在成功状态和 `lineage_facts` 已写入 `common.task_executions` 之后，不能在事实落库前调用。

立即通知与 Meta 周期 collector 必须共同调用同一个 `LineageService.CollectExecution`，不得复制解析或投影逻辑。通知失败不得把已成功 execution 改为失败，周期 collector 负责漏采和失败重试。Item 元数据 refresh 不触发血缘采集。
