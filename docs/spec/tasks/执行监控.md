## Monitor 规范

### 租户执行诊断

执行失败诊断使用同一 `error_details.diagnostic`，契约为 `schema_version=addp.execution-failure/v3`、`stage` 和 `reason`，阶段和原因只接受 Common 声明的闭合枚举。可选 `sql` 仅含 `object={kind,name}` 与 `position={line,column}`；对象类型限 table、column、function、operator，名称只来自 Provider 原生语法树中的标识符，最长 256 个字符／512 UTF-8 字节，禁止控制字符。位置为执行前原查询的 1 起始行号与 UTF-16 列号，符合编辑器坐标。禁止错误全文、Hint／Detail、查询片段、参数值、样本、凭据与其他附加字段。阶段为配置校验、授权、准备、执行或保存结果；原因包括执行配置缺失／无效、查询模板无效、关系参数绑定失败、授权失效、引擎访问失败、语法错误、字段／表不存在、类型不匹配、权限不足、连接失败、超时、取消、资源不足及未进一步分类的执行失败。Owner 根据实际失败边界和已知错误事实生成诊断；Common Observation 同时用于 Monitor 和 Owner 专业响应，仅投影合法诊断。界面由共享组件按中英文固定词条展示失败阶段、具体原因、处理建议、错误码和 execution UUID，不从原始错误拼接文案。未记录当前受控诊断的历史错误继续只展示安全类别和稳定码，不猜测具体原因、不回填历史，不保留旧诊断版本解析路线。

工作流发布目标已存在且 `create` 模式拒绝覆盖时，使用 `stage=result`、`reason=target_exists`，提示更换输出名称或位置；只接受 Runtime 明确的 `TARGET_ALREADY_EXISTS` 终态，不根据自由文本推断，也不推断其他节点没有产出。

数据保护失败沿同一个诊断结构细分原因，不新增自由文本或附加业务字段；Common 从原始错误链中的类型化事实生成受控 reason，Owner 保留实际失败阶段及既有稳定错误码。Develop 和 Transfer 的保护失败使用同一映射，工作台、历史和 Monitor 使用同一共享中英文词条。权限不足和执行授权失效仍使用各自独立原因，不由保护原因推断；无法可靠细分的保护失败仍使用 `data_protection_required`。历史通用诊断不反推、不补写当前原因。

| reason | 必须具备的事实 | 面向用户的处理方向 |
| --- | --- | --- |
| `protection_computed_output_unsupported` | 受保护字段有已证明的派生值输出 | 改为直接读取受保护字段；计算或组合输出暂不支持安全脱敏，原值授权不放行该限制 |
| `protection_lineage_unverified` | Provider 无法证明完整读取集合／输出血缘，或输出被标记 opaque | 使用能验证读取范围和字段来源的操作；无法确认来源时保持拒绝 |
| `protection_role_choice_unavailable` | 显式引用的脱敏方式、当前角色资格或实时结果不可用 | 刷新可选脱敏方式，重新选择并执行；不静默改用默认方式，不等同于数据读取权限不足 |
| `protection_not_ready` | 首次保护同步未完成或目标处于 enrolling | 等待纳管和同步完成；持续未就绪时联系安全管理员 |
| `protection_expired` | 保护规则已经达到有效期截止时间 | 请安全管理员续期或设置长期有效；不提示申请原值权限 |
| `protection_not_yet_valid` | 当前时间尚未到达保护规则生效时间 | 等待生效或请安全管理员核对生效时间 |
| `protection_schema_mismatch` | 当前数据结构／字段指纹与已安装保护规则不匹配 | 更新元数据并重新确认保护规则后重试，不继续使用旧结构交付 |
| `protection_operation_unsupported` | 当前执行路径没有所需字段保护执行器，或 Provider 明确拒绝保护转换 | 改用支持当前保护规则的执行方式，保持源数据和授权规则不变 |

这些原因只细化说明，不改变保护判定、原值授权、源数据权限、查询执行次数、结果保存及错误码。原因不携带字段名、规则 ID、敏感值或底层错误正文；到期后不能因提示细化而交付原值。规则校验仍按既有顺序发生；无法验证的状态不被文案重新解释为到期、权限不足或控制面不可达。

通用未分类执行失败使用 `execution_failed`。表写入诊断新增受控原因 `json_invalid`、`array_invalid`、`bytes_invalid`、`table_write_failed`。可选 `write={column_index,declared_type}` 仅用于前三种值编码错误，列序号从 1 开始，对应本次 Provider 实际写入列顺序（不是源字段下标或数据库全表列号），声明类型分别为 `json|array|bytes`；不公开列名、业务值、原生物理类型或推测的错误行号，不与 `sql` 同时出现。Provider 通过类型化错误保留原因及底层错误链，Owner 不解析自由文本。数据库拒绝无法确定列时只使用 `table_write_failed`，不得猜列。

可选 `target_change_possible=true` 表示 Owner 已进入目标删除、建表准备、替换或非空写入调用，随后执行失败，目标数据或结构可能已改变。只允许真值；未记录该事实表示未知，不能推断未写入。该事实独立于字段编码诊断，也适用于目标准备后发生的源读取、转换或关闭失败。Transfer 在实际副作用调用边界记录，不在纯定义检查或源打开前记录；不从写入计数、失败状态或提交标记缺失推断回滚、提交数量或目标恢复。共享组件展示该风险，复制诊断保留同一提示；沿用当前执行读取 API 和权限，不增加自动重试或清理。

数据脱敏保护校验未通过时，Develop 写入稳定码 `develop.query.protection_required`，受控原因按上表的类型化事实生成；只有无法可靠细分时才使用 `data_protection_required`。无法准备安全读取时使用 `preparation`，查询结果无法安全应用字段规则时使用 `result`。界面按实际原因展示对应建议，不固定提示直接字段读取或规则同步；不得把保护拒绝写成数据项读取权限不足，也不根据自由文本或引擎类型猜测具体原因。拒绝行为及结果不外泄要求不变，原始错误、字段值和保护配置不进入通用诊断。

Develop 查询工作台在结果区持续展示失败诊断；Monitor 详情顶部使用同一组件。Develop 失败面板提供“查看监控错误详情”，使用共享路由构造函数生成原生新标签页链接，保留当前未保存查询和执行结果，不触发离开确认；通过既有 `/monitor/executions?execution_id={execution_id}` 直接打开本次执行的诊断与运行过程，不以任务定义 ID 替代 execution UUID；Monitor 继续按既有读取权限裁决。Develop 查询的领域执行详情按 `/develop/executions/{execution_id}` 打开，包含无任务定义的一次性执行，仍由既有 Owner 读取权限裁决。通用详情不以“打开任务定义”代替领域执行详情。

查询准备阶段的原生语法拒绝、精确目录表／函数解析失败必须按 Provider 的受控错误码展示，并标注准备查询阶段；数据库执行期按保留下来的 SQLSTATE 展示语法、表／字段缺失、字段歧义、函数或运算符不匹配、类型错误及除零等具体原因。分类不解析原始报错文本，不把目录无记录误写为未知执行失败；仍不向通用诊断投影查询正文、业务值、连接信息或自由文本。未被证实的原因继续明确记录为未分类，不猜测对象名或推荐替代表。

对象和位置与错误类型必须匹配。Provider 保留 typed QueryError 上下文，SQL 执行链路不得提前转成字符串；数据库位置必须来自原生结构化 Position，不能解析报错正文。Provider 只对可以精确映射的分页包装及前后空白转换位置；命名参数或关系模板改写后没有源映射时省略位置。Develop 在编译前冻结 `execution_config.inputs.query_source_digest`，仅在 Provider 原查询摘要与冻结摘要相等时保留位置。摘要只用于内部校验，不进入通用诊断；对象名与位置沿同一 Common 安全投影供 Develop 和 Monitor 展示，复制诊断同时包含它们。

关系参数预览编译产物的 `content.query` 为已绑定实际表的只读查询；已消费的 `type=relation` 定义从产物的 `content.query_parameters` 删除，值参数定义保留。原始任务模板不变，完整输入契约和有效资源绑定继续冻结在 `execution_config.inputs`，供导出与血缘消费。Worker 校验并执行这一编译产物，不再把实际表当作未编译的关系参数；编排写入仍校验原模板并按目标编译。

Transfer 专业执行读取同时限定可信 Tenant、`module=transfer` 与 `task_type=sync`。第一方和普通 OAuth User 使用现有 `transfer.task.read`：有定义的历史（含已删除定义）可读，无定义的一次性执行仅发起 User 可读，无主体证据拒绝；详情、进度、事件、任务历史、全局列表及其总数和统计采用同一 SQL 范围。用户读取父执行不授予子执行读取权。模块导出结果仍独立使用已认证 Service Client 与 execution 的 source 精确匹配，且只允许无定义执行；TaskProvider 仍独立使用 `addp-orchestrator` 和 `transfer.task_provider.read`，不套用用户本人规则，两者也必须限定 sync 归属。

Transfer 专业响应采用显式 DTO，保留执行身份、状态、时间和传输计数、Common 安全错误分类、冻结血缘资源与字段映射及结构快照，以及连续同步的分区位点、延迟、检查点健康、捕获恢复观测、恢复退避和结构变化诊断。结构快照不包含字段注释、默认表达式或生成表达式。只展示已声明的专业事实，不返回任意 metadata、原始 checkpoint、SQL／参数／业务样本、完整运行时响应、执行授权引用、fencing／租约或自由文本错误。启动、恢复、回放和重试响应也使用同一投影；模块导出结果另用显式结果 DTO，仅保留身份、状态、安全错误和导出会话所需的 typed `target_refs`。原始持久事实与运行时恢复逻辑不变，专业结果仍由所属模块的授权入口读取。

Manager 用户执行状态查询复用 Owner 已声明的 `manager.derived_artifact.read` 读取范围：可信 Tenant、`module=manager`，类型仅限派生产物及向量化任务；有定义的历史（含已删除定义）可读，一次性执行仅当前发起 User 可读，无主体证据拒绝。`data_profiling` 与 `cleanup_executor` 使用各自的专业或维护入口，不通过派生产物状态入口读取。TaskProvider 状态查询仍由 `addp-orchestrator` Service Client 和 `manager.task_provider.read` 独立授权，同时限定 Manager 已声明的任务类型，不套用用户本人条件。

Manager 专业执行响应使用显式 DTO：执行概览和失败分类复用 Common 安全投影；专业 metadata 只保留向量化和瓦片生成计数、血缘资源身份及操作、Workflow 引擎类型／算子／模式／耗时，以及 GLB 大小、来源格式和 MAX 转换证据（源单位、单位来源、米制比例、导入器版本、贴图引用、源摘要、网格数及静态范围）。血缘保留输入输出端口、Locator、item ID、fingerprint、写入模式、操作 kind/operator 与端口，以及 runtime execution 和 Meta scan 引用；不返回 schema snapshot、字段映射或任意附加字段。不得返回执行配置、访问计划、授权引用、原始 Runtime 响应、command、stdout/stderr、publish 对象、`storage_refs` 等内部存储描述或自由文本错误。专业结果内容仍走已有 Manager 领域结果入口，Monitor 的血缘安全投影不增加 operations 或专业转换证据。此收敛不改变 Owner 权限、持久执行事实、机器 TaskProvider 契约或结果生命周期。

`metadata.workflow_runtime.execution_time_ms` 是 Runtime 返回的毫秒耗时，按工作流接口规范使用 JSON number 并保留小数；可选字段缺失或为 null 时不输出，数值 0 必须保留。它与 Common Observation 的 Owner execution 整数毫秒耗时分别投影，不改写持久历史。

Orchestrator 用户与 TaskProvider 执行读取必须同时限定可信 Tenant、`module=orchestrator` 与 `task_type=orchestration`，编排权限不得读取同模块的 cleanup 执行。用户专业查询在 SQL 中复用 Owner 的任务历史与本人一次性执行范围，缺少发起主体或归属不完整的无定义执行拒绝，列表总数采用相同过滤；合法第一方与普通 OAuth User 沿用现有 workflow.read 权限，TaskProvider 不套用用户本人条件。专业执行详情与单编排历史也必须使用显式安全读取 DTO，不得直接序列化内部 `TaskExecution`。保留执行概览及 `metadata.step_results` 的步骤状态、阶段、时间、耗时、闭合错误码和本地化消息；步骤 `result` 仅投影已记录且规范的子 execution UUID，不传递子任务 outputs、业务结果或完整运行时响应。读取父执行不授予子结果权限，子详情仍经 Monitor/Owner 独立裁决。原始配置、任意 metadata、执行授权事实及自由文本错误不出现在这些响应中；列表与详情采用同一投影，TaskProvider 保持独立安全状态契约。

1. `common.task_executions` 是 execution 状态、错误与结果摘要的唯一事实源。Monitor 只提供显式安全 DTO，禁止序列化整个 TaskExecution；执行配置、原始 metadata、原始查询和参数值、业务样本、Notebook 输出、完整运行时响应、lease/fencing token 和执行授权引用不得进入通用诊断响应。专业结果通过 Owner 页面及其既有授权入口读取。缺少受控消息契约的旧错误只用于归类失败原因，不回显自由文本；稳定错误码及失败目标计数可保留，未知原因明确指向 Owner 领域诊断。
2. Monitor 使用同步 BFF 授权：Tenant Context 和自身 Permission 只是入口条件，Owner 在同一 User 请求内重新核验 AuthContext 并通过唯一 `GET /execution-read-scope` 返回强类型读取范围。规则声明只存在于 Owner；Common 提供范围类型和匹配，不维护任务类型到 Permission 的中央清单。第一版仅接受 Tenant Scope，不声称支持无可信资源归属的 Department/Project Group 隔离。
3. 第一版的 Owner 任务读取 Permission 明确包含本租户该任务类型的执行历史（包括已删除任务定义的历史），不隐含数据结果读取。一次性 execution 仅在 Owner 明确允许且当前发起主体匹配时可读；无主体证据拒绝。父 execution 可读不授予子 execution 读取权。Owner 不可用或授权响应非法时失败关闭；列表、详情、树和执行统计采用相同读取范围。一次同步请求的 Owner 授权共用 5 秒总预算，以最多 4 个并发调用完成；任何必需 Owner 失败或响应非法时取消其余调用，整份请求失败，不返回部分范围、不缓存或跨请求复用授权。
4. 步骤展示复用 Owner 已保存的 `metadata.step_results` 和实际子 execution 身份；只投影步骤标识、状态、时间、耗时、安全错误与子执行引用，不复制步骤 Result。没有证据时显示未记录，不以当前任务定义推断历史；同一 execution 重试后的旧步骤未标注 attempt 时必须提示不能据此认定本次进度；树达到展示预算时必须标识截断。
5. 过程事件使用 PostgreSQL `common.execution_events`，可信 Tenant/module/task type 从 execution 派生。事件按 execution + attempt 关联；bounded 写入校验有效 lease，continuous 写入校验 Owner 既有 fencing。已有文本过程日志替换后删除旧追加路径，不长期双写；已有步骤结果和领域结果不迁入事件表。第一版不接 Alloy/Loki。
6. 过程事件按事件时间保留 30 天（continuous 也滚动清理）。终态概览、步骤摘要及安全错误的目标保留期是 180 天；被领域历史、授权或告警依赖时必须按 Owner 引用约束延长，不能直接删除。概览按同租户父子执行树整体保留，具体边界见[概览保留与清理契约](#概览保留与清理契约)。专业结果、产物与操作审计使用各自生命周期。清理必须走标准维护入口，明确记录过期、截断、清理失败和保留原因；未接入清理前不得宣称保留策略已执行。
7. 分期：第一期完成安全 DTO、Owner 读取裁决、既有步骤与诊断展示；第二期落地有界过程事件、Orchestrator/Transfer/Meta 接入及保留清理；第三期完善专业运行时节点历史和其他 Owner 阶段事件，按实测评估规模。已确认目标契约不代表后续阶段已经实现。
8. 验收覆盖跨租户、同租户无 Owner 权限、父可读子不可读、撤权、一次性执行、已删除任务历史、Owner 不可用、安全投影、状态真实性、分页与截断。新增 PostgreSQL 测试必须确认标准门禁名称筛选命中；新增浏览器回归同步接入根 Makefile 与 CI。真实认证、Gateway、Owner 和 Worker 链路归 T4。现有 Manager 血缘 T4 分别核对 Owner 的完整血缘事实和 Monitor 的安全资源投影，不要求两者完整响应相同；Monitor 不得包含血缘 operations、schema snapshot、专业结果、执行配置或授权引用。

过程事件首个实现切片使用闭合结构：`kind` 为 `started|progress|completed|failed|cancelled|timeout|truncated`，`step_id` 只保存已有步骤身份，`counters` 只接受非负整数进度计数；不接受自由文本消息、参数、业务值、checkpoint 或授权引用。事件时间由写入端生成，Tenant、module、task type 和 attempt 从锁定的 execution 派生。bounded 写入必须在同一事务锁定并验证当前有效 lease（含 owner）；每个 execution + attempt 每 UTC 日最多 1000 条，最后一条为截断标记。读取使用 ID 游标，每页最多 100 条，复用 execution 的 Owner 读取裁决，并返回 30 天保留窗口。事件按写入时间滚动清理；System 的公共存储维护循环分批执行，不删除 execution 概览、步骤结果、专业结果或操作审计。Orchestrator lease 收敛遵循本规范的[编排执行可靠性契约](编排与调度.md#orchestrator-执行可靠性)；概览引用裁决的范围尚待确认，不能借此增加无 lease 写入或直接删除概览的路径。

Transfer continuous 的事件与对应 execution 状态／进展在同一 Infra PostgreSQL 事务提交。Common 只负责锁定 execution、闭合输入、事件时间、每日预算和存储；Transfer 必须先锁定任务、execution 和 Runtime lease，再以 Owner 裁决回调校验 Tenant、transfer/sync、continuous、任务与 execution 归属、owner、fencing token 和锁等待后的有效期，不能套用 bounded lease 或无裁决追加。PostgreSQL 使用锁定后取得的 `clock_timestamp()` 校验有效期，不使用事务开始时间。首次 claim 统一写入 attempt 1，并记录 started；已有 started_at 且 attempt 为 0 的 continuous 记录通过标准 execution store 迁移规范化为 1；每次恢复创建新的 execution，只有实际 claim 后才记录其 started。提交进展只记录累计 records_read / records_written，不复制 partition、position、业务值或心跳。worker 的 completed / failed / cancelled / timeout 只允许当前有效 Runtime lease；暂停／停止允许当前 owner 完成 cancelled，但禁止继续提交进展。过期或不存在 lease 的遗留 running execution 由持有任务与 execution 锁的 supervisor 记录 failed；错误详情保存稳定 `lease_expired` 码用于安全失败归类，结构阻塞保存 `schema_change_blocked` 码。Kafka record 的确定性 block 失败必须保留已有 `RecordDataError.Code`（解码、字段校验、主键校验或类型转换），Supervisor 只向执行摘要传递该稳定码和安全 Message，不传递 Cause 或外层错误包装文本；通用诊断复用安全错误投影，不新增业务样本或自由文本事件；未领取的 pending 取消仅保留取消概览（attempt 0，没有运行过程）；暂停／停止后的遗留 running 执行由任务 Owner 裁决 cancelled（不自动恢复，任务回到 idle，保留 desired_state），不授权过期 worker 写入。已终止执行不重复追加终态，schema-change 的终态投影修订仍沿既有领域事实，不制造第二次运行。预算耗尽不阻断状态或进展提交，事件存储失败则回滚同事务事实；心跳和诊断采样不追加事件。仍复用同一读取授权与 30 天维护清理，专业结果与操作审计生命周期不变。

Monitor 不拥有任务定义。Monitor 聚合观察：

| 层级 | 来源 | 监控内容 |
| --- | --- | --- |
| execution | `common.task_executions` | 状态、耗时、进度、错误、父子关系 |
| schedule | owner 任务状态 API | 是否启用、下一次运行、最近运行摘要 |
| runtime queue | owner 模块队列状态 API | pending、active、retry、dead、延迟 |
| artifact state | owner 模块状态 API | 产物是否 ready、缓存位置、版本、失败原因 |
| provider health | System TaskProvider / module health / 标准任务列表 endpoint | 模块是否声明 TaskProvider 角色、当前是否可调用、无副作用任务发现 endpoint 是否可访问 |

Monitor 可以查询 owner 模块公开的只读状态 API，但不得直接依赖 owner 私有表结构。provider health 不新增 TaskProvider 专用 health endpoint，应复用模块 `/health/ready` 与标准 `GET /tasks?task_type=` 这类无副作用 endpoint 做探活。

provider health 至少检查以下内容：

| 检查项 | 来源 | 说明 |
| --- | --- | --- |
| registration | System `module_definitions.task_provider` | 模块是否声明 provider 并具备基础 endpoint。 |
| capabilities | System `module_definitions.task_provider.capabilities` | JSON 是否可解析、`schema_version` 是否为 `task.capabilities/v2`、`task_capabilities[]` 是否非空。 |
| backend_health | 每个 `provider.backends[].base_url + /health/ready` | 当前有效端点池中的每个 Backend 实例是否可接受平台工作。 |
| task_discovery | 每个 `provider.backends[].base_url + task_list_endpoint + ?task_type=` | 每个 Backend 实例上、每个未 deprecated task type 的标准任务发现 endpoint 是否可访问，且响应体必须是标准任务列表对象，包含 `items`、`total`、`page`、`page_size`。 |

System 返回 `available=false` 或空 `backends[]` 时，Monitor 直接判定 Provider `down`，不对空地址发起探测；`available=true` 时逐个检查当前端点池，再聚合 Provider 状态。provider health 状态只使用：

| 状态 | 说明 |
| --- | --- |
| `up` | 所有 Backend 实例的全部检查通过。 |
| `degraded` | capabilities 非法，或部分 Backend 实例 / task type 检查失败。 |
| `down` | 没有有效 Backend 租约，或全部 Backend 实例不可访问 / 任务发现全部失败。 |
| `unknown` | 无可检查 task type，或 System 注册信息暂时无法获取。 |

Monitor 探测任务发现时只发送 `GET` 请求，不读取 owner 私有表，不触发执行，不创建 execution。deprecated task type 不作为可用任务类型处理，不进入健康失败统计。

Monitor 必须支持按执行记录查询 parent / child execution 树。树边使用 `common.task_executions.execution_id` 与 `parent_execution_id` 连接。Monitor 只读取 `common.task_executions`，不得回查 owner 私有表拼装树。

cleanup execution 属于系统运维执行记录。Monitor 必须能展示 cleanup 父子 execution 树、scan / execute 关联、触发方式、清理模式、影响记录数、释放空间、错误摘要和各模块结果；但不得提供 Orchestrator 编排入口，也不得把 cleanup 当作 TaskProvider 任务定义处理。cleanup 的正式语义见 [ADDP Cleanup 体系规范](../addp-cleanup体系规范.md)。

| 入口 | 用途 |
| --- | --- |
| `GET /api/v1/monitor/executions/{id}/tree` | 按统一执行记录自增 `id` 查询，适合 Monitor 表格内部跳转 |
| `GET /api/v1/monitor/executions/by-execution-id/{execution_id}/tree` | 按全局 UUID 查询，适合各模块拿到 `execution_id` 后跳转统一监控 |

### 概览保留与清理契约

2026-10-19 已确认概览按父子执行树整体保留。本节规定目标契约；当前有 30 天过程事件维护及下述第一期只读候选评估，180 天概览删除尚未实施，不得将文档确认或只读候选报告计为清理能力已完成。

**物理删除边界**：通用概览是安全读取投影，不是可以独立删除的一份物理记录。`common.task_executions` 同一行还可能保存 Owner 专业小结果、结果摘要、outputs、冻结执行配置或待消费血缘事实；例如 Develop 工作流把受限 `final_result` 保存在 `metadata.result`，专业详情仍从这一行读取。整行删除会同时删除这些领域事实。因此，Owner 裁决必须覆盖该行全部领域数据的释放条件，不能只回答有无外部引用。专业结果到期／释放规则尚未确认时，整树保留；不能擅自给专业结果套用 180 天期限，不能裁剪任意 metadata 来绕过引用，也不为清概览默认引入另一套结果存储。

**尚未生成引用的消费义务**：Monitor 连续任务信号会读取最新根执行，告警规则会读取最新一次或最近 N 次终态根执行；没有 incident 不代表没有计算依赖。Meta 未采集的血缘同样可能尚无 observation。必要 Owner 必须同时裁决这些待消费或当前计算窗口，不能把“没有引用行”汇总为“整行可以删除”。Platform 主机资源告警及平台日志沿独立事实链管理，不因此阻塞任意 Tenant 执行树。

1. **保留单元**：从真实 `parent_execution_id` 关系计算同一 Tenant 的完整父子执行树，不新增树实体或 `group_id`。不能用 Monitor 当前用户可见的子树代替完整保留单元，也不能用今日任务定义重建历史关系。未关联父子执行的记录按单节点树处理。
2. **时间及状态**：终态成员以其实际 `completed_at` 和数据库当前时间判断 180 天窗口；树中任一成员未超期、仍为 pending/running、缺少完成时间、仍持有效 lease 或状态无法认定时，整树保留。清理不能代替 Owner 将活动执行强行改为终态。
3. **领域及待消费依赖**：树中任一执行被当前专业结果、任务最近执行、领域历史、有效授权或告警依赖，或仍有待消费事实，整树保留。执行自身 Owner 及已知跨 Owner 消费者分别依据自己的事实裁决；`source_task_id`、历史执行读取 Permission 或某张表中存在执行 ID 均不能单独代替该裁决。Meta 尚未采集的 `lineage_facts` 属于待消费事实，没有 observation 不能推定为无需保留。
4. **诊断指向**：保留父执行时不能单独清除其子执行，避免步骤中的规范子 execution UUID 失去诊断目标。`retry_of_execution_id` 及已保存的恢复来源属于额外依赖：仍被保留执行依赖的来源继续保留，但不据此把全部重试执行伪装成一棵父子树。已保存子引用与真实父子关系不一致、出现断链、环、跨租户指向或无法解释的旧 JSON 引用时，记录异常并保留，不猜补、重绑或丢弃关系。
5. **有界原子性**：只有树内全部成员超期、终态明确，所有必要 Owner 明确无依赖，且并发新增引用与删除的约束已经闭合时，才允许沿共享维护入口删除。树成员删除须在同一有界事务中全部成功或全部回滚；不能先删叶子并提交、以后再处理父执行。超出维护预算的大树保留并记录原因，不为完成清理而拆成可部分提交的批次。远程只读“允许删除”的结果不能独自消除检查后新增引用的竞态，具体存储约束须随对应 Owner 实现同步验证。
6. **职责及权限**：Common 负责共享执行存储、树关系计算、候选筛选及删除事务；各 Owner 负责专业引用、待消费义务和解除保留条件；System 沿已有公共存储维护生命周期调度，不直接遍历其他 Owner 私有表。Monitor 仍只展示获授权的安全诊断。整树保留不授予整树读取权，父可读而子不可读的授权边界保持逐执行裁决；Owner 不可用、响应非法或引用覆盖未完成时保留，不按无引用处理。
7. **生命周期分离**：整树延长的是概览、步骤摘要与安全错误，不延长 30 天过程事件窗口；事件已过期不代表执行概览可以删除。专业结果、物理产物、操作审计及 System/Loki 平台进程日志不进入该删除事务，也不得为了释放概览引用而被连带清理。Ontology 未完成独立改造与引用契约前不接入实际删除，依赖其裁决的树继续保留。
8. **报告及验收**：只读报告区分未超期、活动执行、时间缺失、领域引用、待消费、Owner 不可用、覆盖不完整、关系异常及预算不足，不能把未知写为可删；通用诊断不输出专业引用内容或授权信息。实现门禁须覆盖跨 Tenant、单节点与多层树、父与子分别被引用、父超期而子未超期、待消费血缘、恢复来源、Owner 失联、异常关系、大树预算、并发新引用及事务回滚，并确认专业结果、审计和平台日志不变。Common/System 与各 Owner 既有标准门禁分别验证自身边界；真实维护运行另计 T4。

#### 第一期只读候选评估

2026-10-24 确认的实施范围仅为 Common 共享存储评估及 System 既有公共维护循环的汇总，不新增用户 API、删除命令、专业结果期限或结果存储。评估使用 PostgreSQL 只读、可重复读事务及数据库时间；只选择 execution 身份、父级、重试／恢复来源、状态、完成时间和租约截止时间，不加载执行配置、专业结果、错误正文或授权引用。每轮按 execution 自增 ID 游标选取种子，向上、向下计算同租户完整树；跨租户边只用于识别异常，不合并租户。

默认每批最多 100 个种子、每树 1000 个成员、累计读取 10000 行和 500 次查询，并受维护 Context 的 15 秒期限约束。完整树在同批去重；跨批可能重复观察同一树，批次计数不得累加解释为全库唯一树数。游标到末尾后从头开始；不持久化第二份树或候选台账。超预算的树只报告已观察数量及不完整，不将其记为完整树或时间候选；剩余种子等待后续维护批次。批次失败不发布部分成功报告。

`age_eligible` 只表示完整树的所有成员均为明确终态、完成时间严格早于数据库当前时间减 180 天，且无尚有效的 execution lease；不是可删除许可。报告始终为只读。首期每棵树固定报告 `owner_release_unverified` 与 `consumer_references_unverified`，表示行内专业事实和跨 Owner 引用／待消费义务未核验；没有实际调用 Owner，不伪造 `owner_unavailable`、无引用、已消费或允许删除结论。已保存的树外重试／恢复引用可额外标识 `execution_reference`，但不把重试链并入父子树；缺失、跨租户、自指或非规范来源身份标记关系异常。没有发现这些有限引用不能消除覆盖未知。

System 仅记录本批种子数、观察成员数、完整树／时间候选数、稳定保留原因计数、游标及预算状态，不记录 execution UUID、Tenant、模块私有内容或引用正文。已有 30 天事件清理保持原有行为，评估失败不阻止事件维护。报告不接入 Monitor 用户读取路径，不授予新的任务或结果权限。

维护前后比对全部执行行及事件的数据库内摘要，包含配置、错误、结果 metadata 和 lease；测试驱动仅从本轮进程输出中提取安全批次汇总，不开放租户读取 System/Loki，不归档原始进程日志、凭据或合成私有内容。超期整树、年轻子执行、运行中、有效 lease、pending／完成时间缺失、跨租户／缺父／自指、retry／recovery 引用均须命中声明结果。所有成功、失败及中断路径销毁本轮应用、Infra、卷与凭据并核验零残留；销毁测试部署不能记为 180 天概览清理。该项不验证 Owner 释放、专业结果期限、操作审计清理、30 天事件物理清理或概览删除；代码与确定性测试就绪不等于真实 T4 通过。标准 runner 回归为 `make test-execution-retention-online-runner`，已纳入 Online 聚合与 Platform CI 注册检查；真实验收只由 `online-t4-gates.yml` 的同名人工选项运行，不登记夜间调度。未知状态受现行数据库 CHECK 约束拒绝，只在 Common 防御单元测试中覆盖，不删除或放宽约束来制造 T4 历史。

### 执行诊断页面与授权失效

Monitor 详情只从 execution 已保存的 `recovered_from_execution_id` 和 `recovery_attempt` 展示恢复来源 UUID 与次数，不从当前任务定义补造历史。共享 `ExecutionSteps` 接收父执行状态；父已终态而步骤仍为 pending/running 时只表示最后记录，waiting 等旧阶段不得解释为当前编排仍在等待。同一 execution 重试后，未标 attempt 的旧步骤继续提示不能认定本次进度。

详情是否刷新依据整棵已授权可见树：父已结束但可见子执行仍 pending/running 时继续，全部可见执行终态才停止；不按私有步骤引用补查隐藏节点。概览、树、步骤、血缘和事件的响应必须匹配当前所选 execution 与详情请求代数，关闭/重新打开、切换身份或路由后，迟到响应不得覆盖新详情。

详情请求、事件请求或树刷新收到 401/403/404，或明确的 `503 execution_owner_unavailable` 时，清空本次详情的概览、树、步骤、血缘和事件并停止刷新；终态执行同样处理。401 沿既有会话失效导航，不强求失效后仍显示重新加载；403/404 与 Owner 不可用沿既有失败/重新加载界面处理。其他服务错误不当作权限拒绝；普通事件传输失败只清空事件，网络恢复后可重新读取。

执行列表遇到同类读取失败时清空旧行与总数。每次查询只接受当前请求代数的响应，迟到失败和成功都不得覆盖新查询。Owner 恢复后沿原查询或重新加载入口重新裁决，不缓存或恢复上一轮授权和旧内容。

### 执行监控前端所有权

Monitor 是跨任务、跨模块执行列表和通用执行详情的唯一前端 owner。业务模块不得在侧边栏、功能搜索或模块首页保留另一套跨任务执行列表、通用执行统计或通用执行详情；需要展示本模块全部 execution 时，必须使用 `common-frontend` 的 `MonitorExecutionsButton` 进入带 `module`、可选 `task_type` 的 Monitor 页面。只有无法使用 Vue 组件的调用点才直接调用底层 `openMonitorExecutions()`。

业务模块前端只保留 owner 领域上下文：

1. 任务定义列表可以展示最近执行摘要，并提供进入本模块筛选后 Monitor 列表的入口。
2. 任务详情可以保留按当前任务过滤的执行历史，以及日志、结果、重试、领域诊断等 owner 特有信息；通用状态、耗时、错误和父子执行树仍以 Monitor 为准。
3. 需要查看某个任务的统一历史时，使用 `openMonitorExecutions({ module, task_type, source_task_id })`；查看单次 execution 时使用 `openMonitorExecution(execution_id)`。
4. 模块领域详情与 Monitor 通用详情不得复制同一交互契约。跨模块稳定的执行状态、时间、进度、错误摘要和 Monitor 导航应由 `common-frontend` 提供共享能力。
5. 模块级全局执行列表被 Monitor 替代后，旧菜单、功能搜索、前端路由和纯列表组件必须删除，不保留重定向或双轨兼容入口。

各 TaskProvider 模块的前端所有权固定如下：

| 模块 | 模块内保留 | 统一到 Monitor |
| --- | --- | --- |
| Transfer | 传输任务定义、单任务执行历史、传输日志与结果详情 | 模块全部执行列表、通用统计 |
| Meta | 扫描任务定义、扫描配置与当前运行反馈 | 跨扫描任务执行列表 |
| Manager | 快显、空间、向量化任务定义与领域结果 | 模块全部执行列表 |
| Develop | 开发任务定义、查询/工作流/脚本执行结果详情 | 模块全部执行列表、通用统计 |
| Orchestrator | 编排定义、单编排执行历史与步骤视图 | 跨编排执行列表 |
| Quality | 质量检查方案、规则通过率和规则结果详情 | 跨质量任务执行列表 |
| Graph | 图构建任务、单图及单任务构建上下文 | 跨图构建任务执行列表 |

“模块内保留”不等于允许模块再实现一份通用 execution 表格。单任务历史必须由明确的 `source_task_id` 限定；领域详情只展示 owner 独有的业务结果、日志、诊断或操作，并提供返回统一监控的入口。模块私有 execution 查询接口可以作为单任务轮询或领域投影存在，但不得据此重新暴露模块级全局列表。
