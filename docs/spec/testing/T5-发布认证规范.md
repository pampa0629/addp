# ADDP T5 发布认证规范

[返回测试与验收总入口](../addp测试与验收规范.md)

## 统一入口与认证范围

T5 按产品或 Runtime 独立准备真实前置条件，例如 macOS Keychain、安装包生命周期、HA、故障切换或在线厂商证据。统一 `test-release` 分发器只选择 owner 门禁并生成 `addp.release-gate/v1` 报告，不合并不同产品的运行条件。

发布 workflow 只准备环境、调用标准 Make 入口、归档证据和执行发布动作，不在 YAML 内重写业务测试。System IAM PostgreSQL 属于 T2，不因与发布流程共用 workflow 而变成 T5。

未具备真实凭据或 Runtime 的 T5 suite 不得登记占位实现；需要人工认证时必须明确记录未验证项和后续责任门禁。

## K3s 可用性与弹性验收目标

首个应用试点为 Catalog HTTP。先完成[服务发现与断连验收](scenarios/部署与执行恢复.md#catalog-服务发现试点验收)，再验证下列目标。每份报告记录受测版本、节点与副本拓扑、资源 requests/limits、故障时间线和真实业务请求结果。各项待现场验收。

| 能力 | 必须观察的结果 |
| --- | --- |
| 负载均衡与副本恢复 | 同一 Gateway 入口的连续业务请求实际命中两个就绪副本。一个副本失去就绪并摘除后，新请求只到健康副本。进程退出或失去响应后记录 kubelet 的恢复行为、重新就绪时间和恢复接流时间。业务依赖故障须单独测量 Ready 和存活探针。 |
| 高并发与水平伸缩 | 选定代表性查询、数据集及现场目标吞吐量、P95/P99 延迟和错误率。记录固定副本基线，再按相同负载升压、稳态、降压，核对 HPA 的资源指标、期望副本数、实际可用副本数与业务指标。验证缩容期间的在途请求，并记录数据库连接及下游饱和点。 |
| 节点与控制面高可用 | 分别注入应用节点、外部入口节点和控制面成员失效，从客户端持续访问原域名，记录中断时长及新副本能否调度。嵌入式 etcd 按跨故障域的多数派拓扑验收。 |
| 状态恢复 | 对所选数据库、对象存储及任务租约分别约定允许中断时间和可容忍的数据损失，实际切换或恢复后核对已提交业务数据、checkpoint、任务归属及恢复时间。Catalog 后台同步、投影及协调任务先验证并发执行与交接语义，再对完整模块启用自动扩缩。 |

## 官方介质与 License

厂商只提供离线 Docker tar、且 Runtime 受 OS/CPU 架构约束时，官方介质认证归 T5：owner 脚本必须在一处固定官方 HTTPS 地址和 SHA-256，负责下载、校验、`docker load`、原生启动、真实驱动/SQL 断言及所有退出路径清理；workflow 只选择匹配架构的 Runner 并调用统一 `test-release` 入口。此类 suite 不声明 `ADDP_T2_SERVICES`、不进入 `test-integration` 或辅助 macOS 巡检，也不能替代插件实现后的 T2 Provider 集成与 T4 跨模块验收。

官方介质包含限时试用 License 时，T5 只允许将其用于首次准入评估，不得以重新下载介质、重建容器、替换主机或清除状态的方式重置试用期。长期门禁必须由 owner 提供来源合法、当前有效且 SHA-256 明确的 License，门禁报告只记录授权元数据与摘要，不归档 License 原文。

## GaussDB 双架构认证

GaussDB 开发者版官方介质准入使用 `make test-release RELEASE_SUITE=gaussdb-official-media`，在原生 Linux x86_64、ARM64 Runner 的独占 Ubuntu 22.04 容器分别运行；GitHub 手工选择相应 `release_suite` 仅运行该 owner 的双架构矩阵，任何一个架构失败不得声明支持 ARM。固定介质、驱动与授权边界见[数据引擎扩展指南](../addp数据引擎扩展指南.md)。`make test-release-runner` 验证下载完整性、架构匹配、独立 module、所有权和失败清理；`make test-gaussdb-certification-build` 以 `CGO_ENABLED=0` 编译 Linux／Darwin × amd64／arm64，并在当前宿主执行 GaussDB／PostgreSQL 驱动共存断言，只是构建验证。

原生 T5 验证 SHA-256 认证、只读事务、中文／参数化精确数值、目录及取消后的连接池恢复，禁止跳过。认证源仅保存于 Common owner 的 `testdata`，由入口复制到仓库外独立 module，采用固定公开驱动与校验和，不使用离线驱动 replace 或 `GOENV_REGIST_ALL`；Common 普通包图、tidy 与 workspace 不加载候选驱动。

镜像由对应官方介质构建并记录 ID，不冒称官方发行镜像；报告不含密码、原始介质或驱动。容器、网络、镜像和临时凭据必须全路径清理。Mac 上 Docker 或交叉编译不冒充 Linux 原生 T5，未注册生产 `engine_type`，也不替代后续 T2／T4。

## KingbaseES 受控人工执行

KingbaseES 的 T2 Provider 与 T5 官方介质认证暂不接入 GitHub Actions，保留标准命令与确定性回归，由持有正规 License 的 owner 在受控 Linux x86_64 主机人工执行。T5 未声明 `workflow_job` 表示不由 GitHub Actions 编排，登记检查拒绝 workflow 调用其 suite 或内部 owner 目标；恢复自动执行前需另行确认 Runner 隔离与生命周期方案。此调整不改变 Online T4 的现有协议，脚本回归通过不代表真实授权认证通过。
