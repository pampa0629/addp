## 关系型引擎消费链路

### OceanBase

OceanBase 消费链路 T4 使用专用 OceanBase CE MySQL 模式 Fixture 和永久 `engine_type=oceanbase` Engine Instance。Fixture 固定维护一个 5 行非空间 InnoDB watermark 源表和一个同构空目标表；suite 必须经 Meta 扫描取得两个 ResourceLocator，以同一条 bounded watermark Transfer 任务依次验证首批 5 行、源表确定性更新/新增后的 2 行增量，以及再次执行的 0 行空增量。目标采用 `upsert` 和唯一稳定键 `id`，不得把 OceanBase 降格注册为 MySQL 或为模块增加类型分支。首批与增量完成后，Manager 表预览、Develop SQL 和临时 Query Service 必须通过各自正式数据出口读取同一目标 ResourceLocator，并得到一致 checksum，最终固定为 6 行且无重复键；Manager 预览还必须确认扫描结构中的完整列顺序。临时 Transfer 任务和 Query Service 必须按捕获 ID 删除并确认 404；物理 Fixture 在成功、失败和中断退出路径恢复源表基线与空目标表后停止。该 suite 只登记手工 `workflow_dispatch`，首次真实通过前不得增加定时触发。

### TiDB

TiDB 消费链路 T4 复用同一个关系引擎 owner 断言，在带 `self-hosted`、`macOS`、`addp-online` 标签的专用 Runner 上使用固定官方 digest、无数据卷的 PD/TiKV/TiDB 三组件 Fixture 和永久 `engine_type=tidb` Engine Instance。Fixture 固定重建 5 行非空间 watermark 源表和同构空目标表；suite 必须经 Meta 扫描取得 ResourceLocator，以同一条 bounded watermark + upsert Transfer 任务验证 5/2/0 三次读取计数，并由 Manager、Develop 与临时 Query Service 对最终 6 行结果计算相同 checksum。上层模块只消费通用 ResourceLocator、SQLDialect 和 Provider，不得把 TiDB 登记为 MySQL 或增加 `tidb` 类型分支。临时任务和服务必须按捕获 ID 删除并确认 404；成功、失败和中断退出路径都必须执行 `down --volumes --remove-orphans` 并验证三组件容器零残留。该 suite 首次真实通过前只登记手工 `workflow_dispatch`，不得增加定时触发。

### KingbaseES

KingbaseES 消费链路 T4 复用同一个关系引擎 owner 断言，仅在带 `self-hosted`、`Linux`、`X64`、`addp-kingbase` 标签的受保护 Runner 上使用固定 SHA-256 的 V9R1C10 `V009R001C010B0004` 官方介质和 owner 正规 License。Fixture 每轮启动无卷 `DB_MODE=pg` disposable 容器，固定重建 5 行非空间 watermark 源表和同构空目标表，并输出 owner-only Engine 描述；通用注册器以最小权限 Provisioner Token 通过正式 System API 创建当次 `engine_type=kingbase` Engine Instance。suite 经 Meta 扫描取得 ResourceLocator，以 bounded watermark + `ON CONFLICT` upsert 验证 5/2/0 和最终 6 行 checksum，并由 Manager、Transfer、Develop、Service 经各自正式出口取得一致结果。上层模块只消费通用 ResourceLocator、SQLDialect 和 Provider，不得增加 `kingbase` 分支。成功、失败和中断路径都必须删除本轮平台库、Engine Instance、容器、镜像、临时任务、服务和 owner-only 凭据目录，验证零残留；License 和镜像 tar 不归档。首次真实通过前只允许手工 `workflow_dispatch`。

### openGauss

openGauss 消费链路 T4 复用上述关系引擎 owner 断言，但只在 GitHub Hosted `ubuntu-24.04` x86_64 profile 上运行。生命周期从固定 SHA-256 的 openGauss 6.0.6 LTS 官方介质启动独占容器，创建 `addp_online` 平台库、非默认 Tenant、最小权限消费 User、只含 `system.engine.create/read/execute` 的 Engine Provisioner 和临时 `engine_type=opengauss` Engine Instance。Business Fixture 只管理数据库并输出 owner-only Engine 描述，不调用 System API；System IAM owner helper 只创建身份和 Token，通用 Online 注册器使用 Engine Provisioner Token 通过正式 System API 注册并验证 Engine。Fixture 以 `public` schema 作为 namespace，使用 openGauss 原生 `MERGE` 推进相同的 5/2/0 watermark 数据集；Manager、Transfer、Develop 和 Service 必须通过与 OceanBase 相同的通用 ResourceLocator、SQLDialect 和 Provider 路径得到同一 6 行 checksum，上层模块不得新增 `opengauss` 分支。当次 Engine Instance 只随 disposable 平台库销毁，Token 和连接凭据只保存在不归档的 owner-only `runner.temp` 目录；Engine 注册后必须在进入业务断言前从进程环境清除 Provisioner Token 与数据库凭据，业务证据不得包含凭据。该 suite 在首次真实通过并确认构建身份、清理和零残留证据后，同时保留手工 `workflow_dispatch` 并登记每日夜间 `schedule`；定时事件只能选择 openGauss Hosted Job，其他 Online Job 必须显式排除定时事件。

## Transfer 仅新增 MySQL 同步

Transfer 仅新增 MySQL T4 使用永久 PostgreSQL 与 MySQL Engine Instance，并由专属复合 Fixture 管理两端物理表。真实 User 必须从 Console 页面选择源表和目标库、进入字段映射、通过正式“分析源数据并推荐精度”接口把无声明精度的 PostgreSQL `numeric` 收敛为不会截断当前值的 MySQL `DECIMAL(6,2)`，再以主键 `id` 作为唯一 watermark 创建任务。页面自动执行的首轮必须读写 6 行；Fixture 同时修改 `id=1` 并新增 `id=7` 后，用户从任务详情再次执行必须只读写 1 行。最终 MySQL 目标必须共 7 行、`id=1` 保持首轮值、`id=7` 为新增值且无重复键，以证明单字段水位只覆盖严格递增新增、不承诺旧记录更新。浏览器还必须断言任务配置的 `tie_breaker=[]`、目标 `upsert` 键为 `id`，捕获并删除临时任务且确认 404；Fixture 在全部退出路径删除两端固定表并停止两个容器。该 suite 只登记手工 `workflow_dispatch`，首次真实通过前不得增加定时触发。

## transfer-relational-sql-etl

Transfer 关系型 SQL ETL T4 `transfer-relational-sql-etl` 唯一使用 GitHub Hosted `ubuntu-24.04` x86_64 临时部署，不保留 macOS 专用 Runner 路径。生命周期复用 `scripts/utils/hosted-online.sh`，从零建立独立 Infra、非默认 Tenant 和最小权限测试 User；System-owned IAM helper 创建身份，独立 Engine Provisioner 通过正式 System API 注册当次 PostgreSQL、MongoDB、Doris、ClickHouse 与 MinIO Engine Instance，注册后清除 Provisioner Token；业务 User 不持有 `system.engine.read/execute`，只从 Meta 读取同 Tenant 引擎投影。Business Fixture 管理当次独占数据库容器、固定源表、源集合、写入拒绝目标及 tmpfs MinIO，并输出 owner-only Engine 描述，不调用 System API。数据库用户只能读取源表并在指定 schema 创建、管理自己的目标表。真实 User 必须从 Console 选择源表，确认单语言引擎只显示固定 `SQL` 而不提供 MQL、语言下拉或高级 SQL 编辑入口，通过基础构造器选择输出字段并配置两个参数化行过滤，再选择 PostgreSQL 目标位置创建 snapshot 任务。浏览器必须断言保存事实只有标准 `source.query` SQL statement 与类型化 parameters，其中 decimal 过滤值以字符串保存而不是 JavaScript Number；下一步字段映射只包含实际投影字段，并等待 Worker 读写恰好 2 行。Fixture 必须核对目标行集合、金额汇总和列顺序，以同时证明过滤、投影和精确参数绑定语义。临时任务必须通过正式 API 删除并确认 404。成功、失败和中断退出路径均销毁当次业务容器、Infra、平台数据卷及 owner-only 凭据目录，检查零残留；Engine Instance 与身份随平台库销毁。凭据不进入日志或 Artifact。该 suite 只登记手工 `workflow_dispatch`，首次真实通过前不得增加定时触发。

### Manager 私有导入

同一 `transfer-relational-sql-etl` suite 在其他传输场景前执行 Manager 私有 Shapefile 导入。真实 Console 弹窗上传固定两点 ZIP，核对目标命名空间、CPG 编码、当前 User 的持久 `sync` 任务和 Transfer execution，等待准确 Meta 子扫描及资源树刷新。Transfer 是实际读写和血缘的唯一 owner；浏览器不复制后台导入 HTTP 路线。Business `manager-import` 独立核对完整 PostGIS 行值、点坐标与 SRID，不调用平台响应计算期望。

`manager-private-import.json` 使用 `addp.manager-private-import/v2`，包含两阶段 `addp.manager-private-import-browser/v1`：必须核对 source commit、当前 User／Tenant／Run ID、准确 Transfer／Meta UUID、当前发起 User 与真实父执行，以及非上传者启动同任务时的零读写拒绝和普通 User 直接 Inspect 拒绝。失败时经真实 Transfer 执行详情核对安全诊断；缺少任一页面或领域证明不得登记通过。上传一经接受即捕获 task／execution 身份，后续页面失败也须清理；后续其他场景失败不抹去已完成的独立领域证据，但不能登记完整 suite 通过。完整 suite 版本以当前登记为准。

导入完成后的刷新与 Monitor 导航顺序由既有 Manager 嵌入式 T3 延迟响应回归单独证明，Hosted 导入成功不替代该竞态回归。沿用 `make test-transfer-online-runner`、Manager 前端门禁和原 Hosted workflow；实际结果见[私有导入历史证据](../验收证据索引.md#manager-预览与私有导入历史证据)。

同一入口还验证普通 User 经正式 Manager `/uploads` 上传一个 CSV 和五份 Shapefile 组成文件至独占 Business MinIO；沿用既有用户权限，不将 Infra MinIO 注册为业务 Engine。MinIO 启动复用共享的独占 tmpfs 生命周期，Provisioner 只登记该次 Engine。仅等待上传响应中真实的 Meta UUID，不手工补扫；核对 `source=manager`、当前 User/Tenant、准确 Engine 和 deep 深度，直接用户上传不伪造父执行。独立物理夹具读取六个对象的实际字节、SHA-256、大小、ETag 和修改时间；CSV 的 Meta 列与 storage 大小须为相等正整数，修改时间按同一时刻比较，ETag 原样相等。Shapefile 必须只有一个 multi 逻辑项，大小等于五份实际对象之和，引用集合准确，不新增组合项 ETag 或修改时间聚合规则。`manager-object-upload.json` 按 `addp.manager-object-upload/v1` 绑定当次源码、Run/User/Tenant、Engine、上传响应、Meta UUID 与物理事实；缺项、错来源或不相等均失败。对象源事实自完整 suite v13 起纳入验收；当前报告版本见下文，旧 v12 不证明该链路。原私有导入与领域证据保持独立；上传对象随当次 tmpfs 容器销毁并由 Hosted 退出路径核对零残留，不声称已验证 Manager 业务 DELETE。

### 写入失败与证据边界

Transfer 的 `transfer-relational-sql-etl` Hosted T4 在同一普通 User／Tenant 下追加 Doris、ClickHouse 各两个合成失败场景，沿用现有 suite、生命周期、浏览器和 CI 入口，不复用个人开发部署。独占目标使用固定摘要镜像和随机回环端口，Doris 复用 Business 唯一 FE／BE 启动入口，在夹具实例开启严格写入并限制目标分区范围；ClickHouse 使用 CHECK 约束。四份 Python 生成的创建配置必须经真实 Go planner 纯解析校验，目标使用 database 父节点的 `parent_locator + name`，不得提交 `target.locator`；此跨语言回归纳入既有 runner、Go T1 与 CI 登记检查。1001 行源输入按显式顺序进入同一批次，先提交 1000 行，再因原生约束拒绝末行；另以末行非法 JSON 验证本批无新增行。两者均保留预置哨兵行，独立物理读取分别必须得到 1001 行与 1 行，不能用 execution 的 `records_written=0` 推断目标为空。每个任务必须为 failed、使用不同执行 UUID 且关闭自动扫描，目标 Meta 事实前后保持未扫描；同一登录身份在真实 Transfer 执行详情页核对安全诊断、终态和执行编号，并生成截图，禁止恢复原始 error_msg 或暴露运行时正文。提交标记仍由原生 T2 验证，专业 API 不为验收暴露私有 checkpoint。任务按当次所有权清理，容器／卷在成功、失败及中断路径销毁并核验零残留。runner 通过不计为 T4 通过，首次真实 Hosted 成功须另记证据。

写入安全诊断 v3 的原生门禁与 Hosted 验收分别认定：原生通过不能替代新版 T4，未进入四个 Provider 写入失败场景的前置失败不能计为 v3 T4 通过；新版 T4 必须在同一 suite 中核对安全原因码、可确定的写入列序号与声明类型、目标可能已改变标记及实际物理行数。历史结果与范围限制见[其他验收证据索引](../验收证据索引.md#addp-验收证据索引)。

各层的统一安全诊断断言见[关系型写入与安全诊断门禁](../Owner补充门禁.md#关系型写入与安全诊断门禁)。

### 字段级血缘验收

同一个 `transfer-relational-sql-etl` suite 同时覆盖字段血缘首期：使用无管理员角色、具备 `meta.lineage.read`、`manager.data_item.read` 和 `manager.content.read` 的同一 User，经正式 API 执行原生表 snapshot 的字段改名、decimal 精度转换、同目标 replace MongoDB 夹具必须等待容器 PID 1 成为正式 `mongod`，再进行认证及 ping 探测；[官方镜像入口](https://github.com/docker-library/mongo/blob/master/7.0/docker-entrypoint.sh) 在初始化阶段会启动临时实例、创建账号，再关闭临时实例并执行正式进程，仅认证及 ping 成功不能证明切换完成。两项就绪条件使用同一个有界等待；数据与最小读取权限只初始化一次，失败时不重试部分写入、不发布引擎描述文件。原始启动及驱动错误只留在退出即清理的凭据目录，CI 日志仅输出固定错误分类和非秘密容器状态。

#### 扫描调用链与读取隔离

同一 Transfer Hosted suite 复用既有上传者和同 Tenant、持有完全相同业务权限的另一个普通 User，不新增角色授权。正式对象上传后，上传者须在 Monitor 详情与执行树中读取同一实际 Meta UUID，树只有该扫描且无虚构父执行。有界私有导入后，上传者须读取真实 Transfer 父执行及其唯一 Meta 子扫描；另一 User 可读持久任务的父执行及仅含父执行的过滤树，但不能由父读取权取得该一次性扫描。Meta 专业详情与 Monitor 详情、树、事件四个入口均须返回 404，响应仅含错误字段，不能用缺少 Owner 读取权限的 403 代替身份隔离证明。执行树不得截断、重复、丢失或混入其他 UUID；详情与树中的扫描投影保持一致。

`scan-trace-visibility.json` 使用 `addp.scan-trace-visibility/v1`，绑定源码、Run、两位 User、原有权限、实际父子 UUID、各自可见节点及四个拒绝入口。收据保留公开执行 DTO 中身份、来源、状态与直接父关系的最小投影，以及每个拒绝入口实际返回的 HTTP 状态与响应字段名，不保存任意 metadata、配置或凭据。仅两条链路都通过后保存独立收据，后续场景失败仍保留该证据。完整 suite 使用 v14；旧 v13 仅证明此前对象源事实，不能证明本轮新增 Monitor 链路与读取隔离。标准入口继续为 `make test-transfer-online-runner`，真实验收仍走既有 `transfer-relational-sql-etl` Hosted；现有登记检查锁定新版报告和隔离断言，不新增 workflow、数据库或测试路线。

#### 性能采样口径

宽表交互性能采样沿用同一 Hosted suite，在同一登录上下文的新页面中读取真实 1500 字段节点、1000 条关系图；该页面不安装用于几何取证的 Canvas 观察器。首、中、末字段分别从按钮的真实点击事件计时，到所选字段以至少 11px 字号居中绘制后、下一稳定动画帧结束，并保存 CPU 采样。结果写入 `transfer-wide-native-focus.json` 与三个 `.cpuprofile` 文件，每个页面仍只加载一次字段图。该计时排除字段搜索、Playwright 定位等待和详细几何记录成本，但包含轻量绘制探针及 CPU 采样开销；不能与原有包含导航、请求及自动化验证的总时长直接计算加速比。既有整图完整性、精确映射、拖拽端点与清理断言仍在原验证页面执行。

首次字段图绘制和自动布局复用同一轻量采样实现。首次绘制从字段级切换的真实事件开始，使用浏览器 Resource Timing 中对应字段图请求的 `responseEnd` 分离网络与响应处理，记录响应完成到可读字段稳定绘制的时间；不将 Console 导航或 Playwright 等待计入此段。自动布局从工具栏按钮的真实点击开始，到布局按钮恢复可用且全图下一稳定绘制帧结束；全图适应窗口后的字段字号仅记录，不套用字段聚焦的 11px 要求。两者只观察当前画布实际可见字段，不将图引擎在离屏位置进行的文字测量算作完成。计时与 CPU 采样分别归档为 `transfer-wide-native-render.json`、`transfer-wide-initial.cpuprofile` 和 `transfer-wide-layout.cpuprofile`。该采样不重查字段图、不安装详细几何观察器，也不改变产品布局和 API。

几何验证、包含导航 / 请求 / 自动化等待的端到端时间、原生点击采样和本地受控夹具是不同口径。只有相同环境、相同采样口径的结果才可比较；本机与 Hosted 不直接计算性能倍率。CPU 累计归因可能嵌套，不能相加；采样会话总时长不等于原生点击耗时。单轮独占 Runner 的观察值包含轻量探针和 CPU 采样开销，不构成固定延迟目标或性能保证。

历史通过记录、性能采样数值和本地只读复核见[历史证据索引](../验收证据索引.md#历史证据索引)。这些记录不替代当前源码的验证。

## transfer-continuous-events

Transfer continuous 过程事件 T4 `transfer-continuous-events` 使用独立 GitHub Hosted Linux x86_64 部署，复用共享 Hosted 生命周期；只登记手工调度，真实通过前不加入夜间运行。Business owner 创建独立业务 Kafka、开启 logical WAL 的 PostgreSQL 源／目标和确定性数据；不把 Infra Kafka 冒充业务源，不复用个人容器。普通 User 经 Gateway 创建和控制业务 Kafka 与 PostgreSQL CDC 任务，正式 Worker 执行，Business 夹具独立验证 snapshot、upsert 和 delete 的目标事实。通过 Transfer 与 Monitor 的既有授权入口核对 started、累计提交进展、唯一终态和恢复链；强制退出只允许 pin 当次部署的 Worker PID，恢复使用标准启动入口，不增加产品故障参数，不以测试内 Supervisor 或受控授权 Gate 代替。诊断读取验证同租户仅 Monitor 权限、跨租户及正式撤销 Owner 读取授权，Owner 不可用时失败关闭；事件与通用响应不能回显原始配置、业务样本、原始 checkpoint、内部 Worker 或租约信息。User／Role／Session 只由 System-owned 测试 helper 经正式 IAM Service 创建，不改生产 IAM 或权限规则；业务值和凭据不进入事件证据，全部退出路径核对应用、业务夹具、Infra 和私有凭据清理。第一切片证明真实 API／Worker 链路，沿用共享过程组件的 T1/T3，不宣称 Console 浏览器或 Kafka HA 已经过本 suite 验收。


## FTP 普通 User 消费（ftp-consumer-flow）

本场景只允许手工 GitHub Hosted Linux x86_64 profile。独占 FTP 夹具复用 Business 固定 SFTPGo 镜像、唯一初始化及样例生成器，随机端口、账号、私有 CA 与独立数据／状态卷；不读取个人 `.env`，退出验证当次容器和卷零残留。Business 只输出私有 Engine 描述，正式 System API 由独立 provisioner 调用，后续消费前清除其 Token。原表格消费基线使用 `system.engine_catalog.read`、`meta.catalog.read`、`meta.scan_task.execute`、`meta.scan_task.read`、`manager.data_item.read`、`manager.content.read` 六项 Permission；加入下述模型扩展后，同一普通消费 User 使用明确列出的十项 Permission。

API 与真实 Console 页面必须验证同一 Tenant／Principal。 Console 每次导航或重载后的辅助 API 客户端，必须从该次页面实际发出的受保护请求重新绑定凭据，并核验相同 User、Tenant 和完整 Permission 集合；不得跨导航复用登录时的凭据快照，也不允许在 401 后改用夹具身份、Cookie 或静默重放。普通用户浏览 FTP 账号根及 examples 目录，文件名中的中文、空格、百分号保持原样；原生 Facts 大小与路径吻合，不虚构 ETag。Meta 仅对 examples 目录深度扫描识别 CSV／JSON／Parquet 的既有 table 类型和三字段，Manager 三格式均读取3行完整示例。Meta 页面重新扫描 examples，确认 DataItem 标识稳定；Manager 页面逐一展示三行 ID、中文姓名和金额，并通过真实下载按钮核验原文件名、大小及 SHA-256 与物理种子一致。每一格式和每一阶段必须执行，不把 API 或静态页面替代浏览器验收。

标准入口 `make test-ftp-online-runner` 验证断言、身份夹具、Hosted 生命周期与 CI 登记；真实页面由 `make test-online ONLINE_SUITE=ftp-consumer-flow` 经唯一 `online-hosted-ftp-gate.sh` profile 编排。既有 CSV／JSON／Parquet 的首次正式 Hosted 已通过，结果及源码见[验收证据索引](../验收证据索引.md)；当前仍仅手工调度。协议双架构准入、builtin 注册、Hosted T4 和个人环境分别认定，Hosted 通过不表示个人环境已登记验收。

### IFC／3DS 快显扩展验收（实施中）

IFC 基础扫描核验稳定的单文件身份、类型与物理路径，固定几何 profile 的唯一主文件组成由正式事实投影建立，不要求深度解析产生的 `format_info.ifc.scan_complete`。3DS 则必须具有完整的有界结构识别标记、原样保留的贴图声明以及精确的必需文件组成。验收夹具须保持这一区别，不为 IFC 伪造深度标记，也不放宽 3DS 的结构完整性检查。

该扩展继续使用同一 FTP suite、独占 FTPS 源和正式 Model3D 产品 Runtime。输入复用仓库固定模型，分别为 `models/ifc/model.ifc`、`models/3ds/model.3ds` 及其声明的 `models/3ds/texture.png`；不能把源复制到 NFS 后计为 FTP 转换。模型授权所需的完整组成事实由 models 目录的强制基础扫描建立，组成变化及恢复只重扫 models/3ds；返回事实不完整即失败，不改用 deep 兜底。现有三种表格的 schema 深扫仅限 examples 目录，不作为模型授权事实证据。模型消费身份在上述六项上增加 `manager.derived_artifact.create`、`manager.derived_artifact.read`、`manager.derived_artifact.delete` 和保存预览偏好所需的 `manager.data_item.update`，不增加通用 `system.execution_authorization.create`、任务编辑或 Monitor 权限。模型 purpose 的签发核验现有生成／数据读取 Permission，执行观察复用 Manager 自有接口。数据许可须经 System 正式批准入口建立；不得给消费 User 管理员角色、数据 Grant 签发资格或夹具 Token，不直接写 Grant 表。

Hosted Job 为同一 Linux 产品原生工具链的冷构建和实际消费保留 180 分钟总预算。镜像准备使用现有单 worker 调度，构建中的输出须实时进入门禁日志；收到可处理的中断时，先停止构建进程组，再输出尚未转发的日志并清理临时目录，不等镜像完成才公布全部输出。准备超时、原生 profile、扫描、API 和浏览器的结果分别认定；尚未执行的阶段不记为通过或产品转换失败。该预算不更换 Runner、转换器或样例，也不允许跳过产品镜像的构建和校验。

授权准备沿用独立 `sourceInitializer` User 及私有 `ADDP_ONLINE_FIXTURE_SOURCE_ACCESS_TOKEN`，在已有批准要求初始化、委派创建、Grant 创建／读取四项资格上，仅对 FTP 增加 Grant 撤回与 Deny 创建／释放三项资格。Redis 及其它 suite 不随之扩权。浏览器子进程显式剔除 Engine provisioner 与 sourceInitializer 的 Token，页面仅使用普通消费 User；正式发放、撤回和 Deny 仍走 System 生产接口。

组成变化反例只修改当次独占 FTP 夹具：将固定 3DS 的 `texture.png` 声明换成等长且首尾含空格的 ` tex.png   `（保持原始名称，不匹配裁剪后的 `tex.png`），新文件保持同一 PNG 内容，经目录强制基础扫描核对完整事实摘要变化。先在没有 Deny 时单独切到新组成，证明旧 Grant 不能覆盖它，再恢复原文件及扫描事实。随后建立原组成的 Deny，再次切到新组成，显式撤回旧 Grant 后用新 UUID 批准新组成，证明原 Deny 对同一 DataItem 继续生效；释放 Deny 后当前源规则恢复，但旧组成生成的缓存仍须拒绝。同一数据项、主体、动作不能并存两条有效 Grant，不能用边界变化自动替换旧 Grant。最终恢复物理样例并重新扫描，撤回新组成 Grant，再用新 UUID 明确重新批准原组成，核验原缓存恢复；随后撤回本轮全部 Grant，检查两份实际缓存均为 403。同一普通 User 重新打开实际模型页面，须展示拒绝状态，不能成功取得 GLB 或发起新转换，原成功执行号保持不变。变更前须核对私有夹具归属、运行容器标签及精确只读挂载，不操作个人 Business 目录，不覆盖已有同名新纹理或跟随软链接。独占新纹理的创建、写入及主文件原子替换均纳入清理范围，准备阶段失败也须恢复，不能只清理已进入转换阶段的样例。

旧组成 Grant 无法覆盖新组成时，以及最终撤回两份模型的源 Grant 后，还须对现有自有任务真实提交生成请求并收到明确来源拒绝。从任务最新执行号读取本次失败审计，核验公开的 `attempt=0`、未开始执行及来源拒绝代码；结果仍指向原成功执行，并核对原对象大小和哈希。这类授权前拒绝不能被算作已暂存输入或已发起转换，其执行号不得进入输入准备和输出观察记录。后续撤权页面以这些最新拒绝审计作为进入页面前的基线，证明页面本身没有再发起执行。EA 与租约等私有字段不因响应缺省而视为数据库证明，相关持久约束继续由既有 T1/T2 核验。

固定 Linux IFC profile 在同一个已核验标签、Run ID、镜像及默认入口的 Model3D 产品容器中额外复验：对实际实体挂载外部 HTTP 图片及绝对 FIFO 引用，不覆盖转换器或 options；真实 IfcConvert 在预算内完成，HTTP 哨兵的连接及所有方法调用均为零，FIFO 无写入方仍能完成，输出不含图片或纹理并通过固定盒体几何物理校验。记录实际二进制哈希与版本，不能将下载归档哈希当作可执行文件哈希；临时目录及哨兵线程结束后均须清理。此项只覆盖明确的固定几何 profile 和两种引用形式，不代表支持任意 IFC 外部资源，也不替代正式 FTP 授权及页面验收。

物理存储核验复用当次产品容器的 MinIO SDK，只读取既有 owner 结果详情中的实际 `storage_ref` 及 `metadata.model3d_output_lifecycle.input_preparations[].objects`。先对当前发布 GLB 做 Stat／Get／哈希正向核验，再逐个确认已知输入对象为 `NoSuchKey`；403、连接失败、缺少 bucket 或超时均失败，不能计零残留。不列目录、不猜 nonce，Infra 端口取标准状态及实际回环映射，凭据只通过临时进程标准输入传递。无效 IFC 反例只将同一隔离主文件原子替换成等长非法内容、不改组成或 Meta 版本，通过正式任务 execute 的 `parameters.existing_result_action=overwrite` 触发后台重建；须观察新执行 failed、旧 ready 的执行号／对象／字节保持、本次失败执行输入清单精确且清理已结束，finally 恢复源字节。该反例证明后台失败与清理行为，不仅凭 failed 推断具体原生解析阶段。此时任务最新执行是 failed，结果仍指向原成功执行，页面撤权检查分别核对两者。

撤回全部源 Grant 后，普通 User 仍可使用既有 `manager.derived_artifact.delete` 删除本轮受管结果；删除前保存全部已观察成功／失败执行的精确输入及失败输出 watch 身份，删除后 owner 详情与内容均为 404，并再次逐 key Stat。watch 对象当时不存在只记当前观察结果，不代表未来迟到写永不出现；确定性续清与崩溃矩阵仍以对应 Manager T1／T2 证明。首次 Manager 保护同步只复用共用只读有界等待；之后任何 `security_protection_required` 都不能冒充源 Grant 拒绝通过验收。

正式通过须同时证明：Meta 持久事实形成精确主文件及依赖边界；当前普通 User 从 Console 发起生成；真实执行绑定并消费同一完整配置的 EA；Manager 仅读取获准文件，Model3D 不接收 FTP 凭据；IFC GLB 几何符合固定样例，3DS GLB 保留实际使用的材质、UV 与内嵌图片像素。当前 Human 通过 Manager 自有内容出口读取自包含 GLB，页面初次加载及重开的实际响应字节均与通过物理校验的 GLB 一致，并核验实体渲染像素；请求使用完整请求头验证 Bearer 且不携带 Cookie 或 Ticket query，失败诊断不得输出凭据值。模型源下载继续使用逻辑对象入口 `downloads/file`，保存实际响应体、Content-Type 与 Content-Disposition；IFC 单文件逐字节核对主文件，3DS 按既有多 ref 契约返回 ZIP，精确核对成员仅为 Meta 已确认的 `model.3ds`、`texture.png`，逐一核对长度、SHA-256 和原始字节。缺失、重复、额外、加密或损坏成员均失败，不能以主文件大小断言整个 ZIP，也不能改走单叶子绕过完整组成核验。缓存复用须同时观察页面生成入口及 Manager 任务最新执行事实，不能只依据仍指向旧成果的执行号。收权或组成变化后旧缓存不可继续读取，不借 Resource Ticket 或终态 EA 放行。执行失败保持上一份有效结果；发布与清理按精确对象归属核验，临时输入及退出后的本轮资源零残留。

生成拒绝按 Manager 任务执行入口的正式契约核验 HTTP 403 与非空 `error`；不在 HTTP body 中假设执行记录专属的错误字段。拒绝原因须由新产生的同属主执行记录证明：`error_details.code=source_authorization_required`、`attempt=0`、无父执行、未开始且已终结，不包含 Runtime 或转换事实，也未创建临时输入和输出归属；上一份有效成果及其物理对象保持不变。仅有 403 不能证明源授权拒绝。验收按已完成阶段保存观察记录到现有工件目录，不保存凭据或原始错误响应；阶段记录不代表完整 suite 通过，最终仍须以整套矩阵及清理结果为准。
