### PG 元数据查看过滤（本地验证，跨服务 T4 待补）

System 新增授权与 Catalog 业务批准都必须显式选择 `metadata_read` 或 `read`，初始不预选。System 沿共享资源树多选、节点及递归选择；Catalog 办理只引用业务决定，不接收替换动作。验收须覆盖：缺失／非法动作拒绝；同一数据项、接收方及期限的两种批准分别保留；同编号变更动作冲突；按动作提示已有批准／Grant；仅元数据批准受理及签发后仍为 `metadata_read`，替换为 `read` 不能签发。首期元数据动作仅允许 PG，原有其他引擎内容读取不扩大。

本批本地 System PostgreSQL T2 覆盖元数据签发、受理／签发动作替换拒绝及唯一 Grant／审计；Catalog PostgreSQL T2 覆盖两动作存储、重试、去重与候选。前端单元和浏览器用受控响应验证显式选择及原命令恢复，不代替本批跨服务实际读取验收。原 PG Online 的业务读取请求同步显式提交 `read`；其既有通过不证明新增元数据业务批准 T4 已通过。

新增动作的跨服务场景复用已有两个 PG 表、消费 User、旁观 User、办理 User 和业务负责人，不新增角色／引擎管理范围。在原工作区已归零后、Transfer 新成果之前：先证明无授权时清单隐藏；仅签发 `metadata_read` 后身份及允许的结构投影可见，Manager 内容仍拒绝；临时增加独立 `read` 后实际读到两行，撤回 `read` 不改变元数据 Grant，撤回元数据 Grant 后同凭据恢复隐藏。元数据自然到期沿原 45 秒期限／75 秒观察预算，必须进入 expired 历史且无撤销记录，不续签、不手动撤销代替到期。basic 没有采得的字段结构不伪造成已识别字段。

随后复用既有 Catalog 条目和业务负责人，仅批准元数据查看；确认本身不产生 Grant。办理只提交原决定编号，系统签发的动作、主体、DataItem 边界及期限须逐项等于批准。处理请求夹带动作覆盖字段必须拒绝；重放原请求不得变成数据读取或重复签发，撤销后重放也不能恢复权限。整个阶段只发布身份、动作、状态和计数证据，不记录业务值或 Token。发送前登记全部命令和目标；任何阶段失败均走既有 finally 收权和全目标／全接收主体归零核验。此扩展先完成本地 runner 与既有 CI 契约验证，不据此标记真实 T4 通过，也不自动派发新的 Hosted。

普通 User 的 PG 资源树、通用项／节点查询、路径查询、字段及空间声明、祖先链和统计复用 System 当前 `metadata_read`／`read` 裁决。测试必须同时覆盖可见项和不可见分支；列表与计数先过滤，隐藏单项／指定分支与不存在响应相同。撤权后同一凭据再次查询不能复用旧 Allow；System 核验不可用须明确失败，不能返回未过滤结果或虚假的零总数。

结构查询保留字段名称、类型、主键、嵌套结构和声明坐标系；样本、源行数／大小／范围、注释、默认值和生成表达式不能混入。投影不得修改原 Meta 快照；已有机器 SDK 的受控结构事实消费仍单独验证。现有 Meta Tool 委托只准入已确认的目录／祖先工具，不因为新增通用查询测试扩大工具 Scope。

标准入口：`make test-module MODULE=meta GO_ONLY=1`（含受控 HTTP API／真实统一 client、嵌套字段投影与不可变快照反例）、`make test-meta-postgres`（原有 PostgreSQL 持久化／目录／事实回归）、`bash scripts/swagger/check-route-coverage.sh meta`。对应 Meta owner 自动发现覆盖这些文件，不新增门禁入口。既有 Meta PostgreSQL T2 回归不等于本轮过滤已通过真实跨服务 T4；其他消费出口仍须逐项接入后验收。

PG 用户血缘同时验证 item／field：隐藏起点与不存在统一 404；关系两端均可见；隐藏桥梁不能继续遍历，隐藏节点不能消耗 limit 或改变 truncated／未展开邻居数；历史时点也执行当前权限；用户服务起点 403、图中无服务节点和服务计数。字段表达式及任意 evidence 不向用户返回，机器事实契约保留。HTTP 反例走真实统一 client 的固定血缘入口，验证原凭据、撤权后 404、依赖故障 503；目录／祖先委托不能进入血缘。

该切片复用 `make test-module MODULE=common GO_ONLY=1`、`make test-module MODULE=system GO_ONLY=1`、Meta Go T1、`make test-authorization` 及 System/Meta Swagger 覆盖。`make test-meta-postgres` 已登记 `TestUserLineageVisibilityAgainstPostgres`，在回滚事务中验证实际 PostgreSQL 关系过滤及字段查询；`make test-system-iam-postgres SYSTEM_IAM_POSTGRES_TEST_ARGS="--package engineaccess"` 验证真实当前用户凭据、独立血缘功能权限和 Grant 撤销，以及现有 Meta 委托拒绝。以上本地 T1/T2 均不代替跨服务 T4。

隔离场景的首次及集中重扫由已有引擎管理范围的办理 User 执行，不向普通消费 User 额外授予管理范围。授权前通过 System 正式授权事实接口核对身份与边界，用不含 Meta 数字 ID 的正式 locator 验证读取拒绝；消费 User 在 Grant 签发后才查询 Meta 身份。内容变更期间，管理人每次重扫后核对 System 可信指纹及边界，消费 User 在有权时复核持久 ID、无权时必须 404；不以预先泄漏 Meta 清单来准备测试，也不新设旁路机器查询。

跨服务血缘验证复用原 `pg-source-authorization` 的 Transfer 新成果场景，不另造关系或增加数据 Grant：隔离消费账号与旁观账号仅补 `meta.lineage.read` 功能权限。源表和成果均有权时，实际 item／`person_id` 字段图须包含精确两端与唯一关系，字段证据绑定本次执行。basic 不保证保存 deep 字段结构，字段查询固定使用该执行已公开且与精确源／成果 locator 绑定的 schema snapshot hash，由 Meta 的不可变 observation 证明；不新增 deep 扫描。仍在原 120 秒预算内先等待该执行的 item 关系形成，再查询其字段证据，不重试权限或协议错误；旁观账号查询起点返回 404。撤销源 Grant 后，当前图与撤销前时点的图均只返回成果，不暴露隐藏边、邻居数或截断标志；源起点返回 404。撤销成果后两种粒度的起点均为 404，同一凭据贯穿验证；用户服务起点明确 403。只读等待限于原后台血缘采集尚未形成关系，错误响应或泄漏立即失败。任何阶段失败都沿原 `finally` 清理已登记的源／成果 Grant 和任务。报告只保存身份引用、计数及状态，不保存图中的业务字段值或凭据；本段在取得完整新 T4 结果前始终标为待验证。

字段结构摘要严格沿用 `TableSchemaSnapshotHash` 的 `sha256:` 加 64 位小写十六进制格式，执行证据、字段查询及返回节点均逐字绑定同一个完整值；裸摘要、大小写变体、截短值不得兼容。确定性夹具也必须使用此格式。新成果基本识别、结构证据校验和血缘可见性分别记录当前阶段，失败仍保留原收权与清理要求。

成果血缘检查失败时，原 PG 报告保留有界的 `lineage_diagnostic`：当前操作、item／field 粒度、reader／outsider 主体类别、预期及已收到的 HTTP 状态、具体失败断言，以及结构白名单、数量和身份匹配的布尔检查。不得记录响应正文、任意错误文本、隐藏资源身份、字段值、原始 schema 摘要或凭据。原异常继续抛出，原检查、身份、请求次数、120 秒预算和 finally 清理不变；请求失败而未取得响应时状态保持空，不猜测为 403 或 500。诊断通过仅证明证据保留能力，不替代实际血缘或完整 PG T4 通过。

### 持续节点授权与取消源 Deny（2026-11-02 已确认，实施切换中）

本节是新规则的验收目标。源 Deny 场景及其专用清理退役；旧运行的检查总数仅作历史证据，不能标为本模型通过。其余默认拒绝、撤权、到期、组成、下载、故障恢复和清理断言保留，增加持续节点的范围与来源并集证明，不保留旧协议或双重裁决。

- 同一 System Grant 链核验 PG 根／schema 的本级及递归范围，元数据／读取两种动作，账号／部门／项目组来源；一条节点 Grant 在到期前覆盖现有项和授权后基础识别的新项，不展开成叶子 Grant。
- 仅元数据来源不能读内容；读取包含必要元数据；未覆盖兄弟节点、不同引擎／租户、伪造祖先、未识别／边界不可靠或越界引用均拒绝。真实 typed path 名称包含点、斜杠样式或相似前缀时不能产生扩大匹配。
- 节点与单项、父子节点及个人／组织来源分别签发和撤销。撤销其中一个后其余来源不变；最后来源撤销及自然到期拒绝；组织退出不能删除组织 Grant，退出账号失去该组织来源。旧编号重放不复活或续期。
- Meta 节点身份事实端点只读、当前租户及精确引擎范围，独立机器 Permission 与固定 System Client 守卫均核验；错误类型、未知字段、重复键、错误绑定、重定向及超限拒绝，查询不扫描、不签发、不读内容。
- System 页面明确区分精确批量和持续节点范围，不要求装载节点全部叶子才能签发范围；确认前展示递归及未来新项影响，取消零写，历史／撤销展示真实范围和剩余来源。Deny 路由、按钮和功能角色均退出。
- 原 `pg-source-authorization` suite 新增持续范围切片：同一既有普通账号、PG 引擎和办理资格，schema 元数据 Grant 不读内容，非递归 server 不越过 schema；递归 server Grant 后才由独占 Business 夹具建立 `metric_node_future` 并 basic 识别，Manager 实际读取两行，无叶子 Grant。旁观拒绝、节点读取撤销后独立元数据仍可见、旧命令不复活、自然到期无人工撤销逐项验证。源表随独占容器销毁，所有本轮节点路径和命令发送前登记，原 finally 收权及部署零残留保持。此新切片未取得真实结果前不计 T4 通过。

- 复用标准 `make test-authorization`、Common/System/Meta owner T1、System/Meta PostgreSQL T2、受影响前端与原 PG Online 入口；CI 自动发现已有 owner 变化。首次完整新 T4 需要独立明确授权，失败清理只回收本轮临时 Grant、任务及夹具，通用审计保留，不操作真实组织。

### PG basic 集中扫描（本轮真实验收待运行）

目标规则以[集中采集规范](../../addp元数据扫描机制规范.md#集中采集权限与两种范围语义)为准。原逐任务审批 API、审批页和资格到期场景已退出当前 suite；其固定源码、通过／失败及限制保留在[历史证据](../evidence/数据保护与执行血缘历史证据.md#meta-采集资格验收导读)，不能替代新规则验收。除已批准退役的源 Deny 外，数据 Grant、Catalog、FileGDB 原有断言不删减。

原 `pg-source-authorization` suite 复用隔离 PG、System、Meta Backend／Worker 与已有办理 User。夹具仅显式分配本次所需 `meta.scan_task.create/update/delete/read/execute/cancel`；不发布给真实人员。通过正式 API 创建唯一名称、禁用定时的 PG 整引擎 basic ScanTask，在发送前登记清理归属。当前人员功能权限与目标引擎管理范围缺一不可；缺范围的读取 User 和无权 User 手动触发均须明确 403，且不得创建 execution。具备管理资格的 User 无需普通 DataItem Grant 可重复执行；basic 配置变化可由同一有权人员更新并执行，无需审批。deep 更新拒绝且定义不变。修改任务旧、新引擎分别核验；越租户、错误主体、编排触发、计划变化及无效租约由对应 API／PG T2 反例覆盖，不能以本地反例宣称真实 T4 全部通过。

租户定时通过正式任务 API 启用 `* * * * *`，等待原一分钟 Owner 轮询，不调用手动触发、TaskProvider 或写库模拟。每次观测到唯一新执行后关闭本轮定时，校验 scheduled、source=meta、bounded、无人员触发人／父执行及服务器时间顺序；重复定时执行不需要逐任务批准。创建人失权后的独立运行由专门测试证明，不凭无 triggered_by 推定已经实测角色撤销。人员失权后不能再修改或执行。

运行中取消仍以一次 Catalog 枚举为读取单元。在本轮独占 PG 中建立有界锁和排序在 public 之后的临时 schema；`pg_stat_activity` 必须证明精确账号的表枚举 SQL 已被锁阻塞，正式执行观察须为该任务、当前人员和 running。以独立取消 Permission 请求取消该精确 execution，已准入枚举不被强制终止；释放锁后 execution 与任务摘要以 cancelled 收敛，保留已完成 public 计数，下一 schema 不读取。关闭调度与取消执行不能互相代替。

原源端计数和连接归属断言保留：根枚举 1、表枚举 1、工作区检测 2、其他 0，reset 不变；绑定被锁 PID 的完成语句与统计增量必须完整对账，缺记录或额外调用均失败。源账号快照继续完整保留，不减去猜测的健康探测。正式连接探测沿已有独立控制窗口，仅一次 `version_probe` SQL 增量，并绑定同一 System 会话的空 Ping。只将精确 `;` 和 `-- ping` 视为协议空查询；注释后附真实 SQL、未知来源、重复或缺失记录仍失败。原始 SQL、参数和凭据仅在隔离私有目录，不进入公开报告。旧固定版本复现与历史结果见[连接归属与空 Ping 证据](../evidence/数据保护与执行血缘历史证据.md#pg-连接归属与空-ping--完整-hosted-t4)。

失败清理先关闭本轮全部已登记任务的调度，对本轮在途执行显式取消并释放测试锁，等待真实终态后才删除精确任务和源夹具，核对无活动 execution、任务、锁和临时 schema。未知创建响应只通过本轮唯一名称、租户、引擎、创建人恢复；禁止误清理外来任务，清理失败使整轮失败。保留执行历史，源 Grant 在整个集中扫描场景前后逐项不变。迁移另由 PG T2 验证保留配置历史、关闭旧调度、经 Owner 取消旧执行、不创建新执行、不补人员权限。

标准入口仍为 `make test-pg-authorization-online-runner`；T4 复用已登记 suite 和 Hosted 编排，不新增依赖或兼容入口。不设置定时跟进，不操作个人环境。只有新固定提交、完整业务断言及失败清理的实际结果才能计作本轮通过。

### 审计尾延迟诊断

System 慢解析诊断的阈值、字段、日志安全与池等待归因边界见 [AuthContext 解析诊断](../../../../system/docs/IAM数据模型与迁移规范.md#authcontext-解析诊断)；本节只维护 Hosted 观察方法，不把诊断日志当作运行验收结果。

固定目标裁决采样期间，由同一 Hosted suite 的只读观察连接以 50ms 目标间隔采集 `pg_stat_activity` 的等待类别、事务／查询时间、阻塞 PID，以及 WAL、数据库 I/O、checkpoint 累积计数；同时保存 Linux 磁盘计数与 I/O pressure。只在本轮全新 disposable Infra 启用 `track_io_timing` 和 `track_wal_io_timing`，不改变 `fsync`、同步提交、权限或审计持久化方式。观察连接强制只读、固定 `addp_online`，不输出 SQL 正文、参数、用户数据或凭据；请求时间窗与只读查询所得的审计编号关联，保留预热标记。采集有样本、字节和时限预算，失败、中断及超时须关闭观察连接；缺少证据不能解释为零等待。诊断带来的额外开销须单列，不能直接替代无观察器的基线，也不能将二者差异归因为优化；WAL／磁盘计数是实例／设备级证据，不能仅凭同时增长归因到某个请求，未复现也不能认定历史峰值已修复。确定性采集、准入和失败清理由既有 `make test-pg-authorization-online-runner` 覆盖，真实查询与资源证据由同一 Hosted T4 验证，不另建 suite 或接入个人开发环境。

### 授权生命周期与来源

生命周期、来源和新成果的固定版本证据统一见[规则与分版本证据](#规则与分版本证据)。

#### 隔离夹具与身份边界

PG 源数据授权生命周期使用独立 `pg-source-authorization` T4 suite，经 `make test-online ONLINE_SUITE=pg-source-authorization` 在 GitHub Hosted disposable 部署执行。复用正式 IAM 夹具、共享 Hosted 生命周期及已有 PostgreSQL 业务源，不连接个人开发库。办理 User 与消费 User 分离，前者仅具备本场景办理资格，后者只具备 Meta 基础扫描／目录和 Manager 读取功能权限；消费 User 不获得签发或委托资格。

本 suite 的消费、办理、业务确认和组织维护身份均须使用当前 Tenant 的功能角色分配；AuthContext 中每条角色 Scope 必须精确为当前 `tenant_id` 的 `tenant`，缺失、跨 Tenant、Platform 或已退役的 Department / Project Group Scope（包括遗留字段）均拒绝进入验收。组织事实仍从独立 `organization.departments` / `project_groups` 核验，退出成员前后角色与功能 Permission 不变，不能用删除组织投影或扩大功能权限替代组织来源判定。

#### 单表授权生命周期

对单张普通表验证未授权拒绝、有限期 Grant、重复签发拒绝、精确 basic 强制重扫后身份与边界不变、撤销和自然到期；直接批准阶段的相邻已扫描表保持未授权。读取须经过真实 Manager 预览，不用 System read-check 成功替代；同一消费凭据跨自然到期前后使用，不调整时钟或手工撤销代替到期。

#### 个人与组织来源

同一 PG suite 还验证同一 DataItem 上的个人、部门和项目组三种独立来源：普通成员与无成员关系的同权限旁观 User 分离，组织成员关系在正式 IAM 夹具中先建立、再签发会话，不扩大办理或消费 Permission。当前授权查询须准确合并三种来源，全部记录按直接接收主体筛选；逐项撤销个人／部门来源不能误删项目组来源，最后一个有效 Grant 撤销后默认拒绝，不存在个人排除或 Deny-only 入口。

每个阶段均与真实 Manager 预览对照，旁观 User 和相邻表始终拒绝；失败或中断按本轮全部接收主体清理，不能只清个人 Grant。

#### 成员退出与 API 重新登录

另以夹具已有的租户管理员独立执行成员查询／结束命令，通过正式 IAM API 依次结束消费 User 的部门和项目组关系，不创建含受限 IAM Permission 的自定义角色：每次变更后旧 Access Token 在 AuthContext 和 Manager 预览均须返回 401；同一账号经正式登录取得当前凭据后，退出部门仍可由项目组读取，退出最后一个组织则拒绝读取。身份、Tenant Membership 和四项消费 Permission 不变，当前来源随成员关系减少，组织 Grant 及直接历史保留，不能把成员退出实现为全组撤权。

#### 成员退出后的浏览器刷新

同一场景还保持真实 Console／Manager 浏览器会话打开，在两次成员退出后通过页面重读触发既有 401 静默刷新：每次只轮换一次 Refresh Cookie，Console 与 iframe 的身份和新 Token 收敛，保留同一 iframe、路由和资源选择，不重复登录或误跳页面级 Forbidden；仍有项目组来源时继续显示两行夹具数据，最后一个来源消失时显示数据项级拒绝并清除旧行。

控制协调只传本轮标识和阶段，不传 Token；原始 Playwright 输出及失败附件留在 Secret 目录，公开报告只保留状态与计数。此成员退出阶段不包含业务批准；Catalog 批准在后述独立阶段验收，其他引擎不在本 suite 范围内。

#### 读取功能权限反向门禁

同一 suite 复用已有业务确认 User 验证“有数据 Grant、无读取功能权限”的反向门禁，不新增账号或功能角色。该 User 的当前 AuthContext 须精确保持原 Catalog 确认权限，不包含 `manager.data_item.read`；办理 User 只向其显式签发本轮 PG 单表限时 Grant。正式签发历史在读取前后均须证明同一 Grant 当前有效且完整绑定 DataItem，Manager 真实预览仍返回 `403/permission_denied`，且响应仅含错误、不泄露数据或元数据。

拒绝不能通过自动撤销 Grant 或伪装成源规则／Security 拒绝实现。验收后显式撤销该 Grant 并核对历史；任一阶段失败仍由原有全接收主体清理路径回收，不改变账号功能权限、不借用其他账号凭据。

#### 新成果初始授权

新成果场景的物理连接必须允许在本轮独占业务数据库中新建表：共享 PostgreSQL fixture 仅在 `pg-source-authorization`、Hosted 测试标记及 `addp_online` 隔离环境同时满足时，向登记的连接账号增加 `public` schema 的 `CREATE`，不授予既有源表的 INSERT／UPDATE／DELETE／所有权或超级用户权限。其他 suite 继续使用只读连接。新表由该连接账号创建并拥有，物理访问条件与平台 User 的功能 Permission、DataItem Grant 分别核验，不能把数据库建表失败当成自动授权拒绝或签发完成。

该 suite 在原授权与工作区场景之后，还使用已有消费 User 执行一次 PG 新成果同步；仅补充 Transfer 任务创建／读取／执行／删除及派生 Execution Authorization 的功能 Permission，不给消费 User 签发或委托资格。Hosted 部署增加 Transfer Backend／Worker，System、Meta、Transfer 各用独立 Service OAuth Client。输入为本轮精确限时授权的 `metric_people`，输出为随机唯一的新 PG 普通表；关闭任务自带扫描，核对 Meta 确实产生一个仅识别该叶子的 basic 子执行。

物理任务成功后后台须自动签发唯一 `task_production` Grant，绑定原执行、DataItem／边界、人类来源及独立机器签发者，期限与唯一输入来源相同；不借用机器凭据直接触发签发。Manager 实际读取两行，旁观账号仍拒绝；撤销源 Grant 后成果继续可读，撤销成果 Grant 后拒绝。

失败恢复只查询本轮已捕获任务的执行及精确目标历史，先关闭源授权再核清可能丢失响应的成果 Grant，最后删除任务定义；历史留存，物理新表随独占业务容器销毁。此新成果段必须以新一轮真实 T4 证据验收，不能复用旧授权生命周期的通过结果。

#### 公共清理与证据要求

失败或中断按原命令编号收权，核对无当前来源，并由 Hosted 生命周期销毁本轮账号、源容器和 Infra。

报告仅保存身份引用、状态、行数和边界摘要，不保存凭据或原始数据。凭据只保存在 owner-only 临时文件和进程内存。

确定性反例与生命周期清理由 `make test-pg-authorization-online-runner` 验证并纳入 Online/Platform 门禁；首次真实 Hosted 通过前保持手工触发，不计为已完成 T4，不加入夜间调度。

#### Catalog 集合的确定性验证

Catalog 的既有 PostgreSQL 门禁另经真实 HTTP 路由验证集合功能 Permission 与资源范围独立：同一组 Tenant 功能 Permission 下，当前项目组成员可以访问集合，退出后集合列表／详情不可达，集合及成员条目事实仍保留；部门目录可见性独立限制集合内条目，失去部门成员关系不删除集合条目。缺少功能 Permission 时，即使仍是成员也不能读写。该层只组合真实 Catalog PostgreSQL 与受控 AuthContext fixture，不代替真实 OAuth 和 PG 源内容读取的 T4。

### 读取裁决性能采样约束

下述串行与并发样本共用本节要求，各自的目标、轮次、操作数、时机和预算见对应小节；观察器的隔离、敏感信息保护、额外开销及证据归因统一见[审计尾延迟诊断](#审计尾延迟诊断)。

- 复用原消费 User、凭据与有效测试 Grant，不延长原授权期限、不刷新身份、不重试失败请求。身份、规则或目标漂移不得计为有效基线；HTTP 拒绝、传输失败、异常响应或预算耗尽即失败，保留已采样计数并沿原 finally 清理，不改变既有读取、浏览器及收权断言。凭据只在内存比较，不写入报告。
- 正式 `POST /system/engine-access/read-checks/manager-preview` 成功响应必须只有有效 `observed_at`；该精确 POST 仅作只读裁决，不签发权限，不替代 Manager 真实数据读取。耗时包含 GatewayClient 从发出 HTTP 到 JSON 解码结束的完整往返、身份解析及内部 Meta 事实查询，不等于纯规则计算或 SQL 自耗时，也不与旧服务端整数毫秒日志直接做回归比较。
- 报告保留毫秒原始样本和预热／成功／失败计数；预热不计入分位数，失败不计为有效性能样本。按 nearest-rank 计算每轮与合并样本 P50、P95，并列出轮间范围；不以自动删异常值或性能阈值制造稳定结果。
- 确定性验证使用既有 `make test-pg-authorization-online-runner`，真实样本由原 PG Hosted T4 产生；仅用 disposable 账号与原测试授权，不使用或变更个人开发环境的持续授权，不新增 suite、入口、依赖、权限或生产 API。方法与确定性检查不构成真实采样通过证据。

### 固定目标读取裁决性能样本

在首个既有限时单表 Grant 已验证可读后、重扫及撤销场景之前，复用 `public.metric_people`，串行采集三轮各 500 次正式请求，共 1500 个正式样本。每轮另做 10 次预热；请求间隔 10ms、轮间间隔 1s 均不计入请求耗时，全段预算 90s。

每轮前后核对同一 AuthContext、完整有效 Grant 历史和 DataItem 组成边界，适用[共同采样约束](#读取裁决性能采样约束)。

### 小规模并发与两目标批量性能样本

复用新成果段已经有效的源表和成果表 Grant，在撤销源 Grant 之前采集，不新增账号、表或授权。对单目标和两个不同 DataItem 的批量裁决分别测最大在途数 1／5／10；另以串行的两次单目标请求作为两目标操作对照。每个单元三轮、每轮 10 次预热和 100 次正式操作，整段预算 90s；闭环线程每次完成后才发下一次。记录实际在途峰值、原始操作耗时、HTTP 请求数、墙钟时间及观测吞吐，统计与失败判定沿[共同采样约束](#读取裁决性能采样约束)；两次单目标操作的耗时包含两次完整往返，批量耗时是一请求覆盖两个目标，不将除以目标数后的数值冒充单次裁决耗时。

每单元前后核验同一 AuthContext、两个目标的完整有效 Grant 历史及 Meta 指纹／边界，前后必须一致。并发段复用同一只读观察器，单独生成 `pg-load-waits.jsonl`，保留原 50ms 目标间隔、95s／2000 样本／32MiB 上限；同时保存主机 CPU 计数、CPU／I/O pressure 和负载，不更改同步审计。并发审计编号仅按阶段／单元时间窗核对完整数量，不根据提交顺序伪造单请求关联。旁观账号的整批请求须返回 403 且无数据；源 Grant 撤销后，同一消费账号的两目标批量必须因包含一个未授权目标而整批拒绝，成果本身仍按原场景可读。观察连接和线程必须全部结束后才执行原 finally 收权。该样本仅表示同账号、两目标、小规模闭环负载，不证明多用户、高基数批量或生产容量。

### 依赖故障、直接授权与内容变化

固定 `c8977cecb` 的通过、原件、清理与未覆盖项见[规则与分版本证据](#规则与分版本证据)中的旧许可模型记录；System 并发 T2、确定性 runner 和真实 T4 分别认定。

#### Security 首次保护投影

PG Hosted 部署必须启动 Security，并将其纳入同一构建版本的 Ready 核验；Security 先于 Manager 启动。新测试 Tenant 在服务启动后创建时，须在第一次 Meta 扫描之前，经共享 `online-api.wait_manager_read_boundary` 对正式 Manager 引擎读取接口有界等待首次保护投影同步，并核对精确目标引擎。

仅初始化中的 `security_protection_required` 可等待；其他授权拒绝、异常响应或超时立即失败，不改生产同步周期。源数据未授权必须在保护前置条件已满足后由 System Grant 链路拒绝；`security_protection_required` 不得作为未授权验证通过，也不能通过跳过保护、补写 checkpoint 或扩大消费权限绕过此依赖。

#### Meta 事实依赖离线与恢复

PG 同一 suite 另覆盖 Meta 事实依赖短暂离线与恢复：只在 disposable Hosted 部署通过标准生命周期停止／启动 Meta，不改变源表、DataItem 边界、IAM 权限或凭据。已有有效 Grant 时，事实查询与 Manager 读取须明确返回依赖不可用，不回退原生读取，也不伪装未扫描；离线期间不创建替代授权。恢复后不重扫，数据项身份、批准摘要与原 Grant 历史不变，原有效 Grant 恢复实际读取，未授权相邻表仍拒绝，最后撤销并清理。

故障操作有 Hosted 准入、超时、真实监听及进程身份验证；失败时仍尝试恢复 Meta 并清理本轮规则。此项是事实依赖可用性验收，不计为同身份组成边界扩大或列授权验收。

#### Catalog 业务批准闭环

PG 业务批准沿用同一 suite，在上述阶段完成后，对此前未授权的相邻单表验证业务批准闭环。隔离部署增加 Catalog，仍不启动 Asset／Portal 或扩展其他引擎。独立业务负责人仅具备目录读取、盘点、编目和共享确认权限；办理 User 另具备目录读取、盘点与独立办理权限，消费 User 的权限保持不变。

使用正式基础扫描变化自动建档、编目责任、共享边界核对、业务确认与办理 API，经 Catalog／System 各自 OAuth 身份自动受理和签发；验收脚本不持有机器 Token、不直接写批准或 Grant。不配置逐数据项直接授权许可；业务请求只绑定业务批准及 Meta 边界。

仅业务确认时实际读取仍拒绝，签发后核对相同 DataItem 指纹、边界、接收方、期限及唯一签发历史，并由 Manager 读取确定性数据；同参重试不重发、续期或复活撤销。撤销继续复用 System 的同一路径，未显式获权的旁观 User 不能读取。

所有写入编号在发送前登记；失败、中断也按本轮目标清理规则，并随 Hosted 生命周期销毁账号及目录事实。此阶段补充业务批准闭环，不把只读签发历史当作实际访问证据。

#### Catalog 可选依赖离线与恢复

Catalog 可选依赖的故障验收复用上述 PG 业务 Grant、同一消费凭据及单一 Hosted 故障协调器：标准停止 Catalog 后，Manager 仍能凭原 Grant 读取，System 原签发历史不变。新的 Catalog 办理请求须明确返回模块／代理不可用且不产生 Grant；有办理资格的人员可以独立提交直接授权命令，精确授权给旁观账号，验证读取后撤销。不能将失败的业务请求自动转成直接命令。

Catalog 离线期间仍可撤销原 Grant，实际预览验证撤销后的拒绝；恢复 Catalog 后同参重放原已签发请求不得复活撤销，新失败请求不得产生受理或签发。停止／恢复均核验真实监听、同构建新进程及其他 owner 未重启，失败仍恢复并按预登记编号清理。不重扫、不修改持久模块启用声明、不新增角色；不将未受理的新请求与停机前已受理、可沿原窗口续办的请求混淆。

#### 普通表内容变化

PG 正常内容变化继续使用该 suite 的同一普通表及消费凭据：Business 隔离夹具仅执行固定的行新增、更新、删除与基线恢复，不增加平台写权限或访问个人业务库。每次变化后只对该表执行 `basic + force` 扫描，核对 Meta ID、fingerprint、授权边界和原 Grant 历史不变；有效 Grant 可由 Manager 读到变化后的确定性内容，恢复源基线后仍按原有效 Grant 读取。

撤销 Grant 后再次改变内容、基础重扫及重放原命令均不得恢复读取；旁观账号与相邻表始终拒绝，最后恢复源基线，失败或中断仍回收规则并销毁本轮容器。该场景是 single 数据项的内容更新验收，不计为同身份组成边界变化、列授权或 multi／whole 验收；同身份变边界的 Grant 匹配继续由已有 System PostgreSQL 判定层测试覆盖。

### 授权工作区与办理身份

#### 正式身份与办理角色

PG 授权工作区浏览器验收复用同一 Hosted suite、隔离表与正式登录入口。办理夹具组合既有“数据授权办理员”内置角色，获得引擎、资源树和三类接收候选的只读查询权限；不把不可自定义的权限塞入自定义角色，不增加消费账号权限或办理账号的数据读取权限。

统一“数据授权办理员”内置角色同时承载直接批准和业务确认后的人工办理，PG 夹具的这两项业务办理依赖（`catalog.entry.read`、`system.engine_access_fulfillment.create`）必须来自正式内置角色，不能重复塞进补充自定义角色。

权限目录由 `make test-authorization` 校验；前向迁移、原角色分配保持、已分配主体授权版本推进、旧会话回收及重复启动不再变更由 `make test-system-iam-postgres SYSTEM_IAM_POSTGRES_TEST_ARGS="--package migration --test unified-data-authorizer"` 验证，既有全量 IAM PostgreSQL 门禁自动发现这些测试。

该角色组合不替代业务确认和引擎范围检查，也不自动获得数据 Grant 或引擎管理委派。直接签发不要求逐数据项许可。

#### 工作区前置清理

成员退出场景保留的组织 Grant 属于该阶段的必要验证事实，不能假设后续列表只有个人来源。工作区场景开始前须复用同一生命周期的收权与残留核验，撤销本轮尚有效的个人／组织来源，保留全部签发与撤销历史；核验归零后才签发工作区预登记的单表 Grant。前置清理失败即停止，不进入浏览器或新增 Grant。最终清理仍覆盖本轮全部编号，不得为满足列表计数删除历史、改变成员退出规则或忽略其他来源。

#### 授权视图与实际撤权

“新增授权、当前授权、全部授权记录”三个互斥视图须保持同排；新增授权在 Meta DataItem 树中勾选或取消；节点默认直属项，显式递归包含下级当前项，筛选不缩小节点覆盖范围。选择只形成草稿，不签发 Grant；完整准备后批量确认，失败按原逐项命令恢复。当前授权同时验证表名输入、树叶精确过滤、接收方类型与具体账号过滤及来源展开；全部记录保留有效、撤销与到期语义。脚本预登记单表限时 Grant 后，办理账号在真实 System 页面撤销，当前列表应移除来源、全部记录保留原编号及撤销状态，同一消费浏览器凭据重新读取 Manager 时应拒绝并清除旧行。

#### 导航零写入与请求分类

该场景的浏览器变更检查按已核实的 API 语义区分请求：精确目标引擎的 `POST /catalog/children` 与 `POST /authorization-nodes/query` 是资源树／节点身份读取，不计为授权写入；此场景其他非 GET 引擎请求仍全部进入变更检查。不得用“所有 POST 都是写”误判选择器，也不得扩大排除范围以漏掉 Grant 或委托操作。导航阶段必须零写入；最终授权规则变更仍仅撤销预登记 Grant。

#### 直接授权许可退役（2026-10-31）

删除逐数据项许可接口、Tab 与存储，停用相应功能权限并移除角色关联；此前许可变更验收仅保留历史证据，不再作为现行门禁。前向迁移核对旧 Grant、撤销、Deny 与业务办理记录清零，通用审计和角色分配保持不变，移除功能权限后已分配账号授权版本推进、旧会话失效，重复启动不再次变更。新版已通过 System Go T1、migration／engineaccess／API PostgreSQL T2、170 项前端单测、89 项授权工作区浏览器测试及构建；Console 重认证 5 项通过。新版本的跨服务 T4 与开发库升级尚未验证，不复用旧许可模型的通过结果。

### 文件组成批准的确定性边界

#### 文件组成 Grant 与当前读取 T2

FTP IFC／3DS 的直接批准及当前源读取共用既有不可变 Grant 和 DataItem 规则，不新增文件 ACL。定向 T2 使用 `make test-system-iam-postgres SYSTEM_IAM_POSTGRES_TEST_ARGS="--package engineaccess --test file-composition"`，并由原 engineaccess 全量门禁及 System CI 自动发现。

该测试在独立 IAM 测试 schema 中核验完整组成快照、旧 A Grant 不覆盖新 B、新 B 明确重新授权后才允许、旧生成组成与当前组成／Engine 版本不一致时拒绝、Meta 不可用和最终撤权拒绝。重新批准须沿原关系撤销后使用新命令，不允许 A／B 同时保有一条未到期关系；历史组成保持原样。

上述 T2 的 Meta 事实和精确源目录核验为受控夹具，不是物理 FTP 运行证明，也不涵盖 GLB 的正式执行授权、文件 Catalog 办理、文件任务产出初始授权或前端选择器。真实文件内容链必须由 [FTP 原 Online suite](同步与引擎消费.md#ftp-普通-user-消费ftp-consumer-flow) 在同版本部署中另行核验，不以 PG 的有效 T4 或共享类型测试代替。

#### GLB 与剖析的源执行授权 T2

`make test-system-iam-postgres SYSTEM_IAM_POSTGRES_TEST_ARGS="--package engineaccess --test manager-source"` 同次覆盖既有剖析与 FTP GLB 两用途的正式 IAM／源规则核验，避免共用内核改动只验证新用途。

GLB 负例包括跨用途、同 UUID 改 TTL、原签发审计唯一性、残缺／替换 claim、配置或 Engine 版本变化、审计失败无连接返回及撤销后不复活。

连接是当次已核准 Engine 的纯解密快照，不再次查询；Meta／连接投影仍为受控夹具，此定向 T2 不计物理 FTP、转换器或完整 Worker T4。

#### 共享协议、API 与选择器验证

共享严格 wire 与 HTTP 凭据限制由 Common／System Go T1 验证，IAM 门禁的定向选择器由 `make test-system-iam-runner` 验证。

API 的普通 User 双功能 Guard、固定 Manager Service、严格 JSON 及 no-store 由 System T1 覆盖。

#### 专用环境与当前身份

Host Gate 全量启动 System、Gateway、Meta、Catalog、Asset 和 Portal，并通过 `business/scripts/online-engine-fixture.sh` 幂等准备 `public.addp_online_catalog_fixture`。

真实 User Access Token 先经 System AuthContext 验证 Tenant 和精确 Permission，所有业务请求只经 Gateway，不直连 owner 或直接 SQL。

企业资源目录发布类 T4 使用同一永久 PostgreSQL Engine Instance 及其 owner 生命周期入口创建的稳定表 `public.addp_online_catalog_fixture`。

#### 目录初始化与来源幂等

专用环境必须预置可引用的 Standard Domain 和 Department。suite 触发 Meta 扫描，以 DataItem fingerprint 等待唯一 CatalogEntry 自动建档；首次运行可使用预置 Domain、Department 和当前 User，将该永久数据源对应的 `discovered` CatalogEntry 初始化为稳定 `curated` fixture。后续运行对同一 CatalogEntry 执行临时编目，并在 `finally` 恢复原完整聚合。

同一 suite 必须重复执行真实 Meta 扫描并证明 fingerprint 与 CatalogEntry UUID 幂等，验证 `inventory` / `governance` 视图、治理覆盖率固定维度和精确来源身份解析。

#### 资产发布与临时资源清理

以 CatalogEntry UUID 创建 AssetComponent，发布后由 Portal 返回同一身份，并通过 AssetCategory 目录树和分类子树列表发现该 Asset；真实浏览器随后打开同一分类页，确认目录名称和唯一 Asset 卡片。

每轮 Asset 经 `published → offline → deleted` 正式生命周期清理；suite 先确认空 AssetCategory 已从 Portal 目录树消失，再删除 Asset-owned 目录，双方 GET 404 与 Portal Asset 404 共同证明零临时残留。

临时资源只经正式 API 清理，不直接 SQL 清理。

#### 来源展示与共享历史浏览器

真实浏览器使用同一专用 User 登录 Console，验证覆盖率页、目录详情与 Domain / Department / Engine 名称选择器，并将浏览器 warning/error 计入失败。

浏览器同时以该次登录得到的 User Token 读取当前 CatalogEntry 和本轮已经生成的精确共享确认，不创建额外账号、决定或授权。技术来源在 1440px、900px 下核对接口返回的引擎名称/类型、数据项名称/类型和完整路径，验证双列宽度、长指纹省略、悬浮/聚焦全文、Tab 移出关闭及刷新恢复；这些布局和提示断言与 Console 的受控夹具 T3 共用同一测试 helper。

共享历史核对同一确认的接收方姓名、返回的可选账号编码及“当前账号”标记，刷新后仍一致；候选另行核对姓名和登录名，只读选择当前账号而不提交业务命令。

登录和匿名初始化诊断复用既有浏览器 helper，首次匿名 Refresh 401 单列且最多一次，认证消费开始后的 API 失败仍使验收失败。浏览器报告使用唯一 `addp.enterprise-catalog-publishing-browser/v3` 契约，必须包含来源展示、两种视口、刷新及当前账号断言，并绑定本轮确认编号；缺项、错误布尔类型或新增共享命令均使验收失败。确定性报告校验通过不代表专用 Runner 的真实 T4 已执行。

#### 弃用与责任变更

该 suite 同时在上述专用 Catalog fixture 上验证 `curated → deprecated → curated`，以及已弃用阶段的责任子资源更新。使用现有专用 User 增加或移除可选技术负责人，使责任集合发生实际变化；不为验收新增账号、部门或赋权。断言移交仍保持弃用、业务定义、语义、可见范围设置和来源身份，撤销弃用不恢复认证，旧版本请求返回 `409 catalog_entry_version_conflict` 且无副作用。

成功和失败路径都经正式 API 恢复完整编目聚合并重新读取核对；写响应丢失时先读当前状态，不重试原命令，恢复失败使整个门禁失败。审计和并发版本不回滚，跨部门移交后的可发现范围及权限交集继续由 Catalog T2 验证，不以单账号 T4 冒充。

#### 普通只读共享受理

该 suite 还验证普通只读共享的正式准备、真实双服务 OAuth 反查与首次受理。专用 User 必须是 fixture 的当前业务负责人，显式具备共享确认、独立办理 Permission，并由管理员预置当前有效的引擎管理委派；测试不自动赋权或创建委派。

专用部署须配置独立 `SYSTEM_SERVICE_CLIENT_SECRET`，未配置在生命周期启动前拒绝验收，不改变普通部署允许留空的 Ready 边界。业务办理不查询、不初始化或改写直接授权配置。

正式请求显式限时十分钟，办理窗口仍从首次受理起最多五分钟。决定同编号换用途、办理同编号换决定须返回 `409 catalog_sharing_decision_conflict`，拒绝后原决定／原回执必须不变；不新增决定或办理编号。此拒绝允许产生操作审计，不能以场景预期数量代替数据库计数验证。

同参重放必须保持完整绑定、受理时间及截止时间不变；调用方丢弃已提交响应后恢复只证明调用方边界，不冒充 Catalog→System 网络中断或进程重启。人类 Token 访问机器反查／受理接口必须拒绝；`pending`、绑定错误或恢复失败不能计为通过。

受理回执不等于 Grant 写入或实际可读；本 suite 通过[OAuth 自动签发的只读观察](#oauth-自动签发的只读观察)核对后台签发，不借用机器身份直接写 Grant，也不验证源数据实际读取。

不可变业务决定、已核清的办理记录、System 回执，以及自动签发的 Grant 和签发审计，均作为专用 Tenant 的长期审计事实单列，不按临时 Asset／AssetCategory 删除。

### OAuth 自动签发的只读观察

企业目录发布的 `enterprise-catalog-publishing` 沿用专用 macOS profile：正式 User 发起共享受理后，生产 Catalog 通过自己的 OAuth 服务身份自动签发。

验收脚本不借用该身份，System owner 的现有 Online 测试夹具仅以只读可重复读事务核对精确 Tenant、Engine、请求编号的受理、Grant 和唯一签发成功审计；原参重试后再次核对签发时间与审计次数不变。

报告的 `grant_write` 通过必须依据同一原受理窗口内恰好一条 Grant 和一条成功签发审计；`source_content_read` 仍为 `not-run`，不能由受理或历史签发推断实际可读。

该观察模式只允许回环 `addp_online`，禁止初始化身份、执行迁移或写入，不是人类 API、Catalog Grant 副本或访问裁决。

确定性协议与准入测试归 `make test-online-runner`，真实 PostgreSQL 查询及只读拒写归现有 `make test-system-iam-postgres`，完整 OAuth 链路仍须在现有手工 T4 suite 真实执行后才能计为通过。

## workbench-service-consumption

1. Host Gate 全量启动 System、Gateway、Service、Workbench 和 Console；`business/scripts/online-workbench-mysql-fixture.sh` 使用外部环境变量启动 `business-mysql`，重建仓库既有 `customers + orders` 确定性数据并创建仅有 `SELECT` 的专用账号，同时为 Playwright 安装专用 Chromium。
2. 专用环境长期预置指向该账号的 MySQL Engine Instance，身份由 `ADDP_ONLINE_WORKBENCH_MYSQL_ENGINE_ID` 提供；suite 不创建、修改或删除 Engine Instance。
3. 两个真实 User Token 各自先校验 AuthContext，均属于同一 Tenant，且不得是个人会话或平台管理员 Token。非管理员专用 User 不含管理员角色，只具备 Service/Workbench 场景权限，负责发布与消费；独立 `ADDP_ONLINE_TEST_TENANT_ADMIN_ACCESS_TOKEN` 必须属于 User、含 `tenant.administrator` 角色并具备当次 API 消费方生命周期所用权限，仅负责消费方及凭据生命周期。
4. 非管理员 User 的所有平台操作只经 Gateway：检测 SQL 输出契约，发布私有主 Query Service `commerce-order-analysis` 和同契约未授权 Query Service `commerce-order-analysis-denied`，读取主服务 Consumer Descriptor，创建 Data Application 草稿并执行查询。SQL 只 JOIN 既有表并排除姓名、邮箱、电话和地址；MySQL 将 `BOOLEAN` 暴露为 `TINYINT`，publisher 只把已知语义的 `active_customer` 显式发布为 `bool`，Service 再按冻结契约归一化 `0 | 1`。
5. Tenant Administrator 只经 System 正式 API 创建一个仅授权主 Query Service 的 API 消费方及一枚凭据，按下文[API 消费方身份与数据面](#api-消费方身份与数据面)核对成功、越权拒绝和删除后的凭据失效。
6. API 层还要验证 `order_no` cursor、五类动态筛选、decimal/boolean/timestamp/null、完整有限 CSV，以及无 SpatialInfo 时 Map 不可用。浏览器使用非管理员专用 User 登录 Console 并核对浏览器 AuthContext 与 API User 身份一致，在同一应用草稿中依次打开两个 Component 的正式编辑器，验证 Table 两行结果、Chart canvas 和无空间契约下不存在 Map。
7. 浏览器经正式 Service API 更新主服务的公开默认字段策略以改变 `contract_fingerprint`；刷新同一应用后 Component 编辑器必须显示契约变化告警并禁用预览查询。API 层同时确认已保存快照仍持有旧指纹，不增加 Workbench 执行 API 或测试旁路。
8. `finally` 只按本轮捕获 ID 删除 API 消费方及其级联凭据、未发布 Data Application 和两个 Query Service，并逐项验证 404 或凭据失效；Fixture 和全套 ADDP 再由 Host Gate 统一停止。最终发布运行态由 Outdoor 双服务场景验收，不能为自动清理增加已发布应用强删旁路。

### API 消费方身份与数据面

API 消费方数据面边界由 `workbench-service-consumption` 复用同一 Business MySQL Fixture 和临时 Query Service 验收，不另建平行 suite。凭据只保存在 suite 进程内存；报告、日志和错误不得包含完整 API Key。

| 核对项目 | 实际请求与判定 |
| --- | --- |
| 已授权服务 | 主 Query Service 返回 200。 |
| 同 Tenant 未授权服务 | 同契约未授权 Query Service 返回 `403 api_consumer_service_denied`。 |
| 控制面拒绝 | `GET /api/v1/system/tenant/api-consumers` 返回 `401 api_consumer_control_plane_denied`。 |
| 删除后的旧凭据 | 删除 API 消费方后，旧凭据调用主 Query Service 须在 45 秒内收敛为 `401 api_consumer_credential_invalid`；超时失败。 |

控制面统一拒绝规则见 [Gateway 认证边界](../../../../gateway/docs/gateway架构说明.md#2-路由平面)；本场景只验证表中控制面请求，不代表所有 `/api/v1/*` 路由均已逐项验收。Gateway 30 秒正缓存和 Service 逐请求复核见[缓存与撤销](../../../../gateway/docs/gateway架构说明.md#4-缓存与撤销)；45 秒为本场景的撤销收敛上限，凭据可提前失效。

### NFS FileGDB 整容器授权（2026-10-29 接入范围）

whole 身份与精确组成规则见[授权目标契约](../../addp授权上下文规范.md#557-dataitem-授权的统一目标契约)。本用例仍复用 FTP 授权 helper；其源 Deny Permission、建立／释放和 Deny inspection 断言尚未对齐现行退役契约，不能把旧版检查总数或历史通过当作当前新模型闭环。退役分界与历史解释统一见[退役规则与历史证据](../evidence/数据保护与执行血缘历史证据.md#退役规则与历史证据)。

固定版本的检查总数、失败、清理与未覆盖项以历史记录为准：[原始成员](../evidence/数据保护与执行血缘历史证据.md#nfs-filegdb-原始成员授权--hosted-t4-通过)、[整目录 ZIP](../evidence/数据保护与执行血缘历史证据.md#nfs-filegdb-整目录-zip-下载--hosted-t4-通过)、[浏览器保存与截图时序](../evidence/数据保护与执行血缘历史证据.md#nfs-filegdb-浏览器保存--同响应字节验收)、[子表单元格与切换](../evidence/数据保护与执行血缘历史证据.md#nfs-filegdb-子表单元格与切换--hosted-t4-通过)。各版本分别认定，不跨版本累加，也不把子表切换通过外推为分页已验收。

本节导航：[接入与身份](#接入与身份) · [内容读取与下载](#内容读取与下载) · [浏览器渲染与保存](#浏览器渲染与保存) · [故障恢复与清理](#故障恢复与清理) · [标准入口与覆盖范围](#标准入口与覆盖范围)。

#### 接入与身份

- 本专项复用 `manager-internal-artifact-lineage` 的手动 `filegdb-authorization` case 与 `make test-manager-online-runner`。仅用 NFS 和 GeoPython Runtime；独立消费 User 只有六项读取／扫描／执行观察权限，既有 source initializer 办理本轮整项 Grant。Runtime 绑定本轮只读 NFS 客户端挂载而非宿主机源目录；`noac`、`soft` 等选项仅用于隔离夹具，不改变产品默认值。断连前须确认真实路径可读，停服务后须观察有界 I/O 错误，若仍可读或超时则保留失败，不以停机动作替代断连证据。

- Meta 基础扫描形成一个 whole DataItem；授权选择器只读正式身份清单，`.gdb` 显示为一个叶子，不展示内部碎片作为独立候选。精确数据项批量模式选择节点仅展开当前已识别 DataItem，不授予未来独立项。

- `scope` 严格绑定 NFS、DataItem 与 FileGDB 根目录／规则；新增内部子表不改变摘要。不同根、范围外引用、缺失事实及不完整组成均拒绝。签发前复核基础事实及办理资格，浏览器不提交自造 scope。

- 跨账号切片仅为该独占 FileGDB 用例创建同租户独立普通旁观 User，只有 `manager.content.read`、`manager.data_item.read`，不签发任何数据 Grant、不加入部门或项目组、不修改主账号或办理账号权限。主账号 Grant 生效后，对同一完整 locator 的原子表和后续新增子表分别执行“主账号实际读取成功→旁观账号 403 且无内容→主账号仍可读”，旁观账号前后当前关系均为空，主账号 Grant 历史与当前来源不变，同一凭据保持。逐项验证 `ungranted_account_initial_child_denied`、`ungranted_account_new_child_denied`。失败沿原 finally 回收本轮授权／源文件并核对旁观账号无有效关系，临时身份随独占部署销毁；不把缺少读取功能权限、不同租户、Security 未就绪或匿名请求当成此项通过。

#### 内容读取与下载

- 当前用户读取任一子表前校验整项 Grant、撤销、到期和 Security；实际运行时根必须与授权根相同。父容器只显示 Meta 索引，basic 尚无索引时提示未知，不能以服务身份补读源内容。

- 原始成员流与 `storage-assets` 也必须按当前 User 校验同一根 DataItem，完整内容和每次 Range 都不能绕过 Grant、撤销和到期；读成员不变更授权关系。隔离验收覆盖无 Grant 原始成员拒绝、同一 Grant 的成员字节／Range 与跨账号隔离、撤销和自然到期后的原始成员拒绝。保留 finally 清理，不增加账号、功能权限或授权。

- NFS FileGDB 整目录 ZIP 复用上述同一整项 Grant；保留 `.gdb` 根目录、相对层次、成员原名和字节，当前 User 认证请求完整接收后保存。服务端能力查询须声明实际可下载及 `requires_current_user=true`，不以引擎具有内容读取能力推断所有格式可下载。沿同一 case 验证无 Grant ZIP 拒绝、同一 Grant 覆盖容器内新增子表的 ZIP、旁观账号隔离、撤销与自然到期拒绝、故障恢复与临时包清理，并验证真实浏览器成功下载与未授权／撤销／到期拒绝，全部断言及 finally 清理必须通过。ZIP 按物理源快照独立核对成员集合、CRC、逐成员 SHA-256 和附件头；Manager 崩溃／NFS 断连后仍用原 Grant 恢复下载，逐次请求及最终核对本轮 Manager 不残留临时包描述符。源变化、请求取消及打包中读取失败由确定性 Go T1 核对终止交付和临时包清理；页面按钮、当前账号认证、错误不保存及附件原名由 Manager 前端 T3 核对，不以这些受控证据替代真实 ZIP 的 T4。

#### 浏览器渲染与保存

- 同一 `filegdb-authorization` case 的已授权浏览器阶段须等待真实子表渲染：按 `label`、`value` 列定位并逐格核对 `initial_points` 两行，再通过真实选择器切换到 `added_points`，核对一行数据及旧行已清除；当前页行数、总行数均须匹配。两次子表请求必须绑定同一 locator、当前 User 凭据，各一次且成功，不补请求或替换响应。两份表格截图及实际 DOM 单元格写入归档，新增 `real_browser_child_cells_and_switch`；不得以下载成功或截图时的行数替代表格内容验证。

- 同一容器分页补验保留原两行 `initial_points` 和一行 `added_points`，仅在隔离夹具的新增子表阶段附加 23 行 `paging_points`，沿用同一整项 Grant。真实页面按默认每页 20 行核对第一页 0–19、第二页 20–22，返回第一页后再次进入第二页；随后切换到 `added_points` 并切回 `paging_points`，两次都须重置为第一页且保持每页 20 行。逐格核对值、当前页行数／总行数、页码、前后翻页按钮状态及旧页数据清除，归档各状态截图；每次 UI 操作只产生一条精确当前账号的子表请求，记录 child/page/page_size，不替换响应或修改页面内部状态。新增 `real_browser_child_pagination_and_reset`，原两次子表读取及全部下载、撤权、到期和失败清理断言保留；旧模型二十四项目标不代表本轮已取得完整真实 T4。

- 真实浏览器下载补验仍复用上述 case、同一普通消费 User 和整项 Grant，保留 API／故障／清理检查。Console 正式登录、真实 Manager iframe 和下载按钮分别核对未授权、已授权、撤权、自然到期四阶段；仅已授权阶段产生浏览器保存文件，并独立解包核对根、成员名、CRC 与物理源字节摘要。拒绝阶段须收到同一 locator 的 403、页面显示错误、无成功提示且无下载事件；当前普通 User Bearer 不进入 URL 或公开证据。页面导航不得写入业务配置或授权，前后 Grant 历史、当前关系与源文件不变，沿原 finally 收权、临时包及部署清理。真实保存与三阶段拒绝均须通过；没有真实浏览器报告不能用既有 T3 或 API T4 代替。

- FileGDB 浏览器下载取证在测试中复制当前页面同一次 `fetch` 响应，原响应照常交给页面；副本与保存的 ZIP 逐字节比较并分别归档，再按源快照核对完整成员、CRC、大小和摘要。每阶段下载请求必须恰好一次，仍核对当前账号 Bearer、无 Cookie／URL 凭据及拒绝零下载。不得调用可能重新请求 URL 的 Playwright `response.body()` 代替原响应，也不使用额外请求、网络替换或产品改动取证。复制失败、缺失、重复请求或字节不同均失败；本地浏览器及 runner 负例通过不代替完整真实 T4。

#### 故障恢复与清理

- 异常补验只作用于独占测试部署：Manager 强制退出／源读取通路中断时，保留源文件与原 Grant，恢复后仍按原授权判权；环境不可用不得记成权限拒绝，也不据此新增产品级自动重试、看门狗或故障收权。FileGDB Runtime 使用 `mounted_path`，只有实际读取路径已不可用才能断言读取失败，停止 NFS 服务但本地绑定仍可读不算断连复现。

- 验收子进程在确认持有本轮临时 Grant 后被 SIGKILL，清理责任仍由存活的外层验收进程和已有 Hosted 生命周期承担。仅回收事先登记的本轮临时 Grant 与合成夹具，核对撤销历史、有效来源归零、源文件及 NFS 导出销毁；保留原读取、新增子表、撤权和自然到期断言。清理失败必须使验收失败，不能仅用部署最终销毁替代应用层收权证据；整机／Runner 失联不在这一子进程场景的保证范围内。
