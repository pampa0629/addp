## pg-source-authorization

### 授权生命周期与来源

PG 源数据授权生命周期使用独立 `pg-source-authorization` T4 suite，经 `make test-online ONLINE_SUITE=pg-source-authorization` 在 GitHub Hosted disposable 部署执行。复用正式 IAM 夹具、共享 Hosted 生命周期及已有 PostgreSQL 业务源，不连接个人开发库。办理 User 与消费 User 分离，前者仅具备本场景办理资格，后者只具备 Meta 基础扫描／目录和 Manager 读取功能权限；消费 User 不获得签发或委托资格。对单张普通表验证未授权拒绝、有限期 Grant、重复签发拒绝、精确 basic 强制重扫后身份与边界不变、Deny 优先及解除、撤销和自然到期；直接批准阶段的相邻已扫描表保持未授权。读取须经过真实 Manager 预览，不用 System read-check 成功替代；同一消费凭据跨自然到期前后使用，不调整时钟或手工撤销代替到期。失败或中断按原命令编号收权、解除本轮 Deny，核对无当前来源，并由 Hosted 生命周期销毁本轮账号、源容器和 Infra。报告仅保存身份引用、状态、行数和边界摘要，不保存凭据或原始数据。确定性反例与生命周期清理由 `make test-pg-authorization-online-runner` 验证并纳入 Online/Platform 门禁；首次真实 Hosted 通过前保持手工触发，不计为已完成 T4，不加入夜间调度。

同一 PG suite 还验证同一 DataItem 上的个人、部门和项目组三种独立来源：普通成员与无成员关系的同权限旁观 User 分离，组织成员关系在正式 IAM 夹具中先建立、再签发会话，不扩大办理或消费 Permission。当前授权查询须准确合并三种来源，全部记录按直接接收主体筛选；逐项撤销个人／部门来源不能误删项目组来源，个人和组织 Deny 分别解除，最后一个 Grant 撤销后仍保留 Deny-only 解除入口。另以夹具已有的租户管理员独立执行成员查询／结束命令，通过正式 IAM API 依次结束消费 User 的部门和项目组关系，不创建含受限 IAM Permission 的自定义角色：每次变更后旧 Access Token 在 AuthContext 和 Manager 预览均须返回 401；同一账号经正式登录取得当前凭据后，退出部门仍可由项目组读取，退出最后一个组织则拒绝读取。身份、Tenant Membership 和四项消费 Permission 不变，当前来源随成员关系减少，组织 Grant 及直接历史保留，不能把成员退出实现为全组撤权。每个阶段均与真实 Manager 预览对照，旁观 User 和相邻表始终拒绝；失败或中断按本轮全部接收主体清理，不能只清个人 Grant。凭据只保存在 owner-only 临时文件和进程内存，不进入报告；同一场景还保持真实 Console／Manager 浏览器会话打开，在两次成员退出后通过页面重读触发既有 401 静默刷新：每次只轮换一次 Refresh Cookie，Console 与 iframe 的身份和新 Token 收敛，保留同一 iframe、路由和资源选择，不重复登录或误跳页面级 Forbidden；仍有项目组来源时继续显示两行夹具数据，最后一个来源消失时显示数据项级拒绝并清除旧行。控制协调只传本轮标识和阶段，不传 Token；原始 Playwright 输出及失败附件留在 Secret 目录，公开报告只保留状态与计数。此成员退出阶段不包含业务批准；Catalog 批准在后述独立阶段验收，其他引擎不在本 suite 范围内。

本 suite 的消费、办理、业务确认和组织维护身份均须使用当前 Tenant 的功能角色分配；AuthContext 中每条角色 Scope 必须精确为当前 `tenant_id` 的 `tenant`，缺失、跨 Tenant、Platform 或已退役的 Department / Project Group Scope（包括遗留字段）均拒绝进入验收。组织事实仍从独立 `organization.departments` / `project_groups` 核验，退出成员前后角色与功能 Permission 不变，不能用删除组织投影或扩大功能权限替代组织来源判定。

同一 suite 复用已有业务确认 User 验证“有数据 Grant、无读取功能权限”的反向门禁，不新增账号或功能角色。该 User 的当前 AuthContext 须精确保持原 Catalog 确认权限，不包含 `manager.data_item.read`；办理 User 只向其显式签发本轮 PG 单表限时 Grant。正式签发历史在读取前后均须证明同一 Grant 当前有效且完整绑定 DataItem，Manager 真实预览仍返回 `403/permission_denied`，且响应仅含错误、不泄露数据或元数据。拒绝不能通过自动撤销 Grant 或伪装成源规则／Security 拒绝实现。验收后显式撤销该 Grant 并核对历史；任一阶段失败仍由原有全接收主体清理路径回收，不改变账号功能权限、不借用其他账号凭据。

Catalog 的既有 PostgreSQL 门禁另经真实 HTTP 路由验证集合功能 Permission 与资源范围独立：同一组 Tenant 功能 Permission 下，当前项目组成员可以访问集合，退出后集合列表／详情不可达，集合及成员条目事实仍保留；部门目录可见性独立限制集合内条目，失去部门成员关系不删除集合条目。缺少功能 Permission 时，即使仍是成员也不能读写。该层只组合真实 Catalog PostgreSQL 与受控 AuthContext fixture，不代替真实 OAuth 和 PG 源内容读取的 T4。

### 依赖故障、批准方式与内容变化

PG Hosted 部署必须启动 Security，并将其纳入同一构建版本的 Ready 核验；Security 先于 Manager 启动。新测试 Tenant 在服务启动后创建时，须在第一次 Meta 扫描之前，经共享 `online-api.wait_manager_read_boundary` 对正式 Manager 引擎读取接口有界等待首次保护投影同步，并核对精确目标引擎。仅初始化中的 `security_protection_required` 可等待；其他授权拒绝、异常响应或超时立即失败，不改生产同步周期。源数据未授权必须在保护前置条件已满足后由 System Grant／Deny 链路拒绝；`security_protection_required` 不得作为未授权验证通过，也不能通过跳过保护、补写 checkpoint 或扩大消费权限绕过此依赖。

PG 同一 suite 另覆盖 Meta 事实依赖短暂离线与恢复：只在 disposable Hosted 部署通过标准生命周期停止／启动 Meta，不改变源表、DataItem 边界、IAM 权限或凭据。已有 Grant 且无 Deny 时，事实查询与 Manager 读取须明确返回依赖不可用，不回退原生读取，也不伪装未扫描；离线期间可对已知授权目标建立 Deny。恢复后不重扫，数据项身份、批准摘要与原 Grant 历史不变，原 Deny 仍阻止实际读取；显式解除后方可由原有效 Grant 读取，最后撤销并清理。故障操作有 Hosted 准入、超时、真实监听及进程身份验证；失败时仍尝试恢复 Meta 并清理本轮规则。此项是事实依赖可用性验收，不计为同身份组成边界扩大或列授权验收。

PG 业务批准沿用同一 suite，在上述阶段完成后，对此前未授权的相邻单表显式初始化 Catalog 批准要求。隔离部署增加 Catalog，仍不启动 Asset／Portal 或扩展其他引擎。独立业务负责人仅具备目录读取、盘点、编目和共享确认权限；办理 User 另具备目录读取、盘点与独立办理权限，消费 User 的权限保持不变。使用正式基础扫描变化自动建档、编目责任、共享边界核对、业务确认与办理 API，经 Catalog／System 各自 OAuth 身份自动受理和签发；验收脚本不持有机器 Token、不直接写批准或 Grant。仅业务确认时实际读取仍拒绝，签发后核对相同 DataItem 指纹、边界、接收方、期限及唯一签发历史，并由 Manager 读取确定性数据；同参重试不重发、续期或复活撤销。Deny 优先、解除及撤销继续复用 System 的同一路径，旁观 User 始终不能读取。所有写入编号在发送前登记；失败、中断也按本轮两个目标清理规则，并随 Hosted 生命周期销毁账号及目录事实。此阶段补充业务批准闭环，不把只读签发历史当作实际访问证据。

Catalog 可选依赖的故障验收复用上述 PG 业务 Grant、同一消费凭据及单一 Hosted 故障协调器：标准停止 Catalog 后，Manager 仍能凭原 Grant 读取，System 签发历史和精确目标的业务批准要求不变。新的人类办理请求须明确返回模块／代理不可用；对无授权旁观账号尝试直接批准须因批准方式不符而拒绝，不能由失联自动降级或补权。Catalog 离线期间仍可建立 Deny、解除并撤销原 Grant，实际预览逐步验证拒绝、恢复与最终拒绝；恢复 Catalog 后同参重放原已签发请求不得复活撤销，新失败请求不得产生受理或签发。停止／恢复均核验真实监听、同构建新进程及其他 owner 未重启，失败仍恢复并按预登记编号清理。不重扫、不切换批准方式、不新增角色；不将未受理的新请求与停机前已受理、可沿原窗口续办的请求混淆。

PG 显式批准方式切换沿用同一 suite，只为隔离办理夹具增加独立更新 Permission，不改变消费及确认权限。对业务 Grant 生效的单表验证 `catalog v1 → independent v2 → catalog v3`：无更新权限不能切换；切换不改既有 Grant、期限和已受理原请求，也不自动给旁观账号补权。旧版本的新直接批准及旧版本切换须明确冲突；新版本直接批准可显式授予旁观账号该表读取权，返回业务批准后该 Grant 仍有效，但新的直接批准被拒绝。同模式更新不推进版本，已签发原命令只恢复原历史；该账号的临时 Grant 撤销后再次拒绝读取，因此“旁观账号始终拒绝”仅适用于未显式获权的阶段。新 Catalog 办理若携带旧版本，可按既有提交前持久化协议先返回 pending，但不得受理、签发或自动替换版本；后台核清须关闭原编号，同参恢复仍为 closed。全过程使用真实 Manager 预览及 System 历史，不重扫、不改本地账号，失败仍回收本轮全部来源。

PG 正常内容变化继续使用该 suite 的同一普通表及消费凭据：Business 隔离夹具仅执行固定的行新增、更新、删除与基线恢复，不增加平台写权限或访问个人业务库。每次变化后只对该表执行 `basic + force` 扫描，核对 Meta ID、fingerprint、授权边界和原 Grant 历史不变；有效 Grant 可由 Manager 读到变化后的确定性内容，Deny 存在时仍拒绝，显式解除后恢复读取。撤销 Grant 后再次改变内容、基础重扫及重放原命令均不得恢复读取；旁观账号与相邻表始终拒绝，最后恢复源基线，失败或中断仍回收规则并销毁本轮容器。该场景是 single 数据项的内容更新验收，不计为同身份组成边界变化、列授权或 multi／whole 验收；同身份变边界的 Grant／Deny 匹配继续由已有 System PostgreSQL 判定层测试覆盖。

### 授权工作区与办理身份

成员退出场景保留的组织 Grant 属于该阶段的必要验证事实，不能假设后续列表只有个人来源。工作区场景开始前须复用同一生命周期的收权与残留核验，撤销本轮尚有效的个人／组织来源并解除本轮 Deny，保留全部签发与撤销历史；核验归零后才签发工作区预登记的单表 Grant。前置清理失败即停止，不进入浏览器或新增 Grant。最终清理仍覆盖本轮全部编号，不得为满足列表计数删除历史、改变成员退出规则或忽略其他来源。

该场景的浏览器变更检查按已核实的 API 语义区分请求：精确目标引擎的 `POST /catalog/children` 是资源树读取，不计为授权写入；此场景其他非 GET 引擎请求仍全部进入变更检查。不得用“所有 POST 都是写”误判选择器，也不得扩大排除范围以漏掉 Grant、Deny、批准要求或委托操作。原有导航零写入及最终仅撤销预登记 Grant 的断言保持不变。

PG 授权工作区浏览器验收复用同一 Hosted suite、隔离表与正式登录入口。办理夹具组合既有“数据授权办理员”内置角色，获得引擎、资源树、批准要求和三类接收候选的只读查询权限；不把不可自定义的权限塞入自定义角色，不增加消费账号权限或办理账号的数据读取权限。三个互斥视图须保持同排；新增授权的搜索／树选择只形成草稿，不写批准或 Grant。当前授权同时验证表名输入、树叶精确过滤、接收方类型与具体账号过滤及来源展开；全部记录保留有效、撤销与到期语义。脚本预登记单表限时 Grant 后，办理账号在真实 System 页面撤销，当前列表应移除来源、全部记录保留原编号及撤销状态，同一消费浏览器凭据重新读取 Manager 时应拒绝并清除旧行。浏览器不继承 API Token，办理与读取分别登录；私有输出与凭据留在 Secret 目录，公开证据仅含身份引用、状态、计数和核实后的页面截图。失败仍由原有编号清理路径回收，不操作个人开发部署；确定性 runner 通过不等同于该新增真实浏览器 T4 已通过。

统一“数据授权办理员”内置角色同时承载直接批准和业务确认后的人工办理，PG 夹具的这两项业务办理依赖（`catalog.entry.read`、`system.engine_access_fulfillment.create`）必须来自正式内置角色，不能重复塞进补充自定义角色。权限目录由 `make test-authorization` 校验；前向迁移、原角色分配保持、已分配主体授权版本推进、旧会话回收及重复启动不再变更由 `make test-system-iam-postgres SYSTEM_IAM_POSTGRES_TEST_ARGS="--package migration --test unified-data-authorizer"` 验证，既有全量 IAM PostgreSQL 门禁自动发现这些测试。该角色组合不替代业务确认、批准方式和引擎范围检查，不产生数据 Grant 或委托。

## enterprise-catalog-publishing

### 发布、生命周期与共享受理

1. Host Gate 全量启动 System、Gateway、Meta、Catalog、Asset 和 Portal，并通过 `business/scripts/online-engine-fixture.sh` 幂等准备 `public.addp_online_catalog_fixture`。
2. 真实 User Access Token 先经 System AuthContext 验证 Tenant 和精确 Permission，所有业务请求只经 Gateway，不直连 owner 或直接 SQL。
3. suite 触发 Meta 扫描，以 DataItem fingerprint 等待唯一 CatalogEntry 自动建档；首跑可使用预置 Domain、Department 和当前 User 将永久 fixture 初始化为 `curated`。
4. 后续运行对同一 CatalogEntry 执行临时编目并在 `finally` 恢复原完整聚合；以 CatalogEntry UUID 创建 AssetComponent，发布后由 Portal 返回同一身份，并通过 AssetCategory 目录树和分类子树列表发现该 Asset；真实浏览器随后打开同一分类页，确认目录名称和唯一 Asset 卡片。
5. 每轮 Asset 经 `published → offline → deleted` 正式生命周期清理；suite 先确认空 AssetCategory 已从 Portal 目录树消失，再删除 Asset-owned 目录，双方 GET 404 与 Portal Asset 404 共同证明零临时残留。

企业资源目录发布类 T4 使用同一永久 PostgreSQL Engine Instance 及其 owner 生命周期入口创建的稳定表 `public.addp_online_catalog_fixture`。专用环境必须预置可引用的 Standard Domain 和 Department；首次运行可将该永久数据源对应的 `discovered` CatalogEntry 初始化为稳定 `curated` fixture，后续运行必须在验收后恢复其编目聚合。同一 suite 必须重复执行真实 Meta 扫描并证明 fingerprint 与 CatalogEntry UUID 幂等，验证 `inventory` / `governance` 视图、治理覆盖率固定维度和精确来源身份解析；真实浏览器使用同一专用 User 登录 Console，验证覆盖率页、目录详情与 Domain / Department / Engine 名称选择器，并将浏览器 warning/error 计入失败。每轮创建的 Asset 和 AssetCategory 必须经正式 API 下架、删除并证明零残留；不得直接 SQL 清理。

浏览器同时以该次登录得到的 User Token 读取当前 CatalogEntry 和本轮已经生成的精确共享确认，不创建额外账号、决定或授权。技术来源在 1440px、900px 下核对接口返回的引擎名称/类型、数据项名称/类型和完整路径，验证双列宽度、长指纹省略、悬浮/聚焦全文、Tab 移出关闭及刷新恢复；这些布局和提示断言与 Console 的受控夹具 T3 共用同一测试 helper。共享历史核对同一确认的接收方姓名、返回的可选账号编码及“当前账号”标记，刷新后仍一致；候选另行核对姓名和登录名，只读选择当前账号而不提交业务命令。登录和匿名初始化诊断复用既有浏览器 helper，首次匿名 Refresh 401 单列且最多一次，认证消费开始后的 API 失败仍使验收失败。浏览器报告使用唯一 `addp.enterprise-catalog-publishing-browser/v3` 契约，必须包含来源展示、两种视口、刷新及当前账号断言，并绑定本轮确认编号；缺项、错误布尔类型或新增共享命令均使验收失败。确定性报告校验通过不代表专用 Runner 的真实 T4 已执行。

该 suite 同时在上述专用 Catalog fixture 上验证 `curated → deprecated → curated`，以及已弃用阶段的责任子资源更新。使用现有专用 User 增加或移除可选技术负责人，使责任集合发生实际变化；不为验收新增账号、部门或赋权。断言移交仍保持弃用、业务定义、语义、可见范围设置和来源身份，撤销弃用不恢复认证，旧版本请求返回 `409 catalog_entry_version_conflict` 且无副作用。成功和失败路径都经正式 API 恢复完整编目聚合并重新读取核对；写响应丢失时先读当前状态，不重试原命令，恢复失败使整个门禁失败。审计和并发版本不回滚，跨部门移交后的可发现范围及权限交集继续由 Catalog T2 验证，不以单账号 T4 冒充。

该 suite 还验证普通只读共享的正式准备、真实双服务 OAuth 反查与首次受理。专用 User 必须是 fixture 的当前业务负责人，显式具备共享确认、独立办理和批准要求初始化／读取 Permission，并由管理员预置当前有效的引擎管理委派；测试不自动赋权或创建委派。专用部署须配置独立 `SYSTEM_SERVICE_CLIENT_SECRET`，未配置在生命周期启动前拒绝验收，不改变普通部署允许留空的 Ready 边界。只为上述精确稳定表通过正式 API 初始化尚不存在的 Catalog 批准要求，已有独立批准模式拒绝而不覆盖；不可变业务决定、已核清的办理记录与 System 回执属于专用 Tenant 的长期审计事实，单列证据，不按临时资源删除。正式请求显式限时十分钟，办理窗口仍从首次受理起最多五分钟。同编号换用途或批准要求版本须返回 `409 catalog_sharing_decision_conflict`，拒绝后原决定／原回执必须不变；不新增决定或办理编号。此拒绝允许产生操作审计，不能以场景预期数量代替数据库计数验证。同参重放必须保持完整绑定、受理时间及截止时间不变；调用方丢弃已提交响应后恢复只证明调用方边界，不冒充 Catalog→System 网络中断或进程重启。人类 Token 访问机器反查／受理接口必须拒绝；`pending`、绑定错误或恢复失败不能计为通过。受理不等于 Grant 写入或实际可读，本 suite 不验证或创建源访问 Grant。

### OAuth 自动签发的只读观察

企业目录发布的 `enterprise-catalog-publishing` 沿用专用 macOS profile：正式 User 发起共享受理后，生产 Catalog 通过自己的 OAuth 服务身份自动签发。验收脚本不借用该身份，System owner 的现有 Online 测试夹具仅以只读可重复读事务核对精确 Tenant、Engine、请求编号的受理、Grant 和唯一签发成功审计；原参重试后再次核对签发时间与审计次数不变。该观察模式只允许回环 `addp_online`，禁止初始化身份、执行迁移或写入，不是人类 API、Catalog Grant 副本或访问裁决。确定性协议与准入测试归 `make test-online-runner`，真实 PostgreSQL 查询及只读拒写归现有 `make test-system-iam-postgres`，完整 OAuth 链路仍须在现有手工 T4 suite 真实执行后才能计为通过。

## workbench-service-consumption

1. Host Gate 全量启动 System、Gateway、Service、Workbench 和 Console；`business/scripts/online-workbench-mysql-fixture.sh` 使用外部环境变量启动 `business-mysql`，重建仓库既有 `customers + orders` 确定性数据并创建仅有 `SELECT` 的专用账号，同时为 Playwright 安装专用 Chromium。
2. 专用环境长期预置指向该账号的 MySQL Engine Instance，身份由 `ADDP_ONLINE_WORKBENCH_MYSQL_ENGINE_ID` 提供；suite 不创建、修改或删除 Engine Instance。
3. 两个真实 User Token 先各自校验 AuthContext：现有专用 User 必须属于同一 Tenant、不含管理员角色且只具备 Service/Workbench 场景权限；独立 `ADDP_ONLINE_TEST_TENANT_ADMIN_ACCESS_TOKEN` 必须属于同一 Tenant 的 User、含 `tenant.administrator` 角色且具备当次 API 消费方生命周期所用权限。两者都不得是个人会话或平台管理员 Token。
4. 非管理员 User 的所有平台操作只经 Gateway：检测 SQL 输出契约，发布私有主 Query Service `commerce-order-analysis` 和同契约未授权 Query Service `commerce-order-analysis-denied`，读取主服务 Consumer Descriptor，创建 Data Application 草稿并执行查询。SQL 只 JOIN 既有表并排除姓名、邮箱、电话和地址；MySQL 将 `BOOLEAN` 暴露为 `TINYINT`，publisher 只把已知语义的 `active_customer` 显式发布为 `bool`，Service 再按冻结契约归一化 `0 | 1`。
5. Tenant Administrator 只经 System 正式 API 创建一个仅授权主 Query Service 的 API 消费方及一枚凭据。凭据只保存在 suite 进程内存，不写入报告或日志；用它调用主服务必须返回 200，调用未授权服务必须返回 `403 api_consumer_service_denied`，调用 `/api/v1/system/tenant/api-consumers` 必须返回 `401 api_consumer_control_plane_denied`。删除 API 消费方后，旧凭据必须在 45 秒内收敛为 `401 api_consumer_credential_invalid`。
6. API 层还要验证 `order_no` cursor、五类动态筛选、decimal/boolean/timestamp/null、完整有限 CSV，以及无 SpatialInfo 时 Map 不可用。浏览器使用非管理员专用 User 登录 Console 并核对浏览器 AuthContext 与 API User 身份一致，在同一应用草稿中依次打开两个 Component 的正式编辑器，验证 Table 两行结果、Chart canvas 和无空间契约下不存在 Map。
7. 浏览器经正式 Service API 更新主服务的公开默认字段策略以改变 `contract_fingerprint`；刷新同一应用后 Component 编辑器必须显示契约变化告警并禁用预览查询。API 层同时确认已保存快照仍持有旧指纹，不增加 Workbench 执行 API 或测试旁路。
8. `finally` 只按本轮捕获 ID 删除 API 消费方及其级联凭据、未发布 Data Application 和两个 Query Service，并逐项验证 404 或凭据失效；Fixture 和全套 ADDP 再由 Host Gate 统一停止。最终发布运行态由 Outdoor 双服务场景验收，不能为自动清理增加已发布应用强删旁路。

### API 消费方身份与数据面

API 消费方数据面边界由 `workbench-service-consumption` 复用同一 Business MySQL Fixture 和临时 Query Service 验收，不另建平行 suite。该场景必须分离两个真实 User Token：非管理员 Token 只负责 Service / Workbench 发布与消费，专用 Tenant Administrator Token 只负责 API 消费方与凭据生命周期。suite 通过正式 API 创建一个只授权主 Query Service 的 API 消费方，并必须同时证明：已授权服务返回 200；同 Tenant 未授权 Query Service 返回 `403 api_consumer_service_denied`；任一 `/api/v1/*` 控制面路由返回 `401 api_consumer_control_plane_denied`；删除 API 消费方后，旧凭据在 Gateway 30 秒正缓存对应的 45 秒有界收敛窗口内返回 `401 api_consumer_credential_invalid`。报告、日志和错误不得包含完整 API Key，每轮必须按捕获 ID 删除 API 消费方、其级联凭据、Data Application 和两个临时 Query Service，并验证零残留。
