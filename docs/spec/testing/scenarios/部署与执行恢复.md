## workflow-runtime-health-recovery

入口为 `make test-online ONLINE_SUITE=workflow-runtime-health-recovery`，部署仅使用 GitHub Hosted `ubuntu-24.04` x86_64 一次性环境，由 `online-hosted-workflow-health-gate.sh` 复用共享 Hosted 生命周期。删除该 suite 的自托管 profile、私有 macOS 工具发现及外部永久身份依赖，不要求用户提供机器或配置密钥，不操作个人开发部署。首次正式通过前仅手动触发 Online T4 workflow。

正式入口构建并启动同源码的 PointCloud、Model3D、Document 产品镜像，保留镜像默认启动命令；System、Gateway 使用既有精确进程入口。System owner 的 Online 身份夹具创建非默认 Tenant，观测使用 Develop Service Principal 的租户 descriptor，登记使用各 Runtime 自身的 Service Principal。凭据随机生成，存于不归档的仓库外 owner-only 目录；不运行业务转换、不扩大到其他 Runtime、浏览器或发布认证。

每轮先验收三个 Runtime 首次启动即缺少必需工具的自注册。标准产品构建完成后，仅在本轮测试镜像层移走 PDAL、IfcConvert、LibreOffice，保留产品默认启动命令、运行用户及其他文件；不在产品代码中增加启动钩子。全新 System 中须无对应 Engine，三个 Runtime 的首次健康响应均为 `503/unhealthy`，仅各自目标依赖不可用；由正常启动路径自动登记为同租户 `offline/active`，不能用验收脚本调用登记来代替。等待初次登记健康探测完成后，逐个恢复工具，仅由 System 周期探测自动转为 `online`；恢复期间其他实例保持应有状态，Engine ID、生命周期、容器和进程身份均不变。报告单列三组 `startup_cycles`，不能沿用此前仅运行中故障的通过结果。

镜像层的恢复记录只包含工具内容与权限；容器启动后先将备份实体化为本容器私有文件，再建立 inode 基线，恢复核对该基线。容器尚未建立基线就失败时，清理入口仍须从镜像记录完成恢复。测试镜像与原产品镜像一起由现有生命周期清理。

首次启动恢复完成后，再依次验收原有的运行中 PDAL、IfcConvert、LibreOffice 缺失场景：

1. 故障操作前核对容器 ID、当前 Run ID、suite 标签、镜像和默认入口；只处理容器内固定工具。先将镜像层的工具实体化为容器私有文件，保持内容与权限，以获得稳定 inode，再建立基线。缺失通过原子移走目录项注入，不修改宿主机工具、权限或共享安装。
2. 检查 `503/unhealthy` 与对应 `required=true, available=false`，其他依赖事实不变；不调用连接测试或登记，等待 System 周期探测将同一实例置为 `offline`，另外两个实例继续 `online`。
3. 通过共享 `register_after_listener` 和真实 Runtime 登记函数，在 503 时仍取得 `202` 和同一 Engine ID；等待登记后的健康请求完成再恢复工具，避免把登记探测计为周期恢复。
4. 恢复后检查健康事实完全回到基线，仅等待周期探测恢复 `online`。Engine ID、`active` 生命周期、Runtime 容器 ID/PID/启动时间/重启次数，以及 System/Gateway PID 和启动时间不变。

容器内写前恢复日志支持场景超时或进程被杀后的幂等 `--restore-only`；恢复核对原 inode、权限、SHA-256，遇并发替换拒绝覆盖并使验收失败。Host Gate 在停止隔离服务前再次恢复工具，随后移除本轮容器与镜像仓库、测试镜像、Infra 容器/网络/卷和凭据目录，并核验零残留。缺失的容器只可在恢复清理入口中按未创建处理，正式场景不得跳过。报告只保留安全状态与文件摘要，不保存令牌或密钥。

确定性入口 `make test-workflow-runtime-health-online-runner` 进入既有 `make test-online-runner` 与平台 CI，覆盖真实测试子进程 SIGKILL 后的文件恢复、拒绝覆盖、镜像/容器所有权、Hosted 失败清理和登记一致性；System owner 的最小身份声明测试同次运行。确定性通过不等于真实 Hosted T4 通过。

## module-registry-recovery

唯一部署 profile 为 GitHub Hosted Ubuntu x86_64，由 `scripts/test/online-hosted-module-registry-gate.sh` 复用公共 Hosted 生命周期。先启动 System，通过 System-owned 夹具准备当次非默认 Tenant 与三员账号，执行真实密码/MFA 登录取得只用于实例读取的 Platform 会话，再停止 System。凭据只在观察子进程中加载。节点 IP 明确注入回环地址；退出销毁应用、Infra、卷和凭据并核验零残留。

正式进程编排顺序为 分别对 Manager（Go）和 Copilot（Python）执行 Backend → System → Gateway → 停止 System → 恢复 System。验证模块自身 Ready、直连入口、同 instance_id 自动注册和恢复，以及 Gateway 路由随租约出现、消失和恢复；再验证幂等、多实例、注销和零残留。进程级证据不得用注册 API 或人工重启替代，消费方页面与业务 Engine 恢复仍归独立 consumer-engine-recovery。

模块注册与恢复类 T4 必须使用正式进程入口至少证明：

1. 业务模块先启动、System 后启动时，自身就绪的模块先为 Alive/Ready，注册状态为 starting，直连公开入口可用；System 启动后同一 `instance_id` 进入 registered。
2. System 与业务模块先启动、Gateway 后启动时，Gateway 在首个完整快照后进入 Ready 并建立路由。
3. System 运行中断后，本地依赖正常的 Backend 保持 HTTP Ready 并报告 recovering，Worker/Scheduler 停止领取新工作，Gateway 在已有租约过期后返回 503。
4. System 恢复后实例无需重启即重新注册，Gateway 自动恢复路由，不需要前端人工刷新或二次点击。

仅启动 Probe Server 并直接调用 System 注册 API 可以验证租约与路由算法，但不能替代上述进程级就绪与恢复证据。

专用 Runner 可以通过受 `ADDP_ONLINE_HOST=1` 强制保护的精确进程参数复用正式开发构建与进程入口，以控制业务 Backend、System 和 Gateway 的真实启动顺序；该入口不得成为日常开发的第二套模块依赖路径。精确停止必须先验证受管 PID 的进程身份。观察器统一使用显式模块名和 Backend URL，报告为 `addp.module-lifecycle-process/v2`，包含 `module` 与 `backend` 身份；阶段名使用 `backend-*`。Copilot 还须证明未认证业务请求仍返回 401。其源码身份由干净部署中的模块和 Common Python 归档 SHA-256、提交与启动部署时间注入健康响应。

每个进程阶段都必须把 Liveness、Readiness、业务门禁、实例身份和 Gateway 路由投影写入仓库外证据目录。

### 第二阶段声明发布验收

以下为[发布契约](../../api/健康与平台控制面.md#第二阶段模块声明发布契约)的正式验收标准。复用 GitHub Hosted 独占部署和正式进程。观察用 Platform 身份、模块专属发布身份及运行身份分别取证，报告保留请求状态、版本和必要字段，不记录凭据。

| 场景 | 操作 | 通过条件 |
| --- | --- | --- |
| Catalog 已预建且禁用 | 管理员在无 Catalog 实例时预建 `enabled=false` 的定义。记录 ID、版本 1 和空的发布时间。发布者读取基线，按版本 1 完整发布，再分别用版本 2 和过期版本 1 提交相同内容。 | 首次 PUT 返回 200，ID 不变、版本为 2、发布时间有值、仍禁用。正确版本重发保持版本和时间，过期版本返回 `409 resource_version_conflict` 且无副作用。零实例时声明可读。启动 Catalog 后即使实例获有效租约，Gateway 仍无 Catalog 路由。 |
| System 已 Ready、尚未发布自身声明 | 从空库走正式启动顺序，在部署发布前观察 System 的 Ready、进程标识和注册表。经已就绪的 System 取得发布 Token，发布其自身声明；继续观察原进程和租约。 | 发布前 `/health/ready` 返回 200，发布基线为 404，无 System 实例。首次发布返回 201。同一进程无需重启就完成登记，随后心跳推进租约截止时间。Ready 持续可用。通过注册表核验自登记，System 的 Ready 响应无需增加注册状态字段。 |
| 旧 Manager 在新版声明发布后重连 | 让遵循第二阶段实例协议的正式旧 Manager 登记并记录 `instance_id` 及启动时间。中断其与 System 的连接，确认进入 `recovering`，待旧租约到期后核验 Gateway 已摘除该实例。由发布者提交旧进程也能兑现、但内容可区分的新版模块声明，记录新版内容、发布时间、版本和管理员启用意图，然后恢复连接。 | 同一进程以原 ID 和启动时间重新登记并续租。重新读取定义，新版声明、发布时间、版本及启用意图均与重连前一致。Gateway 按有效租约恢复可选实例。另用旧混合请求携带模块级字段须返回 400，定义保持原值。 |

契约测试另覆盖跨模块发布、运行身份尝试发布、发布者尝试登记或启停均返回 403，以及并发首建、发布与启停争用同一版本时只有一个变更提交。正式 Manager／Copilot 进程继续验证先启动后补发声明、本地 Ready、同进程恢复、租约到期摘路由和清理零残留。报告分别记录确定性测试与 Hosted 正式进程结果。

## Catalog 服务发现试点验收

本节是[第三阶段 Catalog 服务发现契约](../../api/健康与平台控制面.md#第三阶段-catalog-服务发现契约)的待实施验收标准。现有 `module-registry-recovery` 验证 System 租约。未来试点需分别记录可控时钟的契约测试、隔离 Kubernetes 集群的正式进程验收和默认部署回归。

| 场景 | 通过条件 |
| --- | --- |
| 绑定与写入权限 | 只有部署管理员能改绑定。Catalog 进程和发布身份不能改绑定，System 发现身份不能写集群或修改模块声明。错误集群、namespace、Service UID、Slice owner、控制器、端口或未就绪端点均不能产生路由。启用发布未就绪地址的 Service 不可用。 |
| 双副本、就绪失败与滚动退出 | 使用真实 System、Gateway 和两个 Catalog Pod。通过 Gateway 的实际请求和各副本访问记录确认两者都承接流量。使一个 Pod 的自身就绪探针失败，再单独验证滚动退出。Gateway 收到并应用摘除后，新请求只到剩余副本。以 Pod UID 核对替换和 IP 复用，旧端点不再被选用。 |
| 管理员禁用与 Service 重建 | Ready Pod 存在时禁用 Catalog，Gateway 应用快照后返回 503。另在启用状态下删除 Service 并用同名新 UID 重建，即使旧 System 租约未到期也不能选出端点。管理员重绑后，经完整核对才恢复。 |
| 两段链路分别断连 | 分别阻断 Kubernetes 到 System、System 到 Gateway 的连接。记录核对开始时刻、截止时间、快照 revision 与实际转发。最后确认仍有效时可选，恰到截止时即不可选，池空返回 503。用可控时钟覆盖精确边界、部分列表、旧快照重发和过时事件；正式进程须实际观察两段断连各自导致摘除。 |
| 续期与恢复 | 地址不变时连续跨越一个 30 秒窗口，已送达的新核对结果应维持服务。断连到期后恢复链路，并另行验证 System 重启；只有完整核对后的新有效快照能恢复转发。对齐 Pod UID、快照和真实请求结果。 |
| 进程身份与观测 | 在同一 Pod 中重启 Catalog 进程，Pod UID 不变，`instance_id` 改变。Ready 只看自身条件，响应省略 `registration_state`。发现数据未产生实例心跳、主机绑定、CPU/RSS 零值或虚假告警恢复，历史观测仍归原进程。如试点要求保留进程告警，另核对遥测的新旧进程身份与实测样本。 |
| 本地与 Compose 回归 | 分别用原启动入口且不提供 Kubernetes 配置或凭据。核对模块声明、Catalog 实例登记、心跳推进租约和原有进程观测，Gateway 随租约到期摘除、重新登记后恢复，其他模块继续按原发现来源路由。 |

正式进程报告须关联部署制品、Service 和 Pod UID、探针结果、System 核对时间与快照、Gateway 选路时间和实际命中的副本。双副本场景的结论仅覆盖 HTTP 路由。Worker、Scheduler 领取语义以及 Catalog 后台任务的多副本生产验收留待后续。

## Transfer 后台工作资格试点验收

本节为待实施的验收标准，范围是独立 bounded Worker 与 Backend 内嵌 Scheduler。两者分别按[治理资格](../../api/健康与平台控制面.md#transfer-后台工作资格试点)和 [Transfer 事务与在途任务规则](../../tasks/Transfer同步执行.md#bounded-领取与定时触发)取证。下述 A、B 使用相互独立的 bounded 任务，B 在 A 运行期间也满足业务领取条件；用空闲执行槽和到期且授权有效的计划观察停领与停触发。

| 场景 | 通过条件 |
| --- | --- |
| 冷启动、确认范围与进程重启 | 无确认时，B 保持 `pending` 且 attempt 未增加，到期计划未创建 execution、未推进 `next_run_at`。其他模块、其他职责或先前进程的确认都不能开放入口。同 Pod 重启取得新 `instance_id` 后，须重新取得匹配确认。 |
| 两段治理链路分别失联 | 让 A 先取得租约，保持执行库及业务依赖可用，分别中断治理平台到 System、System 到试点进程的链路。确认未到期时仍具备资格，到期即停止发起新操作；B 无新 attempt，计划仍到期。旧确认重发或仅重连均无效。A 可用原 attempt 续租并完成，新确认送达后恢复相应职责。 |
| 单独撤销一种职责 | 撤销 Worker 资格后，即使原确认尚未到期，空闲槽也不能领取。合格 Scheduler 仍能创建 `pending`。另在 Scheduler 已扫描某项、尚未发起事务时撤销其资格，该项无新增 execution、原到期时间不动，合格 Worker 仍可消费已有 `pending`。两种撤销后均验证迟到的旧确认无效。 |
| 并发触发与已发出事务 | 恢复两个合格的 Scheduler 副本，同时处理同一到期项，只产生一次有效触发，`pending` 和 `next_run_at` 一并提交。分别在领取和触发事务已发出、结果未返回时关闭入口，核对最终提交或回滚的数据库事实。后续候选不得发起新事务，结果不确定的事务不得盲目重放。 |
| 正常退出与突然退出 | 分别向 Worker 和承载 Scheduler 的 Backend 发出 SIGTERM，入口先关闭，迟到确认不能恢复领取或触发。在途工作走 Transfer 停机流程，不能只凭信号记为取消。另行强制终止持有 A 的 Worker，接替者不能在原租约有效时夺取 A；过期后按 Transfer 规则收敛为失败，恢复治理不会产生新的运行尝试。 |
| 单独丢失执行租约 | 保持治理资格有效，仅使 A 的执行租约失效。用原 attempt 和 token 做迟到续租、进度和终态写入，全部被拒绝。核对数据库终态及目标端实际写入，确认没有自动重放。 |
| 本地与 Compose 回归 | 分别用原入口启动，无企业凭据。Worker、Scheduler 仅按各自进程的 System 注册状态领取和触发。验证首次注册、进入恢复状态、重新注册三个阶段，同时核对既有执行租约及定时触发事务。 |

可控时钟测试覆盖资格截止前、相等、截止后及迟到确认。正式试点在隔离部署中使用真实 Transfer 进程、治理来源和 PostgreSQL，分别记录撤销或截止时刻、操作发起时刻、进程身份与职责、到期项、execution ID、attempt、租约到期和数据库提交结果。token 只在受控验证中比对，报告仅记录是否匹配。契约测试、正式故障验收和默认部署回归分别记录结果。continuous 的领取、恢复与退避另行验收。

## consumer-engine-recovery

该独立 suite 负责验证全量重启后的浏览器首次就绪与 Engine Instance 动态恢复，不扩大 `module-registry-recovery` 的边界：

1. Host Gate 使用正式全量启动入口，保留 Manager、Service Backend 和三个被测 Frontend 的初始 PID。
2. 专用 Runner 环境预置一个长期存在的 PostgreSQL Engine Instance；仓库外环境文件提供 `ADDP_ONLINE_TEST_ENGINE_ID`、`ADDP_ONLINE_TEST_ENGINE_NAME`、`ADDP_ONLINE_TEST_ENGINE_PORT`、`ADDP_ONLINE_TEST_ENGINE_USER`、`ADDP_ONLINE_TEST_ENGINE_PASSWORD` 和 `ADDP_ONLINE_TEST_ENGINE_DATABASE`。这些变量只属于 Online 业务 Fixture，不得复用平台数据库变量。
3. `business/scripts/online-engine-fixture.sh` 是该物理 Fixture 的唯一生命周期入口，要求 `ADDP_ONLINE_HOST=1`，不读取、不生成 `business/.env`，并只操作 `business-postgres`。
4. Browser 使用 `ADDP_ONLINE_TEST_USER_USERNAME` 与 `ADDP_ONLINE_TEST_USER_PASSWORD` 走真实 Console 登录；API 控制面继续使用同一专用 User 的 `ADDP_ONLINE_TEST_USER_ACCESS_TOKEN`。测试必须确认两种会话属于同一 Tenant User 且具备 `system.engine.read`、`system.engine.execute` 和被测页面的读取权限。
5. 同一 Browser Context 依次首次打开 `/configuration`、`/manager/data-explorer` 和 `/service/query-services`，每页只允许一次导航；页面自身的首次请求成功即为通过，不允许 reload、刷新按钮或失败后重试导航。
6. Manager iframe 保持打开时停止 Fixture、调用 Engine test API 写入 `offline`、等待页面轮询显示不可用；恢复 Fixture 并再次写入 `online` 后，同一 iframe 自动恢复。整个阶段被测消费方 PID 不变。
7. `finally` 路径必须恢复 Fixture 与 Engine `online` 状态；Host Gate 随后停止 Fixture 和全套 ADDP，并把浏览器报告、截图、PID 快照和 Online JSON 报告统一写入仓库外 Artifact 目录。

Engine Instance 是永久身份，因此 suite 禁止按 Run ID 创建后删除测试引擎，也禁止以墓碑、名称前缀清理或直接修改 System 数据库作为收尾方式。

消费方与 Engine Instance 动态恢复类 T4 必须另外证明：全量重启后真实 User 在同一 Browser Context 首次打开 Console 原生页与模块 iframe 不需要 reload、手工刷新或二次点击；Engine Instance 经正式连接检测 API 从 `online` 转为 `offline` 再恢复 `online` 时，已打开页面自动更新，相关 Backend 与 Frontend PID 保持不变。Engine Instance 是永久身份，此类 suite 使用专用 Runner 预置的长期 Engine Fixture，只控制隔离物理端点的连通性，不得按 Run ID 创建、删除 Engine Instance 或清理墓碑。物理 Fixture 必须由 owner 的 Online 专用生命周期入口管理，要求 `ADDP_ONLINE_HOST=1`、不读取仓库内 `.env`、不复用平台 `POSTGRES_DB`，并在成功、失败和中断路径恢复连接观测后停止。

## compose-public-origin

生产 Compose 单入口 T4 使用 Hosted disposable profile：在全新 Runner 上用正式构建入口生成 System Backend、Gateway、Meta Backend、Manager Backend、Transfer Backend、Orchestrator Backend、Console、System Frontend、Meta Frontend、Manager Frontend、Transfer Frontend、Orchestrator Frontend 和 Nginx 镜像，以 `addp-platform` project 启动这些真实容器及当次 Infra。Meta、Manager、Transfer 与 Orchestrator Backend 向 System 自注册，Gateway 从有效 Backend 实例发现对应的 `/api/v1/:module/*`；模块 Frontend 由 Nginx `/module-ui/{frontend}/` 转发，Console 的 `/{module}/` 地址继续由根入口处理。内置 Runtime 属于独立 `addp-runtimes` project，不参与公开入口的业务断言；同一 Runner 额外启动一个真实 GeoPython Runtime 和一个真实 Business MinIO，验证 `addp-runtimes`、`business` 的独立生命周期、Compose project 标签、网络归属和宿主机端口边界。

对外 Nginx 使用非默认回环端口；仅 T4 Compose 覆盖文件允许 System Backend 和 Gateway 额外发布回环诊断端口供通用构建身份预检，正式 Compose 保持只有 Nginx 对外发布。未参与验收的 Nginx 静态 upstream 只提供当次网络名称占位，不模拟参与断言的服务。业务断言必须从公开入口检查 Console、System、Meta、Manager、Transfer、Orchestrator Frontend 及其构建资源，并使用当次一次性 Tenant 的零权限、只读、仅创建 User 验证 System AuthContext 的精确 Permission 集合；System、Meta、Manager、Transfer、Orchestrator 的 API 分别验证未认证 401、无权 403，以及已授权读取。Meta、Transfer、Orchestrator 的写入入口还需用无效请求体证明仅创建权限可越过功能守卫但被参数校验拒绝，且只读账号不能写入；System Role Assignment 详情需证明本租户授权可读、另一租户的授权 ID 返回 404。无效请求体不得创建业务资源。测试还需核对 System 对外 origin、Meta、Manager、Transfer 和 Orchestrator Backend 的就绪与内部地址以及容器实际端口；全部退出路径分别销毁 Runtime、Business MinIO、平台应用、占位容器、镜像仓库和 Infra，核对四个 project 的容器、网络、卷零残留。Transfer Worker 的数据执行和 Orchestrator 的 DAG 执行分别由 owner T4 验收，不以本套入口检查代替。[Hosted T4 run 36141592135](https://github.com/pampa0629/addp/actions/runs/36141592135) 已通过此前的 Transfer 覆盖验收；扩展后的权限矩阵及 Orchestrator 覆盖须在更新提交上手工运行成功后才能计为通过。

同一 `compose-public-origin` suite 必须通过真实生产构建的 Console、Manager iframe 和 `/module-ui/manager/` 独立界面验证 Browser AuthSession。System owner helper 只把既有只读 User 的登录凭据输出到 owner-only 凭据目录；浏览器通过正式登录 UI 建立会话。测试在浏览器中暂时持有共享刷新锁以确定性地制造两个顶层页面同时请求续期，不拦截或伪造任何 HTTP 响应，必须证明只有一次真实 Refresh 请求、HttpOnly Cookie 轮换、三个界面令牌收敛、独立页刷新不额外续期，以及独立页退出后 Cookie 清除和 Console 同步退出。报告和截图不得包含凭据；浏览器证据缺失、身份不匹配或多次续期均使该 suite 失败。确定性验证沿用 `make test-online-runner`，真实部署沿用该 suite 的 Hosted T4 Job。 报告另行记录续期是否保留原 iframe 实例；该诊断不代替未保存业务状态的验收，出现重建时必须在交付中明确说明。

同一套 Hosted 验收也启动生产 Workbench、Portal 和 Asset Backend，以及 Workbench 和 Portal Frontend。Portal 必须以 Compose 内部地址向 System 注册。两个全新浏览器上下文分别从带 query 和 fragment 的 `/data-apps/:id` 与 `/portal/home` 开始，使用同一个当次临时 User 和正式 TOTP 登记。密码后要求 MFA，验证 TOTP 后必须在两个 Tenant Membership 中显式选择，选择前不得签发会话或发出业务请求。选定后核对完整回跳、AAL2、HttpOnly Refresh Cookie 和整页刷新后的身份。随后关闭 Chromium 并确认原浏览器连接断开，用同一临时配置目录启动新进程，验证已有 HttpOnly Cookie 仍有效、一次正式 Refresh 恢复同一 Principal／Tenant／Membership 和 AAL2、完整原始地址及运行页面，且未重新提交密码、MFA 或租户选择。再打开另一模块，核对复用恢复后的会话。每个浏览器配置只存放于当轮私密目录，用例结束关闭浏览器并删除配置目录，报告记录重启、恢复、Cookie 轮换和配置删除结果。Portal 首页必须通过真实 Asset 接口返回 200。Workbench 用当次随机且不存在的应用 ID，必须从真实 Runtime API 得到应用不存在的 404 并显示运行页错误。两条路径的报告只记录 Run ID、公开 origin、所选 Tenant 和断言结果，任何一条缺失都使现有 Hosted Job 失败。

手工调度 `compose-public-origin` 可选 `public_origin_published_workbench`。该场景在同一生产 Compose 入口启动 Service Backend，复用当轮独占 PostgreSQL 只读夹具。Engine 由专用登记 User 通过正式 API 注册。原 MFA User 使用限定的 Service 和 Workbench 权限，通过正式 API 创建私有 Query Service 并发布仅含一个 Table Component 的临时应用。应用默认筛选 `B`，发布预设 `person-a` 筛选 `A`。浏览器在回跳、刷新及跨模块会话复用时均核对完整预设链接、应用发布版本、Runtime 200、Service 实际请求中的等值筛选和表格中与查询结果一致的唯一一行 `A`。结束时先用正式 API 下线应用并验证 Runtime 拒绝运行，删除临时 Service，再由 Hosted 生命周期销毁全部容器、网络、卷和凭据。已发布应用的记录随当轮平台库销毁。定时调度仍运行上述不存在应用的原场景。

同一手工场景启动 Catalog 和 Standard Backend。System 夹具创建临时部门，独立临时 User 使用必要的业务域、Catalog 和 Asset 权限，为当轮已发布的 Workbench 应用治理对应 CatalogEntry，并上架一条数据应用资产。原 MFA User 在 Portal 首页核对真实 API 返回的唯一资产与页面卡片的 ID、名称和描述，覆盖登录回跳、刷新及跨模块会话复用。结束时通过 Asset API 下架，在 Portal 核对详情不可见且首页恢复空态，删除资产并确认管理接口返回 404。临时业务域、部门、目录记录和账号随当轮独占数据库销毁。

### 读取权限与历史保留验收

权限边界扩展沿用同一手动 Hosted T4，不新增认证旁路或生产故障开关。System IAM 夹具提供同 Tenant 的普通读者，其 Orchestrator 读取与 Monitor 读取分别赋权；父执行及嵌套编排可读，Meta 子执行不授予读取权，树仅显示两层编排，子执行详情、树和事件返回 404。独立 Tenant 管理员仅通过正式 IAM 接口撤销该读者的 Orchestrator 角色分配；先验证旧令牌失效为 401，再经正式登录取得同 User、Membership 和 Tenant 的新令牌，确认 Monitor 权限仍在、父执行详情、树及事件均为 404。外部代理只中断本轮 Meta 的 execution-read-scope GET 连接，由真实 Monitor 返回 503 execution_owner_unavailable 且不含执行数据；恢复连接后核对完整执行树不变。凭据与代理控制只存于不归档的 owner-only 临时目录，业务报告不保存角色分配编号，未知撤权结果不重试，失败路径释放故障并由标准生命周期销毁部署。确定性验证归入现有 make test-orchestrator-online-runner 与 make test-online-runner / 平台 CI；扩展首次真实通过前不计为 T4 已通过。

### 删除任务定义后的历史

已删除任务历史扩展沿用同一 `orchestrator-execution` 手动 Hosted T4。所有已知父子执行收敛为终态后，经正式 API 删除本轮任务定义；Orchestrator 用任务详情确认删除前存在、删除后 404，Meta 用正式扫描任务列表确认删除前存在、删除后消失。删除前后逐项比较成功与失败执行的 Monitor 概览、安全步骤、错误类别、父子树和根执行事件，以及 Owner 已保存的步骤事实，禁止用当前定义重建历史。删除后再次验证跨 Tenant、缺少 Owner 权限、父可读而 Meta 子不可读；随后正式撤销父读取分配并重新登录，确认保留的历史仍受当前权限限制。删除请求结果未知时不重试，不报告清理成功；定义删除后任一历史或权限断言失败，整套验收仍失败，执行历史由既有 Hosted 生命周期销毁。报告只记录检查名、定义删除数量及已有安全执行身份，不保存前后快照或原始步骤结果。共享 Online HTTP 客户端按调用方声明校验对象或数组响应，Meta 列表明确采用数组契约，不修改公开 API。确定性用例复用 `make test-orchestrator-online-runner`，共享客户端通过 `make test-online-runner` 扩散验证，现有平台 CI 自动覆盖，无需新增登记；实现变更后须重新运行真实 T4 才能计为通过。

### 一次性执行与专业入口边界

一次性执行权限扩展沿用同一 `orchestrator-execution` 手动 Hosted T4。通过现有 Meta 手动扫描 API 创建无任务定义的真实执行，核对 `source_task_id` 为空、发起主体与当前普通 User 一致、执行收敛成功，Monitor 详情、树和过程事件可读且只含安全投影。System 正式 IAM 夹具增加同 Tenant 的另一普通 User，仅授予 Meta 扫描历史与 Monitor 执行读取权限；先证明该读者能读取已有任务定义的扫描执行，再确认其列表及总数不包含其他 User 的一次性执行，详情、树和事件返回无执行数据的 404。发起人的列表仅增加该执行；跨 Tenant 与缺少 Owner 权限时仍不可见。未知创建结果不重试，已知一次性执行必须收敛为终态，历史随 Hosted Infra 销毁。报告仅增加安全执行 UUID、事件数量、身份权限摘要和闭合检查名，不保存配置、主体编号或响应快照。复用既有 `make test-orchestrator-online-runner`、`make test-online-runner` 与 Platform CI 登记；公开 API、平台进程日志和审计路径不变，真实验收证据见下段。

历史 IAM PostgreSQL 缺口以实际执行的 T2 任务证据闭合；此前取消不计为通过，后续 IAM 实现、迁移或门禁变更仍须独立验证，不扩张执行读取隔离范围。历史结果与范围限制见[其他验收证据索引](../验收证据索引.md#addp-验收证据索引)。

范围限制：上述一次性执行隔离结论针对 Monitor 通用诊断，不能替代 Meta 专业入口的直接隔离证据。模块归属、任务历史、本人一次性执行与 TaskProvider 独立机器读取沿[Meta 专业读取契约](../../tasks/执行监控.md#meta-专业执行读取与响应)；直接入口的回归分工见[Meta 标准门禁](../Owner补充门禁.md#meta-扫描与结果归属门禁)，固定版本的实际覆盖与未覆盖项见[Meta 历史证据](../evidence/资源读取与预览历史证据.md#meta-专业扫描读取--t4)。

### 派发故障

故障扩展使用同一手动 suite：Hosted 包装器为真实 Meta 配置只解析到本机的临时网络别名，将 Orchestrator 与 Monitor 的 Meta HTTP 请求交给本轮代理；代理转交真实请求并保存安全身份与计数，可丢弃已接受请求的响应或暂缓状态读取。

代理不替代 Owner 业务实现、不生成虚构执行身份，生产服务不增加故障接口。响应丢失必须先向真实 Meta 转交一次请求；进程崩溃须待父编排持久化 `waiting` 后，用 pidfd 锁定本轮 Backend，在 UID、可执行文件和部署 Secret 目录核验通过后发送 SIGKILL；替代实例通过 `scripts/dev/start.sh -orchestrator` 启动。

两类故障分别核对 `dispatch_uncertain` 与租约到期后的 `lease_expired`；断言还须证明依赖未派发、已接受请求只有一次、子执行身份真实、Monitor 投影安全及父终态下步骤仅为最后记录。

所有退出路径清理测试代理和本轮网络别名，再由既有生命周期销毁应用与 Infra；新增检查只有在更新提交的 Hosted T4 真实通过后才能计为通过，不自动加入夜间任务。确定性入口为 `make test-orchestrator-online-runner`，由 `make test-online-runner` 和平台 T0/CI 唯一聚合；登记检查同时核对三个 owner 测试文件，禁止遗漏。历史结果与范围限制见[其他验收证据索引](../验收证据索引.md#addp-验收证据索引)。

### 续租故障

续租故障扩展仍归同一手动 Hosted suite：HTTP 代理等待真实子执行状态请求，在父编排已持久化 `waiting` 和真实 Meta 子执行身份后，仅在当次独占 `addp_online` PostgreSQL 安装指定父 UUID 的续租拒绝触发器，以非事务序列核对真实续租错误。触发器只拒绝该父执行处于 `running` 时 `lease_expires_at` 的续租更新，不改写执行事实、不影响其他模块或终态收敛。

必须同时证明监督器取消在途请求、父 execution 在有效租约下以 `coordinator_stopped` 失败收敛并保留 `running + waiting` 最后记录、依赖不派发、真实子 execution 成功且只有一次提交。夹具以 pidfd 证明原 Backend 自行退出，不发送崩溃信号；故障解除并经标准生命周期启动身份不同的替代进程后，父终态、步骤和事件仍须一致。

准入核对 Hosted 私有目录、当次容器 ID、Compose owner 和数据库凭据；禁止在个人或共享本地数据库安装触发器。临时触发器、函数、序列和 schema 清理失败即失败，所有退出路径仍销毁 Hosted Infra。

T0/T1 沿用 `make test-platform`、`make test-orchestrator-online-runner` 与 `make test-online-runner`，现有 Online/Platform CI 自动覆盖，无新增 workflow 或生产接口。历史结果与范围限制见[其他验收证据索引](../验收证据索引.md#addp-验收证据索引)。

## quality-dynamic-binding

### Bounded Worker 恢复时间专项

2026-10-28 用户确认在同一 Hosted 生命周期增加 `quality_case=bounded-recovery`，只运行新增恢复场景，不重复动态绑定业务验收。先通过 `make test-quality-online-runner` 的确定性门禁，再手工运行一次 GitHub Hosted；未经实际执行与清理通过不得记为 T4 通过。

专项仍由普通执行 User 经 Gateway 创建规则、方案及 execution。只在当次 disposable 部署启用已有的两个 Quality Worker 副本、每副本一个执行槽及 30 秒租约配置，生产默认值不变。故障工具每次核验 Linux、Hosted 标记、`addp_online`、私密目录、进程 UID／工作目录／可执行文件／启动标记，并以 pidfd 固定当次 Worker。崩溃场景仅 SIGKILL 本轮 Quality Worker 后经标准启动入口补回缺失副本；旧运行体场景仅 SIGSTOP／SIGCONT 两个已核验的本轮副本，真实等待租约过期，不改时钟、数据库状态或租约字段。

目标 SQL 由当次业务源的事务锁暂缓；公共过程事件表的短事务锁只用于在新 claim 提交前稳定观察恢复后的持久 `pending`。锁不修改数据，租约恢复和再次 claim 均由真实 Worker 完成。私有只读探针只读取本次 User 创建的同租户、同方案、同 execution UUID；核验 UUID／created_at 不变、pending 的 started_at 为空、再次 claim 写新开始时间并递增 attempt／更换 token，以及旧 Worker 恢复后被当前租约围栏拒绝。lease token 仅在内存比较，报告只保存相等／不等结论；不能新增产品调试 API、暴露 token 或以直接改库替代状态推进。

通过正式 Quality／Monitor 详情和过程事件核对恢复排队、当前 attempt 开始／结束时间及运行耗时，最后核对原业务源数据不变。旧运行体场景用真实 Worker 的迟到 heartbeat 被拒绝和新 attempt 状态不被覆盖证明 fencing；任意终态迟到写回的全组合仍以 Common／Quality T1/T2 为证，不把这一场景外推为每种终态写回的真实故障验收。每次暂停前保存私有恢复记录，正常、异常、超时或外层退出先恢复仍属于本轮的暂停进程、释放锁，再沿原 Hosted 路线销毁应用／业务源／Infra／身份和凭据；恢复、业务断言或零残留核验失败均使门禁失败。仅限 Quality bounded，不推广为其他 Owner、continuous、HA 或 T5。

### 过程事件与保留边界

Quality 过程事件扩展复用同一套件和普通 User，经 Gateway 读取 Monitor 的 execution events，核对单条启用规则对应的 started、progress 与真实终态、attempt、百分比、顺序、游标和保留窗口；闭合事件字段之外的参数、业务值和授权信息均使验收失败。Online 分发器要求 Monitor 就绪，Hosted 生命周期显式配置 MONITOR_URL。确定性反例进入既有 make test-online-runner，新增 Quality PostgreSQL 用例按 TestIntegrationPostgres 前缀自动发现；本扩展未经 Hosted 真实执行时不计为 T4 通过。
