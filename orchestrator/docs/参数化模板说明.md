# Orchestrator 执行参数与上游输出绑定

本篇说明编辑器操作与绑定示例。能力与端口契约见 [TaskProvider 规范](../../docs/spec/tasks/TaskProvider接口.md#capabilitiestask_capabilities)，保存与执行规则见[编排定义规范](../../docs/spec/tasks/编排与调度.md#orchestrator-规范)，模块验证与历史证据从 [Orchestrator 开发与验证](../CLAUDE.md#开发与验证)进入。

## 用户可见模型

Orchestrator Step 的执行参数只有三种来源：

1. **工作流配置**：使用 owner 模块任务定义中已保存的当前值，Step 不保存覆盖字段。
2. **执行时指定**：Step 保存显式值，每次执行该编排都用此值覆盖工作流配置。
3. **上游输出**：Step 从直接依赖步骤已声明的稳定输出中选择一个值。

用户不编辑整份 JSON，也不手写输出路径。Orchestrator 从具体任务详情的 `execution_contract` 渲染输入控件，并从依赖任务的 `output_schema` 生成可选输出。

## 画布端口与连线

编排画布同时表达纯控制依赖和参数传值，但两者不得混为同一种连线：

- 纯控制连线只表达等待成功；参数连线从输入／稳定输出端口传值并隐含 `depends_on`。端口生成、单输入绑定、共享依赖和去重规则沿上述正式契约。
- 创建参数连线必须原子地写入参数绑定并补充 `depends_on`；删除同一任务对之间的最后一条参数连线时移除对应 `depends_on`。如仍需纯执行顺序，用户必须明确创建控制依赖。
- 参数表单和画布连线是同一份 `parameters` 事实的两个编辑入口，必须双向同步，不得各自保存一套绑定状态。

资源对象按正式契约使用一个逻辑端口；`locator`、`geometry_column` 等内部身份或自动派生字段不拆成独立端口。

资源参数的保存形状由 `input_schema` 决定，不能按资源选择器控件推断：字符串参数直接保存 locator 或上游输出模板；对象参数在其 `locator`（已有资源）或 `parent_locator`（创建目标）字段中保存绑定，并保留对象内的其他配置。

控制线与参数线共同遵守[编排定义规范](../../docs/spec/tasks/编排与调度.md#orchestrator-规范)的 DAG、全依赖成功及 v1 串行边界；画布分叉不表示并行执行或 OR 触发。

## 内部序列化

上游输出绑定在编排定义中的唯一内部格式为：

```text
{{step_id.outputs.declared.path}}
```

例如，Develop 工作流任务 `produce` 声明保存算子 `save_3` 的资源输出后，下游资源参数可以保存为：

```json
{
  "load_1": {
    "source_resource": {
      "locator": "{{produce.outputs.save_3.resource.locator}}"
    }
  }
}
```

该字符串是内部持久化格式，不是面向用户的表达式语言。不得支持 `{{step_id}}`、`{{step_id.result}}`、`metadata.result`、数组下标或任意响应字段路径，也不得在普通字符串中做局部插值。

## 保存校验

保存时沿[编排定义规范](../../docs/spec/tasks/编排与调度.md#orchestrator-规范)核验有效能力、具体任务契约、直接依赖、声明输出路径与目标类型；默认值、显式值及不完整对象的处理统一见 [Orchestrator 默认值校验](../../docs/spec/tasks/TaskProvider接口.md#orchestrator-默认值校验)。任一校验失败即拒绝保存，不保留旧模板兼容路径。

## 执行流程

1. 执行前重取全部具体任务的最新 `execution_contract` 并复核编排，再按 DAG 拓扑顺序串行推进。
2. 当前步骤从直接依赖响应顶层 `outputs` 解析绑定，与 Step 显式值组成部分 `parameters`；按上述默认值校验规则严格验证真实值，再调用 owner。
3. owner 使用最新契约执行最终领域校验，未覆盖字段仍用其保存配置；覆盖仅作用于本次 execution，不修改任务定义。

路径不存在、来源没有返回声明输出、类型不匹配或契约已变化时，当前步骤和父编排必须失败，不能把缺失值转成 `null` 或回退到任意结果字段。

## 稳定输出边界

稳定输出的声明、持久化位置与安全响应投影沿 [TaskProvider 标准响应体](../../docs/spec/tasks/TaskProvider接口.md#标准响应体)。数据资源优先使用 ResourceLocator，例如：

```json
{
  "outputs": {
    "save_3": {
      "resource": {
        "locator": "addp://engine/3/path/public/roads?type=table",
        "type": "table"
      }
    }
  }
}
```

进程内 DataFrame、运行时句柄、临时文件、任意 execution metadata 和日志都不是稳定输出，不能作为跨任务参数来源。

### 质量方案的运行时表输入

Quality 的 `quality_plan` 通过 `execution_contract` 为每个方案公开表别名，输入固定为 `table_bindings` 对象；不在编排器中另建质量规则或引擎配置。例如方案声明 `orders`，前序任务 `materialize` 声明稳定输出 `outputs.target.locator` 时：

```json
{
  "table_bindings": {
    "orders": "{{materialize.outputs.target.locator}}"
  }
}
```

此值是该质量步骤的 `parameters`，也可以直接填地区表的 ResourceLocator。别名默认值与实际目标合并、授权、冻结统一见[质量方案规范](../../docs/spec/addp数据质量规范.md#2-方案和规则)，不回写方案。当前仅支持 PostgreSQL；一次检查的全部表（包括外键参照表）须属于同一引擎实例，跨地区复用可选择不同实例。

方案与完整目标集合的执行去重、跨目标并发见[执行与授权](../../docs/spec/addp数据质量规范.md#4-执行与授权)，工单按范围闭环和 `passed` 输出见[结果与问题](../../docs/spec/addp数据质量规范.md#5-结果与问题)。这里的并发属于不同 Quality 执行范围，不改变 Orchestrator v1 的 Step 串行规则；error 级规则未通过仍使质量步骤失败并阻断后继。

参数和编辑器回归从上述模块验证入口进入；Quality 真实动态绑定、权限、失败阻断与清理由 [Quality 测试与 CI](../../quality/CLAUDE.md#测试与-ci)说明。本文示例及确定性测试不代表真实链路已验收，历史结果仅覆盖其固定版本与实际场景。
